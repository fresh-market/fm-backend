# 선착순 쿠폰 부하 시험

요구사항이 정한 조건은 **재고 10,000장에 20,000명이 60초에 걸쳐 몰리는 것**이다.
이 폴더의 파일들이 그 조건을 손으로 다시 만들 수 있게 한다.

```
seed-members.sql    가상 회원 2만.  id 1000001 ~ 1020000
seed-coupon.sql     선착순 쿠폰 1장.  coupon_id 900001, 총량 10,000
seed-dummy-data.sql 정합성 검증용 유저 100만 + 발급 이력 300만.  이 시험과 별개다
mint-tokens.py      회원 토큰 2만 장 + 관리자 토큰 1장을 찍는다
issue.js            k6 시나리오
reset.sql           회차 사이에 상태를 되돌린다
```

---

## 시나리오 설계

`issue.js` 가 무엇을 흉내 내는지부터 정한다. 이 선택이 결과 해석을 좌우한다.

### VU 하나가 사람 하나다

```js
executor: 'ramping-vus',
stages: [{ duration: '60s', target: 20000 }, { duration: '30s', target: 20000 }],
```

`ramp-up` 은 **전체 사용자 수에 도달하기까지의 시간**이다 (JMeter 의 정의와 같다).
그래서 60초 뒤에 VU 가 20,000 이 되고, 그때까지 초당 333명씩 들어온다.

VU 는 뜨자마자 자기 몫의 요청을 한 번 쏜다. 그래서 **VU 가 생기는 속도가 곧 도착률**이다.

```
20,000명 / 60초 = 333명/초 = 333건/초
```

### 한 사람이 한 번만 쏜다

```js
const index = exec.vu.idInTest - 1;        // VU 번호 = 사람 번호
if (exec.vu.iterationInInstance > 0) {     // 이미 쏜 VU
  sleep(1);
  return;                                   // 다시 안 쏜다
}
```

일반적인 부하 시험은 `요청 -> sleep -> 요청` 을 반복한다. VU 가 **사용자 세션**을 흉내 내고
`sleep` 이 생각하는 시간이기 때문이다. 지속 부하를 잴 때는 그것이 맞다.

**선착순은 모델이 다르다.** 사람이 한 번 누르고 끝이지 90초 동안 매초 누르지 않는다.

| | 지속 부하 (일반) | 일회성 쇄도 (여기) |
|---|---|---|
| VU 하나가 | 사용자 세션 | **사용자 한 명** |
| 몇 번 하나 | 계속 반복 | **한 번** |
| 총 요청 | 시간에 비례 | **20,000건 고정** |

반복하면 측정도 깨진다. 같은 사람이 두 번째로 쏘면 `uk_mc_coupon_member` 가 두 장을 막아
**같은 순번을 200 으로 다시 돌려준다.** k6 의 발급 카운터가 부풀어 DB 행 수와 어긋난다.

남은 `sleep(1)` 은 발사와 무관하다. 이미 쏜 VU 가 바쁜 루프로 생성기 CPU 를 태우는 것을 막는다.
VU 는 살아 있어야 연결이 유지되고 VU 수도 20,000 까지 올라간다.

### 왜 반복 번호가 아니라 VU 번호인가

전에는 `exec.scenario.iterationInTest`(전역 반복 번호)로 토큰을 골랐다. 그러면 먼저 뜬 VU 가
다시 돌면서 **뒤에 올 사람 몫의 토큰까지 가져간다.** 램프가 끝나기 전에 2만 건이 소진된다.

실제로 그렇게 돌렸을 때 10초에서 25초 사이에 끝났다 (2026-08-30). `ramp-up 60초` 가
성립하지 않았고, 같은 설정의 두 회차가 364 건/초와 2,000 건/초로 갈렸다.

`exec.vu.idInTest` 로 고르면 VU 1번은 언제나 토큰 1번만 쓴다.

**대신 VU 를 20,000 보다 줄이면 시도하는 사람 수도 함께 준다.**
요구 조건을 재는 회차에서는 `VUS` 를 덮어쓰지 않는다.

### 503 만 다시 쏜다

응답에 따라 사람의 행동이 갈린다.

| 응답 | 다시 쏘나 | 왜 |
|---|---|---|
| 200 | 안 쏨 | 받았다 |
| 409 소진 | 안 쏨 | 최종이다. 다시 해도 같다 |
| **503 혼잡** | **쏜다** | 응답이 "잠시 후 다시 시도해주세요" 라고 말한다 |
| 422 / 404 | 안 쏨 | 자격이 아니다 |
| 연결 실패 | 안 쏨 | 생성기가 모자란 것이라 재시도로 덮으면 그 한계가 지표에서 사라진다 |

기다리는 시간은 서버가 정한다. `GlobalExceptionHandler` 가 503 에 `Retry-After: 1` 을 실어 준다.
임의로 더 빨리 쏘면 서버가 요청한 배압을 무시하는 셈이다.

**`MAX_ATTEMPTS` 는 5 다 (첫 시도 + 재시도 4회).** 실제 사람이 몇 번쯤 다시 누르다
포기하는지는 재 본 적이 없어 정한 값이다. 회차 기록에 함께 적어야 비교가 된다.

재시도를 넣으면 `http_reqs` 가 20,000 을 넘는다. 사람은 여전히 20,000명이고 시도가 늘어난다.

대신 k6 와 DB 의 불일치가 줄어든다. 503 을 받았지만 그 티켓이 큐에 남아 결국 써진 사람이
다시 쏘면 `coupon_already_issued` 로 잡힌다. **이 값이 크면 요청 예산이 실제 처리 시간보다
짧다는 뜻이다.**

### 셋을 정상 응답으로 등록한다

```js
http.setResponseCallback(http.expectedStatuses(200, 409, 422, 503));
```

409(소진)와 503(혼잡)은 설계가 정한 정상 응답이다. 이걸 안 알려 주면 k6 가 둘을 실패로 세서
`http_req_failed` 가 뜻을 잃는다.

그래서 임계의 `expected_response:true` 는 **셋을 다 포함한다.** 성공만 재면 느린 거절이
지표에서 사라지는데, 사용자는 응답 코드를 모르고 기다린 시간만 겪는다.

## 왜 토큰을 미리 찍나

`AuthRateLimitFilter` 가 `POST /v1/auth/tokens` 를 **IP 당 분당 10회**로 막는다.
2만 명이 로그인부터 하면 그 필터에서 끝나고, 그 필터를 시험용으로 끄면 **정작 재려던 발급
경로가 아닌 것을 재게 된다.** 그래서 로그인을 건너뛰고 앱과 같은 서명 키로 토큰을 직접 만든다.

토큰의 모양이 앱과 어긋나면 2만 요청이 전부 401 로 돌아온다. 그것을 시험 당일에 알면 그 회차를
통째로 잃으므로, `LoadtestTokenMintTest` 가 이 스크립트가 찍은 토큰을 앱의 `JwtTokenProvider`
에 넣어 본다.

## 절차

### 1. 앱을 띄운다

```
SPRING_PROFILES_ACTIVE=local,coupon LOGGING_LEVEL_ROOT=WARN ./gradlew bootRun
```

**로그 수준을 반드시 낮춘다.** 로컬 프로파일은 root 가 DEBUG 이고 `HttpBodyLoggingFilter` 가
요청과 응답 본문을 남긴다. 그대로 재면 발급이 아니라 로깅을 재게 된다.

`coupon` 프로파일이 가상 스레드, 커넥션 풀 5, Redis 300ms 타임아웃, 회로 값을 건다.
그 값들이 이 시험의 대상이다.

### 2. 데이터를 넣는다

```
docker exec -i freshmarket-mysql mysql --default-character-set=utf8mb4 \
  -ufreshmarket -pfreshmarket freshmarket < loadtest/seed-members.sql
docker exec -i freshmarket-mysql mysql --default-character-set=utf8mb4 \
  -ufreshmarket -pfreshmarket freshmarket < loadtest/seed-coupon.sql
```

문자셋을 안 주면 확인 SELECT 의 한글 별칭에서 구문 오류가 난다.

### 3. 토큰을 찍는다

```
JWT_SECRET=<앱이 쓰는 값> python3 loadtest/mint-tokens.py
```

`loadtest/tokens.csv` 가 나오고, 관리자 토큰은 화면에 한 줄로 나온다. 그 토큰을 다음 단계에서 쓴다.

### 4. 이벤트를 연다

```
curl -X POST -H "Authorization: Bearer $ADMIN" \
  http://localhost:8080/v1/admin/coupons/900001/event:open
```

**이 호출이 Redis 카운터를 세운다.** SQL 로 `is_active` 만 켜면 카운터 없는 Redis 를 요청이
쳐서 시험이 통째로 "준비되지 않음" 으로 끝난다.

### 5. 돌린다

요구 조건을 재는 회차는 **아무것도 덮어쓰지 않는다.** 기본값이 곧 요구 조건이다.

```
k6 run loadtest/issue.js
```

```
VUS    20000   사람 수. 곧 동시 사용자 수
RAMP   60s     여기까지 올리는 데 걸리는 시간
HOLD   30s     램프가 끝난 뒤 유지하는 시간. 밀린 큐가 빠지는 것까지 본다
```

예비로 작게 볼 때만 줄인다. 다만 **VU 를 줄이면 시도하는 사람 수도 함께 준다.**

```
VUS=500 RAMP=30s k6 run loadtest/issue.js     # 500명만 시도한다
```

### 6. 확인한다

k6 요약만으로는 **몇 장이 실제로 나갔는지 알 수 없다.** 예산을 넘겨 503 으로 답한 요청도 그
티켓이 큐에 남아 나중에 써지기 때문이다. DB 를 봐야 한다.

```sql
SELECT COUNT(*) AS 발급행, MAX(issue_seq) AS 최대순번,
       MAX(issue_seq) - COUNT(*) AS 구멍, COUNT(DISTINCT member_id) AS 회원수
  FROM member_coupon WHERE coupon_id = 900001;
```

```
발급행 = 10000   재고만큼 나갔다
구멍 = 0         번호만 태우고 사라진 요청이 없다
회원수 = 발급행   1인 1매가 지켜졌다
```

앱이 낸 갈래별 건수는 관리 포트에서 본다.

```
curl -s http://localhost:8081/actuator/prometheus | grep coupon_issue_results_total
```

### 7. 되돌린다

```
docker exec -i freshmarket-mysql mysql --default-character-set=utf8mb4 \
  -ufreshmarket -pfreshmarket freshmarket < loadtest/reset.sql
```

그 다음 4번(이벤트 열기)을 다시 한다. `reset.sql` 이 `is_active` 를 내리는 것은 그래야 여는
API 가 Redis 를 다시 세우기 때문이다. 켜져 있으면 "이미 열렸다" 로 그냥 돌아가고 지난 회차의
카운터와 매핑이 그대로 남는다.

## 회차 기록 (로컬 리허설)

> **이 기록은 옛 시나리오 것이다 (2026-08-30 이전).**
>
> 그때는 VU 가 `요청 -> sleep(1) -> 요청` 을 반복했고 토큰을 전역 반복 번호로 골랐다.
> 그래서 먼저 뜬 VU 가 뒤에 올 사람 몫까지 가져가 램프가 끝나기 전에 2만 건이 소진됐다.
> **지금 시나리오로는 이 수치가 재현되지 않는다.** 설계가 왜 바뀌었는지는 위 "시나리오 설계" 에 있다.
>
> AWS 에서 요구 조건대로 돌린 기록은 `fm-infra` 의
> `docs/verification/선착순쿠폰_부하시험_기록.md` 에 있다.

**아래 수치는 용량이 아니다.** k6, JVM, MySQL, Valkey 가 16GB 한 대에서 CPU 를 나눠 썼다.
`coupon.md` 3장의 "재서 정할 값" 은 이 환경에서 정하면 안 되고, 부하 발생기를 다른 호스트에
두고 운영과 비슷한 DB 에서 다시 재야 한다.

**기계와 무관하게 유효한 것은 정합성이다.** 아래 세 회차가 그것을 보여 준다.

### 회차 1. VU 20,000 / ramp 60s

```
k6      요청 20,000.  발급 208, 혼잡 11,279, 연결 실패 8,513
        p95 53초
앱      congested-seq-unavailable 14,896
DB      발급행 2,198, 구멍 19, pending 1,019
```

**기계가 먼저 넘어졌다.** Redis 호출이 300ms 타임아웃에 걸리기 시작하자 순번 확보 회로가
열렸고, 그때부터 요청 대부분이 번호를 못 받고 잘렸다. 부하 발생기가 같은 CPU 를 먹은 몫이 크다.

읽을 것이 있다면 **회로가 설계대로 열렸다는 것**이다. Redis 가 느려질 때 요청이 예산 2초를 다
태우고 실패하는 대신, 회로가 빨리 끊었다.

### 회차 2. VU 500 / ramp 30s

```
k6      발급 10,000, 소진 4,287, 혼잡 5,607
        p95 2.06초
앱      issued 10,000 / sold-out 4,287 / congested-budget 1,990
DB      발급행 10,000, 최대순번 10,000, 구멍 0, 회원수 10,000
```

**재고 1만에 2만 명이 몰려 정확히 1만 장이 나갔다.** 순번은 연속이고 1인 1매도 지켜졌다.

`congested-budget 1,990` 이 이 설계의 대가를 숫자로 보여 준다. **예산 2초를 넘겨 503 을 받았지만
그 티켓은 큐에 남아 결국 발급된 요청**이 1,990건이다. 사용자는 실패로 들었는데 쿠폰은 받았다.
반대쪽(예산을 넘기면 순번을 반납한다)을 고르면 도착 순서가 뒤집히므로 이쪽을 골랐다
([coupon.md](../docs/coupon/coupon.md) 9장).

### 회차 3. VU 500 / ramp 30s, 같은 조건 재실행

```
k6      발급 9,928, 소진 4,048, 혼잡 5,903, 연결 실패 121, 예상 밖 0
        p95 1.86초
앱      congested 전부 seq-unavailable
DB      발급행 9,928, 최대순번 10,000, 구멍 72
Redis   pending 73, 확정 표시 없는 매핑 72
```

같은 조건인데 회차 2 와 다르게 무너졌다. **로컬에서 회차마다 결과가 흔들린다는 증거**이고,
그래서 이 환경의 수치로 값을 정하면 안 된다.

대신 여기서 **회수가 도는 것을 확인했다.** 구멍 72개는 번호를 받고 행이 안 들어간 요청들이고,
그 번호가 `pending` 에 묶여 있었다. 매핑이 없는 회원 100명이 소진 상태에서 두드리자

```
pending 73 -> 0
발급행 9,928 -> 10,000
구멍 72 -> 0
```

**회수는 소진 상태에서 요청이 올 때만 돈다.** 시험이 끝나 트래픽이 끊기면 그 번호는 묶인 채로
남고, 요청이 다시 오면 그때 풀린다. 3장이 "주기 배치가 필요 없는 이유" 로 적은 것이 이것이다.

### 회차 4~9. 무엇이 발급을 막는지 하나씩 껐다 (2026-08-30)

**여섯 회차를 같은 기계, 같은 조건(VU 20,000 / 재고 10,000)으로 돌렸다.** `issue.js` 가 VU 번호로
토큰을 고르도록 바뀐 뒤라 VU 를 줄이면 시도하는 사람 수도 함께 준다. 그래서 기본값으로만 돌렸다.

| 회차 | 바꾼 것 | p99 | 발급행 | 구멍 | seq-unavail | 연결 실패 |
|---|---|---|---|---|---|---|
| 4 | 기준 (`11bdb5a`) | 60초 | 1,908 | 488 | 16,858 | 11,659 |
| 5 | 같은 값 재실행 | 59.6초 | 196 | 1,016 | 23,486 | 13,434 |
| 6 | **회로만 끔** | 52.7초 | **5,513** | 2,307 | 9,735 | 11,226 |
| 7 | 느림 200ms + Redis 300ms | 52.6초 | 915 | 2,631 | 29,396 | 16,041 |
| 8 | 회로를 스타터로 이전 | 40.9초 | 1,782 | 2,631 | 32,799 | 6,018 |
| 9 | **Redis 500ms + 예산 30초** | **7.9초** | **10,000** | **0** | **1** | 9,062 |

**회차 9 가 요구를 처음으로 온전히 만족했다.** 발급행 10,000, 최대순번 10,000, 구멍 0, 회원수 10,000
이고 소진(409)이 938건 나왔다. 소진 응답은 재고가 실제로 다 나가야 나오는 것이라, 앞선 회차들은
소진 근처에도 못 갔다는 뜻이다.

#### 병목은 처리 능력이 아니라 앞단의 상한이었다

회차 9 는 90초에 1만 장을 냈다. **초당 109장이다.** 그 능력은 회차 4~8 에도 있었는데 쓰이지 못했다.
막은 것이 둘이다.

**하나는 순번 확보 회로다.** 회차 5 와 6 이 그것만 다르다. 같은 코드로 연달아 돌렸고 회로 스위치
하나만 껐는데 발급행이 196 에서 5,513 으로 갔다. **28배다.**

원인은 회로가 읽는 신호에 있다. 지연 하나에 Redis 건강과 이 JVM 의 GC 정지가 섞여 있는데,
정지가 104~330밀리초라 느림 기준 50밀리초를 늘 넘는다. Redis 가 멀쩡해도 정지 한 번이 그 사이의
호출을 전부 느린 것으로 만든다.

**다른 하나는 Redis 타임아웃이다.** 회차 8 과 9 사이의 차이가 그것이다(100ms -> 500ms). 순번을
못 받은 요청은 큐에도 못 들어가 쿠폰이 되지 않으므로, 이 값만이 발급량을 직접 바꾼다.
`seq-unavailable` 이 32,799 에서 1 로 떨어졌다.

DB 쪽 타임아웃은 발급량을 안 바꾼다. 예산을 넘겨 503 을 받은 요청도 티켓이 큐에 남아 결국
발급된다. 회차 6 에서 `coupon_issued` 3,270 과 발급행 5,513 의 차이 2,243건이 그것이다.

#### 회로 지표가 없어 여덟 회차를 헤맸다

`CircuitBreaker.of(...)` 로 만들어 레지스트리 밖에 있었다. 그래서 `SEQ_UNAVAILABLE` 이 회로 탓인지
Redis 탓인지 회차 8 전까지 구분할 수 없었다. 설정을 resilience4j 스타터로 옮기자 지표가 저절로
붙었고, 회차 8 에서 **32,799건 중 29,016건이 회로가 막은 것**이라고 처음 말할 수 있었다.

#### 이 수치를 그대로 쓸 수 없는 이유

**연결 실패가 6,018 에서 16,041 까지 흔들린다.** 그건 앱이 아니라 노트북이 낸 값이고, 회차마다
조건이 달랐다는 뜻이다. 그래서 회차 사이의 발급행 차이를 설정 탓으로만 돌릴 수 없다.

읽을 수 있는 것은 셋뿐이다. **회차 5 와 6 의 비교**(연달아 돌렸고 변수가 하나다), **회차 8 의
회로 거절 29,016건**(연결 실패가 가장 적은 회차인데 회로는 가장 많이 막았다), 그리고 **회차 9 가
요구를 만족했다는 사실**이다.

#### 회차 9 의 값은 운영에 못 쓴다

```
p99 7.9초    SLO 는 1초다
p95 6.72초
최대 46.5초
```

예산 30초라 요청이 거절 대신 끝까지 기다린 결과다. **처리량과 지연을 맞바꾼 것이고,** 이 교환이
운영에서도 필요한지는 로컬로 답할 수 없다. 로컬에서 Redis 500ms 가 필요했던 것은 k6 와 JVM 과
MySQL 과 Valkey 가 한 CPU 를 다퉜기 때문이다. 같은 VPC 의 ElastiCache 는 1밀리초 아래다.

**클라우드 회차에서 `seq-unavailable` 이 얼마나 나오는지가 그 답을 준다.** 거기서도 크면 타임아웃을
올려야 하고, 그러면 SLO 를 다시 정할지 재고를 덜 팔지 골라야 한다.

## 다음 회차에서 볼 것

이 환경에서 못 정한 것들이다. 부하 발생기를 분리한 뒤에 순서대로 옮겨 가며 잰다.

```
큐 상한         무한 -> 20000 -> 10000 -> 5000 -> 2500 -> 1000
플러시 스레드    1 부터 늘리며 큐 길이가 줄어드는지 본다.  풀이 5 라 그 위로는 커넥션을 못 얻는다
배치 윈도       1ms ~ 100ms
```

**`congested-budget` 과 `congested-seq-unavailable` 의 비율이 무엇을 조일지 알려 준다.**
앞이 크면 플러시가 못 따라가는 것이고, 뒤가 크면 Redis 쪽이다.
