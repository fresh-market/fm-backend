# 검증 워크플로

다섯 게이트가 각각 무엇을 언제 판정하는지를 한 장으로 정리한다.

설계 근거와 상세는 [qa-llm-verification.md](https://github.com/fresh-market/.github/blob/main/docs/software-quality/qa-llm-verification.md)에 있다.
이 문서는 그 설계가 실제로 어떻게 흐르는지를 보기 위한 참조용이다.

## 전체 흐름

```
                              개발자
                                |
                    +-----------+-----------+
                    |      코드 작성        |
                    +-----------+-----------+
                                |  git commit
                                v
     +======================================================+
     |  G-LOCAL           Claude, 로컬, 개발자 재량         |
     |  범위: push 하지 않은 커밋 (인자로 조절)             |
     +------------------------------------------------------+
     |  1. ./gradlew check    커버리지, 정적분석  -> 알림만  |
     |  2. LLM 판정           활성화 항목 전부    -> 알림만  |
     |  3. 기록 저장                                        |
     |     backend/docs/llm-review/                         |
     |     <계정>_<YYYYMMDD-HHMMSS>_llm-review.md           |
     +======================================================+
                                |  고침, 재커밋 (반복)
                                |
                                |  git push
                                v
     +======================================================+
     |  G-BUILD           Gradle, SonarQube, 자동           |
     +------------------------------------------------------+
     |  커버리지  service 패키지 메서드 100%                |
     |  정적분석  신규 Blocker 0건                          |
     |                                          * 병합 차단 |
     +======================================================+
                    실패 ------+------ 통과
                     |                  |
                 여기서 멈춤            v
                            +==========================================+
                            |  G-PR      gemini-2.5-flash, 자동        |
                            |  범위: PR 누적 diff (base...HEAD)        |
                            +------------------------------------------+
                            |  1단계  backend 250건        항상        |
                            |           |                              |
                            |           +- 응답이 온전한가?            |
                            |           |    아니오 -> 나머지 UNJUDGED |
                            |           v 예                           |
                            |  2단계  common+infra 214건   조건부      |
                            |                              비차단      |
                            +==========================================+
                                              |
                                        리뷰 코멘트
                                              |
                                          병합 후
                                              v
     +======================================================+
     |  G-RELEASE         배포와 시험 스크립트, 배포 직전   |
     |  RDS available / 대상그룹 healthy / 인증서 30일 등   |
     |                                          * 배포 차단 |
     +======================================================+

     +======================================================+
     |  G-AUDIT           주기별, 1시간부터 6개월까지       |
     |  기록 존재 확인 -> 티켓 생성              비차단     |
     +======================================================+
```

이 셋 말고 **레지스트리 검사**가 하나 더 있다.
문서를 고치고 `items.yml` 을 재생성하지 않은 PR 을 막는다 (`registry-check.yml`).
점검 항목 문서를 건드린 PR 에서만 돌고, 결정론적이라 차단한다.

**차단하는 것은 도구가 판정하는 게이트뿐이다.**
G-BUILD와 G-RELEASE는 결정론적이라 오탐이 없고, LLM 게이트는 재현율이 미측정이라 차단하지 않는다.

## 게이트별 검증 카테고리

### G-BUILD (도구, 차단)

| 카테고리 | 기준 | 판정 주체 |
|---|---|---|
| 커버리지 | `*.internal.service.*` 메서드 **100%** | Gradle JaCoCo |
| 정적 분석 | 신규 **Blocker 0건** | SonarQube |

`Blocker`는 프로덕션에서 애플리케이션을 망가뜨릴 높은 확률의 버그를 뜻한다. 병합을 막을 근거가 되는 것은 이 등급뿐이다.
`BLD-*` 10건이 이 설정 자체를 점검한다.

### G-PR 1단계: backend 250건 (항상)

| 접두사 | 카테고리 | 건수 |
|---|---|---|
| `API` | API 설계 (Google AIP) | 62 |
| `EJ` | Effective Java | 50 |
| `EC` | 엔티티 생성 패턴 | 31 |
| `DPB` | 도메인 패키지 경계 | 29 |
| `IDS` | 식별자 전략 | 25 |
| `UT` | 단위 테스트 | 20 |
| `BE` | 베이스 엔티티 | 18 |
| `JPA` | JPA 사용 (RDB 관점) | 15 |

**"어떻게 쓰는가"** 를 다룬다. 코드 관용과 패턴이다.

### G-PR 2단계: common + infra 214건 (조건부)

| 접두사 | 카테고리 | 활성화 |
|---|---|---|
| `INF` | 인프라 제약 | 53 |
| `REL` | 신뢰성 | 25 |
| `SEC` | 보안 | 23 |
| `OBS` | 관측 가능성 | 19 |
| `PERF` | 성능 효율성 | 18 |
| `CMP` | 호환성 | 17 |
| `DI` | 데이터 정합성 | 17 |
| `FUN` | 기능 적합성 | 14 |
| `MNT` | 유지보수성 | 13 |
| `FLX` | 유연성과 확장성 | 12 |
| `TRD` | 트레이드오프 | 3 |

**"얼마나 잘 하는가"** (품질 속성)와 **"이 인프라가 강제하는 것"** 을 다룬다.

2단계를 조건부로 둔 이유는 `gemini-2.5-flash`가 464건을 온전히 처리하는지 측정된 바 없기 때문이다.
1단계 응답이 온전할 때만 진행하고, 건너뛴 항목은 `UNJUDGED`로 기록해 통과와 구분한다.

### G-LOCAL: 위 전부

빌드 게이트와 두 단계를 모두 돌리되 차단하지 않는다.
작업 중 반복 실행하는 도구이므로 중간 상태에서 실패하는 것이 정상이다.

### G-RELEASE: `PRE` 13건 (차단)

RDS 상태, 대상 그룹 healthy 수, 인증서 잔여일, CPU 크레딧 잔량 등이다.
**런타임 조회가 필요해 LLM이 아니라 스크립트가 판정한다.**

### G-AUDIT: `INC` 37 + `OPS` 34 등

주기별로 **기록 존재**만 확인한다.
"복원 리허설을 수행했는가"는 판정할 수 없고 "기록 파일이 있고 기한 내인가"는 판정할 수 있다.

## 카테고리가 어디서 오는가

```
fresh-market/.github  docs/software-quality/    217건   품질 속성 (ISO 25010 기반)
fresh-market/fm-backend  docs/code-architecture/   250건   코드 관용과 패턴
fresh-market/fm-infra    docs/infra-review/        100건   인프라 결정이 코드에 부과하는 제약
                                         -----
                                         567건
```

**판정 기준은 세 저장소에서 오지만 판정 대상은 backend 코드 하나다.**
`anchors.yml`이 backend에만 있기 때문이며, Terraform이 생기면 infra에도 만든다.

## 활성화는 앵커 규칙이 정한다

변경 파일이 규칙을 트리거하고, 규칙이 어떤 항목을 켤지 정한다.

```
**/internal/service/*.java   ->  DI PERF REL DPB EJ FUN MNT FLX TRD INF(1,2,8장) SEC(1,2,4,6장)
**/internal/repository/*.java ->  PERF DI JPA SEC(1,2장)
**/internal/entity/*.java    ->  BE EC JPA DI CMP IDS INF(8장)
**/internal/controller/*.java ->  SEC CMP API DPB EJ FUN IDS
**/internal/client/**/*.java ->  REL DPB OBS INF(3장)
application*.yml           ->  REL PERF OBS FLX SEC INF(3,4,5,7,9장)
db/migration/*.sql         ->  DI CMP FLX BE IDS INF(6장)
src/test/**/*Test.java     ->  UT MNT
build.gradle               ->  MNT PERF INF(10장)
```

567건 중 **464건**이 어떤 규칙엔가 걸린다.

`SEC` 를 service 와 repository 에도 켜는 이유는, 소유권 검증과 쿼리 조립의 판정 대상이
컨트롤러가 아니라 그 두 곳이기 때문이다. 컨트롤러만 트리거로 두면
**컨트롤러를 건드리지 않고 서비스 로직에 권한 검사 없는 조회를 추가할 때 아무도 지적하지 않는다.**
3장(입력 검증)은 controller 가, 5장(감사 이력)은 entity 와 migration 이 맡으므로 여기서는 제외한다.
나머지 103건은 `INC` 37, `OPS` 34, `PRE` 13 등으로 **G-AUDIT과 G-RELEASE 소관이라 PR로 트리거되지 않는 것이 정상**이다.

수치의 재현 방법은 [qa-llm-verification.md](https://github.com/fresh-market/.github/blob/main/docs/software-quality/qa-llm-verification.md) 9.2절에 있다.

## 진입점부터의 실행 순서

앞 절이 "언제 무엇을 판정하는가"라면, 이 절은 **"어떤 파일을 순서대로 읽는가"**다.

`[있음]`은 디스크에 존재하는 파일이다. 파이프라인을 이루는 파일은 모두 만들어져 있고, 아직 없는 것은 이 절 끝에 따로 적는다.

```

      |
      v
+- 1 --------------------------------------------------------------+
|  backend/.github/workflows/pr-gate.yml               [ 있음 ]    |
|  G-BUILD 를 먼저 돌리고 성공하면 본체를 부른다                   |
|    on: pull_request  branches: [develop, main]                   |
|    build:  ./gradlew check, sonar          <- 차단한다           |
|    verify: needs build, base_ref == develop                      |
```

**로컬과 CI 의 결과 보존이 다르다.**

```
G-LOCAL   backend/docs/llm-review/ 에 파일로 남고 커밋된다   영구
G-PR      PR 코멘트와 Actions Summary 에만 남는다            비영구
```

CI 결과를 파일로 남기지 않는 것은 의도한 바다.
PR 코멘트가 대화 맥락 안에 있어 찾기 쉽고, 같은 코멘트를 갱신하므로 이력이 필요 없다.
저장소에 쌓으면 PR 마다 파일이 생겨 diff 소음이 된다.

되짚어 볼 필요가 있으면 로컬에서 `/v-commit` 을 돌려 기록을 남긴다.

### 단계별로 읽는 파일

| 단계 | 읽는 것 | 산출 | 상태 |
|---|---|---|---|
| 1 | 호출자 워크플로 | 본체 호출 | 있음 |
| 2 | 본체 워크플로 + `run.py` | 이하 전부 수행 | 있음 |
| 3 | git (3개 저장소) | 작업 트리 | - |
| 4 | git diff | 판정 범위, 재판정 범위 | - |
| 5 | `anchors.yml` | 규칙 11개 | 있음 |
| 6 | (계산) | 앵커 목록, 활성 조건 | - |
| 7 | `items.yml` x 3 | 567건 | 있음 |
| 8 | (계산) | 활성 ID 목록 | - |
| 9 | 가이드 문서 | 항목 본문과 설명 | 있음 |
| 10 | system-design 9개, 165KB | 확정값 (2단계에만) | 있음 (조건부) |
| 11 | 앵커 파일 | 판정 맥락 | - |
| 12 | `known-conflicts.yml` | 억제 목록 | 있음 |
| 13~15 | (LLM) | 판정 결과 | - |
| 16 | 기존 코멘트 | 최종 출력 | - |

### 데이터가 좁혀지는 과정

```
567건  세 저장소의 전체 점검 항목
  |
  |  prefixes   규칙이 지정한 문서군만
  v
  |  levels     코드/설계/인프라/프로세스 중 지정된 것만
  v
  |  chapters   장 번호로 범위 축소 (INF 53건을 규칙당 3~24건으로)
  v
214건  controller 규칙의 활성 항목
  |
  |  ci_stage   1단계와 2단계로 분할
  v
1단계 + 2단계
```

### 5, 7, 9 를 분리한 이유

```
anchors.yml   "무엇을 켤지"      규칙
items.yml     "그게 무엇인지"    메타데이터 (level, gate, domains, ci_stage, defers_to)
가이드 문서   "왜 그런지"        본문과 예시
```

셋을 한 파일에 두면 규칙 하나를 고칠 때 문서를 건드리게 되고, 문서 한 줄을 고칠 때 규칙이 깨진다.

**`items.yml`은 문서에서 자동 생성한다.** 문서가 원본이고 레지스트리는 파생물이므로, 문서를 고치면 재생성해야 한다.

### 구현과 설계가 다른 곳

|  근거 줄이 이 PR 이 추가한 줄인지 diff 로 대조                   |
`run.py`는 LLM 호출을 두 배로 늘리지 않기 위해 다르게 구현했다.

```
|    추가된 줄에 있으면  ->  이 PR 이 만든 것                      |
구현   판정 근거의 file:line 이 이 PR 이 추가한 줄인지 diff 로 대조
```

결정론적이고 호출이 늘지 않는 대신, **추가된 줄 밖에 근거가 있는 신규 위반은 기존 부채로 분류된다.**
줄을 지워서 생긴 위반이 그런 경우다. 재현율을 측정할 때 이 항목을 따로 세야 한다.

### 아직 없는 것

| 없는 것 | 없으면 |
|---------|--------|
| `backend/build.gradle` 의 JaCoCo, SonarQube 설정 | **G-BUILD 가 돌지 않는다.** 차단 게이트 둘 중 하나가 비어 있다 |
| `backend` 의 Java 코드 | 모든 앵커 규칙이 `on_no_match` 로 떨어진다 |
| `infra/.github/llm-verify/anchors.yml` | Terraform 이 생겨도 인프라 코드 자체는 판정되지 않는다 |
| G-RELEASE 스크립트 | `PRE` 13건이 배포 직전에 확인되지 않는다 |

`BLD-1-*` 과 `BLD-2-*` 10건이 첫 행의 설정을 점검 대상으로 삼는다.
**점검 항목은 있는데 점검 대상이 없는 상태다.**

### 확인 방법

`run.py`는 LLM 을 부르지 않고 무엇이 활성화되는지만 보는 모드를 갖는다.
앵커 규칙을 고쳤을 때 의도한 항목이 켜지는지 여기서 먼저 본다.

```bash
python3 ../common/.github/llm-verify/run.py --mode judge --dry-run \
  --backend . --common ../common --infra ../infra --base HEAD~1 --head HEAD
```

```
매칭 규칙   <걸린 규칙>
활성 항목   <n>건
  1단계    <a>건
  2단계    <b>건
  저장소별  {'backend': <x>, 'common': <y>, 'infra': <z>}
앵커 파일   읽음 <p>, 부재 <q>, 실패 <r>
프롬프트 1단계  <문자 수>자 (대략 <토큰 수> 토큰)
```

**부재와 실패는 다르다.** 부재는 그 경로에 파일이 없다는 확인이라 "무언가가 없다" 는 판정의 근거로 쓰이고,
실패는 있는데 못 읽은 것이라 `INSUFFICIENT_EVIDENCE` 사유가 된다.
둘을 뭉개면 점검 항목의 대부분을 차지하는 부재 판정이 전부 증거 부족으로 무너진다.
