# 앱이 장애에 어떻게 반응하나

**이 문서는 앱 코드가 장애 때 무엇을 하는지만 적는다.** 인프라가 무엇을 승격하고 얼마나 걸리는지는
`fm-infra` 가 갖는다. 값이 바뀔 때 고칠 자리를 하나로 두려는 것이다.

```
fm-infra 가 갖는다    토폴로지, 페일오버 시간, 헬스체크, 배포, RTO/RPO, 타임아웃과 회로의 설정값
이 저장소가 갖는다    그 장애가 났을 때 앱이 실행하는 코드
```

선착순 발급은 경로가 따로 있어 [coupon-failure.md](../coupon/coupon-failure.md) 가 다룬다.

---

## 1. 원칙: 대체 경로를 새로 만들지 않기

**이 원칙이 장애 대응 전체를 관통한다.** 대체 경로는 평상시에 안 돌아 **정작 필요한 날 처음 실행된다.**
그날 그 코드가 맞는지 아무도 모른다.

그래서 팀은 세 가지를 안 만들었다.

```
대체 순번 발급기   Redis 가 죽으면 앱이 새 요청을 혼잡(503)으로 끊는다.  다른 곳에서 번호를 만들지 않는다
배치 페일오버      앱이 이어받게 만들지 않는다.  대신 작업 자체를 멱등하게 둔다
재건용 차단 장치   요청을 막는 장치를 새로 만들지 않는다.  스크립트가 이미 막는다
```

**대신 팀은 이미 도는 경로가 장애도 받게 만든다.** 재시도, 조건부 UPDATE, 유니크 제약처럼
평상시에 늘 실행되는 것들이다.

## 2. 무엇이 죽으면 앱이 무엇을 하나

**앱이 할 일이 있는 것과 없는 것이 갈린다.**

| 죽은 것 | 인프라가 하는 일 | 앱이 하는 일 |
|---|---|---|
| ALB | 두 AZ 에 걸쳐 있어 남은 AZ 로 라우팅한다 | **없다** |
| 앱 인스턴스 | 컨테이너는 Docker 가 재시작하고, 인스턴스는 ASG 가 다른 AZ 에 다시 띄운다 | **없다.** 상태를 안 들고 있어 교체가 곧 복구다 |
| MySQL (primary + standby) | 동기 복제라 커밋 손실 없이 Multi-AZ standby 를 자동 승격한다 | 일시적 실패만 가려 커넥션을 다시 얻고 재시도한다 |
| Valkey(Redis) 조회 캐시 (primary + replica) | 비동기 복제라 지연분을 잃고 replica 를 승격한다 | **원본 조회로 강등하고** 적재 실패는 무시한다 |
| Valkey 발급 순번 (primary + replica) | 같은 승격이지만 이벤트 중에는 등급이 Critical 이다 | 승격만으로 안 끝나고 **키가 비어 있으면 앱이 다시 세운다** |
| 배치 인스턴스 | 대체를 두지 않는다 | **없다.** 다음 주기가 따라잡는다 |
| 모니터링 인스턴스 | 대체를 두지 않는다 | **없다.** 핵심 알람만 CloudWatch 로 두 번째 경로를 만든다 |

**아래 셋은 앱이 할 일이 아예 없다.** 죽어도 발급과 주문이 안 멈춘다는 뜻이다.

**팀이 배치를 이중화하지 않는 것은 비용 때문이 아니다.** 프로세스가 항상 하나인 것이 전제라
겹쳐 돌면 같은 배치가 두 번 돈다. 그래서 팀은 이중화 대신 **상태 전이를 조건부 UPDATE 로 두어
겹쳐 돌아도 한 번만 반영되게** 만들었다.

## 3. 헬스체크에 공유 의존성을 안 넣는 이유

**팀은 readiness 에 DB 를 넣지 않는다.** 넣으면 DB 페일오버가 도는 동안
**모든 인스턴스가 동시에 대상 그룹에서 빠진다.** 한 대의 문제가 아니라 전체가 사라지는 것이라
상황이 더 나빠진다.

```
넣는다     인스턴스 로컬 상태.  이 인스턴스만의 문제여야 한다
안 넣는다   DB, Redis 처럼 모든 인스턴스가 함께 보는 것
```

**공유 의존성이 죽은 것은 팀이 인스턴스를 빼서 고칠 수 있는 문제가 아니다.**

## 4. 회로를 걸 때 지키는 것

**느림 문턱은 그 호출의 타임아웃보다 뒤여야 한다.** 팀이 앞에 두면 회로가 정상 응답을 느림으로 세고
**앱 자신이 느린 것을 상대가 죽은 것으로 오진한다.**

이 규칙은 실측에서 나왔다. 선착순 발급에서 회로가 차가운 JVM 의 느림을 Redis 장애로 오진해
**재고가 멀쩡히 남은 상태로 27,382건을 거절**한 적이 있다
([coupon-failure.md](../coupon/coupon-failure.md) 2장).

**팀은 실패 판정도 좁게 잡는다.** `member` 도메인에서 서킷의 실패 판단이 너무 넓어
상태 코드가 있는 정상 응답까지 실패로 셌다. 팀은 **상태 코드 없는 예외를 전송 오류로만** 좁혀 고쳤다.

**서킷이 낸 실패가 재시도 예산을 쓰면 안 된다.** 같은 도메인에서 서킷 실패가 재시도 카운트를
소모하고 있었고 팀이 둘을 분리했다.

## 5. 외부 연동은 반드시 실패한다는 전제

**성공했는지 알 수 없는 응답이 있다.** 그때 앱이 무엇으로 답하느냐를 팀이 도메인마다 정해 두었다.

```
무엇이 실패했나                  앱이 무엇으로 답하나

토큰 재발급의 Redis 보상 실패    "결과 미확정" 으로 답한다.  성공도 실패도 아니라고 하는 편이 안전하다
로그인 시 Redis 사망            DB 로 내려가 처리하고, 저장 실패는 도메인 예외로 바꾼다
카카오 연결 해제 웹훅            규격상 실패해도 200 을 돌려줘야 해서, 실패를 삼키지 않고 따로 남겨 회수한다
이미지 업로드와 DB 기록          한쪽만 성공하면 고아 파일이나 깨진 링크가 남는다.  양쪽을 함께 정리한다
```

**팀은 토큰 무효화 목록만 MySQL 에 둔다.** Redis 에 두면 소실됐을 때
**취소된 토큰이 되살아난다.** 팀은 잃으면 안전이 깨지는 것을 휘발성 저장소에 안 둔다.
