# 자원 예산

**DB 커넥션과 스레드를 인스턴스 종류마다 얼마나 쓰는지, 그리고 그 수가 왜 그 값인지 적는다.**

값을 고치기 전에 여기를 본다. 세 프로필이 같은 RDS 한 대를 보므로 한쪽을 늘리면 다른 쪽이 줄어든다.

## 인스턴스는 셋이다

| 프로필 | 대수 | 하는 일 | ALB |
|---|---|---|---|
| `prod` | 1~3 오토스케일링, 배포 중 4 | 사용자 요청 전부 | 붙는다 |
| `prod,coupon` | 3 (**아직 신설 전**) | 선착순 쿠폰 발급만 | 붙는다. 발급 경로만 온다 |
| `prod,batch` | 1 | 스케줄 작업만 | 안 붙는다 |

셋 다 같은 `application.yml` 을 읽고 프로필 파일이 그 위를 덮는다.

## 최소는 총 개수가 아니라 유휴 개수다

숫자를 읽기 전에 알아야 하는 것이 하나 있다. **`minimum-idle` 은 "적어도 이만큼 놀고 있게 하라" 는 뜻이지 "적어도 이만큼 만들어 두라" 가 아니다.** Hikari 가 더 만들 개수를 이렇게 센다.

```
더 만들 수 = min( 최대 - 총개수 , 최소유휴 - 현재유휴 )
```

그래서 이렇게 움직인다.

```
기동         한 개로 접속을 확인하고, 하우스키퍼가 30초 안에 유휴를 최소까지 채운다
빌려가면     빌린 것은 유휴가 아니므로 최소를 회복하려고 하나 더 만든다. 최대까지
기다리면     대기 스레드가 생긴 즉시 만든다
줄어들면     최소 < 최대 일 때만. 둘이 같으면 유휴 반납 코드를 아예 건너뛴다
```

**실제 상주 개수는 대체로 "일하는 수 + 최소" 다.** 최소 1로 둔 풀이 작업 중에 2를 쥐는 것은 정상이다.

## 커넥션은 60 이 전부다

```
db.t4g.micro 의 max_connections 약 60 (아직 추정치. 실측이 필요하다)
```

| 출처 | 한산할 때 | 부하 (앱 3대) | 배포 중 (앱 4대) |
|---|---|---|---|
| 앱 (최소 2, 최대 8) | 2 | 24 | 32 |
| 선착순 3대 (최소 1, 최대 2) | 3 | 6 | 6 |
| 배치 1대 (최소 1, 최대 4) | 1 | 2 | 2 |
| `mysqld_exporter` | 1~3 | 1~3 | 1~3 |
| 운영자 접속 | 1~2 | 1~2 | 1~2 |
| **합계** | **약 9** | **약 36** | **약 44** |

**배포 중이 기준선이다.** 오토스케일링이 3대까지 올린 상태에서 배포가 신규를 겹쳐 띄우면 4대가 되고, 그때가 가장 빡빡하다.

**셋 다 놀 때는 돌려준다.** 앱은 스케일 인으로 인스턴스째 사라지고, 선착순은 이벤트 사이에, 배치는 작업 사이에 유휴 몫만 남긴다.

## 풀 크기가 왜 그 값인가

### 앱 최소 2, 최대 8

**요청 스레드가 트랜잭션을 연다.** 셋 중 유일하게 커넥션 수요가 동시 요청 수를 따라가는 인스턴스다. 세어서 정할 수 없고 예산에서 나눠 받는다.

**최대 8 은 4대가 동시에 쥐어도 닫히는 값이다.** 4 x 8 = 32 이고 나머지를 다 더해도 44 다.

**최소를 최대와 같게 두면 안 된다.** 그러면 새로 뜬 인스턴스가 요청 하나 받기 전에 8 을 먼저 잡는데, **스케일 아웃이 도는 때가 곧 트래픽이 몰려 DB 도 바쁜 때다.** 가장 빡빡한 순간에 아무 일도 안 하는 커넥션이 예산에서 빠져나간다. 그래서 2 로 시작해 실제 트래픽만큼 늘게 둔다.

늘리는 값을 사용자 요청이 물지는 않는다. 스케일 아웃 인스턴스는 어차피 JVM 기동과 ALB 헬스 체크를 기다리므로 트래픽을 받기 전에 하우스키퍼가 채운다. `connection-timeout` 도 3초라 여유가 크다.

**8 로 내려도 처리량은 안 줄어든다.** DB 가 2코어라 동시에 쓸모 있게 처리하는 문장 수가 5 안팎인데 3대 x 8 이면 이미 그 위다. 줄어드는 것은 DB 안에 서는 줄이다.

### 선착순 전용 최소 1, 최대 2

**요청 스레드가 트랜잭션을 안 연다.** Redis 에서 순번을 받아 큐에 넣고 결과를 기다릴 뿐이라, 요청이 2만 개여도 커넥션 수요가 안 는다. 실제로 쓰는 것은 둘이다.

```
플러시 스레드   1   DB 에 쓰는 것은 이것뿐이다 (flush-threads: 1)
캐시 적재      1   쿠폰 스냅샷을 5초마다 다시 읽는다 (coupon-cache-ttl)
```

**최대 2 가 사는 것은 격리다.** 슬롯이 둘이라 캐시 적재가 하나를 쥐어도 플러시 스레드가 안 기다린다. 1 로 줄이면 DB 가 느려질 때 둘이 한 줄로 서고, 플러시 대기가 `slow-call-duration` 150ms 를 넘기면 DB 쓰기 회로가 열려 그 배치 전체가 혼잡으로 답한다.

**최소 1 은 상시 수요가 하나여서다.** 이벤트가 도는 동안 계속 커넥션을 쓰는 것은 플러시 스레드 하나다. 플러시가 하나를 빌려 가면 유휴가 비므로 둘째가 만들어져 **이벤트 중에는 사실상 2 로 산다.** 이벤트가 끝나고 `idle-timeout`(기본 10분)이 지나면 다시 1 이다. 전용 3대면 이벤트 사이에 셋이 예산으로 돌아간다.

**"발급 요청 0" 에는 단서가 붙는다.** 쿠폰에 `target_grade_id` 가 걸려 있으면 `CouponIssueService` 가 회원 등급을 확인하려고 **요청마다 DB 를 한 번 읽는다.** 그때는 수요가 요청 수에 비례하므로 어떤 풀 크기로도 못 받는다. **선착순 쿠폰에는 등급을 걸지 않는다**는 것이 이 값의 전제다.

### 배치 최소 1, 최대 4

**스케줄러 스레드가 하나라 작업 여덟 개가 한 줄로 돈다.** `spring.task.scheduling.pool.size` 기본값이 1 이고 배치는 가상 스레드를 안 켠다. 작업 안에도 병렬이 없고 `REQUIRES_NEW` 도 없다.

| 시각 | 작업 |
|---|---|
| 00:00 | 캠페인 대상 로트 |
| 03:00 | 카카오 연결 해제 재시도, 관리자 로트 만료 |
| 04:00 | 쿠폰 만료, 대기 이미지 정리 |
| 04:30 | 쿠폰 정합성 검증 (분 단위로 길다) |
| 10분마다 | 쿠폰 이벤트 종료, 옵션 판매 상태 동기화 |

**같은 시각에 둘씩 걸려 있어도 커넥션 수요는 1 이다.** 뒤엣것이 앞엣것 끝나기를 기다리기 때문이다. **작업이 돌 때 앉는 자리는 2**(작업 1 + 유휴 1)이고 4 는 도달할 일이 거의 없는 천장이다.

**최대를 10 으로 두면 안 되는 이유가 있다.** 나중에 누가 스케줄러를 동시 실행으로 바꿔도 풀이 조용히 삼켜서 그 변화가 안 보인다. 4 면 `hikaricp_connections_pending` 에 드러난다.

## 스레드

| 프로필 | 요청 스레드 | 왜 |
|---|---|---|
| `prod` | 플랫폼, 톰캣 200 | 요청이 DB 를 기다리므로 커넥션 풀이 먼저 상한이다 |
| `prod,coupon` | **가상** | 아래 참조 |
| `prod,batch` | 플랫폼 | 요청을 안 받는다 |

**선착순만 가상 스레드를 켠다.** 플러시 스레드가 배치 하나로 최대 500 개의 `future` 를 한꺼번에 완료시키는데, 커널 스레드였다면 그때마다 500 번 깨우는 컨텍스트 스위칭이 난다. 초당 50 배치면 2만 5천 번이다. 가상 스레드는 캐리어 몇 개 위에 마운트만 해서 커널이 안 끼어든다.

**플러시 스레드는 반대로 플랫폼 스레드로 둔다.** 그 개수가 곧 DB 에 동시에 쓰는 수라 셀 수 있어야 한다.

## 고칠 때 보는 지표

Prometheus 가 8081 의 `/actuator/prometheus` 에서 긁는다.

```
hikaricp_connections_pending          커넥션을 기다리는 스레드 수. 0 이 아니면 풀이 모자라다
hikaricp_connections_timeout_total    못 얻고 포기한 횟수. 늘면 이미 실패가 나가고 있다
hikaricp_connections_acquire_seconds  얻기까지 걸린 시간
hikaricp_connections_usage_seconds    쥐고 있던 시간
```

**풀을 늘리기 전에 `usage_seconds` 를 먼저 본다.** 오래 쥐고 있어서 모자란 것이면 풀을 늘려도 줄만 DB 안으로 옮겨간다.

## 남은 숙제

**`max_connections` 를 실측해야 한다.** `coupon.md` 5장이 "약 60(예측)" 으로 적어 둔 뒤로 아직 재지 않았다. 앱이 한 대일 때는 60이든 50이든 티가 안 났지만 **배포 중 최악이 44 까지 가는 지금은 그 차이가 곧 장애다.**

```sql
SHOW VARIABLES LIKE 'max_connections';
```

**선착순 전용 ASG 는 아직 없다.** 위 표의 선착순 행은 신설 후의 값이다. 지금 실제 합계는 그만큼 적다. 신설 전에 필요한 인프라 변경은 `coupon.md` 6장이 정리해 두었다.

**정합성 검증이 도는 동안 10분짜리 배치가 멈춘다.** 스케줄러 스레드가 하나라 04:30 의 검증이 300만 행을 훑는 몇 분 내내 쿠폰 이벤트 종료 배치가 밀린다. 발급 정확성은 안 깨지지만(마감 지난 요청은 기간 검사가 막는다) **이벤트가 닫히는 시각이 그만큼 늦는다.** 커넥션 풀로는 못 고치고 `spring.task.scheduling.pool.size` 를 올려야 하는 별개 사안이다.
