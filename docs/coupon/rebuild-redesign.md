# 부재와 승격을 한 경로로 합친 재건 (설계)

**아직 짜지 않았다.** 코드를 읽고 2026-09-30 회차를 근거로 세운 설계이고, 회차로 검증한 값이
하나도 없다. 읽는 쪽이 실측 기록과 섞지 않도록 여기 따로 둔다.

**지금 재건은 카운터 키가 없을 때만 돈다**([재건 문서](redis-promotion-rebuild.md) 7장).
승격은 키를 지우지 않고 값의 꼬리만 자르므로 그 방아쇠에 안 걸린다. **이 설계는 두 경우를 한
절차로 합친다.**

---

## 1. 분기가 없는 이유

두 경우의 차이가 셋이고, 셋 다 같은 동작으로 덮인다.

| | 카운터 부재 | 승격 | 합치면 |
|---|---|---|---|
| 발급이 멈춰 있나 | 이미 멈췄다 | 돌고 있다 | **락이 문이다.** 락을 잡으면 양쪽 다 멈춘다 |
| 네 키에 옛 내용이 있나 | 없다 | 있다 | **지우고 쓴다.** 비어 있으면 지우기가 무동작이다 |
| 이벤트가 열려 있나 | 확인해야 한다 | 확실하다 | **DB 를 읽는다.** 어차피 `issueEndAt` 이 필요하다 |

**그래서 절차 안에 `if` 가 없다.** 누가 깨웠는지를 안 가른다.

---

## 2. 방아쇠 셋

```
A  요청이 Lua 에서 -2 를 받았다      카운터가 없다.  지금도 있는 길이다
B  Lettuce 재연결 이벤트가 왔다      승격을 의심한다.  새로 만든다
C  플러시가 재건 락 키를 봤다         남이 시작했다.  올리기로 참여한다
```

**C 가 필요한 이유는 따로 있다.** 로드밸런서가 요청을 안 보내는 인스턴스는 `-2` 를 받을 기회가
없어 자기가 쥔 번호를 알릴 길이 없다. 그런데 티켓을 쥔 인스턴스는 그것을 쓰느라 반드시 플러시를
돌리므로 그 자리에서 알아챈다.

---

## 3. 문을 맡는 분산 락

**순번 확보 스크립트에 한 줄이 들어간다.**

```lua
-- KEYS[5] = coupon:{id}:rebuild  (재건 락)
if redis.call('EXISTS', KEYS[5]) == 1 then
  return '-2'
end
```

**카운터의 존재 여부와 무관하게 재건 중에는 번호가 안 나간다.**

| | 지금 | 이 설계 |
|---|---|---|
| 무엇이 문인가 | `counter` 키의 부재 | 재건 락의 존재 |
| 문이 닫히는 때 | 키가 사라진 때 | 락을 잡은 때 |
| 문이 열리는 때 | `openGate` 가 카운터를 세울 때 | 락을 풀 때 |
| 주도자가 죽으면 | 다음 요청이 다시 띄운다 | **락의 만료가 문을 연다** |

**뜨거운 경로에 `EXISTS` 하나가 늘어난다.** 이미 여러 명령을 도는 스크립트라 무게는 작다.

---

## 4. 절차

**아래는 방아쇠 B(재연결)로 들어온 흐름이다.** A 는 3번에서 쿠폰을 이미 알고 있고, C 는 락을
못 잡은 쪽이라 5번과 6번만 한다.

```
1    Lettuce 재연결 이벤트를 받는다
2    그 인스턴스의 재건 스레드가 아래를 처리한다
3    DB 에서 활성 선착순 쿠폰을 확인한다
4    분산 락을 잡는다.  Lua 가 이 키를 보고 순번 발급을 거절한다
5    자기 플러시 스레드를 정지시킨다
6    대기열의 회원과 순번을 rebuild:queued 에 올리고 rebuild:done 에 표시한다
       락을 못 잡은 인스턴스는 여기까지만 하고 돌아간다
7    나머지가 올릴 때까지 기다린다.  상한 시간까지만 기다린다
8    rebuild:queued 를 읽고 그다음 DB 를 읽는다
9    seq 와 free 를 지운다.  pending 에서는 DB 에 행이 있는 회원만 뺀다
10   seq 를 쓴다.  올라온 것 먼저, DB 행이 덮는다
11   pending 에 올라온 것 중 없는 회원을 더한다
12   free 를 쓴다
13   counter 를 쓴다
14   플러시 스레드를 다시 돌린다          <- 정지를 여기까지 넓혔다
15   rebuild:queued 와 rebuild:done 을 지운다
16   분산 락을 푼다
```

**3번이 `issueEndAt` 도 함께 얻는다.** 13번이 네 키의 만료를 그 값에 맞춘다.

**7번이 무엇을 세는지는 6장에 있다.** `coupon:instances` 에서 최근 10초 안에 자기를 갱신한
인스턴스 수만큼 `rebuild:done` 이 차면 상한을 안 쓰고 끝낸다.

**8번 앞에 확인이 하나 더 있다.** 기다리는 동안 관리자가 이벤트를 새로 열었으면 그 카운터를
덮지 않고 끝낸다.

### 9번부터 13번까지의 순서

**10번이 올라온 것을 먼저 넣고 DB 행으로 덮는다.** 같은 회원이 양쪽에 있을 수 있고 그때는
DB 쪽이 이겨야 한다. **확정을 미확정으로 덮으면 회수가 그 번호를 버려진 것으로 보고 남에게
넘긴다**([재건 문서](redis-promotion-rebuild.md) 3장).

**9번이 `pending` 만 통째로 안 지운다.** 살아남은 항목은 참값이고 점수도 실제로 받은 시각이다.
통째로 다시 쓰면 점수가 재건 시각이 되어 **회수가 그만큼 뒤로 밀린다.** 그리고 올라온 것이 비면
`pending` 이 텅 비어, 소진 근처에서 스크립트가 최종 소진으로 판정해 재시도를 막는다.

**13번이 쓰기의 마지막이다.** `counter` 는 DB 최댓값과 올라온 것의 최댓값 중 큰 값이고,
12번의 `free` 는 DB 에도 올라온 것에도 없는 번호다.

## 5. 지금 코드에서 빠지는 것

```
counterExists 관문          락이 문을 맡으므로 없다
경로 분기                   부재와 승격이 한 절차다
openGate 가 문을 여는 역할    락 해제가 맡는다.  counter 쓰기는 값 세우기일 뿐이다
```

---

## 6. 남기는 것과 그 근거

**`rebuild:done` 과 `coupon:instances`.** 조기 종료를 만든다.

```
있으면   기여 대기 55밀리초 (2026-09-23 실측)
없으면   상한까지 고정.  3초
```

**발급이 멈춘 구간이라 그 차이가 곧 사용자가 거절받는 시간이다.** 걷어내면 정지가 열 배 이상 늘어난다.

**인스턴스 안 중복 제거.** 20,000 요청이 동시에 `-2` 를 받으면 그만큼의 작업이 단일 스레드 큐에
쌓인다. **분산 락은 그 앞을 못 막는다.** 락을 잡기 전에 이미 작업이 쌓여 있다.

**8번 앞의 재확인.** 기다리는 동안 관리자가 이벤트를 새로 열 수 있다. 그 카운터를 덮으면 안 된다.

---

## 7. 넓힌 정지 구간

```
지금      올리는 동안만.  밀리초
이 설계    5번부터 14번까지.  읽고 쓰는 동안까지
```

**4번이 발급을 막았으므로 새 티켓이 안 들어온다.** 멈춰 둬도 대기열이 안 자란다.

**그래서 창 하나가 없어진다.** 지금은 DB 를 읽은 뒤 네 키를 쓰기까지의 사이에 커밋된 티켓이
올라온 것에만 있어 미확정으로 남는다. 실측 127밀리초다.

---

## 8. 남는 한계

**4번 직전에 번호를 받은 요청이다.**

```
Lua 가 번호를 돌려준다  ->  (여기서 락이 잡힌다)  ->  티켓이 대기열에 들어간다
```

**그 티켓은 6번의 훑기에도 8번의 DB 에도 안 잡힐 수 있다.** 그러면 12번이 결번으로 분류해 남에게
내준다. **마이크로초 창이고 `uk_mc_coupon_seq` 가 뒤에서 막는다.**

**없애려면 요청 경로가 락을 한 번 더 봐야 한다.** 뜨거운 경로에 검사를 더하는 일이라 안 넣었다.

**그리고 올라온 것이 빌 때의 문제는 이 설계가 안 다룬다.** 플러셔가 실패한 배치를 대기열에서
빼고 되돌리지 않으므로 DB 장애가 겹치면 13번이 카운터를 뒤로 돌린다
([회차 기록](rebuild-and-fault-2026-09-30.md) 3장). **팀이 그 부분은 고려하지 않기로 정했다.**
