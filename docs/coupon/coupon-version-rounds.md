# 버전 비교 회차 설계

**v4 는 이미 채택안이다.** 이 회차들은 그 결정을 뒷받침할 실측을 만든다.
버전의 정의는 [coupon.md](coupon.md) 6장, 브랜치는
[coupon-version-branches.md](coupon-version-branches.md) 에 있다.

부하 조건과 회차 규칙은 [coupon-load-scenarios.md](coupon-load-scenarios.md) 를 그대로 따른다.
아래는 그 문서가 다루지 않는 것만 적는다.

## 1. 이 시험이 기존 시나리오와 다른 점

**그 문서는 "팀이 바꾸는 것은 앱 설정뿐이다" 를 전제로 쓰였다.** 버전 비교는 그것을 넘어
코드와 이미지를 바꾼다. 그래서 규칙 하나를 더한다.

**회차 사이에 바뀌는 것은 배포한 이미지 하나여야 한다.** 앱 설정을 함께 바꾸면 무엇이 값을
움직였는지 못 가른다. 버전마다 설정이 다른 곳은 아래 둘뿐이고 그것이 버전의 정의에 속한다.

| 버전 | `threads.virtual` | `maximum-pool-size` |
|---|---|---:|
| v1 | `false` | 8 |
| v2 | `false` | 8 |
| v3 | `false` | 2 |
| v4 | `true` | 2 |

**v1 과 v2 의 설정이 같다.** 그래서 그 둘의 차이는 순번을 어디서 받느냐 하나다.
**v3 와 v4 의 차이도 가상 스레드 하나다.** v2 와 v3 사이만 둘이 함께 움직이는데,
큐를 들이면 요청 스레드가 트랜잭션을 안 열게 되어 풀 크기가 따라오는 것이라 분리할 수 없다.

## 2. 고정하는 것

부하 조건은 요구사항이 정한 값이라 안 건드린다. 재고 10,000, VU 20,000, ramp-up 60초다.

**워밍업을 전 회차에서 켠다.** 실측에서 껐을 때 3.313초, 켰을 때 0.302초로 **10배가 갈렸다.**
버전 차이보다 큰 변수라 이것이 흔들리면 비교가 성립하지 않는다.

**회차마다 인스턴스를 새로 띄우지 않는다.** 같은 인스턴스에 이미지만 굴린다. 새로 띄우면
JVM 이 덜 데워진 상태가 섞인다.

## 3. 회차 수와 순서

**버전당 3회다.** 같은 설정이 회차마다 0.302초에서 0.518초로 흔들린 이력이 있어 2회로는
회차마다 달라지는 몫과 버전 차이를 못 가른다.

순서는 `v4 -> v1 -> v2 -> v3 -> v4` 다. **v4 를 처음과 끝에 둔다.**

**그 이유가 이 설계의 핵심이다.** 시험이 몇 시간에 걸치면 그 사이 DB 상태와 캐시와 AWS 쪽
사정이 달라진다. 처음과 끝의 v4 가 다르면 그 드리프트만큼 다른 버전의 값도 못 믿는다.
**두 v4 의 차이가 이 시험의 오차 한계다.**

## 4. 회차를 무효로 만드는 조건

**돌리기 전에 정해 둔다.** 뒤에 정하면 유리한 회차만 고르게 된다.

| 조건 | 왜 |
|---|---|
| `k6_dropped_iterations_total` > 0 | 부하 생성기가 부하를 다 못 냈다 |
| 회차 중 `up` 이 0 이 되는 계열이 있다 | 인스턴스가 죽었다 |
| `COUPON_WARMUP_DONE` 이 없거나 `ok` 가 `sent` 와 다르다 | 워밍업이 안 돌았다 |
| 배포한 태그가 그 버전 브랜치의 HEAD 와 다르다 | 다른 코드를 쟀다 |
| 발급 수가 10,000 이 아니다 | 재고를 다 털지 못했으므로 다른 회차와 모집단이 다르다 |
| 인스턴스의 `docker ps` 이미지가 그 버전과 다르다 | SSM `current-sha` 만 보면 못 잡는다 |
| 생성기가 OOM 으로 죽는다 | 그 회차는 앱이 아니라 생성기의 한계를 잰 것이다 |

**SSM 만 보는 검산은 통과해 버린다.** `deploy.sh` 는 SSM 을 먼저 갱신하고 뒤 단계에서
실패할 수 있다. 2026-09-27 에 배포 둘이 겹쳐 SSM 은 새 값인데 인스턴스는 구 이미지인 구간이
생겼고, 회차 스크립트가 "이미지 확인" 을 찍고 넘어갔다.

## 5. 판정에 쓰는 값

[coupon.md](coupon.md) 7장이 정한 그대로다. **처리된 응답의 p99** 다.

**기록에는 한글 이름으로 적는다.** 지표 이름은 이 프로젝트 안에서만 통한다.

| 기록에 적는 이름 | 담는 응답 | k6 지표 |
|---|---|---|
| **처리된 응답 p99** | 발급(200), 이미 받음(409), 소진(410) | `k6_coupon_settled_duration_p99` |
| 전체 응답 p99 | 위 셋과 혼잡(503), 그 밖의 모든 응답 | `k6_http_req_duration_p99` |

**전체 응답 p99 를 합격 판정에 쓰면 안 된다.** 혼잡(503)이 요청 예산을 태우고 끊기므로
**예산을 줄이는 것만으로 그 값이 내려간다. 앱은 하나도 안 빨라졌는데도 그렇다.**

두 값을 다 싣고 간격을 셋째 정보로 본다. 벌어져 있으면 혼잡이 많다는 뜻이다.

### 회차를 무엇으로 가르나

**`round` 태그를 쓰지 않는다.** `issue.js` 에 그 태그를 넣는 코드가 없고, k6 의 `--tag` 로
전역 태그를 붙이면 모든 시계열에 붙어 카디널리티를 늘린다.

**회차 사이를 5분 이상 띄우고 시간 창으로 가른다.** 회차 하나가 90초이므로 간격이 넉넉하면
아래 함정이 애초에 생기지 않는다. 시작과 끝 시각을 회차마다 적는다.

### p99 를 뽑는 방법

**`loadtest-export.sh` 로 p99 를 뽑지 않는다.** 그 스크립트는 시간 창 안의 모든 계열을 합쳐
`max` 를 잡는데 `round` 태그로 가르지 않는다. **회차 간격이 창보다 짧으면 앞 회차의 값을
보고한다.** 지난 시험에서 실제로 같은 값이 두 번 나왔다.

**판정값은 k6 요약의 p99 다.** 회차가 끝났을 때 그 회차의 표본 전체로 계산한 값이다.

Prometheus 로도 뽑되 회차의 시작과 끝 시각으로 자른 `query_range` 를 쓰고, instant query 는
안 쓴다. 최근 5분 안에 표본이 있는 계열만 돌려주고 값도 그 시점의 표본 하나다.

**그 시계열의 최댓값을 판정에 쓰지 않는다.** k6 가 보내는 것은 누적 분포의 p99 라서 표본이
적은 회차 초반에 크게 튄다. 초반의 불안정한 값을 잡을 수 있으므로 참고로만 본다.

**회차에 걸쳐 평균내지 않는다.** p99 는 이미 분포를 요약한 값이라 평균낸 결과는 p99 가
아니다. **버전의 p99 는 그 버전이 낸 p99 중 가장 나쁜 값이다.**

## 6. 버전을 가르는 지표

p99 만 재면 "v3 가 v2 보다 빠르다" 에서 끝나고 **왜인지 못 말한다.** 버전마다 다음을 함께 본다.

| 값 | 어느 버전 차이를 드러내나 |
|---|---|
| `mysql_global_status_innodb_row_lock_waits` | **v1 -> v2.** v1 은 조건부 UPDATE 가 한 행에 배타 락을 건다 |
| `redis_commands_processed_total` | **v1 -> v2.** v1 은 0 에 가깝다 |
| `hikaricp_connections_pending` / `_active` | **v2 -> v3.** v2 는 요청 스레드가 커넥션을 쥔다 |
| `mysql_global_status_slow_queries` | **v2 -> v3.** 벌크가 왕복을 줄인다 |
| `coupon_issue_queue_size` | **v2 -> v3.** v2 는 큐가 없어 0 이다 |
| `jvm_threads_live_threads` / `_peak_threads` | **v3 -> v4.** 플랫폼 스레드 200 벽 |
| `tomcat_threads_busy_threads` | **v3 -> v4.** v3 는 입구가 200 에서 막힌다 |
| `jvm_gc_pause_seconds_count` | 꼬리가 GC 때문인지 가른다 |

## 7. 성능보다 앞선 정합성

**하나라도 깨지면 그 버전의 성능 수치는 의미가 없다.** 빠른 대신 초과 발급하는 것은 진 것이다.

| 불변식 | 재는 법 |
|---|---|
| R1 발급 수 <= `total_quantity` | 최종 발급 수 대 10,000. **초과도 과소도 본다** |
| R2 1인 1매 | `(coupon_id, member_id)` 중복 0 |
| R3 순번 안 겹침 | `issue_seq` 중복 0. 결번 수도 적는다 |
| R5 상태와 이력 일치 | 마지막 전이가 현재 상태와 같은가 |

**v1 에만 있는 차이를 기억해 둔다.** v1 은 미확정 순번이라는 상태가 없어 409 와 410 이
갈리지 않고 소진이 곧 최종이다. 사유별 거절을 셀 때 그 차이를 버전 탓으로 읽지 않는다.

## 8. 회차마다 남길 것

### 임계 판정 전부

**`issue.js` 의 임계가 넷이다. 하나만 보면 나머지 셋이 잡은 것을 놓친다.**

| 임계 | 무엇을 막나 |
|---|---|
| `coupon_settled_duration: p(99)<1000` | SLO 미달 |
| `http_req_failed: rate<0.01` | 503 을 뺀 모든 실패 |
| `coupon_unexpected: count==0` | 봐서는 안 되는 응답 |
| `coupon_congested_rate: rate<0.01` | 거절로 도망가는 것 |

**2026-09-27 회차에서 실제로 놓쳤다.** p99 와 DB 정합성만 뽑았더니, v1 이 요청의 80%에
500 을 돌려주고 있다는 것을 열두 회차 중 한 회차에서 우연히 발견했다. `coupon_unexpected`
가 16,039건으로 그 임계를 깨고 k6 가 exit 99 로 끝났는데 기록에 그 신호가 없었다.

**k6 요약이 사라질 수 있으므로 Prometheus 에서도 뽑는다.** 생성기가 OOM 으로 죽으면 요약을
못 찍는다. 아래 시계열이 같은 값을 갖는다.

```
k6_http_req_failed
k6_coupon_unexpected_total
k6_coupon_congested_total
k6_coupon_issued_total
k6_http_reqs_total
```

**회차가 끝나는 대로 뽑는다.** 전부 끝난 뒤에 몰아 뽑으면 그동안 값을 볼 수 없고, 인프라를
내리면 사라진다. Prometheus 는 로컬 TSDB 를 쓰고 그 볼륨이 인스턴스와 함께 지워진다.


[coupon-load-scenarios.md](coupon-load-scenarios.md) 10장에 더해 둘을 적는다.

```
배포한 이미지 태그      그 버전 브랜치의 HEAD 와 같은지 확인한 결과
설정 확인             COUPON_FLUSHER_STARTED 와 COUPON_WARMUP_DONE
                     v1 과 v2 는 플러시가 큐를 안 쓰므로 그 로그의 뜻이 다르다
```

## 9. 결과를 어디에 적나

회차 원본은 [coupon-load-rounds.md](coupon-load-rounds.md) 에 이어 적는다.
버전 비교표는 아래 모양으로 이 문서 끝에 붙인다.

```
| 버전 | 처리된 응답 p99 | 전체 응답 p99 | 발급 | 혼잡(503) | 큐 최대 | HikariCP pending | row lock waits | 판정 |
```

**대표값은 세 회차 중 가장 나쁜 p99 이고 세 값을 다 싣는다.** 5장이 적은 이유로 중앙값이나
평균을 쓰지 않는다. 분위수를 회차에 걸쳐 다시 요약하면 그 결과는 분위수가 아니다.

## 10. 오류 경로에서 늘어나는 k6 메모리

**VU 2만이 `anon-rss` 7,268 MiB 를 쓴다.** `m7i-flex.large` 의 `MemTotal` 이 7,776 MiB 이고
k6 실행 전 `used` 가 544 MiB 라, 합이 7,812 MiB 로 36 MiB 초과였다.

**원인은 [rebuild-measurement-2026-09-21b.md](rebuild-measurement-2026-09-21b.md) 4장에 있다.**

> 회차 1의 k6 는 살아남았다. **k6 는 오류 경로가 늘면 못 버틴다.** 팀이 회차 2와 3에서
> DB 를 막아 실패 응답이 많았다.

| 회차 | 실패 응답 | k6 |
|---|---|---|
| 2026-09-14 | 혼잡 0, 재시도 0, 실패율 0.00% | **완주** |
| 2026-09-21 회차 1 (정상) | 적다 | **완주** |
| 2026-09-21 회차 2, 3 (DB 차단) | 많다 | 87% 부근에서 죽었다 |
| 2026-09-27 (v1 은 500 이 80%) | 많다 | 열두 회차 중 열한 회차가 죽었다 |

**그래서 실패가 많은 회차일수록 위험하다.** 버전 비교처럼 못 받는 요청이 절반인 시험은 그
조건에 해당한다.

### 인스턴스를 키우는 길

**프리 티어가 8 GiB 를 넘는 타입을 거부한다.** `r7i.large`(2 vCPU / 16 GiB)를 시도했다가
되돌렸다.

```
InvalidParameterCombination: The specified instance type is not eligible for Free Tier.
```

**`vCPU` 가 2 여도 프리 티어 목록에 없으면 안 된다.** 목록은 여덟 개이고 메모리가 가장 큰 것이
`m7i-flex.large` 8 GiB 다. `describe-instance-types` 의 `free-tier-eligible` 필터로 얻는다.

**`run-instances --dry-run` 으로 확인하면 안 된다.** 권한과 파라미터 형식만 보고
`DryRunOperation` 을 돌려주므로 `r7i`, `r6i`, `r5` 가 모두 통과하고 실제로는 셋 다 거부된다.

**그래서 시나리오를 고치는 것이 유일한 길이었다.** 판정을 받은 VU 가 남은 시간을 한 번에 자게
바꿨고, 반복이 90만에서 2만으로 줄었다.

### sleep 수정 전과 뒤의 대조

**`sleep` 수정이 p99 를 바꿀 수 있다.** 부하는 그대로지만 생성기가 하는 일이 줄기 때문이다.

```
sleep(1)  ->  2만 VU 가 초당 2만 번 반복  ->  k6 가 CPU 를 쓴다
                                          ->  응답 처리가 밀리면 p99 가 부풀 수 있다
```

**`http_req_duration` 은 요청을 보낸 시각부터 응답을 받아 처리한 시각까지다.** k6 가 바쁘면 그
지연이 앱의 응답 시간으로 기록된다. **그리고 생성기 CPU 를 한 번도 안 쟀다**
(`fm-infra` 의 `docs/deploy/README.md`).

**그래서 12회차 앞에 v4 대조 회차를 하나 둔다.** 같은 인프라, 같은 이미지, 같은 부하에서
`sleep` 만 다르게 한 값이다.

| 결과 | 뜻 |
|---|---|
| 2026-09-27 의 v4 범위(189 ~ 389ms) 안에 든다 | 생성기 부담이 없었다. 앞선 회차와 비교가 성립한다 |
| 뚜렷하게 낮다 | 지금까지의 p99 에 생성기 부담이 섞여 있었다 |

**2026-09-28 에 돌렸고 205.2ms 로 그 범위 안이었다.** 그래서 앞선 회차와 비교가 성립한다.
같은 회차에서 생성기 CPU 도 처음 쟀고 최대 83.3% 로 포화가 아니었다
([coupon-load-versions.md](coupon-load-versions.md) 6장).

**그 회차에서 CPU 도 함께 잰다.** `mpstat` 이나 `top` 으로 k6 가 2 vCPU 를 포화시켰는지 본다.

**대조 회차를 건너뛰면 12회차를 돌린 뒤에도 "이 값이 앞선 회차와 비교 가능한가" 를 답할 수
없다.** 그것을 모르면 그 회차가 또 버려진다.

### 회차 로그에 남길 것

**`-o experimental-prometheus-rw` 를 붙여 돌린다.** 그래야 k6 가 죽어도 push 한 시계열로
p99 를 얻는다. 다만 죽으면 k6 요약을 잃고 **임계 판정이 거기 있으므로** 8장이 정한 대로
Prometheus 에서도 뽑아야 한다.

**2026-09-27 에 그것을 놓쳐서 v1 이 요청의 80%에 500 을 돌려준다는 것을 열두 회차 중 한
회차에서 우연히 발견했다.**

## 11. 결과

**결과는 [coupon-load-versions.md](coupon-load-versions.md) 에 있다.** 2026-09-28 회차다.

| 버전 | p99 | 발급 | 회차 간 몇 배 | 판정 |
|---|---:|---:|---:|---|
| v1 DB 조건부 UPDATE | 639.8ms | 3,777 ~ 4,006 | 1.01배 | **요청 80%에 500** |
| v2 Redis 카운터 | 351.8ms | 10,000 | 6.54배 | 통과 |
| v3 인스턴스 큐 + 벌크 | 355.8ms | 10,000 | 3.68배 | 통과 |

**이 회차가 가른 것은 v1 과 나머지다.** v1 은 범위가 겹치지 않고 재고를 40%만 턴다. v2 와 v3 는
최악값이 4ms 차이로 사실상 같은 자리다.

**v4 만 범위가 좁고 낮다.** 세 회차가 모두 v2 와 v3 의 최악값 아래에 있다.

**절차의 결함 일곱을 찾아 고쳤다.** 그중 하나가 아래 항목이고 나머지는 결과 문서 9장에 있다.

### 배포 뒤의 전용 ASG 재생성

**`deploy.sh` 는 평상시 앱 ASG 만 교체한다.** 발급 요청은 ALB 가 쿠폰 전용 ASG 로 보내므로
이것을 안 하면 이미지를 바꿔도 발급을 처리하는 코드가 그대로다.

```
deploy.sh <SHA>
  -> coupon-event.sh close      desired 0
  -> coupon-event.sh open 3     새 인스턴스가 SSM current-sha 를 읽어 뜬다
  -> docker ps 로 이미지 확인
```
