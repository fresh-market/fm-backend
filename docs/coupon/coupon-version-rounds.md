# 버전 비교 회차 설계

**v4 는 이미 채택안이다.** 이 회차들은 그 결정을 뒷받침할 실측을 만든다.
버전의 정의는 [coupon.md](coupon.md) 6장, 브랜치는
[coupon-version-branches.md](coupon-version-branches.md) 에 있다.

부하 조건과 회차 규칙은 [coupon-load-scenarios.md](coupon-load-scenarios.md) 를 그대로 따른다.
아래는 그 문서가 다루지 않는 것만 적는다.

## 1. 이 시험이 기존 시나리오와 다른 점

**그 문서는 "팀이 바꾸는 것은 앱 설정뿐이다" 를 전제로 쓰였다.** 버전 비교는 그것을 넘어
코드와 이미지를 바꾼다. 그래서 규칙 하나를 더한다.

**회차 사이에 바뀌는 것은 배포한 이미지 하나여야 한다.** 앱 설정을 함께 바꾸면 무엇이 값을
움직였는지 못 가른다. 버전마다 설정이 다른 곳은 아래 둘뿐이고 그것이 버전의 정의에 속한다.

| 버전 | `threads.virtual` | `maximum-pool-size` |
|---|---|---:|
| v1 | `false` | 8 |
| v2 | `false` | 8 |
| v3 | `false` | 2 |
| v4 | `true` | 2 |

**v1 과 v2 의 설정이 같다.** 그래서 그 둘의 차이는 순번을 어디서 받느냐 하나다.
**v3 와 v4 의 차이도 가상 스레드 하나다.** v2 와 v3 사이만 둘이 함께 움직이는데,
큐를 들이면 요청 스레드가 트랜잭션을 안 열게 되어 풀 크기가 따라오는 것이라 분리할 수 없다.

## 2. 고정하는 것

부하 조건은 요구사항이 정한 값이라 안 건드린다. 재고 10,000, VU 20,000, ramp-up 60초다.

**워밍업을 전 회차에서 켠다.** 실측에서 껐을 때 3.313초, 켰을 때 0.302초로 **10배가 갈렸다.**
버전 차이보다 큰 변수라 이것이 흔들리면 비교가 성립하지 않는다.

**회차마다 인스턴스를 새로 띄우지 않는다.** 같은 인스턴스에 이미지만 굴린다. 새로 띄우면
JVM 이 덜 데워진 상태가 섞인다.

## 3. 회차 수와 순서

**버전당 3회다.** 같은 설정이 회차마다 0.302초에서 0.518초로 흔들린 이력이 있어 2회로는
그 흔들림과 버전 차이를 못 가른다.

순서는 `v4 -> v1 -> v2 -> v3 -> v4` 다. **v4 를 처음과 끝에 둔다.**

**그 이유가 이 설계의 핵심이다.** 시험이 몇 시간에 걸치면 그 사이 DB 상태와 캐시와 AWS 쪽
사정이 달라진다. 처음과 끝의 v4 가 다르면 그 드리프트만큼 다른 버전의 값도 못 믿는다.
**두 v4 의 차이가 이 시험의 오차 한계다.**

## 4. 회차를 무효로 만드는 조건

**돌리기 전에 정해 둔다.** 뒤에 정하면 유리한 회차만 고르게 된다.

| 조건 | 왜 |
|---|---|
| `k6_dropped_iterations_total` > 0 | 부하 생성기가 부하를 다 못 냈다 |
| 회차 중 `up` 이 0 이 되는 계열이 있다 | 인스턴스가 죽었다 |
| `COUPON_WARMUP_DONE` 이 없거나 `ok` 가 `sent` 와 다르다 | 워밍업이 안 돌았다 |
| 배포한 태그가 그 버전 브랜치의 HEAD 와 다르다 | 다른 코드를 쟀다 |
| 발급 수가 10,000 이 아니다 | 재고를 다 털지 못했으므로 다른 회차와 모집단이 다르다 |

## 5. 판정에 쓰는 값

[coupon.md](coupon.md) 7장이 정한 그대로다. **`k6_coupon_settled_duration_p99`** 다.

`k6_http_req_duration_p99` 를 합격 판정에 쓰면 안 된다. 혼잡(503)이 요청 예산을 태우고 끊기므로
**예산을 줄이는 것만으로 그 값이 내려간다. 앱은 하나도 안 빨라졌는데도 그렇다.**

두 값을 다 싣고 간격을 셋째 정보로 본다. 벌어져 있으면 혼잡이 많다는 뜻이다.

### 회차를 무엇으로 가르나

**`round` 태그를 쓰지 않는다.** `issue.js` 에 그 태그를 넣는 코드가 없고, k6 의 `--tag` 로
전역 태그를 붙이면 모든 시계열에 붙어 카디널리티를 늘린다.

**회차 사이를 5분 이상 띄우고 시간 창으로 가른다.** 회차 하나가 90초이므로 간격이 넉넉하면
아래 함정이 애초에 생기지 않는다. 시작과 끝 시각을 회차마다 적는다.

### p99 를 뽑는 방법

**`loadtest-export.sh` 로 p99 를 뽑지 않는다.** 그 스크립트는 시간 창 안의 모든 계열을 합쳐
`max` 를 잡는데 `round` 태그로 가르지 않는다. **회차 간격이 창보다 짧으면 앞 회차의 값을
보고한다.** 지난 시험에서 실제로 같은 값이 두 번 나왔다.

회차의 시작과 끝 시각으로 자른 `query_range` 의 최댓값을 쓴다. instant query 도 안 쓴다. 최근 5분 안에
표본이 있는 계열만 돌려주고 값도 그 시점의 표본 하나라 최댓값이 아니다.

## 6. 버전을 가르는 지표

p99 만 재면 "v3 가 v2 보다 빠르다" 에서 끝나고 **왜인지 못 말한다.** 버전마다 다음을 함께 본다.

| 값 | 어느 버전 차이를 드러내나 |
|---|---|
| `mysql_global_status_innodb_row_lock_waits` | **v1 -> v2.** v1 은 조건부 UPDATE 가 한 행에 배타 락을 건다 |
| `redis_commands_processed_total` | **v1 -> v2.** v1 은 0 에 가깝다 |
| `hikaricp_connections_pending` / `_active` | **v2 -> v3.** v2 는 요청 스레드가 커넥션을 쥔다 |
| `mysql_global_status_slow_queries` | **v2 -> v3.** 벌크가 왕복을 줄인다 |
| `coupon_issue_queue_size` | **v2 -> v3.** v2 는 큐가 없어 0 이다 |
| `jvm_threads_live_threads` / `_peak_threads` | **v3 -> v4.** 플랫폼 스레드 200 벽 |
| `tomcat_threads_busy_threads` | **v3 -> v4.** v3 는 입구가 200 에서 막힌다 |
| `jvm_gc_pause_seconds_count` | 꼬리가 GC 때문인지 가른다 |

## 7. 정합성을 성능보다 먼저 본다

**하나라도 깨지면 그 버전의 성능 수치는 의미가 없다.** 빠른 대신 초과 발급하는 것은 진 것이다.

| 불변식 | 재는 법 |
|---|---|
| R1 발급 수 <= `total_quantity` | 최종 발급 수 대 10,000. **초과도 과소도 본다** |
| R2 1인 1매 | `(coupon_id, member_id)` 중복 0 |
| R3 순번 안 겹침 | `issue_seq` 중복 0. 결번 수도 적는다 |
| R5 상태와 이력 일치 | 마지막 전이가 현재 상태와 같은가 |

**v1 에만 있는 차이를 기억해 둔다.** v1 은 미확정 순번이라는 상태가 없어 409 와 410 이
갈리지 않고 소진이 곧 최종이다. 사유별 거절을 셀 때 그 차이를 버전 탓으로 읽지 않는다.

## 8. 회차마다 남길 것

[coupon-load-scenarios.md](coupon-load-scenarios.md) 10장에 더해 둘을 적는다.

```
배포한 이미지 태그      그 버전 브랜치의 HEAD 와 같은지 확인한 결과
설정 확인             COUPON_FLUSHER_STARTED 와 COUPON_WARMUP_DONE
                     v1 과 v2 는 플러시가 큐를 안 쓰므로 그 로그의 뜻이 다르다
```

## 9. 결과를 어디에 적나

회차 원본은 [coupon-load-rounds.md](coupon-load-rounds.md) 에 이어 적는다.
버전 비교표는 아래 모양으로 이 문서 끝에 붙인다.

```
| 버전 | settled p99 | http p99 | 발급 | 혼잡(503) | 큐 최대 | HikariCP pending | row lock waits | 판정 |
```

**세 회차의 중앙값을 대표값으로 쓰고 세 값을 다 싣는다.** 최솟값을 고르면 그 버전에 유리한
회차를 고른 것이 된다.

## 10. 부하 생성기가 여러 대다

**한 대로는 2만 VU 를 못 낸다.** 2026-09-27 에 k6 가 7.4 GB 를 써서 커널이 죽였다.
VU 당 약 369 KB 이고 `m7i-flex.large` 가 8 GB 다. 93% 라 여유가 없다.

인스턴스를 키우는 길은 막혀 있다. 이 계정이 프리 티어라 `m7i.xlarge` 를 거부한다.
VU 2만은 요구사항이 정한 값이라 줄일 수도 없다. 그래서 나눈다. 2대면 대당 약 3.6 GB 로 45% 다.

```
./scripts/loadtest-box.sh up            load_test_count 만큼 띄우고 세그먼트를 검산한다
./scripts/loadtest-box.sh run v4-1      전 대수에 동시에 k6 를 건다
```

**대별로 손으로 돌리면 안 된다.** 램프가 60초인데 시작이 10초만 밀려도 도착률이 설계값과
달라지고, 그 회차가 무엇을 잰 것인지 말할 수 없다.

### 세그먼트가 어긋나면 앱 탓으로 읽힌다

시나리오가 `exec.vu.idInTest` 로 토큰을 고른다. 두 대가 각자 1부터 세면 **같은 사람을 두 대가
쏘고 1인 1매 위반이 난다.** 그것은 생성기 탓인데 지표에서는 앱 탓과 구분되지 않는다.

`--execution-segment` 가 VU 번호 공간을 나눈다. 2대면 이렇다.

```
1호기   --execution-segment '0:1/2'    --execution-segment-sequence '0,1/2,1'
2호기   --execution-segment '1/2:1'    --execution-segment-sequence '0,1/2,1'
```

`loadtest-box.sh up` 이 띄운 뒤 이 값을 검산한다. 표기가 아니거나 중복이면 멈춘다.

### 무효 조건에 하나를 더한다

| 조건 | 왜 |
|---|---|
| 생성기 중 한 대라도 OOM 으로 죽는다 | 그 회차는 앱이 아니라 생성기의 한계를 잰 것이다 |

`free -m` 에 스왑이 생기는지, CPU 가 100% 에 붙는지도 함께 본다. 근거는 fm-infra 의
`instance_types` 주석에 있다.

## 11. 결과

**2026-09-27 회차의 결과는 [coupon-version-results-2026-09-27.md](coupon-version-results-2026-09-27.md) 에 있다.**

| 버전 | settled p99 범위 | k6 요약 p99 평균 | 판정 |
|---|---|---:|---|
| v1 DB 조건부 UPDATE | 139.8 ~ 274.8ms | 139.0ms | 못 가림 |
| v2 Redis 카운터 | 110.0 ~ 153.6ms | 97.3ms | 못 가림 |
| v3 인스턴스 큐 + 벌크 | 165.1 ~ 323.0ms | 95.2ms | 못 가림. 세 번 중 한 번 큐 포화 |
| v4 가상 스레드 (채택) | 87.6 ~ 126.2ms | 80.8ms | 두 지표 모두 최저 |

**이 설계는 네 버전을 가르지 못했다.** 발급이 초당 약 111건이라 어느 구현에도 부담이 아니다.
설계 6장이 지목한 지표 여덟 중 일곱이 버전에 따라 움직이지 않았다.

**요구 부하를 고정한 채로는 다시 돌려도 같다.** 가르려면 재고를 키우거나 홀드를 줄여야 하고,
둘 다 요구사항 밖이다.
