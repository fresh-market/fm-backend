# commit-wait 예산 720ms 를 네 항목으로 쪼개 본 회차 (2026-10-10)

**이 회차가 처음으로 "800ms 를 어디가 먹는가" 에 답한다.** 앞선 회차들은 발급 경로에 지연
계량기가 하나도 없어서 p99 가 541ms 로 나와도 그 541ms 가 어디 있는지 가릴 수 없었다.

```
AWS 실측     20,000 VU / ramp 60초 / hold 30초 / 재고 10,000장 / 전용 인스턴스 3대
스프링 서버  fm-backend 676cae54.  발급 경로 계량기 셋이 들어 있다
워밍업       requests=20000 concurrency=300 writeRows=10000.  코드 기본값이고 override 가 없다
시나리오     fm-backend main 8ed43e2 의 loadtest/issue.js, k6 v1.7.1
주입         팀이 부하를 먼저 띄우고 k6+50초에 캐시 페일오버를 걸었다
대시보드     infra/loadtest-runs/2026-10-10T10-06-46Z_J-1/grafana
```

**팀이 계량기를 붙인 이유는 예산 네 항목 중 셋을 아무도 재지 않았기 때문이다.** 커넥션 획득은
HikariCP 가 이미 재고 있었지만, 큐 대기와 배치 쓰기와 확정 표시는 재는 것이 없었다.

## 4. 재건이 실패한 원인

**팀이 앞선 회차에서 세운 가설은 `pause-timeout` 이었고 그것은 틀렸다.**

| 시각 (UTC) | 무슨 일이 났나 |
|---|---|
| 10:08:46 | 팀이 캐시 페일오버를 걸었다 |
| 10:08:46.503 | 플러시가 `COUPON_SEQ_COUNTER_BEHIND counter=5225 seen=9999 gap=4774` 를 찍었다 |
| 10:08:46 ~ 10:09:23 | 플러시가 BEHIND 를 114건 찍었고 counter 는 5,202 에서 8,970 까지 올라갔다 |
| 10:09:23.318 | 재연결 감시가 `COUPON_SEQ_RECONNECT_DETECTED coupons=2` 를 찍었다 |
| 10:09:23.424 | 재건이 `COUPON_SEQ_REBUILD_FAILED couponId=900001` 로 실패했다 |
| 10:09:23.546 | 재건이 `COUPON_SEQ_REBUILD_FAILED couponId=1000000` 로 실패했다 |

실패 예외는 둘 다 같다.

```
io.lettuce.core.RedisCommandTimeoutException: Command timed out after 100 millisecond(s)
    at io.lettuce.core.internal.ExceptionFactory.createTimeoutException(ExceptionFactory.java:63)
```

**재건이 `redis.timeout 100ms` 에 걸려 죽었다.** 승격 직후의 새 프라이머리가 아직 부하를 다
받는 중이라 재건의 Lua 호출이 100ms 를 넘겼다.

**재건은 한 번 시도하고 재시도 없이 포기한다.** 그래서 100ms 를 한 번 넘기면 그 회차에서
재건은 끝난다.

**팀이 고칠 곳은 두 군데다.** 하나는 재건 호출에 별도의 더 긴 타임아웃을 주는 것이고, 다른
하나는 실패했을 때 물러나며 재시도하는 것이다. 지금 코드는 둘 다 없다.

### 4.1 재연결 감지가 37초 늦음

**플러시는 10:08:46.5 에 이미 카운터가 뒤로 밀린 것을 알았는데 재연결 감시는 10:09:23 에
알았다.** 37초 차이다.

그 37초 동안 플러시가 BEHIND 를 114건 찍었고, 그것은 그만큼의 배치가 뒤로 밀린 카운터를
보고도 그대로 진행했다는 뜻이다.

**감시는 Lettuce 이벤트 버스를 보고 재건은 감시가 깨우는데, 플러시가 먼저 아는 신호를 아무도
재건으로 잇지 않는다.** BEHIND 가 재건을 깨우게 하면 37초가 사라진다.

## 6. 예산 네 항목의 적절성

**팀이 쓰던 산식은 배치 윈도우 20ms + 커넥션 획득 300ms + 소켓 읽기 300ms + 확정 표시 100ms
= 720ms 다.** 실측과 맞춰 보면 이렇다.

| 항목 | 예산 | 무장애 최대 | 장애 최대 | 판단 |
|---|---:|---:|---:|---|
| 배치 윈도우 | 20 | 설정값 | 설정값 | 맞다 |
| 커넥션 획득 | 300 | 0.02 미만 | 0.03 미만 | **과하다.** 워밍업이 둘을 미리 만들어 둔다 |
| 소켓 읽기 | 300 | 49 | 178 | 여유가 크지만 장애 최대의 1.7배라 줄이기 전에 더 봐야 한다 |
| 확정 표시 | 100 | 12 | **109** | **모자란다.** 장애에서 넘겼다 |

**팀이 줄일 수 있는 것은 커넥션 획득이고 늘려야 하는 것은 확정 표시다.** 다만 큐 대기가 상한
없이 1,285ms 를 쓰는 동안 이 네 항목을 조정하는 것은 효과가 작다.

**예산에서 손을 봐야 할 것은 상한이 없는 큐 대기다.** 지금 산식은 큐 대기를 아예 세지 않는데,
실측에서 그것이 가장 큰 항목이다.

## 7. 팀이 붙인 계량기

`CouponIssueFlusher` 가 셋을 잰다.

| 지표 | 재는 구간 |
|---|---|
| `coupon.issue.queue.wait` | 요청 스레드가 큐에 넣은 시각부터 플러시가 집는 시각까지 |
| `coupon.issue.batch.write` | 벌크 INSERT 호출 전후 |
| `coupon.issue.mark.commit` | `markCommitted` 호출 전후 |

`IssueTicket` 이 `queuedAtNanos` 를 들고 다니며 큐 대기의 시작점을 전한다.

**커넥션 획득은 HikariCP 가 이미 재고 있어서 팀이 새로 붙이지 않았다.** `increase(_sum)` 을
`increase(_count)` 로 나누어 구간 평균을 뽑는다. `_max` 는 게이지라 기동 때의 값이 그대로
남아 있으므로 구간 귀속에 쓸 수 없다.

## 8. 팀이 못 본 것

**큐 대기 1,285ms 가 언제 났는지 초 단위로 가리지 못했다.** 계량기가 Timer 라 최댓값은 구간
전체의 최댓값이고, 그것이 페일오버 직후인지 재건 실패 직후인지는 이 회차 자료로 가를 수 없다.

**재건이 완주하는 데 걸리는 시간을 또 못 쟀다.** 재건이 이번에도 완주하지 않았다. 앞선
2026-10-02 회차와 같은 상태다.

**소켓 읽기 300ms 를 줄여도 되는지 판정하지 못했다.** 장애 최대가 178ms 라 1.7배 여유인데,
더 센 장애에서 얼마까지 가는지 보지 않았다.
