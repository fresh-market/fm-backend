# commit-wait 예산 720ms 를 네 항목으로 쪼개 본 회차 (2026-10-10)

**이 회차가 처음으로 "800ms 를 어디가 먹는가" 에 답한다.** 앞선 회차들은 발급 경로에 지연
계량기가 하나도 없어서 p99 가 541ms 로 나와도 그 541ms 가 어디 있는지 가릴 수 없었다.

```
AWS 실측     20,000 VU / ramp 60초 / hold 30초 / 재고 10,000장 / 전용 인스턴스 3대
스프링 서버  fm-backend 676cae54.  발급 경로 계량기 셋이 들어 있다
워밍업       requests=20000 concurrency=300 writeRows=10000.  코드 기본값이고 override 가 없다
시나리오     fm-backend main 8ed43e2 의 loadtest/issue.js, k6 v1.7.1
주입         팀이 부하를 먼저 띄우고 k6+50초에 캐시 페일오버를 걸었다
대시보드     infra/loadtest-runs/2026-10-10T10-06-46Z_J-1/grafana
```

**팀이 계량기를 붙인 이유는 예산 네 항목 중 셋을 아무도 재지 않았기 때문이다.** 커넥션 획득은
HikariCP 가 이미 재고 있었지만, 큐 대기와 배치 쓰기와 확정 표시는 재는 것이 없었다.

## 4. 재건이 실패한 원인

**팀이 앞선 회차에서 세운 가설은 `pause-timeout` 이었고 그것은 틀렸다.**

| 시각 (UTC) | 무슨 일이 났나 |
|---|---|
| 10:08:46 | 팀이 캐시 페일오버를 걸었다 |
| 10:08:46.503 | 플러시가 `COUPON_SEQ_COUNTER_BEHIND counter=5225 seen=9999 gap=4774` 를 찍었다 |
| 10:08:46 ~ 10:09:23 | 플러시가 BEHIND 를 114건 찍었고 counter 는 5,202 에서 8,970 까지 올라갔다 |
| 10:09:23.318 | 재연결 감시가 `COUPON_SEQ_RECONNECT_DETECTED coupons=2` 를 찍었다 |
| 10:09:23.424 | 재건이 `COUPON_SEQ_REBUILD_FAILED couponId=900001` 로 실패했다 |
| 10:09:23.546 | 재건이 `COUPON_SEQ_REBUILD_FAILED couponId=1000000` 로 실패했다 |

실패 예외는 둘 다 같다.

```
io.lettuce.core.RedisCommandTimeoutException: Command timed out after 100 millisecond(s)
    at io.lettuce.core.internal.ExceptionFactory.createTimeoutException(ExceptionFactory.java:63)
```

**재건이 `redis.timeout 100ms` 에 걸려 죽었다.** 승격 직후의 새 프라이머리가 아직 부하를 다
받는 중이라 재건의 Lua 호출이 100ms 를 넘겼다.

**재건은 한 번 시도하고 재시도 없이 포기한다.** 그래서 100ms 를 한 번 넘기면 그 회차에서
재건은 끝난다.

**팀이 세 군데를 고쳤다.** 커밋은 `c1f8af9b` 다.

| 무엇 | 전 | 후 |
|---|---|---|
| 재건의 Redis 타임아웃 | 발급과 같은 100ms | 전용 통로에서 1초 (`CouponSeqRebuildRedis`) |
| 실패한 뒤 | 재시도 없이 포기 | 200ms 와 400ms 를 쉬며 3회까지 |
| 명부가 빈 것과 못 읽은 것 | 둘 다 0 | `OptionalInt` 로 가른다 (4.2) |

**타임아웃을 나누려고 커넥션을 하나 더 쓴다.** Lettuce 의 명령 타임아웃이 커넥션 팩토리 단위
설정이라 커넥션을 나누지 않고서는 상한을 나눌 수 없다. 전용 3대에서 Valkey 커넥션 셋이고,
재건이 드물게 도는 일이라 이 커넥션은 거의 논다.

**재시도가 멱등한 근거는 재건 절차 자체다.** 재건은 네 키를 비우고 다시 세우며, 실패하면
락이 풀리므로 다음 시도가 처음부터 한다.

### 4.1 재연결 감지가 37초 늦음

**플러시는 10:08:46.5 에 이미 카운터가 뒤로 밀린 것을 알았는데 재연결 감시는 10:09:23 에
알았다.** 37초 차이다.

그 37초 동안 플러시가 BEHIND 를 114건 찍었고, 그것은 그만큼의 배치가 뒤로 밀린 카운터를
보고도 그대로 진행했다는 뜻이다.

**감시는 Lettuce 이벤트 버스를 보고 재건은 감시가 깨우는데, 플러시가 먼저 아는 신호를 아무도
재건으로 잇지 않는다.** BEHIND 가 재건을 깨우게 하면 37초가 사라진다.

**팀은 그것을 아직 붙이지 않았다.** `CouponSeqRebuildTrigger.measureBehind` 의 Javadoc 이
"정상 운영에서 이 표본이 0건이라는 것을 회차로 확인한 뒤에 붙인다" 는 조건을 적어 두었고,
그 조건이 아직 충족되지 않았다. 근거는 6장이다.

### 4.2 명부가 빈 것과 못 읽은 것

**재건이 기여자 0명을 3초 기다린 뒤 실패로 끝나는 자리가 있었다.**

```
REBUILD_STARTED  ->  CONTRIBUTED size=0 lagMillis=31
                 ->  CONTRIBUTIONS_TIMEOUT instances=0   3초를 다 썼다
                 ->  REBUILD_FAILED
```

`CouponSeqInstances.live()` 가 Redis 실패와 "명부가 진짜로 비었다" 를 둘 다 `0` 으로 주었다.
부르는 쪽은 둘을 가를 수 없어 `0` 을 전부 "모른다" 로 다루었고, 그래서 올라올 것이 없는
경우에도 정해진 시간을 다 기다렸다.

**`OptionalInt` 로 가른다.** 빈 값은 "못 셌다" 이므로 기다림을 안 줄이고, `0` 은 "큐를 쥔
인스턴스가 없다" 이므로 즉시 진행한다. 못 센 쪽의 보수적 동작은 그대로 남는다.

**이 절의 뒷부분은 한 번 되돌렸다.** `0` 을 즉시 진행 신호로 쓰는 것이 J-4 에서 결번 180 을
만들었다. 명부가 비는 이유가 재건 자신이었기 때문이고, 경과와 고친 방법은 11장에 있다.
`OptionalInt` 로 가르는 것 자체는 남아 있다.

## 6. BEHIND 를 재건에 잇는 조건이 아직 아님

`measureBehind` 의 Javadoc 은 이 신호를 재건에 붙이는 조건을 이렇게 적어 두었다.

> 재기만 하고 재건은 안 띄운다. 재건은 그 이벤트의 플러시를 3초 넘게 멈추므로 오탐이 곧
> 장애다. 정상 운영에서 이 표본이 0건이라는 것을 회차로 확인한 뒤에 붙인다.

**팀이 그 조건을 세 회차로 재어 보았고 충족되지 않았다.**

| 회차 | 건 장애 | BEHIND 표본 | JVM |
|---|---|---:|---|
| J-1 | 없음 | **0** | ASG 교체 직후라 새 JVM 이다 |
| J-2 | 캐시 페일오버 | 1,689 | J-1 과 같은 JVM 이다 |
| J-3 | **없음** | **1,130** | J-1 과 같은 JVM 이다 |

**장애가 없는 J-3 에서 1,130건이 났다.** 이 상태로 BEHIND 가 재건을 깨우게 하면 회차마다
재건이 천 번 넘게 떠서 플러시가 계속 멈춘다. Javadoc 이 말한 "오탐이 곧 장애" 가 이것이다.

### 6.1 오탐의 원인

**`highWater` 가 앞 회차의 최댓값을 들고 있다.** BEHIND 가 찍은 값이 그것을 가리킨다.

```
counter=37    seen=9999   gap=9962
counter=141   seen=9997   gap=9856
counter=6290  seen=9999   gap=3709
```

`seen` 은 전부 앞 회차의 재고 10,000 에 붙어 있고 `counter` 는 이번 회차에서 0부터 다시
오르는 중이다. 고리는 이렇다.

```
loadtest-seed.sh reset 이 DB 만 되돌린다  ->  Redis 카운터는 남는다
  ->  이벤트를 다시 열면 CouponSeqInitializer 가 카운터를 0 으로 세운다
  ->  highWater 는 JVM 메모리라 앞 회차 10,000 을 그대로 든다
  ->  새 회차의 모든 배치가 counter < 10000 을 보고 BEHIND 를 찍는다
```

`highWater` 가 지워지는 경로는 카운터 키가 없을 때 하나뿐이고, 재준비는 키를 지우는 것이
아니라 0 으로 덮으므로 그 경로를 안 지난다.

**J-1 이 0건인 것이 이 설명의 증거다.** ASG 교체 직후라 `highWater` 가 비어 있었다.

### 6.2 운영에는 없음

**같은 쿠폰을 발급 이력째 지우고 다시 여는 것은 시험 절차뿐이다.** 운영에서 이벤트는 한 번
열리고 마감되며, 같은 `couponId` 로 재고를 다시 채우는 경로가 없다.

**그래서 팀은 코드를 고치지 않고 시험 절차를 고치기로 한다.** 회차마다 쿠폰을 새 `couponId`
로 시드하면 오탐이 사라지고 승격 조건을 깨끗하게 판정할 수 있다. 운영에 없는 문제에 발급
경로의 복잡도를 쓰지 않는 쪽이다.

### 6.3 로그로는 이 표본을 셀 수 없음

**회차 기록에 쓰던 `docker logs ... | tail -40` 이 이 수를 가린다.** 인스턴스 3대라 상한이
120 이고, 실제로 J-2 는 로그에서 114건이었지만 지표로는 1,689건이다. 15배다.

**그리고 회차 경계를 안 지킨다.** 컨테이너 로그가 누적되므로 J-3 수집물에 J-2 의 로그가
섞여 있었다. 이 신호는 `coupon_seq_counter_behind_count` 로 세야 한다.

## 7. 예산 네 항목의 적절성

**팀이 쓰던 산식은 배치 윈도우 20ms + 커넥션 획득 300ms + 소켓 읽기 300ms + 확정 표시 100ms
= 720ms 다.** 실측과 맞춰 보면 이렇다.

| 항목 | 예산 | 무장애 최대 | 장애 최대 J-2 | 장애 최대 J-5 | 판단 |
|---|---:|---:|---:|---:|---|
| 배치 윈도우 | 20 | 설정값 | 설정값 | 설정값 | 맞다 |
| 커넥션 획득 | 300 | 0.02 미만 | 0.03 미만 | 0.07 미만 | 과하지만 **못 내린다** (7.1) |
| 소켓 읽기 | 300 | 49 | 178 | 121 | 여유가 크지만 더 센 장애를 안 봤다 |
| 확정 표시 | 100 | 12 | **109** | **116** | 모자라지만 **못 올린다** (7.2) |

**팀이 옮길 수 있는 항목이 없다.** 실측이 두 항목의 값이 틀렸다고 말하는데 둘 다 다른 제약에
묶여 있다.

**그래서 7장의 결론은 값을 옮기는 것이 아니라 산식에 큐 대기를 적는 것이다.** 실측에서 가장
큰 항목인데 지금 산식은 그것을 아예 세지 않는다.

### 7.1 커넥션 획득 300ms 를 못 내리는 이유

**HikariCP 가 이 값의 하한을 250ms 로 강제한다.** 그보다 작게 적으면 경고와 함께 조용히
250 으로 덮어써서 적힌 값과 도는 값이 갈린다.

**그 250 에 딱 붙이는 것도 안 된다.** 경계에 두면 판이 바뀌어 하한이 오를 때 같은 일이
되풀이되므로, `CouponProfileBindingTest` 의 `하한_경계에_붙이지_않는다` 가 300 이상을
요구한다. **즉 실측과 무관하게 300 이 사실상의 바닥이다.**

### 7.2 확정 표시 100ms 를 못 올리는 이유

**올리면 SLO 천장이 깨진다.** 이 값은 `spring.data.redis.timeout` 이고 천장 계산에 두 번
들어간다.

```
지금     redis.timeout 100 x 2 + commit-wait 800 = 1,000ms  =  p99 1초 SLO
150 이면 redis.timeout 150 x 2 + commit-wait 800 = 1,100ms  >  SLO 가 깨진다
```

**맞추려면 commit-wait 과 소켓 읽기를 함께 줄여 천장 여유를 0 으로 만들어야 한다**
(`250 + 250 + 150`, `commit-wait 700`, 천장 정확히 1,000). 그 대가를 치를 근거가 약하다.
넘긴 것은 평균 1~3ms 인 항목의 드문 꼬리이고, 넘긴 J-2 와 J-5 가 결번 0 과 초과 발급 0 을
지켰다. **그래서 팀은 SLO 여유를 택했다.**

### 7.3 가장 큰 지렛대는 예산 밖에 있음

**`contributeWait` 3초다.** 10.1 이 보인 대로 큐 대기 꼬리가 곧 재건 정지이고, 그 정지의
거의 전부가 기여 대기다. **예산 네 항목 밖에 있는 값이 예산을 터뜨린다.**

**팀은 그 3초를 줄이지 않고 다른 쪽을 고쳤다.** 재건 정지를 685ms 와 3,144ms 로 가른 것이
명부를 읽었는지 하나였고(10장), 명부를 세는 `live()` 가 발급용 100ms 통로를 쓰고 있었다.
그것을 재건 통로로 돌렸다. **천장을 깎는 대신 천장에 닿는 횟수를 줄이는 쪽이다.** 기여 대기를
줄이는 것은 J-4 와 같은 종류의 위험을 지므로(11장) 택하지 않았다.

`CouponIssueFlusher` 가 셋을 잰다.

남아 있으므로 구간 귀속에 쓸 수 없다.

## 9. 팀이 못 본 것

**큐 대기 최댓값이 언제 났는지 초 단위로 가리지 못했다.** 계량기가 Timer 라 최댓값은 구간
전체의 것이다. J-5 에서는 그 값이 재건 정지와 거의 같아 정체가 짚였지만(10.1), 초 단위로
겹쳐 본 것은 아니다.

**소켓 읽기 300ms 를 줄여도 되는지 판정하지 못했다.** 장애 최대가 121 에서 178ms 라 여유가
크지만, 더 센 장애에서 얼마까지 가는지 보지 않았다.

**페일오버 중에 명부를 왜 못 읽는지 좁히지 못했다.** `instances=unknown` 이 재건 정지를
685ms 와 3,144ms 로 갈랐는데(10장), 그 읽기가 타임아웃인지 커넥션 실패인지는
`live()` 가 예외를 `log.debug` 로만 남겨 이 회차 자료로 가를 수 없다.

**결번 180 이 J-4 에서만 난 것이 고침 때문이라고 단정한 근거는 회차 둘이다.** J-4 와 J-5
사이에 바뀐 것이 그 한 군데이고 로그가 `instances=0` 과 `instances=2` 로 갈리지만, 페일오버
심각도가 회차마다 다르므로 같은 조건을 더 돌려 본 것은 아니다.

## 10. 승격 뒤 재건이 처음으로 완주함

**팀은 재건 소요를 이번에 처음 잰 것이 아니다.** 2026-09-23 에 처음 쟀고(204밀리초),
2026-10-01 에 또 쟀다(3,458밀리초). **J-5 가 처음인 것은 승격 경로의 재건이 완주한 것**이다.
앞의 둘은 키를 직접 지운 `seq-loss` 와 기동 오탐으로 걸린 재연결이었고, 뒤쪽은 부하가 끝난
뒤였다.

J-5 에서 재건이 두 번 완주했다.

```
REBUILT couponId=900001 issued=6321 queued=2 maxSeq=6367 freed=44
        rebuildMillis=685   contributeMillis=28  waitMillis=338   readWriteMillis=317
REBUILT couponId=900001 issued=6325 queued=1 maxSeq=6367 freed=41
        rebuildMillis=3144  contributeMillis=17  waitMillis=3009  readWriteMillis=117
```

| 구간 | 빠른 쪽 | 느린 쪽 |
|---|---:|---:|
| 올릴 것을 올리기 | 28 | 17 |
| **남의 것을 기다리기** | **338** | **3,009** |
| 읽고 쓰기 | 317 | 117 |
| **문을 닫아 둔 시간** | **685** | **3,144** |

**둘을 가른 것은 명부를 읽었는지 하나다.**

```
CONTRIBUTIONS_COMPLETE couponId=900001 instances=2 waitedMillis=339            ->  685ms
CONTRIBUTIONS_TIMEOUT  couponId=900001 instances=unknown done=2 waitedMillis=3000  ->  3,144ms
```

**페일오버 중에는 명부를 못 읽어 천장 3초를 태운다.** 2026-10-01 의 3,458밀리초는 부하가
끝나 아무도 참여하지 않은 것이 원인이었는데, 이쪽은 부하가 도는 중인데도 그렇게 됐다. 명부를
세는 것이 Redis 읽기이고, 승격 직후에는 그 읽기가 실패하기 때문이다.

**읽고 쓰기는 117 에서 317밀리초다.** 결번 수에 비례하는 항목이고 이 회차는 `freed` 가
41 과 44 였다.

### 10.1 재건 정지가 큐 대기 꼬리의 정체임

| 회차 | 큐 대기 최대 | 재건이 문을 닫아 둔 시간 |
|---|---:|---:|
| J-5 | **3,170ms** | **3,144ms** |

**두 값이 거의 같다.** 지금까지 팀은 "큐 대기가 예산에서 유일하게 상한이 없다" 까지만 알았고
그 꼬리가 무엇인지는 몰랐다. 재건이 발급을 멈춰 둔 시간이 그대로 큐 대기로 나타난다.

**그래서 `contributeWait` 3초 천장을 줄이는 것이 예산에서 가장 큰 지렛대다.** 커넥션 획득
300밀리초를 100으로 줄이는 것(7장)보다 자리수가 다르다.

## 11. 팀이 넣은 고침 하나가 결번 180 을 만든 경과

**J-4 는 결번 180 이 났고 J-5 는 0 이다.** 둘 사이에 바뀐 것은 한 군데다.

```
J-4   CONTRIBUTIONS_COMPLETE couponId=900001 instances=0 waitedMillis=25
J-5   CONTRIBUTIONS_COMPLETE couponId=900001 instances=2 waitedMillis=339
```

**J-4 에서 재건이 25밀리초만 기다리고 끝냈다.** 그 안에 남의 큐가 올라올 수 없으므로, 재건이
남이 쥔 티켓의 번호를 "아무도 안 쥔 번호" 로 보고 `free` 에 되살렸다. 되살린 번호가 다시
나가고 원래 티켓도 나중에 써지니, 둘 중 하나가 DB 제약에 걸려 포기로 끝난다. 그것이 결번이다.

### 11.1 고리

팀이 4.2 에서 "명부가 비어 있으면 기다리지 않는다" 를 넣었는데, **명부가 비는 이유가 재건
자신이었다.**

```
재건이 시작하며 flusher.pause 로 플러시를 멈춘다
  ->  명부를 갱신하는 것은 플러시가 배치를 집을 때(holdingQueue)다
  ->  멈춘 동안 아무도 갱신하지 않아 STALE_AFTER 뒤에 명부가 빈다
  ->  주도자가 그 빈 명부를 보고 "올라올 것이 없다" 로 읽는다
  ->  남의 큐를 안 기다리고 키를 세운다
```

**재건이 스스로 명부를 비우고 그 빈 명부를 근거로 기다림을 건너뛴다.** `measureBehind` 의
Javadoc 이 "모르는 채로 일찍 끝내는 것이 이 기능에서 가장 나쁜 결과다" 라고 적은 그 실패다.

### 11.2 고친 방법

**명부를 멈추기 전에 읽어 고정한다.** 커밋은 `768586b5` 다.

```java
OptionalInt expected = instances.live();   // 멈추기 전이라 명부가 최신이다

if (!flusher.pause(PAUSE_TIMEOUT)) { ... }
    leadWhilePaused(couponId, coupon, startedAt, expected);
```

`awaitContributions` 가 루프 안에서 다시 세지 않고 이 값을 쓴다. **유휴 시의 즉시 진행은
그대로 남는다.** 부하 중에는 멈추기 전에 실제 수가 읽히고, 발급이 없는 시간에는 0 이 읽혀
3초를 안 기다린다.

### 11.3 시험으로 고정한 것

| 시험 | 지키는 성질 |
|---|---|
| `명부는_멈추기_전에_읽는다` | `instances.live()` 가 `flusher.pause()` 보다 먼저 불린다 |
| `기다리는_동안_명부가_비어도_일찍_안_끝낸다` | 명부가 3 뒤에 0 이 되어도 천장까지 기다린다 |

### 11.4 남는 교훈

**증상을 없애는 고침과 원인을 없애는 고침을 가려야 한다.** 유휴 시간에 재건이 3초를 기다리는
것이 눈에 보이는 증상이었고, 팀은 그것을 "명부가 0 이면 기다리지 말자" 로 처리했다. 그런데
그 0 은 재건 자신이 만든 것이었으므로, 그 고침은 부하 중에 가장 위험한 순간에 기다림을
없앴다.

**정합성 지표 넷 중 결번만 이것을 잡아냈다.** 초과 발급과 1인 1매와 예상 못 한 응답은 J-4
에서도 전부 지켜졌다. DB 제약이 중복을 막아 주기 때문이고, 그래서 **막힌 자리가 결번으로
나타난다.** 회차마다 결번을 보는 것이 이번에 값을 했다.
