# 선착순 발급이 쓰는 Redis 키

**이 문서는 키 하나하나를 설명한다.** 무엇을 담는지, 왜 필요한지, 언제 값이 들어가고 언제 빠지는지다.

왜 그렇게 설계했는지는 [coupon.md](coupon.md) 에 있다. 코드와 SQL 은 실제 파일에 있고 여기서는 **이름과 값만 괄호로 가리킨다.**

---

## 0. 먼저 알아야 할 것 넷

처음 보는 사람을 위한 배경이다. **이미 아는 내용이면 1장으로 건너뛰면 된다.**

### 순번

**한정 수량 쿠폰을 락 없이 지키려고 발급마다 `1, 2, 3...` 번호를 붙인다.** 이것을 순번이라 부른다 (`member_coupon.issue_seq`).

DB 는 "이 쿠폰의 행이 1만 개를 넘지 마라" 를 직접 못 건다. 대신 **행마다 `1..1만` 안의 번호를 하나씩 갖게 하고 그 번호가 겹치지 않게 하면** 결과적으로 행이 1만 개를 못 넘는다. 그것을 지키는 것이 유니크 제약과 체크 제약이다 (`uk_mc_coupon_seq`, `chk_mc_issue_seq`).

**그 번호를 나눠 주는 자리가 Redis 다.** 그래서 이 문서의 키들이 있다.

### 발급 한 건이 지나는 길

```
요청 스레드    Redis 에서 순번을 받는다 -> 큐에 넣고 잔다
플러시 스레드   큐에서 여러 건을 모아 DB 에 한 번에 쓴다 -> 요청 스레드를 깨운다
```

**둘이 나뉘어 있다는 것이 이 문서 전체의 전제다** (`CouponIssueService`, `CouponIssueFlusher`). 요청 스레드는 실패를 직접 보지 못하고, **Redis 뒷정리는 전부 플러시 스레드가 한다** (`CouponSeqCommitter`).

### 확정 표시

**DB 에 행이 만들어진 뒤 Redis 에 남기는 "이 사람은 발급이 끝났다" 는 표시다.** 값 뒤에 `":1"` 을 붙인다. 이것이 있으면 그 회원의 재요청이 DB 까지 안 가고 Redis 에서 끝난다.

### 회수와 재건

```
회수   번호만 받고 사라진 사람의 번호를 뺏어 다른 사람에게 주는 일   (기준 시간 reclaim-after: 60s)
재건   Redis 가 키를 잃었을 때 DB 를 보고 다시 세우는 일            (CouponSeqRebuilder)
```

## 1. 키 여섯

이벤트 하나가 키 여섯을 쓴다. **앞의 넷은 발급이 도는 동안 쓰고, 뒤의 둘은 재건이 도는 동안만 쓴다.** 이름을 만드는 곳은 한 군데다 (`CouponSeqKeys`).

| 키 | 자료구조 | 담는 것 |
|---|---|---|
| `coupon:{id}:counter` | 문자열 | 마지막으로 발행한 순번 |
| `coupon:{id}:seq` | 해시 | 회원 -> 그 회원의 순번 |
| `coupon:{id}:pending` | 정렬 집합 | 번호는 받았는데 발급 여부를 모르는 회원 -> 번호를 준 시각 |
| `coupon:{id}:free` | 정렬 집합 | 쓰이지 않은 것이 확인된 순번 |
| `coupon:{id}:rebuild` | 문자열 | 재건 락 |
| `coupon:{id}:rebuild:queued` | 해시 | 재건 중에 각 인스턴스가 올린 자기 큐 |

**무엇이 각 키를 움직이는지는 이렇다.** 자세한 조건은 키별 절에 있다.

| 키 | 값이 들어가는 계기 | 값이 빠지는 계기 |
|---|---|---|
| `counter` | 아직 아무도 안 쓴 번호를 새로 발행한다 | 그 번호가 준비한 수량을 넘어 곧바로 되돌린다 |
| `seq` | 회원이 번호를 받는다 | 그 번호를 남이 쓰고 있었다. 회수가 짚었다. 이벤트를 열거나 닫는다 |
| `pending` | 회원이 번호를 받는다 | 그 회원이 그 번호로 발급됐는지가 정해진다 |
| `free` | 이미 쿠폰을 가진 회원이 들고 온 새 번호가 버려진다 | 새 번호를 뽑기 전에 여기부터 꺼내 쓴다 |
| `rebuild` | 재건이 시작된다 | 재건이 끝나거나 만료 30초가 지난다 |
| `rebuild:queued` | 인스턴스가 자기 큐를 올린다 | 재건이 넷을 다 세운다 |

**`counter` 만 계기가 좁다.** 나머지는 번호가 나가면 따라 움직이는데, 이 키는 **번호를 새로 만들 때만** 오른다.

## 2. 키 이름과 값의 모양

**쿠폰 아이디는 키 이름에 들어가고, 회원 아이디는 해시의 필드로 들어간다.** 쿠폰 1234 라면 이렇게 들어 있다.

```
coupon:1234:counter   "6"
coupon:1234:seq       {5001: "6:1", 5002: "7"}     필드 = 회원 아이디,  값 = 순번
coupon:1234:pending   {"5002": 1757212345678}      값 = 회원 아이디,   점수 = 준 시각(ms)
coupon:1234:free      {"6": 6}                     값 = 순번,         점수 = 순번
```

**값 쪽에는 쿠폰 아이디가 한 번도 안 나온다.** 회원 아이디와 순번과 시각뿐이다.

**둘 다 요청이 들고 오므로 되짚을 일이 없다.** 쿠폰 아이디는 경로 변수이고 회원 아이디는 인증에서 나온다.

**회원별로 키를 나누지 않은 이유는 개수와 정리 비용이다.** 1만 명이 받아도 키는 넷이라 이벤트가 끝나면 넷만 지우면 된다. 회원별 키였다면 전체를 훑어야 한다.

**이름의 `{id}` 는 문서의 자리 표시다.** 실제 키에는 중괄호가 없다 (`coupon:1234:seq`). Redis 클러스터로 옮기면 한 쿠폰의 네 키가 서로 다른 노드로 흩어져 문제가 되는데, **지금은 클러스터가 아니라 해당 없다.** 이름을 만드는 곳이 한 곳뿐이라 그때 거기만 고치면 된다.

## 3. `counter` - 번호를 만든다

### 무엇을 하나

**하나 올려서 그 결과를 발급 번호로 준다.** 그래서 이 키가 담는 값은 다음에 나갈 번호가 아니라 **마지막으로 발행한 순번**이다.

**그리고 이벤트의 문이다.** 순번 확보 스크립트의 첫 줄이 이 키가 있는지 묻고, 없으면 번호를 안 주고 거절한다 (`coupon-issue-seq.lua`, 반환 `-2`).

**넷의 수명도 이 키가 들고 있다.** 나머지 셋은 만들어질 때 이 키의 만료 시각을 물려받는다.

### 왜 필요한가

**번호가 없으면 상한을 지키려고 쿠폰 한 행에 락을 걸어야 한다.** 그러면 그 행에 요청이 몰려 줄을 서고 **초당 약 330 건이 천장**이 된다. 번호를 미리 나눠 주면 각자 자기 행만 넣으므로 서로 경합하지 않는다.

### 언제 값이 바뀌나

**네 경우다.**

```
관리자가 이벤트를 연다                        0 으로 세운다        (CouponSeqInitializer.prepare)
아직 아무도 안 쓴 번호를 새로 발행한다         1 오른다
새로 발행한 번호가 준비한 수량을 넘었다        방금 올린 것을 곧바로 되돌린다
Redis 가 키를 잃어 DB 에서 다시 세운다         MAX(issue_seq) 를 넣는다   (CouponSeqRebuilder)
```

**두 번째가 본업이고, 조건이 넷이다.**

```
1  이벤트가 열려 있다              이 키가 없으면 아무것도 안 하고 거절한다
2  그 회원이 아직 번호가 없다      있으면 그 번호를 그대로 돌려주고 끝난다
3  다시 내줄 번호가 하나도 없다    있으면 그것부터 나가고 이 키는 안 움직인다
4  새 번호가 준비한 수량 안이다    넘으면 세 번째 경우로 넘어간다     (coupon.total_quantity)
```

**번호는 나가는데 이 값이 안 오르는 경우가 셋이다.**

```
같은 회원이 다시 요청한다             이미 받은 번호를 그대로 돌려준다
쓰이지 않은 것이 확인된 번호를 준다    이미 발행됐던 번호라 새로 만들 필요가 없다
소진 뒤 남의 번호를 회수해서 준다      올렸다가 곧바로 되돌린 뒤 뺏은 번호를 준다
```

**그래서 이 값은 "몇 명에게 나갔나" 가 아니라 "어디까지 새로 발행했나" 다.**

### 없으면 무슨 일이 나나

**번호가 1 부터 다시 나가고, 그 번호는 이미 남이 쓰고 있어 DB 가 막는다** (`uk_mc_coupon_seq`). 서버는 멀쩡한데 발급만 마비된다.

**그래서 이 키가 없으면 아예 번호를 안 준다.** 그 거절이 곧 재건을 띄우는 신호가 된다 (`CouponSeqRebuildTrigger`).

**메모리가 모자라면 이 키도 버려질 수 있다.** 만료가 걸린 키를 버리는 정책을 쓰는데 (`maxmemory-policy volatile-lru`) 이 키에도 만료가 걸려 있기 때문이다. 그것을 막는 것은 정책이 아니라 넉넉한 메모리이고, 그래도 사라졌을 때를 받치는 것이 위의 거절과 재건이다.

## 4. `seq` - 누가 몇 번을 받았나

### 무엇을 하나

**회원을 필드로 두고 그 회원의 순번을 값으로 담는다.** 값의 모양이 세 상태를 가른다.

```
필드가 없다   아직 번호를 안 받았다             -> 새 번호를 준다
"6"           번호는 받았고 발급 여부를 모른다   -> 그 번호로 다시 진행한다
"6:1"         발급이 끝났다                    -> DB 를 안 가고 그 자리에서 이미 발급으로 답한다
```

**`":1"` 의 `1` 은 아무 뜻이 없다.** 읽는 쪽 둘 다 콜론이 있는지만 본다 (`coupon-issue-seq.lua`, `CouponSeqAllocator`).

### 왜 필요한가

**재시도가 새 번호를 태우지 않게 하려는 것이다.** 없으면 이런 일이 난다.

```
A 가 6번을 받고 응답 직전에 연결이 끊긴다
A 가 재시도 -> 새 번호 7번으로 발급 성공
6번은 아무에게도 가지 않는다
```

**그리고 1인 1매 판정을 Redis 에서 끝낸다.** 확정 표시가 붙은 회원의 재요청은 DB 까지 안 간다.

### 가운데 상태가 있어야 한다

**번호를 받았다는 이유만으로 거절하면 안 된다.** 발급에 실패해도 이 값이 남는 경우가 있어서, 거절했다가는 정당한 발급을 막는다. **거절은 확정 표시가 붙었을 때만이다.**

**한 필드에 둘을 담은 것은 갈라질 수 없게 하려는 것이다.** 필드를 둘로 나누면 한쪽만 남은 상태가 생기고, 한 번 읽어서 둘 다 답하지도 못한다.

### 정확성을 지키는 장치는 아니다

**1인 1매는 DB 의 유니크 제약이 지킨다** (`uk_mc_coupon_member`). Redis 가 이 키를 통째로 잃어도 재시도가 새 번호를 들고 오면 두 번째 행이 그 제약에 막힌다.

**이 키가 아끼는 것은 순번이지 정확성이 아니다.** 이 구분이 없으면 Redis 장애를 실제보다 무겁게 보게 된다.

### 언제 담나

**회원이 번호를 받는 순간이다. 예외가 없다.** 번호를 어디서 얻었든 같다.

```
새로 발행한 번호를 받았다              -> "6"
쓰이지 않은 것이 확인된 번호를 받았다   -> "6"
소진 뒤 회수한 남의 번호를 받았다       -> "6"
```

**확정 표시가 붙는 경우가 둘이다.**

```
그 회원의 행이 DB 에 만들어졌다              한 배치의 회원 전부를 한 번에 갱신한다
                                            (CouponSeqCommitter.markCommitted)
이미 쿠폰을 가진 회원이 새 번호를 들고 왔다   이번 번호가 아니라 원래 갖고 있던 번호로 고쳐 넣는다
                                            (CouponSeqCommitter.returnAndRepair)
```

**같은 회원이 다시 요청해도 이 키는 안 바뀐다.** 이미 값이 있으면 그것을 돌려주고 끝나므로, 열 번을 다시 보내도 값도 그대로고 카운터도 안 오른다.

### 언제 빠지나

```
그 번호를 남이 쓰고 있어서 이 회원이 새 번호를 받아야 한다   (CouponSeqCommitter.dropMappings)
소진 뒤, 확정 표시 없이 기준 시간을 넘긴 회원을 회수가 짚었다
관리자가 이벤트를 연다        지난 이벤트의 값을 먼저 치운다   (CouponSeqInitializer.prepare)
이벤트가 끝나고 정리 배치가 돈다                            (CouponSeqInitializer.clear)
```

**세 번째를 빠뜨리면 새 이벤트에서 아무도 번호를 못 받는다.** 지난 이벤트의 값이 남아 있으면 그 회원들이 이미 받은 것으로 보인다.

**회수는 확정 표시가 붙은 것을 안 지운다.** 실제로 발급이 끝난 번호라 뺏으면 두 번 나간다.

## 5. `pending` - 아직 답을 모르는 사람들

### 무엇을 하나

**번호는 받았는데 발급됐는지 아직 모르는 회원의 목록이고, 점수가 번호를 준 시각이다.**

이 하나가 네 가지를 한다.

```
아직 답을 모르는 사람의 명단
회수 대상 목록          기준 시간을 넘긴 것을 골라낸다     (reclaim-after: 60s)
소진이 최종인지 판정      비어 있으면 다시 나올 번호가 없다는 뜻이다 -> 410
재건의 입력             각 인스턴스 큐에 남은 티켓이 곧 이 집합의 정의다
```

### 왜 필요한가

**번호가 묶여서 아무에게도 안 가는 경우가 있다.**

```
클라이언트가 연결을 끊었다     그 사용자가 안 돌아온다
DB 응답이 끊겨 결과를 모른다   커밋됐을 수도 있어 함부로 못 되돌린다
앱이 갑자기 죽었다             뒷정리가 돌 기회가 없었다
```

**원인은 다른데 결과가 같다.** 그 번호가 이벤트 끝까지 묶인다. **원인을 구분할 수 없으므로 시간으로 판정하고, 그 시각을 담는 자리가 여기다.**

**`seq` 만으로는 안 된다.** `seq` 는 언제 받았는지를 못 담고, 확정 표시가 붙은 값은 재요청 응답에 필요해 지울 수도 없다.

### 시각을 Redis 가 매긴다

**점수를 쓰는 인스턴스와 그것을 읽어 판정하는 인스턴스가 다르기 때문이다.** 앱 시계를 쓰면 시계가 어긋난 한 대가 아직 살아 있는 요청의 번호까지 오래된 것으로 보고 뺏는다. 그래서 스크립트가 Redis 시각을 받아 쓴다 (`TIME`).

**재건만 예외다.** 원래 시각을 복원할 수 없어 그때의 앱 시각을 넣는다 (`CouponSeqRebuilder.writePending`). 그만큼 그 티켓들의 회수가 뒤로 밀린다.

### 만료가 아니라 점수인 이유

**만료는 항목을 지우는 동작이다.** 지워지는 순간 회원 아이디를 잃어 그 회원의 번호를 읽을 수 없게 된다. **풀어줄 대상을 잃어버리는 셈이다.**

**점수는 판정만 하고 지우지 않는다.** 번호를 읽어 넘긴 뒤에 지울 수 있고, 기준 시간을 읽는 쪽이 정하므로 나중에 바꾸기도 쉽다.

### 언제 담나

**`seq` 와 같은 순간이다.** 회원이 번호를 받으면 여기에도 반드시 들어온다. 둘을 한 스크립트 안에 둔 것이 그 이유다. **"이 번호는 이 사람 자리다" 와 "아직 발급됐는지 모른다" 가 갈라지면 어느 한쪽만 남은 상태가 생긴다.**

**같은 회원이 다시 요청해도 점수는 안 바뀐다.** 이미 값이 있으면 그것을 돌려주고 끝나기 때문이다. **그게 맞는 동작이다.** 갱신되면 재시도를 계속하는 클라이언트의 번호가 영영 회수되지 않는다.

**점수가 다시 찍히는 경우는 하나뿐이다.** 그 회원의 값이 `seq` 에서 지워진 뒤에 다시 온 경우다.

### 언제 빠지나

**그 회원이 그 번호로 발급됐는지가 정해지면 빠진다.** 됐든 안 됐든 마찬가지다.

```
그 회원의 행이 DB 에 만들어졌다               -> 됐다        (markCommitted)
이미 쿠폰을 가진 회원이라 이번 번호가 버려졌다  -> 안 됐다     (returnAndRepair)
그 번호를 남이 쓰고 있었다                    -> 안 됐다     (dropMappings)
소진 뒤 회수가 기준 시간을 보고 판정했다        -> 안 됐다고 본다
```

**그래서 남아 있는 것이 곧 아직 답을 모르는 것이고, 그게 이 키의 전부다.**

**`seq` 의 확정 표시와는 다른 이야기다.** 그쪽은 **발급됐다**는 표시라 답이 "됐다" 일 때만 붙는다. 여기서 빠지는 것은 **답이 나왔다**는 뜻이라 넷 다 해당한다.

### 언제 여기서 번호를 꺼내 주나

**조건이 다섯이고 다 서야 그 요청자가 번호를 받는다.**

```
1  요청이 도착했다                  회수는 스스로 안 돈다.  누가 와야 돈다
2  그 회원이 아직 번호가 없다
3  다시 내줄 번호가 하나도 없다      있으면 그쪽이 먼저다.  여기까지 안 온다
4  카운터가 이미 최대다              새 번호를 뽑았다가 수량을 넘어 되돌린 상태
5  기준 시간(60초)을 넘긴 항목이 있고, 확정 표시가 안 붙어 있다
```

**60초는 소진 시점부터 세지 않는다.** 점수가 그 사람이 번호를 받은 시각이라 시계는 소진 훨씬 전부터 돌고 있다.

```
10:00:00   5001 이 6번을 받는다.  점수 = 10:00:00
10:00:05   5001 이 사라진다
10:03:00   재고가 다 나간다
10:03:01   다른 요청이 온다 -> 5001 의 점수가 3분 지났다 -> 곧바로 회수된다
```

**대부분 소진되는 순간 이미 기준을 넘겨 있다.** 늦어지는 것은 소진 직전 60초 안에 번호를 받은 사람들뿐이다.

**한 요청이 항목 하나만 본다** (`LIMIT 0 1`). 100명이 묶여 있으면 100번의 요청이 와야 100개가 풀린다.

**짚은 항목에 확정 표시가 붙어 있으면 번호를 안 준다.** 실제로 발급이 끝난 번호라 뺏으면 두 번 나간다. 그 항목은 목록에서 빼기만 하고 그 요청자는 소진 응답을 받는다. **청소는 됐으니 다음 요청이 그다음 것을 본다.**

**소진이 트리거인 덕분에 평상시 비용이 0 이고 주기 배치도 필요 없다.** 대신 요청이 와야 돈다. 소진 뒤 트래픽이 완전히 빠지면 그 번호는 키가 만료될 때까지 남는다.

## 6. `free` - 확실히 안 쓰인 번호

### 무엇을 하나

**발행은 됐는데 아무도 안 쓴 것이 확인된 순번을 담는다.** 낮은 번호부터 다시 나간다.

**"확인된" 이 이 키의 조건이다.** 안 쓰였을 것 같은 번호가 아니라, 그 번호로 행이 안 만들어졌음이 가려진 것만 들어온다.

```
free      쓰이지 않은 것이 확인된 순번    가려내서 담는다.  바로 다시 나간다
pending   아직 답을 모르는 순번          시간으로 판정한다.  틀리면 DB 제약이 잡는다
```

**`coupon.md` 는 여기 담는 동작을 "반납" 이라고 부른다** (`returnAndRepair` 의 이름도 거기서 왔다). 다만 번호를 쥔 사람이 돌려주는 것이 아니라 **실패를 잡은 플러시 스레드가 대신 담는 것**이라, 이 문서는 그 말을 안 쓴다.

### 왜 필요한가

**카운터를 하나 내리는 것으로는 못 고친다.**

```
A 가 6번, B 가 7번을 받는다
A 가 실패해서 카운터를 하나 내린다 -> 카운터 6.  즉 다음에 발행할 순번은 7
C 가 요청한다 -> 7번.  B 가 쥔 번호다 -> 충돌
```

**내리는 것은 맨 위 번호를 지우는 셈이지 A 의 6번이 아니다.** 카운터는 어디까지 나갔는지만 알고 그중 어느 것이 안 쓰였는지는 모른다. **그래서 안 쓰인 번호를 지목해 담는 자리가 따로 필요하다.**

**리스트가 아니라 정렬 집합인 이유가 있다.** 리스트는 같은 번호가 두 번 들어갈 수 있고 그러면 두 사람이 같은 번호를 받는다. 정렬 집합은 같은 값을 하나로 유지한다.

### 언제 담나

**이미 그 쿠폰을 가진 회원이 새 번호를 들고 와서, 그 새 번호가 안 쓰인 채 버려질 때다.** 평상시에 담는 경우는 이것뿐이다 (`CouponSeqCommitter.returnAndRepair`).

거기까지 오는 조건이 넷이다.

```
1  묶어서 넣던 배치가 DB 에서 실패해 한 행씩 다시 넣는 중이다   (CouponIssueFlusher.flushOneByOne)
2  이 회원의 행을 넣다가 유니크 제약에 걸렸다                  확정적 실패다.  되돌려진 것이 확실하다
3  그 회원의 행을 읽어 보니 이미 있다                         uk_mc_coupon_member 쪽이다
4  그 행의 순번이 이번에 받은 번호와 다르다                    이번 번호로는 행이 안 생겼다
```

**담는 것은 이번에 받았다가 못 쓴 번호**이지 그 회원이 원래 갖고 있던 번호가 아니다.

**이 경우가 나오려면 그 회원의 값이 `seq` 에서 사라져 있어야 한다.** 남아 있었다면 원래 번호를 그대로 돌려받아 새 번호를 안 받았을 것이다.

**행은 있는데 `seq` 값만 없는 상태를 만드는 길이 둘이다.**

```
확정 표시가 실패한 뒤 회수가 그 값을 가져갔다
  행은 만들어졌는데 표시가 없어서, 회수가 버려진 것으로 보고 지운다

카운터는 살아남고 seq 만 뒤처졌다
  복제 지연이 남은 채 승격됐거나 일부만 버려진 경우다
```

**둘째가 통째 손실과 다르다는 것이 중요하다.** 통째로 잃으면 카운터도 함께 가서 문이 닫히고, 재건이 DB 를 보고 값을 확정 표시까지 붙여 되살린다. **그래서 이 갈래에 안 온다.** 카운터가 살아 문이 열려 있는 부분 손실에서만 생기고, 그때는 재건을 띄우는 신호조차 안 나온다 ([coupon.md](coupon.md) 10장 "이 장이 다루지 않는 것").

**그래서 정상 이벤트에서는 거의 안 담긴다.**

**DB 에는 이 번호의 흔적이 아예 없다.** 행이 안 만들어졌기 때문이다. "6번이 비어 있다" 는 DB 도 알지만 **"6번이 한 번 나갔다가 안 쓰였다" 는 이 키만 안다.**

### 언제 안 담나

| 실패 | 왜 안 담나 |
|---|---|
| 순번이 같다 | **내가 이미 그 번호로 썼다.** 담으면 실제 행이 쓰는 번호를 남에게 내준다 |
| 행이 없다 | **남이 쓰고 있다.** 담으면 또 다른 회원이 받아 같은 충돌을 되풀이한다 |
| 행을 못 읽었다 | 가르지 못했다. 손대면 잘못된 쪽을 고를 수 있고 **담는 것은 못 되돌린다** |
| DB 응답이 끊겼다 | **커밋 여부를 모른다.** 이미 커밋됐다면 남이 쓰는 번호를 내준다 |
| DB 회로가 열렸다 | 담아도 안전하지만 **값을 두면 재시도가 같은 번호로 온다.** 그게 낫다 |
| 큐가 꽉 찼다 | 번호를 받기 전에 끊는다 (`queue-capacity`). **담을 번호가 아예 없다** |

**"안 쓰였다" 를 알 수 없으면 안 담는다.** 모르는 번호는 `pending` 이 시간으로 판정한다.

### 언제 여기서 꺼내 쓰나

**번호를 내주는 길에서 가장 먼저 본다.** 조건이 둘뿐이다.

```
1  요청이 도착하고 그 회원이 아직 번호가 없다
2  이 키에 담긴 것이 하나라도 있다        낮은 번호부터 꺼낸다 (ZPOPMIN)
```

**새 번호를 뽑는 것보다 앞이다.** 그래서 여기 뭐가 있으면 카운터가 안 움직이고 회수도 안 돈다. **소진 상태여도 마찬가지다.**

**낮은 번호부터 꺼내는 것은 간격을 줄이려는 것이다.** `MAX(issue_seq)` 와 실제 발급 수가 덜 벌어진다.

**비어 있을 때 확인하는 비용은 0 에 가깝다.** 그래서 평상시 이 키가 비어 있어도 정상 경로를 느리게 하지 않는다.

### 그 판정이 틀릴 수 있는 자리

**위 조건 3번과 4번이 답하는 것은 "이 회원의 행" 이지 "이 번호를 쓰는 행" 이 아니다.**

평소에는 둘이 같은 이야기다. **한 번호는 한 사람에게만 나가기 때문**이다. 그 전제를 깨는 것이 회수다.

```
M 이 A 번으로 발급됐는데 확정 표시가 실패했다
회수가 M 의 값을 지우고 A 를 남에게 넘긴다        M 은 행이 있고 값이 없다

M 이 다시 온다.  소진 상태다
회수가 이번엔 N 의 B 번을 짚어 M 에게 준다        B 는 실제로 N 이 쓰고 있다

M 이 행을 넣으려니 두 제약이 동시에 깨진다        uk_mc_coupon_member 와 uk_mc_coupon_seq
M 의 행을 읽어 보니 A 번이라 B 와 다르다 -> B 를 담는다   <- 잘못된 판정이다
```

**확정 표시 실패가 서로 다른 회원에게 두 번 나야 성립한다. 좁다.**

**그리고 스스로 정정된다.** 잘못 담긴 B 는 다음 요청자에게 나가고, 그 사람이 순번 충돌에 부딪히면서 B 의 진짜 주인이 되살아난다 (`CouponIssueFlusher.repairSeqTaken`). **초과 발급도 1인 2매도 안 난다.**

**가르려면 그 회원의 행과 그 번호의 행을 한 번에 물으면 된다** (`WHERE member_id = ? OR issue_seq = ?`). 다만 조건이 둘로 갈라져 인덱스를 제대로 타는지 확인하고 넣어야 한다.

## 7. 넷은 함께 살고 함께 죽는다

**하나만 사라지면 나머지가 거짓말을 한다.**

```
counter 만 사라짐   번호가 1 부터 다시 나간다.  이미 쓴 번호와 충돌한다
seq 만 사라짐       재시도가 새 번호를 태운다.  1인 1매 판정도 놓친다
free 만 사라짐      다시 내줄 순번이 증발한다.  그만큼 덜 나간다
pending 만 사라짐   묶인 번호를 영영 못 찾는다
```

**수명은 `counter` 가 들고 나머지 셋이 따라간다.** 이벤트를 여는 시점에는 `counter` 밖에 없어서 넷에 한꺼번에 만료를 걸 수가 없다. **그래서 나머지 셋이 만들어지는 자리에서 `counter` 의 만료 시각을 읽어 물려받는다.**

```
counter   이벤트를 열 때 건다                      (issue_end_at + 60초)
seq       번호를 줄 때 만들어지면서 물려받는다
pending   같다
free      번호를 담을 때 만들어지면서 물려받는다     (CouponSeqCommitter 의 inheritCounterTtl)
```

**값을 앱이 다시 넘기지 않고 `counter` 에서 읽어 오므로, 관리자가 마감을 바꾸면 그 뒤에 만들어지는 키가 저절로 새 마감을 따라간다.**

**1분은 꼬리를 덮는 값이다.** 마감 직전에 들어온 요청이 Redis 에 닿고 마지막 배치가 뒷정리를 마치는 데까지다.

**마감 시각이 없는 쿠폰은 애초에 선착순이 아니다.** 선착순은 `total_quantity` 와 `issue_end_at` 이 둘 다 있는 것으로 정의된다.

**만료는 그물일 뿐이다.** 주 경로는 종료 배치가 지우는 것이고, 만료는 그 배치가 안 돌았을 때를 받친다.

## 8. 발급 한 건이 키를 어떻게 바꾸나

정상 경로다. **1번이 통째로 한 덩어리라 그 안에는 아무도 끼어들 수 없다** (`coupon-issue-seq.lua`).

```
1  Redis 에서 번호를 받는다
     이벤트가 열려 있나 확인한다
     이 회원이 이미 번호가 있나 본다     있으면 그 번호를 돌려주고 끝
     다시 내줄 번호가 있나 본다          있으면 그것을 준다
     없으면 카운터를 올려 새로 만든다
     seq 에 "6" 을 적고 pending 에 지금 시각을 적는다
     둘에 counter 의 만료 시각을 물려준다

2  큐에 넣고 요청 스레드는 잔다                        (commit-wait: 800ms 까지)

3  플러시 스레드가 DB 에 행을 만든다                    (batch-window: 20ms, batch-size: 500)

4  seq 값을 "6:1" 로 바꾸고 pending 에서 뺀다           (markCommitted, 왕복 둘)

5  요청 스레드를 깨워 200 과 순번을 준다
```

**`seq` 값은 3번보다 먼저 붙고 확정 표시는 3번보다 뒤에 붙는다.** 값이 3번 뒤에 붙는다면 그 사이에 앱이 죽었을 때 번호가 누구 것인지 알 방법이 사라진다.

**3번과 4번 사이가 끊기는 경우는 [coupon.md](coupon.md) 3장이 다룬다.**

### 실패하면 무엇이 달라지나

| 실패 | counter | seq | pending | free |
|---|---|---|---|---|
| 수량 초과 | 되돌림 | - | - | - |
| 이미 쿠폰이 있고 순번이 다름 | - | 실제 번호로 고침 | 뺌 | **번호를 넣음** |
| 이미 쿠폰이 있고 순번이 같음 | - | 확정 표시를 마저 붙임 | 뺌 | - |
| 그 번호를 남이 쓰고 있음 | - | 지움. 주인은 되살림 | 뺌 | - |
| DB 응답이 끊김 | - | 그대로 | **그대로 남음** | - |
| DB 회로가 열림 | - | 그대로 | **그대로 남음** | - |
| 행을 못 읽음 | - | 그대로 | 그대로 남음 | - |

**마지막 셋이 "커밋 여부를 모른다" 다.** 아무것도 안 건드리는 것이 처리이고, 그래서 `pending` 에 남아 나중에 시간으로 판정된다.

## 9. 재건이 쓰는 키 둘

**성격이 위 넷과 다르다.** 재건은 넷이 없을 때 도는 일이라 물려받을 수명이 없고, 이 둘은 자기 만료로 살다가 재건이 끝나면 사라진다.

### `rebuild` - 재건 락

**동시에 "재건 중" 표시이기도 하다.** 락을 못 잡은 인스턴스는 이 키가 있는 것을 보고 자기 큐를 올린다. **플러시가 배치마다 한 번씩 확인하는데** (`CouponSeqRebuildTrigger.checkAfterFlush`), 그 확인이 없으면 **요청을 못 받는 인스턴스가 자기 큐를 영영 안 올린다.**

**언제 담나.** 카운터가 사라진 것을 알아챈 인스턴스가 재건을 시작하려 할 때다.

```
1  요청이 "이벤트가 안 열려 있다" 는 답을 받았다   또는 플러시가 이 키를 봤다
2  DB 를 봐서 정말 열려 있어야 할 이벤트인지 가른다   (coupon.is_active, total_quantity)
3  없을 때만 쓴다    먼저 쓴 한 대만 성공하고 나머지는 큐만 올린다
```

**두 번째가 없으면 안 된다.** 카운터가 없다는 것은 "잃었다" 뿐 아니라 **"아직 안 열었다"** 도 뜻하므로, DB 를 봐야 둘이 갈린다.

**언제 빠지나.** 재건이 끝나면서 자기가 쓴 값인지 확인하고 지운다. 그 전에 프로세스가 죽으면 만료가 대신 푼다 (`rebuild-contribute-wait: 3s` 의 10배인 30초).

### `rebuild:queued` - 각 인스턴스의 큐

**DB 만으로 재건할 수 없어서 있다.** 앱 큐에 아직 행이 안 된 번호가 떠 있는데, DB 만 보고 세우면 그 번호들을 **아무도 안 쥔 것으로 보고 남에게 다시 내준다.**

**회원 하나의 티켓은 한 인스턴스에만 있으므로** 여럿이 같은 해시에 써도 겹치지 않는다.

**언제 담나.** 재건이 도는 것을 알아챈 인스턴스가 자기 큐에 남은 티켓을 올릴 때다 (`CouponSeqContributor`). **주도하는 쪽도 올리므로 참여하는 모든 인스턴스가 각각 한 번씩 쓴다.**

```
1  이 인스턴스가 재건 중인 것을 알았다
2  자기 플러시를 멈춘다             멈추지 못하면 올리지 않고 건너뛴다
3  자기 큐에서 이 쿠폰의 티켓을 골라낸다
4  회원 -> 순번을 한 번에 올린다
5  플러시를 다시 흐르게 한다
```

**멈추는 이유가 있다.** 훑는 사이에 플러시가 같은 티켓을 DB 로 내리면, 재건이 이미 확정된 것을 미확정으로 덮는다. **그러면 회수가 그 번호를 남에게 넘겨 같은 번호가 두 번 나간다.**

**빈 큐면 안 쓴다.**

**언제 빠지나.** 주도하는 인스턴스가 넷을 다 세운 뒤 지운다.

### 재건이 넷을 세우는 순서

```
1  락을 잡는다
2  각 인스턴스가 자기 큐를 올린다 (3초 기다린다)
3  큐를 읽고 DB 를 읽는다              큐가 먼저다
4  seq 를 쓴다      행이 있으면 확정 표시까지, 큐에 있으면 번호만
5  pending 을 쓴다  큐에 있던 것만
6  free 를 쓴다     행에도 큐에도 없는 번호
7  counter 를 쓴다  = MAX(issue_seq).  이 순간 문이 열린다
8  큐 키를 지우고 락을 푼다
```

**큐를 DB 보다 먼저 읽는다.** 티켓은 큐에서 DB 로만 가고 반대로는 안 간다. 큐를 먼저 읽으면 그사이 넘어간 티켓이 양쪽에 다 잡히지만, **DB 를 먼저 읽으면 어디에도 안 잡혀 구멍이 된다.**

**카운터를 마지막에 쓰는 것이 곧 문을 여는 것이다.** 그 전까지 모든 요청이 거절된다. **요청을 막는 장치를 새로 만들지 않았다.** 이벤트의 문이 이미 그 역할을 한다.

---

## 10. 이벤트가 끝날 때

**순서가 있다. 키를 먼저 지우면 지각 요청이 카운터 없는 Redis 를 친다.**

```
1  이벤트 스위치를 끈다              관리자가 누르거나 마감이 지나 배치가 끈다 (coupon.is_active)
2  60초를 기다린다                   진행 중인 배치의 커밋과 뒷정리가 끝나기를 기다린다
3  발급 수를 실제 행 수로 맞춘다      (coupon.issued_quantity)
4  네 키를 지운다                    (CouponSeqInitializer.clear)
```

**4번을 앞당기면 안 된다.** 카운터가 없는 상태에서 지각 요청이 닿으면 번호가 1 부터 다시 나가고, 그 번호는 이미 남이 쓴 것이라 DB 가 막는다.

**지울 때는 백그라운드로 넘긴다** (`UNLINK`). 1만 필드 해시를 그 자리에서 해제하면 그동안 Redis 가 멈춘다.

**정리 대상은 DB 로 찾는다.** Redis 키가 남아 있는지로 찾으면 만료가 키를 먼저 지웠을 때 대상을 놓쳐 3번을 건너뛴다.

## 11. 발급 요청 하나가 Redis 를 네 번 친다

```
인증 커트라인 조회      accessTokenValidAfter:{role}:{id}     요청 예산 밖
순번 확보              스크립트 하나로 끝낸다                  요청 예산 밖
확정 표시              seq 에 ":1" 을 붙인다                  요청 예산 안
미확정 해제            pending 에서 뺀다                      요청 예산 안
```

**첫 키는 쿠폰 도메인의 것이 아니다.** 인증 필터가 토큰 무효화 시각을 읽는 자리인데, **발급 응답 시간에 그 왕복이 그대로 들어가므로** 예산을 셀 때는 함께 센다.

**뒤의 둘은 요청 스레드를 깨우기 전에 친다.** 그래서 그 시간이 요청 예산 안에 든다 (`commit-wait: 800ms`, Redis `timeout: 100ms` 씩 둘). 산식은 `application-coupon.yml` 의 주석에 있다.

**연결은 인스턴스당 하나다.** 동접 2만이어도 접속은 기동 때와 재접속 때만 일어난다.

**순번 확보를 스크립트 하나로 끝내는 이유가 있다.** 나눠 부르면 같은 회원의 동시 요청 둘이 둘 다 "이 회원은 번호가 없다" 를 보고 각자 번호를 받는다.
