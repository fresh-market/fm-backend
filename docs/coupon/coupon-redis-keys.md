# 선착순 발급이 쓰는 Redis 키

발급 경로가 만지는 키를 한곳에 모은다. **키마다 왜 필요한지, 없으면 무슨 일이 나는지, 그리고 어느 코드가 언제 쓰는지**를 적는다.

설계의 근거는 [coupon.md](coupon.md) 3장과 10장에 있고, 이 문서는 그것이 코드에서 어떤 모양으로 서 있는지를 기록한다. 판단이 갈리면 `coupon.md` 가 기준이다.

---

## 1. 한눈에 보기

이벤트 하나가 키 여섯을 쓴다. **앞의 넷은 발급이 도는 동안 살아 있고, 뒤의 둘은 재건이 도는 동안만 산다.**

| 키 | 자료구조 | 담는 것 | 언제 사는가 |
|---|---|---|---|
| `coupon:{id}:counter` | 문자열 | 마지막으로 발행한 순번 | 이벤트를 여는 순간부터 |
| `coupon:{id}:seq` | 해시 | 회원 -> 순번 | 첫 번호가 나가는 순간부터 |
| `coupon:{id}:pending` | 정렬 집합 | 아직 커밋 안 된 회원 -> 번호를 준 시각 | 첫 번호가 나가는 순간부터 |
| `coupon:{id}:free` | 정렬 집합 | 쓰이지 않은 것이 확인된 순번 | 그런 순번이 처음 나오는 순간부터 |
| `coupon:{id}:rebuild` | 문자열 | 재건 락 | 재건이 도는 동안 |
| `coupon:{id}:rebuild:queued` | 해시 | 각 인스턴스가 올린 큐 | 재건이 도는 동안 |

**키마다 무엇이 그 키를 움직이는지가 아래 표다.** 조건은 키별 절에 있다.

| 키 | 담는 계기 | 꺼내거나 지우는 계기 |
|---|---|---|
| `counter` | 아직 아무도 안 쓴 번호를 새로 발행한다 | 그 번호가 수량을 넘어 곧바로 되돌린다 |
| `seq` | 회원이 번호를 받는다 (출처 무관) | 순번 충돌, 소진 뒤 회수, 이벤트 준비와 종료 |
| `pending` | 회원이 번호를 받는다 (`seq` 와 같은 순간) | 커밋, 두 제약 위반, 소진 뒤 회수 |
| `free` | 이미 쿠폰을 가진 회원이 들고 온 새 번호가 버려진다 | 새 번호를 뽑기 **전에** 여기부터 꺼내 쓴다 |
| `rebuild` | 카운터가 사라진 것을 알아챈 인스턴스가 재건을 시작한다 | 재건이 끝나거나 TTL 30초 |
| `rebuild:queued` | 재건 중인 것을 안 인스턴스가 자기 큐를 올린다 | 재건이 넷을 다 세운 뒤 |

**`counter` 만 담는 계기가 좁다.** 나머지 셋은 번호가 나가면 따라 움직이는데, 이 키는 **새로 발행할 때만** 오른다. 재사용과 회수로 나간 번호는 여기 안 잡힌다.

**발급 요청 하나가 `accessTokenValidAfter:{role}:{id}` 도 친다.** 인증 필터가 토큰 무효화 커트라인을 읽는 자리이고 쿠폰 도메인의 키가 아니다. 다만 **발급 응답 시간에 그 왕복이 그대로 들어가므로** 예산을 셀 때는 함께 센다.

## 2. 이름에 쿠폰 아이디가, 필드에 회원 아이디가 들어간다

이름을 만드는 곳은 `CouponSeqKeys` 하나다.

```java
private static final String PREFIX = "coupon:";

static String seq(long couponId)     { return PREFIX + couponId + ":seq"; }
static String free(long couponId)    { return PREFIX + couponId + ":free"; }
static String counter(long couponId) { return PREFIX + couponId + ":counter"; }
static String pending(long couponId) { return PREFIX + couponId + ":pending"; }
```

쿠폰 1234 라면 실제로 이렇게 들어 있다.

```
coupon:1234:counter   "6"
coupon:1234:seq       {5001: "6:1", 5002: "7"}      필드 = 회원 아이디, 값 = 순번
coupon:1234:pending   {"5002": 1757212345678}        값 = 회원 아이디, 점수 = 준 시각(ms)
coupon:1234:free      {"6": 6}                       값 = 순번, 점수 = 순번
```

**값 쪽에 쿠폰 아이디가 한 번도 안 나온다.** 회원 아이디와 순번과 시각뿐이다.

**둘 다 요청이 들고 오므로 되짚을 일이 없다.** `couponId` 는 경로 변수이고 `memberId` 는 인증 주체다. `CouponSeqAllocator.allocate` 가 그 둘로 키 이름 넷과 `ARGV[1]` 을 만들어 스크립트에 넘긴다.

**회원별로 키를 나누지 않은 이유는 개수와 정리 비용이다.** 1만 명이 받아도 키는 넷이고 정리가 `UNLINK` 넷으로 끝난다. 회원별 키였으면 `SCAN` 으로 훑어야 한다. 참여 인원도 `HLEN` 한 번이면 나온다.

**중괄호가 없는 것은 의도다.** `coupon:{id}:seq` 의 `{id}` 는 문서의 자리 표시이지 Redis 클러스터의 해시태그가 아니다. 지금은 `primary + replica` 라 슬롯이 하나여서 문제가 없다. **클러스터로 가면 한 쿠폰의 네 키가 서로 다른 슬롯에 흩어져 네 키를 한꺼번에 만지는 Lua 가 `CROSSSLOT` 으로 거절당한다.** 그때 `coupon:{1234}:seq` 로 바꾸면 되고, 이름 생성을 `CouponSeqKeys` 한 곳에 모아 둔 것이 그 대비다.

## 3. `coupon:{id}:counter`

### 무엇을 하나

**번호를 만든다.** `INCR` 의 결과가 곧 발급 번호다. **그래서 이 키가 담는 값은 다음에 나갈 번호가 아니라 마지막으로 발행한 순번이다.** 이벤트를 열 때 `0` 으로 세우고, 재건도 `MAX(issue_seq)` 를 그대로 넣는다.

**그리고 이벤트의 문이다.** 스크립트 첫 줄이 이 키의 존재를 묻고, 없으면 아무것도 안 하고 `-2` 를 돌려준다.

```lua
if redis.call('EXISTS', KEYS[3]) == 0 then
  return '-2'
end
```

**넷의 수명도 이 키가 들고 있다.** 나머지 셋은 만들어지는 자리에서 이 키의 만료 시각을 물려받는다.

### 왜 필요한가

**상한을 락 없이 지키려면 번호가 있어야 한다.** MySQL 은 `CHECK` 에 집계를 못 쓰므로 "행 수 <= total_quantity" 를 직접 걸 수 없다. 대신 행마다 `1..issue_limit` 의 번호를 배정하면 `chk_mc_issue_seq` 와 `uk_mc_coupon_seq` 가 함께 그 상한을 만든다. **그 번호를 만드는 자리가 이 키다.**

**`coupon` 행의 카운터를 `UPDATE` 하는 안과 비교해 이쪽을 골랐다.** 한 행에 락이 몰리면 직렬화되어 그 행의 천장이 약 330 TPS 다.

### 없으면 무슨 일이 나나

**`INCR` 이 1 부터 다시 준다.** 1번은 이미 남이 쓴 번호라 `uk_mc_coupon_seq` 에 걸린다. 서킷은 열리지 않고 발급만 마비된다.

**그래서 `EXISTS` 가드가 있다.** 이 키가 없는 동안은 모든 요청이 `-2` 를 받고, 그것이 재건을 띄우는 신호가 된다.

**`maxmemory-policy` 도 여기에 걸린다.** `allkeys-lru` 면 Redis 가 멀쩡한 채로 이 키만 축출되고 발급이 마비된다. 지금 쓰는 값은 `volatile-lru` 라 **만료가 걸린 키를 버린다.** 이 키에는 만료가 걸려 있으므로 메모리 압박이 오면 대상이 된다. 그것을 막는 것은 정책이 아니라 **이벤트 규모에 견주어 넉넉한 메모리**이고, 그래도 사라졌을 때를 받치는 것이 `EXISTS` 가드와 재건이다.

### 언제 값이 바뀌나

**값이 바뀌는 경우가 넷이다.**

```
관리자가 이벤트를 연다                          0 으로 세운다
아직 아무도 안 쓴 번호를 새로 만들어 준다        1 오른다
새로 만든 번호가 준비한 수량을 넘었다            방금 올린 것을 곧바로 되돌린다
Redis 가 키를 잃어 DB 에서 다시 세운다           MAX(issue_seq) 를 넣는다
```

**두 번째가 이 키의 본업이고, 조건이 넷이다.**

```
1  이벤트가 열려 있다              이 키가 없으면 아무것도 안 하고 거절한다
2  그 회원이 아직 번호가 없다      있으면 그 번호를 그대로 돌려주고 끝난다
3  다시 내줄 번호가 하나도 없다    있으면 그것부터 나가고 이 키는 안 움직인다
4  새 번호가 준비한 수량 안이다    넘으면 세 번째 경우로 넘어간다
```

**번호는 나가는데 이 값이 안 오르는 경우가 셋이다.**

```
같은 회원이 다시 요청한다        이미 받은 번호를 그대로 돌려준다
안 쓰인 것이 확인된 번호를 준다   그 번호는 이미 발행됐던 것이라 새로 만들 필요가 없다
소진 뒤 남의 번호를 회수해 준다   올렸다가 곧바로 되돌린 뒤 뺏은 번호를 준다
```

**그래서 이 값은 "지금까지 몇 명에게 나갔나" 가 아니라 "번호를 어디까지 새로 발행했나" 다.** 재사용과 회수로 나간 것은 여기 안 잡힌다.

**되돌리기가 안전한 것은 그 자리가 스크립트 안이기 때문이다.** 올린 직후라 아무도 끼어들 수 없어 맨 위가 나인 것이 확실하다. DB 를 갔다 온 뒤에는 그 조건이 안 서므로, 그때는 이 키가 아니라 `free` 를 쓴다.

### 코드에서 만지는 자리 전부

| 언제 | 무엇을 | 어디서 |
|---|---|---|
| 이벤트 준비 | `SET counter "0"` | `CouponSeqInitializer.prepare` |
| 이벤트 준비, 마감 변경 | `EXPIREAT counter (issue_end_at + 60초)` | `CouponSeqInitializer.applyTtl` |
| 번호를 새로 뽑을 때 | `INCR` | `coupon-issue-seq.lua` |
| 한도를 넘었을 때 | `DECR` | 같은 스크립트. 원자 블록 안이라 맨 위가 나인 것이 확실하다 |
| 재건이 문을 열 때 | `SET counter maxSeq` | `CouponSeqRebuilder.openGate` |
| 이벤트 종료 | `UNLINK` | `CouponSeqInitializer.clear` |

**`0` 으로 세워 두는 것이 중요하다.** 그래야 "없다" 가 "사라졌다" 를 뜻한다. 초기화하지 않으면 이벤트 시작 시점과 구분되지 않아 `EXISTS` 가드가 매번 걸린다.

## 4. `coupon:{id}:seq`

### 무엇을 하나

**누가 몇 번을 받았는가**를 담는다. 그리고 값의 모양으로 **커밋이 끝났는지**까지 담는다.

```
필드 없음    아직 번호를 안 받았다        -> 새 번호를 준다
"6"          번호는 받았고 결판이 안 났다  -> 그 번호로 다시 진행한다
"6:1"        커밋까지 끝났다              -> DB 를 안 가고 그 자리에서 이미 발급으로 답한다
```

**`:1` 의 `1` 은 아무 뜻이 없다.** 읽는 쪽 둘 다 콜론의 유무만 본다. Lua 는 `string.find(seq, ':')` 이고, Java 는 `indexOf(":")` 로 자른 앞부분만 쓴다.

### 왜 필요한가

**재시도가 새 번호를 안 태우게 하려는 것이다.** 없으면 이런 일이 난다.

```
A 가 6번을 받고 응답 직전에 연결이 끊긴다
A 가 재시도 -> 새로 INCR -> 7번으로 발급 성공
6번은 아무에게도 가지 않는다
```

**그리고 1인 1매 판정을 Redis 에서 끝낸다.** `"6:1"` 이 붙은 회원의 재요청은 DB 까지 안 가고 스크립트 첫머리의 `HGET` 에서 끝난다.

### 가운데 상태가 있어야 한다

**매핑이 있다고 바로 거절하면 안 된다.** 커밋에 실패해도 매핑이 남는 경우가 있어서, 거절했다가는 정당한 발급을 막는다. **거절은 `:1` 이 붙었을 때만이다.**

**한 필드에 둘을 담은 이유는 원자성이다.** 필드를 둘로 나누면 "번호는 있는데 확정 표시만 있다" 같은 상태가 생기고, `HGET` 한 번으로 둘 다 답하지도 못한다.

### 정확성을 지키는 장치가 아니다

**1인 1매는 `uk_mc_coupon_member` 가 지킨다.** Redis 가 매핑을 통째로 잃어도 재시도가 새 번호를 들고 오면 두 번째 행이 그 제약에 걸린다. **매핑이 아끼는 것은 순번이지 정확성이 아니다.** 이 구분이 없으면 Redis 장애를 실제보다 무겁게 보게 된다.

### 언제 담나

**회원이 번호를 받는 순간이다. 예외가 없다.** 번호를 어디서 얻었든 상관없다.

```
새로 발행한 번호를 받았다            -> "6"
안 쓰인 것이 확인된 번호를 받았다     -> "6"
소진 뒤 회수한 남의 번호를 받았다     -> "6"
```

**셋이 한 함수로 모여서 그렇다** (`give()`). 번호를 내주면서 매핑을 남기는 것이 갈라질 수 없다.

**값 뒤에 `":1"` 이 붙는 경우가 둘이다.**

```
그 회원의 INSERT 가 커밋됐다
  배치에 든 회원 전부를 한 명령으로 갱신한다                (markCommitted)

이미 그 쿠폰을 가진 회원이 새 번호를 들고 왔다
  이번 번호가 아니라 그 회원이 원래 갖고 있던 번호로 고쳐 넣는다   (returnAndRepair)
```

**같은 회원이 다시 요청해도 이 키는 안 바뀐다.** 이미 값이 있으면 그것을 돌려주고 거기서 끝나므로, 열 번을 다시 보내도 값도 그대로고 카운터도 안 오른다.

### 언제 지우나

```
그 번호를 남이 쓰고 있어서 이 회원이 새 번호를 받아야 한다     (dropMappings)
소진 뒤, 확정 표시가 없는 채로 기준 시간을 넘긴 회원이 있다     회수가 그 번호를 뺏는다
관리자가 이벤트를 연다                                        지난 이벤트의 매핑을 먼저 치운다
이벤트가 끝나고 정리 배치가 돈다                              넷을 함께 지운다
```

**세 번째를 빠뜨리면 새 이벤트에서 아무도 번호를 못 받는다.** 지난 이벤트의 매핑이 남아 있으면 그 회원들이 이미 받은 것으로 보인다.

**회수는 `":1"` 이 붙은 것을 안 지운다.** 실제로 발급이 끝난 번호라 뺏으면 두 번 나간다.

### 코드에서 만지는 자리 전부

| 언제 | 무엇을 | 어디서 |
|---|---|---|
| 번호를 줄 때 | `HSET seq {member} "6"` | `coupon-issue-seq.lua` 의 `give()` |
| 커밋이 끝났을 때 | `HSET seq {member} "6:1"` (배치 전체를 한 명령) | `CouponSeqCommitter.markCommitted` |
| `uk_mc_coupon_member` 위반, 순번이 다를 때 | `HSET seq {member} "{실제번호}:1"` | `CouponSeqCommitter.returnAndRepair` |
| `uk_mc_coupon_seq` 위반 | `HDEL seq {member들}` | `CouponSeqCommitter.dropMappings` |
| 소진 뒤 회수 | `HDEL seq {오래된 회원}` | 스크립트의 회수 분기 |
| 재건 | `HSET` 으로 확정분과 큐 분을 통째로 | `CouponSeqRebuilder.writeSeqHash` |
| 이벤트 준비, 종료 | `UNLINK` | `CouponSeqInitializer` |

## 5. `coupon:{id}:pending`

### 무엇을 하나

**아직 결판이 안 난 회원의 목록이고, 점수가 번호를 준 시각이다.**

이 하나가 네 가지를 한다.

```
미확정 티켓 대장     번호를 준 순간부터 행이 될 때까지의 구간을 표시한다
회수 대상 목록       ZRANGEBYSCORE 로 기준 시간을 넘긴 것을 집는다
소진의 최종성 판정   ZCARD 가 0 이면 다시 나올 번호가 없다 -> 410
재건의 입력          각 인스턴스 큐에 남아 있는 티켓이 곧 이 집합의 정의다
```

### 왜 필요한가

**번호가 묶여서 아무에게도 안 가는 경우가 있다.**

```
클라가 연결을 끊었다          그 사용자가 안 돌아온다
타임아웃이라 매핑을 유지했다   커밋 여부를 몰라 다시 못 내준다
앱이 급사했다                 catch 가 돌 기회가 없었다
```

**원인은 다른데 결과가 같다.** `"6"` 인 채로 남아 이벤트 끝까지 묶인다. 원인을 구분할 수 없으므로 **시간으로 판정한다.** 그 시각을 담는 자리가 여기다.

**`seq` 만으로는 안 된다.** `seq` 는 회원 -> 순번이라 **언제** 받았는지를 못 담고, 확정된 값(`"6:1"`)은 재요청 응답에 필요해 지울 수도 없다.

### TTL 이 아니라 점수인 이유

**만료는 항목을 지우는 동작이라, 만료된 순간 회원 아이디를 잃고 매핑에서 번호를 못 읽는다. 풀어줄 대상을 잃어버린다.** 점수는 판정만 하고 지우지 않아 번호를 읽어 넘긴 뒤에 지울 수 있다. 기준 시간을 조회할 때 정하므로 나중에 바꾸기도 쉽다.

### 시각을 Redis 가 매긴다

```lua
local t = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)
```

**점수를 쓰는 인스턴스와 재는 인스턴스가 다르기 때문이다.** 앱 시계를 쓰면 시계가 어긋난 한 대가 아직 살아 있는 요청의 번호까지 오래된 것으로 보고 뺏는다.

**재건만 예외다.** `CouponSeqRebuilder.writePending` 은 원래 시각을 복원할 수 없어 `System.currentTimeMillis()` 를 넣는다. 그만큼 그 티켓들의 회수 기준이 뒤로 밀리고, **시계 출처가 달라지는 것도 여기서 한 번 생긴다.**

### 언제 담나

**`seq` 와 같은 순간이다.** 회원이 번호를 받으면 그 회원이 여기에도 반드시 들어온다.

```lua
local function give(seq)
  redis.call('HSET', KEYS[1], ARGV[1], seq)     -- 이 번호는 이 사람 자리다
  redis.call('ZADD', KEYS[4], now, ARGV[1])     -- 아직 결판이 안 났다
```

**둘을 한 스크립트 안에 둔 것이 그 이유다.** "자리를 잡았다" 와 "아직 결판이 안 났다" 가 갈라지면 어느 한쪽만 남은 상태가 생긴다.

**그래서 조건도 `seq` 와 똑같다.** 새로 발행한 번호든, 안 쓰인 것이 확인된 번호든, 회수한 남의 번호든 마찬가지다.

**같은 회원이 다시 요청해도 점수는 안 바뀐다.** 이미 매핑이 있으면 그 값을 돌려주고 끝나기 때문이다. **그게 맞는 동작이다.** 갱신되면 재시도를 계속하는 클라이언트의 번호가 영영 회수되지 않는다.

**점수가 다시 찍히는 경우는 하나뿐이다.** 그 회원의 매핑이 지워진 뒤에 다시 온 경우다. 그때는 새 번호와 새 시각을 받는다.

### 언제 지우나

**빼는 경우가 넷이라 담는 경우보다 많다.**

```
그 회원의 INSERT 가 커밋됐다                    배치 전체를 한 명령으로       (markCommitted)
이미 쿠폰을 가진 회원이라 이번 번호가 안 쓰였다                              (returnAndRepair)
그 번호를 남이 쓰고 있어 이 회원이 새 번호를 받아야 한다                      (dropMappings)
소진 뒤, 기준 시간을 넘긴 항목을 회수가 짚었다   확정 표시가 붙어 있어도 뺀다
```

**남는 것은 커밋 여부를 모르는 티켓뿐이다.** 타임아웃, 커넥션 실패, 회로 열림, 인스턴스 급사. **그 넷은 아무것도 안 건드리는 것이 처리라 여기 남고,** 그래서 나중에 시간으로 판정된다.

### 언제 여기서 번호를 꺼내 주나

**조건이 다섯이고 다 서야 그 요청자가 번호를 받는다.**

```
1  요청이 도착했다                  회수는 스스로 안 돈다.  누가 와야 돈다
2  그 회원의 매핑이 없다             있으면 그 번호를 돌려주고 끝난다
3  free 가 비어 있다                 차 있으면 그쪽이 먼저다.  여기까지 안 온다
4  카운터가 이미 최대다               새 번호를 뽑았다가 수량을 넘어 곧바로 되돌린 상태
5  기준 시간을 넘긴 항목이 있고, 그 매핑에 확정 표시가 없다
```

스크립트의 순서가 그대로 이 순서다. **앞의 것에서 걸리면 뒤는 아예 안 본다.**

**60초는 소진 시점부터 세지 않는다.** 점수가 그 사람이 번호를 받은 시각이라 **시계는 소진 훨씬 전부터 돌고 있다.**

```
10:00:00   5001 이 6번을 받는다.  점수 = 10:00:00
10:00:05   5001 이 사라진다
10:03:00   재고가 다 나간다
10:03:01   다른 요청이 온다 -> 5001 의 점수가 3분 지났다 -> 곧바로 회수된다
```

**대부분 소진되는 순간 이미 기준을 넘겨 있다.** 늦어지는 것은 소진 직전 60초 안에 번호를 받은 사람들뿐이다.

**한 요청이 항목 하나만 본다.** `LIMIT 0 1` 이라 100명이 묶여 있으면 100번의 요청이 와야 100개가 풀린다.

**짚은 그 하나에 확정 표시가 붙어 있으면 번호를 안 준다.** 실제로 발급이 끝난 번호라 뺏으면 두 번 나간다. 그 항목은 목록에서 빼기만 하고 그 요청자는 소진 응답을 받는다. **청소는 됐으니 다음 요청이 그다음 것을 본다.**

**소진이 트리거인 덕분에 평상시 비용이 0 이고 주기 배치도 필요 없다.** 대신 **요청이 와야 돈다.** 소진 뒤 트래픽이 완전히 빠지면 그 번호는 키가 만료될 때까지 남는다.

### 코드에서 만지는 자리 전부

| 언제 | 무엇을 | 어디서 |
|---|---|---|
| 번호를 줄 때 | `ZADD pending {member} = TIME()` | `coupon-issue-seq.lua` 의 `give()` |
| 커밋이 끝났을 때 | `ZREM pending {member들}` | `CouponSeqCommitter.markCommitted` |
| 두 갈래의 제약 위반 | `ZREM pending {member}` | `returnAndRepair`, `dropMappings` |
| 소진 뒤 회수 | `ZREM pending {오래된 회원}` | 스크립트의 회수 분기. 확정분이어도 뺀다 |
| 재건 | `ZADD` 로 각 인스턴스 큐의 티켓을 | `CouponSeqRebuilder.writePending` |
| 이벤트 준비, 종료 | `UNLINK` | `CouponSeqInitializer` |

## 6. `coupon:{id}:free`

### 무엇을 하나

**발행은 됐는데 아무도 안 쓴 것이 확인된 순번을 담는다.** 점수가 번호라 `ZPOPMIN` 이 낮은 것부터 꺼낸다.

**"확인된" 이 이 키의 조건이다.** 안 쓰였을 것 같은 번호가 아니라, 그 번호로 행이 안 만들어졌음이 증명된 것만 들어온다. 증명이 안 되는 번호는 `pending` 이 시간으로 판정한다.

**`coupon.md` 는 여기 담는 동작을 "반납" 이라고 부른다.** 코드의 `returnAndRepair` 도 그 말에서 왔다. 다만 번호를 쥔 사람이 돌려주는 것이 아니라 **실패를 잡은 플러시 스레드가 대신 담는 것**이라, 이 문서는 그 말을 쓰지 않는다.

**판정 순서가 `INCR` 보다 앞이다.** 여기 담긴 것이 있으면 새로 뽑기 전에 그것부터 나간다.

### 왜 필요한가

**카운터는 앞으로만 가고 `DECR` 로는 못 고친다.**

```
A: INCR -> 6      B: INCR -> 7
A 실패 -> DECR -> 카운터 6.  즉 "다음에 발행할 순번은 7"
C: INCR -> 7      B 가 쥔 번호다 -> uk_mc_coupon_seq 충돌
```

**`DECR` 은 카운터를 1 내릴 뿐이라 맨 위 번호가 지워지는 셈이다. A 의 6번이 아니다.** 카운터는 몇 개까지 나갔는지만 알고 그중 어느 것이 안 쓰였는지는 모른다. **그래서 안 쓰인 번호를 지목해 담는 자리가 따로 필요하다.**

**리스트가 아니라 정렬 집합인 이유가 있다.** 리스트는 같은 번호가 두 번 들어갈 수 있고 그러면 두 사람이 같은 번호를 받는다. `ZADD` 는 같은 값을 하나로 유지한다. 낮은 번호부터 다시 나가서 `MAX(issue_seq)` 와 실제 발급 수의 간격이 덜 벌어지는 것도 이득이다.

### 언제 담나

**이미 그 쿠폰을 가진 회원이 새 번호를 들고 와서, 그 새 번호가 안 쓰인 채 버려질 때다.** 평상시에 담는 경우는 이것뿐이다 (`returnAndRepair`).

거기까지 오는 조건이 넷이다.

```
1  벌크로 넣던 배치가 DB 에서 실패해 한 행씩 다시 넣는 중이다
2  이 회원의 행을 넣다가 UNIQUE 제약에 걸렸다        확정적 실패다.  롤백이 확실하다
3  그 회원의 행을 읽어 보니 이미 있다                1인 1매 쪽에 걸린 것이다
4  그 행의 순번이 이번에 받은 번호와 다르다          이번 번호로는 행이 안 생겼다
```

**넷이 다 서야 담는다.** 그리고 담는 것은 **이번에 받았다가 못 쓴 번호**이지 그 회원이 원래 갖고 있던 번호가 아니다.

**이 경우가 나오려면 그 회원의 매핑이 사라져 있어야 한다.** 매핑이 살아 있었다면 원래 번호를 그대로 돌려받아 새 번호를 안 받았을 것이다. 매핑이 사라지는 길은 셋이다. **회수가 가져갔거나, 순번 충돌로 지워졌거나, Redis 가 해시를 통째로 잃었거나.**

**그래서 정상 이벤트에서는 거의 안 담긴다.**

**DB 에는 이 번호의 흔적이 아예 없다.** 행이 안 만들어졌기 때문이다. "6번이 비어 있다" 는 DB 도 알지만 **"6번이 한 번 나갔다가 안 쓰였다" 는 이 키만 안다.**

### 언제 안 담나

| 실패 | 왜 안 담나 |
|---|---|
| 순번이 같다 | **내가 이미 그 번호로 썼다.** 담으면 실제 행이 쓰는 번호를 남에게 내준다 |
| 행이 없다 | **남이 쓰고 있다.** 담으면 또 다른 회원이 받아 같은 충돌을 되풀이한다 |
| 행 읽기 실패 | 가르지 못했다. 손대면 잘못된 쪽을 고를 수 있고 **담는 것은 못 되돌린다** |
| 타임아웃, 커넥션 실패 | **커밋 여부를 모른다.** 이미 커밋됐다면 남이 쓰는 번호를 내준다 |
| 회로 열림 | 담아도 안전하지만 **매핑을 두면 재시도가 같은 번호로 온다.** 그게 낫다 |
| 큐가 꽉 참 | 번호를 받기 전에 끊는다. **담을 번호가 아예 없다** |

**"안 쓰였다" 를 알 수 없으면 안 담는다.** 모르는 번호는 `pending` 이 시간으로 판정한다.

```
free      쓰이지 않은 것이 확인된 순번.   플러시가 가려내서 담는다.  ZPOPMIN 이 꺼내 쓴다
pending   확인이 안 된 순번.              시간으로 판정한다.  틀리면 uk_mc_coupon_seq 가 잡는다
```

**모르는 번호는 `free` 를 안 거친다.** 회수가 `pending` 에서 직접 뺏어 그 자리에서 새 요청에게 준다.

**그래서 `free` 는 평소 비어 있다.** `ZPOPMIN` 은 평상시 헛치고 그 비용은 왕복에 묻힌다.

### 언제 여기서 꺼내 쓰나

**번호를 내주는 길에서 가장 먼저 본다.** 조건이 둘뿐이다.

```
1  요청이 도착하고 그 회원의 매핑이 없다     있으면 그 번호를 돌려주고 끝난다
2  이 키에 담긴 것이 하나라도 있다           낮은 번호부터 꺼낸다
```

**새 번호를 뽑는 것보다 앞이다.** 그래서 여기 뭐가 있으면 카운터가 안 움직이고, `pending` 의 회수도 안 돈다.

```
free 에 있다        그것부터 나간다.  카운터는 그대로
free 가 비었다      새로 뽑는다.  수량을 넘으면 그때 pending 을 뒤진다
```

**소진 상태여도 마찬가지다.** 카운터가 최대여도 여기 뭐가 있으면 회수까지 안 간다.

**낮은 번호부터 꺼내는 것은 간격을 줄이려는 것이다.** `MAX(issue_seq)` 와 실제 발급 수가 덜 벌어진다.

**빈 상태에서 꺼내는 비용은 0 에 가깝다.** 그래서 평상시 이 키가 비어 있어도 이 확인이 정상 경로를 느리게 하지 않는다.

### 그 판정이 틀릴 수 있는 자리가 하나 있다

**3번과 4번이 답하는 것은 "이 회원의 행" 이지 "이 번호를 쓰는 행" 이 아니다.**

평소에는 둘이 같은 이야기다. **한 번호는 한 사람에게만 나가기 때문**이다. 그 전제를 깨는 것이 회수다.

```
M 이 A 번으로 커밋됐는데 확정 표시가 실패했다
회수가 M 의 매핑을 지우고 A 를 남에게 넘긴다        M 은 행이 있고 매핑이 없다

M 이 다시 온다.  소진 상태다
회수가 이번엔 N 의 B 번을 짚어 M 에게 준다          B 는 실제로 N 이 쓰고 있다

M 이 INSERT -> uk_mc_coupon_member 와 uk_mc_coupon_seq 가 동시에 깨진다
findIssuedSeq(M) -> A.  B 와 다르다 -> B 를 담는다   <- 잘못된 판정이다
```

**확정 표시 실패가 서로 다른 회원에게 두 번 나야 성립한다. 좁다.**

**그리고 스스로 정정된다.** 잘못 담긴 B 는 `ZPOPMIN` 으로 나가고, 받은 사람이 `uk_mc_coupon_seq` 에 부딪히면서 `seq-taken` 복구가 B 의 진짜 주인을 되살린다. 초과 발급도 1인 1매 위반도 안 난다.

**가르려면 조회를 이렇게 넓히면 된다.**

```sql
SELECT member_id, issue_seq FROM member_coupon
 WHERE coupon_id = ? AND (member_id = ? OR issue_seq = ?);
```

왕복은 안 늘지만 `OR` 가 두 유니크 인덱스를 타야 해서 **`index_merge` 가 붙는지 확인하고 넣어야 한다.** 안 붙으면 드문 경로가 느린 경로가 된다.

### 수명을 여기서 건다

**`free` 를 만드는 자리가 `returnAndRepair` 뿐이라, 그 자리가 만료를 안 걸면 넷 중 이 키에만 만료가 영영 안 붙는다.**

```java
private void inheritCounterTtl(long couponId) {
    Long remaining = redisTemplate.getExpire(CouponSeqKeys.counter(couponId), TimeUnit.MILLISECONDS);
    if (remaining != null && remaining > 0) {
        redisTemplate.expire(CouponSeqKeys.free(couponId), Duration.ofMillis(remaining));
    }
}
```

남은 시간을 읽어 상대 시각으로 다시 거는 것은 **절대 만료 시각을 읽는 명령을 스프링이 안 내주기 때문이다.** 그만큼 밀리초 단위로 어긋나지만 TTL 꼬리가 1분이라 잴 값이 아니다.

### 코드에서 만지는 자리 전부

| 언제 | 무엇을 | 어디서 |
|---|---|---|
| `uk_mc_coupon_member` 위반, 순번이 다를 때 | `ZADD free {번호} {번호}` + 수명 물려받기 | `CouponSeqCommitter.returnAndRepair` |
| 번호를 줄 때 | `ZPOPMIN free` | `coupon-issue-seq.lua` |
| 재건 | `ZADD` 로 구멍 전부 | `CouponSeqRebuilder.writeFree` |
| 이벤트 준비, 종료 | `UNLINK` | `CouponSeqInitializer` |

## 7. 넷은 함께 살고 함께 죽는다

**하나만 사라지면 나머지가 거짓말을 한다.**

```
counter 만 사라짐   INCR 이 1 부터 다시 준다.  이미 쓴 번호와 충돌한다
seq 만 사라짐       재시도가 새 번호를 태운다.  1인 1매 판정도 놓친다
free 만 사라짐      다시 내줄 순번이 증발한다.  그만큼 덜 나간다
pending 만 사라짐   묶인 번호를 영영 못 찾는다
```

**수명은 `counter` 가 들고 나머지 셋이 따라간다.** 준비 단계가 넷에 한꺼번에 걸 수는 없다. 그때는 `counter` 만 있고 **없는 키에 `EXPIREAT` 은 아무 일도 안 하기** 때문이다.

```
counter   준비 단계가 issue_end_at + 60초로 건다
seq       스크립트의 give() 가 만들면서 PEXPIRETIME 을 읽어 물려받는다
pending   같다
free      returnAndRepair 가 만들면서 물려받는다
```

**값을 앱이 다시 넘기지 않고 `counter` 에서 읽어 물려주므로, 관리자가 마감을 바꾸면 그 뒤에 만들어지는 키가 저절로 새 마감을 따라간다.**

**`issue_end_at` 이 `NULL` 이면 기준이 없어 안 건다.** 그리고 그런 쿠폰은 **애초에 선착순이 아니다.** 선착순은 `total_quantity` 와 `issue_end_at` 이 둘 다 있는 것으로 정의된다.

**TTL 은 그물일 뿐이다.** 주 경로는 종료 배치가 `UNLINK` 로 지우는 것이고, 이것은 그 배치가 안 돌았을 때를 받친다.

## 8. 발급 한 건이 키를 어떻게 바꾸나

정상 경로다.

```
1  Lua (원자)
     EXISTS counter            문이 열려 있나
     HGET seq {member}         이미 받았나.  있으면 여기서 끝난다
     ZPOPMIN free              다시 내줄 순번이 있나
     INCR counter              없으면 새로 뽑는다
     HSET seq {member} "6"     이 번호는 이 사람 자리다
     ZADD pending {member}     아직 결판 안 났다
     PEXPIREAT seq, pending    counter 의 수명을 물려받는다

2  큐

3  DB   INSERT ... issue_seq = 6      커밋

4  Redis
     HSET seq {member} "6:1"   확정 표시
     ZREM pending {member}     미확정 해제

5  응답 200 { "issueSeq": 6 }
```

**매핑은 커밋 전에 붙고, `:1` 은 커밋 뒤에 붙는다.** 매핑이 커밋 뒤에 붙는다면 매핑을 둔 목적 자체가 사라진다. 커밋 전에 죽으면 매핑이 없어 재시도가 새 번호를 받고 6번이 구멍이 된다.

**3번과 4번 사이가 끊기는 경우는 [coupon.md](coupon.md) 3장의 "확정 표시가 실패하면 회수가 오판한다" 가 다룬다.**

### 실패하면 무엇이 달라지나

| 실패 | counter | seq | pending | free |
|---|---|---|---|---|
| 한도 초과 | `DECR` 로 되돌림 | - | - | - |
| `uk_mc_coupon_member`, 순번 다름 | - | 실제 번호로 고침 | 뺌 | **번호를 넣음** |
| `uk_mc_coupon_member`, 순번 같음 | - | `:1` 을 마저 붙임 | 뺌 | - |
| `uk_mc_coupon_seq` | - | 지움. 주인은 되살림 | 뺌 | - |
| 타임아웃, 커넥션 실패 | - | 그대로 | **그대로 남음** | - |
| 회로 열림 | - | 그대로 | **그대로 남음** | - |
| 행 읽기 실패 | - | 그대로 | 그대로 남음 | - |

**마지막 셋이 "커밋 여부를 모른다" 다.** 아무것도 안 건드리는 것이 처리이고, 그래서 `pending` 에 남아 나중에 시간으로 판정된다.

## 9. `coupon:{id}:rebuild` 와 `coupon:{id}:rebuild:queued`

**성격이 위 넷과 다르다.** 재건은 넷이 없을 때 도는 일이라 물려받을 수명이 없고, 이 둘은 자기 TTL 로 살다가 재건이 끝나면 사라진다.

### `coupon:{id}:rebuild`

**재건 락이고, 동시에 "재건 중" 표시다.**

```java
redisTemplate.opsForValue().setIfAbsent(CouponSeqKeys.rebuild(couponId), token, lockTtl);
```

**락을 못 잡은 인스턴스는 이 키가 있는 것을 보고 자기 큐를 올린다.** 플러시가 배치마다 한 번씩 `hasKey` 로 확인한다. 그 확인이 없으면 **요청을 못 받는 인스턴스가 자기 큐를 영영 안 올린다.**

**TTL 은 `rebuild-contribute-wait` 의 10배다.** 지금 값으로 3초 x 10 = 30초.

**푸는 것은 자기 토큰일 때만이다.** 읽고 지우는 사이가 원자적이지 않아 아주 드물게 남의 락을 지울 수 있는데, 그때도 잃는 것이 없다. 뒤늦게 들어온 쪽이 카운터가 이미 선 것을 보고 그대로 돌아간다.

**언제 담나.** 카운터가 사라진 것을 알아챈 인스턴스가 재건을 시작하려 할 때다.

```
1  요청이 "이벤트가 안 열려 있다" 는 답을 받았다      카운터가 없다는 뜻이다
   또는 플러시가 이 키가 이미 있는 것을 봤다
2  DB 를 봐서 정말 열려 있어야 할 이벤트인지 가른다   관리자가 아직 안 연 것과 구분한다
3  없을 때만 쓴다                                    먼저 쓴 한 대만 성공하고 나머지는 큐만 올린다
```

**두 번째가 없으면 안 된다.** 카운터가 없다는 것은 "잃었다" 뿐 아니라 "아직 안 열었다" 도 뜻하므로, DB 를 봐야 둘이 갈린다.

**언제 지우나.** 재건이 끝나면서 자기가 쓴 값인지 확인하고 지운다. 그 전에 프로세스가 죽으면 TTL 30초가 대신 푼다.

### `coupon:{id}:rebuild:queued`

**재건이 도는 동안 각 인스턴스가 자기 큐를 올려 두는 자리다.** 회원 -> 순번이고, 회원 하나의 티켓은 한 인스턴스에만 있으므로 여럿이 같은 해시에 써도 겹치지 않는다.

**DB 만으로 재건할 수 없어서 있다.** 앱 큐에 아직 커밋 안 된 번호가 떠 있는데, DB 만 보고 세우면 그 번호들을 아무도 안 쥔 것으로 보고 남에게 다시 내준다.

**큐를 DB 보다 먼저 읽는다.** 티켓은 큐에서 DB 로만 가고 반대로는 안 간다. 큐를 먼저 읽으면 그사이 넘어간 티켓이 양쪽에 다 잡히지만, **DB 를 먼저 읽으면 어디에도 안 잡혀 구멍이 된다.**

**올리는 동안 플러시가 멈춘다.** 안 그러면 재건이 확정된 매핑을 미확정으로 덮고, 회수가 그 번호를 남에게 넘겨 같은 번호가 두 번 나간다.

**언제 담나.** 재건이 도는 것을 알아챈 인스턴스가 자기 큐에 남은 티켓을 올릴 때다. **주도하는 쪽도 자기 큐를 올리므로 참여하는 모든 인스턴스가 각각 한 번씩 쓴다.**

```
1  이 인스턴스가 재건 중인 것을 알았다     요청이 거절당했거나, 플러시가 락 키를 봤다
2  자기 플러시를 멈춘다                    멈추지 못하면 올리지 않고 건너뛴다
3  자기 큐에서 이 쿠폰의 티켓을 골라낸다
4  회원 -> 순번을 한 명령으로 올린다
5  플러시를 다시 흐르게 한다
```

**빈 큐면 안 쓴다.** 그 인스턴스는 올릴 것이 없다.

**언제 지우나.** 주도하는 인스턴스가 넷을 다 세운 뒤 `UNLINK` 한다. 그리고 기다리는 사이에 관리자가 이벤트를 다시 열어 카운터가 이미 서 있으면, 넷을 안 세우고 이것만 지우고 물러난다. **락은 그 바깥의 `finally` 가 푼다.**

### 재건이 넷을 세우는 순서

```
1  락을 잡는다                                     rebuild
2  각 인스턴스가 자기 큐를 올린다 (3초 기다린다)     rebuild:queued
3  큐를 읽고 DB 를 읽는다
4  seq 를 쓴다      확정분은 "N:1", 큐 분은 "N"
5  pending 을 쓴다  큐 분만
6  free 를 쓴다     1..maxSeq 중 어디에도 없는 번호
7  counter 를 쓴다  = maxSeq.  이 순간 문이 열린다
8  rebuild:queued 를 지우고 락을 푼다
```

**카운터를 마지막에 쓰는 것이 곧 문을 여는 것이다.** 그 전까지 모든 요청이 `-2` 를 받는다. **요청을 막는 장치를 새로 만들지 않았다.** 스크립트의 `EXISTS` 가드가 이미 그 문이다.

## 10. 이벤트 종료 후

**순서가 있다. 키를 먼저 지우면 지각 요청이 카운터 없는 Redis 를 친다.**

```
1  is_active 를 끈다                       관리자가 누르거나 마감이 지나 배치가 끈다
2  updated_at 이 60초 지날 때까지 기다린다   진행 중인 배치의 커밋과 뒷정리가 끝나기를 기다린다
3  issued_quantity 를 실제 행 수로 맞춘다
4  UNLINK seq, free, counter, pending
```

**4번을 앞당기면 안 된다.** 카운터가 없는 상태에서 지각 요청이 닿으면 `INCR` 이 1 을 주고, 그 번호는 이미 남이 쓴 것이라 `uk_mc_coupon_seq` 에 걸린다.

**`DEL` 이 아니라 `UNLINK` 다.** 1만 필드 해시를 그 자리에서 해제하지 않고 백그라운드로 넘긴다.

**정리 대상은 DB 로 찾는다.** Redis 키가 남아 있는지로 찾으면 TTL 이 키를 먼저 지웠을 때 대상을 놓쳐 3번을 건너뛴다.

## 11. 발급 요청 하나가 Redis 를 네 번 친다

```
밖   JwtAuthenticationFilter  -> accessTokenValidAfter:{role}:{id} (GET)
밖   CouponSeqAllocator       -> 순번 확보 (EVALSHA)
안   CouponSeqCommitter       -> 확정 표시 (HSET)
안   CouponSeqCommitter       -> 미확정 목록에서 제거 (ZREM)
```

**"안" 과 "밖" 은 `commit-wait` 기준이다.** 뒤의 둘이 안인 것은 `completeIssued` 가 요청 스레드를 깨우기 **전에** 확정 표시를 붙이기 때문이다. 그 산식은 `application-coupon.yml` 의 계층 표에 있다.

**연결은 인스턴스당 하나다.** Lettuce 가 커넥션 하나를 공유하고 명령을 다중화하므로, 동접 2만이어도 접속은 기동 때와 재접속 때만 일어난다.

**순번 확보는 스크립트 하나로 끝낸다.** 나눠 부르면 같은 회원의 동시 요청 둘이 다 `HGET` 을 놓쳐 각자 번호를 받고, `ZPOPMIN` 과 `INCR` 사이에도 남이 끼어들 수 있다.
