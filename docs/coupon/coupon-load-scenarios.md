# 선착순 쿠폰: 성능 개선 부하 시험 시나리오

**이 문서는 앞으로 돌릴 회차를 미리 적어 두는 계획서다.**

**이 저장소에 남아 있는 회차 기록은 `loadtest/README.md` 의 로컬 리허설뿐이다.** 그래서 이
문서는 클라우드 기준선이 없는 상태에서 시작하고, 단계 0 이 그 기준선을 만드는 일을 한다.

---

## 0. 지금까지 잰 것과 무엇이 다른가

지금까지의 회차는 목적이 하나였다. **무엇이 발급을 막고 있는가**다.

`loadtest/README.md` 의 회차 4~9 가 그 기록이고, 회차 9 가 요구를 처음 만족했다
(발급 10,000, 구멍 0, 소진 938건).

**그것은 "되게 만드는" 회차였다.** 막힌 것을 뚫었고, 뚫은 뒤에 **어디까지 되는지**는 재지
않았다.

**이 문서가 계획하는 것은 그 다음이다.** 되는 것을 전제로, **어디까지 되는지와 무엇을 바꾸면
얼마나 나아지는지**를 잰다.

**요구 부하는 상한이 아니다.** 도착률 333건/초와 재고 10,000 은 요구사항이 정한 조건이지
([requirement.md](requirement.md)) 이 시스템이 낼 수 있는 최대가 아니다. 그 최대를 아직
모른다.

---

## 1. 회차를 설계하는 규칙

앞선 회차들이 비싼 교훈을 남겼다. 회차 4~9 는 여섯 번을 돌리고도 **읽을 수 있는 것이
셋뿐**이었다.

> 연결 실패가 6,018 에서 16,041 까지 흔들린다. 그건 앱이 아니라 노트북이 낸 값이고,
> 회차마다 조건이 달랐다는 뜻이다. **그래서 회차 사이의 발급행 차이를 설정 탓으로만 돌릴 수
> 없다** (`loadtest/README.md`)

그래서 이 문서의 회차는 넷을 지킨다.

**하나, 한 회차에 한 변수만 바꾼다.** 둘을 같이 바꾸면 어느 쪽이 움직였는지 못 가른다.

**둘, 돌리기 전에 가설과 볼 지표를 적는다.** 돌린 뒤에 지표를 고르면 원하는 그림이 나올
때까지 고르게 된다.

**셋, 같은 회차를 두 번 돌린다.** 한 번은 흔들림인지 변화인지 못 가른다. 회차 4 와 5 가
같은 값으로 발급행 1,908 과 196 을 낸 적이 있다.

**넷, 환경에 따라 답할 수 있는 질문이 다르다.** 이 문서는 회차를 두 곳에서 돌린다.

```
로컬    같은 기계에서 k6 와 JVM 과 MySQL 과 Valkey 가 돈다
        답할 수 있는 것    "A 와 B 중 어느 설정이 나은가"      상대 비교
        답할 수 없는 것    "SLO 를 만족하는가"                 절대값

클라우드  전용 인스턴스 t3.small, 부하 발생기는 별도 호스트
        답할 수 있는 것    둘 다
```

**SLO 정의가 부하 발생기 분리를 요구한다** ([coupon.md](coupon.md) 8장). 그래서 **판정이
붙은 회차는 클라우드에서만 유효하고**, 설정을 고르는 회차는 로컬에서 먼저 돌려 후보를
좁힌다. 로컬에서 진 설정이 클라우드에서 이기는 일은 드물고, 클라우드 회차는 비용이 든다.

**각 회차 표의 "환경" 칸이 그것을 적는다.**

## 2. 기준선을 먼저 세운다

**견줄 자리가 없다.** 이 저장소에 남은 회차 기록은 `loadtest/README.md` 의 로컬 리허설뿐이고,
그 값은 k6 와 JVM 과 MySQL 과 Valkey 가 한 CPU 를 다툰 조건에서 나왔다. SLO 정의가
요구하는 환경(부하 발생기가 앱과 다른 호스트)이 아니라 **판정에 못 쓴다.**

**게다가 그 사이에 코드가 바뀌었다.** `#163` 에서 `#167` 까지 Redis 왕복이 이만큼 줄었다.

```
확정 표시        2 -> 1
매핑 삭제        2 -> 1
번호 되돌리기    5 -> 1
중복 해소        N -> 1
재건             항목마다 -> 500개씩
```

**이 변화가 운영 지연에 얼마나 나타나는지는 아직 모른다.** 지금 있는 값은 전부 로컬
컨테이너 측정이고, 문서가 그 한계를 이미 적어 두었다
([coupon-redis-scripts.md](coupon-redis-scripts.md) 7~8장).

> 절대값은 여전히 로컬 컨테이너 값이다. 근거로 삼는 것은 왕복 수(`N -> 1`)이고,
> 이 표는 그 차이가 실물에서 실제로 보이는지를 확인한 것이다.

## 3. 단계 0. 믿을 수 있는 기준선

**측정 도구부터 믿을 수 있어야 한다.** 여기서 걸리는 것을 먼저 고치지 않으면 뒤 단계의
숫자가 전부 의심스러워진다.

### S0-1. 지표가 실제로 나오는가

| | |
|---|---|
| 이유 | **SLO 판정이 이 지표 하나에 걸려 있다.** `issue.js` 의 임계가 `coupon_settled_duration: ['p(99)<1000']` 인데, 이 지표는 `#163` 에서 새로 붙였고 아직 한 회차도 안 봤다. 안 나오면 뒤 회차의 판정이 전부 헛돈다. |
| 환경 | 로컬로 충분하다. 값이 아니라 배관을 보는 회차다. |
| 가설 | `coupon_settled_duration` 이 Prometheus 까지 온다 |
| 바꾸는 것 | 없다. 지난 회차와 같은 조건으로 한 번 돌린다 |
| 보는 것 | `k6_coupon_settled_duration_p99`, `k6_coupon_sold_out_final_total` |
| 통과 | 두 지표가 대시보드에 값으로 뜬다 |

**이 지표는 #163 에서 새로 붙였고 아직 한 회차도 안 봤다.** SLO 판정이 이 지표에 걸려
있으므로(`coupon_settled_duration: ['p(99)<1000']`), 안 나오면 뒤 회차의 판정이 전부 헛돈다.

### S0-2. 기준선

| | |
|---|---|
| 이유 | **견줄 자리가 없으면 개선을 말할 수 없다.** 뒤 회차의 판정이 전부 "기준선 대비" 로 적힌다. |
| 환경 | 둘 다. 로컬 기준선과 클라우드 기준선을 각각 남긴다. 뒤 회차는 같은 환경의 기준선과만 견준다. |
| 가설 | 요구 부하에서 SLO 를 만족한다 |
| 바꾸는 것 | 없다. 요구 조건 그대로 돌린다 (VU 20,000 / ramp 60초 / 재고 10,000) |
| 보는 것 | p99, 발급 수, `gap`, 회원 수, 사유별 거절, 큐 최대 길이, 연결 실패 |
| 통과 | 발급 10,000 / `gap` 0 / 회원 10,000 / p99 <= 1초 |
| 회차 | 같은 조건 2회 |

**이 회차의 값이 뒤 회차를 견줄 유일한 자리다.** 뒤의 모든 판정이 "기준선 대비" 로 적히므로
두 번 돌려 흔들림 폭까지 함께 남긴다.

**#163 에서 #167 까지 줄인 왕복의 효과도 여기서 처음 드러난다.** 다만 정상 회차에서는 중복
해소 경로에 안 오므로, `S2` 의 배칭 관련 회차까지 가야 그 몫이 보인다.

## 4. 단계 1. 상한을 찾는다

**조이기 전에 어디가 막히는지부터 알아야 한다.** 지금은 요구 부하(333건/초)에서 통과하는
것만 알고, 그 위를 모른다.

### S1-1. 도착률을 올린다

| | |
|---|---|
| 이유 | **요구 부하를 통과하는 것만 알고 그 위를 모른다.** 그리고 조일 곳을 고르려면 먼저 어디가 막히는지 봐야 한다. 이 회차의 사유별 거절 비율이 단계 2 에서 무엇을 건드릴지 지정한다. |
| 환경 | 로컬. 막히는 지점의 절대값은 환경마다 다르지만, 무엇이 먼저 막히는지는 같다. |
| 가설 | 도착률을 올리면 어느 지점에서 p99 가 1초를 넘는다 |
| 바꾸는 것 | ramp 를 줄여 도착률을 올린다. 60초 -> 30초 -> 20초 -> 15초 |
| | 즉 333 -> 667 -> 1,000 -> 1,333 건/초 |
| 보는 것 | p99, `coupon_congested` 의 사유별 내역, 큐 최대 길이 |
| 통과 | 없다. 이 회차는 판정이 아니라 지점 찾기다 |

**VU 총수는 20,000 으로 고정한다.** `issue.js` 가 VU 번호로 토큰을 고르므로 VU 를 줄이면
시도하는 사람 수가 함께 줄어 조건이 둘 바뀐다.

**그리고 이 회차가 다음 단계의 방향을 정한다.** 지난 기록이 읽는 법을 적어 두었다.

> `congested-budget` 과 `congested-seq-unavailable` 의 비율이 무엇을 조일지 알려 준다.
> 앞이 크면 플러시가 못 따라가는 것이고, 뒤가 크면 Redis 쪽이다.

```
congested-budget 이 크다           -> 단계 2 의 쓰기 쪽(S2-1, S2-2)으로 간다
congested-seq-unavailable 이 크다   -> 단계 2 의 Redis 쪽(S2-3)으로 간다
둘 다 작은데 p99 만 오른다          -> 단계 3 으로 간다.  한 대의 한계다
```

### S1-2. 재고를 올린다

| | |
|---|---|
| 이유 | **재고 10,000 에서는 소진이 빨리 와 발급 구간이 짧다.** 처리량의 평평해지는 지점을 보려면 발급이 오래 이어져야 한다. |
| 환경 | 로컬. |
| 가설 | 재고 10,000 은 시험 조건이지 한계가 아니다 |
| 바꾸는 것 | 재고 10,000 -> 50,000. VU 도 함께 올려야 해서 변수가 둘이다 |
| 보는 것 | 초당 발급 처리량, 큐 최대 길이, `hikaricp_connections_pending` |
| 통과 | 없다. 처리량이 평평해지는 지점을 찾는다 |

**변수가 둘이라 S1-1 뒤에 돌린다.** 재고만 올리면 전부 소진 전에 끝나 발급 구간이
안 늘어난다.

## 5. 단계 2. 지목된 병목을 조인다

**S1-1 이 가리킨 쪽만 한다.** 순서대로 다 돌리는 것이 아니다.

### S2-1. 큐 상한

| | |
|---|---|
| 이유 | **이 값은 성능값이 아니라 손실값이다.** [coupon.md](coupon.md) 8장이 큐 최대 길이를 "앱이 급사했을 때 잃는 건수의 상한" 이라고 적는다. 20,000 은 근거를 갖고 정한 값이 아니라 넉넉히 잡아 둔 값이라, 발급 수를 안 깎는 선에서 가장 작은 값을 찾아야 한다. |
| 환경 | 로컬. 큐가 자라는 모양은 상대 비교로 충분하다. |
| 가설 | `queue-capacity` 20,000 은 필요보다 크다 |
| 바꾸는 것 | 20,000 -> 10,000 -> 5,000 -> 2,000 |
| 보는 것 | 큐 최대 길이, `congested-queue-full`, 발급 수 |
| 통과 | 발급 10,000 을 유지하면서 큐 최대 길이가 상한에 안 닿는다 |

**큐 상한은 성능값이 아니라 손실값이다.** [coupon.md](coupon.md) 8장이 이유를 적는다.

> **큐 최대 길이** | 앱이 급사했을 때 잃는 건수의 상한이다

**그래서 이 회차의 목적은 빨라지는 것이 아니라 작아지는 것이다.** 발급 수를 안 깎는 선에서
가장 작은 값을 찾는다.

### S2-2. 플러시 스레드

| | |
|---|---|
| 이유 | **DB 에 쓰는 주체가 이 스레드 하나뿐이다.** 큐가 자란다면 여기가 좁은 것이고, 늘려서 안 줄면 병목은 DB 쪽이다. 즉 이 회차는 튜닝인 동시에 병목의 위치를 가르는 시험이다. |
| 환경 | 로컬에서 방향을 보고 클라우드에서 확인한다. 정확성(`gap`, 회원 수)이 걸려 있어 한 번은 실물에서 봐야 한다. |
| 가설 | 플러시 스레드를 늘리면 큐가 덜 자란다 |
| 바꾸는 것 | `flush-threads` 1 -> 2 |
| 보는 것 | 큐 최대 길이, p99, `hikaricp_connections_pending` |
| 통과 | 큐 최대 길이가 줄고 발급 수와 `gap` 이 안 나빠진다 |

**2 가 상한이다.** 전용 프로필의 `maximum-pool-size` 가 2 라 그 위로는 커넥션을 못 얻는다.
`application-coupon.yml` 이 그것을 적어 두었다.

> 올린다면 `maximum-pool-size` 와 함께 올린다. 한쪽만 올리면 스레드가 커넥션을 못 얻어
> 기다린다.

**풀을 같이 올리는 것은 이 시험의 범위가 아니다.** [coupon.md](coupon.md) 5장이 커넥션
예산에서 역산해 2 로 정했고, 그걸 바꾸는 것은 부하 시험이 아니라 설계 변경이다.

**그리고 이 회차는 정확성을 함께 봐야 한다.** 플러시가 둘이 되면 같은 쿠폰의 티켓이 두
스레드에 갈리고, 지금 뒷정리가 쿠폰 단위로 묶여 있다. `gap` 과 회원 수를 반드시 본다.

### S2-3. Redis 타임아웃

| | |
|---|---|
| 이유 | **로컬에서 이 값 하나가 발급량을 직접 바꿨다.** 회차 8 과 9 사이에서 100ms 를 500ms 로 올리자 `seq-unavailable` 이 32,799 에서 1 로 떨어졌다. 순번을 못 받은 요청은 큐에도 못 들어가 쿠폰이 되지 못하기 때문이다. 그 값이 클라우드에서도 필요한지는 아직 모른다. |
| 환경 | **클라우드만.** 로컬은 Valkey 가 CPU 를 다퉈 값이 부풀고, 같은 VPC 의 ElastiCache 는 1밀리초 아래다. 로컬에서 재면 틀린 결론이 나온다. |
| 가설 | 클라우드에서는 `timeout: 100ms` 로 충분하다 |
| 바꾸는 것 | 없다. 관찰만 한다. 모자라면 100 -> 200 |
| 보는 것 | `congested-seq-unavailable`, 회로 열림 횟수 |
| 통과 | `seq-unavailable` 이 전체 요청의 0.1% 아래다 |

**이 값은 로컬에서 500ms 가 필요했던 자리다.** `loadtest/README.md` 가 그 이유와 한계를
같이 적었다.

> 로컬에서 Redis 500ms 가 필요했던 것은 k6 와 JVM 과 MySQL 과 Valkey 가 한 CPU 를
> 다퉜기 때문이다. 같은 VPC 의 ElastiCache 는 1밀리초 아래다.
>
> **클라우드 회차에서 `seq-unavailable` 이 얼마나 나오는지가 그 답을 준다.**

**올려야 한다면 대가가 따라온다.** 100ms 는 요청 예산 800ms 의 계층 계산에 들어 있는
값이라([coupon.md](coupon.md) 8장), 올리면 안쪽 합 720ms 가 함께 올라간다.

### S2-4. 배치 윈도

| | |
|---|---|
| 이유 | **지연과 묶음 크기를 직접 맞바꾸는 유일한 값이다.** 늘리면 한 회분이 커져 쓰기가 효율적이고, 그만큼 모든 티켓이 더 기다린다. 지금 20ms 는 근거를 갖고 고른 값이 아니다. |
| 환경 | 로컬에서 방향, 클라우드에서 p99 확인. |
| 가설 | `batch-window` 20ms 는 지연과 묶음 크기의 맞바꿈 지점이다 |
| 바꾸는 것 | 20ms -> 10ms -> 40ms |
| 보는 것 | p99, 한 회분의 평균 크기, 초당 발급 처리량 |
| 통과 | 없다. 어느 쪽으로 기울일지 정하는 회차다 |

**이 값도 예산 계층에 들어 있다.** 올리면 안쪽 합이 그만큼 는다.

## 6. 단계 3. 대수를 늘린다

### S3-1. 전용 인스턴스 수 대 처리량

| | |
|---|---|
| 이유 | **[coupon.md](coupon.md) 8장이 이 회차를 미리 지정해 두었다.** 앱은 N 대로 늘려도 DB 는 한 대라, 어느 대수부터 처리량이 안 는다. 그 지점이 이 구조의 상한이고, 그때 평상시 경로가 같이 느려지면 격벽이 새는 것이다. |
| 환경 | **클라우드만.** 로컬에서는 대수라는 변수 자체가 없다. |
| 가설 | 어느 대수부터 처리량이 안 는다. 그 지점이 DB 한계다 |
| 바꾸는 것 | 전용 ASG 1 -> 2 -> 3 |
| 보는 것 | 초당 발급 처리량, `hikaricp_connections_pending`, 평상시 경로의 p99 |
| 통과 | 없다. 평평해지는 지점을 찾는다 |

**[coupon.md](coupon.md) 8장이 이 회차를 미리 지정해 두었다.**

> **인스턴스를 늘려도 처리량이 안 늘기 시작하는 지점**이 DB 한계이고, 그때 평상시 경로가
> 같이 느려지면 격벽이 새는 것이다.

**평상시 경로를 같이 재는 것이 이 회차의 절반이다.** 선착순이 도는 동안 상품 조회가
멀쩡해야 격벽이 선 것이다. 지금 `issue.js` 는 발급만 쏘므로 **평상시 경로를 쏘는 시나리오를
하나 더 붙여야 한다.**

## 7. 단계 4. 이긴 구성에 장애를 건다

**앞 단계가 고른 구성은 정상 회차에서만 검증된 것이다.** 성능을 올리려고 건드린 값들이
하필 장애에서 손실을 키우는 값일 수 있다. 그래서 **마지막에 한 번 더 판다.**

### 왜 여기서 하나

**튜닝한 값 셋이 전부 장애 때 잃는 양과 직결된다.**

```
queue-capacity    앱이 급사하면 큐에 있던 만큼 잃는다.  줄인 것이 여기서는 이득이다
flush-threads     늘렸다면 죽는 순간 쓰던 배치가 둘이다.  잃는 양이 는다
batch-window      늘렸다면 커밋 안 된 티켓이 더 오래 쌓인다.  잃는 양이 는다
```

**앞의 둘은 방향이 반대다.** 큐를 줄이면 손실이 줄고, 플러시를 늘리면 손실이 는다. 성능만
보고 고르면 이 맞바꿈이 안 보인다.

**그리고 이전 장애 회차의 구성이 지금 구성이 아니다.** 그때 잰 값을 그대로 물려받을 수 없다.

### 무엇을 거나

**이전 회차가 언제 끊느냐로 결과가 갈리는 것을 이미 보였다.** 부하 전에 끊으면 발급이 0 이고,
부하 도중에 끊으면 진행분은 나간다. **현실은 도중이므로 도중만 잰다.**

| 회차 | 거는 것 | 방법 |
|---|---|---|
| F-1 | 앱 컨테이너 급사 (3 -> 2) | `docker kill`. SIGKILL 이라 큐가 안 비워진다 |
| F-2 | 캐시 완전 단절 | `iptables DROP` 6379, 전용 3대 전부 |
| F-3 | DB 완전 단절 | `iptables DROP` 3306, 전용 3대 전부 |
| F-4 | 앱 급사 + 캐시 단절 | 위 둘을 함께 |
| F-5 | 캐시 Multi-AZ 페일오버 | `aws elasticache test-failover` |
| F-6 | DB Multi-AZ 페일오버 | `aws rds reboot-db-instance --force-failover` |

**주입 시점은 "램프 종료 직후" 가 아니라 "발급의 절반 지점" 이다.** 재고 10,000 이 초당
333건에서 30초면 소진되므로, 램프(60초)가 끝날 때는 이미 팔 것이 없다.

```
k6+17초   주입.  발급 약 5,000장(재고의 50%) 지점이다
유지 20초  남은 발급 구간 전체가 장애 아래에 놓인다
```

**k6 가 실제로 시작한 시각을 기준으로 센다.** 명령을 보낸 시각부터 세면 명령 전달과 k6
기동만큼 늦어져 소진 뒤에 들어간다.

### 왜 `docker stop` 이 아니라 `docker kill` 인가

**`docker stop` 은 SIGTERM 이라 `stop_grace_period` 안에 스프링이 큐를 비우고 내려간다.**
그러면 재고 손실이 0 인 것이 당연해지고, 시스템이 견딘 것인지 비우고 내려간 것인지 못
가른다. `queue-capacity` 가 "급사했을 때 잃는 건수의 상한" 인데 그 상한이 시험되지 않는다.

### 왜 페일오버를 따로 두나

**`iptables` 단절은 "통째로 안 닿는다" 를 잰다.** 운영에서 더 흔한 것은 Multi-AZ 페일오버로,
수십 초 끊겼다가 엔드포인트가 다른 노드를 가리키게 된다. `terraform.tfvars` 가 그 시험을
근거로 `db_multi_az` 를 켜 두었다.

| | |
|---|---|
| 이유 | **성능 구성을 바꾼 뒤의 손실량을 모른다.** 튜닝 전 값과 견줘 나빠지지 않았는지 본다 |
| 바꾸는 것 | 없다. 단계 0~3 이 고른 구성으로 고정하고 장애만 건다 |
| 보는 것 | **발급 수, `gap`, 회원 수, 재고 손실.** p99 는 참고만 한다 |
| 통과 | 초과 발급 0, 1인 2매 0, 번호 유실 0. 재고 손실이 튜닝 전보다 안 늘었다 |
| 환경 | **클라우드만.** 앱 1대 정지와 인스턴스 차단이 로컬에 없는 축이다 |

**판정 기준이 앞 단계와 다르다.** 단계 0~3 은 빠른 쪽이 이기고, 여기서는 **덜 잃는 쪽이
이긴다.** p99 를 통과 조건에 안 넣는 것은 장애 중의 지연이 원래 나쁘기 때문이고, 그것을
고치는 것이 이 회차의 목적이 아니다.

### 되돌아갈 수 있어야 한다

**F 회차에서 손실이 늘면 그 값을 되돌린다.** 그때 어느 값을 되돌릴지 알려면 단계 2 의
회차별 값이 남아 있어야 하므로, **7장의 기록 양식을 빠짐없이 채운다.**

**이 단계에서 성능을 다시 튜닝하지 않는다.** 장애 중에 빠르게 만드는 것은 축이 다른 일이고,
섞으면 두 목표가 서로를 망친다.

## 8. 회차마다 남길 것

```
일시와 백엔드 커밋
조건          VU, ramp, 재고, 전용 인스턴스 수
바꾼 것       한 줄. 이전 회차와 무엇이 다른가
발급 / gap / 회원 수
p99 (coupon_settled_duration)
사유별 거절   congested-budget / seq-unavailable / queue-full / write-circuit
큐 최대 길이
판정과 다음 회차
```

**연결 실패를 반드시 함께 적는다.** 그 값이 회차마다 크게 흔들리면 그 회차는 비교에 못
쓴다. 지난 기록이 그것 때문에 여섯 회차를 버렸다.

## 9. 이 문서가 다루지 않는 것

**장애를 성능 회차와 섞지 않는다.** 단계 4 에서 따로 걸고, 거기서는 성능을 다시 튜닝하지
않는다. 두 목표를 한 회차에 담으면 어느 쪽 때문에 값이 움직였는지 못 가른다.

**설계를 바꾸는 것은 안 한다.** 커넥션 풀 2, 전용 3대, SLO 1초는 근거를 갖고 정해진
값이다([coupon.md](coupon.md) 5장, 8장). 이 문서는 그 안에서 움직인다.

**워밍업이 뒷정리 스크립트 셋을 안 데우는 것은 여기서 못 고친다.** 워밍업이 소진(410)으로
끝나 뒷정리 경로에 안 닿는다. 부하 조건이 아니라 워밍업 구현의 문제라
[warmup.md](warmup.md) 쪽 일이다.

## 10. 시작하기 전에 고칠 문서 두 곳

**회차를 돌리기 전에 고치는 것이 낫다.** 둘 다 지금 사실이 아니고, 시나리오를 읽는 사람이
그대로 믿으면 잘못된 회차를 설계한다.

**하나, `loadtest/README.md` 411행의 "풀이 5".**

```
지금 문서   플러시 스레드    1 부터 늘리며 큐 길이가 줄어드는지 본다.  풀이 5 라 ...
실제 값     application-coupon.yml 의 maximum-pool-size 는 2 다
```

**둘, `coupon.md` 1660행의 GC 정지.**

```
지금 문서   느린 인스턴스    남는다.  GC 정지(실측 104~330ms) ...
실제        330ms 는 회로 지표를 레지스트리에 붙였을 때 나던 값이고 이미 고쳤다.
            루트 README 는 고친 뒤 값을 최대 1ms 로 적고 있다
```

**두 번째가 더 위험하다.** 고쳐진 문제를 살아 있는 원인으로 적고 있어서, 느린 인스턴스를
보면 GC 부터 의심하게 된다.
