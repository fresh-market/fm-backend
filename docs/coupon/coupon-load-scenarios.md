# 선착순 쿠폰: 성능 개선 부하 시험 시나리오

**이 문서는 앞으로 돌릴 회차를 미리 적어 두는 계획서다.** 돌린 결과는
[coupon-load-rounds.md](coupon-load-rounds.md) 에 남긴다.

---

## 0. 무엇을 찾는가

**이 시험이 개선의 상한을 찾는다.** 지금 값들이 근거를 갖고 정해진 것인지, 더 나아갈 자리가 있는지를
한 변수씩 옮겨 가며 잰다.

```
지금 값    batch-window    20ms
          queue-capacity  20,000
          flush-threads   1
          warmup          켜짐 (요청 3,000 + 쓰기 5,000행)
```

**셋 다 근거의 강도가 다르다.** `flush-threads` 는 커넥션 풀 2 에서 나온 값이고,
`batch-window` 와 `queue-capacity` 는 넉넉히 잡아 둔 값이다.

---

## 1. 부하 조건은 고정이다

**요구사항이 정해 두었고 임의로 고치지 않는다.**

```
재고 10,000장에 20,000명이 동시에 요청해도 초과 발급 0건, 1인 최대 1매
ramp-up : 60s
```

`requirement.md` 3행이 **"주어진 요구사항이므로 임의로 고치지 않는다"** 고 못 박는다.
그래서 **VU, ramp, 재고, 회원 수는 전 회차에서 같다.** 바꾸는 것은 앱 설정뿐이다.

**도착률이 초당 333건으로 일정하다.** `ramping-vus` 가 60초에 걸쳐 VU 20,000 을 만들면
초당 333개가 생기고 각 VU 가 한 번 쏜다. **재고가 30초면 소진되므로 앞 30초가 발급 구간이다.**

---

## 2. 회차를 설계하는 규칙

**하나, 한 회차에 한 변수만 바꾼다.** 둘을 같이 바꾸면 읽는 쪽이 어느 것 때문에 값이
움직였는지 못 가른다.

**둘, 같은 회차를 두 번 돌린다.** 지난 시험에서 첫 회차가 p99 0.724초, 재실행이 0.361초로
두 배 갈렸다. 인스턴스를 올린 직후라 덜 데워진 상태였다. **한 번만 돌리면 이 시험이 그 흔들림을 못 잡는다.**

**셋, 돌리기 전에 가설과 볼 지표를 적는다.** 돌린 뒤에 지표를 고르면 원하는 그림이 나올
때까지 고르게 된다.

**넷, 설정이 실제로 걸렸는지 돌리는 쪽이 로그로 확인한다.** 앱이 기동 때 이렇게 찍는다.

```
event=COUPON_FLUSHER_STARTED threads=1 batchSize=500 batchWindow=PT0.02S
event=COUPON_WARMUP_DONE sent=3000 ok=3000 writeRows=5000 elapsedMs=13651
```

---

## 3. 설정을 회차마다 바꾸는 방법

**전용 인스턴스의 `compose.yaml` 에 `SPRING_APPLICATION_JSON` 을 끼운다.** 스프링이 그
JSON 을 다른 어떤 설정보다 늦게 읽어 `application-coupon.yml` 을 덮는다.

```bash
tune.sh '{"coupon":{"issue":{"batch-window":"40ms"}}}'
tune.sh reset
```

**terraform 을 안 고치는 이유가 있다.** `compose.yaml` 은 인스턴스 부팅 때 user-data 로
렌더된다. 템플릿을 고치면 인스턴스를 새로 띄워야 하고, 회차마다 그럴 수는 없다. 인스턴스는
어차피 일회용이라 그 위에서 직접 고친다.

**컨테이너를 다시 띄우므로 워밍업이 매번 새로 돈다.** 그래서 회차 사이에 가열 상태가
같아진다. 이것이 규칙 둘(두 번 돌리기)과 함께 회차 간 비교를 성립시킨다.

---

## 4. W. 워밍업을 켜고 끈다

**이 회차가 다른 모든 회차의 전제를 정한다.** 워밍업이 얼마나 기여하는지 모르면, 뒤 회차에서
읽는 쪽이 개선을 설정 덕으로 볼지 가열 덕으로 볼지 못 가른다.

| | |
|---|---|
| 이유 | **워밍업은 이미 켜져 있고 그 값이 측정된 적이 없다.** 요청 3,000 과 쓰기 5,000행이라는 값도 논증으로 잡은 시작값이다. 끄고 재 봐야 그 값이 버는 몫이 나온다 |
| 바꾸는 것 | `coupon.warmup.enabled` |
| 보는 것 | p99, 발급 TPS, 혼잡, 첫 1분의 지연 곡선 |
| 회차 | W-off 2회, W-on 2회 |

```
W-off   {"coupon":{"warmup":{"enabled":false}}}
W-on    reset (기본값)
```

**판정은 둘이다.** 워밍업이 p99 를 얼마나 낮추는가, 그리고 **켠 상태가 회차 간에 안정적인가.**
뒤엣것이 더 중요하다. 안정적이지 않으면 뒤 회차의 비교가 성립하지 않는다.

**이후 모든 회차는 워밍업을 켠 상태로 돈다.**

## 5. B. 배치 윈도

| | |
|---|---|
| 이유 | **지연과 묶음 크기를 직접 맞바꾸는 유일한 값이다.** 늘리면 한 회분이 커져 쓰기가 효율적이고 그만큼 모든 티켓이 더 기다린다. 지금 20ms 는 근거를 갖고 고른 값이 아니다 |
| 바꾸는 것 | `coupon.issue.batch-window` |
| 계단 | 5ms -> 10ms -> **20ms(기준)** -> 40ms -> 80ms |
| 보는 것 | p99, 발급 TPS, 한 회분 평균 크기, 큐 최대 길이 |
| 통과 | 없다. p99 가 가장 낮은 지점을 찾는다 |

**예산에 묶여 있다.** [coupon.md](coupon.md) 8장의 계층 산식이 이 값을 20ms 로 세고 있다.

```
배치 윈도 20 + 커넥션 300 + 소켓 300 + 확정 표시 100 = 720ms < commit-wait 800ms
```

**80ms 로 올리면 합이 780ms 가 되어 예산에 거의 닿는다.** 그래서 80ms 가 계단의 끝이고,
거기서 더 좋아진다면 `commit-wait` 를 함께 올릴지 따로 판단해야 한다.

---

## 6. Q. 큐 상한

| | |
|---|---|
| 이유 | **성능값이 아니라 손실값이다.** [coupon.md](coupon.md) 8장이 큐 최대 길이를 "앱이 급사했을 때 잃는 건수의 상한" 이라고 적는다. 20,000 은 근거를 갖고 정한 값이 아니라 넉넉히 잡아 둔 값이다 |
| 바꾸는 것 | `coupon.issue.queue-capacity` |
| 계단 | **20,000(기준)** -> 5,000 -> 2,000 -> 500 -> 100 |
| 보는 것 | 큐 최대 길이, `congested-queue-full`, 발급 수, p99 |
| 통과 | 발급 10,000 을 유지하면서 가장 작은 값 |

**이 회차의 목적은 빨라지는 것이 아니라 작아지는 것이다.** 지난 시험에서 큐 최대가 1~4 였다.
20,000 이 필요한 근거가 없다.

**작아지면 두 가지가 좋아진다.** 급사 때 잃는 상한이 줄고, `congested-queue-full` 이 빨리
떠서 **밀리는 것을 요청자가 바로 안다.** 지금은 큐가 커서 밀려도 거절이 안 난다.

---

## 7. T. 플러시 스레드

| | |
|---|---|
| 이유 | **DB 에 쓰는 주체가 이 스레드 하나뿐이다.** 큐가 자란다면 여기가 좁은 것이고, 늘려서 안 줄면 병목은 DB 쪽이다. 튜닝인 동시에 병목의 위치를 가르는 시험이다 |
| 바꾸는 것 | `coupon.issue.flush-threads`, 필요하면 `maximum-pool-size` 도 함께 |
| 계단 | **1(기준)** -> 2 -> (풀을 올려서) 4 |
| 보는 것 | 큐 최대 길이, 발급 TPS, p99, `hikaricp_connections_pending`, **`gap` 과 회원 수** |
| 통과 | 큐와 p99 가 나아지고 정확성이 안 깨진다 |

**2 가 설정만으로 갈 수 있는 상한이다.** 전용 프로필의 `maximum-pool-size` 가 2 다.
그 위로 가려면 풀도 같이 올려야 하는데, **그것은 [coupon.md](coupon.md) 5장이 커넥션
예산 60 에서 역산해 정한 값이라 설계 변경이다.**

```
전용 3대 x 풀 2 = 6
앱 3대 x 8 + 배치 4 + 관리 3 = 31
합계 37 / 60
```

**풀을 4 로 올리면 전용이 12 가 되어 합계 43 이다.** 아직 예산 안이지만, 배포 중 중복
기동까지 세면 달라진다. **그래서 4 회차는 이 시험이 "커넥션 예산을 넘기지 않는지"를 함께 본다.**

**이 회차는 정확성을 반드시 함께 본다.** 플러시가 둘이 되면 같은 쿠폰의 티켓이 두 스레드에 갈리고,
지금 뒷정리가 쿠폰 단위로 묶여 있다. **`gap` 과 회원 수가 이 회차의 통과 조건에 들어간다.**

---

## 8. 상한을 어떻게 판정하나

**이 시험이 변수마다 계단을 올리다가, p99 가 더 안 내려가는 지점을 그 변수의 상한으로 본다.**

```
개선이 이어진다     계단을 하나 더 올린다
개선이 멈춘다       직전 값이 그 변수의 최적점이다
나빠진다           직전 값에서 멈춘다
정확성이 깨진다     그 값은 쓸 수 없다.  성능과 무관하게 탈락이다
```

**세 변수를 각각 다 돌린 뒤, 최적값을 모아 한 회차를 더 돌린다.** 각각 최적이어도 함께
걸면 다를 수 있다. 그 회차가 이 시험의 결론이다.

**그리고 그 구성에 장애를 건다.** 성능을 올리려고 건드린 값이 하필 장애에서 손실을 키울 수
있다. 특히 `queue-capacity` 를 줄이면 급사 손실이 줄고 `flush-threads` 를 늘리면 는다.
**방향이 반대라 고르는 쪽이 성능만 보면 이 맞바꿈을 놓친다.**

## 9. 장애 회차

**성능 회차가 고른 구성에 건다.** 방법과 시점은 지난 시험에서 정한 것을 쓴다.

| 회차 | 거는 것 | 방법 |
|---|---|---|
| F-1 | 앱 컨테이너 급사 | `docker kill`. SIGKILL 이라 큐가 안 비워진다 |
| F-2 | 앱 급사 + 캐시 페일오버 | 위와 아래를 함께 |
| F-3 | 캐시 Multi-AZ 페일오버 | `aws elasticache test-failover` |

**주입 시점은 발급의 절반 지점이다.** 재고 10,000 이 30초면 소진되므로 램프가 끝날 때는
이미 팔 것이 없다.

```
k6+17초   주입.  발급 약 5,000장(재고의 50%) 지점이다
유지 20초  남은 발급 구간 전체가 장애 아래에 놓인다
```

**k6 가 실제로 시작한 시각을 기준으로 센다.** 명령을 보낸 시각부터 세면 명령 전달과 k6
기동만큼 늦어져 소진 뒤에 들어간다. 지난 시험이 그 실수로 넷을 버렸다.

### 복구까지 걸리는 시간을 함께 잰다

**"견뎠다" 만으로는 모자란다. 얼마 만에 돌아오는지가 운영에서 더 중요하다.**

```
인프라 복구   페일오버가 시작해서 끝나기까지.  AWS 이벤트에서 읽는다
              aws elasticache describe-events / aws rds describe-events
재건          카운터를 잃었을 때 앱이 다시 세우는 데 걸리는 시간
              COUPON_SEQ_REBUILD_STARTED 부터 COUPON_SEQ_REBUILT 까지
발급 재개     발급 TPS 가 0 에서 다시 오르는 시각.  대시보드에서 읽는다
```

**재건이 안 도는 것도 결과다.** 페일오버는 복제본이 데이터를 갖고 승격되므로 카운터가
살아남을 수 있다. 그러면 `COUPON_SEQ_REBUILD_SKIPPED` 가 찍히거나 아예 안 불리고,
**"재건이 필요 없었다" 가 그 회차의 답이다.**

**셋을 나눠 재야 어디가 느린지 보인다.** 인프라가 21초 만에 끝났는데 발급 재개가 60초
뒤라면, 남은 39초는 앱 쪽(재연결, 회로 반열림, 재건)에 있다는 뜻이다.

### 왜 `docker stop` 이 아니라 `docker kill` 인가

**`docker stop` 은 SIGTERM 이라 스프링이 큐를 비우고 내려간다.** 그러면 재고 손실이 0 인
것이 당연해지고, 시스템이 견딘 것인지 비우고 내려간 것인지 못 가른다. **바꾸자마자 `gap` 이
1 로 나왔다.**

## 10. 회차마다 남길 것

```
일시와 백엔드 커밋
바꾼 것        한 줄.  기준 회차와 무엇이 다른가
설정 확인       COUPON_FLUSHER_STARTED 로그의 threads / batchSize / batchWindow
              COUPON_WARMUP_DONE 로그의 sent / writeRows
발급 / gap / 회원 수
p99            round 태그로 가른 query_range 의 최댓값
발급 TPS       rate(k6_coupon_issued_total[30s]) 의 피크
사유별 거절     congested-budget / seq-unavailable / queue-full / write-circuit
큐 최대 길이
연결 실패       회차마다 크게 흔들리면 그 회차는 비교에 못 쓴다

장애 회차에만
  인프라 복구    페일오버 시작 -> 완료 (AWS 이벤트)
  재건          REBUILD_STARTED -> REBUILT.  안 돌았으면 그렇게 적는다
  발급 재개      TPS 가 0 에서 다시 오른 시각
```

**p99 를 `loadtest-export.sh` 로 뽑지 않는다.** 그 스크립트는 시간 창 안의 모든 계열을 합쳐
`max` 를 잡는데 `round` 태그로 가르지 않는다. 회차 간격이 창보다 짧으면 **앞 회차의 값을
보고한다.** 지난 시험에서 실제로 같은 값이 두 번 나왔다.

**instant query 도 쓰지 않는다.** 최근 5분 안에 표본이 있는 계열만 돌려주고, 값도 그 시점의
표본 하나라 최댓값이 아니다.

## 11. 그라파나에서 보는 것

`05 부하 시험` 대시보드에 **발급 처리율(TPS)** 패널을 넣었다.

```
발급/초        rate(k6_coupon_issued_total[30s])
도착/초        rate(k6_http_reqs_total[30s])
소진 응답/초    rate(k6_coupon_sold_out_final_total[30s])
혼잡 거절/초    rate(k6_coupon_congested_total[30s])
```

**도착과 발급이 붙어 있으면 흘리지 않고 받아 낸 것이고, 벌어지면 그만큼 거절하거나 밀린
것이다.** 재고가 소진되면 발급이 0 으로 떨어지는 것이 정상이다.

## 12. 이 문서가 다루지 않는 것

**이 시험은 처리량의 상한을 안 찾는다.** 요구사항이 부하 프로파일을 고정했고 **"도구와 처리량은
평가하지 않는다"** 고도 적는다. 이 시험이 재는 것은 **같은 부하에서 설정을 바꿔 얻는 개선**이다.

**설계를 바꾸지 않는다.** 커넥션 예산 60, 전용 3대, SLO 1초는 근거를 갖고 정해진 값이다.
`flush-threads` 4 회차에서 풀을 건드리는 것이 유일한 예외이고, 그 회차는 예산을 넘기지
않는지를 함께 본다.

### 큐를 Redis 에 두는 대안은 이 시험 뒤에 본다

**지금 큐는 이 JVM 의 힙에만 있다.** `CouponIssueQueue` 가 `LinkedBlockingQueue` 이고,
넣는 쪽과 빼는 쪽이 같은 프로세스라 그렇게 두었다([coupon.md](coupon.md) 7장).

**장애 종류에 따라 유불리가 뒤집힌다.**

```
인스턴스 큐 (지금)   캐시가 죽어도 큐에 든 티켓은 살아서 DB 로 간다
                    인스턴스가 죽으면 그 큐가 통째로 사라진다

Redis 큐            인스턴스가 죽어도 티켓이 남는다
                    캐시가 죽으면 큐까지 같이 잃는다.  그리고 왕복이 하나 는다
```

**비교하려면 이 저장소가 Redis 큐를 새로 구현해야 한다.** 설정을 바꾸는 일이 아니라 대안을
하나 더 만드는 일이라, 이 시험에 넣으면 설정 튜닝이 설계 비교로 바뀐다.

**이번 시험이 답하는 것은 한쪽뿐이다.** 캐시 장애에서 인스턴스 큐가 어떻게 버티는지는
장애 회차가 보여 준다. **반대쪽(인스턴스 장애에서 Redis 큐가 버티는지)은 그 구현이 생긴 뒤에 본다.**
