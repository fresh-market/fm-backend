# 주도자 재건으로 되돌리는 안 (반려)

**이 안은 실행하지 않았다. 근거가 된 측정이 결함 하나 때문이었다.**

```
쓸 때의 근거    rebuild-v3 이 캐시 페일오버에서 7,301장만 팔았다.  main 은 9,837장
드러난 것       그 7,301 은 설계가 아니라 고리 때문이었다.  재건이 61번 돌았다
고친 뒤          rebuild-v4 가 같은 장애에서 9,905장.  결번 0.  재건은 대별 한 번씩
```

**"rebuild-v3 이 main 보다 훨씬 나쁘다" 는 전제가 깨졌다.** 두 판이 같은 수준이고, 되돌림은
명부와 기여 수집과 `contribute-wait` 를 다시 들이는 변경이라 **성적이 같다면 기계를 늘릴 이유가
없다.** 이 세션의 결함 다섯이 전부 그 셋에서 났다.

**그래도 지우지 않고 남긴다.** 되돌림을 검토했다는 것과 왜 안 했는지가 기록으로 남아야 같은
논의를 다시 할 때 출발점이 된다. 아래 4장(주도 횟수를 고치는 자리)은 **되돌리지 않아도 유효한
분석이라** 따로 읽을 값이 있다.

측정은 `rounds-rebuild-v4.md` 에 있다.

---

**재건을 두 번 다시 지었고 두 번 다 회차에서 더 나빠졌다.** 이 문서는 그것을 되돌리는 근거와
범위, 그리고 되돌리면서 함께 고칠 것 하나를 적는다.

---

## 1. 측정

같은 장애, 같은 부하(20,000 VU / 재고 10,000장 / 전용 3대)로 잰 값이다.

| 장애 | main `938fd9da` | #242 `b632a5bd` | #246 `b43cbe4b` |
|---|---:|---:|---:|
| 캐시 페일오버 발급 | **9,837** | 9,596 | 7,301 |
| 캐시 페일오버 결번 | **0** | 404 | 6 |
| 복합 발급 | **9,572** | 9,120 | 8,927 |
| 복합 결번 | **0** | 3 | 0 |

**재건이 제 일을 한 회차가 뒤의 둘에는 사실상 없다.**

```
main    X-2 두 번 완주,  X-3 한 번 완주.  모두 freed 를 쓰고 결번 0
#242    Y-2 는 돌았으나 candidates=352 added=0,  Y-3 은 타임아웃으로 3회 전부 실패
#246    Z-2 는 61번 헛돌았고,  Z-3 은 아예 안 떴다
```

**그라파나 `응답 지연` 의 모양이 그것을 비춘다.**

```
X-2  503 이 1.2초 솟고 800ms 로 내려온다      재건이 299ms 에 끝나 문이 열렸다
X-3  503 이 1.25초 솟고 500ms 로 내려온다     189ms
Z-2  503 이 1.3초에서 끝까지 평평하다          문이 계속 닫혀 있었다
```

**솟았다 내려오느냐, 올라가서 안 내려오느냐.** 숫자가 비슷해도 뜻이 정반대다.

## 2. 두 설계가 무엇을 틀렸나

### 2.1 `#242` 는 세는 일을 없애다 재건을 못 돌게 함

세는 기계를 걷어낸 것은 맞는 방향이었다. **그러나 재건이 완주하는 회차를 한 번도 못 만들었다.**

```
Y-2  free 되돌리기가 candidates=352 added=0.  결번 404
Y-3  재건 전용 Redis 타임아웃 1초에 세 번 걸려 완주 실패
     그 회차의 발급 9,120 과 p99 1.69초는 재건이 없는 시스템의 성적이다
```

**그리고 발급을 안 멈춘 대가가 둘 있었다.** 뒤로 간 카운터로 번호가 나가 결번 404 가 났고,
요청이 `commit-wait` 까지 연결을 쥐어 동시 연결 7,450개가 힙을 채웠다. 한 대가 OOM 으로 죽었다.

### 2.2 `#246` 은 문을 달다 고리를 만듦

문 자체는 결번을 막는다. **그런데 문이 자기를 다시 부른다.**

```
재건이 문을 닫는다 (시한 1초)
  -> 발급 Lua 가 -4
  -> 서비스가 suspect() 로 재건을 깨운다
  -> 그 재건이 문을 다시 닫는다
```

**`#246` 이 안전장치로 넣은 "지우지 않는다, 시간이 연다" 가 여기서 역작용했다.** 주도자가 죽어도
열리게 하려던 성질이 **고리를 영구 기관으로 만들었다.**

세 대가 고르게 스무 번씩 돌았다.

```
i-04cc2bbf 20건   i-04230ca4 21건   i-05acb0f5 20건
```

## 3. 되돌리는 범위

**재건 하위 계통만 `938fd9da` 로 되돌린다.** 그 뒤에 들어온 다른 것은 남긴다.

| 되돌리는 것 | 왜 |
|---|---|
| `CouponSeqRebuilder` | 주도자가 세고 기다리는 모양으로 |
| `CouponSeqContributor` | 기여 수집으로 |
| `CouponSeqInstances`, `RebuildLock` | 되살린다 |
| `coupon-issue-seq.lua` | 재건 락을 보고 `-2`. 문(`raising`)과 `-4` 를 걷는다 |
| `coupon-write-free.lua` | 지운다. 주도자가 전역 시야로 `free` 를 계산한다 |
| `CouponSeqMarks` | 지운다. 주도자가 기여로 전체를 안다 |
| `CouponSeqStallBudgetException` | 지운다. 정지 예산은 문과 짝이었다 |

| 남기는 것 | 왜 |
|---|---|
| `#243` 판정 임계 `http_req_duration` | 지표가 바뀐 것이지 설계가 아니다 |
| `#243` 회차 기록과 README 주의 | 측정 기록이다 |
| `#244` 재건 Redis 상한 3초 | `CouponSeqRebuildRedis` 는 양쪽에 다 있다. V-4 와 Y-3 이 1초에 죽었다 |
| `#247` 순번 역전 계측 | `CouponIssueFlusher.resolveDuplicate` 는 양쪽에 다 있다 |
| `#245` 문 설계 문서 | 시도의 기록으로 남긴다. 이 문서가 그 뒤를 잇는다 |
| `fm-infra` 의 메모리 한도와 덤프 | 인프라 층이라 앱 설계와 무관하다 |

## 4. 함께 고칠 것 하나

**되돌리기만 하면 알려진 결함이 같이 돌아온다. 재건이 한 장애에 두 번 돈다.**

`fault-injection-2026-10-10.md` 5장이 그것을 적었고, main 설계로 돈 회차 여섯 중 넷이 2번이었다.

```
회차   기대   실제
O-1     1      1
X-3     1      1
N-2     1      2
P-1     1      2
V-3     1      2
X-2     1      2
```

### 4.1 왜 두 번 도나

**락 해제 경계의 경합이다.**

```
15:26:45.591  REBUILD_STARTED      A
15:26:45.836  REBUILT              A 가 끝냈다
15:26:46.013  REBUILD_STARTED      B 가 시작한다      177ms 뒤
```

A 가 주도하는 동안 B 의 요청은 `-2` 를 받고 B 의 플러시는 `checkAfterFlush` 로 락을 본다.
**둘 다 `suspect()` 를 부른다.** 그 호출들은 `rebuildInProgress` 에 걸려 기여만 하고 돌아가는데,
`inProgress` 가 그 짧은 작업이 끝나면 풀리므로 **계속 다시 불린다.**

**A 가 락을 푸는 순간 B 의 호출 하나가 검사를 통과해 빈 락을 잡는다.**

### 4.2 세 번의 시도가 빗나간 자리

```
#241   -4 를 내 요청 경로만 막았다.  플러시의 checkAfterFlush 가 그대로 샜다
#242   주도자 개념을 없앴다.  재건이 완주를 못 했다
#246   문을 시한으로 바꿨다.  문이 suspect 를 부르고 그 재건이 문을 연장했다
```

**아무도 `acquireLock` 앞에 "방금 주도했으면 또 하지 않는다" 를 안 넣었다.**

### 4.3 넣을 자리

```java
if (rebuildInProgress(couponId)) {
    contributor.contribute(couponId);     // 기여는 간격과 무관하게 언제나
    return;
}
Coupon coupon = ...;
if (tooSoonToLead(couponId)) {            // 여기 하나
    return;
}
if (!acquireLock(couponId, lock)) {
    contributor.contribute(couponId);
    return;
}
lead(couponId, coupon);
```

**기여 경로 뒤에 두는 것이 요점이다.** `suspect()` 입구에 걸면 기여까지 막혀, 주도자가 그 대의
큐를 모르고 계산한다. **이 세션에서 다섯 번 깨진 자리가 정확히 그것이다.**

간격은 `rebuild-on-reconnect-min-interval`(10초)을 쓴다. 새 설정을 안 만든다.

## 5. 되돌리면 잃는 것

**정직하게 적는다. 세 가지가 돌아온다.**

```
주도자가 죽으면 락 TTL 30초 동안 그 쿠폰의 발급이 멈춘다
  복합 장애가 매번 그 조건을 만든다.  3대 중 주도자가 죽을 확률이 1/3 이다
  X-3 에서 안 걸린 것은 운이다

세는 기계가 돌아온다
  명부, rebuild:queued, rebuild:done, contribute-wait 3초
  이 세션의 결함 다섯이 전부 그 자리에서 났다

재건 중 발급이 멈춘다
  실측 300ms.  #242 가 없애려던 것이다
```

**그래도 되돌리는 까닭은 하나다. 그 셋을 안고도 main 이 가장 많이 팔았고 결번이 0 이었다.**

**순번 역전이 이번 회차의 새 축이다.** main 도 재건 중 발급을 막으므로 `#246` 과 같은 보호를
갖는데, 그 수를 아직 아무도 안 쟀다.
