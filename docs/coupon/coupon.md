# 선착순 쿠폰 발급 시스템

한정 수량 쿠폰을 여러 사람이 동시에 요청할 때, **정확히 정해진 수만큼만 발급되게** 만드는 문제를 다룬다.

이 디렉터리는 그 문제를 **여러 방식으로 풀어 보고 비교하기 위해** 있다. 방식마다 버전을 붙이고, 버전마다 문서와 브랜치를 따로 둔다.

```
docs/coupon/requirement.md   주어진 요구사항
docs/coupon/coupon.md        이 문서. 버전과 무관하게 고정된 것
docs/coupon/coupon-v6.md     v6 설계. 검토했으나 채택하지 않았다
```

**버전 문서는 그 버전의 브랜치에 있다.** `coupon-v1.md` 는 `feat/coupon-issue-v1` 에 있고 이 브랜치에는 없다. `coupon-v6.md` 만 여기 있는데, **브랜치를 딴 버전이 아니라 검토만 하고 접은 안**이기 때문이다.

브랜치는 이렇게 갈라진다.

```
develop
  └─ feat/coupon-issue          이 문서. 버전들이 공유하는 것
       └─ feat/coupon-issue-v1  버전을 딸 때마다 여기서 하나씩 갈라진다
```

`feat/coupon-issue` 를 우산으로 두는 이유는 **버전들이 같은 아키텍처 문서를 봐야 하기 때문**이다. 각 버전을 `develop` 에서 따로 따면 이 문서가 버전마다 복사되거나, 병합 순서에 따라 어느 한쪽에만 있게 된다.

**버전끼리는 서로를 이어받지 않는다.** 둘 다 `feat/coupon-issue` 에서 딴다. 같은 문제를 다른 방식으로 푸는 것이라 코드가 겹치지 않아도 된다. v2 가 v1 을 고치는 것이 아니라 **다시 짜는 것**이다.

`develop` 으로는 우산 브랜치가 통째로 들어간다. 어느 버전을 채택할지 정한 뒤에 그 버전만 남기고 정리한다.

---

## 1. 무엇을 지켜야 하나

버전이 바뀌어도 이 다섯은 변하지 않는다. **구현이 아니라 요구사항이다.**

| | 요구 | 어긋나면 |
|---|---|---|
| R1 | 발급 수가 `total_quantity` 를 넘지 않는다 | 준비한 것보다 많이 나간다. 사업 손실 |
| R2 | 한 회원이 같은 쿠폰을 두 장 받지 않는다 | 형평성이 깨진다 |
| R3 | 순번(`issue_seq`)이 겹치지 않는다 | 같은 번호로 두 행이 생겨 상한 강제가 무너진다 |
| R4 | 재시도가 두 장을 만들지 않는다 | 네트워크 오류 한 번에 R1, R2 가 깨진다 |
| R5 | 같은 상태 변경이 반복되거나 겹쳐도 한 번만 반영된다 | 사용과 만료가 중복 처리되어 이력과 재고가 어긋난다 |

**R1 이 가장 비싸다.** 나머지는 사후에 정정할 수 있지만 이미 나간 쿠폰은 회수하기 어렵다.

## 2. DB 가 이미 지키는 것

스키마(`V1__init_schema.sql`)가 앱과 무관하게 R1~R4 를 **모두** 막는다. **이것이 이 시스템의 바닥이다.**

```sql
UNIQUE KEY uk_mc_coupon_member (coupon_id, member_id)
-- R2. 쿠폰당 1인 1매
-- R4. 재시도가 다른 순번을 들고 와도 두 번째 행이 들어가지 않는다

UNIQUE KEY uk_mc_coupon_seq (coupon_id, issue_seq)
-- R3. 한 쿠폰에서 같은 순번을 두 번 쓸 수 없다

CONSTRAINT chk_mc_issue_seq CHECK (
    (issue_limit IS NULL     AND issue_seq IS NULL)
 OR (issue_limit IS NOT NULL AND issue_seq IS NOT NULL
     AND issue_seq >= 1 AND issue_seq <= issue_limit))
-- R1. 순번은 한정 수량 안에서만 매겨진다
```

`issue_limit` 은 행을 만들 때 `coupon.total_quantity` 를 복사한 값이다. **다른 행을 참조하지 않으므로** 삽입 한 건이 자기 행만 보고 상한을 판정할 수 있다.

**이것은 표시용 스냅샷이 아니라 R1 을 지키는 장치다.** CHECK 은 다른 테이블을 못 보므로 `coupon.total_quantity` 를 참조로 두면 이 제약 자체를 걸 수 없다. 그러면 상한 강제가 DB 를 떠나 앱으로 넘어간다. **정책이 바뀌지 않더라도 이 컬럼은 남는다.**

### 왜 순번으로 세는가

원래 걸고 싶은 제약은 `이 쿠폰의 행 수 <= total_quantity` 인데, **MySQL 은 CHECK 에 집계와 서브쿼리를 금지한다.** 그래서 상한을 세는 방법이 둘로 갈린다.

```
coupon 에 카운터를 두고 UPDATE     한 행에 락이 몰려 직렬화된다
                                   락이 커밋까지 유지되므로 그 행의 천장이 약 330 TPS 다

각 행에 1..issue_limit 을 배정      공유하는 행이 없다. INSERT 는 서로 경합하지 않는다
```

**순번은 집계 제약을 개별 행 제약으로 바꾸는 변환이다.** `chk_mc_issue_seq` 와 `uk_mc_coupon_seq` 가 함께 "행이 limit 개를 못 넘는다" 를 만들고, 삽입 한 건이 자기 행만 보고 판정한다.

순번을 빼면 상한 강제가 앱으로 넘어가거나, DB 에 남기려면 `coupon` 한 행에 락을 물어야 한다. **락 없이 DB 가 상한을 지키는 유일한 방법이고, 그것이 순번을 둔 이유다.**

**순서 기록은 부산물이지만 대신할 컬럼이 없다.** `member_coupon_id` 로는 못 답한다. v2 부터 순번은 Redis 가 병렬로 주고 기록은 배치 단위로 몰려 가므로 **PK 순서와 순번 순서가 어긋난다.** `AUTO_INCREMENT` 는 실패한 요청의 번호도 태우므로(아래 절) 몇 번째인지 셀 수조차 없다. `issued_at` 은 앱이 찍어 인스턴스 간 시계가 다르다. **순번 확보 순서를 담는 것은 `issue_seq` 하나다.**

### 검토했다가 뺀 안

이벤트마다 전용 테이블을 두고 순번을 `AUTO_INCREMENT` 에 맡기는 방식도 검토했다.

```sql
CREATE TABLE coupon_issue_1234 (
    issue_seq  INT    NOT NULL AUTO_INCREMENT,
    coupon_id  BIGINT NOT NULL,
    member_id  BIGINT NOT NULL,
    issued_at  DATETIME(6) NOT NULL,
    PRIMARY KEY (issue_seq),
    UNIQUE KEY uk_ci1234_coupon_member (coupon_id, member_id),
    CONSTRAINT fk_ci1234_coupon FOREIGN KEY (coupon_id) REFERENCES coupon (coupon_id),
    CONSTRAINT fk_ci1234_member FOREIGN KEY (member_id) REFERENCES member (member_id),
    CONSTRAINT chk_ci1234_one   CHECK (coupon_id = 1234),
    CONSTRAINT chk_ci1234_limit CHECK (issue_seq <= 10000)
);
```

테이블이 이벤트 단위라 `AUTO_INCREMENT` 가 1 부터 시작하고 상한도 리터럴 CHECK 로 걸린다. 여기까지는 성립한다.

**뺀 이유는 `AUTO_INCREMENT` 가 롤백해도 다음 숫자를 그대로 쓰기 때문이다.** 트랜잭션 밖의 카운터라 되돌아오지 않고, `ALTER TABLE ... AUTO_INCREMENT` 로도 현재 최대값 아래로는 못 내린다.

```
실패도 재시도도 연타도 전부 번호를 태운다
-> 카운터가 10,000 에 닿아도 행은 그보다 적다
-> 준비한 수량을 못 채운 채 끝나고 되돌릴 수단이 없다
```

Redis 카운터도 트랜잭션 밖이라 성질은 같지만, 그쪽은 실패한 번호를 따로 담아 다시 배정할 수 있다(3장). `AUTO_INCREMENT` 에는 그 자리가 없다.

**발급마다 `AUTO_INCREMENT` 를 쓰는 것이 문제이지 컬럼 자체가 문제는 아니다.** 미리 넣어두고 update 로 잡으면 발급 경로에서 `AUTO_INCREMENT` 가 빠져 이 문제가 사라진다. 그 길이 v6 과 v7 이고, **다른 이유로 접었다**(7장).

### 이것이 뜻하는 바

**순번 발급기가 어디에 있든 초과 발급은 나지 않는다.** 카운터가 앱 메모리에 있든 DB 행이든 Redis 든, 그 값이 틀리면 두 제약 중 하나에 걸려 기록이 실패한다.

| 카운터가 어긋난 방향 | 무슨 일이 나나 | 무엇이 막나 |
|---|---|---|
| 실제보다 작다 | 이미 쓴 번호를 다시 발급한다 | `uk_mc_coupon_seq` |
| 실제보다 크다 | 번호가 한도를 넘는다 | `chk_mc_issue_seq` |

그래서 **버전 사이의 차이는 "안전한가" 가 아니라 "얼마나 빠르고 얼마나 자주 실패하는가" 다.** 어떤 버전을 골라도 R1 은 지켜진다. 비교할 축은 처리량과 실패율이다.

이 성질이 없으면 버전별 비교 자체가 위험했을 것이다. 안전을 스키마가 책임지기 때문에 위쪽 구현을 자유롭게 바꿔 볼 수 있다.

### R5 만 앱이 지킨다

앞의 제약들은 R1~R4 를 막지만 **R5 는 못 막는다.** 같은 전이를 두 번 요청하는 것은 스키마가 보기에 정상적인 UPDATE 두 번이다. 규율로 지킨다.

**읽고 판단한 뒤 쓰지 않는다.** 지금 상태를 `WHERE` 에 넣어 한 문장으로 바꾼다.

```sql
UPDATE member_coupon
   SET status = 'USED', used_at = NOW(6), updated_at = NOW(6)
 WHERE member_coupon_id = ? AND member_id = ? AND status = 'ISSUED';
-- 1행이면 이번 요청이 바꾼 것이다
```

**반복 요청**은 두 번째부터 `status` 가 조건에 안 맞아 0행이다. **동시 요청**은 행 락으로 줄을 서고, 뒤엣것이 깨어났을 때 조건이 이미 어긋나 역시 0행이다. 어느 쪽이든 한 번만 반영된다.

**이력은 1행일 때만, 같은 트랜잭션에서 남긴다.** 나누면 상태는 한 번 바뀌었는데 이력이 두 줄이 되거나 그 반대가 된다.

**0행을 갈라야 한다.** 원인이 다른데 결과가 같다.

```
이미 USED     이번 요청이 늦었을 뿐이다   -> 성공 응답. 이것이 멱등이다
쓸 수 없는 상태                            -> 실패 응답
행이 없다      남의 쿠폰이거나 없다        -> 실패 응답
```

**만료 배치도 같은 모양이다.** 조건을 걸어 두면 사용 요청과 겹쳐도 하나만 이긴다.

```sql
UPDATE member_coupon SET status = 'EXPIRED', updated_at = NOW(6)
 WHERE coupon_id = ? AND status = 'ISSUED' AND valid_to < NOW(6);
```

사용이 먼저 이기면 그 행은 이미 `USED` 라 배치가 건드리지 않는다. 9장에서 배치가 겹쳐 도는 경우를 다루는데, 이 조건이 그때의 멱등을 만든다.

**스키마가 거드는 것이 둘 있다.** 규율이 깨졌을 때 잡아 준다.

| 제약 | 무엇을 막나 |
|---|---|
| `chk_mcsh_transition` | 같은 상태로 가는 전이를 이력에 남기지 못한다 |
| `chk_mc_used_at` | `USED` 인데 사용 시각이 없거나 그 반대인 행을 막는다 |

## 3. 발급 한 건의 뼈대

버전마다 각 단계를 다르게 구현하지만, **단계 자체는 같다.**

```
1. 자격 확인      기간, is_active, 대상 등급, 이미 받았는가
2. 순번 확보      한정 수량 안에서 겹치지 않는 번호를 하나 가져온다
3. 발급 기록      member_coupon 에 insert 한다
                  여기서 1인 1매가 판정된다
4. 응답
```

**2번이 이 시스템의 전부다.** 나머지는 어느 버전이든 비슷하게 생겼고, 동시성 문제도 병목도 전부 2번에 있다.

### 자격 확인이 보는 것

1번이 보는 기간은 `coupon.issue_start_at` 과 `issue_end_at` 이다. 둘 다 `NULL` 이면 제한이 없고, `issue_end_at` 이 `NULL` 이면 소진까지 연다.

**이 체크가 버는 것은 응답의 뜻이다.** 처음에는 "키가 만료된 뒤에 `INCR` 이 1 을 내주는 것" 을 막는 안전장치로 적었는데, 그 자리는 순번 확보 스크립트의 카운터 가드(`EXISTS` 가 0 이면 `-2`)가 이미 막는다. 그래서 이 체크가 없어도 번호가 다시 1 부터 나가지는 않는다.

**대신 사흘 전에 끝난 이벤트가 혼잡으로 답하게 된다.** `-2` 는 "준비 전이거나 재건 중" 이라 재고가 남았을 수 있다는 뜻이고, 그래서 503 과 `Retry-After` 로 나간다.

```
체크가 있다   끝난 이벤트 -> 4xx.  끝났다는 뜻이다
체크가 없다   끝난 이벤트 -> 503.  잠시 후 다시 오라는 뜻이 된다
```

소진과 혼잡을 가른 것과 같은 이유다. **끝난 이벤트에 재시도를 유도하면 안 된다.**

1번이 보는 스위치는 **`coupon.is_active` 하나뿐이다.**

`coupon_product_option.is_active` 라는 같은 이름의 컬럼이 있지만 그것은 **쿠폰을 주문에 적용할 때** 보는 값이라 발급과 무관하다. 발급 로직이 대상 옵션을 조회할 이유가 없다. 근거는 [schema-design-rationale.md](../code-architecture/schema-design-rationale.md) 의 "같은 이름의 is_active 가 둘이다" 에 있다.

`is_active` 를 어디서 어떻게 보느냐는 버전마다 다르다. **순번 확보와 한 연산으로 묶지 않으면** 확인과 확보 사이에 관리자가 쿠폰을 끌 수 있고, 그 틈에 번호가 계속 나간다.

**대상 등급은 `coupon.target_grade_id` 다.** `NULL` 이면 전체이고, 값이 있으면 그 등급인 회원만 받는다. 기간이나 `is_active` 와 달리 **회원마다 답이 갈리므로 쿠폰 하나로 캐시해 둘 수 없다.**

**회원의 등급은 읽어 와야 한다.** 처음에는 로그인 시점에 이미 안다고 적었으나 그렇지 않다. 액세스 토큰이 담는 것은 회원 식별자와 회원/관리자 구분(`role`)뿐이고 등급은 없다.

토큰에 싣는 안과 견줘 **읽는 쪽으로 정했다.**

```
토큰에 싣는다   DB 읽기 0.  대신 승급이 토큰 수명(30분)만큼 늦게 반영된다
                그동안 승급한 회원을 잘못 거절한다.  토큰 발급과 검증을 함께 고쳐야 한다
읽는다          언제나 최신 등급으로 판정한다.  대신 DB 왕복이 하나 는다
```

**그 왕복은 등급을 건 쿠폰에서만 낸다.** `target_grade_id` 가 `NULL` 이면 비교할 것이 없으므로 회원을 아예 읽지 않는다. 선착순 이벤트는 대개 전체 대상이라 이 경로가 흔하다.

**"이미 받았는가" 는 Redis 매핑이 답한다.** 별도 조회를 두지 않는다. 순번 확보 스크립트가 맨 앞에서 `HGET` 을 하므로 **그 결과가 곧 답이고 추가 왕복이 없다**(아래 절).

DB 로 보는 안과 비교해 이쪽으로 정했다. 자격 확인은 1단계라 **소진 거절될 요청까지 전부 통과한다.** DB 로 보면 동접 2만이면 `SELECT` 가 2만 번 돌고 그중 절반은 어차피 2단계에서 거절될 요청이다. v2 가 "거절이 DB 를 안 거친다" 로 얻은 것이 그만큼 사라진다.

### 이벤트가 시작되면 조건이 얼어붙는다

**규칙 둘이 관리자가 바꿀 수 있는 시점을 좁힌다.** 약속한 이벤트를 관리자가 도중에 흔들지 못하게 하는 것이 목적이고, 그 부수 효과로 앱이 자격 확인을 캐시할 수 있게 된다.

```
발급 시각 변경   issue_start_at 이 지났으면 issue_start_at, issue_end_at 둘 다 못 바꾼다
발급 스위치 종료  소진 전이고 마감 전이면 못 끈다
```

**앞 규칙은 관리자가 이미 시작한 이벤트의 일정을 늘리거나 줄이지 못하게 한다.** 시작 전이라면 관리자가 얼마든지 고칠 수 있다.

**뒤 규칙은 관리자가 이벤트 중간에 스위치를 끄지 못하게 한다.** 관리자가 끌 수 있는 것은 둘 중 하나가 참일 때다.

```
소진됐다          더 줄 것이 없으니 끝내도 잃는 사람이 없다
issue_end_at 이 지났다  약속한 시간이 끝났다
```

관리자가 끄는 것과 배치가 끄는 것이 같은 조건을 쓰므로 둘 다 이 규칙 안에 있다.

#### 소진은 이벤트를 끝내지 않는다

**앱이 `coupon.issued_quantity` 로는 소진을 판정하지 못한다.** 아무도 그 값을 발급 중에 갱신하지 않기로 했으므로, 이벤트 도중에 그 값은 언제나 뒤처져 있다.

**Redis 카운터로도 판정하지 못한다.** 카운터가 한도를 넘어도 `free` 에 반납된 번호가 남아 있으면 스크립트가 그것을 다시 내주므로 최종이 아니다.

`member_coupon` 의 행 수는 다르다. 행이 `total_quantity` 만큼 있으면 모든 번호가 행으로 실재하므로 회수할 것이 없어, **그 순간만은 소진이 최종이라고 말할 수 있다.**

**그런데도 소진을 종료 조건으로 삼지 않는다.** 회수가 도는 조건이 "소진 상태에서 요청이 왔을 때" 라서다. 스위치를 끄면 요청이 안 들어오고, 요청이 안 들어오면 회수가 안 돌아 **묶인 번호가 그대로 죽는다.** 소진 뒤에도 켜 두는 편이 순번을 덜 잃는다.

지각 요청은 스크립트가 `-1` 로 정상 거절하므로 켜 두는 것이 해롭지 않다. 그래서 관리자도 배치도 **마감 시각 하나만 본다.**

#### 그래서 자격 확인을 캐시할 수 있다

발급 창 안에서 다섯 값이 전부 얼어붙는다.

```
issue_start_at, issue_end_at    앞 규칙이 막는다
total_quantity, target_grade_id  정책이라 원래 안 바뀐다 (아래 절)
is_active                        뒤 규칙이 막는다.  true 로 고정된다
```

다섯 중 `is_active` 만 그동안 관리자가 언제든 바꿀 수 있어서 앱이 캐시하기 위험했다. **뒤 규칙이 그 변화를 소진과 마감 두 시점으로 못 박아 캐시가 성립한다.**

**TTL 이 곧 앱이 마감을 넘겨 요청을 받아 주는 시간이다.** 배치가 스위치를 꺼도 앱의 캐시가 남은 동안은 요청이 더 통과한다. 그래도 수량은 순번이 행 단위로 막으므로 초과 발급은 안 나고, 그 몇 건이 늦게 발급될 뿐이다. 아래 "이벤트 종료 후" 의 1분 TTL 이 이 지연까지 감안한 값이다.

앱이 캐시를 두느냐는 버전마다 다르다. 두면 **요청 스레드가 요청마다 하던 쿠폰 조회 하나가 사라진다.**

**이 캐시가 회원 조회까지 없애지는 못한다.** `target_grade_id` 는 쿠폰당 값이라 앱이 캐시할 수 있지만, 앱이 그것과 견줄 **회원의 등급은 회원마다 갈리는 값**이다. 등급을 건 쿠폰에서는 앱이 회원을 읽는 일이 그대로 남는다.

### 발급 시점 조건을 복사하지 않는다

쿠폰 정책은 한 번 만들면 바뀌지 않으므로, 할인 종류와 값, 유효기간, 최소 주문 금액을 `coupon` 참조로 두어도 이미 나간 발급분이 흔들리지 않는다.

```
빼는 것   coupon_name, discount_type, discount_value, max_discount_amount
          min_order_amount, valid_from, valid_to

남기는 것  issue_limit.  R1 을 지키는 장치라 참조로 못 바꾼다 (2장)
```

**행이 작아지는 것이 이득이다.** `coupon_name` 하나만 빼도 행이 백 바이트 가까이 줄고, 그만큼 페이지당 행 수가 늘어 **쓰기와 버퍼 풀이 가벼워진다.** 300만 행 규모라 누적 효과가 크고, 발급 경로가 `INSERT` 하나인 이 시스템에서는 행 크기가 곧 쓰기 비용이다.

**대가는 전제 하나다.** 나중에 정책 수정 기능이 생기면 이미 발급된 쿠폰의 조건까지 소급해서 바뀐다. 그때는 그 컬럼들을 다시 복사하는 쪽으로 되돌려야 한다.

**쿠폰함 조회에는 `coupon` 조인이 붙는다.** 발급 경로가 아니라 조회 경로의 비용이고, 피크가 지난 뒤에 흩어져 오므로 감당할 만하다.

**`V30__drop_member_coupon_snapshot.sql` 이 이 변경을 담는다.** v6 을 접은 이유가 "DDL 을 다섯 군데 바꾼다" 였으므로 성격이 어떻게 다른지 구분해 둔다.

| | v6 이 요구하던 것 | 스냅샷 제거 |
|---|---|---|
| 방향 | `NOT NULL` 을 풀고 제약을 **더한다** | 컬럼을 **뺀다** |
| 제약 | 조건부 CHECK 가 새로 생긴다 | 줄어든다 |
| 인덱스 | `idx_pending` 이 는다 | 그대로 |
| 무엇을 위해 | 발급 방식을 바꾸려고 | 행을 줄이려고 |
| 되돌리기 | 데이터가 이미 그 형태다 | 다시 복사하면 된다 |

**v6 은 발급 방식을 바꾸려고 스키마를 늘리는 것이었고, 이쪽은 안 쓰는 컬럼을 걷는 것이다.** 앞의 것은 되돌리기 어렵고 뒤의 것은 쉽다.

**`member_coupon` 은 선착순만 담지 않는다.** 일반 쿠폰 발급도 같은 테이블을 쓰므로 이 변경은 그쪽에도 적용된다. 근거는 [schema-design-rationale.md](../code-architecture/schema-design-rationale.md) 가 함께 갖는다.

### 응답은 네 가지다

4번이 낼 수 있는 답이다.

| 응답 | 상태 | 본문 |
|---|---|---|
| 발급 | 200 | `{ "issueSeq": 6, "alreadyIssued": false }` |
| **이미 발급** | **200** | `{ "issueSeq": 6, "alreadyIssued": true }` |
| 소진 | 4xx | 사유 코드 |
| 혼잡 | 503 + `Retry-After` | 사유 코드 |

**이미 발급을 발급과 같은 모양으로 낸다.** 서버는 "사용자가 다시 눌렀다" 와 "클라이언트가 자동 재시도했다" 를 구분하지 못하기 때문이다.

```
실패로 답하면   첫 응답을 잃고 재시도한 사용자가 못 받은 줄 안다
                계속 다시 누르고 그것이 다시 부하가 된다
같게 답하면     일부러 다시 누른 사용자도 성공을 본다
                클라이언트가 플래그를 보고 "이미 받은 쿠폰" 으로 띄운다
```

2장의 R5 가 상태 전이에서 이미 같은 원칙을 쓴다. **발급만 다르게 하면 같은 API 군에서 규칙이 갈린다.**

> 이미 USED     이번 요청이 늦었을 뿐이다   -> 성공 응답. 이것이 멱등이다

인프라 문서도 재시도를 전제로 깔아 둔다. "클라이언트 재시도가 전제되어야 하며, 쓰기 요청이라면 멱등키가 필요하다"(`백엔드공통_앱과DB_장애대응구조.md` 3.5절). 발급은 `(coupon_id, member_id)` 가 자연 멱등키라 헤더를 따로 받지 않는다.

**소진과 혼잡은 진짜 실패라 모양이 달라도 된다.** 둘을 가르는 것은 **순번을 받았는가**다.

```
소진   스크립트가 -1 을 돌려줬다.  재고가 없다.  최종이다
혼잡   순번을 못 받았거나(Redis 사망), 받고도 요청 예산 안에 못 끝냈다
       재고는 있으니 다시 시도할 값이 있다
```

**둘을 뭉치면 재고가 남았는데 마감으로 답하거나, 끝난 이벤트에 재시도를 유도한다.**

**본문에는 순번만 담는다.** `member_coupon_id` 나 할인 조건을 담는 안과 비교해 이쪽으로 정했다.

```
재요청이 Redis 에서 끝난다   매핑의 "6:1" 로 답이 완성된다.  DB 를 안 친다
                             다른 안은 member_coupon 을 읽어야 한다

피크 구간이 가벼워진다        조건을 담으려면 coupon 을 읽어야 한다
                             스냅샷을 걷은 이유가 피크의 쓰기를 줄이려던 것인데
                             응답에 담으면 읽기로 되돌아온다

순번은 공짜다                 Redis 가 이미 들고 있다
                             "몇 번째로 받았습니다" 를 띄울 수 있다
```

**클라이언트가 아쉬운 것이 없다.** 쿠폰 정보는 발급 전 화면에서 이미 조회했고, `member_coupon_id` 가 필요한 시점은 주문할 때인데 그때는 쿠폰함을 부른다. **그 조회는 피크가 지난 뒤에 흩어져 온다.**

**대가는 하나다.** 발급 응답만으로는 쿠폰을 바로 쓸 수 없어 쿠폰함을 한 번 더 불러야 한다.

### 소진은 두 층에서 막는다

```
1층  Redis 카운터가 한도를 넘으면 거절한다     빠르다. 정상 응답을 준다
2층  스키마가 막는다                          느리다. 예외로 끊는다
```

**v2 부터의 구조다.** v1 은 카운터가 `coupon` 행이라 순번 발급과 소진 판정이 조건부 UPDATE 한 문장에서 끝나고, 두 층이 그 안에서 합쳐진다.

**2층은 어떤 경우에도 뚫리지 않는다.** Redis 가 사라지든 페일오버로 카운터가 뒤로 밀리든, 값이 틀리면 `chk_mc_issue_seq` 나 `uk_mc_coupon_seq` 에 걸린다. 초과 발급은 나지 않는다.

### Redis 가 죽으면 새 요청을 받지 않는다

**대체 순번 발급기를 두지 않는다.** Redis 호출이 연속해서 깨져 회로가 열리면 그때부터 순번을 못 주므로 **혼잡 응답(503 + `Retry-After`)으로 끊는다.**

```
이미 순번을 받아 큐에 있는 요청   그대로 플러시되어 발급된다
순번을 못 받은 요청                혼잡 응답.  큐에 넣지 않는다
```

**앞 줄은 특별한 장치 없이 성립한다.** 큐 항목이 `(seq, member_id, future)` 뿐이고 플러시 스레드는 DB 에만 쓰기 때문이다. Redis 는 2단계에만 있고 3단계에는 없다.

**그래서 서킷 브레이커를 Redis 호출에만 건다.** 발급 기능 전체에 걸면 큐에 있던 것까지 버리게 된다.

**대체 경로를 두지 않는 이유는 셋이다.**

```
순서를 못 정한다     전역 순서기가 사라진 상태라 DB 도달 순서밖에 없다
지키려면 비싸다      직렬화하면 p99 가 초 단위로 오르고 재고를 다 못 판다
평소에 안 돈다       이벤트 중 Redis 가 죽어야 도는 코드다
                     1년에 한 번도 안 돌고 정작 필요한 날 처음 실행된다
```

**세 번째가 가장 크다.** 검증되지 않은 경로를 장애 시점에 처음 태우는 것이 장애를 키운다.

`requirement.md` 는 가용성을 요구하지 않는다. 지키는 것은 **초과 발급 0건과 1인 1매**이고, 그 둘은 Redis 가 죽어도 스키마가 지킨다.

**카운터 키가 축출되는 경로를 막아 둔다.** `maxmemory-policy` 가 `allkeys-lru` 면 Redis 가 멀쩡한 채로 카운터만 사라지고 `INCR` 이 1 부터 다시 시작한다. 서킷은 열리지 않고 발급만 마비된다.

### 기록이 실패하면 순번을 반납한다

카운터를 Redis 로 옮기면 **순번 확보(2번)와 발급 기록(3번)이 서로 다른 원자 단위**가 된다. 그 사이에서 실패하면 번호는 소모됐는데 행이 없다. 그 번호는 아무에게도 가지 않고, 발급 수가 `total_quantity` 에 못 미친 채 끝난다.

**카운터를 내리는 것으로는 못 고친다.**

```
A: INCR -> 6      B: INCR -> 7
A 실패 -> DECR -> 카운터 6. 즉 "다음에 나갈 번호는 7"
C: INCR -> 7      B 가 쥔 번호다 -> uk_mc_coupon_seq 충돌
```

`DECR` 은 **맨 위 번호**를 회수한다. A 의 6번이 아니다. 둘이 일치하는 건 내가 마지막 증가자일 때뿐인데, 선착순에서 그 조건은 거의 성립하지 않는다. 카운터는 몇 개인지만 알고 어느 것인지는 모른다.

**그래서 그 번호를 지목해 반납한다.** 이 문서에서 **반납**은 그 번호를 `free` 정렬 집합에 넣는 것을 뜻한다.

```
ZADD coupon:{id}:free 6 6         실패한 번호를 담는다. 같은 값은 하나만 남는다
판정은 ZPOPMIN 을 INCR 보다 먼저   반납분이 있으면 그것부터, 낮은 번호부터 쓴다
```

**반납하는 주체는 실패를 잡은 쪽이고 버전마다 다르다.**

```
v1, v2    요청 스레드.  자기 트랜잭션이 실패하면 자기가 반납한다
v3 이후   플러시 스레드.  배치를 커밋하다 실패한 쪽이 반납한다
          요청 스레드는 future 를 기다릴 뿐 실패를 보지 못한다
```

카운터는 앞으로만 간다. 반납된 번호는 소유자가 유일하므로 다시 꺼내 써도 겹치지 않는다.

**리스트가 아니라 정렬 집합을 쓴다.** 리스트는 같은 번호가 두 번 들어갈 수 있고 그러면 두 사람이 같은 번호를 받는다. `ZADD` 는 같은 값을 하나로 유지하므로 조건부 반납이 실패해도 중복이 안 생긴다. 낮은 번호부터 회수되어 `MAX(issue_seq)` 가 덜 벌어지는 것도 이득이다.

**재시도가 새 번호를 태우지 않게 매핑을 둔다.** 회원이 받은 번호를 기억하는 자리다. 없으면 재시도 한 번에 구멍이 하나씩 생긴다.

```
A 가 6번을 받고 응답 직전에 연결이 끊긴다
A 가 재시도 -> 새로 INCR -> 7번으로 발급 성공
6번은 아무에게도 가지 않는다
```

**쿠폰당 해시 하나로 둔다.** 회원마다 키를 따로 두는 안과 비교했고 이쪽으로 정했다.

```
HSET coupon:{id}:seq {memberId} {issue_seq}
```

| | 해시 하나 | 회원별 키 |
|---|---|---|
| 조회와 쓰기 | O(1) | O(1) |
| 키 개수 | **1개** | 1만 개 |
| 정리 | **`UNLINK` 한 번** | `SCAN` 으로 훑어야 한다 |
| 배치 갱신 | **한 명령에 여러 필드** | 파이프라인이 필요하다 |
| 인원 수 | **`HLEN` 한 번** | 세려면 `SCAN` |
| 필드별 TTL | 안 된다 | 된다 |
| 클러스터 슬롯 | 한 곳에 몰린다 | 분산된다 |

**회원별 키가 나은 둘이 이 구성에 해당하지 않는다.** 매핑은 이벤트 단위로 통째로 살고 죽으므로 필드별 TTL 이 필요 없고, 4장이 `primary + replica` 로 정해 클러스터 모드가 아니다. 카운터와 `free` 도 이미 단일 키라 매핑만 분산해도 소용이 없다.

**순번 확보는 한 스크립트로 끝낸다.** 나눠 부르면 같은 회원의 동시 요청 둘이 다 `HGET` 을 놓쳐 각자 번호를 받고, `ZPOPMIN` 과 `INCR` 사이에도 남이 끼어들 수 있다.

```lua
-- KEYS[1]=seq, KEYS[2]=free, KEYS[3]=counter, KEYS[4]=pending
-- ARGV[1]=memberId, ARGV[2]=issue_limit, ARGV[3]=회수 기준(ms)
-- 반환 "6" 번호를 받았다 / "6:1" 이미 발급됐다 / "-1" 소진 / "-2" 카운터가 없다
if redis.call('EXISTS', KEYS[3]) == 0 then return '-2' end

local mine = redis.call('HGET', KEYS[1], ARGV[1])
if mine then return mine end                    -- 재시도는 여기서 끝난다

-- 시각은 Redis 가 매긴다. 점수를 쓰는 인스턴스와 재는 인스턴스가 달라서다
local t = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)

local function give(seq)
  redis.call('HSET', KEYS[1], ARGV[1], seq)
  redis.call('ZADD', KEYS[4], now, ARGV[1])       -- 미확정으로 표시한다
  return seq
end

local f = redis.call('ZPOPMIN', KEYS[2])
if f[1] then return give(f[1]) end               -- 반납분부터 쓴다

local n = redis.call('INCR', KEYS[3])
if n <= tonumber(ARGV[2]) then return give(tostring(n)) end
redis.call('DECR', KEYS[3])

-- 여기부터 소진이다. 묶인 번호가 있으면 회수해 이 요청에게 준다
local cut = now - tonumber(ARGV[3])
local stale = redis.call('ZRANGEBYSCORE', KEYS[4], 0, cut, 'LIMIT', 0, 1)
if stale[1] then
  local seq = redis.call('HGET', KEYS[1], stale[1])
  redis.call('ZREM', KEYS[4], stale[1])
  -- 확정 표시가 붙은 것은 실제로 발급된 것이라 회수하지 않는다. pending 에서만 뺀다
  if seq and not string.find(seq, ':') then
    redis.call('HDEL', KEYS[1], stale[1])
    return give(seq)
  end
end
return '-1'
```

**시각을 앱에서 받지 않는다.** 점수를 쓰는 인스턴스와 그것을 재는 인스턴스가 다르므로, 앱 시계로 하면 **한 대만 어긋나도 그 인스턴스가 살아 있는 요청의 번호까지 오래된 것으로 보고 뺏는다.** 이 값은 앱이 한 번도 해석하지 않고 Redis 안에서만 비교되므로 앱에서 댈 이유가 없다. `TIME` 은 쓰기 앞에서도 쓸 수 있다. 효과 복제가 기본이라 복제본에도 계산된 점수가 그대로 간다.

**회수는 확정 표시를 건너뛴다.** 플러시가 표시를 붙이면서 `pending` 에서도 빼므로 정상적으로는 안 생기는 조합이지만, 한쪽만 실패하면 `"6:1"` 이 `pending` 에 남는다. 그것을 그대로 내주면 **이미 발급된 번호가 새 회원에게 간다.** 그래서 표시가 붙은 것은 `pending` 에서만 빼고 매핑은 건드리지 않는다.

**값이 두 상태를 갈라야 한다.** 1인 1매를 여기서 판정하기로 했으므로 "번호를 줬다" 와 "발급이 끝났다" 가 구분되어야 한다.

```
"6"     번호만 받았다.  그 번호로 진행한다
"6:1"   커밋까지 끝났다.  그 자리에서 이미 발급으로 답한다
```

**매핑이 있다고 바로 거절하면 안 된다.** 커밋에 실패해도 매핑이 남는 경우가 있어서(아래 실패 표), 거절했다가는 정당한 발급을 막는다. **거절은 `:1` 이 붙었을 때만이다.**

확정 표시는 **커밋이 끝난 뒤** 플러시 스레드가 남긴다. 배치 전체를 한 명령으로 갱신한다.

```
HSET coupon:{id}:seq     5001 "6:1" 5002 "7:1" ...
ZREM coupon:{id}:pending 5001 5002 ...
```

**둘을 함께 한다.** 확정 표시를 붙이면서 미확정 목록에서 뺀다. 각각 명령 하나라 배치 전체가 왕복 둘로 끝난다.

건당 비용은 사라지지만 **응답 경로 위에 왕복이 하나 붙는다.** 커밋과 응답 사이다. 이 표시를 남기지 못해도 정확성은 그대로다. 다음 요청이 DB 로 가서 `uk_mc_coupon_member` 에 막힐 뿐이다.

**왕복은 `INCR` 만 부를 때와 같은 1회다.** 빈 정렬 집합에 `ZPOPMIN` 은 O(1) 이고 Redis 안에서 도는 시간은 왕복에 묻힌다. `free` 와 매핑을 두는 값이 정상 경로를 느리게 하지 않는다. `-1` 이면 소진이라 DB 를 거치지 않고 그 자리에서 거절한다.

**`pending` 이 묶인 번호를 푼다.** 번호를 받고 커밋 전에 사라진 요청이 있으면 그 번호가 매핑에 잡힌 채 아무에게도 안 간다.

```
클라가 연결을 끊었다          그 사용자가 안 돌아온다
타임아웃이라 매핑을 유지했다   실패 표가 그렇게 정했다
앱이 급사했다                 catch 가 돌 기회가 없었다
```

**원인은 다르지만 결과가 같다.** `"6"` 인 채로 남아 이벤트 끝까지 묶인다. 원인을 구분할 수 없으므로 **시간으로 판정한다.**

**푸는 조건이 둘이고 축이 다르다.** 뭉쳐 읽으면 소진되자마자 다 푸는 것으로 오해한다.

```
트리거   소진 상태다        재고가 있으면 이 구간에 아예 안 온다
조건     기준 시간이 지났다  ZRANGEBYSCORE 로 오래된 것만 고른다
```

**트리거 덕분에 평상시 비용이 0 이고 주기 배치도 필요 없다.** `ZRANGEBYSCORE` 가 `INCR` 이 한도를 넘은 뒤에만 돈다.

**조건의 시계는 소진 시각이 아니라 번호를 준 시각부터 돈다.** `pending` 의 점수가 준 시각이라서다. 묶인 번호는 대개 소진 한참 전에 나간 것이라 **소진되는 순간 이미 기준 시간을 넘겨 바로 회수된다.** 늦어지는 것은 소진 직전 몇 초 안에 묶인 것뿐이다.

**대신 요청이 와야 돈다.** 소진 뒤 트래픽이 완전히 빠지면 회수가 실행될 일이 없고, 그 번호는 키가 만료될 때까지 남는다. 기준 시간을 줄여서 해결되는 문제가 아니다.

**TTL 이 아니라 점수인 이유가 있다.** 만료는 항목을 지우는 동작이라, 만료된 순간 회원 id 를 잃고 매핑에서 번호를 못 읽는다. **풀어줄 대상을 잃어버린다.** 점수는 만료를 판정만 하고 지우지 않아, 번호를 읽어 넘긴 뒤에 지울 수 있다. 기준 시간을 조회할 때 정하므로 나중에 바꾸기도 쉽다.

**여기의 `DECR` 은 안전하다.** 위에서 `DECR` 로는 못 고친다고 한 것은 DB 를 갔다 온 뒤의 얘기다. 그 사이에 남들이 `INCR` 해서 맨 위가 내가 아니게 된다. 이 자리는 스크립트 안이라 `INCR` 과 `DECR` 사이에 아무도 끼어들 수 없어 **맨 위가 나인 것이 확실하다.** `DECR` 이 성립하는 조건은 "아직 아무도 지나가지 않았다" 이고, 원자 스크립트 안이 그것을 만족하는 유일한 자리다.

**매핑은 R4 를 지키는 장치가 아니다.** R4 는 `uk_mc_coupon_member` 가 지킨다. Redis 가 매핑을 통째로 잃어도 재시도가 새 번호를 들고 오면 두 번째 행이 그 제약에 걸린다. **매핑이 아끼는 것은 순번이지 정확성이 아니다.** 이 구분이 없으면 Redis 장애를 실제보다 무겁게 보게 된다.

**Redis 에 두는 것은 넷이다.**

| 키 | 자료구조 | 담는 것 | 수명 |
|---|---|---|---|
| `coupon:{id}:seq` | 해시 | 회원 -> 순번. `"6"` 은 번호만 받음, `"6:1"` 은 커밋 완료 | 넷이 함께 |
| `coupon:{id}:free` | 정렬 집합 | 반납된 순번. `ZPOPMIN` 으로 낮은 것부터 꺼낸다 | 넷이 함께 |
| `coupon:{id}:counter` | 문자열 | 다음에 나갈 번호. `INCR` 로 올린다 | 넷이 함께 |
| `coupon:{id}:pending` | 정렬 집합 | 아직 커밋 안 된 회원. 점수가 **번호를 준 시각**이다 | 넷이 함께 |

**넷은 함께 살고 함께 죽는다.** 하나만 사라지면 나머지가 거짓말을 한다.

```
카운터만 사라짐   INCR 이 1 부터 다시 준다.  이미 쓴 번호와 충돌한다
매핑만 사라짐     재시도가 새 번호를 태운다.  1인 1매 판정도 놓친다
free 만 사라짐    반납분이 증발한다.  그만큼 덜 나간다
pending 만 사라짐  묶인 번호를 영영 못 찾는다
```

**수명도 넷이 같다.** 이벤트 종료 시 배치가 넷을 함께 지운다. TTL 은 `counter` 에만 `issue_end_at + 1분` 으로 걸어 두는데, 그것은 절차가 안 돌았을 때 새 요청이 카운터 없는 Redis 를 치지 않게 하는 그물이다. `issue_end_at` 이 `NULL` 이면 기준이 없어 걸지 않는다. 순서와 이유는 아래 "이벤트 종료 후" 에 있다.

**실패 종류를 갈라야 한다.** 전부 반납하면 남이 쓰는 번호를 다시 내주게 된다. 아래 처리는 모두 **실패를 잡은 쪽**이 한다.

| 실패 | 그 번호는 | 처리 |
|---|---|---|
| `uk_mc_coupon_member` 위반, **순번이 다르다** | 안 쓰였다 | 반납하고 매핑을 고친다 |
| `uk_mc_coupon_member` 위반, **순번이 같다** | **내가 이미 썼다** | 반납 금지. 확정 표시만 마저 남긴다 |
| `uk_mc_coupon_seq` 위반 | 남이 쓰고 있다 | 반납 금지. 매핑만 지우고 새 번호를 받는다 |
| 타임아웃, 커넥션 실패 | 커밋 여부를 모른다 | 반납 금지. 매핑을 유지해 재시도가 같은 번호로 오게 한다 |

**같은 제약 위반이 두 줄인 이유가 있다.** 이 회원이 갖고 있는 순번과 이번에 받은 순번을 **견줘 봐야 그 번호가 쓰였는지 알 수 있다.**

```
커밋은 됐는데 확정 표시를 남기기 전에 앱이 죽는다.  매핑은 "6" 그대로
사용자가 재시도 -> 매핑이 "6" 이라 같은 번호를 받는다
INSERT -> uk_mc_coupon_member 위반
```

여기서 그 번호를 반납하면 **실제 행이 쓰고 있는 6번이 `free` 로 간다.** 다음 사람이 그것을 받아 `uk_mc_coupon_seq` 에 부딪힌다. 두 줄을 가르지 않으면 실패가 실패를 낳는다.

**첫 줄은 매핑이 없었을 때만 온다.** 매핑이 있었다면 새 번호를 안 받았을 테니, 이 경로는 Redis 가 매핑을 잃은 뒤에 온 회원이다.

**어느 제약인지도 예외 메시지로 가르지 않는다.** 형식이 드라이버와 서버 판에 따라 달라진다. 아래 한 번의 읽기가 세 갈래를 다 가른다. 행이 없으면 순번 쪽 위반이고, 있으면 순번을 견줘 위 두 줄을 나눈다.

```sql
SELECT issue_seq FROM member_coupon WHERE coupon_id = ? AND member_id = ?;
```

지우면 재요청마다 새 번호를 받았다 또 막혀 되풀이하고, 그냥 두면 **반납한 번호가 매핑에 남아** 다음 재요청이 남이 가져간 번호를 받는다. 읽기가 하나 붙지만 드문 경로이고, 한 번 고치면 그 회원의 이후 요청이 Redis 에서 끝난다.

**이 읽기마저 실패하면 아무것도 건드리지 않는다.** 가르지 못한 채 손대면 잘못된 쪽을 고르게 되고, 그중 반납은 되돌릴 수 없다. **매핑을 그대로 두는 쪽이 언제나 안전하다.**

**`pending` 도 함께 움직인다.** 매핑을 고치거나 지우는 줄은 `ZREM` 으로 미확정 표시를 뗀다. **매핑을 유지하는 줄만 `pending` 에 남고**, 그래서 시간이 지나면 회수 대상이 된다.

**타임아웃도 안이 갈린다.** DB 에 닿기 전에 끊긴 실패는 커밋이 없었음이 확실해 반납해도 안전하다. 9장에서 나눈다.

**반납 코드 자체가 못 도는 경우는 9장에서 다룬다.**

### 이벤트 종료 후

**대기가 먼저고 나머지 셋은 한 트랜잭션이다.** 키를 먼저 지우면 지각 요청이 카운터 없는 Redis 를 친다.

```
1  마감에서 60초를 기다린다.  진행 중인 배치가 결판나는 시간이다
2  is_active 를 끈다
3  issued_quantity 를 실제 발급 수로 맞춘다
4  네 키를 UNLINK 한다
```

**대기를 종료 조건에 넣는 것이 이 절차의 요점이다.** 끄는 시점에 이미 발급 행 수가 안 움직이므로, 2~4번을 한 트랜잭션으로 묶을 수 있다. 나누면 **껐는데 발급 수가 안 맞은 상태**가 존재하고, 그 상태를 나중에 찾아 고치는 장치가 따로 필요해진다.

```sql
UPDATE coupon SET is_active = FALSE, updated_at = :now
 WHERE coupon_id = :couponId AND is_active = TRUE
   AND issue_end_at IS NOT NULL AND issue_end_at <= :closableBefore;   -- 앱이 지금 - 60초로 넘긴다
```

**관리자와 배치가 같은 조건을 쓴다.** 관리자가 먼저 끄든 배치가 끄든 거치는 경로가 하나뿐이라, 한쪽만 맞추고 다른 쪽은 안 맞추는 갈래가 안 생긴다.

**소진으로는 안 끝낸다.** 카운터가 한도를 넘어도 `free` 에 반납된 번호가 남아 있으면 스크립트가 그것을 다시 내주므로 최종이 아니다. 그리고 **소진 뒤에도 스위치가 켜져 있어야 요청이 올 때 도는 회수가 묶인 번호를 되살린다.** 그때 끄면 그 번호가 그대로 죽는다.

`issue_end_at` 이 `NULL` 인 쿠폰은 끌 수 없다. 끝나는 시각이 없으면 기다릴 기준도, TTL 을 걸 기준도 없다. **키가 계속 남는다.**

**종료 후보는 DB 로 찾는다.** Redis 키가 남아 있는지로 찾지 않는다.

```sql
SELECT coupon_id FROM coupon
 WHERE is_active = TRUE AND total_quantity IS NOT NULL
   AND issue_end_at IS NOT NULL AND issue_end_at <= :closableBefore;
```

**시각은 앱이 넘긴다.** `NOW()` 를 쓰면 **MySQL 서버의 시간대가 판정에 끼어든다.** 앱은 `issue_end_at` 과 `updated_at` 을 자기 기본 시간대의 벽시계로 쓰는데, DB 가 다른 시간대면 그 둘을 견주는 순간 시차만큼 어긋난다. 배포 환경이 우연히 같은 시간대라 안 드러날 뿐이고, 개발자 기계에서는 실제로 어긋난다.

**순번 확보 스크립트와 반대 선택이다.** 그쪽은 인스턴스 A 가 쓴 점수를 B 가 재므로 Redis 시계를 써야 했고, 여기는 **같은 앱이 쓴 값을 같은 앱이 견주므로** 앱 시계가 맞다.

키로 찾으면 **TTL 이 키를 먼저 지웠을 때 대상을 놓쳐** 3번을 건너뛴다. DB 만 보면 TTL 길이와 배치 주기가 서로 묶이지 않는다.

**`is_active = TRUE` 조건이 상한을 대신한다.** 아직 켜져 있는 이벤트만 보므로 후보가 자연히 작고, 한 번 꺼진 쿠폰은 다음 실행부터 이 집합에서 빠진다. 꺼진 것까지 후보로 삼으면 3년 전에 끝난 이벤트까지 매번 세게 되어 상한이 필요했고, **그 상한을 넘긴 쿠폰은 어긋난 채 남았다.** 이제 그 구멍이 없다.

**1번의 60초가 이 절차를 성립시킨다.** Redis 를 마지막으로 만지는 것은 순번 확보가 아니라 **실패 시 반납**이다. 커밋 시도 뒤에 오므로, 진행 중인 배치가 커밋되거나 실패해 반납까지 끝나야 발급 행 수가 멈춘다. 대기는 `배치 윈도우 + 커밋 + 캐시 TTL` 보다 넉넉하면 되고 초 단위다.

**기준이 마감 시각인 것이 중요하다.** "꺼진 시각 + 60초" 로 재면 배치가 언제 끄는지에 따라 기준이 흔들린다. 기다려야 할 것은 **마지막 요청이 들어올 수 있었던 시각**이고 그것이 `issue_end_at` 이다.

**2번이 먼저인 이유.** 새 요청을 1단계에서 끊는다. 다만 그 순간 **이미 서버 안에 들어와 1단계를 통과한 요청들이 남아 있고**, `is_active` 를 캐시해서 보는 버전이면 그 TTL 만큼 더 통과한다. 대기가 그것까지 덮는다.

**4번이 트랜잭션 안에 있어 Redis 가 죽으면 끄기까지 되돌아간다.** 다음 주기가 다시 시도하므로 스스로 낫고, 그 사이 마감 지난 요청은 기간 검사가 이미 막는다. TTL 은 `counter` 에만 걸려 있어 **나머지 세 키는 이 절차가 유일한 정리다.**

**4번을 앞당기면 안 되는 이유.** 카운터가 없는 상태에서 요청이 닿으면 `INCR` 이 1 을 준다. 1번은 이미 남이 쓴 번호라 `uk_mc_coupon_seq` 에 걸린다. `maxmemory-policy` 로 경고한 상황을 손으로 만드는 셈이다.

**소진으로 끝나도 순서는 같다.** 선착순은 대개 시각이 아니라 재고 소진으로 끝나는데, 그때는 카운터가 이미 한도를 넘어 있어 지각 요청이 와도 스크립트가 `-1` 로 거절한다. **키가 살아 있는 동안은 안전하고 위험은 지운 뒤에만 생긴다.**

`DEL` 이 아니라 `UNLINK` 를 쓴다. 1만 필드 해시를 그 자리에서 해제하지 않고 백그라운드로 넘긴다.

**TTL 은 그물로만 건다.** 위 절차가 안 돌았을 때를 위한 것이고 주 경로가 아니다.

```
issue_end_at 이 있다    EXPIREAT (issue_end_at + 1분)
issue_end_at 이 NULL    걸지 않는다.  끝나는 시각이 없어 기준이 없다
```

**`EXPIREAT` 를 쓴다.** 절대 시각이라 스크립트가 몇 번 불려도 값이 같다. `EXPIRE` 로 상대 초를 걸면 부를 때마다 갱신되어 **"마지막 발급 후 1분" 이 되고**, 발급이 잠깐 뜸해지면 그때 사라진다.

**1분은 꼬리를 덮는 값이다.** `issue_end_at` 직전에 1단계를 통과한 요청이 Redis 에 닿는 데까지, 그리고 마지막 배치가 실패해 반납하는 데까지다. 배치 윈도우와 커밋과 캐시 지연을 합쳐도 초 단위다.

**이 TTL 은 1단계의 기간 체크에 기댄다.** 마감이 지난 요청이 거기서 안 걸리면 키가 만료된 뒤에 `INCR` 이 1 을 내준다.

3번은 아래와 같다. `coupon.issued_quantity` 를 실제 발급 수로 맞춘다.

```sql
UPDATE coupon c
   SET issued_quantity = (SELECT COUNT(*) FROM member_coupon WHERE coupon_id = c.coupon_id)
 WHERE coupon_id = ?;
```

여기의 `COUNT(*)` 는 아래 "발급 수를 어떻게 세나" 의 규칙을 따른다. 미리 넣어두는 버전에서는 조건이 붙는다.

**발급 중에는 갱신하지 않는다.** 상한을 순번이 행 단위로 강제하므로 이 값은 판정에 쓰이지 않는다. 순수한 기록이라 늦게 맞춰도 아무것도 틀어지지 않는다.

```
발급 중        건드리지 않는다
이벤트 종료    한 번 맞춘다
관리자 조회    그때 COUNT 해서 맞춘다
```

발급 경로에서 매번 올리면 `coupon` 한 행에 락이 몰려 순번을 둔 의미가 사라진다.

**필요한 버전과 아닌 버전이 갈린다.** v1 은 카운터와 기록이 한 트랜잭션이라 애초에 어긋나지 않는다. 7장을 보라.

### 발급 수를 어떻게 세나

**두 질문을 먼저 갈라야 한다.** 순번을 받고 기록이 실패하면 둘이 갈린다.

| 알고 싶은 것 | 쓸 것 |
|---|---|
| 몇 장이 나갔나 | 발급 수 |
| 순번이 어디까지 소비됐나 | 소비된 최대 순번 |

`issued_quantity` 는 발급 수를 뜻한다. 최대 순번을 넣으면 실패한 번호까지 나간 것으로 센다. 반대로 **카운터를 재건할 때는 소비된 최대 순번 + 1** 이다. 발급 수로 복구하면 이미 쓴 번호를 다시 내주어 `uk_mc_coupon_seq` 에 걸린다.

**그런데 둘을 구하는 식이 버전마다 다르다.** 행이 있다고 발급된 것이 아닌 버전이 있기 때문이다. 미리 넣어두는 버전은 `COUNT(*)` 가 처음부터 `total_quantity` 다. **다른 장은 이 표를 가리킨다.**

| | 발급 수 | 소비된 최대 순번 |
|---|---|---|
| 행이 발급될 때 생긴다 (v1~v5) | `COUNT(*)` | `MAX(issue_seq)` |
| 행을 미리 넣어둔다 (접은 [v6](coupon-v6.md)) | `COUNT(*) WHERE status = 'ISSUED'` | `MAX(issue_seq) WHERE status = 'ISSUED'` |

구멍 수도 갈린다.

```
v1~v5   소비된 최대 순번 - 발급 수          행이 없는 번호가 구멍이다
v6      status = 'PENDING' 인 행 중          구멍이 행으로 실재한다
        issue_seq 가 소비된 최대 순번보다 작은 것
```

**미리 넣는 버전에서 조건을 빠뜨리면 조용히 틀린 값이 나온다.** 발급 수는 언제나 `total_quantity` 가 되어 종료 후 갱신이 실제와 무관해지고, 구멍 수는 언제나 0 이라 검증이 항상 통과한다.

## 4. 배치 구조

선착순 이벤트는 평소와 트래픽 모양이 다르다. **짧은 시간에 한 경로로 몰린다.** 그래서 그 경로를 나머지와 분리한다.

```
                         ALB
                          |
        +-----------------+-----------------+
        |                                   |
  path = 선착순 발급                     그 밖의 모든 경로
        |                                   |
  tg-coupon                              tg-app
  ASG-coupon (t3.small x N)              ASG-app (t3.small x N)
        |                                   |
        +----------------+------------------+
                         |
              +----------+----------+
              |                     |
        ElastiCache            RDS (단일)
        primary + replica
```

**이벤트 전에 전용 ASG 를 올리고 ALB 규칙으로 그 경로만 보낸다.** 이벤트가 끝나면 내린다.

### 왜 분리하나

분리하지 않으면 선착순 트래픽이 톰캣 스레드와 커넥션 풀을 다 먹고, **상품 조회와 주문 같은 평상시 기능이 같이 죽는다.** 격벽을 세워 장애를 한쪽에 가둔다.

부수 효과가 둘 더 있다.

* **버전 비교가 깨끗해진다.** 전용 인스턴스만 재면 다른 트래픽이 지표를 오염시키지 않는다
* **되돌리기가 쉽다.** 문제가 나면 ALB 규칙 하나를 지워 선착순만 차단하고 나머지는 살린다

### 캐시는 2대다

`primary + replica` 로 두고 자동 페일오버를 켠다. 이벤트 구간에는 캐시가 순번의 판정 주체가 되므로 **단일 노드가 죽으면 이벤트가 멈춘다.**

평상시 단일 노드 전제(`fm-infra` 의 `INF-04`)는 캐시가 Degradable 이라는 근거 위에 서 있는데, **이 구간에는 그 전제가 성립하지 않는다.** 등급이 올라가므로 노드도 올린다.

복제가 비동기라 페일오버 시 카운터가 몇 건 뒤로 밀릴 수 있다. **밀려도 초과 발급은 나지 않는다.** 2장의 두 제약이 막는다. 밀린 구간은 이미 쓴 번호라 기록이 실패하고, 그 처리는 버전마다 정한다.

## 5. 커넥션 예산이 확장의 상한이다

앱은 N 대로 늘릴 수 있지만 **DB 는 한 대다.** 늘어난 인스턴스가 전부 같은 RDS 를 본다.

```
db.t4g.micro 의 max_connections 약 60 (예측, OPS-1-11 로 실측)
```

지금도 여유가 넉넉하지 않다. `앱과DB 장애대응구조` 의 배분이다.

| 출처 | 평상시 | 배포 중 |
|---|---|---|
| 앱 2대 | 20 | 30 |
| 배치 1대 | 10 | 10 |
| `mysqld_exporter` | 1~3 | 1~3 |
| 운영자 접속 | 1~2 | 1~2 |
| **합계** | **약 33** | **약 45** |

**여기에 선착순 전용 ASG 가 얹힌다.** 앱과 같은 `application.yml` 을 쓰면 인스턴스당 10 이므로, 전용 3대만 되어도 30 이 더해져 예산을 넘긴다.

| 전용 인스턴스 | 추가 커넥션 | 평상시 33 과 합계 |
|---|---|---|
| 2대 | 20 | 53 |
| 3대 | 30 | 63 (초과) |
| 4대 | 40 | 73 (초과) |

### 그래서 둘 중 하나를 해야 한다

**1. 전용 인스턴스의 풀을 줄인다.** 선착순 발급은 `insert` 한 번이라 긴 트랜잭션이 없다. 풀 4~5 로도 처리량이 나오는지 부하 시험에서 본다. `application-coupon.yml` 같은 별도 프로파일이 필요하다.

**2. DB 를 키운다.** `max_connections` 가 클래스 메모리에 비례하므로 한 단계 올리면 두 배가 된다. 비용이 는다.

**어느 쪽이든 "앱을 N 대로 늘리면 처리량이 N 배" 가 아니다.** DB 가 단일 지점이라 그 앞에서 막힌다. 이 한계를 어디서 만나는지가 부하 시험의 핵심 관찰 대상이다.

순번 확보를 캐시로 옮기는 것이 커넥션 점유 시간을 줄이지만, **커넥션 개수 자체를 줄이지는 않는다.** 개수는 풀 설정이 정한다.

### 전용 풀은 인스턴스가 이미 나눈다

4장이 ALB 경로로 ASG 를 갈랐으므로 **전용 인스턴스의 풀 전체가 곧 선착순 전용 풀**이다. 따로 만들 것이 아니라 `application-coupon.yml` 이 그 풀의 값을 갖는다.

```
maximum-pool-size    줄인다. 위 예산표에서 역산한다
connection-timeout   앱 기본 3초보다 짧게 잡는다 (9장)
```

**한 JVM 안에서 더 쪼개지 않는다.** v3 부터 요청 스레드는 순번을 받아 큐에 넣고 기다릴 뿐이라 DB 를 만지지 않는다. 정상 경로에서 커넥션을 쓰는 주체가 플러시 스레드 하나뿐이라 나눌 상대가 없다.

**쪼갤 신호는 하나다.** 요청 스레드가 풀을 다 잡아 플러시 스레드가 커넥션을 못 얻으면 **큐에 모인 배치 전체가 함께 멈춘다.** 8장의 `hikaricp_connections_pending` 을 플러시 스레드 기준으로 본다.

그때는 플러시 전용 `DataSource` 를 2개짜리로 뗀다. **`JdbcTemplate` 만 쓰게 해** `EntityManagerFactory` 를 늘리지 않는다. 벌크 쓰기라 JPA 가 필요 없다.

## 6. 지금 인프라와 다른 점

위 구조는 목표다. `fm-infra` 의 현재 확정값과 세 군데가 어긋난다. **이벤트 전에 인프라 쪽 변경이 선행되어야 한다.**

| | 현재 | 필요 |
|---|---|---|
| 앱 ASG | `max_size = 2` | N 대 확장 |
| 캐시 | `num_cache_clusters = 1`, 페일오버 off | 2대, 자동 페일오버 |
| ALB | 대상 그룹 1개 | 선착순 전용 그룹과 경로 규칙 |
| 전용 ASG | 없음 | 신설 |

`max_size = 2` 는 임의의 값이 아니라 **무중단 배포 절차가 성립하는 최소치**로 정해진 것이다(`desired +1` 로 신규를 먼저 띄운다). 늘리는 것 자체는 문제가 없으나 그 근거를 함께 고쳐야 한다.

캐시 복제본은 월 비용이 는다. 이벤트 구간에만 올렸다 내리는 방식과 상시 유지 중 어느 쪽인지는 인프라 쪽 결정이다.

## 7. 버전

**요청과 응답은 끝까지 동기다.** 이것이 버전을 가로지르는 고정 제약이다.

응답을 받은 시점에 `member_coupon` 행이 이미 커밋되어 있다. 뒤 버전들이 요청을 묶어 쓰지만 그것은 **묶어서 쓰되 커밋까지 기다리는 것**이지 나중에 쓰는 것이 아니다. 그래서 **모든 버전이 정합성 100% 다.** 발급되었다고 답한 요청은 반드시 기록이 있다.

이 제약을 푸는 순간(접수만 응답하고 나중에 쓰기) 훨씬 단순하고 빨라지지만 다른 기능이 된다. 선착순은 받았는지를 그 자리에서 알아야 하는 기능이라 유지한다.

| | 무엇을 바꾸나 | 무엇을 얻나 | 대가 |
|---|---|---|---|
| **v1** | DB 조건부 UPDATE | 기준선. 추가 인프라 0 | 한 행에 락이 몰린다 |
| **v2** | 카운터를 Redis 로 | **거절이 DB 를 안 거친다** | 캐시가 판정 주체가 된다 |
| **v3** | 인스턴스별 큐 + Bulk INSERT | DB 왕복 감소 | 배치 윈도우만큼 응답이 늦다 |
| **v4** | 가상 스레드 | 대기 중 캐리어 스레드 반납 | pinning 확인이 필요하다. 백프레셔가 커넥션 풀로 밀려 응답 지연 최대값이 는다 |
| **v5** | Bulk INSERT 를 배치 서버로 + Redis 대기열 | **DB 커넥션이 인스턴스 수와 무관해진다** | 분산 요청-응답이 필요하다 |
| [v6](coupon-v6.md) | 미리 넣은 행을 update 로 잡는다 | 구멍이 행으로 실재해 회수가 싸다 | **DDL 다섯 군데. 접었다** |
| v7 | 쿠폰별 테이블에 미리 넣고 update | PK 가 순번을 겸한다 | **이벤트마다 DDL. 접었다** |

```
v1 -> v2 -> v3 -> v4        처리량 사다리.  v4 가 채택안이다
                   |
                   ├─ v5           커넥션 예산이 막힐 때 꺼낸다
                   └─ v6 -> v7     검토했으나 접었다
```

**한 단계에 변수 하나**다. v4 는 v3 위에서 설정 한 줄만 바꾼다.

**v4 가 채택안이다.** v1~v4 는 앞 버전보다 빠르다는 뜻의 사다리이고, v5 부터는 v4 에서 다른 축으로 갈라진다. v5 는 배치 위치만 옮기지만 얻는 것이 처리량이 아니라 커넥션 예산이고 p99 는 오히려 나빠진다. **일렬로 읽어 "번호가 클수록 빠르다" 로 오해하면 안 된다.**

**v6 과 v7 은 접었다.** 순번은 v2 처럼 Redis 가 주지만 스키마를 바꾸는 안이고, 그 대가만큼의 이득이 안 나왔다. 이유는 아래 절에 있다.

### v1 만 정산이 필요 없다

v1 은 `UPDATE` 와 `INSERT` 가 한 트랜잭션이라 `coupon.issued_quantity` 가 곧 실제 발급 수다. 어긋날 자리가 없다.

**v2 부터는 카운터가 Redis 로 가므로** `issued_quantity` 가 갱신되지 않는다. 이벤트 종료 시점이나 관리자가 발급 현황을 조회할 때 실제 행 수로 맞춘다. 발급 경로에서 매번 갱신하면 핫 로우를 피한 의미가 사라진다.

### v2 가 이득의 대부분을 가져간다

선착순 트래픽은 거절이 많다.

```
재고 10,000장에 동시 요청 20,000건
  -> 10,000건이 소진 거절
```

v1 은 거절되는 절반도 커넥션을 잡고 그 행의 락을 기다린다. 조건부 UPDATE 가 0행을 반환해야 소진을 알 수 있어 **판정 자체가 락 뒤에 있기 때문**이다. 요청이 재고보다 더 몰릴수록 이 비율은 올라간다.

v2 는 `INCR` 결과가 한도를 넘으면 DB 를 건드리지 않고 끊는다. 5장의 커넥션 예산이 20 남짓인 환경에서 이 차이가 결정적이다.

### v3 부터는 발급 성공 수에 비례한다

Bulk INSERT 가 줄이는 것은 **성공한 발급의 쓰기 비용**이고, 그 건수 상한은 `total_quantity` 다.

| `total_quantity` | v3 이후의 의미 |
|---|---|
| 1,000 | 거의 없다. v2 에서 실험이 끝난다 |
| **10,000** | **이 과제의 값**([requirement.md](requirement.md)). 커밋 비용이 약 1.5초에서 0.1초대로 준다 |
| 100,000 이상 | 확실하게 벌어진다 |

**목표 수량을 정하지 않으면 v3 이후의 측정이 노이즈에 묻힌다.**

### v3 의 변수는 배치 윈도우다

윈도우를 처음부터 정해두지 않는다. 부하 시험에서 늘려가며 가장 좋은 지점을 찾는 것이 v3 의 실험 내용이다.

```
1ms   5ms   10ms   20ms   50ms   100ms
```

윈도우를 키우면 한 번에 묶이는 행이 늘어 DB 왕복과 커밋 횟수가 줄지만 그만큼 응답이 늦어진다. **처리량과 p99 가 서로 반대로 움직이는 축**이라 한쪽만 보면 값을 못 정한다.

크기 조건을 함께 두어 한산할 때 불필요하게 기다리지 않게 한다.

```
배치 윈도우 20ms  OR  배치 크기 500      먼저 닿는 쪽에서 플러시한다
```

### 큐가 단계마다 다르다

**모든 버전에서 큐는 순번 확보 뒤에 있다.** 순서는 Redis 카운터가 정하고 큐는 쓰기를 묶기만 한다. 그래서 인스턴스별로 두어도 선착순이 깨지지 않는다.

**Redis 가 있어야 성립한다.** `INCR` 이 전역에서 하나뿐인 순서기라 도착 순서가 그대로 번호가 된다. **Redis 가 죽으면 순서를 정할 주체가 없어지고, 그것이 대체 경로를 두지 않는 이유다**(3장). 순서 없이 발급하느니 받지 않는다.

다만 이 순서도 **"Redis 도달 순서" 이지 사용자가 누른 순서는 아니다.** 클라이언트 회선 차이가 수백 ms 씩 벌어지므로 그 앞에서 이미 흔들린다. 큐와 배칭은 그 뒤에 있어 **더 흔들지 않을 뿐**이다.

```
v3, v4   인스턴스별 인메모리 큐    받은 서버가 자기 큐를 소비한다
v5       공유 큐 (Redis 대기열)    배치 서버가 소비한다
```

**인스턴스 큐에는 셋을 저장한다.**

```
seq         Redis 에게 순번 발급 받은 것
member_id   누구에게 발급하는지
future      플러시 스레드가 결과를 돌려줄 통로
```

v3, v4 의 큐는 같은 프로세스가 넣고 빼므로 인메모리로 족하다. 프로세스가 죽으면 그 항목을 기다리던 요청 스레드도 함께 죽어서, 큐가 살아남아도 결과를 돌려줄 상대가 없다. **v5 에서 처음 프로세스 경계를 넘으므로 그때 Redis 가 필요해진다.**

v3 에서 공유 큐를 쓰면 요청을 받은 서버와 처리하는 서버가 갈려 **v5 의 어려운 부분이 앞당겨진다.** 인스턴스별로 둔다.

### 플러시 스레드 수는 재서 정한다

**1개부터 N 개까지 늘려가며 부하 시험으로 정한다.** 배치 윈도우처럼 미리 값을 박지 않는다.

```
1   2   4   8   ...
```

**미리 정하지 않는 이유는 양쪽으로 대가가 있기 때문이다.**

```
적으면   커밋 시간(2~4ms)이 그대로 천장이 된다
         유입이 처리 능력을 넘으면 큐가 쌓이고 요청 예산을 넘긴다

많으면   같은 유입을 나눠 가져 배치가 쪼개진다
         플러시 스레드가 커넥션을 하나씩 물어 5장의 예산을 먹는다
         v3, v4 는 인스턴스별이라 이것이 N 에 비례해, 오토스케일로 같이 는다
```

**어느 쪽이 이길지는 커밋 지연과 유입 모양이 정한다.** 둘 다 재보기 전에는 모르는 값이다.

**함께 볼 지표는 셋이다.**

```
큐 최대 길이                     늘려도 안 줄면 병목이 DB 쪽이다
p99                              스레드를 늘렸는데 오르면 배치가 쪼개진 것이다
hikaricp_connections_pending     플러시 스레드가 커넥션을 못 얻는지 본다
```

**처리량이 평탄해지고 p99 만 오르기 시작하는 지점 앞에서 정한다.** v5 절이 같은 규칙을 쓴다.

**참고할 계산이 하나 있다.** DB 로 갈 쓰기는 `total_quantity` 가 상한이고 거절은 Redis 가 막아 오지 않으므로, **총량 자체가 크지 않다.** 그래서 적은 수로도 충분할 가능성이 있고, 그 확인이 이 시험의 내용이다.

### 요청 예산

요청 스레드가 응답까지 기다리는 총 시간이다. v3 부터 요청 스레드는 큐에 넣고 자므로 이 값이 없으면 무한정 기다린다. 넘으면 **혼잡 응답**으로 끊는다.

**계층이 역전되면 안 된다.**

```
요청 예산  >  플러시 한 번 x 볼 윈도우 수
플러시 한 번 = 커넥션 획득(connection-timeout) + 쓰기(socketTimeout) + 커밋
```

역전되면 요청 스레드가 먼저 포기해 혼잡으로 답한 뒤에 그 배치가 커밋된다. **실패했다고 답했는데 발급된 상태**가 되고, 사용자가 돌아오지 않으면 그 슬롯은 죽은 재고가 된다. 9장이 `connection-timeout` 을 짧게 잡으라고 하는 두 번째 근거가 이것이다.

값은 부하 시험에서 정하되 **ALB 유휴 타임아웃과 사용자가 기다려 줄 시간보다 짧아야 한다.** 기본값을 물려받으면 톰캣 스레드가 그만큼 잡혀 뒤 요청이 다시 밀린다.

### v5 는 다중 플러시가 전제다

배치 서버가 한 스레드로 순차 커밋하면 커밋 시간(2~4ms)이 그대로 천장이 된다. 2 vCPU 를 못 쓰고 그룹 커밋도 묶일 상대가 없다. **단일 스레드로 만들면 v5 가 v3 의 열화판이 된다.**

```
플러시 스레드 수 = 큐 샤드 수 = 배치 서버의 커넥션 수
시작 4~6 (코어 x 2 + 1), 상한 10 (5장의 배치 몫)
```

**앱 인스턴스 수와 묶지 않는다.** 묶으면 커넥션이 다시 N 에 비례해 v5 의 이득이 사라진다. 큐 샤드도 `coupon:q:{instanceId}` 가 아니라 `coupon:q:0` ~ `coupon:q:3` 처럼 **고정 개수**로 둔다. 앱이 오토스케일해도 배치 서버를 다시 설정할 일이 없다.

**배치 크기와 상충한다.** 같은 유입을 나눠 가지므로 스레드를 늘리면 배치가 그만큼 쪼개진다. 유입이 처리 능력 안이면 개수가 결과를 바꾸지 않고, **큐가 쌓이는 폭주 구간에서만 의미가 생긴다.** 그래서 폭주 부하로 재서 처리량이 평탄해지고 p99 만 오르기 시작하는 지점 앞에서 정한다.

### v5 의 대가

배치 서버가 다른 머신이므로 결과를 원래 요청을 붙들고 있는 스레드에게 되돌려야 한다. 상관 ID 와 응답 통로가 필요하고, 유실과 타임아웃을 다뤄야 한다.

v3, v4 에는 이 문제가 없다. 같은 JVM 안이라 객체 하나로 넘긴다.

**이 교환이 v5 의 전부다.** 커넥션 예산이 실제 병목이면 살 만한 대가이고, 아니면 복잡도만 는다. v4 까지 재보면 답이 나온다.

### v6 은 접었다

`member_id` 를 NULL 허용으로 바꾸고 이벤트 전에 `total_quantity` 만큼의 행을 `PENDING` 으로 미리 넣은 뒤, 발급을 insert 가 아니라 **그 순번의 행을 잡는 것**으로 바꾸는 안이었다.

```sql
UPDATE member_coupon
   SET member_id = ?, status = 'ISSUED', issued_at = NOW(6), updated_at = NOW(6)
 WHERE coupon_id = ? AND issue_seq = ? AND status = 'PENDING';
```

**근거가 둘이었는데 하나가 없어지고 하나가 줄었다.**

| 원래 근거 | 지금 |
|---|---|
| Redis 가 죽어도 폴백에 락이 없다 | **폴백을 안 두기로 해 무의미해졌다**(3장) |
| 구멍이 행으로 실재해 회수가 싸다 | `pending` 이 정상 경로를 맡아 **Redis 재건 때만 쓰인다**(3장) |

**내는 것은 그대로다.**

```
DDL 다섯 군데   member_id NULL, issued_at NULL, status 집합에 PENDING
                조건부 CHECK, idx_pending
스냅샷 시점      발급 시점이 아니라 사전 삽입 시점이 박힌다
배칭 손해        UPDATE 는 INSERT 처럼 한 문장으로 안 합쳐진다
```

**드문 상황의 조회 하나를 위해 DDL 을 다섯 군데 바꾸는 거래**라 접었다. v4 는 발급 방식을 위해 스키마를 늘리지 않는다. 스냅샷 컬럼을 걷는 변경은 따로 있지만 **제약을 더하는 것이 아니라 안 쓰는 컬럼을 빼는 것**이라 성격이 다르다(3장).

**10만 이상 규모에서는 다시 볼 값이 있다.** 우측 말단 핫 페이지가 사라지는 효과가 그때는 드러날 수 있다. 설계 전체는 [coupon-v6.md](coupon-v6.md) 에 남겨 두었다.

---

### v7 도 접었다

v6 의 변형이다. **개선이 아니라 대안이었고, 검토 결과 v6 보다도 열등했다.** v6 을 접었으니 자연히 함께 접힌다. 미리 넣고 update 로 잡는 것은 같은데, 그 행을 `member_coupon` 이 아니라 **쿠폰 전용 테이블**에 둔다.

```sql
CREATE TABLE coupon_issue_1234 (
    id        INT    NOT NULL AUTO_INCREMENT,
    coupon_id BIGINT NOT NULL,
    member_id BIGINT NULL,
    issued_at DATETIME(6) NULL,
    PRIMARY KEY (id),
    UNIQUE KEY uk_ci1234_coupon_member (coupon_id, member_id),
    CONSTRAINT fk_ci1234_coupon FOREIGN KEY (coupon_id) REFERENCES coupon (coupon_id),
    CONSTRAINT chk_ci1234_one   CHECK (coupon_id = 1234),
    CONSTRAINT chk_ci1234_limit CHECK (id <= 10000)
);
-- 이벤트 전에 1..10000 을 미리 넣는다
```

**PK 가 순번을 겸하므로 순번 컬럼이 필요 없다.** 테이블이 쿠폰 전용이라 `id` 가 그 쿠폰 안에서 1부터 시작하기 때문이다. 공용 `member_coupon` 은 PK 가 전역이라 이렇게 못 한다.

상한은 두 겹이다. 1..10000 이 이미 차 있어 명시 INSERT 는 PK 중복에 걸리고, `AUTO_INCREMENT` 가 주는 10001 은 `chk_ci1234_limit` 에 걸린다.

| | |
|---|---|
| **얻는 것** | 순번 컬럼이 필요 없다. PK 가 겸한다 |
| | 발급 경로에 `AUTO_INCREMENT` 가 없어 구멍이 안 생긴다 |
| **내는 것** | **이벤트마다 DDL.** Flyway 소유권, `ddl-auto: validate`, JPA 매핑과 부딪힌다 |
| | **쓰기가 두 번이다.** 쿠폰함과 주문은 `member_coupon` 을 보므로 옮기는 단계가 붙는다 |
| | 발급 순서가 안 남는다. PK 가 사전 삽입 순서다 |
| | 상한이 DDL 리터럴이라 이벤트마다 수량이 다르면 슬롯을 용량별로 나눠야 한다 |

DDL 부담은 Flyway 로 슬롯 테이블을 미리 만들어두고 `TRUNCATE` 로 재사용하면 준다. `TRUNCATE` 는 `AUTO_INCREMENT` 도 1 로 되돌린다.

**왜 v6 보다 열등한가.**

| | v6 | v7 |
|---|---|---|
| 발급 시 쓰기 | 1회 | **2회** |
| DDL | 마이그레이션 1회 | **이벤트마다** |
| 발급 순서 기록 | `issue_seq` 가 남는다 | **안 남는다** |
| 스냅샷 시점 | 사전 삽입 시점 | 옮긴 시점 |
| 아끼는 것 | | `member_id` NULL 허용 하나 |

**쓰기가 두 번인 것이 핵심이다.** 슬롯 테이블은 목적지가 아니다. 쿠폰함 조회와 만료 배치가 `member_coupon` 을 보고, 무엇보다 `orders` 와 `order_item` 이 `uk_mc_id_member` 등으로 `member_coupon` 을 복합 외래 키로 참조한다. **옮기지 않으면 받은 쿠폰을 주문에 쓸 수 없다.** 조회를 슬롯 테이블로 돌려서 피할 수 있는 성격이 아니다.

옮기는 시점을 늦추면 쓰기는 한 번이 되지만 발급 직후 주문이 막히고, 조회 경로가 쓰기를 유발하게 되어 읽기 전용으로 유지할 수 없게 된다.

**발급 순서가 안 남는 것도 크다.** PK 가 사전 삽입 순서라 몇 번째로 발급됐는지를 못 알려준다. `issued_at` 만 남는데 인스턴스 간 시계 오차가 있다. `issue_seq` 도 구멍이 재사용되면 도착 순서와 어긋나지만, **어긋나는 자리를 셀 수 있다는 점이 다르다.**

v7 이 아끼는 것은 `member_id` 를 NULL 허용으로 바꾸지 않아도 되는 것 하나인데, **그것도 조건부 CHECK 로 대부분 보완된다.** 하나를 아끼려고 넷을 무는 거래다.

## 8. 무엇을 측정하나

버전을 나누는 목적이 비교이므로, **같은 조건에서 같은 지표를 잰다.** 재지 않으면 버전을 나눈 의미가 없다.

| 지표 | 왜 |
|---|---|
| 초당 발급 처리량 | 버전 사이의 주된 차이가 여기서 난다 |
| 응답 시간 p99 | 평균은 대기가 몰리는 구간을 감춘다 |
| 발급 실패율과 사유 | 충돌, **소진**, **혼잡**, DB 타임아웃을 나눠 센다. 둘을 뭉치면 다 판 것과 못 판 것이 같은 통계가 된다 |
| 재요청 비율 | `alreadyIssued` 로 센다. 200 만 보면 첫 발급과 섞인다 |
| **최종 발급 수 대 `total_quantity`** | R1 검증. 초과는 물론 과소도 본다. 세는 식은 3장을 따른다 |
| DB 커넥션 대기 (`hikaricp_connections_pending`) | 병목이 DB 인지 아닌지 가른다 |
| **큐 최대 길이** | 앱이 급사했을 때 잃는 건수의 상한이다. 폭주 구간에서 얼마나 자라는지 본다 |
| **전용 인스턴스 수 대 처리량** | 5장의 상한을 어디서 만나는지 본다 |
| 평상시 경로의 지표 | 격벽이 실제로 작동했는지. 선착순이 몰리는 동안 상품 조회가 멀쩡해야 한다 |

마지막 두 줄이 이 배치 구조를 택한 이유와 직결된다. **인스턴스를 늘려도 처리량이 안 늘기 시작하는 지점**이 DB 한계이고, 그때 평상시 경로가 같이 느려지면 격벽이 새는 것이다.

부하 시험 환경과 절차는 인프라 저장소(`fm-infra`)가 갖는다. **잰 조건을 결과에 함께 적는다.** 전용 인스턴스 수, Hikari 풀 크기, 배치 윈도우와 배치 크기, 플러시 스레드 수, DB 클래스, 캐시 노드 수가 바뀌면 다른 실험이다.

## 9. 구성 요소가 죽었을 때

평상시 순번 반납은 **앱의 `catch` 가** 실패를 잡아 `free` 에 넣는다(3장). 무엇이 죽느냐에 따라 그 경로가 끊기는 자리가 다르다.

| | 반납 주체 | 끊기는 지점 | 대신 맡는 쪽 |
|---|---|---|---|
| 앱 사망 | 앱의 `catch` | **주체가 사라진다** | 사용자 재시도. 안 오면 `pending` 이 회수한다 |
| Redis 사망 | 앱의 `catch`. 살아 있다 | **넣을 `free` 가 없다** | 복구 시 재건이 채운다 |
| RDB 사망 | 앱의 `catch`. 살아 있다 | **끊기지 않지만 반납하지 않는다** | 사용자 재시도. 안 오면 `pending` 이 회수한다 |

**반납 경로가 끊겨도 별도 배치가 필요 없다.** 앱 사망은 `pending` 이 소진 시점에 풀고, Redis 사망은 복구 시 재건이 `free` 를 채운다. **각각 훅이 있다.**

**진행 중이던 발급으로 보면 무게가 다르다.**

| | 진행 중이던 발급 |
|---|---|
| **앱 사망** | **큐째로 사라진다.** 응답도 못 간다 |
| Redis 사망 | 전부 완료된다. 번호를 받은 뒤로는 DB 만 있으면 되기 때문이다 |
| RDB 사망 | 전부 실패한다. 번호는 그 사용자 것으로 남아 재시도가 이어받는다 |

### 앱이 죽었을 때

프로세스가 통째로 죽으면 `catch` 가 돌 기회가 없다. **큐에 남아 있던 발급분이 함께 사라진다.** 그 요청들은 응답을 받지 못하고, 쥐고 있던 번호는 `free` 에도 DB 에도 남지 않는다.

**사용자가 재시도하면 닫힌다.** 매핑이 같은 번호를 돌려주므로 그대로 성공한다. **재시도가 오지 않을 때만 묶인 채로 남는다.**

남은 것은 **`pending` 이 소진 시점에 푼다**(3장). 그 번호는 매핑에 잡혀 있어 `free` 에도 없고 카운터도 이미 지나갔지만, `pending` 에 준 시각이 남아 있어 **기준 시간을 넘긴 것을 골라낼 수 있다.** 재고가 떨어진 순간 그 번호가 다음 사람에게 간다.

**그래서 주기 배치가 필요 없다.** 앱 급사는 죽은 쪽이 알릴 수 없어 훅이 없는데, **소진이라는 자연스러운 시점이 그 자리를 대신한다.** 재고가 남아 있는 동안은 묶인 것이 있어도 급하지 않으므로 그때까지 아무 일도 하지 않아도 된다.

**잃는 규모는 큐 깊이가 정한다.** 유입이 처리 능력 안이면 배치 윈도우 동안 쌓인 것뿐이라 수십 건이고, 큐가 쌓이는 폭주 구간에서 죽으면 그만큼 늘어난다. 8장에서 큐 최대 길이를 함께 재는 이유다.

### Redis 가 죽었을 때

**진행 중이던 발급은 끊기지 않는다.** 큐 항목이 `(seq, member_id, future)` 뿐이고 플러시 스레드는 DB 에만 쓰므로, 이미 번호를 받은 요청은 그대로 완료되고 응답도 정상적으로 나간다. **셋 중 진행 중인 발급에 가장 무해하다.**

**새 요청은 혼잡으로 끊는다.** 순번을 줄 곳이 없기 때문이다. 대체 경로를 두지 않는 이유는 3장에 있다.

**구멍은 거의 안 생긴다.** 큐에 있던 것은 다 써지므로, 남는 것은 **그중 DB 쓰기까지 실패한 것**뿐이다. 그마저 실패 표상 반납 대상은 `uk_mc_coupon_member` 위반 하나이고 그건 매핑이 없어야 오는 경로라, 실질적으로 0 에 가깝다.

앱은 살아 있어 `catch` 는 정상적으로 돈다. **넣을 곳이 없을 뿐이다.** `free` 가 Redis 에 있어 `ZADD` 가 실패하므로, 그 몇 건은 복구 시 재건이 `free` 를 다시 만들면서 함께 채워진다.

**복귀 시 네 키를 함께 재건한다.** **Redis 호출의 서킷 브레이커**가 닫히는 것을 앱 인스턴스가 **상태 전이 이벤트로** 감지해 돌린다. 폴링이 아니고, 배치가 아니라 앱이다. 여러 대가 동시에 감지해 겹쳐 돌지만 넷 다 절대값으로 세팅해 결과가 같으므로 락을 두지 않는다. 하나만 세우면 나머지가 어긋난다.

```
카운터   소비된 최대 순번 + 1.  발급 수로 세우면 이미 쓴 번호를 다시 내준다
free     구멍 목록.  구하는 식은 3장을 따른다
매핑     주인이 있는 행을 훑어 회원과 순번을 넣는다.  확정 표시를 붙여서 넣는다
pending  비운다.  재건된 매핑은 전부 확정분이라 미확정이 없다
```

**매핑 재건을 빠뜨리기 쉽다.** 매핑이 사라진 동안 발급받은 사람들은 그 기록이 없다. 재건하지 않으면 1인 1매 판정이 그들을 놓쳐 재요청이 계속 DB 까지 간다.

**감지는 구조적으로 늦다.** 회로가 half-open 으로 넘어가면 시험 요청이 이미 `INCR` 을 하는데, 카운터가 재건 전이면 1 을 받는다. 1번은 이미 남이 쓴 번호라 `uk_mc_coupon_seq` 에 걸린다. **트리거를 앞당겨서는 못 막는다.** 회로를 여닫는 주체가 앱이 아니기 때문이다.

**그래서 스크립트가 스스로 막는다.**

```lua
if redis.call('EXISTS', KEYS[3]) == 0 then return '-2' end   -- 카운터가 없다
```

`-2` 를 받은 요청은 혼잡으로 처리하고 재건을 트리거한다. **재건이 언제 돌든 틀린 번호가 나가지 않는다.** 트리거는 빠르면 좋은 것이고, 정확성은 이 조건이 지킨다.

**이벤트 준비 때 카운터를 0 으로 만들어 둔다.** 그래야 "없다" 가 "사라졌다" 를 뜻한다. 초기화하지 않으면 이벤트 시작 시점과 구분되지 않아 이 조건이 매번 걸린다.

### RDB 가 죽었을 때

**일반 대응은 인프라가 갖는다.** `fm-infra` 의 `백엔드공통_앱과DB_장애대응구조.md` 4절이 Multi-AZ 페일오버 60~120초, JVM DNS 캐시 5초, `connectTimeout` 3초와 `socketTimeout` 10초, 503 과 `Retry-After` 응답까지 정해 두었다. 여기서는 **선착순에만 생기는 것**만 적는다.

**커밋된 발급은 사라지지 않는다.** 동기 복제라 RPO 가 0 이다. 페일오버로 R1 이 깨질 일은 없다.

**문제는 카운터가 혼자 앞서 나가는 것이다.** DB 가 죽어도 Redis 는 멀쩡해서 `INCR` 이 계속 성공한다.

```
t0      RDS 프라이머리 장애
t0~120  Redis 는 계속 번호를 내주고 쓰기는 전부 실패한다
t120    정상화. 그동안 나간 번호가 모두 구멍이다
```

**그 번호들을 반납하지 않는다.** 앱도 Redis 도 살아 있어 반납 경로가 끊기지는 않지만, 그렇게 하지 않기로 했다. 위 "장애로 못 쓴 번호는 그 사용자 것으로 남긴다" 가 그 이유다.

**그래서 t120 의 "구멍" 은 주인이 있는 자리다.** 그들이 재시도하면 매핑이 같은 번호를 돌려주고 그대로 성공한다. 안 돌아오는 사람의 번호만 `pending` 이 소진 시점에 회수한다. `issue_limit` 을 올릴 필요는 어느 쪽이든 없다.

**그래도 번호를 태우지 않는 편이 낫다.** 앱의 서킷 브레이커가 연속 실패를 세다 임계를 넘으면 회로를 열고, 그때부터 요청 스레드가 `INCR` 자체를 건너뛰고 바로 거절한다. **묶일 번호가 애초에 생기지 않아** `pending` 이 나중에 풀어야 할 양도 안 쌓이고, 커넥션도 붙잡히지 않는다.

이 회로는 순번 확보에 건 것과 다른 회로다. 저쪽은 Redis 실패를 세고 이쪽은 **DB 쓰기 실패를 세되 막는 대상은 똑같이 순번 확보**다. 둘 다 플러시는 안 막는다. 플러시를 막으면 이미 큐에 들어간 요청까지 버리게 된다.

**장애로 못 쓴 번호는 그 사용자 것으로 남긴다.** 한때 이 자리에서 "DB 에 닿았나" 로 갈라 안 닿은 것은 반납하기로 적었으나, 그것이 **선착순을 서버가 스스로 깨는 처리**라 뒤집었다.

```
A 가 6번을 받는다              우리 DB 가 죽는다.  A 잘못이 아니다
6번을 free 로 반납한다
B 가 9001번째로 도착해 재시도   free 에서 6번을 받는다
A 가 재시도                    매핑이 지워져 새 번호를 받아 맨 뒤로 간다
```

**나중에 온 B 가 먼저 온 A 를 앞지른다.** 순번은 도착 순서의 기록이고, 그것을 잃을 이유가 사용자 쪽에 하나도 없다.

**반납하는 것은 그 번호가 내 것이 아닐 때뿐이다.** 그렇게 보면 3장의 실패 표와 이 구간이 한 규칙으로 읽힌다.

| 실패 | 그 번호는 | 처리 |
|---|---|---|
| `uk_mc_coupon_member` 위반, 순번이 다르다 | 아무도 안 썼다 | 반납한다 |
| `uk_mc_coupon_member` 위반, 순번이 같다 | 내가 이미 썼다 | 반납 금지 |
| `uk_mc_coupon_seq` 위반 | 남이 쓰고 있다 | 반납 금지. 매핑만 지운다 |
| 연결 실패, 타임아웃 | **내 것이고 아직 유효하다** | 반납 금지. 매핑을 유지한다 |

**카운터가 말라 소진으로 답하는 것은 잘못이 아니다.** 장애 중에 번호가 한도까지 다 나가면 그 뒤 요청은 소진을 받는데, 그 번호들을 쥔 사람이 정확히 먼저 온 사람들이다. **행이 아직 없을 뿐 자리는 임자가 있다.** DB 가 살아나면 그들이 재시도할 때 매핑이 같은 번호를 돌려주고 그대로 성공한다.

**안 돌아오는 사람은 `pending` 이 처리한다.** 반납은 "이 사람은 포기했다" 를 근거 없이 즉시 단정하는 것이고, `pending` 은 기준 시간을 넘겼는지 보고 판정한다. **기다려 보고 정하는 쪽이 더 정확하다.**

**`connection-timeout` 3초는 이 구간에 길다.** 근거가 둘이다. 하나는 처리량으로, 인프라 문서가 스레드 고갈을 막으려고 정한 값인데 톰캣 스레드 200 개가 3초씩 잡히면 초당 66 건밖에 흘리지 못한다. 동접 2만이 몰리는 선착순에서는 그 앞이 막힌다.

다른 하나는 **계층 역전**이다. 요청 스레드가 응답을 기다리는 예산이 바깥이고 `connection-timeout` 은 그 안쪽인데, 안쪽이 더 길면 요청이 먼저 포기한 뒤에 그 배치가 커밋된다. **실패했다고 답했는데 발급된 상태**가 된다(7장의 요청 예산 절). 전용 프로파일에서 짧게 잡고 회로 차단기와 함께 쓴다.

### 배치가 죽었을 때

**배치는 발급 경로 위에 없다.** 순번 회수는 `pending` 이, 반납은 앱의 `catch` 가 맡으므로 배치가 멈춰도 발급과 재고에는 영향이 없다.

배치가 맡는 것은 **이벤트 종료 처리**뿐이다.

```
마감 시각이 지난 쿠폰의 is_active 를 끈다
issued_quantity 를 실제 발급 수로 맞춘다
네 키를 UNLINK 한다
```

**셋 다 급하지 않다.** 발급 차단은 1단계의 기간 체크가 정각에 하고, `issued_quantity` 는 판정에 안 쓰이는 기록이며, 키는 TTL 이 그물로 받는다.

**복구는 인스턴스 교체를 기다린다.** ASG 가 새로 띄우기까지 몇 분이고, 그 사이 밀린 몫은 복구 뒤 한 번에 처리된다. 배치가 상태를 들고 있지 않아 따로 챙길 것이 없다.

`application-batch.yml` 의 "스케줄러는 batch 프로필에서만 돈다(`INF-1-10`)" 를 그대로 따른다. `KakaoUnlinkRetryScheduler` 를 비롯한 기존 스케줄러들과 같은 구조다.

**앱이 이어받게 만들지 않는다.** 분산 락을 넣으면 전용 인스턴스를 두는 의미가 사라져 구조가 둘로 갈리고, 무엇보다 **페일오버 경로가 평소에 한 번도 돌지 않는다.** 배치가 살아 있는 동안 앱 쪽 코드는 락 획득에 실패하고 돌아설 뿐이라, 정작 필요한 날 처음 실행된다. 회수가 몇 분 늦는 값으로 살 것이 아니다.

**지연이 실제 문제로 확인되면 그때 옮긴다.** 전용 인스턴스 구분을 없애고 모든 인스턴스에서 하나만 돌리는 쪽이며, ShedLock 같은 라이브러리를 쓴다. 락을 직접 짜지 않는다. Redis 락은 GC 정지나 지연으로 두 곳이 함께 도는 것을 원리적으로 막지 못해, **어느 쪽으로 가든 정확성은 락이 아니라 멱등이 책임진다.**

**그래서 작업 자체를 멱등하게 둔다.** 재시작이나 수동 실행으로 겹쳐 돌 수 있다. `free` 는 `ZADD` 라 같은 번호가 두 번 들어가지 않고, `issued_quantity` 는 증분이 아니라 절대값으로 세팅한다. 증분으로 올리면 겹쳐 돌 때 값이 부풀어 오른다.

## 10. 정합성을 어떻게 검증하나

8장의 성능 측정과 별개다. **이력과 재고가 어긋나지 않았음을 스스로 확인할 수단**이 요구사항이다([requirement.md](requirement.md)).

| 검증할 것 | 어긋남의 모양 |
|---|---|
| 발급 수와 `issued_quantity` | 카운터가 실제 행 수와 다르다 |
| 발급 수와 `total_quantity` | 초과, 또는 과소 |
| 순번의 연속성 | 구멍 수가 곧 어긋남이다. 세는 식은 3장을 따른다 |
| 1인 1매 | 회원과 쿠폰의 UNIQUE 가 막지만 결과로도 확인한다 |
| 상태와 이력 (R5) | `member_coupon.status` 와 `member_coupon_status_history` 의 마지막 전이가 같은가. 어긋나면 2장의 규율이 깨진 것이다 |

**300만 건 전체를 대상으로 하고, 같은 데이터로 재실행하면 같은 결과가 나와야 한다.** 그래서 검증은 상태를 들고 있으면 안 된다. 매번 처음부터 전부 훑어 계산하고, 중간 결과를 저장해 다음 실행에서 재사용하지 않는다.

**9장의 회수 배치와 목적이 다르다.** 회수는 고치는 것이고 검증은 재는 것이다. 검증이 고치면 재실행 결과가 달라져 요구를 위반한다. 둘을 한 배치에 섞지 않는다.
