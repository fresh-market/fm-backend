# 선착순 쿠폰 발급 시스템

**한정 수량 쿠폰을 여러 사람이 동시에 요청할 때 정확히 정해진 수만큼만 발급되게 만드는
문제를 다룬다.**

이 문서는 **버전이 바뀌어도 변하지 않는 것**만 담는다. 값의 근거와 절차는 아래 문서들이
따로 갖는다.

```
requirement.md                주어진 요구사항
coupon-redis-keys.md          Redis 키 넷을 키 단위로
coupon-redis-scripts.md       Lua 스크립트가 무엇을 묶나
coupon-reclaim-after.md       회수 기준 시간을 어떻게 정했나
redis-promotion-rebuild.md    Redis 가 키를 잃었을 때 다시 세우는 절차
coupon-load-scenarios.md      부하 시험 계획
coupon-load-rounds.md         부하 시험 결과
coupon-v4.md                  채택안(v4)이 정하고 만든 것
```

**버전마다 브랜치와 문서를 따로 둔다.** 버전끼리 서로를 이어받지 않고 **같은 문제를 다시
짠다.** 그래서 이 문서를 우산 브랜치(`feat/coupon-issue`)에 두고 버전들이 함께 본다.

---

## 1. 지켜야 할 것 다섯

| | 요구 | 어긋나면 |
|---|---|---|
| R1 | 발급 수가 `total_quantity` 를 안 넘는다 | 준비한 것보다 많이 나간다 |
| R2 | 한 회원이 같은 쿠폰을 두 장 안 받는다 | 형평성이 깨진다 |
| R3 | 순번이 안 겹친다 | 같은 번호로 두 행이 생겨 상한이 무너진다 |
| R4 | 재시도가 두 장을 안 만든다 | 오류 한 번에 R1 과 R2 가 깨진다 |
| R5 | 같은 상태 변경이 겹쳐도 한 번만 반영된다 | 이력과 재고가 어긋난다 |

나머지는 사후에 정정할 수 있지만 이미 나간 쿠폰은 회수하기 어렵다. **그래서 R1 이 가장
비싸다.**

---

## 2. DB 가 막는 R1 에서 R4 까지

**스키마가 앱과 무관하게 넷을 막는다. 이것이 이 시스템의 바닥이다.**

```
uk_mc_coupon_member (coupon_id, member_id)   R2, R4
uk_mc_coupon_seq    (coupon_id, issue_seq)   R3
chk_mc_issue_seq    1 <= issue_seq <= issue_limit   R1
```

`issue_limit` 은 행을 만들 때 `coupon.total_quantity` 를 복사한 값이다. **이 값이 다른 행을
참조하지 않으므로 삽입 한 건이 자기 행만 보고 상한을 판정한다.**

### 왜 순번으로 세는가

**MySQL 이 CHECK 에 집계를 금지해서 스키마가 `행 수 <= total_quantity` 를 직접 못 건다.**

```
coupon 에 카운터를 두고 UPDATE     한 행에 락이 몰려 직렬화된다
각 행에 1..issue_limit 을 배정     공유하는 행이 없다.  INSERT 가 경합하지 않는다
```

**순번은 집계 제약을 개별 행 제약으로 바꾸는 변환이다.** 락 없이 DB 가 상한을 지키는 유일한
방법이라 이 설계가 순번을 골랐다.

### 순번 발급기가 어디 있든 안전한 이유

카운터가 앱 메모리든 DB 행이든 Redis 든, **그 값이 틀리면 두 제약 중 하나가 기록을 막는다.**

```
카운터가 작다   이미 쓴 번호를 다시 준다   uk_mc_coupon_seq 가 막는다
카운터가 크다   번호가 한도를 넘는다      chk_mc_issue_seq 가 막는다
```

**그래서 버전 사이의 차이는 "안전한가" 가 아니라 "얼마나 빠르고 얼마나 자주 실패하는가" 다.**
안전을 스키마가 책임지므로 개발자가 위쪽 구현을 자유롭게 바꿔 볼 수 있다.

### 앱이 지키는 R5

**스키마는 같은 전이를 두 번 요청하는 것을 정상적인 UPDATE 두 번으로 본다.** 그래서 앱이
규율로 지킨다.

**앱은 읽고 판단한 뒤 쓰는 대신 지금 상태를 `WHERE` 에 넣어 한 문장으로 만든다.**

```sql
UPDATE member_coupon SET status = 'USED', ...
 WHERE member_coupon_id = ? AND member_id = ? AND status = 'ISSUED';
-- 1행이면 이번 요청이 바꾼 것이다
```

**반복 요청은 두 번째부터 0행이고, 동시 요청은 행 락으로 줄을 서 뒤엣것이 0행이다.**
어느 쪽이든 한 번만 반영된다.

이미 `USED` 면 성공으로 답하는 것이 멱등이고 쓸 수 없는 상태나 남의 쿠폰이면 실패다.
**그래서 0행의 원인은 앱이 갈라야 한다.**

## 3. 발급 한 건의 뼈대

**버전마다 구현이 달라도 단계는 같다.**

```
1. 자격 확인   기간, is_active, 대상 등급, 이미 받았는가
2. 순번 확보   한정 수량 안에서 겹치지 않는 번호를 하나 가져온다
3. 발급 기록   member_coupon 에 insert 한다.  여기서 1인 1매가 판정된다
4. 응답
```

동시성 문제도 병목도 2번에 있다. **2번이 이 시스템의 전부다.**

### 이벤트가 시작되면 고정되는 조건

**규칙 둘이 관리자가 바꿀 수 있는 시점을 좁힌다.**

```
발급 시각    issue_start_at 이 지났으면 관리자가 시각을 못 바꾼다
발급 스위치   소진 전이고 마감 전이면 관리자가 못 끈다
```

**관리자가 약속한 이벤트를 도중에 흔들지 못하게 하려고 이 둘을 둔다.** 부수 효과로 앱이 자격
확인을 캐시할 수 있는데 발급 창 안에서 다섯 값이 전부 고정되기 때문이다.

회수가 도는 조건이 "소진 상태에서 요청이 왔을 때" 라서 관리자가 스위치를 끄면 요청이 안
들어오고 **묶인 번호가 그대로 죽는다.** 그래서 **소진으로는 이벤트를 안 끝낸다.**

### 응답 다섯 가지

| 응답 | 상태 |
|---|---|
| 발급 | 200 |
| **이미 발급** | **200**, `alreadyIssued: true` |
| 소진, 회수 여지 있음 | 409 |
| **소진, 최종** | **410** |
| 혼잡 | 503 + `Retry-After` |

서버는 사용자가 다시 누른 것과 클라이언트가 자동 재시도한 것을 구분하지 못한다. 실패로
답하면 그 사용자가 못 받은 줄 알고 계속 누르고 **그것이 다시 부하가 된다.** 그래서
**앱이 "이미 발급" 을 발급과 같은 모양으로 낸다.**

**앱이 소진을 둘로 갈라 재시도 폭풍을 막는다.** 동접이 재고의 두 배면 소진 응답을
받는 사람이 재고만큼이고 그들이 전부 재시도하면 가장 힘든 순간에 부하가 두 배가 된다.
**410 은 "그만 두드려라" 를 프로토콜로 말한다.**

```
pending 이 비었다      다시 나올 번호가 없다   410
pending 이 남아 있다   회수로 다시 나온다     409
```

### 두 층에서 막는 소진

```
1층  Redis 카운터가 한도를 넘으면 앱이 거절한다   빠르다.  정상 응답을 준다
2층  스키마가 막는다                            느리다.  예외로 끊는다
```

Redis 가 사라지든 페일오버로 카운터가 밀리든 초과 발급은 안 난다. **2층은 어떤 경우에도 안
뚫린다.**

### Redis 가 죽으면 앱이 새 요청을 안 받는 이유

**이 설계는 대체 순번 발급기를 두지 않는다.** 회로가 열리면 앱이 혼잡(503)으로 끊는다.

```
이미 번호를 받아 큐에 있는 요청   그대로 발급된다
번호를 못 받은 요청               혼잡(503) 응답.  큐에 안 넣는다
```

**대체 경로를 안 두는 이유가 셋이다.** 전역 순서기가 사라져 앱이 순서를 못 정하고 직렬화로
지키면 p99 가 초 단위로 오르며 **무엇보다 그 코드가 평소에 한 번도 안 돌아 정작 필요한 날
처음 실행된다.**

`requirement.md` 는 가용성을 요구하지 않는다. 요구는 초과 발급 0건과 1인 1매에서 그치고
**그 둘은 Redis 가 죽어도 스키마가 지킨다.**

### 기록이 실패하면 앱이 하는 순번 반납

**카운터를 Redis 로 옮기면 순번 확보와 발급 기록이 서로 다른 원자 단위가 된다.** 그 사이에서
앱이 실패하면 번호는 소모됐는데 행이 없다.

**앱이 카운터를 내리는 것으로는 못 고친다.** `DECR` 은 맨 위 번호를 회수하는데 그것이 내
번호인 경우가 선착순에서는 거의 없다. **그래서 앱이 그 번호를 지목해 `free` 에 넣는다.**

앱이 전부 반납하면 남이 쓰는 번호를 다시 내주게 된다. **그래서 앱이 실패 종류를 갈라야 한다.**

| 실패 | 그 번호는 | 앱의 처리 |
|---|---|---|
| `uk_mc_coupon_member`, 순번이 다르다 | 안 쓰였다 | 반납하고 매핑을 고친다 |
| `uk_mc_coupon_member`, 순번이 같다 | 내가 이미 썼다 | 반납 금지. 확정 표시만 남긴다 |
| `uk_mc_coupon_seq` | 남이 쓰고 있다 | 반납 금지. 매핑을 지우고 주인을 고친다 |
| 타임아웃, 커넥션 실패 | 커밋 여부를 모른다 | 반납 금지. 매핑을 유지한다 |

**앱이 어느 제약인지를 예외 메시지로 가르지 않는다.** 메시지 형식이 드라이버 판마다 달라서
앱은 `SELECT issue_seq ... WHERE coupon_id = ? AND member_id = ?` 한 번으로 세 경로를 다
가른다.

**이 읽기마저 실패하면 앱이 아무것도 안 건드린다.** 앱이 잘못 고르면 그중 반납은 되돌릴 수
없다.

### Redis 에 둔 키 넷

| 키 | 담는 것 |
|---|---|
| `seq` | 회원 -> 순번이고 `"6"` 은 번호만 받음, `"6:1"` 은 커밋 완료 |
| `free` | 반납된 순번 |
| `counter` | 마지막으로 나간 번호 |
| `pending` | 아직 커밋 안 된 회원이고 점수가 번호를 준 시각이다 |

**넷은 함께 살고 함께 죽는다.** 하나만 사라지면 나머지가 거짓말을 한다. 수명은 `counter` 가
들고 나머지가 물려받는다.

**키마다 언제 무엇이 담기는지는 [coupon-redis-keys.md](coupon-redis-keys.md) 에 있다.**
**스크립트가 무엇을 묶는지는 [coupon-redis-scripts.md](coupon-redis-scripts.md) 에 있다.**

### 묶인 번호를 푸는 회수

**어떤 요청은 번호를 받고 커밋 전에 사라진다. 그러면 그 번호가 아무에게도 안 간다.** 원인은
여럿인데 결과가 같아서 **앱이 원인을 구분할 수 없다.** 그래서 앱이 시간으로 판정한다.

```
트리거   소진 상태다          재고가 있으면 이 경로에 안 온다
조건     기준 시간이 지났다    pending 의 점수로 고른다
```

**트리거 덕분에 평상시 비용이 0 이고 주기 배치도 필요 없다.**

**기준 시간(`reclaim-after`)을 어떻게 정했는지는
[coupon-reclaim-after.md](coupon-reclaim-after.md) 에 있다.** 기준 시간을 짧게 잡으면 회수가
살아 있는 번호를 뺏어 오히려 더 많이 태운다는 것을 실측으로 확인했다.

### 확정 표시가 실패하면 오판하는 회수

**회수는 "매핑에 확정 표시가 없다" 하나만 증거로 본다. 그런데 그 부재를 둘이 만든다.**

```
정말 버려진 티켓      DB 에 행이 없다   회수가 맞다
확정 표시만 실패한 것  DB 에 행이 있다   회수가 틀렸다
```

**스크립트는 DB 를 못 보므로 둘을 구분할 수 없다.** 스크립트는 오판할 수밖에 없는 정보만
갖고 있다.

**감지 지점이 이미 있다.** 회수가 잘못 짚으면 앱이 그 번호로 INSERT 할 때
`uk_mc_coupon_seq` 에 걸리고 **그 위반이 곧 증거다.** 플러시 스레드가 그 자리에서 진짜
주인을 찾아 매핑을 되살린다.

**피해가 한 명에서 끊긴다.** 그 한 명은 원래 소진 응답을 받았을 사람이라 잃는 것이 응답
한 번이다.

### 이벤트가 끝나면 도는 정리 배치

```
1  마감에서 60초를 기다린다   진행 중인 배치가 결판나는 시간이다
2  is_active 를 끈다
3  issued_quantity 를 실제 발급 수로 맞춘다
4  네 키를 UNLINK 한다
```

배치가 대기를 종료 조건에 넣는다. 끄는 시점에 발급 행 수가 이미 안 움직이므로 배치가 2에서
4까지를 한 트랜잭션으로 묶을 수 있다. **이 대기가 절차의 요점이다.**

카운터가 없는 상태에서 요청이 닿으면 `INCR` 이 1 을 주고 그 번호는 이미 남이 썼다.
**그래서 배치가 4번을 앞당기면 안 된다.**

**TTL 은 그물로만 건다.** TTL 은 위 절차가 안 돌았을 때를 위한 것이고 주 경로가 아니다.

## 4. 배치 구조

**선착순 트래픽은 짧은 시간에 한 경로로 몰리므로 이 설계가 그 경로를 나머지와 분리한다.**

```
ALB 가 경로로 가른다
  선착순 발급  ->  전용 ASG (t3.small)
  나머지      ->  평상시 ASG
둘이 같은 ElastiCache 와 RDS 를 본다
```

**분리하지 않으면 선착순 트래픽이 톰캣 스레드와 커넥션 풀을 다 먹고 상품 조회와 주문이 같이
죽는다.** 이 구조가 격벽을 세워 장애를 한쪽에 가둔다.

이벤트 구간에는 캐시가 순번의 판정 주체라 단일 노드가 죽으면 이벤트가 멈춘다. 평상시의 단일
노드 전제가 이 구간에는 성립하지 않는다. **그래서 이 설계는 캐시를 2대로 둔다.**

## 5. 확장의 상한인 커넥션 예산

**앱은 N 대로 늘릴 수 있지만 DB 는 한 대다.**

```
db.t4g.micro 의 max_connections 약 60
평상시 소비  앱 + 배치 + 모니터링 + 운영자 = 약 30, 배포 중 약 38
```

**전용 ASG 가 그 위에 얹힌다.** 이 ASG 가 평상시 앱과 같은 풀 크기를 쓰면 배포 중에 예산을
넘긴다.

**전용 풀을 작게 잡고 3대까지 세운다.** 이 크기는 예산에서 역산한 값이 아니다. **이 인스턴스가
실제로 쓰는 수를 세어 나온 값이다.** 커넥션을 쥘 수 있는 것이 플러시 스레드와 캐시 적재
둘뿐이고 **요청이 몇 만이든 이 수는 안 는다. 요청 스레드가 트랜잭션을 안 열기 때문이다.**

**발급이 도는 동안 앱이 실제로 쓰는 커넥션은 1개다.** 캐시는 이벤트가 열릴 때 한 번 채우고
마감까지 DB 를 다시 안 치므로, 그 뒤로 플러시 스레드 하나가 커넥션을 쥔다. **그 한 번에
플러시가 안 기다리도록 풀을 2로 뒀다.**

풀이 크면 대기가 DB 안으로 들어가 전부 조금씩 느려지고 **앱은 그 대기를 혼잡(503)으로 못
끊고 느림으로 겪는다.** 이 설계는 전부를 느리게 하는 대신 일부를 빠르게 거절하기로 한 것이라,
대기가 앱의 풀 앞에 서 있어야 한다. **풀을 크게 잡으면 오히려 설계가 흔들린다.**

**"앱을 N 대로 늘리면 처리량이 N 배" 가 아니다.** DB 가 단일 지점이라 처리량이 그 앞에서
막힌다. **이 한계를 어디서 만나는지가 부하 시험의 핵심 관찰 대상이다.**

값과 그 근거는 `application-coupon.yml` 이 갖는다.

## 6. 버전

**요청과 응답은 끝까지 동기다.** 이 동기가 버전을 가로지르는 고정 제약이어서 사용자가 응답을
받은 시점에 `member_coupon` 행이 이미 커밋되어 있다.

**이 제약을 풀면(접수만 응답하고 나중에 쓰기) 훨씬 빨라지지만 다른 기능이 된다.** 선착순은
받았는지를 그 자리에서 알아야 하는 기능이라 이 설계가 제약을 유지한다.

| | 무엇을 바꾸나 | 무엇을 얻나 |
|---|---|---|
| **v1** | DB 조건부 UPDATE | 기준선. 추가 인프라 0 |
| **v2** | 카운터를 Redis 로 | **거절이 DB 를 안 거친다** |
| **v3** | 인스턴스별 큐 + 벌크 INSERT | DB 왕복이 준다 |
| **[v4](coupon-v4.md)** | 가상 스레드 | 대기 중 캐리어 스레드를 반납한다 |
| **v5** | 벌크 INSERT 를 배치 서버로 | **커넥션이 인스턴스 수와 무관해진다** |
| v6, v7 | 행을 미리 넣고 update 로 잡는다 | **접었다** |

```
v1 -> v2 -> v3 -> v4        처리량이 오르는 순서.  v4 가 채택안이다
                   ├─ v5    커넥션 예산이 막힐 때 꺼낸다
                   └─ v6    검토하고 접었다 (아래)
```

**번호가 클수록 빠른 것이 아니다.** v5 는 처리량 대신 커넥션 예산을 얻는다. 요청과
응답이 분산되어 p99 는 오히려 나빠질 것으로 팀은 예상한다.

선착순은 거절이 많은데, v1 은 거절되는 쪽도 커넥션을 잡고 락을 기다린다. **판정 자체가 락
뒤에 있기 때문이다.** v2 는 `INCR` 결과만 보고 DB 를 안 건드리고 끊는다. **그래서 v2 가
이득의 대부분을 가져간다.**

### 접은 v6 과 v7

**둘 다 이벤트 전에 행을 미리 넣어 두는 안이었다. 그 안에서 발급은 insert 를 하는 대신 그
순번의 행을 잡는다.** 어디에 미리 넣느냐가 갈렸다.

```
v6   member_coupon 에 PENDING 행을 미리 넣는다
v7   쿠폰 전용 테이블을 만들어 거기 미리 넣는다
```

**v7 에서 미리 넣은 그 테이블은 목적지가 못 된다. 이 점이 결정적이다.** 쿠폰함 조회와 만료
배치가 `member_coupon` 을 보고 무엇보다 `orders` 가 `member_coupon` 을 외래 키로 참조한다.
**앱이 그 행을 `member_coupon` 으로 옮기기 전까지 사용자가 받은 쿠폰을 주문에 못 쓴다.**

**앱이 옮기는 단계를 두면 발급 한 건에 쓰기가 두 번이 되고 옮기는 시점을 늦추면 발급 직후
주문이 막힌다.** 이 문제는 조회를 그 테이블로 돌려서 피할 수 있는 성격이 아니다.

**v6 은 그 문제가 없는 대신 스키마를 다섯 군데 늘려야 했다.** `member_id` 를 NULL 허용으로
바꾸고 `PENDING` 상태와 조건부 CHECK 와 인덱스를 더한다. **원래 근거였던 둘이 사라지거나
줄어들어** 그 대가를 낼 값이 없어졌다. 이 설계가 폴백을 안 두기로 해 하나가 무의미해졌고
다른 하나는 `pending` 키가 정상 경로를 맡으면서 재건 때만 쓰이게 됐다.

**v4 는 발급 방식을 위해 스키마를 늘리지 않는다.**

### 요청 예산

**요청 예산은 요청 스레드가 응답까지 기다리는 총 시간이다.** v3 부터 요청 스레드는 큐에 넣고
자므로 이 값이 없으면 요청 스레드가 무한정 기다린다. 요청이 예산을 넘으면 앱이
혼잡(503)으로 끊는다.

**계층이 역전되면 안 된다.** 안쪽이 바깥쪽보다 길면 **요청 스레드가 먼저 포기해 혼잡(503)으로
답한 뒤에 그 배치가 커밋된다.** 실패했다고 답했는데 발급된 상태가 되고, 사용자가 안
돌아오면 그 슬롯은 죽은 재고가 된다.

**한때 이 산식이 두 항목을 빠뜨려 실제 합이 예산을 넘고 있었다.** 이 산식은 배치 윈도와 확정
표시가 예산 안이라는 것을 안 셌다. **고친 자리는 확정 표시의 왕복 둘이고, 스크립트 하나에
담아 왕복이 하나가 됐다.**

**계층의 값과 그 근거는 `application-coupon.yml` 이 갖는다.**

## 7. 무엇을 측정하나

**버전을 나누는 목적이 비교이므로 부하 시험이 같은 조건에서 같은 지표를 잰다.**

| 지표 | 왜 |
|---|---|
| 초당 발급 처리량 | 버전 사이의 주된 차이가 여기서 난다 |
| 응답 시간 p99 | 평균은 대기가 몰리는 구간을 감춘다 |
| 실패율과 사유 | 충돌, 소진(409, 410), 혼잡(503), DB 타임아웃을 나눠 센다 |
| **최종 발급 수 대 `total_quantity`** | R1 검증. 초과는 물론 과소도 본다 |
| DB 커넥션 대기 | 병목이 DB 인지 가른다 |
| **큐 최대 길이** | 앱이 급사했을 때 잃는 건수의 상한이다 |
| **전용 인스턴스 수 대 처리량** | 5장의 상한을 어디서 만나는지 본다 |
| 평상시 경로의 지표 | 격벽이 실제로 작동했는지 본다 |

인스턴스를 늘려도 처리량이 안 늘기 시작하는 지점이 DB 한계이고 그때 평상시 경로가 같이
느려지면 격벽이 새는 것이다. **그래서 마지막 두 줄이 이 배치 구조를 택한 이유와 직결된다.**

### 합격 기준

**부하 시험 환경에서 요구 부하를 걸었을 때, 처리된 발급 응답의 p99 가 1초 이하다.**

```
부하   requirement.md 가 정한 값을 그대로 쓴다
대상   발급(200)과 소진(409, 410).  서버가 판정을 끝낸 응답이다
제외   혼잡(503).  요청 예산에서 잘린 값이라 넣으면 예산을 재는 셈이 된다
```

**혼잡을 넣으면 안 되는 이유가 구체적이다.** 그 503 은 정확히 요청 예산을 태우고 끊기므로
**예산을 줄이는 것만으로 p99 가 내려간다.**

**혼잡(503)을 뺐으므로 거절 비율을 따로 묶어야 한다.** 안 그러면 앱이 전부 거절해서 p99 를
맞출 수 있다.

**예산을 줄이는 것만으로는 목표를 달성하지 못한다.** 예산을 줄이는 것은 느린 응답을 거절로
바꾸는 일이라 지표가 지연에서 거절로 옮겨갈 뿐이다. **플러시가 도착률을 따라가느냐가 p99 를
실제로 정하고 그 지점은 부하 시험이 찾는다.**

**계획은 [coupon-load-scenarios.md](coupon-load-scenarios.md), 결과는
[coupon-load-rounds.md](coupon-load-rounds.md) 에 있다.**

## 8. 구성 요소가 죽었을 때

**평상시 순번 반납은 앱의 `catch` 가 맡는다.** 무엇이 죽느냐에 따라 그 경로가 끊기는 자리가
다르다.

| | 진행 중이던 발급 | 반납을 대신 맡는 쪽 |
|---|---|---|
| **앱 사망** | **응답도 못 간 채 큐째로 사라진다** | 재시도시 같은 번호로 발급 / 60초 뒤 회수 |
| Redis 사망 | 전부 완료된다 | 복구 시 재건이 `free` 를 채운다 |
| RDB 사망 | 전부 실패한다 | 재시도시 같은 번호로 발급 / 60초 뒤 회수 |

앱 사망은 회수가 소진 시점에 풀고 Redis 사망은 재건이 채운다. **각각 훅이 있어 반납 경로가
끊겨도 별도 배치가 필요 없다.**

### 앱이 죽었을 때

**프로세스가 통째로 죽으면 `catch` 가 돌 기회가 없다.** 큐에 남아 있던 발급분이 함께
사라지고 그 요청들은 응답을 못 받는다.

**사용자가 재시도하면 닫힌다.** 매핑이 같은 번호를 돌려주므로 그 요청이 그대로 성공한다.
재시도가 안 오는 것만 묶인 채 남고 **그것은 회수가 소진 시점에 푼다.**

**잃는 규모는 큐 깊이가 정하므로 7장이 큐 최대 길이를 함께 잰다.**

### Redis 가 죽었을 때

**진행 중이던 발급은 안 끊긴다.** 큐 항목이 번호와 회원과 응답 통로뿐이고 플러시 스레드는
DB 에만 쓰기 때문이다. **셋 중 Redis 사망이 진행 중인 발급에 가장 무해하다.**

순번을 줄 곳이 없어서 **앱이 새 요청을 혼잡(503)으로 끊는다.**

**감지는 구조적으로 늦다.** 회로가 반열림으로 넘어가면 시험 요청이 이미 `INCR` 을 하는데
카운터가 재건 전이면 그 요청이 1 을 받는다. **앱이 트리거를 앞당겨서는 못 막는다.** 회로를
여닫는 주체가 앱이 아니기 때문이다.

**그래서 스크립트가 스스로 막는다.** 카운터가 없으면 스크립트가 번호를 안 내주므로,
**재건이 언제 돌든 틀린 번호가 안 나간다.**

### RDB 가 죽었을 때

동기 복제라 페일오버로 R1 이 깨질 일이 없어 **커밋된 발급은 안 사라진다.**

**카운터가 혼자 앞서 나간다.** DB 가 죽어도 Redis 는 멀쩡해서 `INCR` 이 계속 성공하기
때문이다.

**앱이 그 번호들을 반납하지 않는다.** 장애로 못 쓴 번호는 앱이 그 사용자 것으로 남긴다.

```
A 가 6번을 받는다              우리 DB 가 죽는다.  A 잘못이 아니다
6번을 free 로 반납한다
B 가 나중에 도착해 그 번호를 받는다
A 가 재시도하면 새 번호를 받아 맨 뒤로 간다
```

**나중에 온 B 가 먼저 온 A 를 앞지른다.** 순번은 도착 순서의 기록이고 그 기록을 잃을 이유가
사용자 쪽에 하나도 없다. **앱은 그 번호가 내 것이 아닐 때만 반납한다.**

**그래도 앱이 번호를 덜 태우는 편이 낫다.** 회로가 열리면 요청 스레드가 `INCR` 자체를
건너뛰어 **묶일 번호가 애초에 안 생긴다.**

### 배치가 죽었을 때

**배치는 발급 경로 위에 없다.** 회수는 스크립트가, 반납은 앱이 맡으므로 배치가 멈춰도 발급과
재고에 영향이 없다. 배치가 맡는 것은 이벤트 종료 처리뿐이고 **셋 다 급하지 않다.**

**이 설계는 앱이 이어받게 만들지 않는다.** 분산 락을 넣으면 구조가 둘로 갈리고 **무엇보다 그
페일오버 경로가 평소에 한 번도 안 돈다.**

**그래서 작업 자체를 멱등하게 둔다.** 배치가 재시작이나 수동 실행으로 겹쳐 돌 수 있다.

## 9. Redis 가 키를 잃으면 하는 재건

**앱이 네 키를 DB 와 각 인스턴스의 큐로부터 다시 세운다.**

**DB 만으로는 안 된다.** 앱 큐에 아직 커밋 안 된 번호가 떠 있어 앱이 DB 만 보고 세우면 그
번호들을 아무도 안 쥔 것으로 보고 남에게 다시 내준다.

```
DB      커밋된 번호
앱 큐    커밋 안 된 번호
둘의 차이가 결번이다
```

**앱은 카운터를 세지 않고 최댓값으로 잡는다.** 이 키는 "몇 개 나갔나" 가 아니라 "가장 큰
번호가 얼마였나" 다. **세는 방식은 결번이 있으면 모자라고 회수가 돌았으면 넘친다.**

**넘치는 쪽이 더 위험하다.** `free` 경로는 상한 검사를 안 지나므로, 카운터가 상한을 넘으면
**그 카운터가 반드시 실패할 번호를 만들어 낸다.**

**절차와 실측은 [redis-promotion-rebuild.md](redis-promotion-rebuild.md) 에 있다.**
그쪽이 처음 보는 사람 기준으로 쓰여 있다.

### 무엇이 보장되나

**초과 발급과 1인 2매는 재건이 아니라 DB 가 막는다.** 재건은 과소 방향을 맡아 **재고를
온전히 다 팔려 하고 여기는 100% 가 아니다.**

### 이 장이 다루지 않는 것

**카운터가 살아남은 채로 나머지가 어긋난 경우다.** Redis 가 복제 지연이 남은 채 승격됐거나
축출이 카운터 아닌 것을 골랐을 때다.

**앱이 못 고치는 것이 아니라 재건이 안 불린다. 이 둘을 갈라야 한다.**

```
복구 능력   있다.  절차가 DB 와 큐만 보고 다시 계산한다
감지 능력   없다.  카운터가 있으면 스크립트가 정상으로 답한다
```

**깨지지 않아야 할 부등식이 하나 있다.**

```
counter >= MAX(issue_seq)
```

**번호는 Redis 가 내준 뒤에야 행이 되므로 이 식은 깨질 수 없다.** 깨졌다면 Redis 가 뒤처진
것이고 차이가 곧 뒤처진 양이다. **지금 그 차이를 재는 곳이 없다.**

## 10. 정합성을 어떻게 검증하나

**정합성 검증은 7장의 성능 측정과 별개다.** 이력과 재고가 어긋나지 않았음을 스스로 확인할
수단이 요구사항이다.

| 검증할 것 | 어긋남의 모양 |
|---|---|
| 발급 수와 `issued_quantity` | 카운터가 실제 행 수와 다르다 |
| 발급 수와 `total_quantity` | 초과, 또는 과소 |
| 순번의 연속성 | 결번 수가 곧 어긋남이다 |
| 1인 1매 | UNIQUE 가 막지만 결과로도 확인한다 |
| 상태와 이력 (R5) | 마지막 전이가 상태와 같은가 |

같은 데이터로 재실행하면 같은 결과가 나와야 하므로 검증이 매번 처음부터 전부 훑어 계산한다.
**검증이 상태를 들고 있으면 안 된다.**

**검증은 회수와 목적이 다르다.** 회수는 고치는 것이고 검증은 재는 것이다. **검증이 고치면 재실행
결과가 달라져 요구를 위반한다.**
