# v4: Redis 순번 + 인스턴스별 큐 + 가상 스레드

`feat/coupon-issue-v4` 브랜치의 작업 기록이다. 버전과 무관하게 고정된 것은 [coupon.md](coupon.md) 에 있고, 여기에는 **v4 에서만 정하고 만드는 것**을 적는다.

**v4 가 채택안이다.** v1~v3 을 거치지 않고 바로 만든다. 사다리는 비교를 위한 것이고, 실제로 쓸 것은 이 형태다.

---

## 1. 무엇을 만드나

```
1  자격 확인      기간, is_active, 대상 등급
2  순번 확보      Redis Lua 한 번
3  발급 기록      인스턴스별 큐 -> 플러시 스레드 -> Bulk INSERT
4  응답           요청 스레드가 future 로 받는다
```

**DDL 을 늘리지 않는다.** 현재 `member_coupon` 이 R1~R4 를 이미 지킨다. `V30` 이 안 쓰는 스냅샷 컬럼을 걷는 것뿐이다.

### 컨트롤러는 비동기로 만들지 않는다

`CompletableFuture` 를 컨트롤러가 반환하는 안과 비교했다. **끊김 감지가 필요 없어져 그쪽 이점이 사라졌다.**

[coupon.md](coupon.md) 3장이 이미 정한 것이다.

> 클라가 연결을 끊었다 / 타임아웃 / 앱이 급사했다
> **원인은 다르지만 결과가 같다. 원인을 구분할 수 없으므로 시간으로 판정한다.**

`pending` 이 시간으로 처리하므로 **누가 왜 사라졌는지 알아낼 이유가 없다.** 그러면 남는 것은 스레드 점유뿐인데, 그건 가상 스레드가 푼다.

```java
Result r = queue.push(seq, memberId).get(요청예산, MILLISECONDS);
```

`CompletableFuture` 는 **큐와 플러시 스레드 사이의 전달 수단으로만** 쓴다. `get()` 이 `LockSupport.park` 라 가상 스레드에서 pinning 이 생기지 않는다.

```
spring.threads.virtual.enabled: true
```

### 가상 스레드가 자연 상한을 없앤다

**두 가지가 딸려 온다.** 둘 다 v4 표가 대가로 적어둔 것의 구체다.

**큐 상한이 사라진다.** [coupon.md](coupon.md) 7장은 큐 길이가 톰캣 스레드 수에 묶인다고 본다.

> 요청 스레드가 큐에 든 만큼 잠겨 있으므로, **큐 길이가 톰캣 스레드 수를 넘을 수 없다.**

플랫폼 스레드에서는 200 이 자연 상한이었다. **가상 스레드는 그 상한이 없어 큐가 메모리까지 자란다.** 앱이 급사했을 때 잃는 건수의 상한도 함께 사라지므로 **명시적으로 걸어야 한다.**

**꼬리 지연이 늘 수 있다.** 스레드를 값싸게 만들 수 있다는 것이 곧 무한정 받아도 된다는 뜻은 아니다.

```
받는 것은 싸다        스레드 생성 비용이 거의 없어 요청을 다 받아들인다
처리는 안 싸다        플러시 처리 능력과 DB 커밋은 그대로다
-> 대기가 큐와 커넥션 풀로 밀린다
-> 앞쪽은 평소대로 나가고 뒤쪽만 계속 밀려 p99 와 p100 이 벌어진다
```

**플랫폼 스레드였다면 200 을 넘는 순간 거절되어 실패로 잡혔을 것**이, 가상 스레드에서는 받아들여진 채 오래 기다리는 모양이 된다. **실패가 지연으로 바뀌는 것이라 지표에서 더 늦게 드러난다.**

8장의 큐 최대 길이와 p99 를 함께 봐야 하는 이유가 이것이다.

## 3. 재서 정할 값

`coupon.md` 8장이 조건으로 잡은 것들이다. **시작값을 박아 두고 부하 시험에서 옮긴다.**

```
배치 윈도우와 배치 크기   20ms / 500 에서 시작.  1ms~100ms 를 훑는다
플러시 스레드 수          1 부터 N 까지 늘려가며 본다
요청 예산                 안쪽 합보다 커야 한다.  계층이 역전되면 안 된다
Hikari 풀 크기            5장 예산에서 역산
connection-timeout        앱 기본 3초보다 짧게
pending 회수 기준 시간     요청 예산보다 넉넉하게
큐 상한                    20000 -> 10000 -> 5000 -> 2500 -> 1000
                           크게 시작해 줄여가며 어디서 무엇이 나빠지는지 본다
```

**20000 부터 시작한다.** 요구 부하의 사람 수와 같은 값이라 2만이 전부 큐에 들어와도 안 막는다. 무한으로 두는 것과 결과가 같으면서 **앱이 급사했을 때 잃는 건수의 상한**은 숫자로 남는다.

톰캣의 `max-connections` 는 안 건드린다. 스프링 기본값 8192 가 그대로 상한이고, 그것이 실제로 물리는지는 시험에서 본다. **요청 예산이 400ms 라 동시에 떠 있는 요청은 도착률 x 0.4초로 묶이는데**, keep-alive 유휴 연결은 그것과 무관하게 남아 있어 어느 쪽이 먼저 닿을지 지금은 알 수 없다.

```
20000    동접 전부를 받는 값.  아무도 안 막는다
10000    재고와 같은 수.  여기부터 거절이 나오기 시작할 수 있다
5000
2500
1000     짧은 큐.  거절이 늘지만 받은 요청의 p99 는 좋아진다
```

**줄일수록 p99 는 좋아지고 거절은 는다.** 어느 쪽을 택할지가 이 시험의 결론이다.

**큐 상한만 성격이 조금 다르다.** 나머지는 성능을 위한 값이지만 이것은 **앱이 급사했을 때 잃는 건수의 상한**이기도 하다. 크게 잡으면 꼬리 지연과 손실이 같이 늘고, 작게 잡으면 멀쩡히 받을 수 있는 요청을 거절한다.

**넘칠 때의 동작은 이미 정해진 것에서 따라온다.**

```
거절한다        안 그러면 메모리까지 자란다
혼잡으로 답한다  재고가 없는 것이 아니므로 소진이 아니다 (3장의 네 응답)
자리를 먼저 잡는다  순번을 받은 뒤에 큐에 못 넣으면 그 번호를 반납해야 한다
                    큐 길이를 먼저 보고 나서 Redis 를 부르면 번호를 안 태운다
```

## 5. 진행 기록

작업하며 채운다. **왜 그렇게 만들었는지가 코드에서 안 읽히는 것만 적는다.**

### 엔티티 (72d2337)

`Coupon`, `MemberCoupon` 과 열거형 셋(`CouponScope`, `DiscountType`, `MemberCouponStatus`)을 만들었다.

**스키마가 진실이고 엔티티가 거기 맞춘다.** `ddl-auto: validate` 라 엔티티가 테이블을 만들지 않는다. 그래서 엔티티의 검증 메서드는 새 규칙이 아니라 **DB 의 `CHECK` 를 앱 쪽에서 한 번 더 막는 것**이다. `validateDiscount` 가 `chk_coupon_rate` 를, `validateIssueSeq` 가 `chk_mc_issue_seq` 를 그대로 비춘다. 둘이 어긋나면 DB 쪽이 맞다.

**`Coupon` 은 팩터리를 둘로 갈랐다.**

```
draftUnlimited(이름, scope, 할인, 유효기간)              일반 쿠폰
draftLimited  (.. + totalQuantity, issueStartAt/EndAt)  선착순 쿠폰
```

호출부가 **어느 쪽을 만드는지 이름에서 드러나게** 한 것이다. 빌더 하나로 두면 `totalQuantity` 를 넣었는지 여부로만 갈려서, 선착순으로 만들 의도였는데 일반 쿠폰이 되는 실수가 조용히 지나간다.

`@Builder` 를 안 쓴 것은 그 다음 문제다. Lombok 은 `builder` 라는 **이름**의 메서드가 이미 있으면 시그니처와 무관하게 생성을 건너뛴다. 팩터리를 쓰기로 한 이상 빌더를 같이 둘 이유가 없다.

**`MemberCoupon` 에는 상태를 바꾸는 메서드가 없다.** `use()` 나 `expire()` 를 두지 않았다.

[coupon.md](coupon.md) 2장의 R5 가 조건부 `UPDATE` 로 지키기로 한 것이라서다. 엔티티에 상태 변경 메서드를 두면 **읽고 -> 바꾸고 -> 저장하는 경로가 열리고**, 그 사이에 남이 끼어들 수 있다. 메서드를 아예 안 두면 그 경로가 생기지 않는다.

### 순번 확보 Lua (`src/main/resources/redis/scripts/coupon-issue-seq.lua`)

[coupon.md](coupon.md) 3장의 설계를 그대로 옮겼다. **네 키를 한 번에 다루는 것이 핵심**이고, 그래서 스크립트여야 한다. 나눠 부르면 그 사이에 끼어들 틈이 생긴다.

```
seq      해시      회원 -> 순번.  "6" 번호만 받음, "6:1" 커밋 완료
free     정렬집합  반납된 순번
counter  문자열    다음에 나갈 번호
pending  정렬집합  아직 커밋 안 된 회원.  점수 = 번호를 준 시각
```

**들어와서 나가는 길이 넷이다.**

```
-2   counter 키가 없다.  준비 전이거나 재건 중이다
"6:1" 이미 발급됐다.  seq 에 확정 표시가 붙어 있다
"6"  번호를 받았다.  free 반납분 -> 새 번호 -> 회수분 순으로 찾는다
-1   소진.  회수할 것도 없다
```

**`-2` 가드가 필요한 이유가 덜 자명하다.** 이게 없으면 키가 사라진 뒤 들어온 요청에서 `INCR` 이 1 을 내준다. 이미 1번이 나간 이벤트인데 또 1번을 주는 것이라, 소진 판정도 순번도 처음부터 다시 시작한다.

**반납분을 먼저 쓰는 것(`ZPOPMIN`)은 낮은 번호부터 나가게 하려는 것**이다. `MAX(issue_seq)` 와 실제 발급 수의 간격이 덜 벌어져야 10장의 정합성 검증이 읽힌다.

#### 회수는 조건이 둘이다

묶인 번호(번호는 받았는데 커밋 전에 사라진 요청)를 푸는 자리다. **트리거와 조건을 나눠 봐야 한다.**

```
트리거   소진 상태다        재고가 있으면 이 구간에 아예 안 온다.  평상시 비용 0
조건     기준 시간이 지났다  ZRANGEBYSCORE 로 오래된 것만 고른다
```

**시계는 소진 시각이 아니라 번호를 준 시각부터 돈다.** `pending` 의 점수가 준 시각이라서다. 묶인 번호는 대개 소진 한참 전에 나간 것이라, **소진되는 순간 이미 기준 시간을 넘겨 바로 회수된다.** 늦어지는 것은 소진 직전 몇 초 안에 묶인 것뿐이다.

**주기 배치가 필요 없는 이유가 이 트리거다.** 급할 때만 찾아보므로 따로 도는 것이 없다.

**대신 요청이 와야 돈다.** 소진 뒤 트래픽이 완전히 빠지면 회수가 실행될 일이 없고, 그 번호는 키가 만료될 때까지 그대로 남는다. 기준 시간을 줄여서 해결되는 문제가 아니다.

기준 시간 값은 3장에 열어 뒀다. **하한은 요청 예산이다.** 그보다 짧으면 아직 살아 있는 요청의 번호를 뺏어 둘이 같은 번호로 `INSERT` 하고 `uk_mc_coupon_seq` 에 걸린다.

#### 시계는 Redis 것을 쓴다

```lua
local t = redis.call('TIME')
local now = t[1] * 1000 + math.floor(t[2] / 1000)
```

처음에는 앱이 `Clock` 으로 시각을 넘겼다. **점수를 쓰는 인스턴스와 그것을 재는 인스턴스가 달라서 그러면 안 된다.**

한 대만 시계가 어긋나도 그 인스턴스는 모든 `pending` 을 오래된 것으로 보고, **방금 번호를 받아 살아 있는 요청들의 번호를 연달아 뺏는다.** 이 시각은 앱이 한 번도 해석하지 않고 Redis 안에서만 비교되므로 앱에서 댈 이유가 없다.

`TIME` 은 쓰기 앞에서도 쓸 수 있다. 효과 복제가 기본이라 복제본에도 계산된 점수가 그대로 간다.

#### 문서 스크립트에 없는 줄이 하나 있다

```lua
-- 확정 표시가 붙은 것은 실제로 발급된 것이라 회수하지 않는다. pending 에서만 뺀다
if seq and not string.find(seq, ':') then
```

플러시 스레드가 확정 표시(`"6:1"`)를 붙이면서 `pending` 에서도 빼므로 **정상적으로는 안 생기는 조합**이다. 한쪽만 실패했을 때 `"6:1"` 을 새 회원에게 그대로 내주는 것을 막는 가드다.

#### 검증

`CouponSeqAllocatorIntegrationTest` 가 실제 Valkey 로 여덟 갈래를 짚는다. 아래 래퍼 절에 목록이 있다.

**회수는 연쇄된다.** 회수해서 받은 요청도 `pending` 에 들어가므로, 그것도 안 끝내면 다음 사람에게 넘어간다. 의도한 동작이고 **번호가 계속 흘러 재고가 안 묶인다.**

### 래퍼 (`CouponSeqAllocator`)

스크립트를 부르고 반환 문자열을 갈래로 바꾸는 것이 전부다. **판단은 전부 스크립트에 있고 여기에는 없다.**

`RefreshTokenRepository` 를 본떠 만들었다가 다시 짰다. 그 클래스의 모양이 이 자리에 안 맞는 데가 셋이었다.

#### 결과를 봉인 계층으로 받는다

```java
public sealed interface SeqOutcome {
    record Allocated(int seq)     implements SeqOutcome { }
    record AlreadyIssued(int seq) implements SeqOutcome { }
    record SoldOut()              implements SeqOutcome { }
    record NotPrepared()          implements SeqOutcome { }
}
```

열거형과 `Integer seq` 로 두면 **순번이 없는 갈래에서도 `seq()` 를 부를 수 있고 `null` 이 나온다.** 봉인 계층은 순번을 있는 갈래에만 두고, 호출부가 `switch` 로 받을 때 빠뜨린 갈래를 컴파일러가 잡는다. **네 갈래가 그대로 네 응답이 되므로 빠뜨리면 안 되는 자리다.**

`SoldOut` 과 `NotPrepared` 를 가른 것이 이 타입의 이유다. `Optional` 하나로는 **"다 팔렸다"(최종, 4xx)와 "다시 시도할 값이 있다"(503)가 같은 값**이 된다.

#### 스크립트를 기동 때 읽는다

`setLocation()` 으로 걸어 두면 **첫 실행에서 파일을 읽는다.** 패키징이 어긋났을 때 그 사실을 이벤트 첫 요청에서 알게 되고, 그때는 모든 요청이 같이 터진다. 생성자에서 다 읽어 **기동이 대신 실패하게** 했다.

#### 회수 기준은 인자가 아니라 설정이다

```java
@Value("${coupon.issue.reclaim-after:60s}") Duration reclaimAfter
```

**회수의 안전은 모든 호출부가 같은 값을 쓰는 데 달려 있다.** 부를 때마다 넘기게 두면 한 군데만 달라져도 살아 있는 요청의 번호를 뺏는다. `issueLimit` 은 쿠폰마다 다르므로 인자로 남겼다.

지금은 기본값 `60s` 뿐이다. 3장에 열어 둔 값이라 `application-coupon.yml` 을 만들 때 그리로 옮긴다.

#### 이름과 나머지

```
CouponIssueSeqRepository -> CouponSeqAllocator   저장소가 아니라 할당기다
@Repository -> @Component                        예외 변환은 템플릿이 이미 한다
nil 을 NotPrepared 로 흘리기 -> 예외              스크립트와 어긋난 것이라 재시도에 묻히면 안 된다
```

#### 테스트는 통합 소스셋에 둔다

Lua 와 Java 가 맞물리는 자리라 **단위 테스트로는 못 잡는다.** KEYS 와 ARGV 의 순서, 반환 문자열의 해석, 회수 경계는 어느 한쪽만 고쳐도 조용히 어긋난다.

```
카운터가 없으면 순번을 내주지 않는다
순번은 1부터 차례로 나간다
같은 회원이 다시 요청하면 같은 번호를 받는다
한도를 넘으면 소진이고 카운터가 부풀지 않는다
반납된 순번이 새 번호보다 먼저 나간다
커밋이 끝난 회원은 이미 발급으로 답한다
묶인 순번은 기준 시간이 지나야 회수된다
확정 표시가 붙은 것은 회수하지 않는다
```

**`IntegrationTestSupport` 에 Valkey 컨테이너를 더했다.** 없으면 `spring.data.redis` 가 `application.yml` 의 기본값인 `localhost:6379` 를 봐서, 개발자 기계에 컨테이너가 떠 있는지에 따라 결과가 갈린다. MySQL 과 같은 이유로 JVM 당 한 번만 띄운다.

`@ServiceConnection(name = "redis")` 로 이름을 준 것은 `compose.yaml` 이 레이블을 다는 이유와 같다. **Spring 이 이미지 이름으로 서비스를 알아보는데 valkey 가 그 목록에 없다.**

### 큐와 플러시 (`coupon.domain.issue`)

```
CouponIssueQueue       인스턴스별 인메모리 큐.  자리도 여기서 본다
CouponIssueFlusher     N 개 스레드가 모아서 쓰고 결과를 돌려준다
IssueTicket            seq, memberId, future 에 행을 만들 값을 더한 것
IssueOutcome           Issued / AlreadyIssued / Congested
CouponIssueProperties  3장의 재서 정할 값을 한곳에 모은 것
CouponSeqCommitter     확정 표시와 반납.  플러시 스레드만 부른다
MemberCouponBulkRepository  JDBC 배치 쓰기
```

#### 자리는 세마포어가 아니라 큐 길이로 본다

3장이 세마포어라고 적었으나 만들면서 바꿨다. **그 항목의 요점은 순서지 정확한 상한이 아니다.**

```
순번을 받기 전에 판정한다   이것이 지켜지면 반납 경로가 안 생긴다
정확히 센다                 여기서는 요구되지 않는다
```

세마포어는 요청마다 경합하는 CAS 를 둘 더한다. **더 큰 문제는 꺼낸 만큼 자리를 돌려주는 코드가 필요해지는 것**이다. 그 사이에서 죽으면 자리가 새고, 새면 큐가 영구히 덜 받는다. 그 증상은 부하 시험에서 "왜 거절이 늘지" 로만 보여 원인을 찾기 어렵다.

큐 길이를 읽는 것은 `AtomicInteger` 하나를 읽는 것이고, **큐가 스스로 세므로 샐 자리가 없다.** 대가는 상한이 대략이 되는 것인데, 이 상한의 쓰임(꼬리 지연, 급사 시 손실 건수)이 정확한 수를 요구하지 않는다.

#### 배치는 다 차거나 윈도우가 닫히면 나간다

```
1  첫 항목을 기다린다        없으면 계속 기다린다
2  이미 쌓인 것을 다 꺼낸다   drainTo
3  모자라면 윈도우까지 더 모은다
```

**붐빌 때는 플러시 스레드가 2번에서 이미 다 채워 안 기다린다.** 그 스레드가 윈도우를 실제로 기다리는 것은 한산할 때뿐이라, 이 값이 지연을 늘리는 쪽으로는 잘 안 작동한다.

#### 한 행이 걸리면 배치 전체가 실패한다

한 문장으로 압축된 `INSERT` 라 **한 행이 제약에 걸리면 아무것도 안 들어간다.** DB 는 어느 행 때문에 걸렸는지 알려주지 않으므로, 플러시 스레드가 한 건씩 다시 넣어 가른다.

**정상 경로에서는 안 도는 코드다.** 제약에 걸릴 일이 없으면 배치가 한 번에 끝난다.

#### 어느 UNIQUE 인지 메시지로 가르지 않는다

```sql
SELECT issue_seq FROM member_coupon WHERE coupon_id = ? AND member_id = ?
```

```
행이 있고 순번이 다르다   uk_mc_coupon_member.  이번 번호는 안 쓰였다 -> 반납
행이 있고 순번이 같다     앞선 시도가 이미 썼다 -> 반납 금지, 표시만 남긴다
행이 없다                uk_mc_coupon_seq.     그 번호를 남이 쓴다 -> 반납 금지
```

**가운데 줄이 처음에 빠져 있었다.** [coupon.md](coupon.md) 3장의 실패 표는 `uk_mc_coupon_member` 위반을 "그 번호는 안 쓰였다" 한 줄로 적었는데, **이번에 받은 번호와 원래 갖고 있던 번호가 같으면 그게 성립하지 않는다.**

```
플러시가 6번 행을 쓴다.  커밋됨
확정 표시를 남기기 전에 앱이 죽는다.  매핑은 "6" 그대로
사용자가 재시도 -> 매핑이 "6" 이라 같은 번호를 받는다
INSERT -> uk_mc_coupon_member 위반 -> 반납하면 살아 있는 6번이 free 로 간다
```

**다음 사람이 그 번호를 받아 `uk_mc_coupon_seq` 에 부딪힌다.** 그래서 플러시 스레드가 두 번호를 견줘 갈라야 한다.

예외 메시지에 제약 이름이 들어 있지만 **그 형식은 드라이버와 서버 판에 따라 달라진다.** 행의 유무는 안 달라진다. 그 읽기마저 실패하면 플러시 스레드가 가를 수 없으므로 **아무것도 건드리지 않는다.** 매핑을 유지하는 쪽이 언제나 안전하다.

#### 확정 표시는 응답보다 앞이다

커밋 -> 확정 표시 -> 응답 순이다. **뒤로 미루면 사용자의 재시도가 표시보다 먼저 도착해 DB 까지 간다.** 그 왕복을 아끼려고 두는 표시라 응답 앞에 있어야 뜻이 있다.

표시를 못 남겨도 정확성은 그대로다. 그래서 `CouponSeqCommitter` 는 예외를 밖으로 던지지 않는다. **던지면 이미 발급된 요청에 혼잡으로 답하게 되어 잘못이 더 커진다.**

#### 플러시 스레드는 플랫폼 스레드다

하는 일이 JDBC 블로킹이고 **개수를 정확히 N 으로 잡아 재는 것이 목적**이다. 가상 스레드로 두면 그 N 이 의미를 잃는다. 요청 스레드가 가상 스레드인 것과 이유가 정반대다.

#### 조율 값을 한곳에 모았다

`CouponIssueProperties` 하나가 3장의 값을 전부 갖는다. **이 값들이 서로의 상하한이라 따로 고치면 계층이 역전된다.**

```java
require(reclaimAfter.compareTo(requestBudget) > 0, ...)
```

회수 기준이 요청 예산보다 짧으면 살아 있는 요청의 번호를 뺏는다. **기동에서 막아 부하 시험 중에 이 조합이 나오지 않게 했다.**

#### 검증

`CouponIssueFlusherIntegrationTest` 다섯 건이 실제 MySQL 과 Valkey 로 확인한다.

```
큐에 넣으면 행이 되고 결과가 돌아온다
한 배치가 여러 건을 함께 쓴다
커밋한 뒤 확정 표시를 남긴다
이미 가진 회원이면 번호를 반납하고 매핑을 고친다      uk_mc_coupon_member
자기 번호로 다시 오면 반납하지 않는다                 살아 있는 번호를 지킨다
남이 쓰는 번호면 반납하지 않고 매핑만 지운다          uk_mc_coupon_seq
```

**실패 두 갈래를 실제 제약으로 재현했다.** 이 분기는 사람이 읽어서는 맞는지 알기 어렵고, DB 가 실제로 어느 쪽을 던지는지에 달려 있다.

### 컨트롤러와 서비스

```
CouponIssueController  POST /v1/coupons/{couponId}/issues.  평범하게 블로킹한다
CouponIssueService     자격 확인 -> 자리 -> 순번 -> 큐 -> 응답
CouponIssueResponse    { issueSeq, alreadyIssued }
CouponErrorCode        소진과 혼잡을 다른 코드로 둔다
```

#### 서비스에 트랜잭션이 없다

쓰기는 플러시 스레드가 자기 커넥션으로 한다. 이 메서드는 큐에 넣고 기다릴 뿐이다.

**여기서 트랜잭션을 열면 기다리는 내내 커넥션을 쥔다.** 동시 요청 수만큼 커넥션이 잡혀 5장의 예산을 그대로 먹고, 정작 쓰려는 플러시 스레드가 커넥션을 못 얻어 **큐에 모인 배치 전체가 함께 멈춘다.**

#### 등급 확인은 필요할 때만 회원을 읽는다

자격 확인 셋 중 기간과 `is_active` 는 이미 읽은 쿠폰 행에 있다. **대상 등급만 회원을 봐야 한다.**

```java
if (coupon.getTargetGradeId() == null) {
    return;   // 대부분의 선착순 쿠폰이 여기서 끝난다
}
```

이 읽기는 DB 왕복이라 선착순 경로에서 되도록 피한다. **등급을 걸지 않은 쿠폰은 회원을 아예 안 읽는다.**

`MemberInfo` 에 `memberGradeId` 를 더했다. 등급은 `member` 도메인이 갖고 있는데 그 창구가 안 내주고 있었다. `coupon` 이 `member` 의 엔티티를 직접 읽으면 도메인 경계 규칙에 걸리므로 창구를 넓히는 쪽이 맞다.

**회원이 없으면 인증 실패로 답한다.** `memberId` 는 검증된 토큰에서 오므로, 없다는 것은 그 사이에 탈퇴했다는 뜻이다. 쿠폰의 실패가 아니라 자격 증명의 실패라 `CommonErrorCode.UNAUTHENTICATED` 를 쓴다. `member` 의 오류 코드를 쓰고 싶어도 도메인 경계가 막는다.

#### 기간 검사의 근거가 바뀌었다

[coupon.md](coupon.md) 3장은 이 검사를 **"키가 만료된 뒤에 `INCR` 이 1 을 내주는 것"** 을 막는 안전장치로 적고 있었다. 그 자리는 스크립트의 카운터 가드가 이미 막는다.

```lua
if redis.call('EXISTS', KEYS[3]) == 0 then
  return '-2'
end
```

**그래도 이 검사는 남긴다. 버는 것이 응답의 뜻으로 바뀌었을 뿐이다.**

```
있다   사흘 전 끝난 이벤트 -> 422 NOT_ISSUABLE   끝났다
없다   사흘 전 끝난 이벤트 -> 503 CONGESTED      잠시 후 다시 오라는 뜻이 된다
```

`-2` 는 재고가 남았을 수 있다는 뜻이라 혼잡으로 나간다. **끝난 이벤트에 재시도를 유도하게 된다.** 3장이 소진과 혼잡을 가른 것과 같은 이유로 이 검사를 둔다.

#### 네 응답이 두 곳에서 갈린다

```
순번 확보에서   AlreadyIssued -> 200 (true)     큐도 DB 도 안 거친다
                SoldOut       -> 409            최종이다
                NotPrepared   -> 503            재고는 있을 수 있다
                Allocated     -> 큐로 간다

플러시 결과에서 Issued        -> 200 (false)
                AlreadyIssued -> 200 (true)     uk_mc_coupon_member 로 갈라낸 것
                Congested     -> 503
                예산 초과      -> 503
```

**소진만 최종이고 나머지 실패는 다시 시도할 값이 있다.** 그래서 409 와 503 을 가른다.

#### Retry-After 는 상태 코드가 붙인다

`GlobalExceptionHandler` 가 503 과 429 에 붙인다. **도메인 지식이 아니라 상태 코드가 정하는 것**이라 그 자리가 맞고, `common` 이 도메인을 모른다는 규칙도 안 건드린다.

없으면 **못 받은 요청이 곧바로 다시 몰린다.** 지금 503 을 내는 것은 카카오 응답 없음과 이 혼잡 둘뿐이고 둘 다 붙는 게 맞다. 429 는 레이트 리밋 필터가 직접 status 를 세팅해 이 핸들러를 안 거친다.

#### 검증

`CouponIssueServiceTest` 16건이다. 서비스 패키지는 단위 테스트 메서드 커버리지 100% 게이트가 걸려 있어 모든 갈래를 지난다.

```
없는 쿠폰 / 무제한 쿠폰 / 스위치 꺼짐 / 기간 지남
대상 등급이 없으면 회원을 읽지 않는다      DB 왕복을 아끼는 것이 지켜지는지
대상 등급 불일치 / 토큰의 회원이 사라짐
큐에 자리가 없으면 순번을 받지 않는다      Redis 를 안 부른 것까지 본다
소진 / 준비 안 됨 / 이미 발급
순번을 받으면 큐에 넣는다 / 플러시 세 갈래 / 예산 초과
```

### 이벤트 준비와 종료, 관리자 API

```
CouponSeqInitializer        prepare / applyTtl / clear
CouponEventService          open / close / changeIssuePeriod / 배치 둘
AdminCouponEventController  열기, 닫기, 발급 시각 변경
CouponEventScheduler        끄기 1분, 정리 10분
```

#### 여는 순서를 트랜잭션이 지킨다

요구가 둘인데 서로 반대 방향이었다.

```
카운터가 먼저   스위치가 먼저 켜지면 그 틈의 요청이 카운터 없는 Redis 를 쳐서
                재고가 멀쩡한데 혼잡 응답을 받는다
스위치가 먼저   두 관리자가 동시에 열면 뒤늦은 쪽이 도는 이벤트의 카운터를 지운다
                activateIfInactive 가 행을 잠가야 그것을 막는다
```

**트랜잭션이 둘을 함께 만족시킨다.** 스위치 갱신은 커밋 전까지 남에게 안 보이므로, 이 메서드가 잠금을 먼저 잡아도 **남이 스위치를 보는 시점에는 카운터가 이미 서 있다.**

그래서 `open()` 에 `@Transactional` 이 붙어 있다. 리포지터리 쪽 트랜잭션에 맡기면 갱신이 그 자리에서 커밋되어 순서가 도로 뒤집힌다. Redis 호출이 트랜잭션 안에 들어가 커넥션을 쥐지만, 관리자가 가끔 부르는 동작이라 치르는 값이다.

#### 조건을 SQL 안에 둔다

관리자 API 셋이 전부 조건부 갱신이다. 서비스가 같은 조건을 미리 보고 사유를 갈라 답하지만, **그 확인과 갱신 사이에 남이 끼어드는 것은 SQL 조건이 막는다.**

```
갱신된 행 수 0   그 조건이 거짓이었다는 뜻이다
```

#### 시각을 앱이 넘긴다

처음에는 SQL 에 `NOW(6)` 을 썼다. **통합 테스트가 그 자리에서 깨졌다.**

```
JVM      KST 로 issue_end_at 을 쓴다
컨테이너  UTC 로 NOW(6) 를 돌려준다
-> 9시간 어긋나 "마감이 지났다" 판정이 뒤집힌다
```

배포 환경이 우연히 같은 시간대라 안 드러날 뿐이고, **앱 시간대와 DB 시간대가 같아야만 도는 설계**였다. 앱이 `LocalDateTime.now(clock)` 을 넘기게 고쳐 그 결합을 끊었다.

**순번 확보 스크립트와 반대 선택이다.** 그쪽은 인스턴스 A 가 쓴 점수를 B 가 재므로 Redis 시계여야 했고, 여기는 같은 앱이 쓴 값을 같은 앱이 견주므로 앱 시계가 맞다. **누가 쓰고 누가 재는지가 매번 답을 정한다.**

#### 배치를 예약이 아니라 폴링으로 둔다

특정 시각에 한 번만 도는 예약과 견줬다.

```
JVM 에 예약   그 인스턴스가 사라지면 함께 사라진다
              선착순은 전용 ASG 를 이벤트 뒤에 내리므로 그 소멸이 정상 경로다
DB 에 예약    살아남지만 그 표를 읽는 폴링이 다시 생긴다
```

**정밀도도 쓸 데가 없다.** 마감이 지난 요청은 서비스의 기간 검사가 이미 막고, Redis 키는 `EXPIREAT` 이 따로 치운다. 스위치가 늦게 꺼져서 달라지는 것은 정리 대기가 늦게 시작되는 것뿐이다.

**주기는 둘로 나눴다.** 끄기는 쿠폰 표만 훑는 갱신이라 사실상 공짜지만, 정리는 후보마다 `member_coupon` 을 세는 상관 서브쿼리가 있어 무겁다.

#### 검증

```
CouponEventServiceTest              15건   단위.  서비스 100% 게이트를 지난다
CouponSeqInitializerIntegrationTest  6건   실제 Valkey
CouponEventQueryIntegrationTest     13건   실제 MySQL
```

**조건부 SQL 은 단위 테스트로 아무것도 확인하지 못한다.** 목이 돌려주는 숫자를 그대로 믿을 뿐이고, 그 숫자를 정하는 것이 SQL 조건이다. 종료 조건의 상관 서브쿼리와 정리의 하한/상한을 실제 MySQL 로 짚었다.

### 서킷 브레이커

```
CouponSeqCircuitProperties    coupon.circuit.  언제 포기할지를 정하는 값이다
CouponSeqUnavailableException 순번을 못 준다는 뜻 하나
```

#### 순번 확보에만 건다

[coupon.md](coupon.md) 3장이 정한 것이다. **발급 기능 전체에 걸면 이미 큐에 들어간 요청까지 버린다.**

```
큐에 있는 요청     그대로 플러시되어 발급된다.  Redis 는 2단계에만 있고 3단계에는 없다
순번을 못 받은 요청  혼잡.  큐에 넣지 않는다
```

그래서 회로는 `CouponSeqAllocator` 안에만 있다. 플러시 스레드가 부르는 `CouponSeqCommitter` 와 관리자가 부르는 `CouponSeqInitializer` 는 **회로 밖**이다. 뒤엣것에 걸면 회로가 열린 동안 관리자가 복구 동작을 못 한다.

#### 느린 호출도 실패로 센다

```java
.slowCallDurationThreshold(properties.slowCallDuration())
.slowCallRateThreshold(properties.failureRateThreshold())
```

**Redis 가 완전히 죽는 것보다 느려지는 쪽이 흔하다.** 그때 예외가 안 나면 회로가 안 열리고, 요청 스레드들이 전부 거기서 기다리며 요청 예산을 태운다. 큐는 비어 있는 채로 굶는다.

#### 예외를 하나로 묶는다

회로가 열린 것(`CallNotPermittedException`)과 Redis 가 답하지 않은 것(`DataAccessException`)을 `CouponSeqUnavailableException` 하나로 감싼다.

**호출자가 할 일이 같아서다.** 재고는 남아 있을 수 있으므로 소진이 아니고, 다시 시도할 값이 있으므로 혼잡으로 답한다. 갈라야 할 호출자가 없으니 타입을 둘로 나눌 이유도 없다.

라이브러리 예외를 밖으로 안 내보내는 것도 겸한다. 서비스가 그 타입을 알면 라이브러리를 바꿀 때 서비스까지 따라 고쳐야 한다.

#### 곁들여 고친 것

**회로를 달기 전에는 Redis 장애가 500 으로 나갔다.** 서비스가 `allocate` 를 감싸지 않아 `DataAccessException` 이 그대로 올라갔고, 공통 핸들러가 그것을 내부 오류로 바꿨다. 3장이 정한 혼잡 응답과 어긋나 있었다.

#### 직접 만들지 않은 이유

캐시 때와 반대로 판단했다.

```
캐시    담고 꺼내고 만료시키는 것이 전부.  처음에는 직접 만들었다
회로    닫힘 -> 열림 -> 반열림 상태 전이와 슬라이딩 윈도우 집계
        틀리기 쉽고, 정작 장애 때 처음 도는 코드라 그 위험을 안 지는 편이 낫다
```

**"평소에 안 도는 코드를 장애 시점에 처음 태우는 것이 장애를 키운다" 가 대체 경로를 안 두는 이유였는데, 회로 자체에도 그대로 적용된다.**

#### 검증

`CouponSeqAllocatorCircuitTest` 셋이다.

```
Redis 가 답하지 않으면 순번을 못 준다고 던진다
연속해서 깨지면 회로가 열려 Redis 를 안 부른다      열린 뒤의 호출이 Redis 까지 안 간 것을 센다
기다린 뒤 성공하면 회로가 다시 닫힌다               안 닫히면 Redis 가 살아나도 이벤트가 죽는다
```

**가운데가 요점이다.** "실패하면 예외가 난다" 가 아니라 **"열린 뒤에는 아예 안 보낸다"** 가 회로를 두는 이유다.

### DB 실패를 두 갈래로 가른다

```
DataAccessFailures    잠시 뒤면 될 것과 고쳐야 할 것을 가르는 규칙 한 곳
IssueOutcome.Failed   플러시가 고쳐야 할 실패를 만났다는 뜻
```

#### 읽기 실패가 500 으로 나가고 있었다

발급 경로에서 DB 를 읽는 곳이 둘인데 아무도 안 잡고 있었다.

```
CouponCache.load()       쿠폰을 읽는다.  캐시 미스일 때만 돈다
memberApi.findMember()   회원 등급을 읽는다.  등급 걸린 쿠폰에서만 돈다
```

**이 항목이 이벤트를 살리지는 않는다.** DB 가 죽으면 플러시도 못 쓰므로 그 요청은 어차피 실패한다. 고치는 것은 **신호**다. 500 은 진짜 버그와 같은 칸을 쓰므로, 그대로 두면 나중에 실제 버그가 이 소음에 묻힌다.

#### `DataAccessException` 을 통째로 잡으면 안 된다

그 아래에는 인프라 실패만 있는 것이 아니다.

```
CannotGetJdbcConnectionException  커넥션을 못 얻었다   -> 잠시 뒤면 된다
QueryTimeoutException             응답이 없다          -> 잠시 뒤면 된다
BadSqlGrammarException            SQL 이 틀렸다        -> 고쳐야 한다.  재시도해도 같다
```

**뒤엣것을 혼잡으로 덮으면 그 버그가 재시도에 묻혀 배포 뒤에도 한참 안 드러난다.**

**스프링의 `TransientDataAccessException` 만으로는 못 가른다.** 커넥션을 못 얻은 실패를 스프링은 비일시적으로 분류하는데, **Multi-AZ 페일오버는 60~120초 뒤에 끝나므로 여기서는 일시적**이다.

#### 읽는 쪽과 쓰는 쪽이 같은 규칙을 쓴다

플러시도 같은 병을 앓고 있었다. 한쪽에만 적용하면 왜 갈렸는지를 나중에 설명해야 한다.

```
읽기(서비스)    일시적이면 CONGESTED, 아니면 그대로 올려 500
쓰기(플러시)    일시적이면 Congested, 아니면 Failed -> 서비스가 500 으로 올린다
```

`IssueOutcome` 에 `Failed` 를 더한 것이 그래서다. `Congested` 하나로 두면 **플러시가 만난 버그를 요청 스레드가 "잠시 후 다시" 로 바꿔 답한다.**

#### 캐시가 포장을 벗긴다

```java
} catch (CompletionException e) {
    if (e.getCause() instanceof RuntimeException cause) {
        throw cause;
    }
```

이게 없으면 서비스의 `catch (DataAccessException)` 이 **`CompletionException` 에 가려 안 걸린다.** 겸사겸사 캐시가 안에서 future 를 쓴다는 사실이 계약으로 새는 것도 막는다.

#### 검증

```
쿠폰을 못 읽으면 혼잡으로 답한다
회원을 못 읽으면 혼잡으로 답한다
SQL 오류는 혼잡으로 덮지 않는다              <- 이 항목의 핵심이다
플러시가 고칠 실패를 만나면 혼잡으로 답하지 않는다
DB 실패가 포장 없이 그대로 나온다
```

**셋째와 넷째가 요점이다.** 넓게 잡으면 버그가 503 에 묻힌다는 것이 이 변경의 위험이고, 그것을 테스트가 못 박는다.

### DB 회로

```
CouponCircuitProperties   coupon.circuit.seq / coupon.circuit.write.  같은 모양 두 벌
CouponCircuits            둘을 같은 규칙으로 만든다
CouponWriteCircuit        플러시가 통과해서 쓰고, 서비스가 상태를 읽는다
```

#### 순번 회로만으로는 안 잡히는 자리가 있다

```
DB 가 죽는다.  Redis 는 멀쩡하다
-> 순번 회로는 안 열린다.  Redis 에 아무 문제가 없다
-> 요청마다 번호를 받고, 큐에 들어가고, 요청 예산을 다 태우고 실패한다
```

**세는 것은 DB 쓰기 실패이고 막는 것은 순번 확보다.** [coupon.md](coupon.md) 3장이 "회로를 Redis 호출에만" 이라고 한 것과 안 부딪힌다. 그 문장의 뜻은 **회로가 플러시를 막으면 안 된다**는 것이고, 이 회로도 플러시는 안 막는다.

#### 무엇을 실패로 세느냐가 요점이다

```
DuplicateKeyException      안 센다.  선착순에서 정상적으로 나오는 결과다
BadSqlGrammarException     안 센다.  버그다.  세면 회로가 열린 뒤 영영 안 닫힌다
일시적 DataAccessException  센다
```

**중복 키를 세면 이벤트가 멀쩡할 때 회로가 열린다.** 재시도와 매핑 유실로 중복이 꾸준히 나오는 것이 이 설계의 정상 동작이기 때문이다. 앞서 만든 `DataAccessFailures.isTransient` 를 `recordException` 에 그대로 물려 판정을 한 곳에 뒀다.

#### 세는 쪽과 읽는 쪽이 다르다

```
플러시 스레드   회로를 통해 쓴다.  허가를 소비하고 결과를 기록한다
요청 스레드     getState() 로 본다.  허가를 소비하지 않는다
```

**요청 스레드가 허가를 소비하면 반열림에서 통과시켜 보는 몇 건을 요청 스레드가 다 써버려**, 정작 플러시가 DB 를 시험해 볼 기회가 없어진다.

두 스레드를 잇는 것은 **공유된 `CircuitBreaker` 객체 하나**다. 메시지도 폴링도 없다. 다만 **JVM 하나짜리**라 인스턴스마다 여는 시점이 조금씩 다르다.

#### 반열림에서 다시 받아야 한다

여기 함정이 있다.

```
회로가 열린다 -> 서비스가 순번을 안 준다 -> 큐에 새 항목이 안 들어간다
-> 플러시가 쓸 게 없다 -> 아무도 회로를 시험 안 한다 -> 영영 안 닫힌다
```

그래서 서비스는 **"닫힘일 때" 가 아니라 "열림이 아닐 때"** 받는다.

```java
public boolean acceptsWrites() {
    return circuitBreaker.getState() != CircuitBreaker.State.OPEN;
}
```

#### 시험이 스스로 증명한 것

TTL 시험이 간헐적으로 깨져 캐시 실행기를 `Runnable::run` 으로 바꿔 봤더니 **동시 시험이 교착했다.** 로딩이 Caffeine 의 모니터 안에서 돌아 가상 스레드 스물이 전부 핀된 것이다.

**이 프로젝트가 `AsyncCache` 를 쓰는 이유를 시험이 그대로 재현했다.** 지금은 시험에 단일 스레드 실행기를 주고 콜백이 끝나기를 기다려 순서를 정한다.

#### 검증

```
중복 키는 회로를 열지 않는다              <- 이 회로의 핵심이다
SQL 오류는 회로를 열지 않는다
DB 가 답하지 않으면 회로가 열린다
회로가 열리면 쓰기가 DB 까지 안 간다
기다리면 다시 받기 시작한다               <- 안 그러면 영영 안 닫힌다
쓰기 회로가 열려 있으면 순번을 받지 않는다  (서비스 쪽)
```

### 전용 프로파일 (`application-coupon.yml`)

```
--spring.profiles.active=prod,coupon
```

4장이 ALB 경로로 ASG 를 갈랐으므로 이 프로필은 그 전용 ASG 에서만 켠다. **프로필을 켜는 것은 `fm-infra` 쪽 일**이고 이 파일은 켜졌을 때의 값만 갖는다.

#### 빠져 있던 전제가 하나 드러났다

```yaml
spring.threads.virtual.enabled: true
```

**v4 설계가 이것을 전제하는데 어디에도 설정돼 있지 않았다.** 요청 스레드가 큐에서 자는 구조라 플랫폼 스레드면 톰캣 200 개가 그대로 상한이 되어 동접 2만을 못 받는다.

전역이 아니라 이 프로필에 둔다. 가상 스레드가 큐 길이의 자연 상한을 없애는 것도 이 경로에서만 감당하기로 한 대가다.

#### 계층을 실제 숫자로 맞췄다

```
요청 예산 400ms  >  connection-timeout 100 + socketTimeout 250  =  350ms
```

전역값(`connection-timeout` 3000, `socketTimeout` 10000)으로는 **안쪽이 바깥보다 길어 역전돼 있었다.** 그 상태면 요청 스레드가 먼저 포기해 혼잡으로 답한 뒤에 그 배치가 커밋된다.

값 자체는 [coupon.md](coupon.md) 8장의 SLO(처리된 응답 p99 500ms)에서 역산했다. **요청 예산이 곧 성공 응답의 지연 상한**이라 그것이 SLO 보다 길면 SLO 를 구조적으로 못 지킨다.

500 이 아니라 400 인 것은 앞단 때문이다. **Redis 왕복 둘이 예산 밖에 있다.** 인증 필터의 커트라인 조회와 순번 확보가 각각 Redis 타임아웃(100ms)을 쓰므로, 최악이면 200ms 를 총 시간에 얹는다.

회로의 느림 기준도 함께 내렸다(`seq` 50ms, `write` 150ms). **각자의 타임아웃보다 앞이어야** 느려지는 구간에서 회로가 열린다. 같은 값이면 실제로 끊긴 호출만 세게 되어, 그때까지 요청마다 타임아웃을 그대로 문다.

#### 풀 크기는 예산에서 역산했다


### 큐 길이 지표 (`CouponIssueMetrics`)

8장이 재라고 한 것 중 **앱이 직접 내야 하는 값**만 등록한다. 나머지는 이미 나오고 있다.

```
처리량, p99          http.server.requests            자동
DB 커넥션 대기        hikaricp_connections_pending    자동
평상시 경로의 지표     같은 http 지표                   자동
큐 길이              coupon.issue.queue.size          여기서 낸다
캐시 적중률           cache.gets{cache=coupon.eligibility}  여기서 낸다
```

#### 앱은 현재 길이만 낸다

8장이 요구한 것은 **큐 최대 길이**인데 앱은 게이지로 현재 값만 낸다. 최댓값은 대시보드가 `max_over_time` 으로 뽑는다.

**앱이 최댓값을 들고 있으면 언제 리셋할지를 앱이 정해야 하고, 그 창이 대시보드의 창과 안 맞는다.**

이 값을 p99 와 함께 봐야 하는 이유가 있다. 가상 스레드는 요청을 다 받아들이므로 **폭주가 실패가 아니라 지연으로 나타나는데**, 큐 길이를 같이 보면 얼마나 밀려 있는지가 드러난다.

#### 캐시 적중률은 TTL 을 조정할 근거다

`coupon.issue.coupon-cache-ttl` 을 줄이면 마감 초과 허용치가 줄어드는 대신 DB 조회가 는다. **그 교환을 숫자로 봐야 정할 수 있다.**

Caffeine 의 `recordStats()` 를 이미 켜 뒀으므로 Micrometer 의 바인더를 붙이는 것이 전부다.

#### 발급 결과는 상태 코드로 못 가른다

8장이 요구한 것이다.

> 충돌, **소진**, **혼잡**, DB 타임아웃을 나눠 센다. 둘을 뭉치면 다 판 것과 못 판 것이 같은 통계가 된다

**상태 코드로는 소진(409)과 혼잡(503)까지만 갈린다.** 혼잡 안에 순번 충돌과 큐 포화와 DB 실패와 예산 초과가 다 들어 있다. `coupon.issue.results{result=...}` 가 그것을 가른다.

```
issued / already-issued / sold-out / not-issuable
congested-seq-taken       충돌
congested-db-failed       DB 타임아웃
congested-queue-full / write-circuit / seq-unavailable / not-prepared / budget / read / aborted
```

**재요청 비율도 여기서 나온다.** `already-issued` 를 전체로 나누면 된다. 그 전에는 응답 본문의 플래그에만 있어 셀 수가 없었다.

#### 사유를 `Congested` 가 들고 다닌다

플러시가 만난 실패를 서비스가 503 으로 옮기고 나면 **순번 충돌인지 DB 실패인지가 사라진다.** 그래서 그 갈래에 사유를 붙였다.

```java
record Congested(IssueResult reason) implements IssueOutcome { }
```

서비스는 자기가 만든 사유(큐 포화, 회로, 예산 초과)를 그대로 세고, 플러시가 들고 온 것은 **바꾸지 않고 그대로** 센다.

#### 계량기를 기동 때 다 만든다

처음 그 갈래가 나올 때 만들면, **한 번도 안 난 갈래가 대시보드에서 아예 안 보인다.** "혼잡이 0 건" 과 "혼잡을 안 센다" 가 같은 모양이 되어 읽는 쪽이 구분하지 못한다.

#### 검증

```

충돌과 소진과 DB 실패가 다른 값으로 잡힌다
큐 길이가 지표로 나온다
캐시 적중과 실패가 지표로 나온다
플러시가 들고 온 사유를 그대로 센다      (서비스 쪽)

```

**이름이나 등록이 틀리면 앱은 멀쩡히 뜨고 대시보드만 빈다.** 그것을 부하 시험 당일에 알면 그 회차를 통째로 다시 돌려야 한다.

### 상태 머신 (`MemberCouponStatusService`)

[requirement.md](requirement.md) 가 요구한 마지막 갈래다. 발급된 쿠폰이 `ISSUED -> USED -> CANCELED` 와 `ISSUED -> EXPIRED` 로만 움직이고, **같은 전이가 반복되거나 겹쳐도 한 번만 반영되어야 한다.**

주문 도메인과 잇는 것은 범위 밖으로 뒀다. **창구(`CouponApi`)까지만 만든다.**

#### 읽고 판단한 뒤 쓰지 않는다

스키마가 R1~R4 는 막지만 **R5 는 못 막는다.** 같은 전이를 두 번 요청하는 것은 DB 가 보기에 정상적인 `UPDATE` 두 번이다. 그래서 지금 상태를 `WHERE` 에 넣어 한 문장으로 만든다.

```
UPDATE member_coupon SET status = 'USED' ... WHERE member_coupon_id = ? AND status = 'ISSUED'
```

```
반복 요청   두 번째부터 status 가 조건에 안 맞아 0행
동시 요청   행 락으로 줄을 서고, 뒤엣것은 깨어났을 때 조건이 어긋나 역시 0행
```

**앱이 읽어서 판단하면 그 사이가 열린다.** 읽은 값이 `ISSUED` 라는 것은 읽은 순간의 이야기이고, 쓰는 순간에도 그렇다는 보장이 없다.

#### 0행을 세 갈래로 가른다

0행은 실패가 아니다. 무엇 때문에 0행인지를 앱이 한 번 더 읽어서 가른다.

```
이미 그 상태다   늦게 도착한 같은 요청이다.  조용히 성공으로 답한다
다른 상태다      만료된 것을 쓰려 했다.  422 INVALID_STATUS_TRANSITION
행이 없다        없거나 남의 것이다.  404 MEMBER_COUPON_NOT_FOUND
```

**남의 것과 없는 것을 가르지 않는 것이 중요하다.** 가르면 번호를 훑어 남의 쿠폰의 존재를 알아낼 수 있다. `memberId` 를 `WHERE` 에 넣는 것이 소유권 검증이고, 그 결과가 "없음" 과 같은 모양이 되는 것이 의도다.

이 재조회는 **전이가 실패한 뒤에만** 돈다. 정상 경로는 갱신 한 번으로 끝난다.

#### 사용을 철회하면 사용 시각도 비운다

`chk_mc_used_at` 이 사용 상태와 사용 시각을 묶고 있다. `status` 만 `CANCELED` 로 바꾸면 **그 갱신 자체가 제약에 걸려 실패한다.** DB 가 앱의 빠뜨림을 막아 주는 자리다.

#### 만료는 층이 셋이다

만료 배치는 하루에 한 번 돈다. 그래서 **기간이 지난 발급분이 한동안 `ISSUED` 로 남아 있는 창**이 생긴다. 상태만 조건에 넣으면 그 창에서 만료된 쿠폰이 그냥 쓰인다.

배치를 자주 돌려서 해결하는 문제가 아니다. 아무리 자주 돌려도 창이 0 이 되지 않는다. **층을 나눠야 한다.**

```
사용 조건 (WHERE)  정확성.  기간이 지난 것은 표시가 어떻든 안 나간다
조회 시 해소       표시.    저장된 값이 늦어도 회원에게는 만료로 보인다
만료 배치          저장된 값을 맞춘다.  정합성 검증과 통계가 읽을 값이다
```

그래서 사용 갱신이 `coupon` 을 조인해 `valid_from <= 오늘 AND valid_to >= 오늘` 을 함께 건다. **배치가 늦어도 만료된 쿠폰은 안 나간다.**

**가운데 층은 아직 없다.** 보유 쿠폰 조회 API 가 [requirement.md](requirement.md) 밖이라 만들지 않았다. 만들 때 `status` 를 그대로 뿌리면 안 된다.

```
status = 'USED'                      사용함
기간 밖                              만료      -- ISSUED 든 CANCELED 든
그 밖(ISSUED / CANCELED) + 기간 안   사용 가능
```

`V1__init_schema.sql` 의 `member_coupon.status` 주석이 "CANCELED 는 조회 시 앱이 ISSUED 나 EXPIRED 로 해소한다" 로 이미 요구하고 있던 것이다. **기간이 지난 `ISSUED` 도 같은 표현식이 함께 해소한다.**

#### 철회한 쿠폰은 다시 쓸 수 있다

출발 상태가 `ISSUED` 하나가 아니다. 주문 취소로 돌려받은 쿠폰은 **기간이 남았으면 다시 쓸 수 있어야 한다.** `ISSUED` 만 조건에 넣으면 한 번 철회된 쿠폰은 영영 못 쓴다.

`IN ('ISSUED','CANCELED')` 로 묶지 않고 **출발 상태별로 나눠 시도한다.** 한 문장으로 묶으면 무엇에서 출발했는지를 갱신한 뒤에는 알 수 없어 이력의 `from_status` 를 못 채운다. 정상 경로는 첫 번째에서 끝나고, 두 번째는 철회분을 다시 쓸 때만 돈다.

**철회에는 기간을 안 건다.** 주문 취소는 쿠폰 기간이 지난 뒤에도 일어난다. 거기에 기간을 걸면 늦게 취소된 주문이 쿠폰을 영영 못 돌려준다.

#### 0행 갈래가 하나 늘었다

기간을 조건에 넣었으므로 **상태는 쓸 수 있는데 기간이 아닌** 0행이 생긴다. `422 NOT_USABLE_PERIOD` 로 답한다. `INVALID_STATUS_TRANSITION` 과 합치면 회원이 "왜 못 쓰는지" 를 못 듣는다.

**이미 사용됐는지를 기간보다 먼저 본다.** 순서를 뒤집으면 사용한 뒤에 기간이 지난 쿠폰에서 같은 요청의 재시도가 기간 오류를 받는다. 그 요청은 이미 반영된 것이라 성공이어야 한다.

#### 만료 배치는 유효기간을 `coupon` 에서 읽는다

`V30` 이 발급 시점 복사본을 걷어냈다. **발급 행만 봐서는 만료 여부를 알 수 없어** 만료 대상 조회와 갱신이 `coupon` 을 조인한다.

갱신에 조건을 **그대로 다시 거는 것**이 요점이다. 대상을 고른 뒤 갱신하기까지 사이에 사용 요청이 끼어들 수 있고, 그때는 사용 쪽이 이기고 만료가 그 행을 건너뛰어야 한다.

이력도 같은 이유로 `updated_at = :now` 로 되찾는다. 우리가 넘긴 시각을 갱신에 박아 두고 그 값으로 고른다. **상태만 보고 고르면 남이 같은 사이에 만료시킨 행까지 우리 이력으로 들어간다.**

#### 청크 루프가 서비스 밖에 있다

`MemberCouponExpireScheduler` 가 루프를 들고 `expireOverdueChunk()` 를 반복해서 부른다. 서비스 안에서 자기 메서드를 부르면 **자기 호출이라 프록시를 안 거치고 `@Transactional` 이 안 붙는다.** 그러면 상태 갱신과 이력 삽입이 갈라져, 하나만 반영된 채로 끝나는 창이 생긴다.

스케줄러는 `batch` 프로파일에서만 돈다. 발급 전용 인스턴스가 같은 배치를 중복해서 돌리지 않게 하려는 것이다.

#### 검증

**동시성은 단위 시험으로 못 본다.** 조건부 `UPDATE` 가 겹친 요청을 하나로 줄이는 것은 행 락이 하는 일이라, 실제 MySQL 이 있어야 드러난다.

```
단위   0행 네 갈래 / 이력이 상태와 함께 남는다 / 고른 사이에 다 사용됐으면 이력을 안 남긴다
       이미 썼으면 기간이 지났어도 성공으로 답한다
통합   같은 요청 두 번 -> 이력 한 줄
       스무 스레드가 동시에 사용 -> 스무 개가 다 성공으로 답하고 이력은 한 줄
       기간이 지나면 표시가 ISSUED 여도 못 쓴다.  상태도 이력도 안 바뀐다
       철회한 쿠폰을 다시 쓰면 이력의 from_status 가 CANCELED 다
       기간이 지나도 철회는 된다 / 철회하면 used_at 이 비워진다
       남의 발급분은 없는 것과 같다
```

**동시 요청이 다 성공으로 답하는 것이 맞다.** 하나만 이기고 열아홉이 실패하는 것이 아니라, 늦게 온 열아홉은 "이미 그 상태" 라서 조용히 성공한다. 바뀐 것은 한 번뿐이라는 것을 이력 줄 수가 말한다.


### 이벤트 종료를 한 트랜잭션으로 묶었다

끄기와 정리가 배치 둘로 나뉘어 있었다. 하나로 합쳤다.

```
전    closeFinishedEvents  1분.   마감 지난 것을 끈다
      cleanupClosedEvents 10분.  꺼진 지 60초 지난 것의 발급 수를 맞추고 키를 지운다
후    closeFinishedEvents 10분.  마감에서 60초 지난 것을 끄면서 맞추고 지운다
```

#### 대기를 종료 조건으로 옮긴 것이 전부다

기다려야 하는 이유는 하나다. **마감 뒤에도 진행 중인 플러시가 행을 더 넣어서 발급 수가 아직 움직인다.** 그래서 예전에는 끄고 나서 60초를 더 기다렸다가 맞췄다.

기준을 "꺼진 시각" 에서 **"마감 시각"** 으로 옮기면 끄는 시점에 이미 행 수가 멈춰 있다. 그러면 끄기와 맞추기를 **한 트랜잭션**에 넣을 수 있다.

```sql
UPDATE coupon SET is_active = FALSE, updated_at = :now
 WHERE coupon_id = :couponId AND is_active = TRUE
   AND issue_end_at IS NOT NULL AND issue_end_at <= :closableBefore
```

기준으로도 이쪽이 옳다. **"꺼진 시각 + 60초" 는 배치가 언제 끄는지에 따라 흔들린다.** 기다려야 할 것은 마지막 요청이 들어올 수 있었던 시각이고 그것이 `issue_end_at` 이다.

#### 없어진 것 셋

```
보정 장치    "껐는데 발급 수가 안 맞은" 상태가 아예 안 생긴다
             후보 조건의 issued_quantity <> COUNT(*) 가 그 상태를 찾는 장치였다
7일 상한     조건이 is_active = TRUE 라 후보가 자연히 작다.  꺼지면 집합에서 빠진다
             상한을 넘겨 어긋난 채 남던 쿠폰도 함께 사라졌다
countIssued  소진 판정에만 쓰이던 것이라 부르는 곳이 없어졌다
```

#### 소진으로는 못 끈다

관리자 종료의 두 갈래 중 소진 쪽을 뺐다. 이유가 회수에 있다.

**회수는 "소진 상태에서 요청이 왔을 때" 만 돈다.** 스위치를 끄면 요청이 안 들어오고, 요청이 안 들어오면 회수가 안 돌아 **묶인 번호가 그대로 죽는다.** 소진 뒤에도 켜 두는 편이 순번을 덜 잃는다.

지각 요청은 스크립트가 `-1` 로 정상 거절하므로 켜 두는 것이 해롭지 않다. 관리자와 배치가 **마감 시각 하나만 본다.**

#### 키 정리를 빼려다 TTL 의 구멍을 찾았다

TTL 이 이미 `issue_end_at + 1분` 이고 종료가 `issue_end_at + 60초` 라 `clear` 가 겹쳐 보였다. 확인해 보니 **`counter` 하나에만 TTL 이 걸려 있었다.**

```
counter   prepare() 의 SET + applyTtl 의 EXPIREAT        걸려 있다
seq       순번 확보 스크립트의 HSET                       없다
pending   순번 확보 스크립트의 ZADD                       없다
free      returnAndRepair 의 ZADD                        없다
```

[coupon.md](coupon.md) 3장은 처음부터 "넷에 똑같이 건다" 로 적고 있었다. **코드가 설계를 안 따르고 있었다.**

##### 왜 벌어졌나

```
9b72f04 [Docs]  "넷은 함께 살고 함께 죽는다".  수명이 같다는 성질만 적고 누가 거는지는 안 적었다
09c5933 [Feat]  순번 확보 Lua.  seq 와 pending 을 만드는 코드인데 expire 가 한 번도 안 나온다
237ce6f [Feat]  이벤트 준비와 종료.  applyTtl 이 counter 하나에만 건다
```

**TTL 을 거는 자리를 준비 단계 하나로 잡은 것이 원인이다.** `prepare()` 시점에는 `counter` 만 있고, **없는 키에 `EXPIREAT` 은 아무 일도 안 한다.** 그 자리에서는 넷에 걸고 싶어도 못 건다. 설계가 성질만 적고 책임자를 안 정해서, 셋을 만드는 코드가 자기 일인 줄 모른 채 쓰였다.

안 걸린 이유도 셋이다. 종료 배치의 `clear` 가 넷을 다 지워 **정상 경로에서는 키가 실제로 사라진다.** TTL 은 "배치가 안 돌았을 때" 의 그물인데 그 경우를 아무도 시험하지 않았다. 그리고 수명을 보는 시험 셋이 전부 `counter` 만 봤다.

##### 만드는 자리가 물려받게 했다

```lua
local deadline = redis.call('PEXPIRETIME', KEYS[3])
```

스크립트가 `counter` 의 만료 시각을 읽어 자기가 만드는 `seq` 와 `pending` 에 그대로 건다. 반납 경로가 `free` 를 맡는다. **값을 앱이 넘기지 않는 것이 요점이다.** 관리자가 마감을 바꿔 `counter` 의 TTL 이 다시 걸리면 그 뒤에 만들어지는 키가 저절로 새 마감을 따라간다.

스크립트 안이라 왕복이 안 는다. 내부 호출 둘이 늘 뿐이다.

##### 마감 없는 쿠폰은 열지 않는다

같은 자리에서 하나 더 나왔다. `issue_end_at` 이 `NULL` 인 한정 쿠폰이다.

```
applyTtl     issue_end_at 이 null 이면 그냥 돌아간다.  넷 다 수명이 없다
isClosable   issue_end_at != null 을 요구한다.  끌 수 없다
```

**열리는 순간 네 키가 아무도 못 지우는 채로 남는다.** 전에는 관리자가 소진 갈래로 끌 수 있었는데 그 갈래를 없애면서 유일한 출구가 사라졌다.

막는 자리는 여는 쪽이다. 끝나는 시각이 없으면 **끄는 조건도 키의 수명도 걸 기준이 없어서**, 그런 이벤트는 선착순으로 성립하지 않는다. `changeIssuePeriod` 로 마감을 넣은 뒤에는 열린다.

##### 마감 없는 수량 쿠폰은 선착순이 아니다

같은 자리에서 하나 더 나왔다. `issue_end_at` 이 `NULL` 인 수량 쿠폰이다.

```
applyTtl     issue_end_at 이 null 이면 그냥 돌아간다.  넷 다 수명이 없다
isClosable   issue_end_at != null 을 요구한다.  끌 수 없다
```

**열리는 순간 네 키가 아무도 못 지우는 채로 남는다.** 전에는 관리자가 소진 갈래로 끌 수 있었는데 그 갈래를 없애면서 유일한 출구가 사라졌다.

막는 자리를 여는 쪽이 아니라 **선착순의 정의**로 잡았다.

```java
public boolean isLimited() {
    return totalQuantity != null && issueEndAt != null;
}
```

여는 쪽에 검사를 하나 더 두면 발급 경로는 그대로 통과한다. 정의에 넣으면 `open` 도 발급도 같은 판정 하나를 지나므로 **그런 쿠폰에는 Redis 키가 아예 안 생긴다.** 키가 없으면 끌 일도 없다.

수량이 0 초과인 것은 `chk_coupon_quantity` 와 `validateTotalQuantity` 가 이미 보장해서 판정에 안 넣었다.

**`isIssuableAt` 의 널 검사도 함께 걷었다.** `isLimited` 가 마감을 요구하므로 "끝이 없으면 소진까지 연다" 는 갈래가 도달 불가가 되고, 남겨 두면 **없는 규칙을 코드가 말하게 된다.**

##### 그래도 clear 는 남는다

TTL 은 그물이고 주 경로는 여전히 종료 시 `UNLINK` 다. 1만 필드 해시를 마감 1분 뒤까지 들고 있을 이유가 없다. 그래서 Redis 호출이 트랜잭션 안에 남았고, **Redis 가 죽으면 끄기까지 되돌아간다.** 다음 주기가 다시 시도하므로 스스로 낫고, 그 사이 마감 지난 요청은 기간 검사가 이미 막는다.

#### 주기를 10분으로 늘려도 되는 이유

마감 조건에 이미 60초 대기가 들어 있어 그보다 자주 돌 값이 없다. 마감 지난 요청은 `CouponIssueService` 의 기간 검사가 막고, 스위치가 늦게 꺼져서 달라지는 것은 **그동안 회수가 더 돌 수 있다는 것뿐**이라 오히려 순번을 덜 잃는다.

### 정합성 검증 (`CouponConsistencyService`)

[requirement.md](requirement.md) 가 **검증 수단 자체를 구현물로** 요구한다. 10장의 다섯 항목을 그대로 잰다.

```
발급 수와 issued_quantity   카운터가 실제 행 수와 다른가
발급 수와 total_quantity    한정 수량을 넘겼는가
순번의 연속성                MAX(issue_seq) - COUNT(*) 가 곧 구멍 수다
1인 1매                     UNIQUE 가 막지만 결과로도 확인한다
상태와 이력 (R5)             마지막 전이가 현재 상태와 같은가
```

#### 재는 것만 하고 고치지 않는다

요구사항이 **"같은 데이터 기준으로 재실행하면 같은 결과"** 를 요구한다. 검증이 무엇이든 고치면 두 번째 회차가 첫 번째와 다른 답을 낸다. 그래서 리포지터리에 쓰기가 하나도 없고, 서비스는 `readOnly` 다.

**상태도 안 들고 있다.** 중간 결과를 저장해 다음 회차에서 재사용하면 같은 이유로 재실행이 깨진다. 매번 처음부터 전부 훑는다.

#### 이벤트 종료 배치에 붙이지 않았다

붙이는 쪽을 먼저 검토했다. **붙이면 검증이 죽는다.**

```java
couponRepository.syncIssuedQuantity(couponId);   // issued_quantity = COUNT(*)
```

종료 배치가 하는 일이 10장 첫 항목이 대조할 바로 그 값을 덮어쓰는 것이다. 거기 붙은 검증은 **방금 고쳐진 값을 재게 되어 언제나 깨끗하게 나온다.** 보정이 실패한 것을 잡는 게 검증의 값인데 그게 사라진다.

주기도 안 맞는다. 종료 배치는 10분이고 300만 건 전체 스캔은 그 주기로 못 돈다.

**그리고 다섯 항목이 좋은 시점을 공유하지 않는다.**

```
issued_quantity   종료 배치가 돌 기회를 가진 뒤
상태와 이력       만료 배치(04:00) 뒤.  그날 만료분이 반영된 값을 잰다
순번 연속성       진행 중이던 요청이 결판난 뒤
```

**모든 보정 경로가 제 일을 할 기회를 가진 뒤**가 검증의 자리다. 04:30 이 그 조건을 만족한다.

한 쿠폰짜리로 대체할 수도 없다. 요구사항이 **300만 건 전체를 대상으로, 재실행하면 같은 결과**를 요구하는데 이벤트 종료는 쿠폰당 한 번뿐인 사건이라 재실행을 걸 자리가 없다.

#### 한 트랜잭션으로 읽는다

다섯 항목을 나눠 읽으면 그 사이에 들어온 발급이 앞 항목에는 없고 뒤 항목에는 있다. **아무도 안 틀렸는데 어긋남으로 잡힌다.** `REPEATABLE READ` 라 한 트랜잭션 안의 여러 쿼리가 같은 스냅숏을 본다.

#### 어긋남으로 세지 않는 것 둘

```
다 안 나간 수량   이벤트가 안 끝났거나 안 팔린 것이다.  값은 remaining 으로 남긴다
이력 없는 발급분  발급 경로가 이력을 안 남기는 것이 지금의 설계다.  값만 세고 판정은 안 한다
```

두 번째는 **열어 둔 것**이다. 발급 한 건마다 이력을 남기면 선착순 경로의 쓰기가 두 배가 된다. 남길지 말지를 정하기 전에 값부터 재 둔다.

#### 구멍 수가 곧 어긋남인 이유

`issue_seq` 는 쿠폰마다 1부터 1씩 오르고 `uk_mc_coupon_seq` 가 중복을 막는다. 빠짐없이 들어갔다면 `MAX` 와 `COUNT` 가 같다. **하나 빌 때마다 차이가 정확히 1씩 벌어진다.** 300만 건에서 빠진 번호를 일일이 찾는 것과 집계 두 개를 빼는 것은 비용이 다르다.

```
재고 10,000, MAX = 10,000, COUNT = 9,997
-> 소진으로 판정됐는데 실제로 나간 것은 9,997장.  3장은 번호만 태웠다
```

**차가 음수여도 어긋남이다.** 행이 `MAX` 보다 많다는 뜻이라 순번이 중복됐거나 0 이하가 들어간 것이다. 그래서 `> 0` 이 아니라 `!= 0` 을 본다.

#### 검증

**정상 데이터에서 "깨끗하다" 가 나오는 것은 아무것도 증명하지 않는다.** 아무것도 안 보는 검증도 같은 답을 낸다. 그래서 어긋난 데이터를 일부러 만들어 넣는다.

```
단위   무엇을 어긋남으로 셀 것인가.  과소는 아니고 초과는 맞다.  음수 구멍도 어긋남이다
통합   카운터 불일치 / 순번 구멍 / 한정 수량 초과 / 마지막 전이 불일치를 주입해 잡히는지
       두 번 돌려 같은 결과가 나오고 데이터가 안 바뀌는지
       300만 건 전체를 실제로 훑고 끝나는지
```

마지막 것이 중요하다. **상관 서브쿼리로 짜면 거기서 안 끝난다.** 더미데이터를 만들 때 이미 한 번 만난 함정이라 검증 쿼리는 마지막 전이를 한 번에 모아 조인한다.

`chk_coupon_quantity` 가 `issued_quantity <= total_quantity` 를 막고 있어 **카운터는 한정 수량을 못 넘긴다.** 넘길 수 있는 것은 실제 발급 행 수뿐이고, 그것을 DB 가 못 막는 것이 이 항목이 있는 이유다.

#### 더미데이터의 카운터를 맞췄다

`seed-dummy-data.sql` 이 `issued_quantity` 를 0 으로 두고 있었다. 그대로 두면 **더미데이터 자체가 첫 항목에서 어긋난 것으로 잡혀**, 검증이 무엇을 재는 데이터인지 알 수 없다. 적재 뒤에 실제 행 수로 맞춘다. 운영에서 종료 배치가 하는 일을 씨딩이 미리 해 두는 것이다.

#### 알려진 상한

300만 건에서 상태와 이력 대조 한 쿼리가 9초 안팎이고 전역 `socketTimeout` 이 10초다. **데이터가 더 늘면 그 쿼리가 먼저 끊긴다.** 배치 프로필의 `socketTimeout` 을 따로 늘리는 것이 그때의 대응이고, 지금은 상한을 아는 채로 둔다.


### 관리자 API 인가

부하 시험을 준비하다 찾았다. `AdminCouponEventController` 에 권한 애너테이션이 없고, 쿠폰 경로를 잡는 필터 체인도 없었다.

```
SecurityConfig 의 마지막 체인   anyRequest().authenticated()
-> 로그인한 회원 아무나 이벤트를 열고 닫고 발급 시각을 바꿀 수 있었다
```

**이벤트를 여는 것은 Redis 카운터를 세우는 일이다.** 도는 이벤트에 그것을 다시 걸면 카운터가 0 으로 돌아가 선착순이 처음부터 다시 시작한다. 인가 구멍이 곧 재고 파괴 경로였다.

도메인이 자기 경로의 인가를 소유하는 이 저장소의 규약대로 `CouponSecurityConfig` 를 뒀다.

```
/v1/coupons/*/issues      로그인한 회원.  자격 판정은 서비스가 따로 본다
/v1/admin/coupons/**      hasRole("ADMIN").  SUPER_ADMIN 은 RoleHierarchy 가 포함시킨다
```

**시험이 그 구멍을 실제로 잡는지 확인했다.** 설정을 빼고 돌리니 회원 토큰으로 이벤트를 여는 시험과 발급 시각을 바꾸는 시험 둘이 그대로 실패했다. 인가 매트릭스는 도메인에 속한 검사가 아니라 베이스 패키지의 `SecurityAuthorizationIntegrationTest` 에 함께 둔다.

### 부하 시험 (로컬 리허설)

절차와 회차 기록은 [loadtest/README.md](../../loadtest/README.md) 에 있다.

**아래 회차는 타임아웃을 줄이기 전 값으로 돌린 것이다.** 요청 예산 2초, Redis 300ms,
`socketTimeout` 1000ms 였다. 지금 값은 8장 SLO 에서 역산해 다시 잡았으므로, 이 수치를
새 설정의 결과로 읽으면 안 된다. 여기에는 **그 시험이 무엇을 답했고 무엇을 못 답했는지**만 적는다.

#### 답한 것

**재고 1만에 2만 명이 몰려 정확히 1만 장이 나갔다.** 순번이 연속이고 회원 수가 발급 행 수와 같았다.

```
발급행 10,000 / 최대순번 10,000 / 구멍 0 / 회원수 10,000
```

**회수가 실제로 도는 것을 봤다.** 다른 회차에서 구멍이 72개 생겼는데, 번호를 받고 행이 안 들어간 요청들이 `pending` 에 묶인 것이었다. 매핑 없는 회원 100명이 소진 상태에서 두드리자 그대로 풀렸다.

```
pending 73 -> 0 / 발급행 9,928 -> 10,000 / 구멍 72 -> 0
```

3장이 "주기 배치가 필요 없다" 고 한 근거가 이것이다. **회수는 소진 상태에서 요청이 올 때만 돈다.** 트래픽이 끊기면 안 돌고, 다시 오면 그때 풀린다.

**회로가 설계대로 열렸다.** 20,000 VU 회차에서 Redis 호출이 300ms 타임아웃에 걸리자 순번 확보 회로가 열렸고, 요청이 예산 2초를 다 태우고 실패하는 대신 빨리 잘렸다.

#### 숫자로 드러난 대가

```
congested-budget 1,990
```

**예산 2초를 넘겨 503 을 받았지만 그 티켓은 큐에 남아 결국 발급된 요청**이 1,990건이다. 사용자는 실패로 들었는데 쿠폰은 받았다. 9장에서 "반납하지 않는다" 를 고른 대가가 이 숫자다. 반대쪽을 고르면 장애로 못 쓴 번호가 나중에 온 사람에게 넘어가 도착 순서가 뒤집힌다.

#### 못 답한 것

**3장의 "재서 정할 값" 은 이 환경에서 정할 수 없다.** k6 와 JVM 과 MySQL 과 Valkey 가 16GB 한 대에서 CPU 를 나눠 썼다. 20,000 VU 회차의 p95 53초는 앱의 한계가 아니라 부하 발생기와 앱이 같은 코어를 다툰 결과다.

**같은 조건을 두 번 돌렸더니 다르게 무너졌다.** 한 번은 플러시가 못 따라가 `congested-budget` 이 쌓였고, 한 번은 Redis 가 먼저 타임아웃 나서 `congested-seq-unavailable` 만 나왔다. 회차마다 흔들린다는 것 자체가 이 환경의 수치로 값을 정하면 안 된다는 근거다.

#### 준비하며 걸린 것 넷

```
로그 수준       로컬 프로파일이 root DEBUG 에 본문까지 남긴다.  그대로 재면 로깅을 재게 된다
CSV 줄 끝       파이썬 csv 기본값이 CRLF 다.  토큰 뒤 \r 이 헤더를 망가뜨려 톰캣이 400 을 낸다
시계            컨테이너가 UTC 이고 앱이 KST 다.  NOW(6) 로 몇 시간짜리 발급 창을 잡으면 넣자마자 지난 이벤트다
문자셋          mysql 클라이언트에 utf8mb4 를 안 주면 확인 SELECT 의 한글 별칭에서 구문 오류가 난다
```

넷 다 **시험 당일에 만나면 그 회차를 잃는 것들**이라 스크립트와 문서에 박아 뒀다.

### 다음

**2장의 만들 것 목록도, 8장이 요구한 지표도 다 나왔다.** 남은 것은 만드는 일이 아니라 재는 일이다.

```
부하 시험   3장의 "재서 정할 값" 을 순서대로 옮겨 가며 잰다
            큐 상한은 20000 -> 10000 -> 5000 -> 2500 -> 1000
            플러시 스레드는 1 부터 늘리며 큐 길이가 줄어드는지 본다
            부하 발생기를 다른 호스트에 둬야 한다.  로컬 리허설에서 그 이유가 드러났다
```

**실패 갈래별 반납은 안 하기로 정했다.** [coupon.md](coupon.md) 9장이 "안 닿았으면 반납" 으로 적고 있었는데, 그것이 **선착순을 서버가 스스로 깨는 처리**라 문서를 뒤집었다.

```
반납한다   장애로 못 쓴 번호를 나중에 온 사람이 가져간다.  도착 순서가 뒤집힌다
유지한다   그 번호가 먼저 온 사람 것으로 남는다.  안 돌아오면 pending 이 시간으로 회수한다
```

**반납은 "이 사람은 포기했다" 를 근거 없이 즉시 단정하는 것**이고, `pending` 은 기준 시간을 보고 판정한다. 지금 코드가 이미 유지 쪽이라 코드는 안 바뀌었다.

#### 자격 확인 캐시 (`CouponCache`)

[coupon.md](coupon.md) 3장이 발급 창 안에서 다섯 값이 얼어붙는다고 정했다. 그러면 **요청마다 도는 쿠폰 조회 하나를 없앨 수 있다.**

```
로컬 인메모리   왕복이 안 는다.  인스턴스마다 따로 가져도 벌어지는 폭이 TTL 로 묶인다
Redis          왕복이 하나 더 는다.  DB 를 걷어낸 값이 절반만 남는다
```

**앱이 캐시를 자기 JVM 힙에 둔다.** 요청 스레드가 참조 하나만 읽으면 되고 아무 데도 나가지 않는다. 인스턴스마다 사본이 따로 생기지만, 그 값들이 발급 창 안에서 얼어붙으므로 사본끼리 갈리는 순간은 마감이나 소진으로 스위치가 꺼질 때뿐이다.

TTL 은 5초에서 시작한다. **이 값이 곧 앱이 마감을 넘겨 발급을 받아 주는 시간**이고, 종료 절차의 1분 TTL 안에 넉넉히 들어간다.

##### 값을 모니터 안에서 계산하지 않는다

`ConcurrentHashMap` 은 `computeIfAbsent` 나 `compute` 가 도는 동안 **버킷 모니터를 잡는다.** 요청 스레드가 그 안에서 DB 를 기다리면 **가상 스레드가 캐리어를 못 놓고 핀된다**(Java 21).

**이건 라이브러리 선택 문제가 아니다.** 직접 만들든 Caffeine 의 동기 `get(key, loader)` 를 쓰든, 값 계산이 모니터 안에서 돌면 똑같이 핀된다. 로딩 API 를 쓰느냐가 갈림이다.

처음에는 `ConcurrentHashMap` 으로 직접 만들어 `get` 과 `put` 을 나눠 썼다. 핀은 피했지만 **캐시가 빈 순간 여러 요청 스레드가 같이 DB 를 읽는 것**을 대가로 받아들였다.

**Caffeine 의 `AsyncCache` 가 그 대가 없이 둘 다 준다.**

```java
CachedCoupon loaded = cache.get(couponId,
        (id, executor) -> CompletableFuture.supplyAsync(() -> load(id), executor)).join();
```

**맵에 담기는 값이 결과가 아니라 `CompletableFuture` 다.** `ConcurrentHashMap` 이 모니터를 쥐고 있는 동안 하는 일이 future 하나를 만들어 넣는 것뿐이고, 실제 읽기는 그 바깥에서 돈다. 기다리는 요청 스레드도 `join()` 이 `LockSupport.park` 라 캐리어를 반납한다.

```
직접 만든 것   핀 없음.  TTL 마다 여러 스레드가 같이 읽는다
AsyncCache     핀 없음.  먼저 온 하나만 읽고 나머지는 그 future 를 기다린다
```

TTL 5초에 초당 수천이면 그 몰림이 **5초마다, 인스턴스 수만큼** 곱해진다. 없앨 수 있는데 두고 있던 것이라 바꿨다.

**executor 를 따로 준다.** Caffeine 의 기본값이 공용 `ForkJoinPool` 인데, 그 풀은 CPU 작업 기준으로 크기가 잡혀 있어 **JDBC 블로킹이 거기서 막히면 다른 작업까지 굶는다.** 가상 스레드 실행기를 준다.

크기 기반 축출과 적중률 통계(`recordStats`)도 함께 딸려 온다.

**순서를 지켰다.** 얼어붙는다는 전제는 관리자 API 가 그렇게 막을 때만 참이라, 그 규칙이 코드로 선 뒤에 얹었다.

##### 켜진 쿠폰만 담는다

만들면서 좁힌 것이다. **얼어붙는다는 보장이 켜져 있는 동안에만 성립한다.**

```
켜진 값을 담는다   마감으로 꺼진 뒤 TTL 만큼 더 받는다.  수량은 순번이 막고 몇 건이 늦게 나갈 뿐이다
꺼진 값을 담는다   관리자가 여는 순간부터 TTL 만큼 "지금은 발급할 수 없다" 로 답한다
```

**두 방향의 대가가 다르다.** 뒤쪽은 이벤트가 열리는 바로 그 순간, 사람이 가장 많이 몰릴 때 정당한 요청을 거절한다. 이벤트 전에도 사람들이 새로고침하므로 캐시는 그때 이미 `false` 로 데워져 있다.

그래서 **켜진 쿠폰만 담고, 꺼진 쿠폰과 없는 쿠폰은 매번 DB 를 읽는다.** 이벤트 전 트래픽은 그만큼 DB 를 치지만, 그 요청들은 어차피 422 로 끝나 Redis 도 큐도 안 거친다.

덤으로 항목 수가 **도는 이벤트 수만큼**으로 묶인다. 없는 쿠폰 id 를 훑는 요청이 캐시를 부풀릴 수 없다.

##### 판정식을 한 군데만 둔다

`isIssuableAt` 과 `isTargetGrade` 를 엔티티에서 `CachedCoupon` 으로 옮겼다. 양쪽에 같은 식을 두면 한쪽만 고쳤을 때 **캐시가 켜졌을 때와 꺼졌을 때 답이 달라진다.**

엔티티에는 `isLimited()` 만 남았다. 관리자 API 가 그것을 쓴다.

##### 관리자 동작 뒤에 자기 사본을 비운다

`open`, `close`, `changeIssuePeriod` 가 끝나면 그 인스턴스의 사본을 지운다. **다른 인스턴스는 여전히 TTL 을 기다린다.** 그것을 없애려면 인스턴스 간 통지가 필요한데, TTL 이 이미 그 폭을 묶고 있어 값을 안 한다.

**[coupon.md](coupon.md) 3장은 맞췄다.** 스크립트에 `TIME` 과 확정 표시 가드를 넣고, 회수를 트리거와 조건으로 나눠 쓰고, 실패 표에 순번을 견주는 갈래를 더했다.

#### `rewriteBatchedStatements` 는 전역에 넣었다

이것이 없으면 JDBC 배치가 문장 하나로 안 합쳐지고 건별 왕복이 그대로 남는다. 전용 프로파일과 견줘 전역으로 정했다.

**영향 범위가 0 이다.** `hibernate.jdbc.batch_size` 가 없어 Hibernate 는 배치를 안 하고, 그 밖에 `batchUpdate` 를 쓰는 곳도 없다. 지금 이 설정이 건드리는 코드는 플러시 하나뿐이다.

**결정적인 것은 그 다음이다.** 전용 프로파일에 넣으면 테스트와 운영이 다른 경로를 탄다.

```
통합 테스트   프로파일 없음 -> 건별 INSERT.  일부만 들어가고 실패할 수 있다
운영          프로파일 있음 -> 한 문장.      전부 들어가거나 전부 안 들어간다
```

실패 처리 분기가 두 모양에서 다르게 도는데, **테스트가 검증하는 쪽이 운영에서 안 도는 쪽이 된다.** 성능 설정 하나 때문에 감수할 값이 아니다.

**`IntegrationTestSupport` 에도 같은 파라미터를 걸었다.** 접속 URL 을 컨테이너가 만들기 때문에 `application.yml` 만 고치면 테스트에는 안 걸린다. 그러면 위 근거가 그대로 무너진다.
