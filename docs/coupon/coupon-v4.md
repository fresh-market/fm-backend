# v4: Redis 순번 + 인스턴스별 큐 + 가상 스레드

**채택안이다.** 버전과 무관하게 고정된 것은 [coupon.md](coupon.md) 에 있고, 여기에는 **v4 가
정하고 만든 것**만 적는다.

```
1  자격 확인   기간, is_active, 대상 등급
2  순번 확보   Redis Lua 한 번.  키 넷을 한 번에 다룬다
3  발급 기록   인스턴스별 큐 -> 플러시 스레드 -> 벌크 INSERT
4  응답        요청 스레드가 future 로 받는다
```

**v4 는 DDL 을 안 늘린다.** `member_coupon` 이 이미 R1 에서 R4 까지 지킨다.

---

## 1. 컨트롤러를 비동기로 안 만든다

**`CompletableFuture` 를 컨트롤러가 반환하는 안과 견줬고, 끊김 감지가 필요 없어져 그쪽
이점이 사라졌다.**

[coupon.md](coupon.md) 3장이 이미 정했다. 클라이언트가 끊었는지 타임아웃인지 앱이 급사했는지
**원인은 달라도 결과가 같아서 회수가 시간으로 판정한다.** 그러면 누가 왜 사라졌는지 알아낼
이유가 없고, 남는 것은 스레드 점유뿐인데 **그건 가상 스레드가 푼다.**

**`CompletableFuture` 는 큐와 플러시 스레드 사이의 전달 수단으로만 쓴다.** `get()` 이
`LockSupport.park` 라 가상 스레드에서 pinning 이 안 생긴다.

---

## 2. 가상 스레드가 자연 상한을 없앤다

**딸려 오는 것이 둘이고, 둘 다 대가 쪽이다.**

**큐 상한이 사라진다.** 플랫폼 스레드에서는 요청 스레드가 큐에 든 만큼 잠겨 있어 **톰캣
스레드 수가 큐 길이의 자연 상한**이었다. 가상 스레드는 그 상한이 없어 **큐가 메모리까지
자란다.** 앱이 급사했을 때 잃는 건수의 상한도 함께 사라지므로 **앱이 명시적으로 걸어야 한다.**

**꼬리 지연이 늘 수 있다.** 스레드를 값싸게 만들 수 있다는 것이 무한정 받아도 된다는 뜻은
아니다.

```
받는 것은 싸다   스레드 생성 비용이 거의 없어 요청을 다 받아들인다
처리는 안 싸다   플러시 처리 능력과 DB 커밋은 그대로다
                -> 대기가 큐와 커넥션 풀로 밀린다
```

**플랫폼 스레드였다면 거절되어 실패로 잡혔을 것이 가상 스레드에서는 받아들여진 채 오래
기다리는 모양이 된다.** 실패가 지연으로 바뀌는 것이라 **지표에서 더 늦게 드러난다.**

**그래서 큐 최대 길이와 p99 를 함께 봐야 한다.**

---

## 3. 큐 상한만 성격이 다르다

**나머지 설정은 성능을 위한 값이지만 이것은 앱이 급사했을 때 잃는 건수의 상한이기도 하다.**

```
크게 잡으면   꼬리 지연과 손실이 같이 는다
작게 잡으면   멀쩡히 받을 수 있는 요청을 거절한다
```

**넘칠 때의 동작은 이미 정해진 것에서 따라온다.** 앱이 거절하고, 재고가 없는 것이 아니므로
혼잡으로 답하며, **큐 자리를 먼저 보고 나서 Redis 를 부른다.** 순번을 받은 뒤에 못 넣으면
그 번호를 반납해야 하는데, 순서를 이렇게 두면 반납할 일이 안 생긴다.

**시작값과 측정 결과는 [coupon-load-rounds.md](coupon-load-rounds.md) 에 있다.**

## 4. 코드에서 안 읽히는 판단들

### 엔티티에 상태를 바꾸는 메서드를 안 둔다

**`use()` 나 `expire()` 를 두지 않았다.** R5 를 조건부 `UPDATE` 로 지키기로 했기 때문이다.
메서드를 두면 **읽고 바꾸고 저장하는 경로가 열리고 그 사이에 남이 끼어든다.** 메서드를 아예
안 두면 그 경로가 안 생긴다.

**스키마가 진실이고 엔티티가 거기 맞춘다.** `ddl-auto: validate` 라 엔티티가 테이블을 만들지
않는다. 엔티티의 검증 메서드는 새 규칙이 아니라 **DB 의 `CHECK` 를 앱 쪽에서 미리 걸러 주는
것**이다.

### 서비스가 트랜잭션을 안 연다

**요청 스레드가 큐에서 자는 동안 트랜잭션을 쥐고 있으면 안 된다.** 동시 요청 수만큼 커넥션이
잡혀 커넥션 예산을 그대로 먹고, **정작 쓰려는 플러시 스레드가 커넥션을 못 얻어 큐에 모인
배치 전체가 함께 멈춘다.**

### 회로를 둘로 나눈다

```
couponSeq    Redis 실패를 센다
couponWrite  DB 쓰기 실패를 센다
둘 다 막는 대상은 순번 확보이고, 플러시는 안 막는다
```

**플러시를 막으면 이미 큐에 들어간 요청까지 버리게 된다.**

**느린 것도 세야 한다.** Redis 가 완전히 죽는 것보다 느려지는 쪽이 흔한데, 그때 예외가 안
나면 회로가 안 열리고 **요청 스레드들이 전부 거기서 기다리며 요청 예산을 태운다.**

**DB 회로가 중복 키를 세면 안 된다.** 재시도와 매핑 유실로 중복이 꾸준히 나오는 것이 이
설계의 정상 동작이라, 그것을 세면 **이벤트가 멀쩡할 때 회로가 열린다.**

**반열림 허가를 요청 스레드가 쓰면 안 된다.** 요청 스레드가 허가를 소비하면 **정작 플러시가
DB 를 시험해 볼 기회가 없어진다.**

### DB 실패를 두 갈래로 가른다

**잠시 뒤에 다시 하면 될 실패만 혼잡으로 바꾼다.** SQL 문법 오류처럼 사람이 고쳐야 하는
것까지 "잠시 후 다시" 로 덮으면 **그 버그가 사용자의 재시도에 묻혀 배포 뒤에도 한참 안
드러난다.**

**스프링의 `TransientDataAccessException` 만으로는 못 가른다.** 커넥션을 못 얻은 실패를
스프링은 비일시적으로 분류하는데, **Multi-AZ 페일오버는 시간이 지나면 끝나므로 일시적이다.**

### 지표를 기동 때 다 등록한다

**처음 그 경로가 나올 때 만들면 "혼잡이 0 건" 과 "혼잡을 안 센다" 가 대시보드에서 같아
보인다.** 그래서 앱이 기동 때 모든 결과 종류의 계량기를 0 으로 세워 둔다.

**상태 코드로는 소진과 혼잡까지만 갈린다.** 혼잡 안에 순번 충돌과 큐 포화와 DB 실패와 예산
초과가 다 들어 있어, 앱이 사유별로 따로 센다.

### 이벤트 종료를 한 트랜잭션으로 묶는다

**대기를 종료 조건에 넣은 것이 이 절차의 요점이다.** 끄는 시점에 발급 행 수가 이미 안
움직이므로 스위치와 정산과 키 삭제를 함께 묶을 수 있다. **나누면 껐는데 발급 수가 안 맞은
상태가 존재하고, 그것을 나중에 찾아 고치는 장치가 따로 필요해진다.**

**시각은 앱이 넘긴다.** `NOW()` 를 쓰면 MySQL 서버의 시간대가 판정에 끼어든다. **순번 확보
스크립트와 반대 선택이다.** 그쪽은 인스턴스 A 가 쓴 점수를 B 가 재므로 Redis 시계여야 했고,
여기는 같은 앱이 쓴 값을 같은 앱이 견주므로 앱 시계가 맞다.

### 정합성 검증은 모든 보정이 끝난 뒤에 돈다

**회수와 종료 배치가 제 일을 할 기회를 가진 뒤**가 검증의 자리다. 먼저 돌면 아직 보정되지
않은 것을 어긋남으로 센다.

**검증이 상태를 들고 있으면 안 된다.** 중간 결과를 저장해 다음 회차에서 재사용하면 재실행이
깨진다. **매번 처음부터 전부 훑는다.**

## 5. 만들면서 고친 것

**이 절은 같은 실수를 다시 하지 않으려고 남긴다.**

### 설정 키를 틀려도 앱은 멀쩡히 뜬다

**키 이름을 하나 틀리면 스프링이 조용히 기본값을 쓴다.** 그러면 부하 시험에서 값을 바꿔도
아무 일이 안 일어나고 왜 안 바뀌는지 한참 찾게 된다.

**그래서 프로파일 바인딩을 시험으로 못 박았다.** 값이 실제로 그 자리에 꽂히는지를 확인한다.

### `connection-timeout` 은 250ms 아래로 못 내린다

**HikariCP 가 하한을 강제하고 그보다 작은 값은 경고와 함께 조용히 덮어쓴다.** 한때 그보다
작게 적어 두고 계층 합을 계산했는데 **적힌 값과 도는 값이 달라 그 표 전체가 거짓이었다.**

### TTL 을 거는 자리가 하나면 세 키가 빠진다

**준비 단계에는 `counter` 만 있고, 없는 키에 `EXPIREAT` 은 아무 일도 안 한다.** 그래서
나머지 셋은 만들어지는 자리에서 `counter` 의 만료 시각을 물려받게 고쳤다.

**앱이 값을 다시 넘기지 않고 `counter` 에서 읽어 물려주므로**, 관리자가 마감을 바꾸면 그 뒤에
만들어지는 키가 저절로 새 마감을 따라간다.

### 관리자가 소진으로 끄는 길을 없앴더니 출구가 사라졌다

**마감이 없는 쿠폰은 열리는 순간 네 키가 아무도 못 지우는 채로 남는다.** 전에는 관리자가
소진으로 끌 수 있었는데 그 길을 없애면서 유일한 출구가 사라졌다.

**그래서 선착순 판정이 마감을 요구하게 했다.** 마감이 없으면 여는 것도 발급하는 것도 그
앞에서 막히고, **그런 쿠폰에는 키가 아예 안 생겨 끌 일도 없다.**

### 회로 지표가 없어 여덟 회차를 헤맸다

**회로를 레지스트리 밖에서 만들어 Micrometer 가 그것을 못 봤다.** 회로가 열려도 지표에 아무
흔적이 없어, 순번 확보 실패가 회로 탓인지 Redis 탓인지 구분할 수 없었다.

**설정을 스타터로 옮기자 지표가 저절로 붙었다.**
