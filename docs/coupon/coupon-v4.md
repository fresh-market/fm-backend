# v4: Redis 순번 + 인스턴스별 큐 + 가상 스레드

`feat/coupon-issue-v4` 브랜치의 작업 기록이다. 버전과 무관하게 고정된 것은 [coupon.md](coupon.md) 에 있고, 여기에는 **v4 에서만 정하고 만드는 것**을 적는다.

**v4 가 채택안이다.** v1~v3 을 거치지 않고 바로 만든다. 사다리는 비교를 위한 것이고, 실제로 쓸 것은 이 형태다.

---

## 1. 무엇을 만드나

```
1  자격 확인      기간, is_active, 대상 등급
2  순번 확보      Redis Lua 한 번
3  발급 기록      인스턴스별 큐 -> 플러시 스레드 -> Bulk INSERT
4  응답           요청 스레드가 future 로 받는다
```

**DDL 을 늘리지 않는다.** 현재 `member_coupon` 이 R1~R4 를 이미 지킨다. `V30` 이 안 쓰는 스냅샷 컬럼을 걷는 것뿐이다.

---

## 2. 만들 것

```
Lua 스크립트        순번 확보.  seq, free, counter, pending 네 키를 한 번에 다룬다
큐와 플러시 스레드   배치 윈도우 또는 배치 크기에서 플러시
Bulk INSERT         JDBC batch.  한 문장으로 압축된다
컨트롤러            CompletableFuture 를 반환한다.  클라 끊김을 감지하려면 비동기여야 한다
서킷 브레이커        Redis 호출에만 건다.  플러시 스레드는 회로 밖이다
이벤트 준비 절차     카운터 0 초기화, 네 키에 EXPIREAT
종료 배치           is_active 끄기, issued_quantity 맞추기, 네 키 UNLINK
JPA 엔티티          Coupon, MemberCoupon.  ddl-auto: validate 라 스키마와 정확히 맞아야 한다
```

---

## 3. 재서 정할 값

`coupon.md` 8장이 조건으로 잡은 것들이다. **시작값을 박아 두고 부하 시험에서 옮긴다.**

```
배치 윈도우와 배치 크기   20ms / 500 에서 시작.  1ms~100ms 를 훑는다
플러시 스레드 수          1 부터 N 까지 늘려가며 본다
요청 예산                 안쪽 합보다 커야 한다.  계층이 역전되면 안 된다
Hikari 풀 크기            5장 예산에서 역산
connection-timeout        앱 기본 3초보다 짧게
pending 회수 기준 시간     요청 예산보다 넉넉하게
```
