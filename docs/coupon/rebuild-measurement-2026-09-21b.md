# 캐시 유실을 직접 주입해 본 회차 (2026-09-21)

**앞 회차([rebuild-measurement-2026-09-21.md](rebuild-measurement-2026-09-21.md))가 만든 것은 전손이었다.** 키가 통째로 사라지는 모양인데, Multi-AZ 복제에서 가장 안 일어난다. 실제 페일오버에서 확률이 높은 것은 복제가 밀린 채 승격돼 `counter` 가 뒤로 가는 쪽이다. 그 모양을 `fm-infra` 의 `loadtest-fault.sh lost-tail` 로 만들어 돌렸다.

```
AWS 실측   20,000 VU / ramp 60초 / 재고 10,000장 / 전용 인스턴스 3대
앱         fm-backend main 24380f8a
```

## 2. counter 가 뒤로 가면 재건이 아니라 스키마가 막는다

회차 1이 이것을 보려고 돈 회차다. 램프 중 `counter` 가 2,791 일 때 200건을 유실시켰다.

```
SEQ_TAKEN                 67 + 67 + 66 = 200     주입량과 정확히 같다
REBUILD                   0                      세 대 전부
COUPON_SEQ_TAKEN_REPAIRED 돎                     뒷정리가 주인을 되살렸다
congested-seq-taken       200                    지표가 로그와 맞는다
```

**재건 로그가 한 줄도 없다.** `coupon-issue-seq.lua` 는 `counter` 가 없을 때만 `-2` 를 내고 값이 작아진 것은 못 본다([재건 문서](redis-promotion-rebuild.md) 7장). 그래서 이미 DB 에 행이 있는 번호가 다시 나갔고, 그것을 `uk_mc_coupon_seq` 가 막았다.

**막혔는데도 아무것도 안 잃었다.** 재고 10,000장이 정확히 다 나갔고 결번이 0 이다. 번호를 빼앗긴 200명은 `SEQ_TAKEN` 응답을 받고 재시도해 다시 받았다.

```
20,000 VU / 1,162,645 요청 / 실패 0.00%
p90 68.99ms   p95 123.70ms   p99 321.77ms   max 750.30ms
```

**장애를 주입한 회차인데 p99 가 321.77ms 다.** SLO 1초 안이다.

## 3. 기여가 DB 읽기 뒤에 있다

회차 2와 3이 `lagMillis` 분포를 얻으려고 돈 회차인데 **또 표본이 0건이었다.** 이번에는 이유를 찾았다.

`CouponSeqRebuilder.rebuildIfLost` 가 제일 먼저 하는 일이 DB 읽기다.

```java
Coupon coupon = couponRepository.findById(couponId).orElse(null);   // 96행
...
if (!acquireLock(couponId, lock)) {
    contributor.contribute(couponId);                               // 107행
    return;
}
```

**DB 가 막힌 인스턴스는 96행에서 터져 107행에 못 온다.** 기여는 Redis 와 자기 큐만 건드리는데도 그렇다. 회차 2에서 비주도자 두 대의 큐에 825건과 820건이 쌓여 있었는데 한 건도 안 올라갔다.

| 인스턴스 | 재건 시작 | 재건 완료 | 재건 실패 | 기여 | 기여 건너뜀 |
|---|---:|---:|---:|---:|---:|
| 주도자 | 1 | 1 | 5 | 0 | 0 |
| 비주도자 A | 0 | 0 | 16 | 0 | 0 |
| 비주도자 B | 0 | 0 | 22 | 0 | 0 |

비주도자는 `재건 시작` 이 0 이다. 락을 다투기 전에 죽었다는 뜻이다. 실패 로그의 스택에서 앱 프레임이 `findById` 하나인 것으로 확인했다. 회차 3에서도 같은 모양이 나왔다(실패 30건과 38건, 기여 0건).

### 왜 이것이 `lagMillis` 를 영영 0 으로 두나

**기여할 수 있는 인스턴스는 DB 가 살아 있다는 뜻이고, 그러면 큐가 20밀리초 창에 빠져 비어 있다.** 큐가 두꺼우려면 플러시가 막혀야 하는데, 플러시를 막는 것은 DB 장애이고, 그 장애가 기여를 함께 막는다. **두 조건이 서로를 배제한다.**

회차 2에서 큐 최댓값이 1,140 까지 올라간 것은 쟀다(평상시 92). 쌓이기는 쌓였고 올라가지 못했을 뿐이다.

### 이것이 위험한 이유

`CouponSeqContributor` 가 적어 둔 그대로다. 큐는 Redis 가 죽어도 살아 있는 유일한 미확정 기록이고, 안 올리면 재건이 그 번호들을 아무도 안 쥔 것으로 보고 남에게 다시 내준다. **DB 장애가 겹치면 그 보호가 통째로 빠진다.**

다만 회차 2와 3에서 그 때문에 초과 발급이나 1인 2매가 나지는 않았다. 스키마가 막았고, 잃은 것은 결번뿐이다.

## 4. 부하 상자가 20,000 VU 를 간신히 감당한다

회차 2와 3의 k6 가 87% 부근에서 **OOM 으로 죽었다.** 상자가 `m7i-flex.large`(8GB)인데 20,000 VU 가 7.4GB 를 쓴다.

```
Out of memory: Killed process 2839 (k6) total-vm:8803444kB, anon-rss:7464780kB
```

회차 1은 살아남았다. **오류 경로가 늘면 못 버틴다.** 회차 2와 3은 DB 를 막아 실패 응답이 많았다.

그래서 **회차 2와 3의 결번은 그대로 못 읽는다.** HOLD 30초가 통째로 날아가 회수가 돌 시간이 없었다. 회차 3에서 장애를 18초 만에 푼 덕에 결번이 1,050 에서 836 으로 줄었는데, 그 차이가 곧 시간 부족분이다.

## 5. 다음에 할 것

1. **기여를 DB 읽기 앞으로 옮길지 정한다.** 96행의 `findById` 는 "관리자가 아직 안 열었으면 카운터가 없는 것이 정상" 을 가리는 용도다. 기여는 그 판정을 안 기다려도 된다
2. `counter >= MAX(issue_seq)` 불변식을 정합성 검증에 넣는다([재건 문서](redis-promotion-rebuild.md) 7장). 회차 1의 어긋남을 지금은 아무것도 안 잡는다
3. 부하 상자를 메모리가 큰 타입으로 올리거나 VU 를 나눠 돌린다
4. `lagMillis` 는 위 1번을 하기 전에는 못 잰다
