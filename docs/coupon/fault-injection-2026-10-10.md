쿠폰         회차마다 번호를 바꿨다 (900009 ~ 900013).  근거는 5장이다
대시보드     docs/coupon/rounds-2026-10-10/

## 3. 승격 경로 재건의 소요

**팀이 재건 소요를 이번에 처음 잰 것은 아니다.** 2026-09-23 에 204밀리초를, 2026-10-01 에
3,458밀리초를 쟀다. **이번에 처음인 것은 캐시 페일오버로 걸린 재건을 잰 것**이다.

### 3.1 N-2 캐시 페일오버

```
REBUILT couponId=900010 issued=5792 queued=67 maxSeq=5859 freed=0
        rebuildMillis=716  contributeMillis=57  waitMillis=51  readWriteMillis=607

REBUILT couponId=900010 issued=5784 queued=22 maxSeq=5784 freed=-22
        rebuildMillis=244  contributeMillis=69  waitMillis=2   readWriteMillis=172
```

| 구간 | 첫째 | 둘째 |
|---|---:|---:|
| 올릴 것을 올리기 | 57 | 69 |
| 남의 것을 기다리기 | 51 | 2 |
| 읽고 쓰기 | 607 | 172 |
| **문을 닫아 둔 시간** | **716** | **244** |

**기여 대기가 51밀리초와 2밀리초다.** 조기 종료가 제대로 들었다. 2026-10-01 과 J-5 에서
천장 3초를 태우던 것이 사라졌고, 그것이 명부 세기를 재건 통로로 돌린 결과다.

**정지 시간의 주된 항목이 읽고 쓰기로 바뀌었다.** 607밀리초와 172밀리초다. 이 항목은 결번
수에 비례하므로 회차마다 달라진다.

### 3.2 O-1 순번 키 유실

```
REBUILT couponId=900013 issued=9995 queued=0 maxSeq=9995 freed=0
        rebuildMillis=327  contributeMillis=8  waitMillis=107  readWriteMillis=210
```

**327밀리초다.** 부재 경로라 카운터가 아예 없는 상태에서 세운 것이고, 승격 경로보다 가볍다.

## 4. 재건이 스스로 카운터를 뒤로 민 것

**N-2 에서 재건이 같은 쿠폰에 두 번 돌았고 둘째가 첫째보다 낮은 값으로 문을 열었다.**

```
첫째   maxSeq=5859 로 문을 열었다
둘째   maxSeq=5784 로 문을 열었다    75 만큼 뒤로 갔다
```

**이것은 설계가 금지한 것이다.** `CouponSeqRebuildTrigger.measureBehind` 의 Javadoc 이
불변식을 이렇게 적어 두었다.

```
counter >= 이 배치의 최대 순번      재건이 살아 있는 티켓보다 낮게 문을 열면 깨진다
counter >= 여태 본 최대 순번        복제가 밀린 채 승격돼 카운터가 뒤로 가면 깨진다
```

**첫 줄이 정확히 이 경우다.** 재건이 고치려는 증상을 재건이 만들었다.

### 4.1 왜 두 번 도나

**막는 장치가 셋 다 이 경우를 안 잡는다.**

| 장치 | 왜 안 잡나 |
|---|---|
| 재건 락 | 동시 실행만 막는다. 첫 재건이 풀면 다음 인스턴스가 또 주도자가 된다 |
| `reprepared()` | 카운터가 `0` 일 때만 건너뛴다. `5859` 는 0 이 아니라 통과한다 |
| 재연결 감시 | 인스턴스마다 독립으로 띄운다. 3대면 최대 3번 순차로 돈다 |

**부하 중에는 DB 가 계속 자라므로 나중 재건이 더 이른 스냅샷을 읽을 수 있다.** `issued` 가
5,792 에서 5,784 로 줄어든 것이 그 증거다.

### 4.2 정합성이 깨지지 않은 이유는 다른 데 있음

**DB 제약이 받아냈다.** 카운터가 뒤로 가도 `seq` 해시에 확정분이 남아 있어 중복 번호가
`uk_mc_coupon_seq` 에 걸리고, 그 뒤 발급이 이어져 카운터가 다시 올라갔다.

**최후 방어선이 받아낸 것이고 설계가 지켜진 것이 아니다.** 부하가 끝나는 순간에 둘째 재건이
돌면 카운터가 낮은 채로 남고, 그다음 이벤트나 회수가 그 값을 믿는다.

### 4.3 고친 방법

**두 번 도는 것을 막지 않고 낮은 값으로 덮지 않게 했다.** 재연결이 인스턴스마다 오는 것은
정상이고, 카운터가 단조 증가하면 여러 번 돌아도 해롭지 않다.

```
전    counter = maxSeq                  무조건 덮는다
후    counter = max(counter, maxSeq)     coupon-open-gate.lua 가 원자적으로 한다
```

**비교와 쓰기를 스크립트 하나에 담는다.** 읽고 나서 쓰면 그 사이에 남의 재건이나 발급이
끼어들어 같은 문제가 난다.

**낮게 열려던 시도를 로그로 남긴다.** `COUPON_SEQ_GATE_KEPT_HIGHER couponId= mine= kept=` 다.

### 4.4 로그의 freed 가 음수로 나온 것

```
REBUILT ... issued=5784 queued=22 maxSeq=5784 freed=-22
```

**`freed` 는 `maxSeq - issued - queued` 산술이고 실제 되살린 번호 수가 아니다.** 같은 회원이
DB 행과 큐 티켓을 동시에 가지면 음수가 된다. `writeFree` 에 넘기는 리스트는 `1..maxSeq` 중
아무도 안 쥔 번호라 음수가 될 수 없다. **로그가 보여 주는 수와 실제로 되살린 수가 다르다.**

## 5. 회차마다 쿠폰을 바꾸면 뒤처짐이 사라짐

**같은 쿠폰을 거듭 쓰면 장애가 없는 회차에도 뒤처짐이 쏟아졌다.** 2026-10-10 J-3 에서
1,130건이었고 원인은 `budget-breakdown-2026-10-10.md` 6장에 있다.

| 회차 | 쿠폰 | 장애 | 뒤처짐 표본 |
|---|---|---|---:|
| J-3 | 900001 (재사용) | 없음 | **1,130** |
| L-2 | 900006 (새 번호) | 없음 | **0** |
| N-1 | 900009 | 서버 종료 | **0** |
| N-2 | 900010 | 캐시 페일오버 | **2** |
| O-1 | 900013 | 순번 키 유실 | **0** |

**페일오버 회차에서도 2건이다.** 즉 앞서 본 천 단위는 전부 시험 환경이 만든 오탐이었다.

### 5.1 그것이 만든 부작용

**회차마다 번호를 바꾸니 앞 회차 쿠폰이 열린 채로 쌓였다.** `reset.sql` 이 그 회차 쿠폰
하나만 내렸기 때문이다. 재연결 감시는 `findOpenLimitedEvents()` 로 **열린 이벤트를 모두**
찾으므로, 재연결 한 번에 재건이 쌓인 쿠폰 수만큼 떴다.

2026-10-10 L-3 에서 본 쿠폰이 900007 인데 재건이 900001 부터 900006 까지 다섯 개에 떴고,
재시도 20건과 실패 10건을 내는 동안 플러시가 반복 멈춰 명부가 1명으로 밀렸다. **결번 6 이
그래서 났다.**

**`reset.sql` 이 `coupon_id >= 900000` 전체를 내리게 고쳤다** (`0c98954c`). 그 뒤 M-1 에서
재건이 본 쿠폰 하나에만 떴고 재시도와 실패가 0 이 되었으며 결번도 0 으로 돌아왔다.

## 6. 복합 장애를 못 건 이유

**N-3 와 N-4 에서 캐시 페일오버가 거부됐다. 둘 다 서버 종료만 걸렸다.**

```
TestFailoverNotAvailableFault: Test failover already in progress
```

**사유는 24시간 한도다.** 그 노드그룹에 24시간 내 `test-failover` 를 8회 호출했고 한도는
5회다. AWS 가 메시지를 "진행 중" 으로 주는데, 15:26:30 에 완료 이벤트가 찍힌 뒤에도 거부가
이어졌으므로 진행 중이 사유가 아니다.

**`ReplicationGroups[0].Status` 로는 못 가린다.** 거부 당시 `available` 이었다. 가리려면
`describe-events` 에서 `Test Failover API called` 를 세야 한다.

**이번에는 거부가 로그에 남았다.** 2026-10-02 의 G-3 는 같은 거부를 조용히 삼켜 "복합 장애"
로 기록됐는데, fm-infra `cbde01d` 가 사유를 띄우게 고친 덕에 이번에는 반쪽 주입을 그대로
기록하지 않았다.

**N-3 와 N-4 를 복합으로 읽으면 안 된다.** 서버 종료만 걸린 회차이고, 그래서 N-1 과 같은
조건이 세 번 돈 셈이 되었다.

### 6.1 그 반복이 준 값

| 회차 | 장애 | p99 | 결번 |
|---|---|---:|---:|
| N-1 | 서버 1대 종료 | 0.276초 | 0 |
| N-3 | 서버 1대 종료 | 0.342초 | 0 |
| N-4 | 서버 1대 종료 | 0.182초 | 0 |

**같은 조건에서 p99 가 0.182 에서 0.342초로 1.9배 흩어진다.** 단일 회차 p99 를 비교에 쓰지
말라는 기존 결론과 같은 방향이고, **결번은 세 번 모두 0 이다.**

## 7. 거절의 모양이 장애마다 다름

| 지표 | N-1 서버 종료 | N-2 캐시 페일오버 |
|---|---:|---:|
| 혼잡 비율 | 32.64% | **69.91%** |
| 게이트웨이 실패 | **12,420** | 7,723 |
| 포기 | 1,917 | **6,999** |
| 소진 응답 | **8,032** | 545 |
| 예상 못 한 응답 | 0 | 0 |

**서버가 죽으면 그 대로 가던 요청이 게이트웨이 실패로 끊긴다.** ALB 가 아직 그 대상을
빼지 못한 동안의 요청이다.

**캐시가 페일오버하면 전 인스턴스가 함께 느려져 혼잡으로 돌려보낸다.** 그래서 혼잡이 70% 에
닿고 포기가 늘지만, 게이트웨이 실패는 오히려 적다. 서버가 다 살아 있기 때문이다.

**N-1 의 소진 응답이 8,032 로 큰 것은 재고가 빨리 바닥났기 때문이다.** 한 대가 죽어도 남은
두 대가 재고를 다 내보냈고, 그 뒤에 온 요청이 소진을 받았다.

## 9. 팀이 못 본 것

**복합 장애(서버 종료 + 캐시 페일오버)를 못 걸었다.** 페일오버 한도가 풀리는 2026-10-11
09:46 UTC 이후에 다시 걸어야 한다.

**낮은 값으로 문을 열려는 시도가 실제로 막히는 것을 못 봤다.** O-1 에서 재건이 한 번만 돌아
`GATE_KEPT_HIGHER` 가 뜨지 않았다. 그 상황은 재연결이 인스턴스마다 올 때 생기는데 페일오버
한도에 막혀 재현하지 못했다. 고침은 회귀 시험 둘로만 고정되어 있다.

**Lua 로직을 단위 시험으로 보지 못했다.** 실제 Redis 를 띄우는 시험이 이 저장소에 없어
`coupon-open-gate.lua` 의 비교 로직은 회차로만 확인했다.

**N-2 의 재건 둘 중 어느 것이 최종 카운터를 남겼는지 가리지 못했다.** 로그가 둘을 찍은
순서는 알지만 그 사이에 발급이 카운터를 얼마나 올렸는지는 이 회차 자료에 없다.
