# 재건을 다시 설계한다 (2026-10-12)

**이 문서는 코드를 바꾸기 전에 썼고, 바꾼 뒤 회차로 확인한 결과를 8장에 더했다.**
2026-10-10 하루에 재건에 고침 여섯이 들어갔고 매번 "그 고침이 드러낸 다음 결함" 을 고쳤다.
그 패턴이 설계 문제의 신호라고 보고 멈췄다.

**결론을 먼저 적으면 재건이 1회로 떨어졌다.** 재연결을 3대가 봐도 한 번만 돈다 (8장).

```
c1f8af9b   재건 전용 Redis 통로(1초) + 재시도 3회 + 명부의 못 셌다/0명 구분
768586b5   위의 셋째가 결번 180 을 만들어 되돌렸다
9f65a378   명부 세기를 재건 통로로 돌렸다
453f2aaf   회차마다 다른 쿠폰으로 시드한다
0c98954c   그 분리가 쿠폰을 쌓아 결번 6 을 만들어 reset 을 고쳤다
378aa35a   문을 열 때 카운터를 올리기만 하게 했다
df8a6483   기여를 누가 올렸는지 로그로 가릴 수 있게 했다
```

**여섯 중 둘이 앞선 고침이 만든 결함을 되돌린 것이다.** 한 자리를 고치면 다른 자리가 깨지는
구조라는 뜻이다.

## 1. 지금 구조가 얽혀 있는 자리

재건이 여섯 가지를 동시에 한다.

| | 하는 일 | 어디에 있나 |
|---|---|---|
| 1 | 키 부재와 승격을 한 절차로 다룬다 | `CouponSeqRebuilder.rebuild` |
| 2 | 요청을 막는다 | 락 키를 `coupon-issue-seq.lua` 가 본다 |
| 3 | 남의 메모리 큐를 모은다 | `CouponSeqContributor` + `rebuild:queued` |
| 4 | 정지를 짧게 한다 | `awaitContributions` 의 조기 종료 |
| 5 | 죽은 대를 안 기다린다 | `CouponSeqInstances` 의 `STALE_AFTER` |
| 6 | 중복 실행을 막는다 | `inProgress` 집합 + 재건 락 |

**3 과 4 와 5 와 6 이 서로 얽혀 있다.**

```
정지를 짧게 하려면 (4)     ->  언제 다 모였는지 알아야 한다
다 모였는지 알려면 (3)     ->  몇 대를 기다릴지 세야 한다
대수를 세려면              ->  명부가 필요하다
명부가 죽은 대를 걸러야 (5) ->  갱신 시각을 점수로 둬야 한다
그 갱신을 누가 하나        ->  플러시가 배치를 집을 때 한다
그 전부가 Redis 에 있다    ->  Redis 장애 때 못 믿는다.  재건이 필요한 때가 그때다
```

**오늘 고친 여섯이 전부 이 고리에서 나왔다.**

## 2. 실측이 드러낸 결함 둘

### 2.1 명부가 빠뜨린 살아 있는 대

2026-10-10 N-2 회차다.

```
큐 대기 건수    342    5,328    8,181
배치 건수        35      844      918
CONTRIBUTIONS_COMPLETE instances=2 waitedMillis=2
```

**세 대가 모두 발급을 처리하는 중인데 명부는 2 로 읽혔다.** 한 대가 앞 회차에서 죽었다
되살아나 ALB 가 요청을 천천히 보냈고(342건, 다른 둘의 1/20), 명부 갱신이 플러시에 묶여
있어 `STALE_AFTER` 10초 안에 갱신이 없었다.

**그래서 주도자가 2밀리초에 "다 모였다" 로 끝냈다.** 빠진 대가 큐를 쥐고 있었으면 그 번호가
어디에도 안 잡혀 `free` 로 되살려진다. 그 회차는 결번 0 이었지만 보장이 아니다.

### 2.2 재건이 자기를 다시 부르는 고리

2026-10-12 Q-1 회차다.

```
43.154  i-01fb8da8  주도 시작  ->  44.453 완주
44.533  i-01fb8da8  주도 시작  ->  44.999 완주      80밀리초 뒤에 자기가 또
45.055  i-01fb8da8  주도 시작  ->  45.844 완주      56밀리초 뒤에 또
```

**이 회차는 명부가 정확했다.** `instances=3` 이고 식별자 셋이 전부 들어왔다. 그런데도 네 번
돌았다.

```
재건이 돈다  ->  락 때문에 순번 확보가 -2 를 낸다
             ->  -2 를 받은 요청이 suspect() 를 부른다
             ->  재건이 끝나 inProgress 가 비는 순간 그 요청이 다음 재건을 띄운다
```

**끊는 장치가 `inProgress` 하나뿐이고 그것이 재건 경계에서 열린다.** 2만 VU 가 `-2` 를 받는
중이므로 그 틈이 즉시 메워진다.

**정합성은 지켜졌다.** `maxSeq` 가 네 번 다 6631 이고 결번 0 이다. `378aa35a` 가 카운터를
올리기만 하게 고친 결과다. **문제는 가용성이다.** 네 번의 정지가 쌓여 p99 가 990.53ms 로
SLO 경계에 닿고 재고 10,000 중 591장이 안 나갔다.

## 3. 그대로 둘 것

**이 셋은 회차로 어렵게 얻은 것이고 근거가 문서에 있다.**

| | 왜 그래야 하나 |
|---|---|
| 큐를 DB 보다 먼저 읽는다 | 티켓은 큐에서 DB 로만 간다. 반대로 읽으면 그사이 넘어간 티켓이 어디에도 안 잡혀 결번이 된다 |
| 카운터를 가장 마지막에 쓴다 | 스크립트가 카운터 부재에 `-2` 를 내므로 그 쓰기가 곧 문을 여는 동작이다. 요청을 막는 장치를 새로 만들지 않는다 |
| 확정분을 미확정 뒤에 넣는다 | 확정 표시를 미확정으로 덮으면 회수가 그 번호를 넘겨 끝난 발급이 두 번 나간다 |

**그리고 이 둘도 둔다.**

```
키 부재와 승격을 한 절차로      승격은 카운터를 살려 두므로 존재를 관문으로 두면 영영 안 걸린다
카운터를 올리기만 한다          378aa35a.  Q-1 에서 네 번 돌아도 maxSeq 가 같았다
```

## 5. 고침 1. 명부의 갱신원

### 5.1 어긋난 세는 대상

| | 세는 것 |
|---|---|
| 지금 | 최근 10초 안에 **배치를 집은** 대 |
| 필요한 것 | 최근 10초 안에 **번호를 받은** 대 |

**재건이 알아야 하는 것은 뒤쪽이다.** 번호를 받은 대만 큐에 티켓이 있을 수 있다.

**지금 갱신은 `holdingQueue()` 하나뿐이고 플러시가 배치를 집을 때 부른다.** 그래서 요청을
20분의 1 받는 대는 배치가 드물어 10초 공백이 생기고 `live()` 가 그 대를 안 센다. N-2 가 그
모양이다.

### 5.2 바꿀 자리

```
coupon-issue-seq.lua 가 ARGV[4]=instanceId 를 받는다
번호를 내준 뒤 coupon:instances 에 그 ID 를 지금 시각 점수로 넣는다
```

**왕복이 늘지 않는다.** 그 스크립트가 이미 도는 자리다.

**`holdingQueue()` 는 남긴다.** 둘이 같은 것을 가리키고, 그것이 막는 경우를 순번 확보가 못
막는다. DB 가 막혀 배치를 못 끝내는 대가 그 경우이고, 그 Javadoc 이 적어 둔 그대로다.

> 쓰기 성공에 묶으면 안 된다. DB 가 막힌 인스턴스가 배치를 못 끝내 알림이 멈추면 큐를 쥐고
> 있는데도 명부에서 빠진다. 실제 회차에서 그렇게 됐다.

**`live()` 와 `STALE_AFTER` 10초는 그대로 둔다.** 점수가 갱신 시각이라 죽은 대가 10초 뒤에
빠지는 장치가 유지된다. 조기 종료도 그대로 둔다. 명부가 정확해지면 그 판정이 맞다.

## 6. 고침 2. 자기를 부르는 고리

### 6.1 두 뜻을 겸하는 한 응답

`coupon-issue-seq.lua` 가 `-2` 를 내는 자리가 둘이다.

```lua
if redis.call('EXISTS', KEYS[5]) == 1 then return '-2' end   -- 재건 락이 있다
if redis.call('EXISTS', KEYS[3]) == 0 then return '-2' end   -- 카운터가 없다
```

**`SeqOutcome.NotPrepared` 의 Javadoc 이 그 겸침을 이미 적고 있다.**

> 이벤트 준비 전이거나 카운터 재건 중이다.

그리고 서비스는 둘을 안 가리고 똑같이 처리한다.

```java
case SeqOutcome.NotPrepared ignored -> {
    rebuildTrigger.suspect(couponId);
    throw congested(IssueResult.NOT_PREPARED);
}
```

**카운터가 없는 경우에는 이것이 맞다.** 누군가 재건해야 하고 요청이 그 신호다. 부재 경로
재건이 그렇게 뜬다.

**재건 중인 경우에는 틀렸다.** 이미 돌고 있는데 "재건해라" 를 부른다. 그리고 2만 VU 가 그
`-2` 를 받으므로 그 호출이 쌓인다.

### 6.2 고리

```
재건이 락을 잡는다  ->  Lua 가 -2 를 낸다  ->  -2 가 suspect() 를 부른다
->  inProgress 가 걸러낸다  ->  재건이 끝나며 그 집합을 비운다
->  그 직후의 -2 하나가 통과해 다음 재건을 띄운다
```

**재건이 만든 상태가 내는 신호를 자기를 부르는 입력으로 쓴다.** 끊는 장치가 `inProgress`
하나뿐이고 재건 경계에서 열리는데, 그 순간 대기 중인 `-2` 가 수천 건이라 틈이 즉시 메워진다.
Q-1 에서 80밀리초와 56밀리초 뒤에 같은 대가 다시 주도했다.

**부재 경로는 이 고리가 스스로 닫힌다.** 재건이 카운터를 세우면 `-2` 가 멈춘다. **승격 경로는
락이 풀려도 이미 쌓인 `-2` 가 남아 안 닫힌다.**

### 6.3 고침 가. 응답을 둘로

```
지금    카운터 없음  ->  -2        누가 재건해라
        락이 있음    ->  -2        재건 중이다

고침    카운터 없음  ->  -2        누가 재건해라
        락이 있음    ->  -4        재건 중이다. 기다려라
```

**`-4` 를 받은 요청은 `suspect()` 를 안 부른다.** 재건이 도는 동안 신호가 생산되지 않으므로
끝난 뒤에도 쌓인 것이 없다.

**막는 장치를 더하는 것이 아니라 잘못된 신호를 안 만드는 것이다.** 상태가 늘지 않는다.

**사용자 응답은 그대로 503 이다.** `SeqOutcome` 에 갈래를 하나 더하고 둘 다 혼잡으로 답한다.
재건 중인 쪽에 `Retry-After` 를 더 길게 주는 선택이 따로 있다.

### 6.4 고침 나. 락을 일찍 푸는 것

```
지금    카운터를 쓴다  ->  플러시를 재개한다  ->  기여 키를 지운다  ->  락을 푼다
고침    카운터를 쓴다  ->  락을 푼다  ->  나머지 뒷정리
```

**카운터가 서면 발급이 가능하다.** `openGate` 가 마지막 쓰기이고 그 뒤는 뒷정리뿐인데, 지금은
그 뒷정리 동안 락이 남아 `-2` 가 계속 난다.

**가와 함께 두면 그 구간도 사라진다.** 가만으로도 `-4` 라서 신호가 안 나지만, 나까지 하면
발급이 더 일찍 재개된다.

**대가는 뒷정리 중에 새 재건이 시작될 수 있다는 것이다.** 다만 카운터가 이미 섰으므로 `-2` 가
안 나고, 남는 신호는 재연결 감시뿐이다. 그쪽은 고침 1 로 기여 판정이 정확해져 한 번에 끝난다.

### 8.1 고침 2 의 증거

**재연결을 3대가 봤는데 재건은 1회다.**

```
전 (Q-1)   재연결 3건  ->  재건 4회.  한 대가 80밀리초와 56밀리초 뒤에 또 주도했다
후 (R-1)   재연결 3건  ->  재건 1회
```

**둘째와 셋째 대는 락을 보고 기여만 하고 돌아갔다.** `done` 에 식별자 셋이 다 들어온 것이
그것이다. 재건은 한 번인데 셋의 기여를 다 받았다.

**`-4` 가 신호를 안 만든 결과다.** 재건 중 요청이 `suspect()` 를 안 부르므로 재건이 끝나는
순간에 예약된 다음 회차가 없다.

### 8.2 고침 1 의 증거

**R-1 에서 `instances=3` 으로 셋을 다 세고 85밀리초에 다 모였다.** 순번 확보가 명부를 올리니
번호를 받은 대가 빠지지 않는다.

**R-2 의 `instances=2` 는 맞는 값이다.** 한 대를 죽였으니 번호를 받을 수 있는 대가 둘이고,
`queued=0` 도 그와 맞는다. 살아남은 둘이 큐를 이미 비웠다.

```
N-2    3대가 번호를 받는 중인데 instances=2     틀린 값이었다
R-2    2대만 살아 있고 instances=2              맞는 값이다
```

**같은 수가 한쪽에서는 결함이고 다른 쪽에서는 정상이다.** 그 차이를 가리는 것이 이 고침의
값이고, 그래서 `done` 에 식별자를 함께 남기기로 했다.

### 8.3 조기 종료를 남긴 판단

```
기여 대기    85밀리초, 52밀리초
천장         contributeWait 3초
```

**명부가 정확해지니 조기 종료가 수십 밀리초에 끝난다.** 이 문서의 앞선 판은 `contributeWait`
를 늘 다 쓰자고 적었는데, 그러면 두 회차 모두 3초를 태웠을 것이다.

## 9. 고친 판으로 장애 3종을 돌린 결과

| 회차 | 장애 | 발급행 | 결번 | p99 | 재건 |
|---|---|---:|---:|---:|---:|
| S-1 | 스프링 서버 1대 비정상 종료 | 10,000 | **0** | 0.354초 | 0회 |
| S-2 | 캐시 Multi-AZ 페일오버 | 10,000 | **0** | **1.330초** | 0회 |
| S-3 | 서버 1대 종료 + 캐시 페일오버 | 10,000 | **0** | 0.347초 | 1회 |

**셋 다 재고 10,000장을 다 내보내고 결번 0, 초과 발급 0, 예상 못 한 응답 0 이다.** 복합
장애까지 재고를 다 낸 것은 이번이 처음이다. 2026-10-10 P-1 은 9,542장이었다.

**재건이 한 번도 두 번 이상 돌지 않았다.** 고침 2 가 들었다.

### 9.1 S-2 의 p99 를 만든 커널 OOM

```
coupon_settled_duration   p90  63.77ms   p95  143.2ms   p99 1.330초
http_req_duration         p90   2.54초   p95   3.87초   max 9.930초
coupon_gateway_failed     12,417
```

**발급 본체는 빠르고 `http_req_duration` 만 느리다.** ALB 가 보냈는데 앱이 못 받았다는 뜻이다.

```
i-008cfc5a   Up 50 minutes (생성은 5시간 전)   dmesg "out of memory" 1건
i-0dd97977   Up 5 hours                       OOM 0건
```

**한 대가 커널 OOM 으로 죽었다 다시 떴다.** `REBUILD_REDIS_READY` 가 주입 직후에 찍힌 것이 그
재기동이고, ASG 활동은 조용했으니 컨테이너만 죽었다.

**`RestartCount=0` 과 `OOM=false` 를 믿으면 안 된다.** Docker 가 보는 것은 재시작된 새
컨테이너이고 커널이 죽인 것은 그 앞의 프로세스다. `dmesg` 를 봐야 한다. 2026-10-10 F-2 에서
같은 함정을 밟았다.

**재건이 `RETRY` 한 번 뒤에 끝난 것도 그 탓이다.** `QueryTimeoutException` 이고 그 대가 죽어
이어가지 못했다.

**컨테이너 메모리 한도가 없는 것이 뿌리다.** fm-infra 의 미결정 값 2.1.1 이고, 한도를 두면
커널이 호스트를 흔드는 대신 컨테이너만 죽는다.

### 9.2 S-3 이 고침 1 의 구멍을 드러냄

```
07:13:07.822  CONTRIBUTIONS_COMPLETE instances=0 done=[e89cbd48] waitedMillis=8
07:13:07.997  REBUILT issued=10000 queued=0 freed=0
07:13:08.510  CONTRIBUTED instance=08f01b6e size=0      688밀리초 늦었다
```

**명부가 0 으로 읽혀 8밀리초에 끝냈고 둘째 대의 기여가 버려졌다.**

**발급이 끝난 뒤에 재건이 돌았기 때문이다.** 명부를 올리는 두 경로가 그때 다 멈춘다.

| 경로 | 그 시점에 |
|---|---|
| 순번 확보 Lua | 번호가 다 나가 아무도 안 받는다 |
| `holdingQueue()` | 큐가 비어 집을 배치가 없다 |

`STALE_AFTER` 10초를 넘겨 세 대가 전부 빠졌다. k6 가 끝난 지 14초 뒤였다.

**이번에는 피해가 없었다.** `queued=0` 이라 놓칠 큐가 없었다. 그런데 **2026-10-10 J-4 에서
결번 180 을 만든 바로 그 모양이다** (`instances=0` 에 `waitedMillis=25`). 큐에 티켓이 있는
순간에 이 경로를 타면 결번이 난다.

**같은 `0` 이 두 뜻을 겸하는 것이 문제다.**

```
정말 아무도 큐를 안 쥐었다       S-3.  빨리 끝내는 것이 맞다
쥐고 있는데 갱신이 멈춰 빠졌다    J-4.  결번이 났다
```

### 9.3 고침 3. 큐를 쥔 동안의 알림

**플러시가 세 자리에서 알리게 했다.**

```
배치를 집은 직후        전과 같다
집을 배치가 없을 때     큐에 티켓이 남아 있으면 알린다
재건에 멈춰 있을 때     같다
```

**그러면 명부의 `0` 이 한 뜻만 갖는다.** 큐를 쥔 대는 비울 때까지 명부에 남으므로, 0 은 "정말로
아무도 안 쥐었다" 다. 재건이 그 0 을 믿고 일찍 끝내도 안전하다.

**조기 종료를 지키면서 결번 위험을 없앤다.** `instances=0` 을 "모르겠다" 로 다루는 대안은
S-3 유형에서 늘 3초를 태우므로 택하지 않았다.

| | 재건 정지 | 결번 위험 |
|---|---|---|
| 고치기 전 | 0.19초 | 있다 |
| `0` 을 모르겠다로 | 3초 | 없다 |
| **큐를 쥔 동안 알린다** | **0.19초** | **없다** |

시험 셋으로 고정했다.

```
집을_배치가_없어도_큐가_있으면_알린다
큐가_비면_알리지_않는다
멈춰_있어도_큐가_있으면_알린다
```

## 10. 재지 않은 것

**고침 3 을 회차로 확인하지 않았다.** 시험으로만 고정되어 있다. 확인에 필요한 것은 발급이
끝난 뒤에 재건이 도는 회차이고, S-3 가 그 조건이었으므로 복합 장애를 한 번 더 돌리면 된다.

**기여 `size` 와 재건 `queued` 를 대조하지 못했다.** S-2 와 S-3 의 `size` 가 둘 다 0 이고
`queued` 도 0 이라 검산이 성립하지 않는다. 큐에 티켓이 남은 상태에서 재건이 도는 회차가
있어야 그 둘을 맞출 수 있다.

**`-2` 와 `-4` 의 비율을 안 쟀다.** k6 는 둘을 혼잡으로 묶어 세므로 구별되지 않는다. 가르려면
지표를 따로 붙여야 한다.

**재연결 편차가 더 큰 조건을 못 봤다.** R 과 S 회차에서 재건이 1회였지만, 편차가 1.26초보다
큰 경우에도 1회인지는 확인하지 않았다.
