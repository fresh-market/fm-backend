# 버전 비교 회차 결과 (2026-09-27)

[coupon-version-rounds.md](coupon-version-rounds.md) 가 설계한 회차를 v1 부터 v4 까지 각 3회,
모두 12회 돌린 결과다. 부하 생성기 2대로 2만 VU 를 나눠 걸었다.

**설계가 요구한 무효 조건을 먼저 적용하고 그 뒤에 값을 읽었다.** 순서를 바꾸면 유리한
회차만 고르게 된다.

---

## 1. 결론

**이 회차는 네 버전의 우열을 가리지 못했다.** 버전 사이의 차이가 같은 버전 안의 회차 사이
변동보다 작다. v1 은 같은 코드로 72.72ms 와 207.95ms 를 냈고, 그 폭이 v1 과 v4 의 차이보다 크다.

**원인은 구현이 아니라 부하다.** 회차가 끝났을 때 **락 대기가 0, HikariCP 대기가 0, 활성
커넥션이 1, JVM 스레드 최대가 68 이다.** 네 구현 어디도 자기 병목에 닿지 않았다. 병목에
닿지 않은 부하에서는 병목을 없앤 설계가 값을 내지 못한다.

**같은 말을 [coupon-load-rounds.md](coupon-load-rounds.md) 10장이 이미 적어 뒀다.** 그 회차는
워밍업 말고 움직이는 변수가 없다고 했고, 이번 회차는 구현을 넷으로 바꿔도 같다는 것을 더했다.

**한 회차만 갈렸다.** v3-2 에서 큐가 2,620 까지 차고 혼잡이 13,278건 나왔다. 같은 코드의
다른 두 회차는 큐 최대가 1 과 2 다. **v3 의 큐는 평소에 안 차고 한 번 터졌다.**

**대신 생성기 대수가 갈랐다.** 같은 코드를 1대로 돌린 회차가 602.1ms 이고 2대 회차는
87.6ms 와 126.2ms 다. 7배 차이다. **앞선 회차들의 0.3초대는 앱이 아니라 생성기가 8 GB 벽에
닿아 낸 값이다** (9장).

## 2. 이 회차가 실제로 걸었던 부하

**요구사항이 정한 값을 덮어쓰지 않았다.**

| 요구사항 | 실제 | 어디서 확인하나 |
|---|---|---|
| 재고 10,000장 | 10,000 | `coupon 900001` 의 `total_quantity` |
| 20,000명 동시 요청 | 20,000 | `vus_max` 10,000 에 생성기 2대 |
| ramp-up 60s | 60s | `issue.js` 의 `RAMP` 기본값 |
| 가상 유저 100만 | 1,000,000 | seed 로그 |
| 발급 이력 300만 | 3,000,000 | seed 로그 |

**`HOLD 30s` 는 요구사항에 없고 팀이 정했다.** 요구사항은 램프까지만 정했다.

### 발급은 90초에 걸쳐 나가지 않는다

**`default` 함수가 판정을 받은 VU 를 다시 쏘지 않는다.**

```javascript
  // 이 사람은 이미 끝났다. 남은 시간 동안 접속만 유지한다
  if (settled) {
    sleep(1);
    return;
  }
```

**그래서 도착률은 VU 가 생기는 속도가 정하고 그것은 초당 약 333명이다.** 반복 수가 회차마다
60만을 넘는 것은 판정이 끝난 VU 가 `sleep(1)` 로 도는 빈 반복이다.

**재고 10,000 은 램프 시작 30초에 소진된다.** 남은 60초는 소진 응답만 나간다. 회차 길이
90초로 재고를 나누면 발급 TPS 를 세 배 낮게 본다.

## 3. 회차별 원본

**판정에 쓰는 값은 `k6 요약 p99` 다.** 회차가 끝났을 때 그 회차의 표본 전체로 계산한 값이고,
[coupon.md](coupon.md) 7장의 SLO 가 재는 것이 이것이다. 생성기 두 대의 값을 따로 싣는다.

`Prom p99` 두 열은 k6 가 5초마다 보낸 p99 시계열을 회차 창으로 잘라 최댓값을 잡은 것이다.
**같은 p99 이지 다른 종류의 지표가 아니다.** 다만 그 시계열은 누적 분포의 p99 라서 표본이
적은 회차 초반에 크게 튄다. **그래서 판정에 쓰지 않고 참고로만 싣는다.**

### 유효 회차

| 회차 | k6 요약 p99 (1호기) | k6 요약 p99 (2호기) | Prom p99 settled | Prom p99 http | 발급 | 혼잡 |
|---|---:|---:|---:|---:|---:|---:|
| v1-1 | 172.79ms | 207.95ms | 274.8ms | 274.8ms | 10,000 | 0 |
| v1-3 | 102.41ms | 72.72ms | 139.8ms | 139.8ms | 10,000 | 0 |
| v2-1 | 88.75ms | 105.28ms | 153.6ms | 181.7ms | 10,000 | 0 |
| v2-2 | 95.31ms | 100.03ms | 110.0ms | 127.8ms | 10,000 | 0 |
| v3-1 | 70.02ms | 91.44ms | 165.1ms | 165.1ms | 10,000 | 0 |
| v3-3 | 143.97ms | 75.45ms | 323.0ms | 323.0ms | 10,000 | 0 |
| v4-5 | 87.58ms | 75.33ms | 87.6ms | 152.7ms | 10,000 | 0 |
| v4-6 | 76.54ms | 83.83ms | 126.2ms | 139.4ms | 10,000 | 0 |

### 무효 회차

**발급 수가 10,000 이 아니라 설계 4장의 조건에 걸렸다.** 네 회차 모두 혼잡(503)이 나왔고,
발급과 혼잡의 합이 재고에 닿는다.

| 회차 | Prom p99 settled | Prom p99 http | 발급 | 혼잡 | 발급+혼잡 |
|---|---:|---:|---:|---:|---:|
| v1-2 | 978.5ms | 1,023.4ms | 9,776 | 224 | 10,000 |
| v2-3 | 370.5ms | 454.9ms | 9,991 | 2 | 9,993 |
| v3-2 | 358.7ms | 2,259.8ms | 7,021 | 13,278 | 20,299 |
| v4-4 | 785.7ms | 810.3ms | 9,948 | 8 | 9,956 |

**무효 조건의 사유 문구가 틀렸다.** 설계 4장은 "발급 수가 10,000 이 아니다 -> R1 이 깨졌다"
라고 적었는데, R1 은 발급이 10,000 을 **넘을** 때 깨진다. 이 넷은 재고를 다 털지 못한 것이고
R1 은 지켜졌다. 조건 자체는 유효하므로 그대로 적용했고, 사유만 이 문서가 바로잡는다.

## 4. 버전 비교

**분위수를 평균내지 않는다.** p99 는 이미 분포를 요약한 값이라, 회차와 생성기에 걸쳐 평균을
내면 그 결과는 p99 가 아니다. **버전의 p99 는 그 버전이 낸 p99 중 가장 나쁜 값이다.**

생성기가 둘이라 표본이 갈려 있다. 두 대의 표본을 합쳐 p99 를 다시 계산하는 것이 옳지만
k6 요약은 대별로만 남는다. **그래서 보수적으로 큰 쪽을 쓴다.**

| 버전 | p99 | 어느 회차 | 발급 | 최대 큐 | 락 대기 |
|---|---:|---|---:|---:|---:|
| v1 DB 조건부 UPDATE | **207.95ms** | v1-1 2호기 | 10,000 | 1 | 0 |
| v2 Redis 카운터 | **105.28ms** | v2-1 2호기 | 10,000 | 3 | 0 |
| v3 인스턴스 큐 + 벌크 | **143.97ms** | v3-3 1호기 | 10,000 | 2 | 0 |
| v4 가상 스레드 (채택) | **87.58ms** | v4-5 1호기 | 10,000 | 2 | 0 |

**네 버전 모두 SLO 인 1초를 크게 밑돈다.** v4 가 가장 낮고 v1 이 가장 높으며 2.4배 차이다.

### 이 표로 우열을 말할 수 없는 이유

**같은 코드가 낸 값이 세 배 벌어진다.** v1 의 네 값은 `172.79 / 207.95 / 102.41 / 72.72` 다.
가장 나쁜 값과 가장 좋은 값이 2.9배 차이다. v3 는 `70.02 / 91.44 / 143.97 / 75.45` 로 2.1배다.

**버전 사이의 차이(2.4배)가 한 버전 안의 변동(2.9배)보다 작다.** 어느 쪽이 구현의 차이이고
어느 쪽이 회차의 우연인지 이 표본으로는 가를 수 없다.

## 5. 버전을 가르는 지표가 버전을 가르지 못했다

설계 6장이 지표 여덟 개를 지목했다. **그중 일곱이 버전에 따라 움직이지 않았다.**

| 지표 | 기대한 차이 | 실측 |
|---|---|---|
| `innodb_row_lock_waits` | v1 이 크다 | 전 버전 0. v3-2 만 123 |
| `redis_commands_processed_total` | v1 이 0 에 가깝다 | 전 버전 약 242,000 으로 같다 |
| `hikaricp_connections_pending` | v2 가 크다 | 전 버전 0 |
| `hikaricp_connections_active` | v2 가 크다 | 전 버전 1 |
| `slow_queries` | v2 가 크다 | 전 버전 0 |
| `coupon_issue_queue_size` | v2 는 0 | 전 버전 1 ~ 3. v3-2 만 2,620 |
| `jvm_threads_peak_threads` | v3 가 200 벽에 붙는다 | 전 버전 68 |
| `tomcat_threads_busy_threads` | v3 가 200 에서 막힌다 | 수집되지 않았다 |

**`redis_commands_processed_total` 이 v1 에서도 24만인 것이 이 표의 핵심이다.** v1 은 Redis 를
쓰지 않으므로 발급 10,000건만큼 적어야 한다. 값이 같다는 것은 **이 지표가 압도적으로 배경
트래픽을 재고 있고 발급 부하는 그 안에 묻힌다**는 뜻이다.

**`tomcat_threads_busy_threads` 는 아예 없었다.** 지표 이름이 다르거나 노출되지 않는다.
설계가 지목하기 전에 존재를 확인하지 않았다.

**`jvm_threads_peak_threads` 68 이 v3 와 v4 를 가르지 못하는 이유도 같다.** 플랫폼 스레드
200 벽은 그 근처까지 스레드를 써야 보이는데 68 에서 끝났다.

## 6. v3-2 한 회차

**같은 코드가 세 번 중 한 번 다르게 움직였다.**

| 값 | v3-1 | v3-2 | v3-3 |
|---|---:|---:|---:|
| 발급 | 10,000 | 7,021 | 10,000 |
| 혼잡(503) | 0 | 13,278 | 0 |
| 최대 큐 | 2 | 2,620 | 1 |
| 락 대기 | 0 | 123 | 0 |
| GC 횟수 | 48 | 72 | 32 |
| settled p99 | 165.1ms | 358.7ms | 323.0ms |
| http p99 | 165.1ms | 2,259.8ms | 323.0ms |

**큐가 2,620 까지 찼고 그 뒤 혼잡으로 돌려보냈다.** `http p99` 가 2.26초인데 `settled p99` 가
358.7ms 인 간격이 설계 5장이 말한 그대로다. 혼잡이 요청 예산을 태우고 끊기므로 판정이 끝난
응답만 보는 쪽은 낮게 남는다.

**이 회차가 v3 의 위험을 보여준다.** 큐가 평소 1 과 2 에서 노는 것은 여유가 아니라
**포화까지의 거리를 알 수 없다는 뜻이다.** 한 번 차기 시작하면 2,620 까지 갔다.

**재현되지 않았다.** 세 번 중 한 번이고 방아쇠를 찾지 못했다. **v3 를 채택하지 않기로 한
결정에 이 회차를 근거로 쓸 수는 있지만, 그것만으로는 약하다.**

## 7. 이 회차가 답하지 못한 것

**네 구현의 우열이다.** 부하가 병목에 닿지 않아 넷이 같은 값을 냈다. 가르려면 둘 중 하나를
바꿔야 한다.

| 바꿀 것 | 무엇이 달라지나 |
|---|---|
| 재고를 10,000 보다 크게 | 도착률은 그대로지만 발급이 30초에서 90초까지 이어져 누적 부하가 커진다 |
| 램프를 60초보다 짧게 | 도착률 자체가 올라간다. 30초면 초당 667명이다 |

**둘 다 요구사항이 고정한 값이라 이 시험 안에서는 못 바꾼다.** 요구사항 밖의 회차로 따로
설계해야 한다.

**`tomcat_threads_busy_threads` 를 못 봤다.** v3 와 v4 를 가르는 핵심 지표인데 수집되지
않았다. 지표 이름을 확인하고 노출부터 고쳐야 한다.

**혼잡이 왜 회차마다 생겼는지 모른다.** 네 무효 회차 모두 혼잡이 났고, 같은 버전의 다른
회차는 0 이다. **회차 사이에 남는 상태가 있는지 의심스럽다.**

## 8. 절차에서 고칠 것

### k6 threshold 줄이 로그에 남지 않는 조건

**혼잡이 한 건이라도 난 회차는 threshold 줄이 로그에 없다.** 혼잡 0 인 유효 회차 여덟 개는
모두 `✓ 'p(99)<1000' p(99)=...` 를 남겼고, 혼잡이 난 네 회차는 그 줄이 없다. 상관은 완전한데
**원인을 확정하지 못했다.**

그래서 이 문서의 p99 는 Prometheus 를 창으로 자른 값을 쓴다. **k6 요약에만 의지하면 가장
나쁜 네 회차의 값을 잃는다.**

### 회차 로그에 남기지 못한 것

### SSM 만 보는 이미지 검산이 통과해 버린다

**`deploy.sh` 는 2단계에서 SSM `current-sha` 를 갱신하고 4단계에서 실패할 수 있다.** 그러면
SSM 은 새 값인데 인스턴스는 구 이미지다. 2026-09-27 에 `apply.sh` 가 건 배포와 손으로 건
배포가 같은 ASG 를 동시에 밀어 `desired 4 is above max value 3` 으로 그렇게 됐다.

**무효 조건의 "배포한 태그가 브랜치 HEAD 와 다르다" 가 이 경우를 못 잡는다.** 회차 스크립트가
SSM 만 읽어 "이미지 확인" 을 찍고 넘어갔다. **인스턴스에서 `docker ps` 의 이미지 태그를
읽어야 한다.**

### 회차 로그에서 k6 오류를 버렸다

회차 로그를 `grep` 으로 걸러 남겼는데, 그 목록에 오류 문구가 없어서 k6 가 왜 죽었는지
로그에 안 남았다. `(Failed)` 한 줄만 남아 SSM 이력을 따로 파야 했다.

**진행 표시만 걷고 나머지는 통째로 남긴다.** 진행 줄은 `^running (` 과 `VUs  ` 둘로 걸러진다.

### verify 의 숫자 줄

`verify` 의 숫자 줄을 회차마다 못 남겼다. 필터가 머리글과 빈 줄만 남겨서
**회차별 `gap` 과 `max_seq` 가 사라졌다.** 정합성은 마지막 회차의 값 하나만 있다.

```
issued_rows	max_seq	gap	members
10000	10000	0	10000
```

발급 수는 k6 의 `coupon_issued` 합으로 대신 셌다. **그 값은 앱이 200 을 돌려준 횟수이고
DB 행 수가 아니다.** 다음 회차에서는 숫자 줄을 통째로 남겨야 한다.

## 9. 생성기 대수가 p99 를 가른다

**이전 회차의 0.302 ~ 0.518초와 이번 87.58ms 를 나란히 놓으면 안 된다.** 둘은 부하 생성기
대수가 다르다. 그것을 확인하려고 같은 코드를 생성기 1대로 한 회차 더 돌렸다.

### 회차 g1-1

```
이미지     4e60611  (2026-09-27 의 main. b86d86fb 와 src/ 가 같고 문서 한 파일만 다르다)
생성기     m7i-flex.large 1대, 2만 VU 전부
그 밖      재고 10,000 / ramp 60s / hold 30s / 전용 ASG 3대. 2대 회차와 같다
```

| | 생성기 1대 (g1-1) | 생성기 2대 (v4-5) | 생성기 2대 (v4-6) |
|---|---:|---:|---:|
| settled p99 | **602.1ms** | 87.6ms | 126.2ms |
| http p99 | **854.5ms** | 152.7ms | 139.4ms |
| k6 완주 | **죽었다** | 완주 | 완주 |
| 발급 | 10,000 | 10,000 | 10,000 |
| `gap` | 0 | 0 | 0 |

**7배 차이다.** 같은 코드이고 같은 부하이고 같은 앱 구성이다.

### 1대는 8 GB 벽에 닿는다

**회차 중 생성기 메모리를 5초마다 재 뒀다.**

```
21:02:42    596MB     램프 시작 전
21:02:52  3,102MB
21:03:22  5,227MB
21:03:52  7,394MB
21:04:07  7,667MB     여기서 커널이 죽였다
21:04:16    488MB     프로세스가 사라진 뒤
```

```
Out of memory: Killed process 3185 (k6) total-vm:8800500kB, anon-rss:7468152kB
```

**7.47 GB 를 쓰고 죽었다.** 설계 10장이 적어 둔 "VU 당 약 369 KB" 와 맞는다.

**k6 가 메모리 벽에 붙은 채로 내는 응답 시간에는 생성기의 지연이 섞인다.** `http_req_duration`
은 요청을 보낸 시각부터 응답을 받아 처리한 시각까지라, 생성기가 스스로 바쁘면 그 시간이
앱의 응답 시간으로 기록된다.

### 그래서 앞선 회차의 수치를 어떻게 읽나

`load_test_count` 는 2026-09-27 에 생겼다. **그 전의 모든 회차는 1대였고 인스턴스 타입도
같은 `m7i-flex.large` 였다.**

| 회차 | 생성기 | p99 |
|---|---|---|
| 2026-09-14 성능 회차 (워밍업 켬) | 1대 | 0.302 ~ 0.518초 |
| 2026-09-27 g1-1 | 1대 | 0.602초 |
| 2026-09-27 v4-5, v4-6 | 2대 | 0.088 ~ 0.126초 |

**1대 회차는 셋 다 0.3초에서 0.6초 사이이고 2대 회차는 0.1초 아래다.** 생성기 대수로 값이
갈린다.

**[coupon-load-rounds.md](coupon-load-rounds.md) 의 수치를 이번 값과 비교하지 않는다.**
그 문서의 결론(워밍업이 유일하게 p99 를 움직였다)은 그 안에서 조건이 같으므로 그대로 선다.

### 이 회차가 답하지 못한 것

**2026-09-14 회차가 어떻게 완주했는지 모른다.** 같은 타입 1대인데 그때는 19회차를 돌렸고
이번에는 죽었다. 그 사이 시나리오가 VU 를 더 오래 살려 두게 바뀌었을 수 있으나 확인하지
않았다.

**1대 회차의 k6 요약이 없다.** 죽어서 요약을 못 찍었다. 위 602.1ms 는 Prometheus 를 창으로
자른 값이라 판정값과 모집단이 다르다. **그래도 결론은 서는데, 7배 차이가 그 차이보다
훨씬 크기 때문이다.**
