# 선착순 쿠폰 장애 부하 시험 기록

**장애를 부하가 도는 도중에 주입해 다시 잰 회차들이다.**
앞선 회차(장애를 부하 전에 걸었다)는 [coupon-test.md](coupon-test.md) 에 있다.

일시 **2026-09-01 07:15 ~ 10:26 KST** (UTC 2026-08-31 22:15 ~ 2026-09-01 01:26)
백엔드 **`402fb1f4`** / 전용 인스턴스 `t3.small` 3대 / VU 20,000, ramp-up 60초, 재고 10,000

시나리오는 `loadtest/issue.js`, 장애 주입은 `fm-infra` 의 `scripts/loadtest-fault.sh` 다.

## 이 회차들의 방법론

**앱을 세울 때는 `docker stop` 을 쓴다.** `systemctl stop` 은 `docker compose down` 으로
컨테이너를 지워 큐를 비울 틈도 종료 로그도 남기지 않는다. 그것으로 쟀다가 `gap 4` 를
코드 결함으로 읽을 뻔했다.

**장애는 부하가 도는 도중(25초 지점)에 주입한다.** 앞서 부하 전에 끊고 쟀다가 결과를 잘못
읽을 뻔했다. 캐시를 먼저 끊으면 순번을 받은 요청이 애초에 없어 "발급 0" 이 나오는데, 그것은
장애의 성격이 아니라 시험 순서가 만든 값이다. 실제 장애는 이벤트가 도는 중에 난다.

**발급 수는 지표가 아니라 DB 행으로 센다.** Prometheus `increase()` 는 구간 경계를 보정하는
외삽 때문에 재고보다 큰 값을 낸다 (재고 10,000 인데 10,146 이 나온 적이 있다). 갈래별 건수는
카운터 원값의 회차 전후 차이로 센다.

## 1. 결과 한눈에

| # | 시나리오 | 발급 / 재고 | `gap` | 1인 1매 | p99 | ALB 오류 |
|---|---|---:|---:|---|---:|---:|
| 1 | 정상 | **10,000** / 10,000 | 0 | 지켜짐 | 0.729초 | 0 |
| 2 | 앱 1대 장애 | **10,000** / 10,000 | **0** | 지켜짐 | 0.816초 | 502 4,600 / 연결 4,574 |
| 3 | 캐시 장애 | **7,908** / 10,000 | **0** | 지켜짐 | 12.50초 | 502 7,309 / 연결 3,955 |
| 4 | DB 장애 | **8,088** / 10,000 | **693** | 지켜짐 | 12.50초 | 502 7,309 / 연결 3,955 |
| 5 | 앱 1대 + 캐시 | **9,471** / 10,000 | **0** | 지켜짐 | 1.052초 | 502 9,363 / 연결 9,343 |

**다섯 회차 모두 초과 발급 0, 1인 2매 0 이다.** 발급 정확성은 어떤 장애에도 흔들리지 않았다.

갈리는 것은 **재고를 얼마나 잃느냐**다.

```
gap 0     앱 1대 장애      종료 유예 안에 큐를 비운다
gap 0     캐시 장애        순번을 못 받으니 번호가 안 나간다
gap 0     앱 1대 + 캐시
gap 693   DB 장애          순번은 나가고 쓰기만 실패한다
```

**DB 장애만 재고를 잃는다.** 캐시가 죽으면 번호 자체가 안 나가고, 앱이 죽어도 종료 유예
안에 큐를 비우므로 손실이 없다. DB 가 죽을 때만 번호가 정상적으로 나간 뒤에 못 쓴다.

> **이 `gap 0` 은 고쳐서 얻은 값이 아니다.** 애플리케이션은 한 줄도 안 바뀌었고, 종료 유예도
> 앞 회차와 같았다. 종료 순서에 결함이 있어서 `gap` 은 **재고가 남은 채로 앱이 내려갈 때만**
> 난다. 이 회차들은 그 조건이 안 맞았을 뿐이다. 아래 3절에 근거를 적었다.

## 2. 정상 (장애 없음)

```
발급 10,000 / 재고 10,000    max_seq 10,000    gap 0    members 10,000
p99 0.729초   p95 0.094초
504 / 연결 오류 / 502         0 / 0 / 0
```

**요구 조건 p99 1초를 통과한다.** 서버 오류가 한 건도 없고 재고를 정확히 소진했다.

p95 가 0.094초인데 p99 가 0.729초다. **꼬리 1%가 전체를 끌어올린다.** 앞선 회차들에서
확인했듯 그 꼬리는 재고가 바닥나는 순간에 몰리는 409 다.

## 3. 앱 1대 장애 (부하 중 정지)

3대 중 1대를 부하 25초 지점에 `docker stop` 으로 세웠다.

```
발급 10,000 / 재고 10,000    max_seq 10,000    gap 0    members 10,000
p99 0.816초   p95 0.815초
504 0   연결 오류 4,574   502 4,600
```

**재고를 하나도 안 잃었다.** 종료 로그가 그 이유를 보여준다.

```
event=COUPON_FLUSHER_LEFTOVERS size=1
event=COUPON_FLUSHER_STOPPED
```

큐에 남아 있던 티켓 1건을 종료 직전에 마저 썼다. `CouponIssueFlusher` 가 `SmartLifecycle`
이라 `stop()` 에서 배치를 끝까지 마치고 `drainLeftovers()` 로 큐를 비운다.

**부하 전에 죽였을 때와 결과가 다르다.** 미리 죽이면 ALB 가 이미 대상에서 빼 둔 상태라
2대로 깔끔히 돌지만, 도중에 죽이면 **ALB 가 알아채기까지 그 인스턴스로 요청이 계속 간다.**

```
헬스체크 interval 10초 x unhealthy 5회 = 퇴출까지 50초
회차 길이 90초
```

그 50초 동안 간 요청이 502 와 연결 오류 약 4,200건이다. 90초짜리 이벤트에서 **절반 이상을
죽은 대상에 보내는 셈**이다.

### 어떻게 죽이느냐가 결과를 바꿨다

처음에는 `systemctl stop` 으로 세웠고 `gap = 4` 가 났다. `docker stop` 으로 바꾸니 0 이
나왔다. **처음에는 이것을 주입 방식의 차이로 적었는데 틀렸다.** 확인해 보니 두 경로가 주는
종료 유예는 같다.

```
StopTimeout=45          컨테이너 설정에 박혀 있다 (docker inspect 로 확인)
docker stop             SIGTERM 뒤 45초
docker compose down     stop 단계에서 같은 45초를 지키고, 그 뒤에 컨테이너를 지운다
TimeoutStopSec=60       systemd 가 그 바깥에서 60초를 준다. 45초를 자르지 않는다
```

두 방식의 실제 차이는 **`down` 이 컨테이너를 지워서 종료 로그를 못 본다**는 것뿐이다.
`gap` 이 달라진 이유는 따로 있다. 아래 종료 순서 결함이다.

### 4건을 되찾은 것은 배수가 아니다

`docker stop` 회차의 로그는 `event=COUPON_FLUSHER_LEFTOVERS size=1` 하나뿐이다.
되찾은 것은 4건인데 배수가 건진 것은 1건이다. 나머지 3건은 다른 데서 왔다.

`drainAll` 은 **큐만** 비운다. 그런데 플러시 스레드는 큐에서 꺼낸 티켓을 자기 지역
`List<IssueTicket> batch` 에 쌓아 두고 (`batch-size: 500`), 이것들은 이미 큐 밖이라
`drainAll` 이 못 본다. 이 티켓들을 살리는 것은 `stop()` 의 앞 두 줄이다.

```java
executor.shutdown();
executor.awaitTermination(10초);   // 돌고 있던 batch 가 여기서 flush 까지 끝난다  <- 3건
drainLeftovers();                  // 그러고도 큐에 남은 꼬리                        <- 1건
```

즉 회수의 본체는 `awaitTermination` 이고 `drainLeftovers` 는 꼬리다. `size` 는 배치 수가
아니라 티켓 수(`leftovers.size()`)라, `size=1` 을 "손실이 1건이었다" 로 읽으면 안 된다.

### `gap = 0` 은 보장된 값이 아니다

종료 순서가 거꾸로다. `CouponIssueFlusher` 는 `getPhase()` 를 재정의하지 않아 기본값
`Integer.MAX_VALUE` 이고, 톰캣의 우아한 종료는 그보다 낮다.

```
CouponIssueFlusher                  2147483647   재정의 안 함
WebServerGracefulShutdownLifecycle  2147482623   = Integer.MAX_VALUE - 1024
```

`DefaultLifecycleProcessor.stopBeans` 는 `Comparator.reverseOrder()` 로 **높은 phase 부터**
멈춘다. 그래서 **플러셔가 먼저 죽고 그다음에 톰캣이 남은 요청을 처리한다.** 그 사이에 들어온
요청은 `hasRoom()` 을 통과해 Redis 순번을 받고 `submit()` 하는데, `submit()` 에는 종료
가드가 없고 꺼내 갈 스레드는 없고 `drainLeftovers()` 는 이미 지나갔다. 그 순번은 gap 이 된다.

회차별 `gap` 이 이것으로 그대로 설명된다. **종료 창에서 순번을 받아 갈 수 있었던 회차에만
`gap` 이 나왔다.**

| 회차 | 종료 시점에 순번 할당이 가능했나 | gap |
|---|---|---|
| 2 앱 1대 | 예. 재고가 남아 있었고 캐시도 정상이었다 | 4 |
| 2b 앱 1대 | 아니오. 재고 1만이 소진됐다 (`sold-out-final 2392`) | 0 |
| 5 앱 1대 + 캐시 | 예 | 10 |
| 5b 앱 1대 + 캐시 | 아니오. 캐시가 막혀 할당 자체가 불가능했다 | 0 |

즉 **`gap = 0` 은 고쳐서 얻은 값이 아니라 우연히 조건이 안 맞은 값이다.** 재고가 남은 채로
앱이 정상 종료되면 재현된다. 배포할 때마다 지나는 경로다. 고치려면 `getPhase()` 를 톰캣보다 낮게(예:
`Integer.MAX_VALUE - 2048`) 내려 플러셔가 **뒤에** 멈추게 해야 한다. 아직 안 고쳤다.

```
systemctl stop  ->  docker compose down  ->  컨테이너를 지운다
                    큐를 비울 틈이 없고 종료 로그도 사라진다

docker stop     ->  SIGTERM 뒤 stop_grace_period 45초
                    스프링이 SmartLifecycle.stop 을 끝까지 돈다
```

**이것은 시험 방법의 교훈이면서 운영의 교훈이기도 하다.** 배포나 스케일인으로 인스턴스를
내릴 때 유예를 안 주면 그만큼 재고를 잃는다. 지금 설정은 유예를 준다
(`stop_grace_period: 45s`, `TimeoutStopSec=60`).

다만 **정말로 갑자기 죽는 경우**(전원 차단, OOM 킬)는 이 배수 기회가 없다. 그때 남는 번호는
`reclaim-after 60s` 가 회수 대상으로 잡는다.

### 남는 대가

재고는 안 잃었지만 **그 50초 동안의 사용자 경험은 잃는다.**

```
헬스체크 interval 10초 x unhealthy 5회 = 퇴출까지 50초
회차 길이 90초
```

ALB 가 알아채기 전까지 죽은 대상으로 간 요청이 502 와 연결 오류 약 4,600건이다.
90초짜리 이벤트에서 **절반 이상을 죽은 대상에 보내는 셈**이다.

## 4. 캐시 장애 (부하 중 차단)

`iptables` 로 전용 인스턴스에서 캐시(6379)로 가는 패킷을 25초 지점에 버렸다.

```
발급 7,908 / 재고 10,000    max_seq 7,908    gap 0    members 7,908
p99 12.50초   p95 11.83초
504 39   연결 오류 3,955   502 7,309

갈래   congested-seq-unavailable 28,230
       issued 5,717
```

**`gap = 0` 이 이 회차의 핵심이다.** `max_seq` 와 발급 행이 둘 다 7,908 이다.
**순번을 받은 요청은 100% 발급됐다.**

플러시 스레드는 DB 에 쓰고 Redis 는 확정 표시에만 쓴다. 그 표시가 실패해도
`markCommitted` 가 삼키고 `ticket.complete(Issued)` 가 그대로 돈다. 설계가 의도한 대로다.

못 나간 2,092 장은 **잃은 것이 아니라 안 나간 것**이다. 캐시가 죽은 뒤에 온 요청은 순번
자체를 못 받았고(`congested-seq-unavailable` 28,230), 그 재고는 그대로 남는다.

**캐시 장애의 성격은 "이미 받은 사람은 지키고 새 사람은 못 받는다" 다.** 전면 중단이 아니다.

p99 12.5초는 순번을 기다리다 재시도를 반복한 요청들의 값이다. 사용자는 "잠시 후 다시" 를 받는다.

## 5. DB 장애 (부하 중 차단)

같은 방식으로 DB(3306)를 25초 지점에 끊었다.

```
발급 8,088 / 재고 10,000    max_seq 8,781    gap 693    members 8,088
실패율 0.00%   unexpected 0

갈래   sold-out 9,979
       issued 8,088
       congested-budget 7,259
       congested-write-circuit 5,118     <- 쓰기 회로가 순번 발급을 막았다
       congested-db-failed 2
```

**쓰기 회로가 일했다.** DB 가 죽으면 순번을 받아 봐야 커밋할 수 없다. 회로가 열려
**순번 확보 전에 5,118건을 끊었으므로** 못 쓸 번호가 그만큼 덜 나갔다.

### `gap = 693` 이 뜻하는 것

캐시 장애(`gap 0`)와 갈리는 지점이다.

```
max_seq 8,781    번호는 여기까지 나갔다
발급     8,088    DB 에 써진 것
차이       693    번호는 받았는데 DB 에 못 쓴 요청
```

**캐시가 죽으면 순번을 못 받으니 애초에 번호가 안 나간다.** 반면 **DB 가 죽으면 순번은
Redis 에서 정상적으로 나가고 그 뒤에 쓰기가 실패한다.** 그래서 못 쓴 번호가 남는다.

`congested-budget` 7,259 가 그 경로다. 요청 스레드가 확정을 800ms 기다리다 포기했고,
그 티켓들이 큐에 남아 결국 못 써졌다.

**초과 발급은 아니다.** 693개 번호는 아무에게도 안 갔고 재고 693장이 안 쓰인 채 남는다.
`reclaim-after 60s` 가 회수 대상으로 잡지만 이벤트가 90초라 그 안에 안 돌아온다.

### 쓰기 회로가 없었다면

`congested-write-circuit` 5,118 이 회로가 막아 준 몫이다. 회로가 없었다면 그 5,118건도
순번을 받고 큐에 들어가 `gap` 이 693 이 아니라 훨씬 컸을 것이다. **회로의 값어치가 이
숫자로 보인다.**

## 6. 앱 1대 + 캐시 장애 (부하 중)

25초 지점에 1대를 세우고 동시에 캐시를 끊었다.

```
발급 9,471 / 재고 10,000    max_seq 9,471    gap 0    members 9,471
p99 1.052초   p95 0.583초
504 0   연결 오류 9,343   502 9,363

갈래   congested-seq-unavailable 15,613
       issued 7,353
```

**`gap = 0` 이다.** 앱은 유예 안에 큐를 비웠고, 캐시는 순번을 못 주었을 뿐이라 번호가
안 나갔다. 두 장애가 겹쳐도 **잃은 재고는 없다.**

못 나간 529 장은 캐시가 죽은 뒤에 온 요청이 순번을 못 받은 몫이다 (`congested-seq-unavailable`
15,613). 재고는 그대로 남는다.

ALB 오류가 다섯 회차 중 가장 크다 (502 9,363 / 연결 9,343). 두 장애가 겹치면 **죽은 대상으로
가는 요청과 순번을 못 받는 요청이 함께 쌓인다.**

## 확인하지 않은 것

* **장애에서 회복.** 도중에 끊는 것은 쟀지만 다시 붙였을 때의 회복 속도는 재지 않았다
* **부분 장애.** 캐시 노드 하나만 죽거나 읽기 복제본만 죽는 경우
* **상한.** 도착률 333건/초는 요구 조건이지 한계가 아니다
* **`reclaim-after` 의 실제 회수.** DB 장애가 남긴 693개 번호가 60초 뒤 회수되는지는
  이벤트가 90초라 이 시험 안에서 못 봤다
* **갑자기 죽는 경우.** `docker kill` 이나 인스턴스 강제 종료처럼 유예가 없을 때는 큐를
  못 비운다. 그때 `gap` 이 얼마나 되고 회수가 메우는지 확인하지 않았다
* **종료 순서 결함.** 플러셔가 톰캣보다 먼저 멈춘다. 재고가 남은 채 종료되면 순번이 샌다.
  `getPhase()` 를 톰캣 아래로 내려야 한다. 배포 경로(`deploy.sh` 의 `systemctl stop`)가
  대상 그룹에서 빼지 않고 바로 멈추므로 배포마다 이 창을 지난다.
* **DB 장애의 `gap 693` 을 줄이는 길.** 쓰기 회로가 5,118건을 막아 이미 줄인 값이다.
  더 줄이려면 회로가 더 일찍 열려야 하는데, 그러면 정상 상황의 오판 위험이 커진다
* 장애에서 회복. 도중에 끊는 것은 쟀지만 다시 붙였을 때의 회복 속도는 재지 않았다
* 상한. 도착률 333건/초는 요구 조건이지 한계가 아니다
