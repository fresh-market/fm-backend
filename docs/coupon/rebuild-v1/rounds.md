# 재건을 고친 판으로 장애를 다시 주입한 회차 (2026-10-10)

**이 회차 묶음이 처음으로 승격 경로 재건의 소요를 재고, 그 재건이 스스로 카운터를 뒤로 미는
것을 잡았다.**

```
AWS 실측     20,000 VU / ramp 60초 / hold 30초 / 재고 10,000장 / 전용 인스턴스 3대
스프링 서버  fm-backend 453f2aaf 와 378aa35a.  재건 고침 넷이 들어 있다 (3장)
워밍업       requests=20000 concurrency=300 writeRows=10000.  코드 기본값이고 override 가 없다
시나리오     fm-backend main 8ed43e2 의 loadtest/issue.js, k6 v1.7.1
쿠폰         회차마다 번호를 바꿨다 (900009 ~ 900014).  근거는 6장이다
주입         k6 를 먼저 띄우고 그로부터 24초 뒤에 걸었다.  회차별 시각은 2장이다
대시보드     docs/coupon/rebuild-v1/rounds/
```

## 4. 승격 경로 재건의 소요

**팀이 재건 소요를 이번에 처음 잰 것은 아니다.** 2026-09-23 에 204밀리초를, 2026-10-01 에
3,458밀리초를 쟀다. **이번에 처음인 것은 캐시 페일오버로 걸린 재건을 잰 것**이다.

### 4.1 N-2 캐시 페일오버

```
REBUILT couponId=900010 issued=5792 queued=67 maxSeq=5859 freed=0
        rebuildMillis=716  contributeMillis=57  waitMillis=51  readWriteMillis=607

REBUILT couponId=900010 issued=5784 queued=22 maxSeq=5784 freed=-22
        rebuildMillis=244  contributeMillis=69  waitMillis=2   readWriteMillis=172
```

| 구간 | 첫째 | 둘째 |
|---|---:|---:|
| 올릴 것을 올리기 | 57 | 69 |
| 남의 것을 기다리기 | 51 | 2 |
| 읽고 쓰기 | 607 | 172 |
| **문을 닫아 둔 시간** | **716** | **244** |

**기여 대기가 51밀리초와 2밀리초다.** 조기 종료가 제대로 들었다. 2026-10-01 과 J-5 에서
천장 3초를 태우던 것이 사라졌고, 그것이 명부 세기를 재건 통로로 돌린 결과다.

**정지 시간의 주된 항목이 읽고 쓰기로 바뀌었다.** 607밀리초와 172밀리초다. 이 항목은 결번
수에 비례하므로 회차마다 달라진다.

### 4.2 P-1 복합 장애

```
REBUILT couponId=900014 issued=8681 queued=0  maxSeq=8681
        rebuildMillis=852  contributeMillis=288  waitMillis=8   readWriteMillis=555

REBUILT couponId=900014 issued=8703 queued=13 maxSeq=8716
        rebuildMillis=435  contributeMillis=27   waitMillis=25  readWriteMillis=382
```

**0.852초와 0.435초다.** 여기도 카운터가 8,681 에서 8,716 으로 올라갔다.

**재시도가 두 번 걸린 뒤 완주했다.** `COUPON_SEQ_REBUILD_RETRY` 가 2건이다. 두 장애가 겹쳐
Redis 가 더 느렸는데 `c1f8af9b` 의 재시도가 받아냈다. 그 고침이 없던 J-2 에서는 같은 자리에서
재건이 죽었다.

### 4.3 O-1 순번 키 유실

```
REBUILT couponId=900013 issued=9995 queued=0 maxSeq=9995 freed=0
        rebuildMillis=327  contributeMillis=8  waitMillis=107  readWriteMillis=210
```

**327밀리초다.** 부재 경로라 카운터가 아예 없는 상태에서 세운 것이고, 승격 경로보다 가볍다.

## 5. 재건이 한 장애에 여러 번 도는 것

**N-2 에서 재건이 같은 쿠폰에 두 번 돌았다.**

```
15:26:44.719  RECONNECT_DETECTED      인스턴스 A
15:26:45.591  REBUILD_STARTED         A 가 주도한다
15:26:45.836  REBUILT maxSeq=5784     A 가 끝냈다 (244ms)
15:26:45.975  RECONNECT_DETECTED      인스턴스 B.  A 가 끝난 뒤 139밀리초다
15:26:46.013  REBUILD_STARTED         B 가 주도한다
15:26:46.735  REBUILT maxSeq=5859     B 가 끝냈다 (716ms)
```

**카운터는 5,784 에서 5,859 로 올라갔다. 뒤로 가지 않았다.** 팀이 한때 이 순서를 거꾸로 읽어
"둘째가 카운터를 뒤로 밀었다" 고 적었는데 사실이 아니다.

**플러시가 두 번 멈춘 것이 이 회차의 실제 비용이다.** 244밀리초와 716밀리초로 약 1초다.

### 5.1 왜 여러 번 도나

**재연결 감시는 열린 선착순 이벤트가 있으면 무조건 재건을 띄운다.** 조건이 둘뿐이다.

```
그 인스턴스가 minInterval(10초) 안에 이미 띄웠나
열린 선착순 이벤트가 있나          findOpenLimitedEvents
```

**카운터가 멀쩡한지 안 본다.** 그것이 의도된 설계다. 승격은 카운터를 살려 두고 값만 뒤로
밀기 때문에 카운터를 관문으로 두면 그 경우가 영영 안 걸린다
(`CouponSeqRebuilder` 클래스 주석).

**그래서 막는 장치 셋이 이 경우를 다 통과한다.**

| 장치 | 왜 안 잡나 |
|---|---|
| `inProgress` 집합 | 인스턴스 안의 맵이다. 다른 JVM 을 모른다 |
| 재건 락 | 동시 실행만 막는다. 앞 재건이 풀면 다음 인스턴스가 또 주도자가 된다 |
| 감시의 `minInterval` | 인스턴스마다 따로 센다. A 의 타이머가 B 를 안 막는다 |

**횟수는 세 가지가 곱해져 정해진다.** 인스턴스 수, 열린 이벤트 수, 재연결 횟수다. N-2 는
둘이 돌았고, L-3 는 쿠폰이 여섯 개 열려 있어 다섯이 돌았다 (6.1).

### 5.2 여러 번 도는 것을 막지 않았음

**해로운 쪽과 헛된 쪽을 갈라야 한다.**

| | 무엇 | 실측 |
|---|---|---|
| 헛되다 | 둘째가 DB 를 다시 읽고 같은 값이나 더 높은 값을 낸다 | **N-2 가 그랬다** |
| 해롭다 | 둘째가 더 이른 스냅샷을 읽어 낮은 값을 쓴다 | **난 적이 없다** |

**팀은 횟수를 막지 않고 값만 막았다.** 막아 두면 그 사이 진짜 필요한 재건이 안 도는 위험이
생기는데, 그쪽이 더 나쁘다고 보았다.

```
전    counter = maxSeq                  무조건 덮는다
후    counter = max(counter, maxSeq)     coupon-open-gate.lua 가 원자적으로 한다
```

**읽는 순서와 쓰는 순서가 보장되지 않는 것이 근거다.** N-2 는 먼저 읽은 쪽이 먼저 써서
순서가 맞았지만 그것이 보장은 아니다. 비교를 Redis 안에 두면 왕복이 늘지 않는다.

**낮게 열려던 시도를 로그로 남긴다.** `COUPON_SEQ_GATE_KEPT_HIGHER couponId= mine= kept=` 다.
아직 실제로 뜬 적은 없다 (10장).

### 5.3 남은 비용

**재건이 도는 동안 그 이벤트의 플러시가 멈춘다.** N-2 는 두 번에 약 1초였다. 카운터가 멀쩡한
재연결에서도 이 비용을 낸다.

| 회차 | 건 장애 | 재건 횟수 | 플러시 정지 총량 |
|---|---|---:|---:|
| N-2 | 캐시 페일오버 | 2 | 0.960초 |
| P-1 | 복합 | 2 | **1.287초** |
| O-1 | 순번 키 유실 | 1 | 0.327초 |

**인스턴스가 3대인데 둘만 재연결을 보았다.** 세 번 돈 회차가 없고 정지 총량도 1.3초를 넘지
않는다.

**줄일 자리는 있다.** 둘째 재건은 첫째가 세운 카운터를 보고도 DB 를 다시 읽는다. 이 재연결에
대해 누가 이미 재건했다는 표시를 짧은 수명으로 남기면 둘째가 기여만 하고 돌아간다.

**팀은 넣지 않기로 했다.** 위 실측에서 정지 총량이 1.3초를 넘지 않아 막아서 얻는 것이 작고,
막아 두면 그 사이 진짜 필요한 재건이 안 도는 위험이 생긴다. 회차가 더 쌓여 세 번 넘게 도는
경우가 보이면 다시 판단한다.

### 5.4 로그의 freed 가 음수로 나온 것

```
REBUILT ... issued=5784 queued=22 maxSeq=5784 freed=-22
```

**`freed` 는 `maxSeq - issued - queued` 산술이고 실제 되살린 번호 수가 아니다.** 같은 회원이
DB 행과 큐 티켓을 동시에 가지면 음수가 된다. `writeFree` 에 넘기는 리스트는 `1..maxSeq` 중
아무도 안 쥔 번호라 음수가 될 수 없다. **로그가 보여 주는 수와 실제로 되살린 수가 다르다.**

## 6. 회차마다 쿠폰을 바꾸면 뒤처짐이 사라짐

**같은 쿠폰을 거듭 쓰면 장애가 없는 회차에도 뒤처짐이 쏟아졌다.** 2026-10-10 J-3 에서
1,130건이었고 원인은 `rebuild-v1/budget-breakdown.md` 6장에 있다.

| 회차 | 쿠폰 | 장애 | 뒤처짐 표본 |
|---|---|---|---:|
| J-3 | 900001 (재사용) | 없음 | **1,130** |
| L-1 | 900005 (새 번호) | 없음 | **0** |
| L-2 | 900006 | 없음. J-3 과 같은 자리다 | **0** |
| M-1 | 900008 | 캐시 페일오버 | 1.10 |
| N-1 | 900009 | 서버 1대 종료 | **0** |
| N-2 | 900010 | 캐시 페일오버 | 2.27 |
| N-3 | 900009 계열 | 서버 1대 종료 | **0** |
| N-4 | 900012 | 서버 1대 종료 | **0** |
| O-1 | 900013 | 순번 키 유실 | **0** |
| P-1 | 900014 | 복합 | 4.51 |

**무장애 회차 여섯이 모두 0 이다.** 앞서 본 천 단위는 전부 시험 환경이 만든 오탐이었다.

**장애 회차에서도 1 에서 5건이다.** 캐시 페일오버가 1.10 과 2.27, 복합이 4.51 이다.

### 6.0 이것이 재건에 붙일 조건을 채움

`measureBehind` 의 Javadoc 이 "정상 운영에서 이 표본이 0건이라는 것을 회차로 확인한 뒤에
붙인다" 는 조건을 적어 두었고, **위 표가 그 조건을 채운다.** 무장애에서 0 이고 장애에서도
몇 건이므로, 이 신호가 재건을 깨워도 "오탐이 곧 장애" 가 되지 않는다.

**붙이면 얻는 것은 감지 지연 37초다.** J-2 에서 플러시가 10:08:46.5 에 뒤처짐을 알았고
재연결 감시는 10:09:23 에 알았다. 그 사이 BEHIND 가 쏟아졌지만 아무도 재건으로 잇지 않았다.

**팀은 아직 붙이지 않았다.** 정할 것이 남아 있고 그것은 `rebuild-v1/budget-breakdown.md`
6.0 에 적었다.

### 6.1 그것이 만든 부작용

**회차마다 번호를 바꾸니 앞 회차 쿠폰이 열린 채로 쌓였다.** `reset.sql` 이 그 회차 쿠폰
하나만 내렸기 때문이다. 재연결 감시는 `findOpenLimitedEvents()` 로 **열린 이벤트를 모두**
찾으므로, 재연결 한 번에 재건이 쌓인 쿠폰 수만큼 떴다.

2026-10-10 L-3 에서 본 쿠폰이 900007 인데 재건이 900001 부터 900006 까지 다섯 개에 떴고,
재시도 20건과 실패 10건을 내는 동안 플러시가 반복 멈춰 명부가 1명으로 밀렸다. **결번 6 이
그래서 났다.**

**`reset.sql` 이 `coupon_id >= 900000` 전체를 내리게 고쳤다** (`0c98954c`). 그 뒤 M-1 에서
재건이 본 쿠폰 하나에만 떴고 재시도와 실패가 0 이 되었으며 결번도 0 으로 돌아왔다.

## 7. 복합 장애가 두 번 거부된 뒤 걸린 경과

**N-3 와 N-4 에서 캐시 페일오버가 거부됐다. 둘 다 서버 종료만 걸렸다.** 쿨다운을 두고 다시
건 P-1 에서 성공했다.

```
TestFailoverNotAvailableFault: Test failover already in progress
```

**사유는 쿨다운이다.** AWS 메시지가 말하는 그대로이고, 팀이 한때 24시간 5회 한도로 잘못
짚었다.

```
15:26:10   N-2 의 페일오버를 걸었다
15:26:30   완료 이벤트가 찍혔다
15:30:53   N-3 의 주입이 거부됐다       완료 4분 뒤인데도 거부다
15:36:56   N-4 의 주입이 거부됐다
16:23:24   팀이 다시 걸어 보니 통과했다   완료로부터 약 57분이다
```

**완료 이벤트가 찍힌 뒤에도 다음 호출을 받지 않는 구간이 있다.** 그 길이를 팀이 재지는
않았고, 위 실측으로는 4분에 거부되고 57분에 통과한다는 것만 안다.

**24시간 호출 수는 사유가 아니었다.** 그 구간에 8회를 호출했고 한도가 5회라 그것으로
설명했는데, 같은 24시간 안에서 뒤에 통과했으므로 그 설명이 틀렸다.

**`ReplicationGroups[0].Status` 로는 쿨다운을 못 가린다.** 거부 당시 `available` 이었고
노드그룹도 `available` 이었다. 가릴 방법을 팀이 아직 못 찾았다. 그래서 복합 장애를 걸 때는
앞 페일오버로부터 충분히 띄우는 것 말고는 수가 없다.

**이번에는 거부가 로그에 남았다.** 2026-10-02 의 G-3 는 같은 거부를 조용히 삼켜 "복합 장애"
로 기록됐는데, fm-infra `cbde01d` 가 사유를 띄우게 고친 덕에 이번에는 반쪽 주입을 그대로
기록하지 않았다.

**N-3 와 N-4 를 복합으로 읽으면 안 된다.** 서버 종료만 걸린 회차이고, 그래서 N-1 과 같은
조건이 세 번 돈 셈이 되었다.

### 7.1 P-1 이 성공한 조건

```
16:23:24   팀이 확인용으로 페일오버를 걸었다
16:23:42   완료 이벤트가 찍혔다
16:37:03   P-1 의 주입이 통과했다        완료로부터 13분 19초다
```

**완료 뒤 13분이면 통과했다.** N-3 는 4분에 거부됐으므로, 쿨다운은 4분과 13분 사이에서
풀린다. 팀이 그 경계를 더 좁히지는 않았다.

**회차를 연달아 돌리는 것이 거부의 원인이었다.** 회차 사이에 페일오버 완료를 확인하고 10분쯤
띄우면 이 멈춤이 사라진다.

### 7.2 거부된 두 회차가 준 값

| 회차 | 장애 | p99 | 결번 |
|---|---|---:|---:|
| N-1 | 서버 1대 종료 | 0.276초 | 0 |
| N-3 | 서버 1대 종료 | 0.342초 | 0 |
| N-4 | 서버 1대 종료 | 0.182초 | 0 |

**같은 조건에서 p99 가 0.182 에서 0.342초로 1.9배 흩어진다.** 단일 회차 p99 를 비교에 쓰지
말라는 기존 결론과 같은 방향이고, **결번은 세 번 모두 0 이다.**

## 8. 거절의 모양이 장애마다 다름

| 지표 | N-1 서버 종료 | N-2 캐시 페일오버 |
|---|---:|---:|
| 혼잡 비율 | 32.64% | **69.91%** |
| 게이트웨이 실패 | **12,420** | 7,723 |
| 포기 | 1,917 | **6,999** |
| 소진 응답 | **8,032** | 545 |
| 예상 못 한 응답 | 0 | 0 |

**서버가 죽으면 그 대로 가던 요청이 게이트웨이 실패로 끊긴다.** ALB 가 아직 그 대상을
빼지 못한 동안의 요청이다.

**캐시가 페일오버하면 전 인스턴스가 함께 느려져 혼잡으로 돌려보낸다.** 그래서 혼잡이 70% 에
닿고 포기가 늘지만, 게이트웨이 실패는 오히려 적다. 서버가 다 살아 있기 때문이다.

**N-1 의 소진 응답이 8,032 로 큰 것은 재고가 빨리 바닥났기 때문이다.** 한 대가 죽어도 남은
두 대가 재고를 다 내보냈고, 그 뒤에 온 요청이 소진을 받았다.

## 10. 팀이 못 본 것

**쿨다운 길이를 모른다.** 4분에 거부되고 13분에 통과한다는 것만 안다. 그 사이 어디서 풀리는지
재지 않았고, API 로 남은 시간을 보는 방법도 못 찾았다.

**낮은 값으로 문을 열려는 시도가 실제로 막히는 것을 못 봤다.** O-1 에서 재건이 한 번만 돌아
`GATE_KEPT_HIGHER` 가 뜨지 않았다. 그 상황은 재연결이 인스턴스마다 올 때 생기는데 페일오버
한도에 막혀 재현하지 못했다. 고침은 회귀 시험 둘로만 고정되어 있다.

**Lua 로직을 단위 시험으로 보지 못했다.** 실제 Redis 를 띄우는 시험이 이 저장소에 없어
`coupon-open-gate.lua` 의 비교 로직은 회차로만 확인했다.

**N-2 의 재건 둘 중 어느 것이 최종 카운터를 남겼는지 가리지 못했다.** 로그가 둘을 찍은
순서는 알지만 그 사이에 발급이 카운터를 얼마나 올렸는지는 이 회차 자료에 없다.
