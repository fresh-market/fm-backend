# 선착순 발급이 장애에 어떻게 반응하나

**발급은 경로가 따로라 장애 반응도 따로다.** 공통 원칙은
[../incident/failure-response.md](../incident/failure-response.md) 에 있고, 여기는 발급 경로만 적는다.

```
1. 둘로 나눈 회로                    couponSeq 와 couponWrite 를 왜 나눴나
2. 재고를 지키지 않고 발급을 막은 회로   오진이 진짜 장애를 만든 일
3. 무엇이 죽으면 진행 중인 발급이 어떻게 되나
4. 장애 주입과 계측
```

**여기 적은 수치는 장애의 크기를 말하는 것만이다.** 회차별 값은
[coupon-load-rounds.md](coupon-load-rounds.md), 설정값은 `application-coupon.yml` 의 주석이 갖는다.

---

## 1. 둘로 나눈 회로

```
couponSeq    Redis 실패를 센다
couponWrite  DB 쓰기 실패를 센다
```

**둘 다 막는 대상은 순번 확보 하나다. 플러시는 안 막는다.** 플러시를 막으면
**이미 큐에 들어간 요청까지 버리게 된다.** 그 요청들은 번호를 받았고 응답을 기다리는 중이라
버리면 그 번호가 통째로 묶인다.

**회로가 느린 것도 세야 한다.** Redis 가 완전히 죽는 것보다 느려지는 쪽이 흔한데, 그때 예외가 안 나면
회로가 안 열리고 **요청 스레드들이 전부 거기서 기다리며 요청 예산을 다 쓴다.**

**DB 회로가 중복 키를 세면 안 된다.** 재시도와 매핑 유실로 중복이 꾸준히 나오는 것이
이 설계의 정상 동작이라, 중복을 세면 **이벤트가 멀쩡할 때 회로가 열린다.**

**반열림 허가를 요청 스레드가 쓰면 안 된다.** 요청 스레드가 허가를 소비하면
**정작 플러시가 DB 를 시험해 볼 기회가 없어진다.**

## 2. 재고를 지키지 않고 발급을 막은 회로

**이 시험의 가장 큰 소득이다.** 팀이 같은 코드와 같은 차가운 JVM 에서 순번 확보 회로만 껐다.

| | 회로 켜짐 | 회로 꺼짐 |
|---|---:|---:|
| 혼잡 503 | 27,382 | **3** |
| 총 요청 | 45,202 | **20,003** |
| 발급 (DB 확인) | 8,870 | **10,000** |
| 살아남은 인스턴스 | 3 -> 2 | 3 유지 |

**재고가 멀쩡히 남은 상태로 앱이 27,382건을 거절하고 있었다.**

무엇이 잘못이었나. **회로의 느림 판정 기준은 Redis 가 느린지 보라고 정한 값인데,
회로가 실제로 잰 것은 호출을 감싼 구간 전체였다.** 거기에는 가상 스레드가 캐리어를 기다린
시간이 함께 들어간다.

```
차가운 JVM  ->  요청당 CPU 5배  ->  2 vCPU 포화
  ->  스케줄 대기가 측정에 섞임  ->  Redis 왕복 0.8ms 를 105~323ms 로 잰다
    ->  느린 호출 비율 100%  ->  회로 열림  ->  재고가 남아 있는데 503
      ->  재시도로 요청이 2.26배  ->  CPU 100%
        ->  헬스체크 초과  ->  ALB 퇴출, ASG 종료
```

**`0.8ms` 와 `105~323ms` 가 오진의 증거다.** 회로가 잰 값이 실제 왕복의 130배에서 400배다.
그 차이가 전부 앱 안에서 기다린 시간이다.

**회로가 자기 앱의 느림을 Redis 장애로 오진했고, 그 오진이 진짜 장애를 만들었다.**
그동안 ElastiCache 의 엔진 CPU 는 3.7% 였다.

**팀이 고친 방법은 회로를 떼는 것이 아니다.** `CouponSeqAllocator` 가 이 회로를
지표 전용 상태로 넘긴다. **판정과 지표는 그대로 두고 거절만 안 한다.**
무엇이 느렸는지는 여전히 보이면서 재고가 남은 요청을 안 돌려보낸다.

**여기서 규칙 하나가 나왔다.** 느림 문턱은 그 호출의 타임아웃보다 뒤여야 한다.

**팀이 이 오진을 밝히는 데 하루가 걸린 이유가 따로 있다.** 팀이 회로를 레지스트리 밖에서 만들어
**Micrometer 가 그것을 못 봤다.** 회로가 열려도 지표에 아무 흔적이 없어서,
순번 확보 실패가 회로 탓인지 Redis 탓인지 구분할 수 없었다. 설정을 스타터로 옮기자 지표가 붙었다.

## 3. 무엇이 죽으면 진행 중인 발급이 어떻게 되나

**평상시 순번 반납은 앱의 `catch` 가 맡는다.** 무엇이 죽느냐에 따라 그 경로가 끊기는 자리가 다르다.

| | 진행 중이던 발급 | 반납을 대신 맡는 쪽 |
|---|---|---|
| **앱 사망** | **큐째로 사라진다.** 응답도 못 간다 | 사용자 재시도. 안 오면 회수 |
| Redis 사망 | 전부 완료된다 | 복구 시 재건이 `free` 를 채운다 |
| RDB 사망 | 전부 실패한다 | 사용자 재시도. 안 오면 회수 |

**Redis 사망이 진행 중인 발급에 가장 무해하다.** 큐 항목이 번호와 회원과 응답 통로뿐이고
플러시 스레드는 DB 에만 쓰기 때문이다.

**반납 경로가 끊겨도 별도 배치가 필요 없다.** 앱 사망은 회수가 소진 시점에 풀고,
Redis 사망은 재건이 채운다. **각각 훅이 있다.**

### 재건이 끝날 때까지 멈추는 발급

**카운터가 서기 전까지 앱이 모든 요청을 거절한다.** 그래서 재건에 걸리는 시간이 곧 장애 시간이다.

```
기여 대기    3,000 ms   각 인스턴스가 자기 큐를 올리기를 기다리는 고정 시간
읽고 쓰기      427 ms   DB 를 읽고 네 키를 세운다
합계        약 3.4초
```

**대부분이 고정 대기라 코드를 빠르게 해도 별로 안 줄어든다.** 줄이려면 그 대기 값을 건드려야
하는데, 짧게 잡으면 큐를 아직 못 올린 인스턴스의 티켓이 빠진 채로 키가 선다.

**감지 시간은 여기에 안 들어 있다.** 요청이 도는 중에는 첫 거절이 곧 신호라 사실상 즉시지만,
트래픽이 뜸한 구간에 페일오버가 나면 그만큼 늦어진다.

> 경우별 상세와 RDB 사망 때 앱이 번호를 반납하지 않는 이유는 [coupon.md 8장](coupon.md),
> 재건 절차와 실측 근거는 [redis-promotion-rebuild.md](redis-promotion-rebuild.md) 에 있다.

## 4. 장애 주입과 계측

**팀은 AWS 에 인프라를 올려 가장 좋은 구성에 장애를 주입했다.** 앱 급사(SIGKILL),
캐시 Multi-AZ 페일오버, 둘을 겹친 것 셋이다.

**팀은 DB 페일오버를 뺐다.** DB 가 죽으면 애초에 발급이 안 되므로 잴 것이 없다.

### 장애 중이 아니라 회로가 닫힐 때 몰리는 실패

**캐시 페일오버 실측이 20초대인데 순번 확보가 막힌 구간은 45초를 넘었다.**

```
+15 ~ +45초   순번 확보가 통째로 막힌다.  번호가 안 나가니 충돌도 없다
+60초         회로가 닫히며 밀린 것이 쏟아진다.  실패가 전부 여기 몰린다
```

**차이가 회로다.** 캐시가 돌아와도 회로는 열린 상태를 유지할 시간을 기다렸다가
반열림으로 몇 건을 시험하고서야 닫힌다. **그리고 닫히는 순간 밀린 요청과 재시도가
한꺼번에 들어와 같은 회원의 요청이 겹친다.**

### 그래서 바뀐 회수 기준 시간

**값은 60초 그대로이고 근거가 바뀌었다.**

```
전   요청 예산보다 길어야 한다
후   장애가 끝나고 회로가 닫히는 구간보다 길어야 한다
```

**둘의 차이가 수십 배다.** 약한 쪽만 적혀 있어서 팀이 10초로 내렸다가 발급이 깨졌다.

**회수 가드가 무력해지기 때문이다.** 가드가 읽는 확정 표시는 `markCommitted` 가 붙이는데
**그것도 Redis 호출이라 Redis 가 죽으면 표시가 안 붙는다.** 회수는 표시가 없는 것을
버려진 번호로 보고 **이미 DB 에 있는 번호를 남에게 넘긴다.**

> 60초와 30초와 10초를 재서 고른 과정은 [coupon-reclaim-after.md](coupon-reclaim-after.md),
> 회차별 값은 [coupon-load-rounds.md](coupon-load-rounds.md) 에 있다.

### 결번이 무엇으로 이루어지나

**장애 회차에서 발급 못 한 건수는 두 가지로 갈린다.**

```
앱이 아는 것     DB 쓰기가 거부됐다.  지표로 확인된다
앱이 모르는 것   Redis 가 번호를 주고 응답이 유실됐다.  원리상 확인할 수 없다
```

**뒤엣것은 네트워크 너머 호출이라 "안 됐다" 와 "됐는데 못 들었다" 를 구분할 방법이 없다.**
그래서 회수가 뒤처리를 맡는 구조다.

**반납되는 것은 결번을 안 만든다.** 이미 발급된 회원의 번호와 남이 쓰는 번호는
반납 경로를 타고 되돌아와 다시 나간다.
