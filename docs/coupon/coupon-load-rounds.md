# 선착순 쿠폰: 부하와 장애 회차 기록 (2026-09-14)

계획은 [coupon-load-scenarios.md](coupon-load-scenarios.md) 에 있다. 이 문서는 그 계획을
실제로 돌린 결과다.

```
일시      2026-09-14 20:20 ~ 20:47 KST (11:20 ~ 11:47 UTC)
백엔드    2bb1ab3d  (#163 ~ #167 이 다 들어간 main)
구성      전용 t3.small 3대 / RDS db.t4g.micro Multi-AZ / ElastiCache cache.t4g.micro 2노드
부하      VU 20,000, ramp-up 60초, 재고 10,000, 회원 20,000
생성기    m7i-flex.large, 별도 호스트
```

**부하 조건은 요구사항이 정한 값이다.** `requirement.md` 가 재고 10,000 에 20,000명,
`ramp-up : 60s` 를 적고 **"주어진 요구사항이므로 임의로 고치지 않는다"** 고 못 박는다.
그래서 이 회차들은 프로파일을 바꾸지 않는다.

---

## 1. 결과 한눈에

| 회차 | 장애 | 발급 | `gap` | 회원 | 초과 발급 | SLO p99 |
|---|---|---:|---:|---:|---:|---:|
| B-1 | 없음 (첫 회차) | **10,000** | 0 | 10,000 | 0 | 0.724초 |
| B-2 | 없음 (기준선) | **10,000** | 0 | 10,000 | 0 | **0.361초** |
| F-1 | 앱 컨테이너 급사 | 9,999 | **1** | 9,999 | 0 | 0.359초 |
| F-2 | 캐시 완전 단절 | 5,707 | 0 | 5,707 | 0 | 0.328초 |
| F-3 | DB 완전 단절 | 5,591 | **732** | 5,591 | 0 | 0.525초 |
| F-4 | 앱 급사 + 캐시 단절 | 6,180 | **1** | 6,180 | 0 | 0.306초 |
| F-5 | 캐시 Multi-AZ 페일오버 | 7,310 | 0 | 7,310 | 0 | 0.779초 |
| F-6 | DB Multi-AZ 페일오버 | 5,809 | **1** | 5,809 | 0 | 0.491초 |

**여덟 회차 전부 초과 발급 0, 1인 2매 0 이다.** 회원 수가 언제나 발급 수와 같다.

**SLO p99 는 전 회차가 1초 아래다.** 가장 나쁜 것이 F-5 의 0.779초다.

---

## 2. 기준선은 두 번째 회차로 잡는다

```
B-1   p99 0.724초   혼잡 207건    전용 인스턴스가 막 뜬 직후
B-2   p99 0.361초   혼잡   9건    같은 조건 재실행
```

**두 배 차이가 난다.** B-1 은 인스턴스를 올린 직후라 JIT 와 커넥션 풀이 덜 데워진 상태였다.
한 번만 돌렸으면 0.724초를 기준선으로 삼을 뻔했다.

**그래서 기준선은 B-2 의 0.361초다.** "같은 회차를 두 번 돌린다" 규칙이 실제로 잡아낸 값이다.

---

## 3. 장애를 발급 한가운데에 걸었다

**지난 시도는 넷 다 소진 뒤에 걸려 무의미했다.** 원인이 둘이었다.

```
하나   재고 10,000 이 초당 333건에서 30초면 소진된다.  ramp 60초의 앞 절반이 발급 구간이다
둘     주입 시점을 "내가 SSM 명령을 보낸 때" 부터 셌다.  명령 전달과 k6 기동만큼 늦게 들어갔다
```

**이번에는 k6 가 실제로 시작한 시각을 박스에서 받아 거기서 셌다.**

```
k6+0초    k6 시작 (박스가 date +%s 를 돌려준다)
k6+2초    첫 요청
k6+17초   주입        발급 약 5,000장 (재고의 50%)
k6+37초   복구 명령    유지 20초
```

**여섯 회차 모두 주입이 `k6+17초` 에 들어갔다.** 발급이 절반쯤 나간 시점이고, 그 뒤로
5,000장이 남아 있어 **장애 중에도 발급이 이어지는지**를 볼 수 있다.

**복구 완료는 회차마다 달랐다(k6+40초 ~ k6+120초).** `iptables` 규칙을 전용 3대에서 각각
빼는 데 시간이 들어서다. 주입 시점은 정확했고 해제만 늦었다.

## 4. 앱을 어떻게 죽이느냐가 결과를 바꾼다

**`docker stop` 을 `docker kill` 로 바꿨다.**

```
docker stop   SIGTERM.  stop_grace_period 45초 안에 스프링이 큐를 비우고 내려간다
docker kill   SIGKILL.  큐에 있던 것이 그대로 사라진다
```

**바꾸자마자 `gap` 이 1 로 나왔다.** 우아한 종료였을 때는 0 이었다.

```
F-1   발급 9,999   max_seq 10,000   gap 1
```

**순번을 받았지만 DB 에 못 들어간 티켓이 1건 있었다는 뜻이다.** `coupon.md` 8장이
`queue-capacity` 를 "앱이 급사했을 때 잃는 건수의 상한" 이라고 적는데, **우아하게 내려가면
그 상한이 한 번도 시험되지 않는다.**

**저장소의 다른 문서들은 이미 `docker kill` 을 적고 있었다** (`operation-guideline.md`
OPS-2-01, `백엔드공통_앱과DB_장애대응구조.md`). `loadtest-fault.sh` 만 어긋나 있었고 이번에
맞췄다.

## 5. 장애 종류에 따라 잃는 것이 다르다

```
회차   장애              발급     재고 손실   gap    무엇이 막혔나
F-1   앱 급사            9,999        1       1    남은 2대가 받아 냈다
F-5   캐시 페일오버       7,310    2,690      0    수십 초 끊겼다가 새 노드로 붙었다
F-4   앱 급사 + 캐시      6,180    3,820      1
F-6   DB 페일오버         5,809    4,191      1
F-2   캐시 완전 단절      5,707    4,293      0    순번을 못 받아 발급이 멈췄다
F-3   DB 완전 단절        5,591    4,409    732    번호는 나갔는데 DB 에 못 썼다
```

### 앱 한 대는 거의 손실이 없다

**3대 중 1대가 죽어도 남은 2대가 받아 낸다.** 재고 손실 1장이다.

### 캐시가 끊기면 발급이 멈춘다

**순번을 Redis 가 내주기 때문이다.** 캐시에 못 닿으면 번호를 못 받고, 번호가 없으면 큐에도
못 들어간다. 그래서 **깨끗하게 멈춘다(`gap` 0).** 잘못 나가는 것이 없다.

### DB 가 끊기면 번호가 탄다

**`gap` 732 가 F-3 에서 나왔다.** Redis 는 번호를 계속 내주는데 플러시가 DB 에 못 써서
그 번호들이 버려진다. 여섯 회차 중 유일하게 세 자리 `gap` 이다.

**설계가 예상한 모양 그대로다.** 소진 시점에 회수가 이 번호들을 되살리는데, 이 회차는
소진까지 못 가서 회수가 돌지 않았다.

### 페일오버가 완전 단절보다 낫다

```
캐시   완전 단절 5,707   페일오버 7,310    +1,603장
DB     완전 단절 5,591   페일오버 5,809    +218장
```

**Multi-AZ 를 켠 값이 여기서 나온다.** `terraform.tfvars` 가 "장애 주입 시험의 reboot with
failover 가 이것 없이는 성립하지 않는다" 며 월 14.6 USD 를 더 내고 있는데, 그 비용이
캐시에서 1,603장을 더 파는 것으로 돌아왔다.

## 6. 장애 중 실패 응답은 ALB 가 낸 것이다

**상태 코드를 나눠 보면 앱이 잘못 답한 것이 아니다.**

```
회차   200     409      502      504     503(혼잡)
B-2   10,000    587        -        -         9
F-1    9,999  4,718    5,283        -         -
F-2    5,707      -     1,127    6,418    42,040
F-3    5,591  9,980        -        1    25,137
F-4    6,179      -    11,121        -    25,575
F-5    7,310      -     3,263    3,451    38,922
F-6    5,809 10,000        -        -    22,518
```

**502 는 ALB 가 죽은 컨테이너에서 응답을 못 받아 낸 것이고, 504 는 게이트웨이 타임아웃이다.**
앱이 500 을 던진 것이 아니다.

**F-1 에서 5,283명이 502 를 받았지만 재고는 9,999장이 나갔다.** 그 사람들이 못 받은 몫을
다른 사람들이 받았다는 뜻이고, **재고 관점의 손실은 1장**이다.

**503 은 혼잡이고 설계된 거절이다.** 그 요청들의 티켓은 큐에 남아 결국 발급된다.

## 7. 이 회차가 답하지 못한 것

**처리량(TPS)을 안 쟀다.** 요구사항이 `ramp-up : 60s` 로 부하 프로파일을 정해 두었고
**"도구와 처리량은 평가하지 않는다"** 고 적고 있다. 프로파일을 바꿔야 TPS 를 잴 수 있는데
그것은 요구 조건을 어기는 일이라 하지 않았다.

**상한을 안 찾았다.** 같은 이유다. 요구 부하에서 통과한다는 것만 안다.

**회복을 안 봤다.** 유지 20초를 물면 복구 시점이 소진 뒤가 된다. 회복까지 보려면 주입을
더 앞으로 당기고 유지를 짧게 해야 하는데, 그러면 장애 구간이 얕아진다. 이번 회차의 질문이
"장애 중에도 발급이 이어지는가" 하나여서 그쪽을 택했다.

**`gap` 이 회수로 메워지는지 안 봤다.** F-3 의 732개가 소진 시점에 되살아나야 하는데,
그 회차는 소진까지 못 갔다.
