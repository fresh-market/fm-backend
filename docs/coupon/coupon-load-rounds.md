# 선착순 쿠폰: 성능과 장애 회차 기록 (2026-09-14)

계획은 [coupon-load-scenarios.md](coupon-load-scenarios.md) 에 있다. 이 문서는 그 계획을
실제로 돌린 결과다.

```
일시      2026-09-14 22:30 ~ 23:28 KST
백엔드    2bb1ab3d  (#163 ~ #167 이 다 들어간 main)
구성      전용 t3.small 3대 / RDS db.t4g.micro Multi-AZ / ElastiCache cache.t4g.micro 2노드
부하      VU 20,000, ramp-up 60초, 재고 10,000, 회원 20,000 (요구사항 고정값)
회차      성능 14 + 종합 2 + 장애 3 = 19회
```

---

## 1. 결론

**워밍업이 유일하게 p99 를 움직인 변수다.** 나머지 셋은 회차 간 흔들림 안에 들어간다.

```
워밍업 끔     2.396 ~ 3.313초    SLO 1초 초과
워밍업 켬     0.302 ~ 0.518초    약 8배 개선

배치 윈도      10ms / 20ms / 40ms 가 서로 구별되지 않는다
큐 상한        20,000 / 2,000 이 서로 구별되지 않는다
플러시 스레드   1 / 2 가 서로 구별되지 않는다
```

**열아홉 회차 전부 초과 발급 0, 1인 2매 0 이다.**

---

## 2. 기준선의 흔들림이 판정의 기준이다

**같은 설정을 두 번 돌린 값이 이만큼 갈린다.**

```
W-on-1   0.518초
W-on-2   0.302초
폭       0.216초
```

**이 폭보다 작은 차이는 개선이 아니다.** 아래 모든 판정이 이 기준을 쓴다.

**한 번씩만 돌렸으면 틀렸을 것이다.** `Q-2000-1` 이 0.294초라 "큐를 줄이니 빨라졌다" 고
읽힐 뻔했는데 2차가 0.464초다.

---

## 3. W. 워밍업

| 회차 | 설정 | p99 | 발급 | 혼잡 | 판정 |
|---|---|---:|---:|---:|---|
| W-off-1 | `warmup.enabled=false` | **3.313초** | 10,000 | 508 | SLO 초과 |
| W-off-2 | 같음 | **2.396초** | 10,000 | 72 | SLO 초과 |
| W-on-1 | 기본값 | 0.518초 | 9,774 | 226 | 통과 |
| W-on-2 | 기본값 | **0.302초** | 10,000 | 0 | 통과 |

**워밍업 없이는 요구 부하를 못 버틴다.** p99 가 예산의 2.4~3.3배다.

**정확성은 안 깨진다.** 네 회차 다 `gap` 0 에 회원 10,000 이다. **느려질 뿐 잘못 나가지는
않는다.**

**워밍업이 하는 일은 로그로 확인했다.**

```
COUPON_WARMUP_DONE sent=3000 ok=3000 writeRows=5000 elapsedMs=15034
```

요청 3,000건으로 읽기 경로를 데우고, 행 5,000개를 넣었다 되돌려 쓰기 경로를 데운다.
**그 15초가 p99 를 8배 낮춘다.**

---

## 4. B. 배치 윈도

| 설정 | 회차 1 | 회차 2 |
|---|---:|---:|
| 10ms | 0.378초 | 0.493초 |
| **20ms (기준)** | 0.518초 | 0.302초 |
| 40ms | 0.439초 | 0.529초 |

**세 설정이 구별되지 않는다.** 여섯 값이 0.302~0.529 사이에 고르게 흩어져 있고, 설정별로
뭉치지 않는다.

**큐가 거의 안 차기 때문으로 본다.** 배치 윈도는 "얼마나 모았다가 쓸까" 를 정하는데,
모을 것이 없으면 값이 무의미하다. 지난 회차에서 큐 최대가 1~4 였다.

---

## 5. Q. 큐 상한

| 설정 | 회차 1 | 회차 2 | 발급 | 비고 |
|---|---:|---:|---:|---|
| **20,000 (기준)** | 0.518초 | 0.302초 | 10,000 | |
| 2,000 | 0.294초 | 0.464초 | 10,000 | 혼잡 0 |
| 500 | **0.852초** | 0.364초 | 10,000 | 1차에 혼잡 51, 예상 밖 779 |

**2,000 은 안전하다.** 발급 수도 p99 도 기준선과 구별되지 않고 혼잡이 0 이다.

**500 은 아니다.** 한 회차가 0.852초로 튀고 예상 밖 응답이 779건 나왔다.

### 성능이 아니라 손실을 줄이는 값이다

**이 값은 p99 를 바꾸지 않는다. 바꾸는 것은 앱이 급사했을 때 잃는 건수의 상한이다**
([coupon.md](coupon.md) 8장).

```
20,000 -> 2,000    성능은 그대로,  급사 때 잃는 상한이 10분의 1
```

**그래서 종합 구성에 이 값만 넣었다.**

## 6. T. 플러시 스레드

| 설정 | 회차 1 | 회차 2 | `gap` | 회원 |
|---|---:|---:|---:|---:|
| **1 (기준)** | 0.518초 | 0.302초 | 0 | 10,000 |
| 2 | 0.474초 | 0.369초 | 0 | 10,000 |

**구별되지 않는다.** 그리고 **2 에서도 정확성이 안 깨졌다.**

**이것이 이 회차의 실제 소득이다.** 플러시가 둘이면 같은 쿠폰의 티켓이 두 스레드에 갈리고
뒷정리가 쿠폰 단위로 묶여 있어 `gap` 이 날 수 있다고 봤는데, 안 났다.

**다만 지금 쓸 이유가 없다.** 큐가 안 차므로 스레드를 늘려도 할 일이 없다. **큐가 차기
시작하면 그때 쓸 수 있는 값이라는 것을 확인한 것이다.**

## 8. 장애 셋

**종합 구성에 걸었다.** 주입은 발급의 절반 지점(`k6+17초`), 유지 20초다.

| 회차 | 장애 | 발급 행 | `max_seq` | `gap` | 회원 | 초과 발급 | p99 |
|---|---|---:|---:|---:|---:|---:|---:|
| F-1 | 앱 컨테이너 급사 | 9,994 | **10,000** | **6** | 9,994 | 0 | 0.293초 |
| F-2 | 앱 급사 + 캐시 페일오버 | 9,997 | **10,000** | **3** | 9,997 | 0 | 0.264초 |
| F-3 | 캐시 Multi-AZ 페일오버 | 7,209 | 7,209 | 0 | 7,209 | 0 | 0.720초 |

**셋 다 초과 발급 0, 1인 2매 0 이다.**

### 발급 행이 10,000 인 회차는 없다. 그리고 그것이 정상이다

**발급 행은 DB 의 `member_coupon` 행 수다.** 실제로 쿠폰을 쥔 사람 수이고, 시드 스크립트가
이 질의로 센다.

```sql
SELECT COUNT(*) AS 발급행, MAX(issue_seq) AS 최대순번,
       MAX(issue_seq) - COUNT(*) AS 구멍, COUNT(DISTINCT member_id) AS 회원수
  FROM member_coupon WHERE coupon_id = 900001;
```

**`max_seq` 와 나눠 봐야 무엇을 잃었는지가 갈린다.**

```
F-1   번호 10,000 까지 나감   쿠폰 9,994장   6장은 번호만 타고 아무도 못 받았다
F-2   번호 10,000 까지 나감   쿠폰 9,997장   3장은 번호만 타고 아무도 못 받았다
F-3   번호  7,209 까지 나감   쿠폰 7,209장   2,791장은 번호조차 안 나갔다
```

**둘 다 재고 손실이다.** 다만 원인이 다르다. 앞엣것은 **번호를 태우고 잃었고**, 뒤엣것은
**애초에 안 팔았다.** 태운 번호는 다시 쓸 수 없다.

**그 6명과 3명은 쿠폰 대신 502 를 받았다.** 요청이 큐에 들어간 뒤 인스턴스가 죽어 응답이
안 갔다.

**앱 급사에서 `gap` 0 은 나올 수 없다.** `docker kill` 이 SIGKILL 이라 큐에 든 티켓은
반드시 사라진다. 0 이 되려면 죽는 순간 큐가 비어 있어야 하는데, **초당 333건이 들어오는
중에는 그럴 수 없다.**

**그래서 이 숫자가 `queue-capacity` 가 정하는 손실의 실측값이다.** 큐 상한 2,000 인 구성에서
실제로 잃은 것이 6장과 3장이다.

### 앱 한 대가 죽어도 손실이 0.1% 아래다

```
F-1   쿠폰 9,994 / 재고 10,000   손실 6장   0.06%
F-2   쿠폰 9,997 / 재고 10,000   손실 3장   0.03%
```

**남은 두 대가 받아 낸다.** 전용 3대 구성이 그것을 위해 있다. 죽은 한 대가 들고 있던 큐만큼만
잃는다.

### 캐시 페일오버가 가장 비싸다

```
F-3   발급 7,209   재고 손실 2,791장   p99 0.720초
```

**순번을 Redis 가 내주기 때문이다.** 캐시가 넘어가는 20초 동안 번호를 못 받아 발급이 멈춘다.
`gap` 이 0 인 것은 **번호를 안 받았으니 태울 것도 없다**는 뜻이다.

**이것이 이 설계의 가장 아픈 자리다.** 앱이 죽으면 0.06% 를 잃고, 캐시가 넘어가면 28% 를
못 판다.

### DB 페일오버는 안 돌린다

**DB 가 막히면 발급이 안 되는 것이 자명하다.** 순번은 Redis 가 내주므로 번호는 계속 나가고
플러시가 못 써서 그 번호들이 탄다. **재는 값이 "얼마나 많이 타는가" 뿐이고, 그것은 장애
길이에 비례할 뿐 설계 판단을 바꾸지 않는다.**

**그리고 주입 시점을 맞추기 어렵다.** `reboot-db-instance` 는 호출과 실제 재시작 사이가
82초여서 발급 구간(30초) 안에 넣을 수 없다. 캐시의 `test-failover` 가 20초 만에 끝나는
것과 다르다.

## 9. 복구에 걸린 시간

```
캐시 페일오버   API 14:20:09 -> 완료 14:20:29    20초
재건           한 번도 안 돌았다
```

**재건 로그가 세 인스턴스 모두 0건이다.**

```
COUPON_SEQ_REBUILD_STARTED   없음
COUPON_SEQ_REBUILT           없음
COUPON_SEQ_REBUILD_SKIPPED   없음
```

**페일오버는 복제본이 데이터를 갖고 승격되므로 카운터가 살아남는다.** 재건의 방아쇠가
카운터 부재인데 그 조건이 안 생긴다. **"재건이 필요 없었다" 가 이 회차의 답이다.**

**이것이 Multi-AZ 를 켠 값이다.** 카운터가 사라졌다면 재건이 DB 를 통째로 읽어 네 키를
다시 세워야 하고, 그동안 발급이 멈춘다.

## 10. 이 회차가 답하지 못한 것

**개선의 상한을 못 올렸다.** 워밍업 말고는 움직이는 변수가 없었다. 요구 부하에서 혼잡 0,
연결 실패 0, 큐가 거의 안 차는 상태라 **병목이 이 셋 중에 없다.**

**더 올리려면 부하를 키워야 하는데 요구사항이 프로파일을 고정했다.** 큐가 차기 시작해야
배치 윈도와 플러시 스레드가 의미를 갖는다.

**예상 밖 응답이 장애 회차에서 나왔다** (F-1 4,865건, F-2 5,084건, F-3 6,012건). 지난
회차에서 확인한 대로 ALB 가 낸 502/504 이고 앱이 500 을 던진 것이 아니다. 이번에는 상태
코드를 따로 안 갈랐다.

**큐를 Redis 에 두는 대안은 안 봤다.** 구현이 없어서다
([coupon-load-scenarios.md](coupon-load-scenarios.md) 12장).
