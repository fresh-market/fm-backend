# 선착순 쿠폰: 성능과 장애 회차 기록 (2026-09-14)

계획은 [coupon-load-scenarios.md](coupon-load-scenarios.md) 에 있다. 이 문서는 그 계획을
실제로 돌린 결과다.

```
일시      2026-09-14 22:30 ~ 23:28 KST
백엔드    2bb1ab3d  (#163 ~ #167 이 다 들어간 main)
구성      전용 t3.small 3대 / RDS db.t4g.micro Multi-AZ / ElastiCache cache.t4g.micro 2노드
부하      VU 20,000, ramp-up 60초, 재고 10,000, 회원 20,000 (요구사항 고정값)
회차      성능 14 + 종합 2 + 장애 3(재실행) = 19회
```

---

## 1. 결론

**워밍업이 유일하게 p99 를 움직인 변수다.** 나머지 셋은 회차 간 흔들림 안에 들어간다.

```
워밍업 끔     2.396 ~ 3.313초    SLO 1초 초과
워밍업 켬     0.302 ~ 0.518초    약 8배 개선

배치 윈도      10ms / 20ms / 40ms 가 서로 구별되지 않는다
큐 상한        20,000 / 2,000 이 서로 구별되지 않는다
플러시 스레드   1 / 2 가 서로 구별되지 않는다
```

**열아홉 회차 전부 초과 발급 0 이고 1인 1매가 지켜졌다.**

---

## 2. 판정의 기준이 되는 기준선의 흔들림

**이 시험이 같은 설정을 두 번 돌렸는데 값이 이만큼 갈렸다.**

```
W-on-1   0.518초
W-on-2   0.302초
폭       0.216초
```

**이 폭보다 작은 차이는 개선이 아니다.** 아래 모든 판정이 이 기준을 쓴다.

**이 시험이 한 번씩만 돌렸으면 틀린 결론을 냈을 것이다.** `Q-2000-1` 이 0.294초라 "큐를 줄이니 빨라졌다" 고
읽힐 뻔했는데 2차가 0.464초다.

---

## 3. W. 워밍업

| 회차 | 설정 | p99 | 발급 | 혼잡(503) | 판정 |
|---|---|---:|---:|---:|---|
| W-off-1 | `warmup.enabled=false` | **3.313초** | 10,000 | 508 | SLO 초과 |
| W-off-2 | 같음 | **2.396초** | 10,000 | 72 | SLO 초과 |
| W-on-1 | 기본값 | 0.518초 | 9,774 | 226 | 통과 |
| W-on-2 | 기본값 | **0.302초** | 10,000 | 0 | 통과 |

**워밍업 없이는 요구 부하를 못 버틴다.** p99 가 예산의 2.4~3.3배다.

**정합성은 안 깨진다.** 네 회차 다 `gap` 0 에 회원 10,000 이다. **느려질 뿐 잘못 나가지는
않는다.**

**워밍업이 무엇을 하는지는 앱이 로그로 찍는다.**

```
COUPON_WARMUP_DONE sent=3000 ok=3000 writeRows=5000 elapsedMs=15034
```

워밍업 러너가 요청 3,000건으로 읽기 경로를 데우고 행 5,000개를 넣었다 되돌려 쓰기
경로를 데운다.
**그 15초가 p99 를 8배 낮춘다.**

---

## 4. B. 배치 윈도

| 설정 | 회차 1 | 회차 2 |
|---|---:|---:|
| 10ms | 0.378초 | 0.493초 |
| **20ms (기준)** | 0.518초 | 0.302초 |
| 40ms | 0.439초 | 0.529초 |

**세 설정이 구별되지 않는다.** 여섯 값이 0.302~0.529 사이에 고르게 흩어져 있고 설정별로
뭉치지 않는다.

**큐가 거의 안 차기 때문이라고 이 시험은 본다.** 배치 윈도는 "얼마나 모았다가 쓸까" 를 정하는데,
모을 것이 없으면 값이 무의미하다. 지난 회차에서 큐 최대가 1~4 였다.

---

## 5. Q. 큐 상한

| 설정 | 회차 1 | 회차 2 | 발급 | 비고 |
|---|---:|---:|---:|---|
| **20,000 (기준)** | 0.518초 | 0.302초 | 10,000 | |
| 2,000 | 0.294초 | 0.464초 | 10,000 | 혼잡 0 |
| 500 | **0.852초** | 0.364초 | 10,000 | 1차에 혼잡 51, 예상 밖 779 |

**2,000 은 안전하다.** 발급 수도 p99 도 기준선과 구별되지 않고 혼잡(503)이 0 이다.

**500 은 아니다.** 한 회차가 0.852초로 튀고 예상 밖 응답이 779건 나왔다.

### 성능이 아니라 손실을 줄이는 값

**이 값은 p99 를 바꾸지 않는다. 바꾸는 것은 앱이 급사했을 때 잃는 건수의 상한이다**
([coupon.md](coupon.md) 7장).

```
20,000 -> 2,000    성능은 그대로,  급사 때 잃는 상한이 10분의 1
```

**그래서 이 시험은 종합 구성에 이 값만 넣었다.**

---

## 6. T. 플러시 스레드

| 설정 | 회차 1 | 회차 2 | `gap` | 회원 |
|---|---:|---:|---:|---:|
| **1 (기준)** | 0.518초 | 0.302초 | 0 | 10,000 |
| 2 | 0.474초 | 0.369초 | 0 | 10,000 |

**두 설정이 구별되지 않는다.** 그리고 **플러시 스레드가 둘이어도 정합성이 안 깨졌다.**

**이것이 이 회차의 실제 소득이다.** 플러시가 둘이면 같은 쿠폰의 티켓이 두 스레드에 갈리고
뒷정리가 쿠폰 단위로 묶여 있어 `gap` 이 날 수 있다고 이 시험은 봤는데, 안 났다.

**다만 지금 쓸 이유가 없다.** 큐가 안 차므로 스레드를 늘려도 할 일이 없다. **큐가 차기
시작하면 그때 쓸 수 있는 값이라는 것을 이 회차가 확인했다.**

| FINAL-1 | 0.374초 | 10,000 | 0 | 10,000 | 0 | 0 |

**두 회차 다 완주했다** (k6 정상 종료). 요구 부하에서 거절이 한 건도 없다.

## 8. 장애

**이 시험이 종합 구성에 장애를 걸었다.** 장애를 일으키는 것을 "주입" 이라고 쓴다. 주입은 돌리는
쪽이 컨테이너를 죽이거나 페일오버를 부르는 그 순간이다.

```
주입 시점   k6+17초.  발급이 절반쯤 나간 지점이다
유지        20초
```

| 회차 | 장애 | 발급 | `max_seq` | `gap` | 회원 | 초과 발급 | p99 |
|---|---|---:|---:|---:|---:|---:|---:|
| F-1b | 앱 컨테이너 급사 | **10,000** | 10,000 | 0 | 10,000 | 0 | 0.522초 |
| F-2e | 캐시 Multi-AZ 페일오버 | 9,989 | 10,000 | 11 | 9,989 | 0 | **1.041초** |
| F-3c | 앱 급사 + 캐시 Multi-AZ 페일오버 | 9,031 | 9,035 | 4 | 9,031 | 0 | 0.321초 (200) |

**셋 다 초과 발급 0 이고 1인 1매가 지켜졌다.**

### 502 를 다시 쏘는 것이 전제

**`issue.js` 가 502 와 504 를 재시도한다.** ALB 가 낸 응답이라 앱이 답을 못 한 것이다.
실제 사람은 실패하면 다시 누른다.

**안 쏘면 회수가 시험되지 않는다.** 죽은 인스턴스의 큐에 있던 티켓은 번호를 태우는데,
그 번호는 **소진 뒤에 들어온 요청이 있어야 되살아난다.** 502 를 받은 VU 가 그대로
잠들면 그 경로가 영영 안 돈다.

**F-1b 의 `gap` 0 이 그 결과다.** 태워진 번호를 회수가 되살렸고 다시 쏜 VU 가 가져갔다.

### 지연을 대가로 내는 재시도

```
F-2e   발급 9,989장   p99 1.041초   SLO 1초를 넘었다   혼잡 52,667건
```

**재시도가 재고를 되찾는 대신 응답을 늦춘다.** 부하 생성기가 502 를 받고 1초 쉬었다 다시
쏘므로 그 VU 의 반복 시간이 그만큼 늘어난다.

**이것이 맞바꿈이다.** 이 시스템은 재고를 다 파는 것과 p99 1초를 동시에 지키지 못한다.
**장애 중에는 앞엣것이 맞다고 이 시험은 본다.** 다만 SLO 판정은 정상 회차로 하는 것이지 장애 회차로 하는 것이 아니다.

### 보장이 아닌 회수

**회수는 소진 뒤에 들어온 요청이 있어야 돈다.** 그 타이밍이 회차마다 달라지므로 `gap` 0 은
운이 좋았던 것이지 구조가 약속하는 값이 아니다.

**`max_seq` 는 회차마다 10,000 이다.** 번호는 끝까지 나갔고 그중 몇 장이 DB 에 못 들어갔느냐만
갈렸다.

### 캐시가 넘어갈 때 멈추는 발급

**순번을 Redis 가 내주기 때문이다.** 페일오버 20초 동안 앱이 번호를 못 받는다. 그 구간의 요청이
전부 재시도로 돌아와 혼잡 52,667건과 p99 1.041초를 만들었다.

**그래도 재고는 9,989장이 나갔다.** 페일오버가 짧고 재시도가 있으면 이 시스템은 거의 다 판다.

### 간격을 둬야 걸리는 조합 장애 (F-3c)

**앞선 시험이 "연속 호출 제한 때문에 조합을 못 돌린다" 로 접었던 회차다.** 그 판단은 그
세션 안에서만 참이었다. 이 시험이 2026-09-15 에 다시 걸어 보니 **간격만 충분하면 걸린다.**

```
02:05:59   앱 컨테이너 급사 (SIGKILL)   k6+20초.  남는 대수 2
02:06:03   캐시 페일오버 호출            k6+24초
02:06:23   페일오버 완료                 k6+44초
02:06:27   복구
```

**쿨다운이 생각보다 길다.** 이 시험이 네 번 시도해서 두 번 거부당했다.

```
01:15:49   1차 페일오버 완료
01:20:14   거부  TestFailoverNotAvailableFault: Test failover already in progress
01:23:02   거부  같은 오류
02:06:03   성공  48분 뒤
```

**ElastiCache 가 페일오버를 마친 뒤에도 최소 7분 넘게 거부한다.** "연속 호출을 거부한다" 가 아니라 **"완료 후에도
한동안 거부한다"** 가 맞다. 조합 회차를 반복하려면 돌리는 쪽이 그 간격을 일정에 넣어야 한다.

### 두 장애가 겹치면 남는 재고

```
F-1b   앱 급사만        발급 10,000    다 팔았다
F-2e   캐시 페일오버만  발급  9,989    거의 다 팔았다
F-3c   둘 다            발급  9,031    969장이 남았다
```

**정합성은 그대로다.** 초과 발급 0, 1인 1매 유지, `gap` 4. 무너지는 것은 판매량이다.

응답 경로별로 나눠 보면 무슨 일이 있었는지가 드러난다.

| 응답 | 건수 | p99 | p95 | 최대 |
|---|---:|---:|---:|---:|
| 200 발급 | 9,017 | 0.321초 | 0.108초 | 0.810초 |
| 502 (ALB) | 9,731 | 0.544초 | 0.277초 | 1.431초 |
| 503 혼잡 | 18,319 | 0.843초 | 0.835초 | 1.693초 |
| **합계** | **37,067** | | | |

**409(소진)가 한 건도 없다.** 재고가 안 바닥났기 때문이다. VU 20,000 이 37,067건을 쐈고
그 차이가 전부 502/503 재시도다.

**502 는 죽인 인스턴스의 몫이다.** 앱이 셋에서 둘로 줄었고 그 사이 ALB 로 들어간 요청이
9,731건 실패했다. **503 이 그보다 두 배 많은 것이 캐시 페일오버의 몫이다.** 순번을 Redis 가
내주므로 페일오버 구간에는 앱이 번호를 못 받는다.

**p99 는 200 기준 0.321초로 SLO 안이다.** 다만 읽는 쪽이 이 숫자를 정상 회차와 나란히
놓으면 안 된다.
**답을 못 받은 요청이 28,050건**이고 그 요청은 이 p99 에 안 들어간다.

## 9. 복구에 걸린 시간

```
캐시 페일오버   API 14:20:09 -> 완료 14:20:29    20초
재건           한 번도 안 돌았다
```

**재건 로그가 세 인스턴스 모두 0건이다.**

```
COUPON_SEQ_REBUILD_STARTED   없음
COUPON_SEQ_REBUILT           없음
COUPON_SEQ_REBUILD_SKIPPED   없음
```

**페일오버는 복제본이 데이터를 갖고 승격되므로 카운터가 살아남는다.** 재건의 방아쇠가
카운터 부재인데 그 조건이 안 생긴다. **"재건이 필요 없었다" 가 이 회차의 답이다.**

**이것이 Multi-AZ 를 켠 값이다.** 카운터가 사라졌다면 재건이 DB 를 통째로 읽어 네 키를
다시 세워야 하고 그동안 발급이 멈춘다.

---

## 10. 이 회차가 답하지 못한 것

**이 시험은 개선의 상한을 못 올렸다.** 워밍업 말고는 움직이는 변수가 없었다. 요구 부하에서 혼잡(503) 0,
연결 실패 0, 큐가 거의 안 차는 상태라 **병목이 이 셋 중에 없다.**

**더 올리려면 돌리는 쪽이 부하를 키워야 하는데 요구사항이 프로파일을 고정했다.** 큐가 차기 시작해야
배치 윈도와 플러시 스레드에 의미가 생긴다.

**DB 페일오버는 이 시험이 안 걸었다.** DB 가 막히면 발급이 안 되는 것이 자명하다. 재는 값이
"번호가 얼마나 타는가" 하나여서 장애 길이에 비례할 뿐이다. `reboot-db-instance` 는 호출과
실제 재시작 사이가 82초여서 발급 구간 30초 안에 넣을 수도 없다.

**큐를 Redis 에 두는 대안은 이 시험이 안 봤다.** 구현이 없어서다
([coupon-load-scenarios.md](coupon-load-scenarios.md) 12장).
