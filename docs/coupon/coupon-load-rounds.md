**모든 회차에서 초과 발급 0, 1인 2매 0, 번호 유실 0 이다.**

**SLO p99 는 전 회차가 1초 아래다.** 유효한 회차 중 가장 나쁜 것이 F-1 의 0.693초로
예산의 69% 다. 무효인 S1-2 를 넣어도 0.757초로 넘지 않는다.

**혼잡(503)은 F-4 의 36건이 전부다.** 나머지 여덟 회차는 0 이고, 그 36건도 티켓이 큐에
남아 결국 발급됐다.

### p99 는 어떻게 뽑았나

**`loadtest-export.sh` 의 값을 그대로 쓰면 안 된다.** 그 스크립트는 시간 창 안의 모든 계열을
합쳐 `max` 를 잡는데, 회차 간격이 창보다 짧으면 **앞 회차의 최댓값을 집는다.**

```
S0-2   export 0.3138   <- 실제로는 S0-1 의 값이다
S0-2   실제   0.2705
```

**그래서 `round` 태그로 가른 뒤 `query_range` 로 회차마다 따로 뽑았다.**

```
query_range(k6_coupon_settled_duration_p99, step=15s)  -> 회차별 계열의 max
```

**`query` (instant) 도 쓰면 안 된다.** 최근 5분 안에 표본이 있는 계열만 돌려주고, 값도
그 시점의 표본 하나라 최댓값이 아니다. S1-1b 를 0.258 로 잘못 읽었던 것이 이것이다.

## 3. 처리율은 이 시험으로 못 잰다

**처음에는 650건/초를 처리했다고 적었다. 그 숫자는 틀렸다.**

rate 창을 바꾸면 값이 따라 움직인다.

```
회차      rate[10s]   rate[15s]   rate[30s]   목표 도착률
S1-1a        665         650         434        667/s
S1-1b        816         646         423      1,000/s
```

**원인은 부하의 모양이다.** `issue.js` 는 `ramping-vus` 로 VU 를 올리고 각 VU 가 한 번만
쏜다. 그래서 부하가 **삼각형**이고 일정한 속도로 유지되는 구간이 없다.

```
constant-arrival-rate   ───────────   평평한 구간에서 TPS 를 읽는다
ramping-vus + 1회 발사   ╱╲            평평한 구간이 없다.  창이 답을 정한다
```

**평균으로 내려도 안 된다.** 총 요청을 계열이 존재한 시간으로 나누면 30건/초쯤인데, 그건
램프가 끝난 뒤 아무도 안 쏘는 구간까지 분모에 넣은 값이다.

### 그래서 무엇을 말할 수 있나

```
말할 수 있다   요구 조건(재고 10,000 / 회원 20,000 / ramp 60초)을 SLO 안에서 처리했다
             램프를 20~30초로 줄여도 거절 0건이었다
말할 수 없다   초당 몇 건까지 처리하는가
```

**TPS 를 재려면 시나리오를 바꿔야 한다.** `constant-arrival-rate` 로 일정 속도를 유지하며
올리고, 평평한 구간에서 읽어야 한다. 그것은 이 회차의 설계에 없었다.

## 4. 도착률을 올려도 발급 경로는 안 힘들어진다

**이것이 이번 회차의 가장 중요한 발견이다.**

```
333건/초     p99 0.314 / 0.271
667건/초     p99 0.436
1,000건/초   p99 0.334      <- 오히려 내려갔다
```

**단조가 아니다.** 재고가 10,000 으로 고정이라, 도착률을 올리면 **더 빨리 소진되고 그 뒤의
요청은 전부 410 이라는 싼 경로로 빠진다.** 발급 경로를 지나는 요청 수는 어차피 10,000 이라
안 늘고, 비싼 구간만 짧아진다.

**그래서 도착률은 이 시스템의 부하를 키우는 지렛대가 아니다.** 재고가 지렛대다.

## 5. 재고를 올리는 회차(S1-2)는 못 돌렸다

**부하 생성기가 OOM 으로 죽는다.**

```
dmesg   Out of memory: Killed process 2754 (k6)  anon-rss 7,467,352kB
집계된 발급  523건에서 끊겼다
```

재고를 20,000 으로 올리면 **모든 요청이 발급 경로를 타고 싼 410 경로가 사라진다.** k6 가
in-flight 응답을 그만큼 더 들고 있어야 해서 8 GB 를 넘긴다.

**이것은 예고된 제약이다.** `fm-infra` 의 `variables.tf` 가 적어 두었다.

> 확정값은 `m7i.xlarge` (4 vCPU / 16 GB) 였고 실측에서 나온 값이었다. 그런데 이 계정이
> 프리 티어라 `RunInstances` 가 거부한다. 띄울 수 있는 것 중 메모리가 가장 큰 것이
> `m7i-flex.large` 8 GB 다.
>
> 하나. 메모리 여유가 얇다. 2만 VU 에 5.0 GB 를 썼으니 8 GB 의 63% 다.
> **실제 서버는 응답이 밀려 in-flight 버퍼가 더 잡히므로 이보다 오른다.**

**요구 조건 회차(재고 10,000)도 끝에서 죽는다.** 다만 그때는 이미 모든 요청을 보낸 뒤라
DB 결과와 Prometheus 값이 온전하다. 재고를 올리면 보내는 도중에 죽어 회차가 무효가 된다.

**계정을 유료로 올리기 전에는 이 회차를 못 한다.**

## 6. 장애 넷을 걸었다. 다만 주입 시점이 늦었다

**튜닝으로 바꾼 값이 없어서 기본 구성이 곧 이긴 구성이다.** 혼잡이 0 이고 큐가 4까지만
차서 조일 데가 없었다.

```
F-1  앱 1대 정지        발급 10,000  gap 0  회원 10,000   p99 0.693초
F-2  캐시 차단 (3대 전부) 발급 10,000  gap 0  회원 10,000   p99 0.555초
F-3  DB 차단 (3대 전부)  발급 10,000  gap 0  회원 10,000   p99 0.496초
F-4  앱 1대 + 캐시      발급 10,000  gap 0  회원 10,000   p99 0.431초, 혼잡 36건
```

### 이 결과를 무엇으로 읽어야 하나

**주입 시점이 발급 완료 뒤였다.** 시각을 맞춰 보면 이렇다.

```
회차   발급 완료(UTC)   장애 주입(UTC)   차이
F-1     07:50:29        07:51:04       +35초
F-2     07:54:29        07:55:09       +40초
F-3     07:58:59        07:59:37       +38초
F-4     08:04:14        08:05:03       +49초
```

**재고가 램프 도중에 소진되기 때문이다.** 333건/초에 재고 10,000 이라 **발급이 시작 25~30초
만에 끝난다.** 램프는 60초이므로 소진 뒤로도 30초가 남고, 그 뒤에 장애가 들어갔다.

**주입 지연도 있었다.** 주입 시각을 SSM 명령을 보낸 시점부터 셌는데, 명령 전달과 k6 기동
(토큰 20,000장 로드)에 시간이 든다. 그만큼 늦게 들어갔다.

**그래서 이 회차가 증명한 것은 아래 뒤엣것이다.**

```
증명 안 됨   장애 중에도 발급이 계속된다
증명 됨      이미 발급된 것이 장애로 망가지지 않는다
```

**뒤엣것도 값어치가 없지는 않다.** 앱 1대가 죽고 캐시와 DB 가 끊긴 상태에서도 발급 10,000,
`gap` 0, 회원 10,000 이 유지됐다. 롤백도 유실도 없었다.

**그리고 p99 도 다시 읽어야 한다.** 장애 구간에 남아 있던 요청은 전부 소진(410) 경로라,
0.693초는 **발급 경로가 아니라 소진 경로의 지연**이다.

### 제대로 재려면

```
지금      ramp 60초, 재고 10,000   ->  30초에 소진, 그 뒤에 주입
고쳐야     소진 전에 주입한다.  두 방법이 있다
  가      재고를 늘려 발급 구간을 길게 만든다.  생성기 메모리가 막는다(5장)
  나      k6 시작 시각을 받아 그 기준으로 주입 시점을 센다.  발급 구간 한가운데를 노린다
```

**나가 지금 할 수 있는 쪽이다.** 발급 구간이 25~30초이므로 k6 시작 후 10~15초에 넣으면
한가운데다.

## 7. 이 회차가 정하지 못한 것

**상한을 못 찾았다.** 혼잡이 한 번도 안 나서 어디서 무너지는지 모른다. 그리고 처리율 자체를
이 부하 모양으로는 못 잰다(3장).

**발급 도중의 장애를 못 봤다.** 넷 다 소진 뒤에 걸렸다(6장). 다시 돌려야 한다. 도착률로는 못 올리고
(3장) 재고로 올리려면 생성기가 더 커야 한다(4장).

**그래서 단계 2 의 튜닝 회차를 못 돌렸다.** 조일 곳을 지목해 줄 신호가 안 나왔다. 다만
`queue-capacity` 만은 측정으로 답이 나왔다.

```
queue-capacity   20,000
실측 큐 최대      1 ~ 4
```

**세 자릿수만큼 크다.** 이 값은 앱이 급사했을 때 잃는 건수의 상한이므로, 줄이면 성능은 그대로고
손실만 준다. 다만 이번 회차는 혼잡이 없던 회차라, **혼잡한 회차에서 큐가 얼마나 자라는지를
보고 정해야 한다.** 지금 값으로 2,000 을 권하기에는 근거가 얇다.

**단계 3(대수 대 처리량)도 못 돌렸다.** 3대에서 이미 놀고 있어 1대로 줄여도 통과할 가능성이
높은데, 그것을 재려면 회차가 더 필요하다.
