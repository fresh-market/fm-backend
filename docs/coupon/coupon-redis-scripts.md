# 선착순 발급이 쓰는 Lua 스크립트

**스크립트 넷이 있다.** 무엇을 묶는지, 언제 누가 부르는지, 왜 나눠 부르지 않는지를 적는다.

키가 무엇을 담는지는 [coupon-redis-keys.md](coupon-redis-keys.md) 에 있고, 설계의 근거는
[coupon.md](coupon.md) 에 있다. 여기는 **묶음의 단위**만 다룬다.

---

## 1. 넷 한눈에

| 스크립트 | 누가 부르나 | 언제 | 묶는 명령 | 요청 예산 |
|---|---|---|---|---|
| `coupon-issue-seq.lua` | 요청 스레드 | 번호를 받을 때마다 | 최대 10 | 밖 |
| `coupon-mark-committed.lua` | 플러시 스레드 | 배치를 커밋한 뒤 | 2 | **안** |
| `coupon-drop-mapping.lua` | 플러시 스레드 | 배치 끝, 순번 충돌 뒷정리 | 2 | 밖 |
| `coupon-return-and-repair.lua` | 플러시 스레드 | 중복 해소, 티켓마다 | 5 | 밖 |

**"요청 예산" 은 `commit-wait` 기준이다.** 안에 있으면 그 왕복이 사용자 응답 시간에 들어가고
계층 산식에 잡힌다. 지금 안에 있는 것은 확정 표시 하나뿐이다.

**넷 다 왕복이 하나다.** 묶기 전에는 각각 여러 번이었다.

## 2. 왜 묶는가

**이유가 둘이고, 스크립트마다 어느 쪽인지가 다르다.**

```
원자성이 필요하다    나눠 부르면 그 사이에 남이 끼어들어 틀린 결과가 나온다
왕복을 줄인다        나눠 불러도 결과는 맞지만 느리다
```

**원자성이 필요한 것은 순번 확보 하나뿐이다.** 나머지 셋은 왕복 때문이고, 원자성은 덤으로
생길 뿐 그것이 목적이 아니다.

**그 구분이 중요하다.** 뒤의 셋은 반쪽만 반영돼도 해가 없다는 것을 각 절에서 따로 적는다.
해가 없다는 근거가 있어야 나중에 다시 나눌 수도 있다.

## 3. `coupon-issue-seq.lua` - 순번 확보

**요청 스레드가 번호를 받을 때마다 부른다.** 발급 경로에서 가장 자주 도는 스크립트다.

```
KEYS   seq, free, counter, pending
ARGV   회원, 준비 수량, 회수 기준(ms)
반환   "6" 번호를 받았다 / "6:1" 이미 발급됐다 / "-1" 소진 / "-2" 안 열렸다 / "-3" 최종 소진
```

**담는 명령이 갈래마다 다르고 최대 열이다.**

```
언제나        EXISTS counter          이벤트가 열려 있나
              HGET seq {회원}          이미 번호가 있나.  있으면 여기서 끝
              TIME                    점수에 쓸 시각.  앱 시계를 안 쓴다
              PEXPIRETIME counter     새로 만들 키에 물려줄 수명

번호를 줄 때   ZPOPMIN free            다시 내줄 번호가 있나
              INCR counter            없으면 새로 발행한다
              HSET seq {회원} {번호}
              ZADD pending {회원} {시각}
              PEXPIREAT seq, pending   수명을 물려준다

한도를 넘으면  DECR counter            방금 올린 것을 되돌린다
소진 분기      ZRANGEBYSCORE pending   기준 시간을 넘긴 항목 하나
              HGET / ZREM / HDEL       그 번호를 뺏어 이 요청에게 준다
              ZCARD pending            비었으면 최종 소진이다
```

### 여기만 원자성이 진짜로 필요하다

**나눠 부르면 두 가지가 깨진다.**

```
같은 회원의 동시 요청 둘이 다 HGET 을 놓친다   각자 새 번호를 받아 1인 2매가 된다
ZPOPMIN 과 INCR 사이에 남이 끼어든다          같은 번호가 두 사람에게 간다
```

**`DECR` 이 안전한 것도 이 원자성 덕이다.** 올린 직후라 아무도 끼어들 수 없어 맨 위가 나인
것이 확실하다. DB 를 갔다 온 뒤에는 그 조건이 안 서므로 그때는 `free` 를 쓴다.

## 4. `coupon-mark-committed.lua` - 확정 표시

**플러시 스레드가 배치를 커밋한 뒤 부른다.** 배치에 든 회원 전부를 한 번에 처리한다.

```
KEYS   seq, pending
ARGV   회원, 값, 회원, 값, ...    값은 "6:1" 처럼 확정 표시가 붙은 순번이다
```

```
HSET seq     {회원들과 값들}     확정 표시를 붙인다
ZREM pending {회원들}            미확정 목록에서 뺀다
```

**`ARGV` 의 모양이 `HSET` 이 받는 모양과 같아서 그대로 넘긴다.** `ZREM` 은 회원만 받으므로
홀수 자리만 골라낸다.

### 이것만 요청 예산 안이다

**`completeIssued` 가 요청 스레드를 깨우기 전에 부른다.** 그래서 이 왕복이 `commit-wait`
안에 들어가고 계층 산식에 잡힌다.

```
확정 표시   100ms   Redis 왕복 하나
```

**나눠 부르면 이 값이 200ms 가 되고 안쪽 합이 예산을 넘는다.** 그것이 이 스크립트를 만든
직접적인 이유다.

### 반쪽만 돼도 해가 없다

```
확정 표시만 남는다     회수가 그 표시를 보고 안 뺏는다.  pending 에서만 청소된다
미확정 해제만 된다     아무도 그 번호를 회수 대상으로 안 본다
```

**그래서 원자성은 덤이다.** 필요해서 묶은 것이 아니다.

## 5. `coupon-drop-mapping.lua` - 매핑만 지우기

**플러시 스레드가 배치 끝에서 부른다.** 그 배치에서 순번 충돌이 난 회원들을 한 번에 처리한다.

```
KEYS   seq, pending
ARGV   회원 목록
```

```
HDEL seq     {회원들}     매핑을 지운다.  다음 요청이 새 번호를 받게 된다
ZREM pending {회원들}     미확정 목록에서 뺀다
```

### `free` 가 안 들어가는 것이 요점이다

**받은 번호를 남이 쓰고 있어서 온 경로다.** 그 번호를 다시 내줄 자리에 담으면 **또 다른
회원이 받아 같은 충돌을 되풀이한다.** 그래서 이 스크립트는 `free` 키를 아예 안 받는다.

### 빈 목록으로 부르지 않는다

**`unpack` 에 빈 표를 넘기면 `HDEL` 이 인자 없이 호출돼 오류가 난다.** 부르는 쪽이 비면
곧바로 돌아가므로 이 스크립트에는 그 검사가 없다.

## 6. `coupon-return-and-repair.lua` - 번호를 되돌리고 매핑을 고치기

**플러시 스레드가 중복을 해소할 때 부른다. 지금은 티켓마다 한 번이다.**

```
KEYS   seq, pending, free, counter
ARGV   회원, 이번에 받았다가 못 쓴 번호, 그 회원이 원래 갖고 있는 번호
```

```
ZADD  free {버린 번호}          안 쓰인 것이 확인된 번호를 담는다.  점수가 번호다
PEXPIRETIME counter             넷의 수명을 들고 있는 키에서 만료 시각을 읽는다
PEXPIREAT   free                free 에 같은 수명을 물려준다
HSET  seq     {회원} {실제 번호}  원래 갖고 있던 번호로 고쳐 넣는다
ZREM  pending {회원}             미확정 목록에서 뺀다
```

**다섯 중 가운데 둘이 수명 물려주기다.** `free` 를 만드는 자리가 여기뿐이라, 여기서 안 걸면
넷 중 이 키에만 만료가 영영 안 붙는다.

### 여기서 수명 물려주기가 정확해진다

**앱에서 하던 방식은 남은 시간을 읽어 상대 시각으로 다시 걸었다.**

```
앱      PTTL counter -> PEXPIRE free {남은 시간}     읽고 쓰는 사이만큼 어긋난다
스크립트  PEXPIRETIME counter -> PEXPIREAT free {그 시각}   어긋남이 없다
```

**앱이 상대 시각을 쓴 이유는 절대 만료 시각을 읽는 명령을 스프링이 안 내주기 때문이었다.**
스크립트 안에서는 그 제약이 없다. 순번 확보 스크립트가 이미 같은 방식으로 `seq` 와 `pending`
에 수명을 물려주고 있어, **`free` 만 예외였던 것이 없어진다.**

### 매핑을 지우지 않고 고치는 이유

**지우기만 하면 그 회원의 다음 요청이 또 새 번호를 받아 또 같은 제약에 막힌다.** 되풀이를
끊으려면 원래 갖고 있던 번호를 넣어 줘야 한다.

## 7. 파이프라인을 썼다가 되돌렸다

**확정 표시를 처음에는 파이프라인으로 묶었다가 스크립트로 바꿨다.** 재 보니 파이프라인이
순차 왕복 둘보다 오히려 느렸기 때문이다.

```
배치   스크립트   순차     파이프라인      (p50, 마이크로초)
   1      795   1,447      4,455
  50    1,240   1,949      4,494
 500    2,216   2,903      4,258
```

**명령이 하나도 없는 빈 파이프라인이 4.6밀리초였다.** 느린 것은 명령이 아니라 파이프라인을
여는 것 자체다.

**Lettuce 는 공유 커넥션으로 파이프라인을 못 한다.** auto-flush 를 끄고 명령을 쌓아 두는
방식이라 그 커넥션을 다른 요청이 같이 쓰면 안 되고, 그래서 스프링이 전용 커넥션을 따로
얻는다. **그런데 커넥션 풀이 없어 호출마다 새 연결이 열린다.**

`application-coupon.yml` 이 그 전제를 이미 적어 두고 있었는데 파이프라인이 그것을 깨는 것을
못 봤다.

> Lettuce 가 커넥션 하나를 공유하고 명령을 다중화하므로 접속은 **기동 때와 재접속 때만**
> 일어난다.

**측정은 `CouponSeqMarkCommittedLatencyIntegrationTest` 가 들고 있다.** 추정으로 정했다가
재서 뒤집힌 자리라 그 값을 시험으로 남겼다.

**나머지 둘도 같은 시험이 잰다.**

```
                p50      순차 대비      왕복
매핑 삭제  1      379      -47%         2 -> 1
매핑 삭제  50     577      -41%
매핑 삭제  500  1,782      -21%
번호 되돌리기    421      -77%         5 -> 1
```

**되돌리기가 가장 크다.** 왕복이 다섯에서 하나로 주는 것이 그대로 나온다. 배치가 커질수록
폭이 주는 것은 인자를 실어 보내는 시간이 왕복 하나를 아낀 몫을 덮기 시작해서다.

**믿을 것은 방향이지 폭이 아니다.** 회차마다 개선 폭이 17%에서 45% 사이로 흔들렸고, 로컬
컨테이너 왕복이 1밀리초를 넘는 것 자체가 이상하다. **근거로 삼는 것은 왕복 수이지 이 표의
절대값이 아니다.**

## 8. 제약

### 인자 개수

**`unpack` 은 루아 스택 한계에 걸린다.** Redis 의 루아는 그 한계가 8,000쯤이다.

```
확정 표시   배치 500 -> ARGV 1,000     안전하다
            batch-size 를 4,000 위로 올리면 걸린다
매핑 삭제   배치 500 -> ARGV 500       안전하다
```

**`batch-size` 를 크게 올릴 때 함께 봐야 한다.** 걸리면 청크로 나눠야 한다.

### 스크립트 캐시

**스프링이 `EVALSHA` 로 보내고, 서버에 없으면 `NOSCRIPT` 로 튕긴 뒤 `EVAL` 로 본문을 싣는다.**
그 대가를 무는 것은 첫 `EVAL` 이 돌아오기 전에 날아간 요청들뿐이고 그 뒤는 전부 `EVALSHA` 다.

**순번 확보 스크립트는 그 비용을 실측했다.** 캐시가 비면 네 배였다
(`CouponSeqScriptCacheLatencyIntegrationTest`).

### 워밍업이 셋을 안 데운다

**기동 워밍업은 요청을 소진(410)으로 끝낸다.** 그래서 순번 확보 스크립트만 캐시에 오르고
**뒷정리 스크립트 셋은 한 번도 안 태운다.**

```
데워진다     coupon-issue-seq.lua
안 데워진다   coupon-mark-committed.lua      요청 예산 안이다
             coupon-drop-mapping.lua
             coupon-return-and-repair.lua
```

**확정 표시가 특히 걸린다.** 그 스크립트는 요청 예산 안에 있어서, **이벤트의 첫 배치가
`NOSCRIPT` 왕복을 예산 안에서 문다.** 배치 하나 분량이라 규모는 작지만, 하필 이벤트가 가장
바쁜 순간이다.

**아직 안 고쳤다.** 워밍업이 `SCRIPT LOAD` 로 넷을 미리 올리거나, 워밍업 요청 하나를 발급까지
보내는 방법이 있다. 재 보고 정할 값이다.

## 9. 지금 어디까지 들어갔나

```
coupon-issue-seq.lua          처음부터 스크립트였다
coupon-mark-committed.lua     명령 둘을 순차로 치던 것을 바꿨다.  파이프라인을 거쳐 왔다
coupon-drop-mapping.lua       명령 둘을 순차로 치던 것을 바꿨다
coupon-return-and-repair.lua  명령 다섯을 순차로 치던 것을 바꿨다
```

**`repairSeqTaken` 의 주인 조회는 스크립트로 안 묶는다.** 그쪽은 DB 를 읽어야 해서 Redis
스크립트 안에서 못 한다.
