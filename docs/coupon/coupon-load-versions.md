# 선착순 쿠폰 버전별 부하 시험 기록

[coupon-version-rounds.md](coupon-version-rounds.md) 가 설계한 회차의 결과를 여기 모은다.
회차가 늘면 이 문서에 이어 적는다.

---

## 1. 2026-09-28 회차

v1 부터 v4 까지 각 3회, 모두 12회차를 돌렸다.

```
부하 생성    k6 1.7.1, m7i-flex.large
k6 출력      -o experimental-prometheus-rw
p99          회차 창을 자른 query_range 의 최댓값
부하         재고 10,000 / VU 20,000 / ramp 60s / hold 30s
스프링 서버  쿠폰 전용 ASG t3.small 3대 / RDS db.t4g.micro Multi-AZ / ElastiCache cache.t4g.micro 2노드
```

**12회차 전부 k6 가 완주했고 임계 4개를 다 읽었다.** 앞선 회차는 생성기가 죽어 임계 3개를
잃었는데, 판정을 받은 VU 가 남은 시간을 한 번에 자게 고쳐서 해결했다
([coupon-version-rounds.md](coupon-version-rounds.md) 10장).

## 2. 결론

**v1 은 요구 부하에서 요청의 80%에 500 을 돌려준다.** 재고 10,000 중 3,777 에서 4,006 만 나가고
p99 도 631.6ms 에서 639.8ms 다. **느린 것이 아니라 깨진 것이다.**

```
http_req_failed      79.97 ~ 81.11%
coupon_unexpected    15,994 ~ 16,223건   전부 status=500, COMMON-001
k6 exit              99                  임계 둘을 깼다
```

**v1 에서 v2 로 가는 값이 가장 크다.** 재고를 다 털고 p99 가 2.7배 내려간다. Redis 카운터가
거절을 DB 앞에서 끊는 것이 그만큼을 벌었다.

**큐와 가상 스레드는 한 쌍이다.** 큐만 넣으면(v2 -> v3) 아무것도 안 벌리고, 그 위에 가상 스레드를
켜면(v3 -> v4) 2.67배가 나온다. **각자 다른 벽을 치우기 때문이다.** 5장에 근거가 있다.

**12회차 전부 정합성이 깨지지 않았다.** `gap 0` 이고 `members = issued_rows` 다.

## 3. 버전 비교

**판정값은 k6 요약의 p99 다.** 회차가 끝났을 때 그 회차의 요청 전체로 계산한 값이고, k6 의
임계가 평가하는 것도 이 값이다. 분위수는 표본 집합 위에서 정의되므로 회차 하나에 값이 하나다.

**모집단은 처리된 응답이다.** [coupon.md](coupon.md) 7장이 이렇게 정했다.

| 담는다 | 안 담는다 |
|---|---|
| 발급(200), 이미 받음(409), 소진(410) | 혼잡(503), 그 밖의 오류 |

**혼잡을 넣으면 요청 예산을 줄이는 것만으로 값이 내려간다.** 스프링 서버를 고치지 않고 통과할 수 있다.

### 판정값

**그 버전이 낸 p99 중 가장 나쁜 값이다.**

| 버전 | p99 | 발급 | SLO 1초 | 판정 |
|---|---:|---:|---|---|
| v1 DB 조건부 UPDATE | 639.8ms | 3,777 ~ 4,006 | 통과 | **요청 80%에 500. 깨진 것이다** |
| v2 Redis 카운터 | 351.8ms | 10,000 | 통과 | |
| v3 인스턴스 큐 + 벌크 | 355.8ms | 10,000 | 통과 | |
| v4 가상 스레드 (채택) | **133.4ms** | 10,000 | 통과 | **4개 중 최저** |

**v1 이 SLO 를 통과한 것에 속으면 안 된다.** 500 은 판정된 응답이 아니라 이 모집단에 안
들어간다. **성공한 4,000건의 지연일 뿐이다.**

### 3회차의 평균

평균은 판정값이 아니다. **같은 코드를 3회 돌렸을 때 값이 얼마나 달라지는지를 보는 자리다.**
오른쪽 칸은 가장 나쁜 회차가 가장 좋은 회차의 몇 배인지다.

| 버전 | p99 평균 | 가장 좋은 회차 | 가장 나쁜 회차 | 몇 배 | 발급 평균 |
|---|---:|---:|---:|---:|---:|
| v1 DB 조건부 UPDATE | 635.6ms | 631.6 | 639.8 | **1.01배** | **3,922** |
| v2 Redis 카운터 | 172.8ms | 53.8 | 351.8 | 6.54배 | 10,000 |
| v3 인스턴스 큐 + 벌크 | 187.5ms | 96.6 | 355.8 | 3.68배 | 10,000 |
| v4 가상 스레드 (채택) | **114.8ms** | 102.9 | 133.4 | **1.30배** | 10,000 |

**v1 은 3회차가 631.6, 635.5, 639.8ms 로 거의 같다.** 1.01배다. **늘 나쁘고 그 나쁨이
일정하다.** 병목이 구조에 있어서 회차마다 달라질 여지가 없다는 뜻이다.

**v4 도 1.30배로 좁다.** v2 는 6.54배이고 v3 는 3.68배다. **값이 낮으면서 회차마다 고른 것이
v4 하나다.**

### v1 과 나머지 사이의 선

```
v1        632 ~ 640ms     재고 39%     요청 80%가 500
v2         54 ~ 352ms     재고 100%
v3         97 ~ 356ms     재고 100%
v4        103 ~ 133ms     재고 100%
```

| 두 버전 | 범위가 겹치나 |
|---|---|
| v1 과 나머지 | **겹치지 않는다.** 632 > 356 |
| v2 와 v3 | 겹친다. 54 ~ 352 와 97 ~ 356 |
| v3 와 v4 | 겹친다. 97 ~ 356 와 103 ~ 133 |

**v2 와 v3 는 사실상 같은 자리다.** 최악값이 351.8ms 와 355.8ms 로 4ms 차이다.

**v4 만 범위가 좁고 낮다.** 최악값 133.4ms 가 v2 와 v3 의 최저값(53.8, 96.6)보다는 크지만,
**v4 의 3회차가 모두 v2 와 v3 의 최악값 아래에 있다.**

### Grafana 화면과의 차이

**대시보드의 응답 지연 패널은 `k6_http_req_duration_p99` 를 상태별로 나눠 그린다.** 판정값과
같은 축이 아니므로 그 화면의 숫자를 기록에 옮기면 안 된다.

| 무엇 | 대시보드 | 판정값 |
|---|---|---|
| 지표 | `http_req_duration` | `coupon_settled_duration` |
| 모집단 | 전체 응답 | 처리된 응답 |
| 계열 | 상태별로 쪼갠다 | 하나 |
| 집계 | 시계열 | 회차 전체 표본 |

**상태별로 쪼개면 낮은 선이 함께 보인다.** v4-2 회차의 3개 계열이 그 예다.

```
error_code=1409 (이미 받음)    최댓값   6.5ms
error_code=1410 (소진)         최댓값  10.1ms
발급                           최댓값 252.5ms
```

**소진 응답은 재고가 없다는 답만 하므로 빠르다.** 대시보드에서 전체가 좋아 보이는 것이 이 때문이다.

**그리고 k6 가 5초마다 보내는 p99 는 누적 분포의 값이다.** 회차 끝에서 요약과 같은 값에
수렴하고, 표본이 적은 초반에는 위로 튄다. **그 시계열의 최댓값을 기록에 쓰면 회차마다 최대
2배까지 부풀려진다.** push 간격을 바꾸면 값이 움직이므로 어느 회차와도 비교할 수 없다.

**그래서 시계열은 "p99 가 언제 튀었나" 를 보는 데 쓰고, 기록에는 요약값을 적는다.**

## 5. 왜 그 값이 나왔나

설계 6장이 지목한 지표를 회차 창별로 뽑았다.

| 지표 | v1 | v2 | v3 | v4 |
|---|---:|---:|---:|---:|
| `innodb_row_lock_waits` | **4,634 ~ 13,017** | 0 | 0 | 0 |
| `redis_commands_processed_total` | **20,094 ~ 29,335** | 260,094 ~ 359,339 | 241,664 ~ 339,980 | 241,184 ~ 241,650 |
| `hikaricp_connections_pending` | **34 ~ 35** | 0 | 0 | 0 |
| `hikaricp_connections_active` | **8** | 3 | 0 ~ 1 | 1 |
| `coupon_issue_queue_size` | 0 | 0 | 2 | 3 ~ 30 |
| `jvm_threads_peak_threads` | 102 | 102 ~ 181 | 183 | **71** |

### v1: 한 행의 배타 락

**`innodb_row_lock_waits` 가 최대 13,017 이고 다른 셋은 0 이다.**

v1 은 조건부 UPDATE 로 재고를 깎는다.

```sql
UPDATE coupon SET issued_quantity = issued_quantity + 1
 WHERE coupon_id = ? AND (total_quantity IS NULL OR issued_quantity < total_quantity)
```

**모든 요청이 같은 행을 두고 줄을 선다.** `hikaricp_connections_pending` 34 가 그 대기열이고
`active` 8 은 커넥션 8개가 락을 기다리며 묶여 있다는 뜻이다. **풀이 8 이라 전부 잡혔다.**

**`redis_commands_processed_total` 이 2만대로 다른 셋의 10분의 1 이다.** v1 은 Redis 를 쓰지
않으므로 이 값은 배경 트래픽이다. **이 지표가 버전을 가장 뚜렷하게 가른다.**

**그래서 요청의 80%가 500 으로 끝난다.**

```
http_req_failed      79.97 ~ 81.11%
coupon_unexpected    15,994 ~ 16,223   전부 status=500 body={"code":"COMMON-001"}
```

`COMMON-001` 은 잡히지 않은 예외의 공통 응답이다. **커넥션 획득 타임아웃이 가장 그럴듯하다.**
풀이 8 인데 대기가 34 이면 뒤에 선 요청은 기다리다 끊긴다. 다만 스프링 서버 로그로 확인하지 않았으므로
추정이다.

**이 500 은 처리된 응답 p99 에 안 담긴다.** 판정된 응답이 아니기 때문이다. 그래서 v1 의
p99 639.8ms 는 **성공한 4,000건의 지연**이다.

### v2: DB 앞에서 끊는 거절

**`innodb_row_lock_waits` 가 0 으로 떨어진다.** Redis 카운터가 재고를 세므로 초과분이 DB 에
닿지 않는다. `redis_commands_processed_total` 이 26만에서 36만으로 올라간 것이 그 일이다.

**`hikaricp_connections_pending` 도 0 이다.** 락 대기가 없으니 커넥션이 묶이지 않는다.
`active` 3 은 실제 쓰기만큼이다.

**남은 비용은 요청 스레드가 커넥션을 쥔 채 쓰는 것이다.** `jvm_threads_peak_threads` 가 102 에서
181 까지 오르내리는 것이 그 부하다. **회차마다 p99 가 6.54배까지 벌어지는 것도 여기서 온다.**

### v3: 쓰기를 모으는 큐

**`jvm_threads_peak_threads` 가 183 이다.** 플랫폼 스레드를 쓰므로 `server.tomcat.threads.max`
200 이 실제 상한이고 그 근처까지 갔다.

**`coupon_issue_queue_size` 가 2 로 거의 차지 않는다.** 벌크가 들어오는 속도를 따라 비웠다.

### v4: 가장 적은 플랫폼 스레드

**`jvm_threads_peak_threads` 가 71 로 4개 중 가장 낮다.** v3 의 183 의 5분의 2 다.

**가상 스레드는 대기하는 동안 캐리어를 놓는다.** 동시 요청이 2만이어도 플랫폼 스레드는 71개로
끝난다.

**`coupon_issue_queue_size` 가 3 에서 30 으로 4개 중 가장 크다.** 입구가 200 에서 막히지 않으니
큐까지 요청이 더 들어온다. **그런데도 p99 가 가장 낮고 회차마다 1.30배 안에 든다.**

### 한 쌍인 큐와 가상 스레드

**단계별로 보면 큐만으로는 아무것도 안 벌린다.**

| 단계 | 무엇을 더했나 | 전 | 후 | 배수 |
|---|---|---:|---:|---:|
| v1 -> v2 | Redis 카운터 | 639.8ms | 351.8ms | 1.82배 |
| v2 -> v3 | 큐 + 벌크 INSERT | 351.8ms | 355.8ms | **0.99배** |
| v3 -> v4 | 가상 스레드 | 355.8ms | 133.4ms | **2.67배** |

**그 이유가 큐 길이에 있다.**

| 지표 | v2 | v3 | v4 |
|---|---:|---:|---:|
| `coupon_issue_queue_size` | 0 | **2** | **3 ~ 30** |
| `jvm_threads_peak_threads` | 102 ~ 181 | **183** | **71** |

**v3 의 큐가 최대 2 까지만 찬다.** 입구가 `server.tomcat.threads.max` 200 에서 막혀 있어 큐까지
도달하는 요청이 그만큼뿐이다. 스레드 peak 183 이 그 벽에 붙은 값이다.

**v4 는 큐가 3에서 30까지 찬다. 4개 중 가장 크다.** 가상 스레드가 대기 중 캐리어를 놓으므로
입구가 200 에서 막히지 않고 요청이 큐까지 도달한다. **그런데 스레드 peak 는 71 로 v3 의 5분의
2 다.**

**그래서 둘은 각자 다른 벽을 치운다.**

```
큐 + 벌크       쓰기를 모아 왕복을 줄이는 장치
가상 스레드      그 장치에 요청이 도달하게 하는 조건
```

**큐만 넣으면 입구 200 이 막는다.** 큐가 아무리 넓어도 동시에 큐에서 잠들 수 있는 요청이
200 개다. **가상 스레드만 켜고 큐가 없으면(v2) 요청 스레드가 DB 쓰기를 직접 기다리므로 커넥션
풀 8 이 다음 벽이 된다.**

**v3 브랜치의 설정 주석이 이것을 예고했다.**

> 그래서 `server.tomcat.threads.max` 200 이 다시 실제 상한이 된다. 동시에 큐에서 잠들 수 있는
> 요청이 200 개이므로 큐 길이의 실효 상한도 200 이다.

**실측이 그 예측보다 강하다.** 실효 상한이 200 이 아니라 2 였다.

### 큐가 만드는 고른 값

| 버전 | 가장 나쁜 회차가 좋은 회차의 몇 배 |
|---|---:|
| v2 | 6.54배 |
| v3 | 3.68배 |
| v4 | **1.30배** |

**v2 와 v3 의 p99 는 같은데 이 값이 절반으로 준다.** 큐의 몫이 p99 가 아니라 여기서 드러난다.
**요청이 몰리는 순간을 큐가 흡수하기 때문이다.**

**그래서 v3 를 "값을 못 낸 단계" 로 읽으면 안 된다.** 가상 스레드가 입구를 열기 전에는 값이
안 보이고, 열면 2.67배가 나온다. **v4 의 개선분 전체가 가상 스레드의 몫이 아니라 두 설계가
맞물려 나온 것이다.**

### 수집되지 않은 지표

**`tomcat_threads_busy_threads` 는 이번에도 없었다.** 설계 6장이 v3 와 v4 를 가르는 지표로
지목했는데 존재를 확인하지 않고 적었다. 지표 이름을 확인하고 노출부터 고쳐야 한다.

## 6. 병목이 아니었던 생성기

**`node_exporter` 를 생성기에 넣어 CPU 를 처음 쟀다.** 2026-08-28 에 인스턴스를 고를 때
실측하지 못하고 그 뒤로도 못 쟀던 값이다.

| 회차 | CPU 최대 | CPU 평균 | 남은 메모리 최소 |
|---|---:|---:|---:|
| v4-1 | 57.6% | 7.4% | 1,831 MB |
| v4-2 | 58.5% | 7.1% | 1,692 MB |
| v4-3 | 49.1% | 8.1% | 1,941 MB |
| v1-1 | 52.9% | 2.4% | 2,110 MB |
| v1-2 | 49.5% | 7.1% | 1,640 MB |
| v1-3 | 51.1% | 9.8% | 2,069 MB |
| v2-1 | 45.6% | 2.2% | 1,701 MB |
| v2-2 | **80.2%** | 16.3% | 1,921 MB |
| v2-3 | 50.9% | 15.2% | 1,667 MB |
| v3-1 | **83.3%** | 3.8% | 1,773 MB |

**최대 83.3% 이고 100% 에 붙은 회차가 없다.** 평균은 2.2 ~ 16.3% 다.

**남은 메모리가 최소 1,640 MB 다.** 앞선 회차는 이 값이 0 에 닿아 커널이 k6 를 죽였다.

**그래서 이 회차의 p99 에 생성기 부담이 섞이지 않았다.** 설계 10장이 요구한 대조 회차도 같은
답을 냈다. `sleep` 수정 전 v4 가 189 ~ 389ms 이고 수정 뒤 대조 회차가 205.2ms 로 그 범위 안이다.

## 7. 정합성

**12회차 전부 깨지지 않았다.**

| 불변식 | 확인 방법 | 결과 |
|---|---|---|
| R1 초과 발급 없음 | `issued_rows <= 10,000` | 전 회차 통과 |
| R2 1인 1매 | `members = issued_rows` | 전 회차 통과 |
| R3 번호 충돌 없음 | `max_seq = issued_rows` | 전 회차 통과 |
| R4 번호 유실 없음 | `gap = 0` | 전 회차 통과 |

**v1 도 이 네 항목은 통과했다.** 발급된 4,000건은 전부 올바르다.

**그러나 v1 을 "정확하지만 느리다" 로 읽으면 안 된다.** 나머지 16,000건이 500 으로 끝났다.
정합성 검증은 DB 에 들어간 행만 보므로 **응답을 못 받은 요청은 그 검증의 대상이 아니다.**
`gap 0` 은 "번호를 태우고 사라진 요청이 없다" 는 뜻이고 "모든 요청이 제대로 응답받았다" 는
뜻이 아니다.

## 8. 이 회차가 답하지 못한 것

**v2 와 v3 와 v4 의 우열이다.** 세 범위가 겹친다. 가르려면 표본을 늘리거나 부하를 올려야 한다.

**v1 의 500 이 무슨 예외인지 모른다.** `COMMON-001` 은 잡히지 않은 예외의 공통 응답이고 어느
예외인지는 스프링 서버 로그에 있는데 회차 뒤에 인스턴스를 파괴했다. `hikaricp_connections_pending` 34 에
`active` 8 이므로 커넥션 획득 타임아웃이 그럴듯하지만 **추정이다.**

**v2 와 v3 가 회차마다 왜 그만큼 달라지는지 모른다.** 6.54배와 3.68배다. v2-2 는 혼잡이 0.25% 있었고 v3-1 은
`redis_commands` 가 34만으로 다른 v3 회차의 24만보다 높다. **2회차가 무엇 때문에 달랐는지
가르지 못했다.**

**`tomcat_threads_busy_threads` 를 못 봤다.** v3 와 v4 를 가르는 지표인데 수집되지 않았다.

## 9. 절차에서 고친 것

**이 회차를 세우는 동안 7개를 찾았다.** 앞의 6개는 조용히 통과해 버리는 종류다.

### 발급 경로에 닿지 않는 배포

**`deploy.sh` 는 평상시 스프링 서버 ASG 만 교체한다.** 발급 요청은 ALB 가 쿠폰 전용 ASG 로 보내는데,
그 ASG 를 건드리지 않으므로 **이미지를 바꿔도 발급을 처리하는 코드가 그대로다.**

회차 검산이 SSM `current-sha` 만 봤고 `deploy.sh` 가 SSM 을 먼저 갱신하므로 **검산이 통과해
버렸다.** 네 버전이 서로 구별되지 않는 회차가 나왔고 v4 코드만 돌았기 때문이었다.

이제 배포 뒤에 전용 ASG 를 다시 세우고 인스턴스의 `docker ps` 로 이미지를 읽는다.

```
deploy.sh <SHA>
  -> coupon-event.sh close      desired 0
  -> coupon-event.sh open 3     새 인스턴스가 SSM current-sha 를 읽어 뜬다
  -> docker ps 로 이미지 확인
```

### 1초마다 깨어나던 VU

`sleep(1)` 로 두면 k6 가 반복을 초당 2만 번 세고 **그때마다 남는 것이 있다.** 램프가 끝난 뒤
45초 동안 2,440 MB 가 쌓여 커널이 k6 를 죽였다. **요청은 한 건도 안 보내는 구간이다.**

```
sleep(1)            VU 당 45회   2만 VU -> 90만 회   약 2,440 MB
남은 시간만큼 한 번   VU 당  1회   2만 VU ->  2만 회   약 54 MB
```

**고친 뒤 12회차 전부 완주했고 메모리 최고점이 5,666 ~ 6,140 MB 다.** 앞선 회차는
7,667 MB 에서 죽었다.

### 임계가 없던 거절 비율

`coupon.md` 7장이 SLO 모집단에서 혼잡(503)을 빼면서 거절 비율을 따로 묶어야 한다고 적었는데
그 임계가 없었다. **503 이 세 임계 어디에도 안 걸렸다.** `coupon_congested_rate` 를 두어 1% 를
상한으로 걸었고, 이 회차에서 처음으로 그 값을 읽었다.

### 죽어도 완료로 끝나던 시드

SSM 에 명령 셋을 넘겼고 마지막이 `rm` 이었다. **SSM 은 마지막 명령의 exit code 를 전체 상태로
삼으므로 `rm` 이 늘 성공해서 본문이 죽어도 `Success` 가 됐다.** `rm` 을 본문과 한 줄에 이어
붙여 `rc` 를 보존하고, 넣은 뒤에 행 수를 센다.

### 스프링 서버보다 먼저 돌린 시드

**스키마는 스프링 서버가 부팅할 때 만든다.** 스프링 서버 healthy 를 기다린 뒤에 시드를 넣어야 한다.

### 로그를 값으로 읽은 검산

`log` 이 stdout 으로 찍혔다. **stdout 은 `run_on_batch` 가 배치의 출력을 돌려주는 자리라
`out=$(run_on_batch ...)` 가 로그를 값으로 읽었다.** `log` 를 stderr 로 보냈다.

### 잴 수 없던 생성기 CPU

**`node_exporter` 가 생성기에 없었다.** Prometheus 의 node 잡이 이미 그 인스턴스를 찾고 있었는데
익스포터가 없어 타깃이 down 이었다. 회차마다 `top` 을 손으로 걸어야 했고 그래서 한 번도 못
쟀다. 익스포터를 두어 **6장의 값을 처음 얻었다.**
