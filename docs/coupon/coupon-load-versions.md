# 선착순 쿠폰 버전별 부하 시험 기록

[coupon-version-rounds.md](coupon-version-rounds.md) 가 설계한 회차의 결과를 여기 모은다.
회차가 늘면 이 문서에 이어 적는다.

---

## 1. 2026-09-28 회차

v1 부터 v4 까지 각 3회, 모두 12회 돌렸다.

```
부하 생성  k6 1.7.1, m7i-flex.large
k6 출력    -o experimental-prometheus-rw
p99        회차 창을 자른 query_range 의 최댓값
부하       재고 10,000 / VU 20,000 / ramp 60s / hold 30s
앱         쿠폰 전용 ASG t3.small 3대 / RDS db.t4g.micro Multi-AZ / ElastiCache cache.t4g.micro 2노드
```

**열두 회차 전부 k6 가 완주했고 임계 넷을 다 읽었다.** 앞선 회차는 생성기가 죽어 임계 셋을
잃었는데, 판정을 받은 VU 가 남은 시간을 한 번에 자게 고쳐서 해결했다
([coupon-version-rounds.md](coupon-version-rounds.md) 10장).

---

## 2. 결론

**v1 은 요구 부하에서 요청의 80%에 500 을 돌려준다.** 재고 10,000 중 3,777 에서 4,006 만 나가고
p99 도 638.5ms 에서 699.8ms 다. **느린 것이 아니라 깨진 것이다.**

```
http_req_failed      79.97 ~ 81.11%
coupon_unexpected    15,994 ~ 16,223건   전부 status=500, COMMON-001
k6 exit              99                  임계 둘을 깼다
```

**v1 에서 v2 로 가는 값이 가장 크다.** 재고를 다 털고 p99 가 2.7배 내려간다. Redis 카운터가
거절을 DB 앞에서 끊는 것이 그만큼을 벌었다.

**v2 와 v3 와 v4 는 이 부하에서 서로 구별되지 않는다.** 세 범위가 겹친다. 다만 v4 가 회차 간
흔들림이 가장 작고 플랫폼 스레드를 가장 적게 쓴다.

**열두 회차 전부 정합성이 깨지지 않았다.** `gap 0` 이고 `members = issued_rows` 다.

## 3. 버전 비교

**두 p99 가 담는 것이 다르다.**

| 이름 | 담는 응답 | 무엇을 재나 | k6 지표 |
|---|---|---|---|
| **처리된 응답 p99** | 발급(200), 이미 받음(409), 소진(410) | **SLO 판정.** 서버가 판정을 끝낸 응답의 지연 | `coupon_settled_duration` |
| 전체 응답 p99 | 위 셋과 혼잡(503), 그 밖의 모든 응답 | 사용자가 겪은 시간 | `http_req_duration` |

**판정에 쓰는 것은 앞의 것이다.** [coupon.md](coupon.md) 7장이 "처리된 발급 응답의 p99 가
1초 이하" 로 정했다. 혼잡을 넣으면 **요청 예산을 줄이는 것만으로 값이 내려가서, 앱을 고치지
않고 통과할 수 있다.**

### 판정값

**그 버전이 낸 p99 중 가장 나쁜 값이다.** 분위수를 평균내면 그 결과는 분위수가 아니다.

| 버전 | p99 | 발급 | SLO 1초 | 판정 |
|---|---:|---:|---|---|
| v1 DB 조건부 UPDATE | **699.8ms** | 3,777 ~ 4,006 | 통과 | **요청 80%에 500. 깨진 것이다** |
| v2 Redis 카운터 | 470.7ms | 10,000 | 통과 | |
| v3 인스턴스 큐 + 벌크 | **739.1ms** | 10,000 | 통과 | |
| v4 가상 스레드 (채택) | **252.5ms** | 10,000 | 통과 | 넷 중 최저 |

**v1 이 SLO 를 통과한 것에 속으면 안 된다.** 500 은 판정된 응답이 아니므로 이 모집단에 안
들어간다. **성공한 4,000건의 지연일 뿐이다.**

### 세 회차의 평균

평균은 판정값이 아니다. 회차 변동의 중심과 폭을 보는 값이다.

| 버전 | p99 평균 | 최저 | 최악 | 폭 | 발급 평균 |
|---|---:|---:|---:|---:|---:|
| v1 DB 조건부 UPDATE | 661.9ms | 638.5 | 699.8 | **1.10배** | **3,922** |
| v2 Redis 카운터 | 244.7ms | 92.4 | 470.7 | 5.09배 | 10,000 |
| v3 인스턴스 큐 + 벌크 | 366.6ms | 172.7 | 739.1 | 4.28배 | 10,000 |
| v4 가상 스레드 (채택) | **216.0ms** | 192.3 | 252.5 | **1.31배** | 10,000 |

**v1 의 폭이 가장 작다.** 1.10배다. 늘 나쁘고 그 나쁨이 일정하다.

**v4 의 폭도 작다.** 1.31배이고 v2 의 5.09배와 v3 의 4.28배보다 훨씬 좁다. **값이 낮으면서
흔들림도 작은 것이 v4 하나다.**

### v1 과 나머지 사이에만 선이 있다

```
v1        638 ~ 700ms     재고 39%    요청 80%가 500
v2         92 ~ 471ms     재고 100%
v3        173 ~ 739ms     재고 100%
v4        192 ~ 253ms     재고 100%
```

**v2 와 v3 와 v4 의 범위는 서로 겹친다.** 그래서 이 회차가 가른 것은 v1 과 나머지다.

## 5. 왜 그 값이 나왔나

설계 6장이 지목한 지표를 회차 창별로 뽑았다.

| 지표 | v1 | v2 | v3 | v4 |
|---|---:|---:|---:|---:|
| `innodb_row_lock_waits` | **4,634 ~ 13,017** | 0 | 0 | 0 |
| `redis_commands_processed_total` | **20,094 ~ 29,335** | 260,094 ~ 359,339 | 241,664 ~ 339,980 | 241,184 ~ 241,650 |
| `hikaricp_connections_pending` | **34 ~ 35** | 0 | 0 | 0 |
| `hikaricp_connections_active` | **8** | 3 | 0 ~ 1 | 1 |
| `coupon_issue_queue_size` | 0 | 0 | 2 | 3 ~ 30 |
| `jvm_threads_peak_threads` | 102 | 102 ~ 181 | 183 | **71** |

### v1: 한 행의 배타 락이 발급을 직렬화한다

**`innodb_row_lock_waits` 가 최대 13,017 이고 다른 셋은 0 이다.**

v1 은 조건부 UPDATE 로 재고를 깎는다.

```sql
UPDATE coupon SET issued_quantity = issued_quantity + 1
 WHERE coupon_id = ? AND (total_quantity IS NULL OR issued_quantity < total_quantity)
```

**모든 요청이 같은 행을 두고 줄을 선다.** `hikaricp_connections_pending` 34 가 그 대기열이고
`active` 8 은 커넥션 여덟 개가 락을 기다리며 묶여 있다는 뜻이다. **풀이 8 이라 전부 잡혔다.**

**`redis_commands_processed_total` 이 2만대로 다른 셋의 10분의 1 이다.** v1 은 Redis 를 쓰지
않으므로 이 값은 배경 트래픽이다. **이 지표가 버전을 가장 뚜렷하게 가른다.**

**그래서 요청의 80%가 500 으로 끝난다.**

```
http_req_failed      79.97 ~ 81.11%
coupon_unexpected    15,994 ~ 16,223   전부 status=500 body={"code":"COMMON-001"}
```

`COMMON-001` 은 잡히지 않은 예외의 공통 응답이다. **커넥션 획득 타임아웃이 가장 그럴듯하다.**
풀이 8 인데 대기가 34 이면 뒤에 선 요청은 기다리다 끊긴다. 다만 앱 로그로 확인하지 않았으므로
추정이다.

**이 500 은 처리된 응답 p99 에 안 담긴다.** 판정된 응답이 아니기 때문이다. 그래서 v1 의
p99 699.8ms 는 **성공한 4,000건의 지연**이다.

### v2: 거절을 DB 앞에서 끊는다

**`innodb_row_lock_waits` 가 0 으로 떨어진다.** Redis 카운터가 재고를 세므로 초과분이 DB 에
닿지 않는다. `redis_commands_processed_total` 이 26만에서 36만으로 올라간 것이 그 일이다.

**`hikaricp_connections_pending` 도 0 이다.** 락 대기가 없으니 커넥션이 묶이지 않는다.
`active` 3 은 실제 쓰기만큼이다.

**남은 비용은 요청 스레드가 커넥션을 쥔 채 쓰는 것이다.** `jvm_threads_peak_threads` 가 102 에서
181 까지 흔들리는 것이 그 부하다. **p99 의 폭이 5.09배로 가장 큰 것도 여기서 온다.**

### v3: 큐가 쓰기를 모아 왕복을 줄인다

**`jvm_threads_peak_threads` 가 183 이다.** 플랫폼 스레드를 쓰므로 `server.tomcat.threads.max`
200 이 실제 상한이고 그 근처까지 갔다.

**`coupon_issue_queue_size` 가 2 로 거의 차지 않는다.** 벌크가 들어오는 속도를 따라 비웠다.

### v4: 플랫폼 스레드를 가장 적게 쓴다

**`jvm_threads_peak_threads` 가 71 로 넷 중 가장 낮다.** v3 의 183 의 5분의 2 다.

**가상 스레드는 대기하는 동안 캐리어를 놓는다.** 동시 요청이 2만이어도 플랫폼 스레드는 71개로
끝난다.

**`coupon_issue_queue_size` 가 3 에서 30 으로 넷 중 가장 크다.** 입구가 200 에서 막히지 않으니
큐까지 요청이 더 들어온다. **그런데도 p99 가 가장 낮고 폭도 1.31배로 좁다.**

### 수집되지 않은 지표

**`tomcat_threads_busy_threads` 는 이번에도 없었다.** 설계 6장이 v3 와 v4 를 가르는 지표로
지목했는데 존재를 확인하지 않고 적었다. 지표 이름을 확인하고 노출부터 고쳐야 한다.

## 7. 정합성

**열두 회차 전부 깨지지 않았다.**

| 불변식 | 확인 방법 | 결과 |
|---|---|---|
| R1 초과 발급 없음 | `issued_rows <= 10,000` | 전 회차 통과 |
| R2 1인 1매 | `members = issued_rows` | 전 회차 통과 |
| R3 번호 충돌 없음 | `max_seq = issued_rows` | 전 회차 통과 |
| R4 번호 유실 없음 | `gap = 0` | 전 회차 통과 |

**v1 도 이 네 항목은 통과했다.** 발급된 4,000건은 전부 올바르다.

**그러나 v1 을 "정확하지만 느리다" 로 읽으면 안 된다.** 나머지 16,000건이 500 으로 끝났다.
정합성 검증은 DB 에 들어간 행만 보므로 **응답을 못 받은 요청은 그 검증의 대상이 아니다.**
`gap 0` 은 "번호를 태우고 사라진 요청이 없다" 는 뜻이고 "모든 요청이 제대로 응답받았다" 는
뜻이 아니다.

## 8. 이 회차가 답하지 못한 것

**v2 와 v3 와 v4 의 우열이다.** 세 범위가 겹친다. 가르려면 표본을 늘리거나 부하를 올려야 한다.

**v1 의 500 이 무슨 예외인지 모른다.** `COMMON-001` 은 잡히지 않은 예외의 공통 응답이고 어느
예외인지는 앱 로그에 있는데 회차 뒤에 인스턴스를 파괴했다. `hikaricp_connections_pending` 34 에
`active` 8 이므로 커넥션 획득 타임아웃이 그럴듯하지만 **추정이다.**

**v2 와 v3 의 p99 폭이 왜 큰지 모른다.** 5.09배와 4.28배다. v2-2 는 혼잡이 0.25% 있었고 v3-1 은
`redis_commands` 가 34만으로 다른 v3 회차의 24만보다 높다. **두 회차가 무엇 때문에 달랐는지
가르지 못했다.**

**`tomcat_threads_busy_threads` 를 못 봤다.** v3 와 v4 를 가르는 지표인데 수집되지 않았다.

## 9. 절차에서 고친 것

**이 회차를 세우는 동안 일곱을 찾았다.** 앞의 여섯은 조용히 통과해 버리는 종류다.

### 배포가 발급 경로에 닿지 않는다

**`deploy.sh` 는 평상시 앱 ASG 만 교체한다.** 발급 요청은 ALB 가 쿠폰 전용 ASG 로 보내는데,
그 ASG 를 건드리지 않으므로 **이미지를 바꿔도 발급을 처리하는 코드가 그대로다.**

회차 검산이 SSM `current-sha` 만 봤고 `deploy.sh` 가 SSM 을 먼저 갱신하므로 **검산이 통과해
버렸다.** 네 버전이 서로 구별되지 않는 회차가 나왔고 v4 코드만 돌았기 때문이었다.

이제 배포 뒤에 전용 ASG 를 다시 세우고 인스턴스의 `docker ps` 로 이미지를 읽는다.

```
deploy.sh <SHA>
  -> coupon-event.sh close      desired 0
  -> coupon-event.sh open 3     새 인스턴스가 SSM current-sha 를 읽어 뜬다
  -> docker ps 로 이미지 확인
```

### 판정을 받은 VU 가 1초마다 깨어났다

`sleep(1)` 로 두면 k6 가 반복을 초당 2만 번 세고 **그때마다 남는 것이 있다.** 램프가 끝난 뒤
45초 동안 2,440 MB 가 쌓여 커널이 k6 를 죽였다. **요청은 한 건도 안 보내는 구간이다.**

```
sleep(1)            VU 당 45회   2만 VU -> 90만 회   약 2,440 MB
남은 시간만큼 한 번   VU 당  1회   2만 VU ->  2만 회   약 54 MB
```

**고친 뒤 열두 회차 전부 완주했고 메모리 최고점이 5,666 ~ 6,140 MB 다.** 앞선 회차는
7,667 MB 에서 죽었다.

### 거절 비율에 임계가 없었다

`coupon.md` 7장이 SLO 모집단에서 혼잡(503)을 빼면서 거절 비율을 따로 묶어야 한다고 적었는데
그 임계가 없었다. **503 이 세 임계 어디에도 안 걸렸다.** `coupon_congested_rate` 를 두어 1% 를
상한으로 걸었고, 이 회차에서 처음으로 그 값을 읽었다.

### 시드가 죽어도 완료로 끝난다

SSM 에 명령 셋을 넘겼고 마지막이 `rm` 이었다. **SSM 은 마지막 명령의 exit code 를 전체 상태로
삼으므로 `rm` 이 늘 성공해서 본문이 죽어도 `Success` 가 됐다.** `rm` 을 본문과 한 줄에 이어
붙여 `rc` 를 보존하고, 넣은 뒤에 행 수를 센다.

### 시드를 앱보다 먼저 돌렸다

**스키마는 앱이 부팅할 때 만든다.** 앱 healthy 를 기다린 뒤에 시드를 넣어야 한다.

### 검산이 로그를 값으로 읽었다

`log` 이 stdout 으로 찍혔다. **stdout 은 `run_on_batch` 가 배치의 출력을 돌려주는 자리라
`out=$(run_on_batch ...)` 가 로그를 값으로 읽었다.** `log` 를 stderr 로 보냈다.

### 생성기 CPU 를 잴 수 없었다

**`node_exporter` 가 생성기에 없었다.** Prometheus 의 node 잡이 이미 그 인스턴스를 찾고 있었는데
익스포터가 없어 타깃이 down 이었다. 회차마다 `top` 을 손으로 걸어야 했고 그래서 한 번도 못
쟀다. 익스포터를 두어 **6장의 값을 처음 얻었다.**
