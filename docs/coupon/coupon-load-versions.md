# 선착순 쿠폰 버전별 부하 시험 기록

[coupon-version-rounds.md](coupon-version-rounds.md) 가 설계한 회차의 결과를 여기 모은다.
회차가 늘면 이 문서에 이어 적는다.

**이 회차를 세우는 동안 절차의 결함 여섯을 찾았고 9장에 적었다.** 그중 하나는 배포가 발급
경로에 닿지 않는 것이어서, 그것을 고치기 전의 회차는 버렸다.

---

## 1. 2026-09-27 회차 (생성기 1대)

v1 부터 v4 까지 각 3회, 모두 12회 돌렸다.

```
생성기     m7i-flex.large 1대, 2만 VU 전부
k6 출력    -o experimental-prometheus-rw
p99        회차 창을 자른 query_range 의 최댓값
부하       재고 10,000 / VU 20,000 / ramp 60s / hold 30s
앱         쿠폰 전용 ASG t3.small 3대 / RDS db.t4g.micro Multi-AZ / ElastiCache cache.t4g.micro 2노드
```

**이 회차를 두 번 버리고 세 번째에 얻었다.** 무엇을 왜 버렸는지는 8장에 있다.

## 2. 결론

**v1 은 요구 부하에서 요청의 80%에 500 을 돌려준다.** 재고 10,000 중 3,746 에서 4,020 만
나가고, p99 도 1.29초에서 1.71초로 SLO 1초를 넘긴다. **느린 것이 아니라 깨진 것이다.**

```
http_req_failed      80.19%   16,039 / 20,000        (v1-3)
coupon_unexpected    16,039   전부 status=500, COMMON-001
k6 exit              99       임계 셋을 깼다
```

**v1 에서 v2 로 가는 값이 가장 크다.** p99 가 3.1배 내려가고 재고를 다 턴다. Redis 카운터가
거절을 DB 앞에서 끊는 것이 그만큼을 벌었다.

**v2 와 v3 와 v4 는 이 부하에서 서로 구별되지 않는다.** 세 범위가 겹친다. 다만 v4 가 가장
낮고 플랫폼 스레드를 가장 적게 쓴다.

**열두 회차 전부 정합성이 깨지지 않았다.** `gap 0` 이고 `members = issued_rows` 다.
**다만 v1 에서 그것은 발급된 4,000건에 한해서만 맞는 말이다.** 나머지 16,000건은 서버 오류로
끝났다.

## 4. 버전 비교

**판정값은 그 버전이 낸 p99 중 가장 나쁜 값이다.** 분위수를 평균내면 그 결과는 분위수가
아니므로 평균으로 판정하지 않는다. 평균은 회차 변동의 중심을 보는 값으로 아래에 따로 싣는다.

| 버전 | p99 | 발급 | SLO 1초 | 판정 |
|---|---:|---:|---|---|
| v1 DB 조건부 UPDATE | **1,714.9ms** | 3,746 ~ 4,020 | **미달** | 요청 80%에 500. 깨진 것이다 |
| v2 Redis 카운터 | 532.4ms | 10,000 | 통과 | |
| v3 인스턴스 큐 + 벌크 | 420.9ms | 10,000 | 통과 | |
| v4 가상 스레드 (채택) | 388.6ms | 10,000 | 통과 | 넷 중 최저 |

### 세 회차의 평균

**평균은 판정값이 아니다.** p99 를 회차에 걸쳐 평균낸 값은 p99 가 아니다. 다만 회차 변동의
중심과 폭을 함께 보여주므로 싣는다.

| 버전 | 처리된 응답 p99 평균 | 최저 | 최고 | 폭 | 전체 응답 p99 평균 | 발급 평균 |
|---|---:|---:|---:|---:|---:|---:|
| v1 DB 조건부 UPDATE | 1,443.8ms | 1,287.8 | 1,714.9 | 1.33배 | 1,443.8ms | **3,909** |
| v2 Redis 카운터 | 468.0ms | 368.4 | 532.4 | 1.45배 | 710.7ms | 10,000 |
| v3 인스턴스 큐 + 벌크 | 344.1ms | 216.5 | 420.9 | 1.94배 | 423.2ms | 10,000 |
| v4 가상 스레드 (채택) | **311.5ms** | 188.9 | 388.6 | 2.06배 | **378.1ms** | 10,000 |

**평균으로도 순서가 같다.** v1 이 홀로 높고 v4 가 가장 낮다.

**폭이 v1 에서 가장 작다.** 1.33배다. v1 은 늘 나쁘고 그 나쁨이 일정하다. v4 는 2.06배로 가장
흔들리는데 **값이 작아서 같은 절대 변동이 큰 비율로 보이는 것이다.** v4 의 폭은 200ms 이고
v1 의 1.33배는 427ms 다.

**`전체 응답 p99` 평균에서 v2 가 튄다.** settled 468.0ms 인데 http 710.7ms 로 간격이 242.7ms 다.
v2-2 의 간격 499.1ms 가 평균을 끌어올렸다. 혼잡이 그만큼 있었다는 뜻이다.

**v1 은 두 값이 같다.** 세 회차 모두 혼잡이 0 이라 그렇다. 아래 두 절이 그 이유를 적는다.

### v1 과 나머지 사이에만 선이 있다

```
v1        1,288 ~ 1,715ms     재고 40%
v2          368 ~   532ms     재고 100%
v3          217 ~   421ms     재고 100%
v4          189 ~   389ms     재고 100%
```

**v1 만 다른 자리에 있다.** v2, v3, v4 의 범위는 서로 겹친다.

| 두 버전 | 범위가 겹치나 |
|---|---|
| v1 과 v2 | 겹치지 않는다. 1,288 > 532 |
| v2 와 v3 | 겹친다. 368 ~ 532 와 217 ~ 421 |
| v3 와 v4 | 겹친다. 217 ~ 421 와 189 ~ 389 |

**그래서 이 회차가 가른 것은 v1 과 나머지다.** v2 에서 v4 까지의 순서는 경향으로만 읽는다.

## 5. 왜 그 값이 나왔나

설계 6장이 지목한 지표를 회차 창별로 뽑았다. **이번에는 지표가 버전을 갈랐다.**

| 지표 | v1 | v2 | v3 | v4 |
|---|---:|---:|---:|---:|
| `innodb_row_lock_waits` | **4,599 ~ 12,934** | 0 | 0 | 0 |
| `redis_commands_processed_total` | **20,106 ~ 29,321** | 260,088 ~ 359,669 | 241,733 ~ 340,466 | 241,420 ~ 241,758 |
| `hikaricp_connections_pending` | **35 ~ 102** | 0 | 0 | 0 |
| `hikaricp_connections_active` | **8** | 2 ~ 4 | 1 | 0 ~ 1 |
| `slow_queries` | **0 ~ 19** | 0 ~ 1 | 0 | 0 |
| `coupon_issue_queue_size` | 0 | 0 | **1 ~ 3** | 0 ~ 1 |
| `jvm_threads_peak_threads` | **247 ~ 248** | 136 ~ 248 | 95 ~ 136 | **67** |

### v1: 한 행의 배타 락이 발급을 직렬화한다

**`innodb_row_lock_waits` 가 최대 12,934 다.** 다른 셋은 0 이다.

v1 은 조건부 UPDATE 로 재고를 깎는다.

```sql
UPDATE coupon SET issued_quantity = issued_quantity + 1
 WHERE coupon_id = ? AND (total_quantity IS NULL OR issued_quantity < total_quantity)
```

**모든 요청이 같은 행을 두고 줄을 선다.** 초당 333명이 도착하는데 한 번에 하나만 그 행을
쥘 수 있으니 나머지는 대기한다. `hikaricp_connections_pending` 이 최대 102 인 것이 그
대기열이고, `active` 8 은 커넥션 여덟 개가 락을 기다리며 묶여 있다는 뜻이다.

**`redis_commands_processed_total` 이 2만대로 다른 셋의 10분의 1 이다.** v1 은 Redis 를 쓰지
않으므로 이 값은 배경 트래픽이다. **이 지표가 버전을 가장 뚜렷하게 가른다.**

**`slow_queries` 19 건도 v1 에서만 나왔다.** 락을 기다린 UPDATE 가 느린 쿼리 기준을 넘었다.

**그래서 재고를 다 털지 못한다.** 90초 동안 4,000건이면 초당 약 44건이고, 도착률 333건의
13%다.

**나머지는 500 으로 끝났다.** v1-3 의 k6 요약이 그것을 보인다.

```
http_req_failed      80.19%   16,039 / 20,000
coupon_unexpected    16,039   전부 status=500 body={"code":"COMMON-001"}
```

`COMMON-001` 은 잡히지 않은 예외의 공통 응답이다. **어느 예외인지는 앱 로그에 있는데 회차
뒤에 인스턴스를 파괴해서 확인하지 못했다.** `hikaricp_connections_pending` 이 최대 102 이고
`active` 가 8 이므로 커넥션 획득 타임아웃이 가장 그럴듯하지만 **추정이다.**

**이 500 은 `coupon_settled_duration` 에 담기지 않는다.** 판정된 응답이 아니기 때문이다.
그래서 v1 의 p99 1.29초는 **성공한 4,000건의 지연**이고, 실패한 16,039건은 그보다 빨랐다.

```
coupon_settled_duration  avg 607.58ms     성공 응답만
http_req_duration        avg 384.79ms     전체. 500 이 더 빨랐다
```

### v2: 거절을 DB 앞에서 끊는다

**`innodb_row_lock_waits` 가 0 으로 떨어진다.** Redis 카운터가 재고를 세므로 초과분은 DB 에
닿지 않는다. `redis_commands_processed_total` 이 26만에서 36만으로 올라간 것이 그 일이다.

**`hikaricp_connections_pending` 도 0 이다.** 락 대기가 없으니 커넥션이 묶이지 않는다.
`active` 2~4 는 실제 쓰기만큼이다.

**남은 비용은 요청 스레드가 커넥션을 쥔 채 쓰는 것이다.** 발급 하나마다 요청 스레드가
INSERT 를 기다린다. `jvm_threads_peak_threads` 가 136 에서 248 까지 흔들리는 것이 그 부하다.

### v3: 큐가 쓰기를 모아 왕복을 줄인다

**`coupon_issue_queue_size` 가 1에서 3으로, v3 에서만 0 이 아니다.** 인스턴스별 큐가 실제로
동작했다는 증거다. 다만 **최대 3 이라 큐가 거의 차지 않았다.** 벌크가 들어오는 속도를 따라
비웠다는 뜻이다.

**`jvm_threads_peak_threads` 가 95에서 136으로 v2 보다 낮다.** 요청 스레드가 티켓만 큐에 넣고
바로 풀리므로 동시에 살아 있는 스레드가 줄었다.

**`slow_queries` 가 0 이다.** 벌크 INSERT 가 왕복을 줄인 값이다.

### v4: 플랫폼 스레드를 가장 적게 쓴다

**`jvm_threads_peak_threads` 가 67 로 넷 중 가장 낮다.** v3 의 95~136 보다도 낮다.

**가상 스레드는 플랫폼 스레드를 점유하지 않는다.** 대기하는 동안 캐리어 스레드를 놓으므로,
동시 요청이 2만이어도 플랫폼 스레드는 67개로 끝난다. v1 의 247~248 과 비교하면 4분의 1 이다.

**p99 도 넷 중 가장 낮다.** 다만 v3 와 범위가 겹치므로 이 회차만으로 v4 가 v3 보다 빠르다고
말하지는 않는다.

### v1 은 거절하지 않고 모두 줄 세운다

**두 지표의 간격이 그것을 말한다.** `coupon_settled_duration` 은 판정이 끝난 응답(200, 409,
410)만 담고 `http_req_duration` 은 혼잡(503)까지 담는다. 그래서 간격이 벌어지면 혼잡이 많다는
뜻이다.

| 회차 | 처리된 응답 | 전체 응답 | 간격 |
|---|---:|---:|---:|
| v1-1 | 1,287.8ms | 1,287.8ms | **0** |
| v1-2 | 1,714.9ms | 1,714.9ms | **0** |
| v1-3 | 1,328.8ms | 1,328.8ms | **0** |
| v2-1 | 503.2ms | 706.3ms | 203.1ms |
| v2-2 | 532.4ms | 1,031.5ms | **499.1ms** |
| v2-3 | 368.4ms | 394.4ms | 26.0ms |
| v3-1 | 420.9ms | 498.2ms | 77.3ms |
| v3-2 | 394.9ms | 541.1ms | 146.2ms |
| v3-3 | 216.5ms | 230.4ms | 13.9ms |
| v4-1 | 388.6ms | 561.2ms | 172.6ms |
| v4-2 | 188.9ms | 199.3ms | 10.4ms |
| v4-3 | 357.1ms | 373.9ms | 16.8ms |

**v1 은 세 회차 모두 간격이 정확히 0 이다.** 혼잡 응답이 한 건도 없었다.

**v1 에는 큐가 없어 503 을 낼 자리가 없다.** 요청이 락을 기다리다 결국 응답을 받으므로 전부
판정된 응답으로 담긴다. v2 부터는 큐와 서킷이 있어 넘치면 돌려보낸다.

**이것이 두 설계의 성격을 가른다.** v1 은 감당할 수 없는 요청도 전부 줄 세워 p99 를 1.7초까지
끌고 가면서 90초 안에 재고를 못 턴다. **v2 부터는 못 받을 요청을 빨리 돌려보내고 나머지를
제때 처리한다.** 재고를 다 터는 것과 p99 가 낮은 것이 같은 뿌리에서 나온다.

### 수집되지 않은 지표

**`tomcat_threads_busy_threads` 는 이번에도 없었다.** 설계 6장이 v3 와 v4 를 가르는 지표로
지목했는데 존재를 확인하지 않고 적었다. 지표 이름을 확인하고 노출부터 고쳐야 한다.

## 6. 정합성

**열두 회차 전부 깨지지 않았다.**

| 불변식 | 확인 방법 | 결과 |
|---|---|---|
| R1 초과 발급 없음 | `issued_rows <= 10,000` | 전 회차 통과 |
| R2 1인 1매 | `members = issued_rows` | 전 회차 통과 |
| R3 번호 충돌 없음 | `max_seq = issued_rows` | 전 회차 통과 |
| R4 번호 유실 없음 | `gap = 0` | 전 회차 통과 |

**v1 도 이 네 항목은 통과했다.** 발급된 4,000건은 전부 올바르다.

**그러나 v1 을 "정확하지만 느리다" 로 읽으면 안 된다.** 나머지 16,039건이 500 으로 끝났다.
정합성 검증은 DB 에 들어간 행만 보므로 **응답을 못 받은 요청은 그 검증의 대상이 아니다.**
`gap 0` 은 "번호를 태우고 사라진 요청이 없다" 는 뜻이고, "모든 요청이 제대로 응답받았다" 는
뜻이 아니다.

## 7. 생성기가 회차마다 OOM 으로 죽었다

**VU 2만이 7.44 ~ 7.49 GB 를 쓰고 인스턴스가 7.78 GB 다.** 열두 회차 중 열한 회차에서 k6 가
커널에 죽었다.

| 종료 | 회차 | 뜻 |
|---|---|---|
| `exit 137` | 열한 회차 | SIGKILL. OOM |
| `exit 99` | v1-3 | 임계 실패로 정상 종료. **완주했다** |

**여유 300 MB 가 열두 번 중 한 번 넘기는 경계다.**

```
Out of memory: Killed process (k6) total-vm:8804788kB, anon-rss:7442372kB
```

**그래도 값을 얻었다.** k6 가 5초마다 Prometheus 로 push 하므로 죽기 전까지의 시계열이
남는다. 재고와 정합성은 죽기 전에 달성된다.

**세 후보를 측정으로 배제했다.**

| 후보 | 어떻게 배제했나 |
|---|---|
| `-o experimental-prometheus-rw` 가 마지막 한 방울 | 빼도 죽었다. 차이 18 MB |
| 시나리오 변경(105줄)이 VU 당 메모리를 늘렸다 | 2026-09-14 시점으로 되돌려도 죽었다. 차이 44 MB 안 |
| AMI 와 커널이 바뀌었다 | `20260904` AMI 를 띄워 재 봤다. `MemTotal` 동일 |

**그러니 1대로는 2만 VU 를 안정적으로 낼 수 없다.** 여유 300 MB 로 늘 경계에 있다.

### 앞선 회차는 완주했다

**그 회차들의 기록이 그것을 증명한다.** `fm-infra` 의 부하 시험 기록 2장에 이 줄이 있다.

```
| 실패율                            | (정하지 않음) | 0.00%   |
| 504 / 502 / 연결 오류 / Target 5xx |              | 0/0/0/0 |
```

**`실패율` 과 `연결 오류` 는 k6 요약에서만 나오는 값이다.** k6 가 죽으면 요약을 못 찍으므로
이 줄을 쓸 수 없다. `http_reqs` 가 정확히 20,000 이라는 서술도 같다. 혼잡이 27,382건 난
회차의 세부까지 적혀 있으니 그 회차들도 끝까지 돌았다.

**그리고 그 팀은 배치 서버 메모리 고갈을 기록에 남겼다.** k6 OOM 이 났으면 적었을 것이다.

**그러니 같은 환경에서 이전에는 됐고 이번에는 안 된다. 원인을 찾지 못했다.** 위 세 후보를
배제했고 그 밖을 보지 못했다. 가르는 순서는 8장에 적었다.

## 8. 이 회차가 답하지 못한 것

**v2 와 v3 와 v4 의 우열이다.** 세 범위가 겹친다. 가르려면 표본을 늘리거나 부하를 올려야
한다.

**v1 의 500 이 무슨 예외인지 모른다.** `COMMON-001` 은 잡히지 않은 예외의 공통 응답이고
어느 예외인지는 앱 로그에 있는데 회차 뒤에 인스턴스를 파괴했다. `hikaricp_connections_pending`
최대 102 에 `active` 8 이므로 커넥션 획득 타임아웃이 그럴듯하지만 **추정이다.**

**OOM 이 왜 이번에만 나는지 모른다.** 생성기 환경을 세 축으로 재서 같음을 확인했고 앞선
회차가 완주했음도 기록으로 확인했는데 원인을 찾지 못했다. 가르려면 이 순서가 값싸다.

| 순서 | 무엇 | 왜 |
|---|---|---|
| 1 | VU 1만으로 한 회차 | 메모리가 선형인지 본다. 3.7 GB 면 VU 당 369 KB 가 맞다 |
| 2 | 2026-09-14 커밋을 통째로 체크아웃해 회차 | 시나리오만 되돌린 것과 달리 앱까지 그때로 맞춘다 |
| 3 | 판정 뒤 `sleep` 을 길게 해 반복을 2만으로 | 반복과 메트릭 표본의 몫을 확인한다 |

**2번이 가장 결정적이다.** 이전에 완주한 조합을 그대로 재현하는 것이고, 그래도 죽으면 인프라
밖을 봐야 한다.

**열한 회차의 임계 판정을 모른다.** `issue.js` 의 임계가 넷인데 p99 와 DB 정합성만 뽑았다.
그래서 v1 이 요청의 80%에 500 을 돌려준다는 것을 v1-3 한 회차에서 우연히 발견했다.

```
✗ 'rate<0.01' rate=80.19%
thresholds on metrics 'coupon_settled_duration, coupon_unexpected, http_req_failed' have been crossed
k6 exit 99
```

**`coupon_unexpected: ['count==0']` 이 정확히 이것을 잡으려고 있었는데 내 기록에 그 신호가
없었다.** 나머지 열한 회차는 k6 요약이 OOM 으로 사라지고 Prometheus 도 파괴해서 영영 모른다.
`k6_coupon_unexpected_total` 이 시계열 목록에 있었는데 뽑지 않았다.

**그래서 v2, v3, v4 도 500 을 냈는지 모른다.** 발급이 10,000 이었으므로 대량은 아니었겠지만
`count==0` 을 지켰는지는 확인할 수 없다.

**`tomcat_threads_busy_threads` 를 못 봤다.** v3 와 v4 를 가르는 지표인데 수집되지 않았다.

**v1 회차의 p99 모집단이 다르다.** 재고를 다 털지 못했으므로 소진 응답(410)의 비율이 다른
회차와 다르다. 그래서 v1 의 p99 를 다른 버전과 같은 축에 놓고 읽을 때 주의해야 한다.
**다만 발급 수라는 다른 축이 같은 방향을 가리키므로 결론은 흔들리지 않는다.**

## 9. 절차에서 고친 것

**이 회차를 세우는 동안 여섯을 찾았다.** 앞의 다섯은 조용히 통과해 버리는 종류다.

### 배포가 발급 경로에 닿지 않는다

**`deploy.sh` 는 평상시 앱 ASG 만 교체한다.** 발급 요청은 ALB 가 쿠폰 전용 ASG 로 보내는데,
그 ASG 를 건드리지 않으므로 **이미지를 바꿔도 발급을 처리하는 코드가 그대로다.**

그때 회차 검산이 SSM `current-sha` 만 봤다. `deploy.sh` 가 SSM 을 먼저 갱신하므로 **검산이
통과해 버렸다.** 네 버전이 서로 구별되지 않는 회차가 나왔고, **v4 코드만 돌았기 때문이었다.**
그 회차는 버렸다.

이제 배포 뒤에 전용 ASG 를 다시 세우고 인스턴스의 `docker ps` 로 이미지를 읽는다.

```
deploy.sh <SHA>
  -> coupon-event.sh close      desired 0
  -> coupon-event.sh open 3     새 인스턴스가 SSM current-sha 를 읽어 뜬다
  -> docker ps 로 이미지 확인
```

**`refresh-env.sh` 가 부팅 시 `GIT_SHA=$(get current-sha)` 로 SSM 을 읽으므로 재생성이 새
이미지를 가져온다.** 그것을 확인하고 넣었다.

### 시드가 죽어도 완료로 끝난다

SSM 에 명령 셋을 넘겼고 마지막이 `rm` 이었다. **SSM 은 마지막 명령의 exit code 를 전체 상태로
삼으므로 `rm` 이 늘 성공해서 본문이 죽어도 `Success` 가 됐다.**

```
ERROR 1146 (42S02) at line 19: Table 'freshmarket.member_coupon_status_history' doesn't exist
```

앱이 스키마를 만들기 전에 시드가 돌아 이렇게 죽었는데 스크립트는 26초 만에 완료로 끝났고,
회차가 빈 DB 로 시작해 이벤트 열기가 404 로 멈췄다. 그때서야 드러났다.

**`rm` 을 본문 실행과 한 줄에 이어 붙여 `rc` 를 보존하고, 넣은 뒤에 행 수를 센다.**

### 시드를 앱보다 먼저 돌렸다

**스키마는 앱이 부팅할 때 만든다.** `apply.sh` 가 배포를 비동기로 걸어 두므로 앱 healthy 를
기다린 뒤에 시드를 넣어야 한다.

### 검산이 로그를 값으로 읽었다

`log` 이 stdout 으로 찍혔다. **stdout 은 `run_on_batch` 가 배치의 출력을 돌려주는 자리라
`out=$(run_on_batch ...)` 가 로그를 값으로 읽었다.** 방금 넣은 검산이 그렇게 깨졌다.

```
회원 [10:25:55] / 발급이력 배치 / 시험쿠폰 i-0ff2fb4b4a3900a67
```

시드는 제대로 들어가 있었는데 검산이 없다고 판정했다. **`log` 를 stderr 로 보냈다.**

### 파괴가 버전 이미지를 지운다

`destroy.sh` 가 ECR 리포지토리를 지운다. 그 뒤 `apply` 하면 GitHub Actions 가 `main` 만
빌드하므로 **`perf/coupon-v1`, `v2`, `v3` 이미지가 없다.** v1 배포가 SSM 만 바꾸고 컨테이너는
안 떴다.

**`deploy.yml` 의 `skip_rolling=true` 로 이미지만 만든다.** 다만 셋을 동시에 걸면 안 된다.
`concurrency` group 이 하나라서 **`cancel-in-progress: false` 라도 대기 건이 여럿이면 GitHub
이 가장 최근 것만 남긴다.** 순차로 돌린다.

### 임계 넷 중 하나만 확인했다

8장에 적었다. **이번 회차의 가장 큰 결함이다.**
