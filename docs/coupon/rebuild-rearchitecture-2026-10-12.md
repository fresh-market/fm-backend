# 재건을 바닥부터 다시 세우는 설계

`rebuild-redesign-2026-10-12.md` 가 고침 셋을 넣었고 셋 다 회차로 확인됐다. 그런데 T-1 에서
또 같은 모양의 결함이 나왔다. **고침을 더 얹는 대신 재건이 무엇을 책임지는지부터 다시 정한다.**

이 문서는 설계만 담는다. 코드를 아직 안 고쳤다.

---

## 1. 열 번 고쳐도 같은 자리가 새는 까닭

이 세션에서 잡은 결함을 늘어놓으면 전부 한 문장으로 모인다.

| 회차 | 증상 | 뿌리 |
|---|---|---|
| N-2 | 3대가 도는데 명부가 2 | 주도자가 남을 못 셌다 |
| Q-1 | 재건이 4회, 한 대가 3회 | 주도자가 자기를 다시 불렀다 |
| S-3 | 명부가 0, 8밀리초에 끝남 | 주도자가 남을 못 셌다 |
| J-4 | 결번 180 | 주도자가 남을 못 셌다 |
| T-1 | 발급 안 하는 대가 주도, `instances=0` | 셀 자격 없는 대가 주도자가 됐다 |

**다섯 개가 다 "주도자가 참가자를 세는 데 실패한 것" 이다.**

고침은 매번 세는 방법을 손봤다. 플러시가 알리게 했고, 순번 확보가 알리게 했고, 큐를 쥔 동안
알리게 했다. **세는 방법을 고칠 때마다 안 세어지는 새 경우가 나왔다.**

그럴 수밖에 없다. **지금 재건은 분산 합의다.** 주도자가 "참가자 전원" 을 알아야 하고, 그
명부를 **장애가 난 그 저장소에** 두고 있다. 합의를 최선노력 가십으로 구현한 것이라, 구멍은
고칠 때마다 자리를 옮긴다.

**그래서 세는 방법을 또 고치지 않는다. 셀 필요를 없앤다.**

---

## 2. 재건이 실제로 책임지는 것

재건이 지킨다고 여겨 온 것을 갈라 보면 둘이 섞여 있다.

```
안전   같은 순번이 두 사람에게 안 나간다,  한 사람이 두 장 안 받는다,  재고를 안 넘는다
활용   재고를 남기지 않고 다 내보낸다,      번호만 태우고 사라진 것을 되살린다
```

**안전은 재건이 지키는 것이 아니다. DB 가 지킨다.**

```sql
UNIQUE KEY uk_mc_coupon_member (coupon_id, member_id)   -- 1인 1매
UNIQUE KEY uk_mc_coupon_seq    (coupon_id, issue_seq)   -- 같은 순번 두 번 금지
CONSTRAINT chk_mc_issue_seq    CHECK (issue_seq <= issue_limit)  -- 재고 상한
```

**카운터가 뒤로 밀려 같은 번호가 두 번 나가도 초과 발급은 안 난다.** 둘 중 하나가
`uk_mc_coupon_seq` 에 걸려 그 요청이 실패하고, 그 번호가 결번으로 남는다. 이것은 기존 주석에도
이미 적혀 있다 (`application-coupon.yml` 의 `rebuild-contribute-wait`).

**그러면 재건의 기다림은 안전이 아니라 활용을 위한 것이다.** 결번과 실패 요청을 줄이려고 3초를
쓰는 것이고, 그 3초 동안 발급은 멈춘다.

**설계가 잘못 놓인 자리가 여기다.** 재건을 안전 장치로 여겨 차단형 합의로 지었는데, 실제로는
품질 장치다. **품질 장치에 합의를 쓰면 합의가 깨질 때 품질이 아니라 가용성이 깨진다.**

---

## 3. 지금 설계가 합의를 요구하는 지점

네 키 중 둘이 **완전한 전역 시야**를 요구한다.

| 키 | 세우는 식 | 전역 시야가 필요한가 |
|---|---|---|
| `counter` | `max(DB 의 MAX(issue_seq), 모든 큐의 최대 순번)` | 필요하다 |
| `free` | `1..counter` 에서 DB 와 모든 큐를 뺀 나머지 | 필요하다 |
| `seq` | DB 행 + 모든 큐의 티켓 | 빠진 만큼만 빈다 |
| `pending` | 모든 큐의 티켓 | 빠진 만큼만 빈다 |

**`counter` 와 `free` 의 "모든" 이 합의를 끌어들인다.** 하나라도 빠지면 `counter` 가 뒤로 가고
`free` 가 남이 쥔 번호를 아무도 안 쥔 것으로 본다. 그래서 주도자가 참가자를 세고, 세려고 명부를
두고, 명부를 Redis 에 두어 장애와 함께 잃는다.

## 4. 바꾸는 축

**합의를 버리고 단조 병합으로 간다.**

`counter` 를 "모두가 합의해 정하는 값" 이 아니라 **올리기만 하는 값**으로 본다. 올리기만 하는
최댓값 레지스터는 교환법칙과 결합법칙과 멱등을 모두 만족한다. 그러면 N 대가 각자 아는 값으로
제멋대로 올려도 결과가 전체 최댓값 하나로 수렴한다. **누가 몇 대인지 아무도 몰라도 된다.**

**이 성질은 이미 코드에 있다.** `coupon-open-gate.lua` 가 현재 값보다 작은 값을 안 쓴다. 그
스크립트의 주석이 "재건은 언제나 올리는 방향이다" 라고 적어 두었다. **그 성질을 방어가 아니라
설계의 중심으로 옮긴다.**

여기에 하나를 더한다.

**각 인스턴스는 전체 최댓값은 몰라도 자기가 받은 최댓값은 안다.** 순번 확보가 번호를 돌려줄 때
그 값을 보기 때문이다. 그 값은 전체 최댓값의 하한이고, **자기가 쥔 번호를 지키기에는 그것으로
충분하다.** 남이 쥔 번호는 그 남이 자기 값으로 지킨다.

```
전체 최댓값 = max(각 인스턴스의 자기 최댓값, DB 의 MAX(issue_seq))
```

**오른쪽 항들은 전부 지역 정보다.** 각자 자기 항만 올리면 왼쪽이 저절로 선다. 기다릴 대상이
없다.

## 5. 새 설계

### 5.1 순번 확보가 스스로 고치는 구조

**승격으로 카운터가 뒤로 간 것은 재건이 아니라 순번 확보가 고친다.**

인스턴스는 이 쿠폰에서 자기가 받은 최대 순번을 들고 있다. 그 값을 스크립트에 함께 넘긴다.

```lua
-- ARGV[5]=이 인스턴스가 이 쿠폰에서 받은 최대 순번. 없으면 0
local mark = tonumber(ARGV[5])
local n = redis.call('INCR', KEYS[3])

-- 카운터가 내가 이미 받은 번호보다 낮으면 승격이 뒤로 민 것이다. 그 번호들은 누군가 쥐고 있다
if n <= mark then
  n = mark + 1
  redis.call('SET', KEYS[3], n)
end

if n <= tonumber(ARGV[2]) then
  return give(tostring(n))
end
```

**왕복이 늘지 않는다.** 같은 스크립트 안의 비교 하나와, 드물게 `SET` 하나다.

**이 네 줄이 승격 경로의 재건을 대체한다.** 재연결 감시도, 주도자도, 락도, 명부도, 기여도,
3초 기다림도 필요 없다. 뒤로 간 카운터는 **그것을 아는 인스턴스의 다음 요청 한 건이** 고친다.

**정지가 0 이다.** 지금 측정값은 경로별로 0.244 ~ 0.856초이고 그동안 그 이벤트의 모든 발급이
멈춘다. 새 구조에서는 멈추는 구간이 없다.

**지금도 이 값을 이미 재고 있다.** `CouponSeqRebuildTrigger.measureBehind` 가 `highWater` 로
같은 비교를 하고 **재기만 한다.** `rebuild-redesign-2026-10-12.md` 6장이 "BEHIND 승격" 을
미결로 남긴 그 항목이고, 이 설계가 그것을 승격시키는 방법이다. 승격 조건인 "무장애 회차에서
표본 0건" 은 L-1/L-2/N-1/N-3/N-4/O-1/T-1 에서 충족됐다.

### 5.2 키 부재만 남는 재건

키가 통째로 사라진 경우에는 `INCR` 이 1 을 다시 주므로 5.1 로 안 된다. 스크립트가 `-2` 를
내고 누군가 카운터를 다시 세워야 한다.

**그 재건은 기다리지 않는다.**

```
bound = max(DB 의 MAX(issue_seq), 내가 받은 최대 순번)
coupon-open-gate.lua 로 counter 를 bound 까지 올린다
```

**DB 조회 하나와 Redis 왕복 하나다.** 멱등이고 단조라 **여러 대가 각자 돌아도 결함이 아니다.**
오히려 여러 대가 도는 것이 수렴을 돕는다. 다섯 대가 다섯 번 돌면 다섯 항의 최댓값이 선다.

**락이 없다.** 락은 동시 실행을 막으려고 있었고, 동시 실행이 위험한 까닭은 낮은 값이 높은 값을
덮을 수 있어서였다. 올리기만 하면 덮을 수 없다.

**`-4` 도 없다.** 재건이 발급을 멈추지 않으므로 "재건 중" 이라는 상태 자체가 없다. Q-1 의
자기호출 고리는 상태가 없어져 사라진다.

### 5.3 각자 자기 몫만 복구하는 기여

키 부재는 `seq` 와 `pending` 도 함께 잃는다. 그러면 이미 번호를 받고 기다리는 회원이 재시도해
새 번호를 받을 수 있고, 둘 중 하나가 `uk_mc_coupon_member` 에 걸려 번호 하나가 결번이 된다.

**이것은 지역 정보로 막힌다.** 그 티켓을 쥔 인스턴스가 자기 큐의 회원들을 `seq` 와 `pending` 에
다시 써 넣으면 된다. **자기 큐는 자기만 알고, 자기만 쓰면 되고, 남을 기다릴 일이 없다.**

```
각 인스턴스는 -2 를 보면 자기 큐의 티켓을 seq 와 pending 에 다시 쓴다
쓰고 나서 아무에게도 보고하지 않는다
```

**지금 `CouponSeqContributor` 가 하는 일과 쓰는 내용이 같다.** 다른 것은 **완료를 보고하지
않는다**는 것 하나다. 보고가 없으면 주도자도 필요 없고, 주도자가 없으면 셀 것도 없다.

**지역 복구의 합집합이 전역 복구와 같다.** 각 티켓은 정확히 한 인스턴스에 있으므로, 전원이 자기
몫을 쓰면 빠지는 티켓이 없다. **그런데 그것을 확인하려고 기다릴 필요가 없다.** 늦게 쓰는 대가
있어도 그 대의 티켓이 늦게 복구될 뿐이고, 그동안 그 회원이 재시도하면 결번 하나가 난다.

```
지금    전원을 기다린다        늦은 대 하나가 전체 발급을 3초 멈춘다
새로    각자 쓴다              늦은 대의 회원만 그 사이 재시도에서 결번을 낸다
```

**장애를 전체에서 지역으로 가둔다.** 느린 인스턴스 하나의 비용을 그 인스턴스가 낸다.

### 5.4 온라인에서 세우지 않는 `free`

`free` 만은 지역 정보로 안 된다. `1..counter` 에서 DB 와 모든 큐를 빼야 하므로 전역 시야가
필요하고, **이것이 합의를 요구하는 유일한 항목으로 남는다.**

**그래서 온라인에서 안 세운다. 재건은 `free` 를 비운 채 둔다.**

번호만 태우고 사라진 요청은 두 경로가 되살린다.

| 경로 | 무엇을 되살리나 | 전역 시야 |
|---|---|---|
| `pending` 회수 (`reclaim-after` 60초) | 사용자가 떠난 번호 | 필요 없다. 회원 단위다 |
| 정합성 배치 (`CouponConsistencyScheduler`) | `pending` 째 잃은 번호 | 필요하다. 온라인이 아니다 |

**회수가 흔한 경우를 이미 덮는다.** `free` 재건이 필요한 것은 `pending` 까지 잃은 경우뿐이고,
그때도 5.3 이 각 인스턴스의 티켓을 `pending` 에 다시 넣으므로 남는 것은 **아무도 안 쥔 번호**
뿐이다. 그것은 급하지 않다. 발급이 끝난 뒤에 세어도 늦지 않다.

**배치를 온라인 경로에서 뺀 것이 요점이다.** 완전한 시야가 필요한 계산을 요청 경로에서 치우면,
요청 경로에 합의가 안 남는다.

## 6. 절차

### 6.1 평상시

```
1. 순번 확보가 free 를 먼저 보고, 없으면 counter 를 INCR 한다
2. 받은 값이 내가 아는 최댓값보다 낮으면 그 최댓값 다음으로 올린다      <- 새로 넣는다
3. 재고 상한을 넘으면 되돌리고 소진 경로로 간다
4. 번호를 주고 seq 와 pending 에 쓴다
5. 받은 값으로 내 최댓값을 갱신한다                                   <- 새로 넣는다
```

### 6.2 키가 사라졌을 때

```
6.  스크립트가 -2 를 돌려준다
7.  그 요청은 혼잡(503)으로 답한다. 지금과 같다
8.  이 인스턴스가 복구를 띄운다. 쿠폰별 중복만 막고 남을 안 기다린다
9.  DB 에서 MAX(issue_seq) 를 읽는다
10. bound = max(그 값, 내가 아는 최댓값)
11. counter 를 bound 까지 올린다. 올리기만 하는 스크립트다
12. 내 큐의 티켓을 seq 와 pending 에 쓴다
13. 끝낸다. 아무에게도 보고하지 않고 아무도 기다리지 않는다
```

**9 ~ 12 를 다른 인스턴스가 동시에 돌아도 된다.** 11 은 단조라 순서가 무관하고, 12 는 서로 겹치지
않는 집합에 쓴다.

### 6.3 승격으로 카운터가 뒤로 갔을 때

```
14. 아무 일도 따로 하지 않는다. 2 가 다음 요청에서 고친다
```

## 8. 나빠지는 것

**정직하게 적는다. 공짜가 아니다.**

### 8.1 결번이 늘 수 있는 창

**키 부재 경로에서 늦게 복구하는 인스턴스의 회원은 그 사이 재시도에서 결번을 낼 수 있다.**
지금은 주도자가 3초를 기다려 그것을 막는다.

크기를 가른다. 그 창은 그 인스턴스가 12 를 끝내기까지이고, 실측 기여 시간이 20 ~ 58밀리초였다
(T-1). **대가로 3초 전체 정지가 사라진다.** 어느 쪽이 결번을 더 내는지는 **회차로 재야 한다.**

### 8.2 `free` 가 즉시 안 돌아오는 것

`pending` 까지 잃으면 아무도 안 쥔 번호가 배치까지 결번으로 남는다. 지금은 재건이 그 자리에서
되돌린다.

**다만 지금도 그 되돌림이 완전하지 않다.** 전역 시야를 못 갖춘 재건이 남이 쥔 번호를 `free` 에
넣으면 같은 번호가 두 번 나가므로, 지금 설계는 **틀릴 수도 있는 값을 즉시 쓰는 쪽**이고 새
설계는 **맞는 값을 늦게 쓰는 쪽**이다.

### 8.3 승격을 못 보게 되는 것

`CouponSeqReconnectWatcher` 를 지우면 승격을 신호로 뭔가 하는 주체가 없어진다. **5.1 이 신호
없이 고치므로 설계상 문제가 아니지만, 승격이 일어났다는 사실을 아무도 기록하지 않게 된다.**
`COUPON_SEQ_COUNTER_BEHIND` 지표를 남겨 그 횟수를 세게 둔다.

### 8.4 요청 한 건이 버려지는 것

승격 직후 카운터가 뒤로 간 동안 들어온 요청 중, **5.1 의 점프가 재고 상한을 넘기면** 그 요청은
소진으로 답한다. 지금은 재건이 멈춰 세워 혼잡으로 답한다. **사용자에게는 소진이 혼잡보다 나쁜
답이다.** 상한을 넘는 점프에서만 생기므로 재고 끝자락에 한정되지만, 재야 한다.

## 9. 받아들이기 전에 재야 할 것

**설계가 맞는지는 회차가 정한다.** 아래를 다 재기 전에는 넣지 않는다.

| 재는 것 | 지금 값 | 기준 |
|---|---|---|
| 결번 | 0 | **0 이어야 한다.** 이것이 깨지면 설계를 버린다 |
| 초과 발급 | 0 | 0 이어야 한다 |
| 재건 정지 | 0.244 ~ 0.856초 | 승격 경로에서 **0** 이어야 한다 |
| 발급 본체 p99 | 0.347 ~ 1.330초 | 나빠지지 않아야 한다 |
| 재고 소진 | 10,000 / 7,395 | 무장애에서 재고를 다 내야 한다 |
| `COUNTER_BEHIND` 표본 | 무장애 0, 장애 1.10 ~ 4.51 | 장애에서 **점프 횟수로** 찍혀야 한다 |
| 소진 오답 | 안 쟀다 | 8.4 의 크기를 재야 한다 |

**회차는 장애 3종과 `seq-loss` 와 `cache-wipe` 를 돌린다.** 키 부재 경로가 이 설계에서 유일하게
남는 복구 경로이므로 그 둘이 핵심이다.

## 10. 요약

**재건을 품질 장치로 다시 놓고, 합의를 단조 병합으로 바꾼다.**

```
지금   주도자가 참가자 전원을 세고 기다려 정확한 값을 한 번에 쓴다
       -> 세기가 틀리면 결번이 나거나 발급이 멈춘다
       -> 명부를 장애 난 저장소에 두어 그 세기가 장애와 함께 틀어진다

새로   각자 자기가 아는 값으로 올리기만 한다. 아무도 안 세고 아무도 안 기다린다
       -> 틀릴 수가 없다. 올리기만 하면 결과가 최댓값으로 수렴한다
       -> 완전한 시야가 필요한 계산(free)은 온라인 밖으로 낸다
```

**안전은 DB 의 유니크 키가 지킨다.** 재건이 그 역할을 겸하려 한 것이 설계가 무거워진 까닭이다.
