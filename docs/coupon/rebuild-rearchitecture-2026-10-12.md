# 재건을 바닥부터 다시 세우는 설계

`rebuild-redesign-2026-10-12.md` 가 고침 셋을 넣었고 셋 다 회차로 확인됐다. 그런데 T-1 에서
또 같은 모양의 결함이 나왔다. **고침을 더 얹는 대신 재건이 무엇을 책임지는지부터 다시 정한다.**

이 문서는 설계만 담는다. 코드를 아직 안 고쳤다.

---

## 1. 열 번 고쳐도 같은 자리가 새는 까닭

이 세션에서 잡은 결함을 늘어놓으면 전부 한 문장으로 모인다.

| 회차 | 증상 | 뿌리 |
|---|---|---|
| N-2 | 3대가 도는데 명부가 2 | 주도자가 남을 못 셌다 |
| Q-1 | 재건이 4회, 한 대가 3회 | 주도자가 자기를 다시 불렀다 |
| S-3 | 명부가 0, 8밀리초에 끝남 | 주도자가 남을 못 셌다 |
| J-4 | 결번 180 | 주도자가 남을 못 셌다 |
| T-1 | 발급 안 하는 대가 주도, `instances=0` | 셀 자격 없는 대가 주도자가 됐다 |

**다섯 개가 다 "주도자가 참가자를 세는 데 실패한 것" 이다.**

고침은 매번 세는 방법을 손봤다. 플러시가 알리게 했고, 순번 확보가 알리게 했고, 큐를 쥔 동안
알리게 했다. **세는 방법을 고칠 때마다 안 세어지는 새 경우가 나왔다.**

그럴 수밖에 없다. **지금 재건은 분산 합의다.** 주도자가 "참가자 전원" 을 알아야 하고, 그
명부를 **장애가 난 그 저장소에** 두고 있다. 합의를 최선노력 가십으로 구현한 것이라, 구멍은
고칠 때마다 자리를 옮긴다.

**그래서 세는 방법을 또 고치지 않는다. 셀 필요를 없앤다.**

## 2. 재건이 실제로 책임지는 것

재건이 지킨다고 여겨 온 것을 갈라 보면 둘이 섞여 있다.

```
안전   같은 순번이 두 사람에게 안 나간다,  한 사람이 두 장 안 받는다,  재고를 안 넘는다
활용   재고를 남기지 않고 다 내보낸다,      번호만 태우고 사라진 것을 되살린다
```

**안전은 재건이 지키는 것이 아니다. DB 가 지킨다.**

```sql
UNIQUE KEY uk_mc_coupon_member (coupon_id, member_id)   -- 1인 1매
UNIQUE KEY uk_mc_coupon_seq    (coupon_id, issue_seq)   -- 같은 순번 두 번 금지
CONSTRAINT chk_mc_issue_seq    CHECK (issue_seq <= issue_limit)  -- 재고 상한
```

**카운터가 뒤로 밀려 같은 번호가 두 번 나가도 초과 발급은 안 난다.** 둘 중 하나가
`uk_mc_coupon_seq` 에 걸려 그 요청이 실패하고, 그 번호가 결번으로 남는다. 이것은 기존 주석에도
이미 적혀 있다 (`application-coupon.yml` 의 `rebuild-contribute-wait`).

**그러면 재건의 기다림은 안전이 아니라 활용을 위한 것이다.** 결번과 실패 요청을 줄이려고 3초를
쓰는 것이고, 그 3초 동안 발급은 멈춘다.

**설계가 잘못 놓인 자리가 여기다.** 재건을 안전 장치로 여겨 차단형 합의로 지었는데, 실제로는
품질 장치다. **품질 장치에 합의를 쓰면 합의가 깨질 때 품질이 아니라 가용성이 깨진다.**

## 3. 지금 설계가 합의를 요구하는 지점

네 키 중 둘이 **완전한 전역 시야**를 요구한다.

| 키 | 세우는 식 | 전역 시야가 필요한가 |
|---|---|---|
| `counter` | `max(DB 의 MAX(issue_seq), 모든 큐의 최대 순번)` | 필요하다 |
| `free` | `1..counter` 에서 DB 와 모든 큐를 뺀 나머지 | 필요하다 |
| `seq` | DB 행 + 모든 큐의 티켓 | 빠진 만큼만 빈다 |
| `pending` | 모든 큐의 티켓 | 빠진 만큼만 빈다 |

**`counter` 와 `free` 의 "모든" 이 합의를 끌어들인다.** 하나라도 빠지면 `counter` 가 뒤로 가고
`free` 가 남이 쥔 번호를 아무도 안 쥔 것으로 본다. 그래서 주도자가 참가자를 세고, 세려고 명부를
두고, 명부를 Redis 에 두어 장애와 함께 잃는다.

---

## 4. 바꾸는 축

**합의를 버리고 단조 병합으로 간다.**

`counter` 를 "모두가 합의해 정하는 값" 이 아니라 **올리기만 하는 값**으로 본다. 올리기만 하는
최댓값 레지스터는 교환법칙과 결합법칙과 멱등을 모두 만족한다. 그러면 N 대가 각자 아는 값으로
제멋대로 올려도 결과가 전체 최댓값 하나로 수렴한다. **누가 몇 대인지 아무도 몰라도 된다.**

**이 성질은 이미 코드에 있다.** `coupon-open-gate.lua` 가 현재 값보다 작은 값을 안 쓴다. 그
스크립트의 주석이 "재건은 언제나 올리는 방향이다" 라고 적어 두었다. **그 성질을 방어가 아니라
설계의 중심으로 옮긴다.**

여기에 하나를 더한다.

**각 인스턴스는 전체 최댓값은 몰라도 자기가 받은 최댓값은 안다.** 순번 확보가 번호를 돌려줄 때
그 값을 보기 때문이다. 그 값은 전체 최댓값의 하한이고, **자기가 쥔 번호를 지키기에는 그것으로
충분하다.** 남이 쥔 번호는 그 남이 자기 값으로 지킨다.

```
전체 최댓값 = max(각 인스턴스의 자기 최댓값, DB 의 MAX(issue_seq))
```

**오른쪽 항들은 전부 지역 정보다.** 각자 자기 항만 올리면 왼쪽이 저절로 선다. 기다릴 대상이
없다.

## 5. 새 설계

### 5.1 순번 확보가 스스로 고치는 구조

**승격으로 카운터가 뒤로 간 것은 재건이 아니라 순번 확보가 고친다.**

인스턴스는 이 쿠폰에서 자기가 받은 최대 순번을 들고 있다. 그 값을 스크립트에 함께 넘긴다.

```lua
-- ARGV[5]=이 인스턴스가 이 쿠폰에서 받은 최대 순번. 없으면 0
local mark = tonumber(ARGV[5])
local n = redis.call('INCR', KEYS[3])

-- 카운터가 내가 이미 받은 번호보다 낮으면 승격이 뒤로 민 것이다. 그 번호들은 누군가 쥐고 있다
if n <= mark then
  n = mark + 1
  redis.call('SET', KEYS[3], n)
end

if n <= tonumber(ARGV[2]) then
  return give(tostring(n))
end
```

**왕복이 늘지 않는다.** 같은 스크립트 안의 비교 하나와, 드물게 `SET` 하나다.

**이 네 줄이 승격 경로의 재건을 대체한다.** 재연결 감시도, 주도자도, 락도, 명부도, 기여도,
3초 기다림도 필요 없다. 뒤로 간 카운터는 **그것을 아는 인스턴스의 다음 요청 한 건이** 고친다.

**정지가 0 이다.** 지금 측정값은 경로별로 0.244 ~ 0.856초이고 그동안 그 이벤트의 모든 발급이
멈춘다. 새 구조에서는 멈추는 구간이 없다.

**지금도 이 값을 이미 재고 있다.** `CouponSeqRebuildTrigger.measureBehind` 가 `highWater` 로
같은 비교를 하고 **재기만 한다.** `rebuild-redesign-2026-10-12.md` 6장이 "BEHIND 승격" 을
미결로 남긴 그 항목이고, 이 설계가 그것을 승격시키는 방법이다. 승격 조건인 "무장애 회차에서
표본 0건" 은 L-1/L-2/N-1/N-3/N-4/O-1/T-1 에서 충족됐다.

### 5.2 키 부재만 남는 재건

키가 통째로 사라진 경우에는 `INCR` 이 1 을 다시 주므로 5.1 로 안 된다. 스크립트가 `-2` 를
내고 누군가 카운터를 다시 세워야 한다.

**그 재건은 기다리지 않는다.**

```
bound = max(DB 의 MAX(issue_seq), 내가 받은 최대 순번)
coupon-open-gate.lua 로 counter 를 bound 까지 올린다
```

**DB 조회 하나와 Redis 왕복 하나다.** 멱등이고 단조라 **여러 대가 각자 돌아도 결함이 아니다.**
오히려 여러 대가 도는 것이 수렴을 돕는다. 다섯 대가 다섯 번 돌면 다섯 항의 최댓값이 선다.

**락이 없다.** 락은 동시 실행을 막으려고 있었고, 동시 실행이 위험한 까닭은 낮은 값이 높은 값을
덮을 수 있어서였다. 올리기만 하면 덮을 수 없다.

**`-4` 도 없다.** 재건이 발급을 멈추지 않으므로 "재건 중" 이라는 상태 자체가 없다. Q-1 의
자기호출 고리는 상태가 없어져 사라진다.

### 5.3 각자 자기 몫만 복구하는 기여

키 부재는 `seq` 와 `pending` 도 함께 잃는다. 그러면 이미 번호를 받고 기다리는 회원이 재시도해
새 번호를 받을 수 있고, 둘 중 하나가 `uk_mc_coupon_member` 에 걸려 번호 하나가 결번이 된다.

**커밋된 회원은 DB 에서 세운다. 이것만은 뺄 수 없다.** 발급 경로에 DB 중복 검사가 없어서
"이미 발급됐다" 를 `seq` 해시에서만 알기 때문이다. 비어 있으면 **이미 받은 만 명의 재시도가
각자 번호를 하나씩 더 태운다.**

**그 읽기는 합의와 무관하다.** 무거워진 원인은 남을 세고 기다린 쪽이었고, DB 를 읽는 것은 이
인스턴스 혼자 할 수 있는 일이다. **읽기는 남기고 기다림만 걷는다.**

**이것은 지역 정보로 막힌다.** 그 티켓을 쥔 인스턴스가 자기 큐의 회원들을 `seq` 와 `pending` 에
다시 써 넣으면 된다. **자기 큐는 자기만 알고, 자기만 쓰면 되고, 남을 기다릴 일이 없다.**

```
각 인스턴스는 -2 를 보면 자기 큐의 티켓을 seq 와 pending 에 다시 쓴다
쓰고 나서 아무에게도 보고하지 않는다
```

**지금 `CouponSeqContributor` 가 하는 일과 쓰는 내용이 같다.** 다른 것은 **완료를 보고하지
않는다**는 것 하나다. 보고가 없으면 주도자도 필요 없고, 주도자가 없으면 셀 것도 없다.

**지역 복구의 합집합이 전역 복구와 같다.** 각 티켓은 정확히 한 인스턴스에 있으므로, 전원이 자기
몫을 쓰면 빠지는 티켓이 없다. **그런데 그것을 확인하려고 기다릴 필요가 없다.** 늦게 쓰는 대가
있어도 그 대의 티켓이 늦게 복구될 뿐이고, 그동안 그 회원이 재시도하면 결번 하나가 난다.

```
지금    전원을 기다린다        늦은 대 하나가 전체 발급을 3초 멈춘다
새로    각자 쓴다              늦은 대의 회원만 그 사이 재시도에서 결번을 낸다
```

**장애를 전체에서 지역으로 가둔다.** 느린 인스턴스 하나의 비용을 그 인스턴스가 낸다.

### 5.4 온라인에서 세우지 않는 `free`

`free` 만은 지역 정보로 안 된다. `1..counter` 에서 DB 와 모든 큐를 빼야 하므로 전역 시야가
필요하고, **이것이 합의를 요구하는 유일한 항목으로 남는다.**

**그래서 온라인에서 안 세운다. 재건은 `free` 를 비운 채 둔다.**

번호만 태우고 사라진 요청은 두 경로가 되살린다.

| 경로 | 무엇을 되살리나 | 전역 시야 |
|---|---|---|
| `pending` 회수 (`reclaim-after` 60초) | 사용자가 떠난 번호 | 필요 없다. 회원 단위다 |
| 정합성 배치 (`CouponConsistencyScheduler`) | `pending` 째 잃은 번호 | 필요하다. 온라인이 아니다 |

**회수가 흔한 경우를 이미 덮는다.** `free` 재건이 필요한 것은 `pending` 까지 잃은 경우뿐이고,
그때도 5.3 이 각 인스턴스의 티켓을 `pending` 에 다시 넣으므로 남는 것은 **아무도 안 쥔 번호**
뿐이다. 그것은 급하지 않다. 발급이 끝난 뒤에 세어도 늦지 않다.

**배치를 온라인 경로에서 뺀 것이 요점이다.** 완전한 시야가 필요한 계산을 요청 경로에서 치우면,
요청 경로에 합의가 안 남는다.

## 6. 구현된 로직 순서

설계 단계의 축약본이 아니라 코드에 들어간 순서다. 각 단락의 번호를 뒤에서 그대로 인용한다.

### 6.1 평상시 발급, 요청 하나

```
1.  요청이 순번 확보 Lua 를 부른다. 자기가 본 최대 순번을 함께 넘긴다
2.  카운터가 없으면 -2 를 돌려준다                              -> 19 로
3.  이 회원이 이미 받았으면 그 번호를 그대로 돌려준다
4.  free 에 반납된 번호가 있으면 그것을 준다
5.  없으면 counter 를 INCR 한다
6.  받은 값이 내가 본 최댓값 이하면 그 최댓값 다음으로 올린다      <- 승격 복구가 여기다
7.  재고 상한을 넘으면 되돌리고 회수나 소진으로 간다
8.  번호를 주고 seq 와 pending 에 쓴다
9.  앱이 받은 번호를 기억에 넣는다. 번호가 1 이면 기억을 1 로 되돌린다
10. 티켓을 큐에 넣고 요청 스레드가 잠든다
```

**6 이 이 설계의 절반이다.** 승격으로 뒤로 간 카운터를 **요청 한 건이 그 자리에서** 고친다.
왕복이 안 늘고, 주도자도 락도 명부도 기다림도 끼지 않는다.

**9 의 번호 1 규칙이 그 대가를 막는다.** 기억은 JVM 안의 값이라 이벤트 경계를 모른다. 준비
단계가 카운터를 0 으로 세우므로 1 은 갓 열린 이벤트의 첫 번호이고, 그 뒤로는 이벤트가 도는
동안 다시 안 나온다. 안 되돌리면 같은 쿠폰을 다시 열 때 6 이 지난 최댓값까지 건너뛰어
**재고를 통째로 버린다.**

### 6.2 플러시, 배치 하나

```
11. 창 20밀리초나 500건을 모아 배치를 집는다
12. 벌크 INSERT 로 DB 에 쓴다
13. Redis 에 확정 표시를 붙이고 pending 에서 뺀다
14. 요청 스레드들을 깨운다
15. 카운터를 읽는다
16.   없으면 전손이다. 복구를 띄운다                            -> 19 로
17.   방금 쓴 최댓값을 기억에 넣는다
18.   카운터가 기억보다 낮으면 지표에 적고 기억까지 올린다
```

**16 과 18 이 요청을 안 받는 인스턴스를 맡는다.** ALB 가 발급 경로를 전용 ASG 로만 보내므로
어떤 대는 `-2` 를 볼 기회가 없는데, **티켓을 쥔 대는 그것을 쓰느라 반드시 이 자리를 지난다.**

**둘이 없으면 두 가지로 깨진다.**

```
16 없이   요청을 안 받는 대가 전손을 영영 모르고 자기 큐를 seq 에 못 되살린다
          그 회원들의 재시도가 번호를 하나씩 더 태우고 uk_mc_coupon_member 에 걸린다
18 없이   그 대가 쥔 번호를 남들이 다시 내주고 한쪽이 uk_mc_coupon_seq 에 걸린다
```

**18 은 재기만 하지 않고 올린다.** 올리기만 하는 쓰기라 남이 더 높게 세워 두었으면 아무 일도
안 하고, 뒤처지지 않은 평상시에는 쓰기가 아예 없다.

### 6.3 전손 복구, 카운터가 사라졌을 때만

```
19. 쿠폰별로 한 번만 띄운다. 돌고 있으면 그냥 돌아간다
20. DB 에서 쿠폰을 읽는다. 안 열렸거나 선착순이 아니면 그만둔다
21. 카운터가 "0" 이면 관리자가 방금 다시 준비한 것이다. 그만둔다
22. DB 의 발급 행을 전부 읽어 seq 에 쓴다. 값에 확정 표시를 붙인다
23. 내 큐의 티켓을 seq 와 pending 에 되살린다. 둘 다 "없을 때만" 쓴다
24. bound = max(DB 최댓값, 내 기억)
25. counter 를 bound 까지 올린다. 올리기만 하는 스크립트다
26. 네 키에 카운터의 수명을 물려준다
27. 끝낸다. 아무에게도 보고하지 않고 아무도 안 기다린다
```

**19 ~ 27 을 여러 인스턴스가 동시에 돌아도 된다.** 25 는 단조라 순서가 무관하고, 23 은 서로
겹치지 않는 집합에 쓰며, 22 는 같은 값을 쓴다. **멱등이라 한 장애에 다섯 번 돌아도 결과가 같다.**

**22 를 카운터보다 먼저 한다.** 25 가 곧 문을 여는 동작이라, 순서가 뒤바뀌면 이미 번호를 쥔
회원이 `seq` 에 없는 틈에 재시도해 번호를 하나 더 태운다.

**23 이 "없을 때만" 쓰는 것이 플러시 멈춤을 없앤 근거다.** 훑는 사이에 그 티켓이 커밋되면 확정
쪽이 `"N:1"` 을 쓰는데, 내 쓰기가 먼저면 그쪽이 덮고 내 쓰기가 나중이면 `NX` 가 아무 일도
안 한다. 어느 순서로도 확정 표시가 미확정으로 덮이지 않는다.

**24 가 `-2` 에서도 기억을 들고 있어야 한다.** 버리면 아직 큐에 떠 있는 번호가 빠진 채로
카운터가 선다. 큐가 5,000 ~ 5,050 을 쥐고 DB 최댓값이 4,900 이면 **51개가 겹쳐 결번이 된다.**

## 8. 나빠지는 것

**정직하게 적는다. 공짜가 아니다.**

### 8.1 결번이 늘 수 있는 창

**키 부재 경로에서 늦게 복구하는 인스턴스의 회원은 그 사이 재시도에서 결번을 낼 수 있다.**
지금은 주도자가 3초를 기다려 그것을 막는다.

크기를 가른다. 그 창은 그 인스턴스가 12 를 끝내기까지이고, 실측 기여 시간이 20 ~ 58밀리초였다
(T-1). **대가로 3초 전체 정지가 사라진다.** 어느 쪽이 결번을 더 내는지는 **회차로 재야 한다.**

### 8.2 `free` 를 안 세워 재고가 덜 나가는 것

`pending` 까지 잃으면 아무도 안 쥔 번호가 배치까지 결번으로 남는다. 지금은 재건이 그 자리에서
되돌린다.

**다만 지금도 그 되돌림이 완전하지 않다.** 전역 시야를 못 갖춘 재건이 남이 쥔 번호를 `free` 에
넣으면 같은 번호가 두 번 나가므로, 지금 설계는 **틀릴 수도 있는 값을 즉시 쓰는 쪽**이고 새
설계는 **맞는 값을 늦게 쓰는 쪽**이다.

### 8.3 승격을 못 보게 되는 것

`CouponSeqReconnectWatcher` 를 지우면 승격을 신호로 뭔가 하는 주체가 없어진다. **5.1 이 신호
없이 고치므로 설계상 문제가 아니지만, 승격이 일어났다는 사실을 아무도 기록하지 않게 된다.**
`COUPON_SEQ_COUNTER_BEHIND` 지표를 남겨 그 횟수를 세게 둔다.

### 8.4 요청 한 건이 버려지는 것

승격 직후 카운터가 뒤로 간 동안 들어온 요청 중, **5.1 의 점프가 재고 상한을 넘기면** 그 요청은
소진으로 답한다. 지금은 재건이 멈춰 세워 혼잡으로 답한다. **사용자에게는 소진이 혼잡보다 나쁜
답이다.** 상한을 넘는 점프에서만 생기므로 재고 끝자락에 한정되지만, 재야 한다.

---

### 8.5 승격이 되돌린 `free` 에 손을 못 대는 것

승격 경로에서는 이제 복구가 아예 안 돈다. 그러면 `ZPOPMIN` 이 되돌려진 `free` 항목이 남아
같은 번호가 두 번 나갈 수 있다. 예전에는 복구가 `free` 를 비우고 다시 세워 그것을 걷었다.

**크기는 작다.** `free` 는 소진 근처에서 회수가 채우기 전까지 비어 있으므로, 노출되는 구간이
재고 끝자락이다. 그리고 두 번 나간 번호는 `uk_mc_coupon_seq` 가 한쪽을 떨어뜨려 결번 하나가
된다. **구현하면서 드러난 항목이고 회차로 재야 한다.**

### 8.6 기억이 이벤트를 넘어 남는 것

순번 확보가 보는 기억은 JVM 안의 값이라 이벤트 경계를 모른다. 같은 쿠폰을 다시 열면 지난
이벤트의 최댓값이 남아, 순번 확보가 그 값까지 건너뛰어 **그만큼의 재고를 통째로 버린다.**
만 장짜리에서 기억이 5,887 이면 4,113장만 나간다.

**번호 1 로 가른다.** 준비 단계가 카운터를 0 으로 세우므로 1 은 갓 열린 이벤트의 첫 번호이고
이벤트가 도는 동안 다시 나오지 않는다. 스크립트는 `n == 1` 에서 건너뛰기를 안 하고, 자바는
1 을 보면 기억을 1 로 되돌린다. 시험 `번호_1_을_보면_지난_이벤트의_기억을_버린다` 가 그것을
고정한다.

## 9. 받아들이기 전에 재야 할 것

**설계가 맞는지는 회차가 정한다.** 아래를 다 재기 전에는 넣지 않는다.

| 재는 것 | 지금 값 | 기준 |
|---|---|---|
| 결번 | 0 | **0 이어야 한다.** 이것이 깨지면 설계를 버린다 |
| 초과 발급 | 0 | 0 이어야 한다 |
| 재건 정지 | 0.244 ~ 0.856초 | 승격 경로에서 **0** 이어야 한다 |
| 발급 본체 p99 | 0.347 ~ 1.330초 | 나빠지지 않아야 한다 |
| 재고 소진 | 10,000 / 7,395 | 무장애에서 재고를 다 내야 한다 |
| `COUNTER_BEHIND` 표본 | 무장애 0, 장애 1.10 ~ 4.51 | 장애에서 **점프 횟수로** 찍혀야 한다 |
| 소진 오답 | 안 쟀다 | 8.4 의 크기를 재야 한다 |

**회차는 장애 3종과 `seq-loss` 와 `cache-wipe` 를 돌린다.** 키 부재 경로가 이 설계에서 유일하게
남는 복구 경로이므로 그 둘이 핵심이다.

## 10. 요약

**재건을 품질 장치로 다시 놓고, 합의를 단조 병합으로 바꾼다.**

```
지금   주도자가 참가자 전원을 세고 기다려 정확한 값을 한 번에 쓴다
       -> 세기가 틀리면 결번이 나거나 발급이 멈춘다
       -> 명부를 장애 난 저장소에 두어 그 세기가 장애와 함께 틀어진다

새로   각자 자기가 아는 값으로 올리기만 한다. 아무도 안 세고 아무도 안 기다린다
       -> 틀릴 수가 없다. 올리기만 하면 결과가 최댓값으로 수렴한다
       -> 완전한 시야가 필요한 계산(free)은 온라인 밖으로 낸다
```

**안전은 DB 의 유니크 키가 지킨다.** 재건이 그 역할을 겸하려 한 것이 설계가 무거워진 까닭이다.

**발급 행을 읽는 것은 그대로 남았다.** 처음에는 `MAX(issue_seq)` 한 줄로 줄였는데, 그러면

대부분이었다. 남은 비용은 만 행 읽기와 만 필드 쓰기다.

### 11.1 옮기면서 내가 과하게 걷은 둘

**둘 다 "요청을 안 받는 인스턴스" 를 잊어서 생겼다.** 합의를 걷는 데 집중하다가, 플러시 쪽
확인이 합의가 아니라 **신호 수집**이었던 것을 못 보고 같이 지웠다.

| 걷은 것 | 어떻게 깨지나 | 되살린 자리 |
|---|---|---|
| 플러시의 전손 확인 | 요청을 안 받는 대가 자기 큐를 `seq` 에 못 되살린다 | 6.2 의 16 |
| 뒤처짐에서 올리기 | 그 대가 쥔 번호를 남들이 다시 내준다 | 6.2 의 18 |

**그리고 `-2` 에서 기억을 버리던 것을 지웠다.** 재개장을 막으려고 넣었는데, 그 역할은 이미
6.1 의 9 와 6.3 의 21 이 한다. 버리면 24 가 `max(DB, 0)` 이 되어 큐에 떠 있는 번호가 빠진 채로
카운터가 선다.

시험 셋으로 고정했다.

```
카운터가_없으면_복구를_띄운다
뒤처지면_카운터를_올린다
뒤처지지_않으면_안_올린다
```

## 12. 회차 결과

**AWS 실측이다.** 전용 3대(t3.small), 재고 10,000, VU 20,000, 램프 60초. 커밋 `caa13bf2`.

| 회차 | 장애 | 발급행 | 최대 순번 | 결번 | p99 | 복구 |
|---|---|---:|---:|---:|---:|---:|
| U-1 | 카운터 삭제 | 10,000 | 10,000 | **0** | 0.353초 | **3회** |
| U-2 | 네 키 전손 | 10,000 | 10,000 | **0** | 0.067초 | **3회** |
| U-3 | 캐시 페일오버 | 9,911 | 9,953 | **42** | 0.868초 | 0회 |
| U-4 | 서버 1대 종료 | 10,000 | 10,000 | **0** | 0.125초 | 0회 |
| U-5 | 서버 1대 + 캐시 | 9,553 | 9,573 | **20** | 0.741초 | 0회 |

**다섯 회차 모두 초과 발급 0, 1인 2매 0, 예상 못 한 응답 0, p99 가 SLO 1초 안이다.**

### 12.1 단조 병합이 확인됨

**U-1 에서 세 대가 16밀리초 안에 각자 복구를 돌았고 카운터가 최댓값으로 수렴했다.**

```
i-032497d   dbMax=7945  mark=7944  bound=7945  ->  counter=7945
i-06135fb   dbMax=7945  mark=7947  bound=7947  ->  counter=7948
i-0f5f3f1   dbMax=7945  mark=7945  bound=7945  ->  counter=7949
```

**`counter=` 는 쓴 뒤의 값이다.** 셋째 대는 7,945 를 쓰려 했는데 7,949 를 돌려받았다. 남이 이미
더 높게 세워 둔 것이고, **낮은 값이 높은 값을 덮지 못하는 성질이 실측으로 작동했다.**

**옛 설계에서는 이것이 결함이었다.** 한 장애에 재건이 여러 번 도는 것이 N-2 와 Q-1 의 증상이었고,
그중 하나가 낮게 쓰면 결번이 났다. **지금은 세 번 도는 것이 정상이고 수렴을 돕는다.**

**`mark` 가 `dbMax` 보다 높은 대가 실제로 있었다.** U-1 에서 7,947 대 7,945 이고 U-2 에서는
세 대가 다 그랬다 (8,102 / 8,108 / 8,126 대 8,100). 큐에 떠 있던 번호를 그 기억이 지킨 것이고,
**옛 설계가 3초를 기다려 남의 큐를 모아야 알던 값이다.**

### 12.2 승격에 복구가 돌지 않음

**U-3 과 U-5 에서 `REBUILT` 가 세 대 모두 한 줄도 안 찍혔다.** 재연결 감시를 지웠고 6.1 의 6 이
그 일을 맡는다는 주장이 그대로 확인됐다.

**`COUNTER_BEHIND` 도 0 이다.** 카운터가 뒤로 밀리지 않아 기억 점프를 쓸 일조차 없었다.

| | 옛 설계 | 새 설계 |
|---|---|---|
| 승격에 발급이 멈추는 시간 | 0.244 ~ 0.856초 | **없다** |
| 캐시 페일오버 p99 | 1.330초 (S-2, SLO 초과) | **0.868초** |
| 복합 장애 발급량 | 7,395 (T-1) | **9,553** |

### 12.3 `free` 를 버린 대가는 미확정

**처음에 이 절을 "대가가 측정됨" 으로 적었다. 그 판단이 성급했다.**

U-3 의 결번 42 를 보고 `free` 재구성을 뺀 크기로 단정했는데, **같은 코드로 두 번 더 돌리니
3 과 1 이 나왔다** (2026-10-13 V-1, V-2).

| 회차 | 결번 | 쓸기 |
|---|---:|---|
| U-3 | 42 | 없던 판 |
| V-1 | 3 | 있지만 36회 전부 실패 |
| V-2 | 1 | 전부 실패 |

**셋 다 되살린 번호가 0 이라 쓸기가 없는 것과 같은 조건이다.** 그러니 42 와 1 의 차이는
전부 승격의 복제 지연 창 차이다. **한 점을 원인의 크기로 삼은 것이 잘못이다.**

**빠진 번호가 한 구간에 모이는 것은 세 회차가 같다.**

```
U-3   6437 ~ 6949 사이에만 42개
V-1   5743, 5744, 5747          셋이 붙어 있다
```

**승격의 복제 지연 창이라는 해석은 그대로 선다.** 틀린 것은 그 창의 크기를 42 로 못박은 쪽이다.

**옛 설계와는 방향이 다르다.** `free` 를 세우던 판의 캐시 페일오버 회차는 둘 다 결번 0 이었다
(S-2, N-2). 새 설계는 42 / 3 / 1 이다. **방향은 맞고 크기를 모른다.**

```
옛 설계   0, 0
새 설계   42, 3, 1
```

**원인이 아직 둘로 갈려 있다.**

| | 쓸기가 집나 |
|---|---|
| `seq` 항목까지 되돌려져 아무도 안 쥔 번호가 됐다 | 집는다 |
| `seq` 에는 남고 티켓만 사라져 주인이 죽은 번호다 | **건너뛴다. 쓸기의 대상 정의가 틀린 것이다** |

**둘을 가르려면 쓸기가 실제로 돌아야 한다.** `COUPON_SEQ_FREE_ALL_HELD` 로그가 "후보가 있었는데
전부 쥐어져 있었다" 를 말하는데, 배치에서 Redis 로 가는 길이 막혀 그 로그가 한 번도 안 찍혔다
(`docs/coupon/free-sweep-2026-10-12.md` 10장).

### 12.4 복구 시간

| 회차 | 복구 한 번 | 비고 |
|---|---:|---|
| U-1 | 834 ~ 860밀리초 | 배포 직후 첫 회차. 커넥션과 질의 계획이 차갑다 |
| U-2 | 119 ~ 186밀리초 | 같은 8,000행대를 읽는다 |

**7배 차이가 난다.** 두 값을 다 남긴다. **어느 쪽이든 그 동안 발급이 멈추지 않는다** 는 것이
옛 설계와 다른 점이고, 옛 0.244 ~ 0.856초는 전부 정지 시간이었다.

### 12.5 큐 대기

U-5 에서 한 대가 최대 1.056초였다. 옛 S 회차의 0.828초보다 크다.

**그런데 commit-wait 800밀리초를 넘긴 요청이 혼잡으로 끊겨도 그 티켓은 큐에 남아 결국 써진다.**
U-5 의 발급행 9,553 이 k6 가 센 9,396 보다 많은 것이 그 증거다. 바뀌는 것은 그 발급을 성공으로
세느냐이고, 총량이 아니다.

## 13. 판정

**9장의 기준 일곱 줄 중 하나가 깨졌다.**

| 재는 것 | 기준 | 결과 |
|---|---|---|
| 결번 | 0 | **U-3 42, U-5 20, V-1 3, V-2 1. 깨졌다. 크기는 변동이 크다** |
| 초과 발급 | 0 | 0 |
| 재건 정지 | 승격에서 0 | **0** |
| 발급 본체 p99 | 나빠지지 않는다 | 0.067 ~ 0.868초. 모두 SLO 안 |
| 재고 소진 | 무장애에서 10,000 | 키 부재에서도 10,000 |
| `COUNTER_BEHIND` | 장애에서 점프 횟수 | 0. 점프가 필요하지 않았다 |
| 소진 오답 | 크기를 잰다 | 안 쟀다 |

**깨진 것은 단조 병합이 아니다.** 그쪽은 U-1 과 U-2 가 결번 0 으로 증명했고, 세 대가 동시에 돌아
수렴하는 것까지 로그로 확인됐다.

**깨진 것은 거기에 얹어 `free` 재구성을 함께 버린 결정이다.** 둘은 서로 독립이다. 합의를 걷는 것과
`free` 를 온라인에서 빼는 것을 한 커밋에 넣은 것이 판정을 섞이게 만들었다.

**그래서 설계를 버리지 않고 `free` 만 되돌리는 것이 맞다.** 되돌리려면 전역 시야가 필요하므로
기여 수집이 돌아와야 하고, 그러면 이번에 걷어낸 것의 일부를 다시 들인다. 다만 **기다림 없이**
들일 수 있다. `free` 는 문을 여는 데 필요하지 않아서, 카운터를 먼저 올려 발급을 재개한 뒤에
천천히 모아 채워도 된다. **그 설계는 아직 안 썼다.**
