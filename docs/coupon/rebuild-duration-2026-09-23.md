# 재건이 문을 닫아 둔 시간을 처음 잰 회차 (2026-09-23)

**팀은 그동안 "재건 정지 3.4초" 라고 써 왔는데 그것은 계산값이었다.** 팀이 설정값 3,000밀리초와 앞선 회차의 읽고 쓰기 427밀리초를 더한 것이지 실측이 아니다. 팀은 이번에 네 구간을 전부 재는 계측을 붙이고 회차를 돌렸다.

```
AWS 실측   20,000 VU / ramp 60초 / 재고 10,000장 / 전용 인스턴스 3대
앱         fm-backend main cbb46dee
주입       레디스 장애와 인스턴스 + 레디스 장애. DB 장애는 넣지 않았다
```

## 1. 결론

| | 회차 1 `seq-loss` | 회차 2 `app+seq-loss` | 회차 3 `app+seq-loss` |
|---|---:|---:|---:|
| 큐 수집 대기 | 55 | 2 | **3,016** |
| 주도자 기여 | 21 | 8 | 14 |
| 읽고 쓰기 | 127 | 123 | 161 |
| **재건 총 소요** | **204** | **135** | **3,193** |

**재건 총 소요가 정상 조건에서 204밀리초다.** 팀이 써 오던 3.4초는 열여섯 배 과대평가였다.

**세 회차 전부 초과 발급 0 이고 1인 1매가 지켜졌다.** 세 회차 모두 `10000 / 10000 / 결번 0 / 회원 10000` 이다.

## 2. 계산값이 왜 그렇게 빗나갔나

팀이 더한 두 항 모두 실제보다 컸다.

```
큐 수집 대기   3,000 (설정값)  ->    55 (실측)
읽고 쓰기        427 (옛 측정)  ->   127 (실측)
```

**앞의 것은 조기 종료가 붙기 전의 값이다.** 이제는 주도자가 명부의 수만큼 표시가 차면 그 자리에서 끝내므로 설정값을 다 안 쓴다.

**뒤의 것은 결번 수에 비례한다.** 427밀리초는 팀이 결번 799개일 때 잰 값이고, 이번 세 회차는 `freed=0` 이라 읽고 쓰기가 훨씬 가벼웠다. **팀이 회차마다 달라지는 값을 상수처럼 써 온 것이 문제였다.**

## 3. 죽은 인스턴스 하나가 정지를 열여섯 배로 늘린다

팀이 회차 2와 3에 **같은 주입을 넣었는데 결과가 갈렸다.** 팀이 둘에서 다르게 한 것은 **한 대를 죽인 뒤 `counter` 를 지울 때까지의 간격** 하나다.

```
        죽이기와 키 삭제 사이   주도자가 센 명부   올라온 표시   큐 수집 대기
회차 2          11초              instances=2      done=2          2ms
회차 3           1초              instances=3      done=2      3,016ms
```

**주도자가 센 명부가 회차 2에서는 2고 회차 3에서는 3이다.** 명부는 `STALE_AFTER` 10초 안에 갱신한 항목만 센다. 죽은 대는 갱신을 멈추지만 점수가 그 자리에 남으므로 **10초 동안은 주도자가 그 대를 살아 있는 것으로 센다.**

| | 죽은 대가 명부에 | 주도자가 기다린 대상 | 큐 수집 대기 |
|---|---|---|---:|
| 회차 2 (11초 차) | 빠졌다 | 살아 있는 두 대, 둘 다 올렸다 | 2ms |
| 회차 3 (1초 차) | 남아 있다 | 세 대, 죽은 한 대는 안 올린다 | 3,016ms |

**회차 3에서 주도자는 이미 죽은 인스턴스의 기여를 기다렸다.** 주도자가 20밀리초 간격으로 보다가 시한 3,000밀리초를 넘겼고, 마지막 한 바퀴가 얹혀 3,016밀리초가 됐다.

```
COUPON_SEQ_CONTRIBUTIONS_TIMEOUT couponId=900001 instances=3 done=2 waitedMillis=3000
```

**팀이 두 회차의 간격을 11초와 1초로 가른 것은 의도가 아니라 주입 방법에서 나왔다.** 팀은 그 절차를 부록에 적었다.

**그래서 `STALE_AFTER` 10초가 재건 정지 시간에 그대로 얹힌다.** 인스턴스가 죽고 10초 안에 레디스 키가 사라지면 이 일이 난다. **ASG 교체나 배포 중에 충분히 겹칠 수 있는 창이다.**

### 값을 줄이면 되나

**팀이 안전과 속도를 맞바꾸는 자리다.** 팀이 `STALE_AFTER` 를 짧게 잡으면 이 구간이 줄지만, 살아 있는데도 명부에서 빠지는 인스턴스가 생긴다. 그러면 주도자가 그 인스턴스의 큐를 안 기다리고 키를 세워 **그 번호들을 남에게 다시 내준다.**

명부의 실수는 **주도자가 덜 기다리는 쪽만 위험하다.** 주도자가 더 기다리는 것은 3초를 넘지 않는다.

## 4. 이 수치를 읽을 때의 한계 셋

**세 회차 모두 큐가 비어 있었다**(`queued=0`, `freed=0`). 이 표의 읽고 쓰기는 가장 가벼운 조건에서 나온 값이다. 팀이 앞선 회차에서 `freed=5753` 을 본 적이 있으니 그때는 읽고 쓰기가 훨씬 컸을 것이다.

**이 수치에 감지 지연이 안 들어 있다.** 이 수치는 카운터가 사라진 때가 아니라 주도자가 일을 시작한 때부터다. **실제 정지는 이 값보다 길다.**

**팀이 k6 요약을 안 거뒀다.** 팀이 `size` 와 시간 측정에 집중하다 빠뜨렸고, 팀이 인프라를 내려 이제 못 가져온다. 팀은 정합성 수치를 DB 에서 받아 적었다.

## 5. 회차 1에서 재건이 두 번 걸렸다

한 대가 `CONTRIBUTIONS_TIMEOUT instances=3 done=1` 로 3초를 다 쓰고 `REBUILD_SKIPPED` 로 끝났다. 다른 대가 먼저 문을 열어서다.

**락이 있는데 두 주도자가 동시에 뛴 셈이다.** 쿠폰이 둘(`900001`, `1000000`)이고 `seq-loss` 가 둘의 카운터를 다 지우므로 그것과 얽혔을 수 있다. **팀은 아직 안 밝혔다.**

## 6. 다음에 할 것

1. **팀이 큐가 찬 상태로 다시 잰다.** `readWriteMillis` 가 결번 수에 어떻게 비례하는지 봐야 팀이 이 값을 쓸 수 있다
2. **팀이 감지 지연을 잰다.** 카운터가 사라진 때부터 주도자가 시작할 때까지다. 팀이 그것까지 더해야 진짜 정지 시간이 된다
3. **팀이 `STALE_AFTER` 를 어떻게 할지 정한다.** 팀이 10초가 정지에 얹히는 것을 봤으니 근거가 생겼다
4. 팀이 회차 1의 이중 재건을 밝힌다
5. **팀이 `loadtest-fault.sh app+seq-loss` 를 죽이기와 키 삭제를 한 호출로 보내게 고친다.** 지금은 그 시나리오가 SSM 을 두 번 왕복해 둘 사이가 11초로 벌어지고, 그래서 **팀이 가장 위험한 회차 3을 스크립트로 못 만든다**(부록)

## 부록. 어떻게 다시 돌리나

### 준비

팀은 전용 ASG 3대를 띄우고 배포를 먼저 끝낸다. **팀이 부하보다 배포를 먼저 해야 한다.** 팀이 ASG 를 먼저 열면 인스턴스가 아직 안 올라간 이미지 태그를 당겨 못 뜬다.

```
cd fm-infra
./scripts/apply.sh                 # 인프라
./scripts/deploy.sh                # 이미지 태그는 40자 전체 SHA 다
./scripts/loadtest-seed.sh         # 배포가 스키마를 만든 뒤에 돌려야 한다
./scripts/coupon-event.sh open     # 이벤트를 연다
```

### 주입 시점

**팀은 주입을 k6 시작 8초 뒤에 넣었다.** 재고 만 장이 램프업 중에 수십 초면 다 나가므로, 팀이 늦게 넣으면 재고가 소진된 뒤가 되고, 그러면 큐가 비어 재건이 `issued=10000 queued=0` 으로 끝난다.

### 회차별 주입

| 회차 | 팀이 무엇을 넣었나 | 죽이기와 키 삭제 사이 |
|---|---|---:|
| 1 | `./scripts/loadtest-fault.sh seq-loss` | 해당 없음 |
| 2 | `./scripts/loadtest-fault.sh app+seq-loss` | 11초 |
| 3 | 팀이 죽이기와 `DEL` 을 SSM 한 호출로 합쳤다 | 1초 |

**팀이 회차 2와 3의 간격 차이를 의도한 것이 아니라 스크립트의 모양이 그것을 만들었다.** `app+seq-loss` 가 `stop_one_app; drop_keys counter` 로 SSM 을 두 번 왕복하는데, 그 왕복이 대당 4~5초씩 걸려 둘 사이가 11초가 된다. **그 11초가 `STALE_AFTER` 10초를 넘겨 죽은 대가 명부에서 빠졌고, 그래서 회차 2의 큐 수집 대기가 2밀리초로 끝났다.**

팀은 그 창 안을 보려고 회차 3에서 두 일을 한 SSM 호출에 담아 손으로 보냈다. **팀은 지금 스크립트로 회차 3을 재현할 수 없다.**

### 무엇을 거두나

팀은 앱 로그에서 이 한 줄을 거둔다. 이 줄이 네 구간을 다 갖고 있다.

```
COUPON_SEQ_REBUILT couponId=... issued=... queued=... maxSeq=... freed=...
  rebuildMillis=... contributeMillis=... waitMillis=... readWriteMillis=...
```

팀은 주도자가 명부에서 몇 대를 세었는지를 그 앞줄에서 본다.

```
COUPON_SEQ_CONTRIBUTIONS_COMPLETE couponId=... instances=... waitedMillis=...
COUPON_SEQ_CONTRIBUTIONS_TIMEOUT  couponId=... instances=... done=... waitedMillis=...
```

팀은 정합성 수치를 DB 에서 직접 받는다. 발급행, 최대순번, 결번, 회원수 넷이다.
