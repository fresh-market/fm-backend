**병합 전 브랜치를 올려 시험했다.** `feat/rebuild-on-reconnect` 의 `ec2d6ae5` 를 ECR 에 직접
올리고 `current-sha` 를 그 값으로 세웠다. `main` 은 건드리지 않았다.

## 1. 기준 회차

**장애를 넣지 않고 한 회차를 먼저 돌렸다.** 뒤의 세 회차를 읽을 바닥이다.

| B-1 | 값 |
|---|---:|
| 발급행 | 10,000 |
| 최대 순번 / 결번 | 10,000 / 0 |
| 회원 수 | 10,000 |
| 판정된 응답 p99 | **85.89ms** |
| 같은 지표 최댓값 | 253.71ms |
| 예상 못 한 응답 | 0 |
| HTTP 실패율 | 0.00% |
| 혼잡(503) 비율 | 0.00% |
| 재시도 | 0 |

**요청 20,000건의 결말이 셋으로 갈린다.**

```
10,000   발급
 9,991   최종 소진.  재시도할 것이 없다
     9   회수 가능한 소진.  묶인 번호가 풀리기를 기다릴 수 있었다
```

**혼잡이 한 건도 없다.** 예산에 걸려 503 을 받은 요청이 0 이므로, 이 회차의 p99 는 예산 설정과
무관한 값이다.

**재건 로그가 없다.** 주입이 없으니 걸릴 이유가 없고, 새로 붙인 재연결 감시기도 조용했다.
기동 로그에는 `COUPON_SEQ_RECONNECT_WATCH_STARTED minIntervalMillis=10000` 이 세 대 모두 떴다.
**감시기가 살아 있는데도 평상시에 재건을 부르지 않는다는 것이 이 회차가 확인한 것이다.**

### p99 를 앞 회차와 견줄 때

**85.89ms 를 서버가 빨라진 증거로 읽으면 안 된다.** 같은 조건으로 견줄 앞 회차가 없다.

| 견줌 | 앞 회차 | 이번 | 읽는 법 |
|---|---:|---:|---|
| 무장애 | 302.95ms (09-22) | **85.89ms** | **생성기 세대가 다르다.** 비교 못 한다 |
| 서버 1대 종료 + 캐시 페일오버 | 0.228초 (09-30) | 0.210초 | **같은 세대다.** 거의 같다 |
| 서버 1대 종료 (최댓값) | 0.442초 (09-30) | 0.331초 | **같은 세대다.** 같은 자리다 |

**생성기 수정은 09-30 에 이미 들어가 있었다.** `fd4322ab` 가 09-28 에 PR #227 로 `main` 에
들어갔고, 09-30 문서 제목이 "부하 생성기가 죽지 않는 조건에서" 다. **그래서 생성기로는 09-30 과의
차이를 설명할 수 없다.**

```
09-21b, 09-22   수정 전.  sleep(1) 로 놀고 있는 반복이 쌓이던 판
09-28           fd4322ab 가 main 에 들어갔다
09-30, 10-01    수정 후
```

**수정 후끼리 견주면 차이가 없다.** F-3 가 0.210 대 0.228 이고, F-1 의 최댓값이 0.331 대 0.442 다.
**서버가 빨라졌다고 말할 근거가 이 회차에는 없다.**

**B-1 에 비교 대상이 없는 이유는 09-30 이 무장애 회차를 안 돌렸기 때문이다.** 수정 후의 무장애
회차는 B-1 이 처음이다. 85.89ms 가 이기는 것처럼 보이는 302.95ms 는 09-22, 즉 수정 전의
무장애 회차다.

### 수정 전 수치에 멈춤이 섞였다고 보는 근거

**분포 모양이 다르다.**

```
09-21b   p90  68.99ms   p95 123.70ms   p99 321.77ms   max 750.30ms
B-1      p90  55.12ms   p95  59.97ms   p99  85.89ms   max 253.71ms
```

**p95 에서 p99 로 뛰는 폭이 앞은 2.6배이고 이번은 1.4배다.** 몸통은 비슷한데 꼬리만 두꺼운
모양이고, 간헐적인 멈춤이 섞일 때 나는 모양이다.

**메모리 곡선이 그 멈춤의 자리를 집어 준다.** 회차가 램프 60초에 홀드 30초라 90초인데, 수정 전에는
막판 10여 초를 83~99% 에서 돌았다.

```
+58초   5,227 MB   67%
+78초   6,473 MB   83%
+103초  7,667 MB   99%   커널이 k6 를 죽였다
```

**다만 이것은 분포 모양과 메모리 곡선으로 세운 추론이고, 같은 서버에 두 생성기를 번갈아 돌려
가른 것이 아니다.** 09-22 회차의 생성기 메모리는 기록에 없다.

### B-1 에 남는 교란 둘

생성기를 제쳐도 09-22 와 사이에 둘이 바뀌었고 이 회차로 못 가른다.

```
1  워밍업     기동 때 3,000건을 보내 writeRows 5,000 을 데운다. 09-22 에는 없었다
2  서버 코드  09-15 이후 쿠폰 경로에 커밋 스무 건 이상
```

### 이 지표가 담는 것과 안 담는 것

**모집단의 절반이 싼 경로다.** `coupon_settled_duration` 은 200 과 409 와 **410(최종 소진)** 을
담는다. B-1 은 발급 10,000 에 최종 소진 9,991 이라 절반이 Lua 에서 `-3` 만 받고 돌아가는
요청이다. **그래서 이 p99 는 사실상 발급 경로의 p98 이다.**

**도착률은 초당 218건이다.** 요구에 적힌 "동시 요청 20,000" 은 VU 수이고 VU 하나가 한 번만
쏘므로, 서버가 동시에 쥐는 요청은 램프 속도인 초당 약 333건이 상한이다.

```
요청 20,000건 / 91.5초 = 초당 218건
iterations 60,000 중 40,000 은 요청을 안 보내는 반복이다
```

**이 모양을 고르면서 잃은 것과 얻은 것이 갈린다.** 사람 2만 명이 각각 한 장을 받는다는 요구를
그대로 옮긴 것이 얻은 것이고, 초당 수천 건이 쏟아지는 상태를 이 시나리오로는 못 본다는 것이
잃은 것이다.

## 2. 장애 3종

**부하를 먼저 띄우고 k6 시작 +15초에 주입한다.** 09-30 회차가 "DB 를 먼저 막는다" 순서로
돌렸다가 ALB 가 막힌 인스턴스를 대상에서 빼서 발급 2,886 에 재건 `queued=0` 을 냈다.
그 순서를 뒤집은 것이 이 회차의 절차다.

| 회차 | 건 장애 | `loadtest-fault.sh` |
|---|---|---|
| F-1 | 스프링 서버 1대 비정상 종료 | `app` (컨테이너 SIGKILL) |
| F-2 | 캐시 Multi-AZ 페일오버 | `cache-failover` (test-failover) |
| F-3 | 스프링 서버 1대 비정상 종료 + 캐시 페일오버 | `app+cache-failover` |

**`app` 이 `docker kill` 인 것이 중요하다.** `docker stop` 은 SIGTERM 을 보내 스프링이 45초 안에
대기열을 비우고 내려가므로, 재고 손실 0 이 나와도 시스템이 견딘 것인지 비우고 내려간 것인지
못 가른다. `queue-capacity` 의 존재 이유가 비정상 종료 때 잃는 건수의 상한이라 그 상한이
시험되어야 한다.

### F-1 스프링 서버 1대 비정상 종료

| | 값 |
|---|---:|
| 주입 | k6+15초. 03:19:33 에 `i-0d265e...` 의 컨테이너를 SIGKILL |
| 발급행 | 10,000 |
| 최대 순번 / 결번 | 10,000 / 0 |
| 회원 수 | 10,000 |
| 판정된 응답 p99 | **89.13ms** |
| 예상 못 한 응답 | 0 |
| 게이트웨이 실패(502/504) | 7,252 |
| 재시도 | 7,184 |
| 포기(5회 소진) | 68 |
| HTTP 실패율 | 26.67% |

**세 대 중 한 대를 죽였는데 재고를 다 팔았다.** 죽은 인스턴스로 가던 요청이 502 와 504 를 받고
재시도로 돌아왔다. 포기 68건은 다섯 번을 다 써 버린 것이고, 그래도 재고가 남지 않았으므로
**그 68명이 못 받은 것은 남은 재고가 아니라 남의 발급이다.**

**`http_req_failed` 임계가 깨지는 것이 맞다.** 시나리오 주석이 이미 그렇게 적고 있다. 이 회차의
판정은 임계 통과가 아니라 발급 수와 결번이다.

### F-2 캐시 Multi-AZ 페일오버

**이 회차에서 전용 인스턴스 세 대의 JVM 이 전부 커널 OOM 킬러에게 죽었다.** 팀이 이 구성에서
쿠폰 인스턴스의 OOM 을 본 것은 이번이 처음이다.

| | 값 |
|---|---:|
| 주입 | k6+15초. 03:25:34 에 `test-failover` |
| 발급행 | **5,741** |
| 최대 순번 / 결번 | 5,741 / **0** |
| 회원 수 | 5,741 |
| 판정된 응답 p99 | 83.78ms |
| 예상 못 한 응답 | **0** |
| 혼잡(503) | 29,060 (45.51%) |
| 게이트웨이 실패 | 26,385 |
| 연결 실패 | 2,662 |
| 재시도 | **47,208** |
| 포기(5회 소진) | 8,237 |
| 전체 응답 시간 p95 | 54.58초 |

**죽은 증거가 커널 로그에 있다.**

```
18:27:01  i-03e773...  Out of memory: Killed process (java)  anon-rss 1,415,292 kB
18:28:22  i-0254a7...  Out of memory: Killed process (java)  anon-rss 1,412,924 kB
호스트 메모리 총 1,906 MB (t3.small).  컨테이너에 메모리 한도가 없다
```

**`restartCount=1` 과 `exitCode=137` 이 세 대에 다 찍혔다.** `docker inspect` 가 보여 주는
`ExitCode` 는 재시작한 새 컨테이너 것이라 0 으로 보인다. 앞 컨테이너의 종료 코드는 도커 데몬
로그에만 남는다. **이 자리에서 판단을 한 번 틀렸다가 데몬 로그로 바로잡았다.**

### OOM 이 어떻게 일어났나

```
캐시가 승격 중이라 명령이 시간 초과   ->   요청이 쥔 상태가 안 풀린다
503 과 502 를 받은 요청이 재시도      ->   재시도 47,208건.  F-1 은 7,184건이었다
재시도가 다시 대기 중인 일을 늘린다   ->   RSS 1.38GB.  호스트가 1.9GB 다
```

**메모리 한도가 없는 것이 결정적이다.** `memLimit=0` 이라 JVM 이 호스트 전체를 기준으로 힙을
잡는다. 그래서 호스트가 먼저 말라 커널이 죽인다. 컨테이너 한도를 두면 그 자리에서
`OutOfMemoryError` 가 나고 힙 덤프와 함께 죽으므로 원인이 남는다.

### 그래도 깨지지 않은 것

**세 번의 OOM 을 통과했는데 결번이 0 이고 예상 못 한 응답이 0 이다.** 초과 발급도 없고
1인 1매도 지켜졌다. **5,741장이 안 팔린 것은 정합성 문제가 아니라 가용성 문제다.**

**판정된 응답의 p99 는 83.78ms 로 SLO 를 지켰다.** 그런데 이 수치를 합격으로 읽으면 안 된다.
전체 응답의 p95 가 54.58초이고, 판정까지 간 요청만 이 지표에 들어가기 때문이다.
**죽은 인스턴스로 갔다가 판정을 못 받은 요청은 이 분모에 없다.**

### 이 회차가 증명하지 못한 재연결 재건

| 인스턴스 | `RECONNECT_DETECTED` | `REBUILT` |
|---|---:|---:|
| `i-0d265e...` | 1 | 2 |
| `i-0254a7...` | **0** | **0** |
| `i-03e773...` | **0** | **0** |

**`i-0d265e...` 의 1건은 F-1 에서 넘어온 것이다.** 시각이 18:21:41 이라 F-2 의 주입(18:25:34)
보다 앞선다.

**두 대는 다시 붙기 전에 죽었다.** 활성화 이벤트가 오지 않았으니 감시기가 걸릴 자리가 없었다.
**승격 뒤 재건이 실제로 도는 것을 이 회차도 못 보여 줬다.**

### F-3 스프링 서버 1대 비정상 종료 + 캐시 페일오버

| | 값 |

**k6 가 센 발급 9,995 와 DB 의 10,000 이 어긋난 것을 설명할 수 있다.** 차이 5 가
`coupon_already_issued` 5 와 정확히 같다. 서버가 행을 쓴 뒤 응답이 게이트웨이에서 끊긴
요청들이고, 그 사람들이 재시도해서 409 를 받았다. **`uk_mc_coupon_member` 가 두 번째를
막았으므로 중복 발급은 없다.** 09-30 f4-3 회차의 미해명 차이 1,844 와 달리 이번에는 장부가 맞는다.

### F-2 와 F-3 의 차이를 만든 것

**조합이 아니라 페일오버의 세기다.** F-3 는 더 많은 장애를 걸었는데 혼잡이 0 이고 OOM 도 없었다.

| | F-2 | F-3 |
|---|---:|---:|
| 건 장애 | 캐시 페일오버 | 서버 1대 종료 + 캐시 페일오버 |
| 재시도 | 47,208 | 7,259 |
| 혼잡 | 29,060 | 0 |
| OOM | 3대 | 없음 |
| 발급 | 5,741 | 10,000 |

**`test-failover` 가 얼마나 오래 명령을 막는지가 회차마다 다르다.** F-2 에서는 그 창이 길어
재시도가 여섯 배로 불고 메모리가 말랐다. F-3 에서는 짧게 끝났다.

**그래서 이 두 회차로는 조합 장애가 더 위험한지 알 수 없다.** 같은 주입을 여러 번 돌려
페일오버 창의 분포를 봐야 한다.

## 3. 재건이 문을 닫아 둔 시간

**이 회차가 얻은 재건 실측은 두 건이고, 둘 다 F-1 에서 되살아난 인스턴스가 낸 것이다.**

| 구간 | 쿠폰 900001 | 워밍업 쿠폰 1000000 |
|---|---:|---:|
| 올릴 것을 올리기 | 67 | 12 |
| 남의 것을 기다리기 | 3,026 | 7 |
| 읽고 쓰기 | **364** | 26 |
| **문을 닫아 둔 시간** | **3,458** | 46 |

```
issued=10000 queued=0 maxSeq=10000 freed=0    <-  900001
issued=0     queued=0 maxSeq=0     freed=0    <-  1000000
```

### 09-23 과 견주면

| 구간 | 2026-09-23 (`seq-loss`, 부하 중) | 2026-10-01 (재연결, 부하 끝난 뒤) |
|---|---:|---:|
| 남의 것을 기다리기 | 55 | 3,026 |
| 읽고 쓰기 | 127 | **364** |
| 합계 | **204** | **3,458** |

**기다리기가 55 에서 3,026 으로 벌어진 것은 부하가 없었기 때문이다.** 올리기 참여는 플러시가
재건 락을 보는 자리에서 일어나는데, 부하가 끝난 뒤에는 플러시가 돌지 않아 아무도 참여하지
않는다. 그래서 `contributeWait` 3초를 끝까지 태운다. 실제 이벤트 중이라면 창이 20밀리초라
09-23 처럼 수십 밀리초에 끝난다.

```
COUPON_SEQ_CONTRIBUTIONS_TIMEOUT couponId=900001 instances=0 done=1 waitedMillis=3000
```

**`instances=0` 이 그 증거다.** 명부에 올라온 인스턴스가 하나도 없었다.

### 읽고 쓰기가 127 에서 364 로 늘어난 까닭

**이것은 부하와 무관하고 이 PR 이 늘린 것이다.** `pending` 을 통째로 지우지 않기로 하면서
DB 에 행이 있는 회원만 골라 빼는 일이 생겼다.

```
9번   seq 와 free 는 UNLINK 로 한 번에 지운다
      pending 에서는 DB 에 행이 있는 회원 10,000명을 쪼개어 ZREM 한다   <-  새로 생긴 값
11번  올라온 것 중 없는 회원만 ZADD NX
```

**이 값을 지불한 이유가 둘이다.** `pending` 의 점수가 그 회원이 실제로 번호를 받은 시각이라
덮으면 회수가 뒤로 밀린다. 그리고 올릴 것이 빌 때 이 키를 비우면 소진 근처에서 스크립트가
최종 소진으로 판정해 재시도를 막는다.

**364밀리초는 재고 10,000장이 전부 팔린 상태의 값이다.** 이 구간은 DB 행 수에 비례하므로
이벤트 초반에 재건이 걸리면 더 짧다.

### 3,458밀리초를 어떻게 읽나

**이 값은 최악의 조건에서 나온 값이지 평상시 값이 아니다.** 부하가 없어 참여가 0 이었고 재고가
다 팔려 읽을 행이 최대였다. **평상시 재건은 09-23 의 204밀리초에 읽고 쓰기 증가분을 더한
400~500밀리초 근처로 보는 것이 맞다.** 다만 팀은 그 값을 이 회차로 재지 못했다.

## 4. 이 회차가 찾아낸 고칠 것

### 기동 실패를 재연결로 보는 감시기 (고쳤다)

**증상.** 캐시가 멀쩡한데 재건이 걸려 발급이 3.4초 멈춘다.

**원인.** Lettuce 가 붙는 데 실패하면 끊김을 먼저 내고 다음 시도에서 활성화를 낸다. 그 모양이
재연결과 같다. `sawDisconnect` 표시만으로는 가를 수 없다.

**고친 방법.** 한 번이라도 성공적으로 붙은 뒤인지를 함께 본다. 첫 활성화는 기동으로 세고
그 앞의 끊김은 버린다. 테스트 둘을 붙였다.

### 없는 컨테이너 메모리 한도

**`compose.yaml.tftpl` 의 주석과 설정이 어긋나 있다.**

```
주석    "MaxRAMPercentage 는 컨테이너 한도 기준이다"
설정    mem_limit 도 deploy.resources.limits 도 없다
결과    70% 가 호스트 1,906MB 기준이라 힙이 1.33GB.  OOM 때 RSS 가 1.38GB 였다
```

**한 대에 앱만 도는 것이 아니다.** node-exporter 와 cadvisor 와 alloy 와 dockerd 가 같은
1,906MB 를 쓴다. 앱이 호스트의 70% 를 힙으로 잡으면 나머지 전부의 몫이 30% 안에 들어가야 한다.

**한도를 두면 얻는 것이 둘이다.** 주석이 말하는 대로 비율이 동작하고, 말랐을 때 커널이 아니라
JVM 이 `OutOfMemoryError` 로 죽어 힙 덤프가 남는다. **지금은 왜 말랐는지가 안 남는다.**

이 회차에서는 고치지 않았다. 발사대 템플릿을 바꾸면 재배포와 회차를 다시 돌려야 하고,
측정 중에 조건을 바꾸면 앞의 네 회차와 견줄 수 없다.

### 회차를 반복할 때 쏟아지는 카운터 오탐

**`COUPON_SEQ_COUNTER_BEHIND` 가 네 회차에 111건 찍혔고 전부 오탐이다.**

```
회차 1 끝   카운터 10,000.  인스턴스가 기억하는 최대 순번도 10,000
회차 2 시작  event:open 이 카운터를 0 으로 다시 세운다
            그런데 기억은 JVM 힙에 있어 10,000 그대로다
            카운터가 0 -> 10,000 으로 오르는 동안 매 배치가 "뒤처졌다" 를 찍는다
```

**gap 이 단조적으로 줄어드는 것이 오탐의 표식이다.** 진짜 승격이라면 카운터가 뒤로 가므로
gap 이 갑자기 벌어진다. 이번 111건은 전부 줄어드는 쪽이었다.

**이것이 실제로 해를 끼치는 자리는 하나다.** 승격이 일어난 회차에서 진짜 경보를 이 소음이
가린다. F-2 가 정확히 그 회차였다.

**재건은 안 띄우므로 운영에 주는 해는 없다.** `measureBehind` 는 재기만 한다.

## 5. 남은 것

```
1  승격 뒤 재건을 실제로 돌려 보기.  OOM 을 먼저 막아야 이 관측이 가능하다
2  컨테이너 메모리 한도를 두고 F-2 를 다시 돌리기
3  같은 주입을 여러 번 돌려 test-failover 창의 분포를 보기
4  회차 사이에 카운터 기억을 버리게 하거나, 회차마다 다른 쿠폰을 쓰기
```

**1번이 2번에 막혀 있다.** 두 대가 다시 붙기 전에 죽으면 활성화 이벤트가 안 오고, 그러면
감시기가 걸릴 자리가 없다. **메모리를 고치는 것이 이 기능을 검증하는 전제다.**
