# 지금 도는 재건

**이 문서 하나로 재건을 다 읽을 수 있게 쓴다.** `rebuild-v2` 와 `rebuild-v3` 은 그때 무엇을 왜
바꿨나의 기록이라 "지금 어떻게 도나" 를 알려면 셋을 겹쳐 읽어야 했다.

```
태그        rebuild-v4 (93c78d30)
코드        CouponSeqRebuildTrigger  CouponSeqRebuilder  CouponSeqContributor
스크립트    coupon-issue-seq.lua  coupon-open-gate.lua  coupon-write-free.lua
회차        docs/coupon/rebuild-v4/rounds.md
```

**`rebuild-v4` 가 `rebuild-v3` 에서 바꾼 것은 3.2 하나다.** 나머지 장은 v2 와 v3 에서 그대로
이어받은 것이고, 여기 다시 적는 까닭은 한 자리에 모으기 위해서다.

---

## 1. 재건이 고치는 것

Redis 가 이 쿠폰의 키 네 개를 잃거나 뒤로 돌린다.

| 키 | 담는 것 |
|---|---|
| `counter` | 여태 몇 번이 나갔나 |
| `seq` | 회원 -> 번호. 값에 `:1` 이 붙으면 DB 행까지 된 것이다 |
| `free` | 주인 없이 돌아온 번호 |
| `pending` | 번호는 나갔는데 아직 DB 행이 안 된 것 |

**통째로 잃는 것보다 뒤로 가는 것이 나쁘다.** 복제본이 밀린 채 승격되면 카운터가 이미 나간
번호보다 작아진다. 그 값으로 번호를 내주면 **이미 번호를 쥔 사람에게 같은 번호가 또 나간다.**

재건은 **DB 와 각 인스턴스의 기억으로 네 키를 다시 세우는 일**이다.

---

## 2. 전체 그림

**가운데 줄이 본선이고 오른쪽으로 빠지는 것은 거기서 끝나는 가지다.**

```
입구 셋 (3.1)
  요청이 "카운터가 없다" 를 받는다
  요청이 "재건 중이다" 를 받는다
  Redis 연결이 끊겼다 다시 붙는다
        |
        v
   재건을 깨운다  ---> 이 서버가 10초 안에 깨웠으면 여기서 끝 / 이 서버에서 이미 돌고 있으면 여기서 끝
        |
        |  여기서 요청 스레드가 돌아간다. 아래는 재건 스레드가 한다
        v
   DB 를 읽는다 (3.4)  ---> 관리자가 아직 안 연 이벤트면 여기서 끝 / 관리자가 방금 다시 연 이벤트면 여기서 끝
        |
        v
   A 단계  (4장)   서버 세 대가 각자 한다. 락을 안 건다
   순번 발급 차단 -> seq -> 내 큐 -> 카운터 -> 그 차단의 시한 1초를 다시 센다 (4.4)
        |
        v
   B 단계  (5장)   락을 잡은 서버 한 대만 한다
   free 되돌리기
        |
        v
   순번 발급 차단이 시한 1초로 저절로 풀린다 (6장)
```

**순번 발급 차단은 그 쿠폰의 번호 내주기를 모든 서버에서 멈추는 것이다.** 그동안 들어온 요청은
번호를 못 받고 503 을 받는다. 재건이 틀린 번호를 내주느니 잠깐 끊는 쪽을 골랐다 (6장).

**깨우기를 거르는 둘은 그 서버 혼자만의 기준이다.** 기록이 Redis 가 아니라 **각 서버의 메모리**에
있다. 그래서 한 서버가 걸러도 나머지 둘은 자기 재건을 돈다. **A 단계를 서버 세 대가 다 해야 하기
때문이다 (4.1).**

## 3. 깨우기

**주기 실행이 아니다. 평소에는 도는 것이 없다.**

### 3.1 입구 셋

| 입구 | 부르는 이 | 무엇을 보고 |
|---|---|---|
| 카운터가 없다 | 요청 스레드 | 발급 스크립트가 카운터를 못 찾았다 |
| 재건 중이다 | 요청 스레드 | 발급 스크립트가 순번 발급 차단을 봤다 |
| 재연결 | 재연결 감시 | Redis 연결이 끊겼다 다시 붙었다 |

**앞의 둘은 발급 스크립트의 답이다.** 코드와 로그에서는 `-2` 와 `-4` 로 보이고, 자바 쪽 이름은
`SeqOutcome.NotPrepared` 와 `SeqOutcome.Rebuilding` 이다. 이 문서는 뜻으로 부른다.

**셋 다 집합에 넣기만 하고 돌아간다.** 이벤트가 열리는 순간 수만 개가 같은 자리를 지나므로,
거기서 일을 시키면 수만 개가 같은 재건을 하려 든다. 일은 데몬 스레드 하나가 한다.

#### 재연결을 따로 보는 까닭

**승격은 키를 지우지 않는다.** 복제가 밀린 채 승격되면 카운터는 살아 있고 **값만 뒤로 간다.**
그러면 발급 스크립트가 "카운터가 없다" 를 안 내므로, **앞의 두 입구는 승격을 못 본다.**

그래서 재연결 자체를 두 번째 신호로 둔다. 끊겼다 붙으면 **DB 에서 열려 있는 선착순 이벤트를
찾아 전부 깨운다.**

**처음 붙는 것은 신호가 아니다.** 기동과 배포에도 활성화가 오므로, **끊긴 것을 본 뒤의 활성화만**
센다. 안 가리면 배포마다 열려 있는 이벤트의 발급이 멈춘다. 그리고 기동 때 첫 연결이 실패하면
끊김이 먼저 오고 다음 시도에서 활성화가 와 재연결과 모양이 같으므로, **한 번이라도 붙은 뒤인지**를
함께 본다.

**전손에서는 이 입구가 안 뜬다.** 서버가 전부 재기동되면 첫 연결이 기동이라서다. 그때는 첫
요청이 "카운터가 없다" 를 받아 깨운다.

#### 플러시 경로는 입구가 아님

**플러시 스레드도 배치를 쓴 뒤 Redis 를 본다.** 그런데 그 자리는 **재기만 하고 재건을 안 띄운다.**

```java
// CouponIssueFlusher -> checkAfterFlush -> measureBehind
// 카운터가 이미 나간 순번보다 뒤처졌는지 재서 로그와 지표로만 남긴다
```

**재건은 그 이벤트의 플러시를 3초 넘게 멈추므로 오탐이 곧 장애다.** 정상 운영에서 이 표본이
0건이라는 것을 회차로 확인한 뒤에 입구로 붙인다
(`rebuild-v1/measurement-cache-loss.md` 5장).

### 3.2 10초 최소 간격

**`rebuild-v4` 가 더한 것이 이것 하나다.**

`rebuild-v3` 에서 순번 발급 차단이 스스로를 먹였다.

```
차단이 걸린다 -> 발급이 "재건 중이다" 를 낸다 -> 서비스가 재건을 깨운다 -> 그 재건이 차단을 다시 건다
  -> 다음 요청이 또 "재건 중이다" 를 받는다 -> 처음으로
```

**`inProgress` 로는 못 막는다.** 그것은 도는 동안만 막는데 **차단의 시한이 그보다 오래 서 있다.**
재건이 끝나도 차단이 남아 있으면 다음 요청이 또 깨우고, 그 재건이 차단을 연장한다. **트래픽이
있는 한 안 멈춘다.**

2026-10-31 Z-2 회차가 그 모양이었다.

```
재건 61번 (대별 20 / 21 / 20).  매번 같은 값이었다
  issued=7301  dbMax=7307  counter=7307
그동안 발급이 막혀 혼잡률 90.02%, 재고 10,000장 중 2,699장이 안 나갔다
```

그래서 `suspect()` 입구에 **쿠폰마다 이 인스턴스가 마지막으로 띄운 시각**을 두고, 10초 안이면
안 띄운다.

```java
if (tooSoon(couponId)) return;
if (!inProgress.add(couponId)) return;
worker.execute(...);
```

**갱신을 성공한 쪽에서만 한다.** 막힌 호출이 시계를 밀면 트래픽이 계속 있는 동안 간격이 영영
안 끝난다.

**간격을 둬도 전파는 산다.** 남의 서버가 건 차단을 보고 자기 재건을 **한 번** 도는 것이
전파(6.3)이고, 그 한 번 뒤로는 간격이 막으므로 차단이 시한에 풀린다.

| | `rebuild-v3` | `rebuild-v4` |
|---|---:|---:|
| 재건 | 61번 | 3번 |
| 발급 | 7,301 | 9,905 |
| 미판매 | 2,699 | 95 |
| 결번 | 6 | 0 |

### 3.3 간격이 막은 서버는 어떻게 되나

**대개는 괜찮다.** 간격에 막혔다는 것은 **이 서버가 10초 안에 이미 재건을 띄웠다**는 뜻이고,
그 재건의 A 단계에서 자기 큐를 이미 올렸기 때문이다.

**안 괜찮은 틈이 하나 있다.** 그 10초 사이에 이 서버가 **새로 받은 티켓**은 안 올라간다. 번호는
나갔는데 `seq` 에 기록이 없는 상태가 되고, 그 회원이 재시도하면 번호를 하나 더 태운다. 두 행 중
하나가 `uk_mc_coupon_member` 에 걸려 **결번 하나가 남는다.**

**받아들인 위험이다.** 이 틈이 만드는 것은 결번 몇 장이고, 간격을 빼면 Z-2 처럼 **재고 2,699장**
이 안 나간다. 9장에 다시 적는다.

### 3.4 일을 시작하기 전에 거르는 둘

**깨우는 신호가 손실만 뜻하지 않는다.** 관리자가 아직 안 연 이벤트도 같은 "카운터가 없다" 를
낸다. 그 둘을 **DB 를 보고** 가른다.

```java
if (coupon == null || !coupon.isActive() || !coupon.isLimited()) return;
if (reprepared(couponId)) return;
```

둘째가 더 미묘하다. 준비 단계가 카운터를 **0** 으로 세우는데, 재건이 세울 값은 나간 번호의
최댓값이라 0 이 될 수 없다. **0 이 보이면 관리자가 방금 새로 연 것이므로 덮지 않는다.** 덮으면
지난 이벤트의 최댓값까지 건너뛰어 **그만큼의 재고를 통째로 버린다.**

### 3.5 세 번 해 보는 까닭

재건이 실패하면 200밀리초씩 늘려 가며 세 번까지 해 본다.

**"다음 요청이 다시 띄운다" 에 기대던 자리인데 그 다음이 없는 경로가 있다.** 2026-10-10 J-2 가
한 번 실패하고 끝나 재고 10,000장 중 1,030장이 안 나갔다.

## 4. A 단계

**서버 세 대가 전부 한다. 락을 안 건다.**

```
1  순번 발급을 차단한다          SET coupon:{id}:raising "1" PX 1000
2  DB 에서 발급 행을 읽는다      member_id, issue_seq
3  seq 해시를 다시 쓴다          값에 확정 표시 :1 을 붙인다
4  자기 큐를 되살린다            contributor.restore()
5  카운터를 세운다               openGate(max(DB 최댓값, 이 서버의 기억))
6  그 차단의 시한을 다시 센다    SET coupon:{id}:raising "1" PX 1000
```

**6번은 1번의 되풀이가 아니다.** 같은 키에 같은 값을 쓰지만 `SET` 이 TTL 을 지우고 다시 걸므로,
**차단이 풀리는 시각만 뒤로 민다.** 왜 그래야 하는지는 4.4 에 있다.

### 4.1 왜 락을 안 거나

**4번을 남이 대신 못 한다.** 그 서버의 메모리 큐에 어떤 티켓이 들어 있었는지는 **그 서버만 안다.**
서버 한 대만 뽑아 시키면 나머지 두 대의 큐가 통째로 사라진다.

**큐는 Redis 가 죽어도 살아 있는 유일한 미확정 기록이다.** DB 에는 커밋된 것만 있고, 큐에는
번호를 받았지만 아직 행이 안 된 것이 있다.

5번도 각자 해야 한다. 각 서버가 기억하는 "여태 본 최대 순번" 이 서로 다르고, **가장 큰 값을 아는
서버가 어느 것인지 아무도 모른다.**

### 4.2 왜 각자 올려도 되나

**`coupon-open-gate.lua` 가 올리기만 하기 때문이다.** 낮은 값이 높은 값을 못 덮는다. 그래서 서버
세 대가 어떤 순서로 읽고 써도 가장 높은 값이 남는다.

```
V2-1 회차
  서버 A 가 7200 을 들고 들어왔다
  서버 B 가 7044 를 들고 들어왔다
  서버 C 가 7234 를 들고 들어왔다
  서버 세 대가 끝난 뒤 counter = 7234
```

**이 성질이 없으면 재건이 고치려는 증상을 재건이 만든다.** 낮은 값이 높은 값을 덮을 수 있으면
그것이 곧 "카운터가 뒤로 간 것" 이다.

### 4.3 왜 카운터가 마지막인가

**5번이 발급을 재개시키는 동작이다.** 그 전에 세우면 이미 번호를 쥔 회원이 `seq` 에 없는 틈이
생긴다. 그 회원이 재시도하면 번호를 하나 더 받고, 두 INSERT 중 하나가 `uk_mc_coupon_member` 에
걸려 **번호 하나가 결번이 된다.**

그래서 3번과 4번이 5번보다 앞에 있어야 한다. **순서가 곧 안전장치다.**

**3번에서 확정 표시를 붙이는 것도 같은 줄기다.** 표시를 안 붙이면 그 번호가 미확정으로 보여,
기준 시간이 지날 때 **이미 DB 행이 된 번호를 남에게 넘긴다.**

### 4.4 왜 끝에서 다시 차단하나

1번만 있으면 **시작 시각** 기준이라, A 단계가 시한 1초(`raise-gate-ttl`)보다 길면 **아직 일하는
중에 차단이 풀린다.** 6번을 두면 차단이 풀리는 때가 **마지막으로 끝낸 서버를 기준으로 1초 뒤**가 된다.

```
t=5ms     서버 A 가 차단한다
t=20ms    서버 C 가 "재건 중이다" 를 받고 자기 A 를 시작한다.  차단이 연장된다
t=330ms   서버 A 가 끝나고 다시 건다
t=360ms   서버 C 가 끝나고 다시 건다
t=1.36s   마지막 연장으로부터 1초가 지나 차단이 풀린다
```

## 5. B 단계

**락을 잡은 서버 한 대만 한다.** 주인 없이 떠 있는 번호를 `free` 로 되돌린다.

```java
if (!setIfAbsent(rebuild(couponId), token, 30초)) {
    // 남이 세우고 있다. A 단계는 이미 했으므로 그대로 돌아간다
    return;
}
```

후보는 **DB 에 행이 없고 카운터에서 500 이상 떨어진 번호**다. 그 거리가 "그 뒤로 몇 개가 더
나갔나" 라서, 방금 나가 아직 누가 쥐고 있는 번호를 거른다.

**B 단계는 DB 를 안 읽는다.** A 단계가 2번에서 읽어 둔 목록을 그대로 받는다. 그래서 재건 한
번에 DB 전수 조회는 한 번뿐이고, B 가 하는 일은 셋 다 Redis 안에서 끝난다.

```
1  카운터를 읽는다      GET coupon:{id}:counter
2  후보를 고른다        자바 메모리. A 가 준 목록과 카운터만 본다
3  스크립트를 부른다    HGETALL seq 로 쥔 번호를 가리고 ZADD NX 로 넣는다
```

**다시 읽어도 더 정확해지지 않는다.** A 와 B 사이에 생긴 행이 있어도 스크립트가 `seq` 해시로 한
번 더 거르고, 그 가리기와 넣기가 한 스크립트 안에 있어야 발급을 멈추지 않고도 안전하다
(`rebuild-v2/design.md` 5.3).

### 5.1 락이 하는 일

**중복을 막는다. 그것뿐이다.** B 의 입력은 DB 행과 카운터뿐이라 **누가 해도 답이 같다.** 서버 세 대가
나란히 하면 같은 답을 세 번 계산해 같은 것을 세 번 쓴다.

`coupon-write-free.lua` 가 매번 `seq` 해시를 **통째로 읽는다.** 회원 만 명이면 만 개 필드다.
Redis 가 한 스레드라 그 읽기가 도는 동안 **모두의 발급이 멈춘다.**

```
측정된 B 단계 시간    freeMillis = 8 ~ 12
락이 아끼는 것        그 10밀리초를 두 번
```

### 5.2 락이 안 하는 일

**발급을 한 번도 안 막는다.** 못 잡은 서버는 A 만 하고 돌아간다.

**안전도 안 지킨다.** 스크립트가 `ZADD NX` 로 넣어 멱등이라 둘이 같이 해도 결과가 같다. 그래서
락이 틀려도 잃는 것이 없다.

| 어긋나는 경우 | 결과 |
|---|---|
| 락 잡은 서버가 죽는다 | 30초 뒤 TTL 이 푼다 |
| 남의 락을 잘못 지운다 | 둘이 해도 결과가 같다 |
| 아무도 못 잡는다 | 그럴 수 없다. `NX` 는 반드시 하나를 통과시킨다 |

**`rebuild-v1` 은 이러지 않았다.** 그때는 이 락이 발급까지 막았고, 못 잡은 서버는 재건을 아예 안
했다. 그래서 **주도자가 죽으면 30초 동안 전부 멈췄다.**

### 5.3 아직 한 건도 못 되살린 것

**정직하게 적는다. B 단계는 쓸모를 아직 못 보였다.**

```
전 회차 기록
  COUPON_SEQ_FREE_WRITTEN   124건   added=0  (124건 전부)
  COUPON_SEQ_FREE_NONE        4건
```

후보는 찾는다. 그런데 **스크립트가 전부 "아직 누가 쥔 번호" 로 가리고 넘어간다.**

```
2026-10-31 회차   counter=7307   DB 행 7,301   결번 6
                  candidates=6   added=0
```

**결번 6개를 정확히 집었는데 6개 다 못 넣었다.** B 가 도는 때가 재건 중이라, 되살리고 싶은 바로
그 번호의 매핑이 아직 `seq` 해시에 살아 있기 때문이다.

**평상시 회수는 B 가 아니라 발급 Lua 가 한다.** 그쪽이 `pending` 에서 오래된 티켓을 걷어 번호를
`free` 로 돌린다. B 는 **그 경로까지 날아간 경우의 2차 그물**인데, 그 조건을 만드는 회차를 아직
안 돌렸다. 9장에 다시 적는다.

---

## 6. 순번 발급 차단

**그 쿠폰의 번호 내주기를 모든 서버에서 멈춘다.** 한 서버가 걸면 다른 서버의 요청도 번호를 못 받고
503 을 받는다. 재건이 도는 동안에는 카운터가 살아 있어도 그 값이 뒤로 가 있을 수 있어서,
**그 값으로 번호를 내주면 이미 번호를 쥔 회원에게 새 번호가 나간다.**

**발급만 막는다.** 조회와 그 밖의 쿠폰 API 는 그대로 돌고, 이미 번호를 받아 큐에 든 티켓도
끝까지 DB 로 간다.

### 6.1 무엇이 거나

| | 순번 발급 차단 | 재건 락 |
|---|---|---|
| 키 | `coupon:{id}:raising` | `coupon:{id}:rebuild` |
| 거는 이 | A 단계에 들어가는 모든 서버 | B 단계를 맡을 서버 한 대 |
| 수명 | 1초. 시간이 푼다 | 30초 또는 토큰 대조 해제 |
| 막는 것 | 모든 서버의 순번 발급 | 아무것도 안 막는다 |
| 못 얻으면 | 요청이 503 을 받는다 | A 만 하고 돌아간다 |

**`openGate` 는 둘 중 어느 쪽도 아니다.** 그 메서드가 여는 것은 **카운터**이고, 그것이 도는
동안에도 차단은 걸려 있다. 이름이 `coupon-open-gate.lua` 와 짝이라 그대로 둔다.

### 6.2 거는 방식

```
덮어쓴다      NX 가 아니다. 그래야 나중에 깬 서버가 차단을 연장한다
지우지 않는다  먼저 끝낸 서버가 지우면 아직 하는 서버의 차단까지 풀린다
TTL 을 매번 준다  SET 이 TTL 을 지우므로 시한을 같이 준다
```

**세운 서버가 죽어도 저절로 풀린다.** 푸는 이가 없는 것이 이 설계의 요점이다.

### 6.3 차단이 스스로 퍼짐

**새 신호를 안 만든다. 차단 표시 자체가 신호다.**

```
A 가 재연결을 감지하고 순번 발급을 차단한다
C 의 요청이 "재건 중이다" 를 받는다  -> suspect() -> C 가 자기 A 단계를 돈다
```

**C 가 재연결을 못 봤어도 퍼진다.** 한 번의 단절에 모든 서버가 연결 이벤트를 받는 것은 아니고,
받아도 10초 간격에 막힐 수 있다. **그래도 C 는 요청에서 차단을 본다.**

---

## 7. 정지 예산

A 단계가 걸음 사이마다 총 벽시계를 본다. 상한은 **5초**다.

**명령 단위 타임아웃으로는 이 시간이 안 묶인다.** 재건 한 번이 Redis 를 서른 번 안팎 치는데,
명령마다 상한 아래로 느리기만 하면 **아무것도 안 터지면서 총합이 분 단위로 는다.** 그동안 발급이
멈춰 있다.

**넘으면 그만둔다.** 차단은 시한이 풀고, 그 뒤는 재건이 없던 때와 같은 상태다. **결번을
받아들이고 가용성을 지키는 선택이다.**

그만둔 뒤에는 재시도하지 않는다. 다시 돌면 그 시도가 차단을 또 걸어 **발급 정지가 예산의 배수로
늘어난다.**

---

## 8. 안전이 어디서 지켜지나

**재건이 아니라 DB 가 지킨다.** 이것이 이 설계 전체에서 제일 중요하다.

| 제약 | 막는 것 |
|---|---|
| `uk_mc_coupon_member` | 한 사람이 두 장을 받는 것 |
| `uk_mc_coupon_seq` | 한 번호가 두 사람에게 가는 것 |
| `chk_mc_issue_seq` | 번호가 재고를 넘는 것 |

**그래서 재건이 실패하면 결번이 난다. 초과 발급은 안 난다.** 여태 잰 모든 회차에서 초과 발급은
0건이다.

이 성질이 있어서 A 단계를 서버 세 대가 락 없이 돌릴 수 있고, B 단계의 락이 틀려도 괜찮고, 예산을
넘겼을 때 그냥 그만둘 수 있다. **Redis 쪽이 틀리는 최악이 결번으로 끝난다.**

## 9. 남는 위험

### 9.1 10초 사이에 받은 티켓

3.3 에 적었다. 간격에 막힌 서버가 그 사이 새로 받은 티켓을 안 올려 **결번 몇 장**이 남는다.
간격을 빼면 Z-2 처럼 재고 수천 장이 안 나가므로, **적은 쪽을 골랐다.**

### 9.2 B 단계를 맡은 서버가 중간에 죽는 것

못 잡은 두 서버는 **이미 돌아갔다.** 그래서 그 회차의 B 가 통째로 빠지고, 다음 `suspect()` 는 10초
간격에 묶여 있다.

**락이 없으면 반대다.** 서버 세 대가 다 시도하고 하나만 살아남아도 된다. **가용성을 사려고 쓴 설계에
가용성을 깎는 자리가 하나 들어가 있다.**

### 9.3 B 단계가 쓸모를 못 보인 것

5.3 에 적었다. 124번 돌아 되살린 번호가 0개다.

**다음 회차에서 재현 조건을 만들어야 한다.** 캐시를 통째로 날려 `pending` 까지 잃은 상태로
재건을 돌리는 것이다. 거기서도 0건이면 **B 단계와 재건 락을 같이 떼는 것이 맞다.**

### 9.4 재건이 도는 동안의 503

차단이 서 있는 동안 전 인스턴스가 503 을 낸다. **이것은 고장이 아니라 설계다.** 다만 혼잡률
지표가 그만큼 오르므로, 회차를 읽을 때 **낮은 혼잡률이 좋은 신호가 아닐 수 있다**는 것을 같이
봐야 한다 (`rebuild-v4/rounds.md` 4장).

`CouponIssueProperties` 가 기동 때 그것을 확인한다.
