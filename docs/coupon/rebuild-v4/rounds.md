# `rebuild-v4` 장애 3종 회차 (V2, `settled` 로 잰 판)

**재건이 처음으로 설계대로 돌았다.** 다만 **이 판의 지연 수치는 `coupon_settled_duration` 이고
`http_req_duration` 이 아니다.** 임계를 `http` 로 옮긴 변경(#243)이 코드에 들어가 있었지만
부하 생성기가 시나리오를 `origin main` 에서만 받아 와서, `main` 이 그 변경 전이라 이 판은 옛
시나리오로 돌았다. k6 는 임계가 걸린 지표에만 p99 를 찍으므로 요약의 p99 는 `settled` 다.

**`http` 로 잰 같은 장애는 [`s-rounds.md`](s-rounds.md) 에 있다.**

```
AWS 실측     20,000 VU / ramp 60초 / hold 30초 / 재고 10,000장 / 전용 3대
스프링 서버  rebuild-v4 (93c78d30)
워밍업       기동 때 ApplicationRunner 가 돈다. healthy 가 곧 warm 이다
주입         k6 를 먼저 띄우고 24~25초 뒤에 걸었다
대시보드     docs/coupon/rebuild-v4/rounds/
```

**이 회차가 잰 로직은 [`design.md`](design.md) 에 있다.**

## 1. 결론

| 회차 | 장애 | 발급 | 미판매 | 미확정 번호 | 초과 발급 | `settled` p99 | 실패율 | 재건 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| V2-3 | 스프링 서버 1대 비정상 종료 | **10,000** | 0 | **0** | 0 | 443.93ms | 25.94% | 0 |
| V2-1 | 캐시 Multi-AZ 페일오버 | 9,905 | 95 | **0** | 0 | **451.03ms** | **0.00%** | 3 |
| V2-2 | 복합 (서버 1대 종료 + 캐시 페일오버) | 9,600 | 400 | **0** | 0 | 343.36ms | 30.31% | 2 |

**3회차 다 미확정 번호 0, 초과 발급 0, 1인 1매, 예상 못 한 응답 0 이다.**

**이 4개는 k6 가 아니라 DB 가 낸 수다.** 서버가 무엇이라 답했든 행이 최종 사실이라, 회차가
끝난 뒤 팀이 한 문장으로 본다.

```sql
SELECT COUNT(*), MAX(issue_seq), MAX(issue_seq) - COUNT(*) AS gap, COUNT(DISTINCT member_id)
  FROM member_coupon WHERE coupon_id = 900001;
```

| 무엇 | 어떻게 읽나 |
|---|---|
| 발급 | `COUNT(*)` |
| 미확정 번호 | `MAX(issue_seq) - COUNT(*)`. 번호는 나갔는데 행이 없는 것 |
| 초과 발급 | `COUNT(*)` 가 재고 10,000 을 넘는지 |
| 1인 1매 | `COUNT(DISTINCT member_id)` 가 `COUNT(*)` 와 같은지 |

나머지 열의 출처는 다르다. 미판매는 재고 10,000 에서 발급을 뺀 것이고, `settled` p99 와 실패율은
k6 요약에서, 재건 횟수는 `COUPON_SEQ_RAISED` 로그에서 온다.

**이 판에는 `http` p99 가 없다.** 저 수는 `settled` 라서 답을 받은 요청만 담는다. 장애 회차에서
답을 못 받은 요청이 바로 가장 느린 요청들이므로 **이 수는 좋은 쪽으로 치우쳐 있다.** SLO 1초를
이 판으로 판정할 수 없다.

k6 요약에 남은 `http` 값은 p95 와 max 까지다. 임계가 `settled` 에 걸려 있어 `http` 의 p99 를
k6 가 찍지 않았고, Prometheus 는 `destroy.sh` 가 지웠으므로 **지금 되살릴 수 없다.**

| 회차 | 장애 | `settled` p99 | `http` p95 | `http` max | 실패율 |
|---|---|---:|---:|---:|---:|
| V2-3 | 서버 1대 | 443.93ms | 56.51ms | 933.94ms | 25.94% |
| V2-1 | 캐시 페일오버 | **451.03ms** | 512.04ms | **2.63초** | **0.00%** |
| V2-2 | 복합 | 343.36ms | 316.56ms | 1.98초 | 30.31% |

**`http` max 가 `settled` p99 보다 크게 벌어진다.** 캐시 페일오버는 451.03ms 와 2.63초다. 같은
장애를 `http` 로 다시 잰 회차는 p99 가 973.67ms 였다([`s-rounds.md`](s-rounds.md)).

## 2. 재건이 설계대로 돈 것

`rebuild-v2` 부터 각 대가 자기 몫을 하므로 **기대값이 대당 1번**이다.

```
캐시 페일오버   3건   i-0fd47fe9 1,  i-02674593 1,  i-018d24a7 1
복합           2건   1대가 죽어 남은 2대가 1번씩
서버 1대       0건   Redis 를 안 건드리는 장애다. 재건이 뜰 이유가 없다
```

**대별로 정확히 1번씩이다.** 전파가 살아 있으면서 고리가 없다.

```
event=COUPON_SEQ_RAISED issued=7178 dbMax=7200 mark=7200 bound=7200 counter=7234 raiseMillis=411
event=COUPON_SEQ_RAISED issued=7030 dbMax=7038 mark=7044 bound=7044 counter=7234 raiseMillis=283
event=COUPON_SEQ_RAISED issued=7203 dbMax=7208 mark=7234 bound=7234 counter=7234 raiseMillis=185
```

**서버 3대가 각자 다른 `mark` 를 들고 왔는데 `counter` 가 모두 7,234 로 수렴했다.** 카운터가 올리기만
하는 값이라 순서와 무관하게 최댓값이 남는다는 것이 실측으로 보인다.

**정지 예산 초과 0, 재건 실패 0, 순번 역전 0 이다.**

## 3. 재건이 걸린 시간

### V2-1 (캐시 페일오버, 서버 3대)

| 시각 | 이벤트 | 걸린 시간 |
|---|---|---:|
| 08:11:05.076 | 서버 1 이 A 를 시작 | |
| 05.359 | 서버 1 A 끝 | 283ms |
| 05.391 | 서버 1 B 끝 | 23ms |
| 05.213 | 서버 2 가 A 를 시작 | |
| 05.624 | 서버 2 A 끝 | 411ms |
| 05.650 | 서버 2 B 끝 | 18ms |
| 05.745 | 서버 3 이 A 를 시작 | |
| 05.930 | 서버 3 A 끝 | 185ms |
| 05.955 | 서버 3 B 끝 | 21ms |

```
서버별 합        306 / 429 / 206 ms
전체 벽시계      879ms        05.076 -> 05.955
순번 발급 정지   약 1.88초     마지막이 끝난 뒤 차단 시한 1초가 더 붙는다
```

### V2-2 (복합 장애, 서버 2대)

```
서버별 A        136 / 124 ms
B               후보가 없어 FREE_NONE
전체 벽시계     233ms
순번 발급 정지  약 1.23초
```

### 정지 시간을 어떻게 얻었나

**위 두 값은 계측이 아니라 계산이다.** 조각 2개로 되어 있고 출처가 서로 다르다.

```
전체 벽시계   COUPON_SEQ_RAISED 로그의 타임스탬프에서 가장 이른 것과 가장 늦은 것의 차
차단 시한     코드에 박힌 1초.  팀이 재지 않고 더했다
```

`raiseMillis` 는 서버 1대가 자기 구간을 `System.nanoTime()` 으로 잰 값이라 **그 1대 안만
본다.** 3대에 걸친 전체 길이를 아는 지표가 없어서, 팀이 로그 줄들의 타임스탬프를 늘어놓고 뺐다.

**그래서 이 수는 상한에 가깝다.** 차단 시한은 마지막 서버가 차단을 다시 건 시점부터 세는데 그
시점을 따로 안 찍어서, 팀이 전체 벽시계 끝에 1초를 그대로 붙였다. 중간에 차단이 잠깐 비는
구간이 있었는지도 안 봤다.

**요청 쪽에서 센 지표는 없다.** 발급이 실제로 몇 초 막혀 있었나를 팀은 혼잡(503) 비율로
간접으로만 본다(8장).

### 3배 차이가 어디서 났는지

**행 수로는 설명이 안 된다.** V2-1 이 **덜 읽고 더 오래 걸렸다.**

```
V2-1   issued 7,030 ~ 7,203    raise 185 ~ 411ms
V2-2   issued 9,584 ~ 9,585    raise 124 ~ 136ms
```

**`raise` 가 한 덩어리로만 잡혀 있어 구간을 못 가른다.** DB 조회인지 `seq` 해시 쓰기인지
`openGate` 인지가 지금 자료로는 안 나온다.

**짐작은 2가지다. 2가지 다 확인 안 했다.**

```
V2-1 은 페일오버 직후라 Redis 명령 자체가 느렸을 수 있다
V2-1 은 세 서버의 기억이 7044 / 7200 / 7234 로 벌어져 있었다
  V2-2 는 9598 / 9599 로 거의 같았다
```

### `rebuild-v1` 과 견주면

**나아진 것이 아니다. 더 오래 막힌다.**

| | 순번 발급 정지 | 어떻게 풀었나 |
|---|---:|---|
| `rebuild-v1` 부하 중 | **204ms** | 주도자가 전원 완료를 알고 바로 열었다 |
| `rebuild-v1` 부하 끝난 뒤 | 3,458ms | 참여할 플러시가 없어 기다림 3초를 끝까지 태웠다 |
| `rebuild-v4` 부하 중 | **약 1.88초** | 아무도 안 연다. 시한 1초가 지나야 풀린다 |

**`rebuild-v1` 의 3,458ms 를 견주면 안 된다.** 그 값은 부하가 끝난 뒤에 잰 것이고, 3,026ms 가
"남의 것을 기다리기" 였다 (`rebuild-v1/reconnect-and-fault.md` 3장). 부하 중에는 204ms 였다.

**이 느려짐은 `rebuild-v3` 이 미리 적어 둔 대가다** (`rebuild-v3/design.md` 5장). 전원이 끝난
것을 아는 길을 없애서 **일찍 못 연다.** 대신 주도자가 죽어도 30초를 멈추지 않고, 세는 것이
실패하는 경우도 없다.

### B 단계가 서버마다 돈 것

```
05.391   서버 1 의 FREE_WRITTEN   freeMillis=23
05.650   서버 2 의 FREE_WRITTEN   freeMillis=18
05.955   서버 3 의 FREE_WRITTEN   freeMillis=21
```

**락이 "하는 중" 표시라 끝나면 지워진다.** 서버 3대의 A 가 300ms 간격으로 끝나니 락이 1번도
안 부딪혔다. 뒤 서버가 빈 락을 새로 잡고 또 B 를 했다.

**이 회차에서 락이 아낀 것은 없다.**

## 4. `rebuild-v3` 에서 무엇이 달라졌나

`rebuild-v3` 은 같은 장애에서 재건이 **61번** 돌았다. 대별로 20 / 21 / 20 이다.

```
차단이 걸린다 -> Lua 가 -4 -> 서비스가 재건을 깨운다 -> 그 재건이 차단을 다시 건다
```

`inProgress` 는 도는 동안만 막는데 **차단의 시한이 그보다 오래 서 있어서** 다음 요청이 또 깨웠다.
`rebuild-v4` 가 `suspect()` 에 최소 간격을 걸어 끊었다.

| | `rebuild-v3` | `rebuild-v4` |
|---|---:|---:|
| 재건 | 61번 | 3번 |
| 발급 | 7,301 | 9,905 |
| 미판매 | 2,699 | 95 |
| 미확정 번호 | 6 | 0 |
| 혼잡률 | 90.02% | 84.88% |

## 5. 실패율이 무엇을 뜻하나

`http_req_failed` 는 **앱이 제대로 답하지 못한 비율**이다. k6 가
`expectedStatuses(200, 409, 410, 422, 503)` 밖을 실패로 센다.

**이번 판은 전부 게이트웨이 실패였다. 다른 것이 안 섞였다.**

```
서버 1대   실패 7,013 / 27,031 = 25.94%    coupon_gateway_failed 7,013   정확히 같다
복합       실패 20,278 / 66,884 = 30.31%   coupon_gateway_failed 20,278  정확히 같다
페일오버   실패 0 / 65,463 = 0.00%         게이트웨이 실패 지표 자체가 없다
```

**502/504 다.** ALB 가 죽인 인스턴스로 보낸 요청이고, 대상 그룹에서 빼기까지 몇 초가 걸린다.

**혼잡(503)과 가른다.** 혼잡은 앱이 살아서 판단하고 끊은 것이라 설계가 의도한 보호다. 캐시
페일오버에서 혼잡 84.88% 에 실패 0% 인 것이 그 차이를 보여준다. **전 인스턴스가 느려졌지만
살아 있어서 전부 답했다.**

## 6. 지연을 읽는 법

| 장애 | `settled` p99 | `http` p99 | 실패율 |
|---|---:|---:|---:|
| 서버 1대 | 443.93ms | (요약에 없음) | 25.94% |
| 캐시 페일오버 | 451.03ms | (요약에 없음) | 0.00% |
| 복합 | 343.36ms | (요약에 없음) | 30.31% |

**`coupon_settled_duration` 을 임계에서 빼려고 했지만 이 판에서는 안 빠졌다.** 코드에는 그
변경이 있었고 생성기가 받아 온 시나리오에는 없었다. 그 지표는 답을 받은 요청만 담는데, 장애
회차에서 답을 못 받은 요청이 바로 가장 느린 요청들이라 **모집단이 좋은 쪽으로 치우친다**
(`rebuild-v2/rounds.md` 3장).

**분모가 온전한 것은 캐시 페일오버뿐이다.** 실패율 0% 이고 **451.03ms 가 이 판에서 가로로
비교할 수 있는 유일한 수다.** 그래도 `settled` 라서 다른 판의 `http` p99 와는 못 견준다.

나머지 둘은 `max` 로 그 폭을 가늠한다.

```
서버 1대   http max 933.94ms
캐시       http max 2.63초
복합       http max 1.98초
```

**캐시 페일오버의 2.63초가 p99 451ms 와 벌어진 것은 꼬리가 짧고 뾰족하다는 뜻이다.** 재건이
도는 동안 발급이 막히는 구간이 그 자리로 보이지만, 그것까지는 안 갈랐다.

## 7. 회차 순서가 수치에 미치는 것

**같은 JVM 이 회차를 거듭할수록 빨라진다.** 가로로 비교할 때 이 순서를 같이 봐야 한다.

```
전용 3대 기동   16:55
캐시 페일오버   17:09   기동 14분 뒤.  첫 회차
복합           17:29   둘째.  1대는 직전 회차에서 죽어 재기동됐다
서버 1대       17:51   셋째.  가장 뜨겁다
```

**복합 회차가 1대를 죽이고 되돌린다.** 그 대는 재기동 뒤 워밍업을 다시 돌므로, 다음 회차에서
3대의 온도가 같지 않다.

## 8. 안 한 것

```
판정 지표        http 로 옮기지 못한 채 돌았다. 생성기가 옛 시나리오를 받아 왔다
반복 측정        장애마다 1회차뿐이다. 설계 문서가 "cache-failover 두세 번" 을 권했다
seq-loss         키 부재 경로를 이 판에서 안 걸었다
cache-wipe       같다
발급 정지 측정    발급이 막혀 있던 시간을 직접 안 쟀다. 혼잡률로 간접으로만 본다
```

**발급 수의 차이는 변동 범위 안이다.** 캐시 페일오버 역대 기록이 9,723 ~ 10,000 이고 폭이
280장이라, **이 판의 9,905 가 다른 판보다 낫다고 말할 수 없다.** 말할 수 있는 것은
`rebuild-v3` 의 7,301 과는 범위가 다르다는 것뿐이다.
