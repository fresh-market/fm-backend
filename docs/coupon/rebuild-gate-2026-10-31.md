# 재건이 끝날 때까지 순번을 안 내주는 설계

**재건이 지켜야 할 것이 하나 더 있다. 선착순이다.** README 5.6 이 그 원칙을 적었다.

> 장애로 못 쓴 번호는 그 사용자 것으로 남긴다. 반납하면 나중에 온 사람이 그 번호를 가져가고,
> **먼저 온 사람은 재시도해서 맨 뒤로 간다.** 순번은 도착 순서의 기록이고 그것을 잃을 이유가
> 사용자 쪽에 없다.

**지금 설계(#242)는 그것을 못 지킨다.** 재건 중에도 번호를 내주기 때문이다.

---

## 1. 순서가 깨지는 경로

```
회원 M 이 3,000번을 받는다.  티켓이 C 서버 큐에 있고 아직 INSERT 전이다
페일오버로 seq 해시가 사라진다
C 가 아직 자기 큐를 못 되살린 사이 M 이 재시도한다
  HGET seq M -> nil  ->  INCR 로 6,500번을 받는다
```

M 의 INSERT 가 둘이 되고 `uk_mc_coupon_member` 가 하나만 통과시킨다.
`CouponIssueFlusher.resolveDuplicate` 가 그 충돌을 푸는데 **먼저 커밋한 쪽을 남긴다.**

```
3,000 이 먼저 커밋   ->  재시도의 6,500 이 free 로 반납된다.  M 은 3,000.  순서가 지켜진다
6,500 이 먼저 커밋   ->  큐의 3,000 이 반납된다.  M 은 6,500.  M 이 맨 뒤로 간다
```

**페일오버 중에는 뒤쪽이 일어난다.** 플러시도 `completeIssued` 에서 Redis 를 치므로 그때 같이
느려지고, 그 틈에 재시도가 먼저 들어간다.

**정합성은 안 깨진다.** 초과 발급도 1인 1매도 DB 제약이 지킨다. 깨지는 것은 순서뿐이다.

### 값싼 문제가 아님

어긋난 번호 하나가 치르는 왕복이 넷이다.

```
Redis EVALSHA     새 번호를 태운다
DB INSERT         uk_mc_coupon_member 에 걸린다
DB SELECT         resolveDuplicate 가 실제 번호를 읽는다
Redis 스크립트     번호를 free 로 반납한다
```

**네 번 왕복하고 아무것도 못 얻는다.** 그리고 이것이 DB 와 Redis 가 이미 느린 순간에 쏟아진다.
막는 것이 정합성뿐 아니라 처리량에도 이롭다.

## 2. 바꾸는 것

**재건이 도는 동안 그 쿠폰의 순번 발급을 끊는다. 문이 열리는 조건은 시간이다.**

```
새 키   coupon:{id}:raising      문자열.  PX T 로 시한이 붙는다.  지우지 않는다
```

나머지는 전부 이미 있는 것을 쓴다.

---

## 3. 로직

### 3.1 발급 Lua

맨 앞에 세 줄이 는다.

```lua
-- KEYS[5] = raising
if redis.call('EXISTS', KEYS[5]) == 1 then
  return '-4'
end
```

`-4` 는 `SeqOutcome.Rebuilding` 이 되고 서비스가 **503 과 재건 깨우기**로 답한다.

**`-2`(준비 안 됨)와 반드시 갈라야 한다.** `-2` 는 그 대의 기억(`CouponSeqMarks`)을 버리는
신호인데, 재건 중에 버리면 **카운터를 세울 하한을 잃어** `bound` 가 DB 최댓값으로 떨어진다.
그러면 큐에 떠 있던 번호가 다시 나간다.

### 3.2 재건 스레드

각 대가 독립으로 돈다. 기다릴 대상도 셀 대상도 없다.

```
1  문을 닫는다        SET raising 1 PX T       덮어쓴다.  남이 닫아 놨어도 연장된다
2  DB 발급 행을 읽는다
3  seq 해시에 "N:1" 을 쓴다
4  자기 큐를 seq 와 pending 에 되살린다      HSETNX / ZADD NX
5  counter 를 max(DB MAX, 내 marks) 로 올린다
6  문을 다시 닫는다     SET raising 1 PX T       끝낸 시각 기준으로 다시 센다
```

**6번이 없으면 안 된다.** 1번만 있으면 **시작** 기준이라 A 단계가 T 보다 길 때 문이 먼저 열린다.
6번을 두면 문이 열리는 때가 **마지막으로 끝낸 대로부터 T 뒤**가 된다.

**지우지 않는다.** 먼저 끝낸 대가 `delete` 하면 아직 하는 대의 문까지 열어 버린다.

### 3.3 문이 스스로 퍼짐

**새 신호를 안 만든다. 문 자체가 신호다.**

```
A 가 재연결을 감지하고 문을 닫는다
C 의 요청 경로가 Lua 에서 -4 를 받는다        ->  suspect()  ->  C 가 자기 A 단계를 돈다
C 의 플러시 경로가 checkAfterFlush 에서 본다   ->  같다
```

**각 대가 Lettuce 재연결을 따로 감지할 때까지 기다리지 않는다.** 2026-10-13 V-3 에서 두 대의
재건이 **29초** 떨어져 돌았는데, 문을 보고 아는 쪽은 요청 한 번이나 배치 한 번(`batch-window`
20ms) 안이다.

**장벽이 아니라 힌트다.** 트래픽도 배치도 없는 대는 못 보지만, 그 대는 자기 재연결 감시기가
결국 깨운다. 그때 문을 다시 닫고 자기 몫을 한다.

### 3.4 T

```
T  =  전파 시간  +  A 단계 시간  +  여유
      수십 ms       300ms          ->  1초
```

A 단계 실측은 2026-10-14 X-2 의 `rebuildMillis=299` 다 (`contributeMillis=38`,
`readWriteMillis=191`).

### 3.5 한 바퀴

```
t=0      캐시 승격.  A 가 먼저 감지
t=5ms    A 가 문을 닫는다.  이 순간부터 전 인스턴스의 발급이 503
t=20ms   C 가 요청에서 -4 를 받고 자기 A 를 시작.  문이 연장된다
t=30ms   B 도 같다
t=330ms  A 가 끝나고 문을 다시 닫는다
t=350ms  C 가 끝나고 다시 닫는다
t=360ms  B 가 끝나고 다시 닫는다
t=1.36s  마지막 연장으로부터 T 가 지나 문이 열린다
```

**재건이 성공하면 발급 정지가 약 1.36초다.** 그 대가로 어긋난 번호 발급이 0 이 된다.

**실패하거나 느리면 이 수가 안 지켜진다.** 아래 6장이 그 자리다.

## 4. 왜 락이 아니라 시한인가

```java
// 기존 B 단계 락
redisTemplate.opsForValue().setIfAbsent(key, token, lockTtl);   // SET key token NX EX 30

// 문
redisTemplate.opsForValue().set(key, "1", Duration.ofMillis(T)); // SET key 1 PX T
```

| | 락 (`NX`) | 문 (덮어쓰기) |
|---|---|---|
| 뜻 | 내가 그 일을 맡는다 | 지금은 발급하면 안 된다 |
| 겹치면 | 둘째가 실패한다 | 둘째가 시한을 연장한다 |
| 쥔 대가 죽으면 | TTL 까지 막힌다. 지금 30초다 | T 뒤에 열린다 |
| 푸는 주체 | 토큰이 맞는 대만 | 없다. 시간이 연다 |

**연장이 공짜로 되는 것이 `NX` 를 안 쓰는 이유다.** `NX` 면 첫 대만 성공해서, 나중에 깬 대가
아직 복구 중인데 문이 열린다.

**`SET` 은 TTL 을 지우므로 매번 `PX` 를 같이 줘야 한다.** 안 주면 시한 없는 키가 되어 그 쿠폰의
발급이 영영 막힌다. 이 저장소는 반대 방향으로 한 번 밟았다. `coupon-open-gate.lua` 에서 `SET`
이 카운터의 만료를 지워 `KEEPTTL` 을 붙였다. **문은 연장돼야 하고 카운터는 수명이 보존돼야 한다.**

## 5. main 과 무엇이 같고 다른가

**같아지는 것은 하나다. 재건 중 발급을 막는다.** #242 의 간판이던 "재건이 발급을 멈추지
않는다" 를 버리는 것이고, 그 사실을 숨기지 않는다.

| | main | 이 설계 |
|---|---|---|
| 명부 `coupon:instances` | 있다 | **없다** |
| 기여 수집 `rebuild:queued` / `rebuild:done` | 있다 | **없다.** 각자 자기 큐를 직접 쓴다 |
| `rebuild-contribute-wait` 3초 | 있다 | **없다** |
| 플러시 정지 `pause` / `resume` | 있다 | **없다.** `NX` 쓰기가 대신한다 |
| 카운터 | 주도자가 전역 계산해 한 번 쓴다 | 각자 단조 증가로 올린다 |
| 문이 열리는 조건 | 주도자가 락을 풀 때 | 시한 T |

**이 세션의 결함 다섯이 전부 위 표의 위 세 줄에서 났다. 그것은 안 돌아온다.**

### 나빠지는 것

**main 은 일찍 열 수 있었고 이 설계는 못 연다.**

```
X-2 의 실측
  rebuildMillis=299  contributeMillis=38  waitMillis=69  readWriteMillis=191
```

`waitMillis=69` 가 요점이다. 기여 대기는 상한이 3초지만 **전원이 보고하면 69ms 만에 끝났다.**
세는 기계의 값어치가 거기 있다.

```
main      문이 약 300ms 닫혔다.  전원 완료를 알고 바로 열었다
이 설계    문이 T 동안 닫힌다.    일찍 못 연다
```

**세기를 버린 대가가 그것이다.** 발급 정지가 300ms 에서 약 1.4초로 는다.

## 6. 정지 예산

**T 만으로는 정지 시간이 안 묶인다.** 5.1 의 1.36초는 재건이 한 번에 성공했을 때의 수다.

```
재건 한 번이 Redis 를 치는 횟수
  HSET seq (500개씩)        발급 1만이면 20회
  HSETNX + ZADD 파이프라인    큐 깊이 / 500
  EVALSHA, TTL, 락, 카운터    열 번 안팎
                            합쳐서 서른 번 안팎
```

**명령 단위 타임아웃은 이 총합을 못 묶는다.** 명령마다 `CouponSeqRebuildRedis` 의 상한 3초
아래로 느리기만 하면 **아무것도 안 터지면서 총합이 분 단위로 는다.** 그동안 문이 닫혀 있다.

그리고 재시도가 그것을 더한다. 각 시도가 시작할 때 문을 다시 닫기 때문이다.

### 회로로 안 묶이는 까닭

**회로는 호출을 자르지 않는다.** 통계를 보고 다음 호출을 막을 뿐이라, **진행 중인 재건의
벽시계를 못 묶는다.** 창이 차서 회로가 열릴 때쯤이면 이미 수십 초를 쓴 뒤다.

게다가 이 저장소는 그 함정을 한 번 밟았다. 발급 쪽 `couponSeq` 회로가 지금 `METRICS_ONLY`
인데, 까닭이 **GC 정지 104~330ms 가 느림 기준 50ms 를 늘 넘어서 Redis 가 멀쩡해도 느린 것으로
세어지기 때문**이다. 재건 쪽에 회로를 달면 같은 문제가 그대로 걸린다.

### 벽시계 상한

```
coupon.issue.rebuild-stall-budget: 5s
```

재건이 단계 사이에서 이 예산을 확인하고, 넘으면 **그만두고 문을 시한에 맡긴다.**

```
최악의 발급 정지  =  정지 예산 5초  +  문 시한 1초  =  6초
```

**예산 초과는 재시도하지 않는다.** 다시 돌면 그 시도가 문을 또 닫아 정지가 예산 너머로
늘어난다. `CouponSeqStallBudgetException` 을 따로 둔 이유가 그것이다.

**그만두면 그 쿠폰은 재건이 없던 때와 같은 상태로 남는다.** 뒤로 간 카운터가 그대로면 결번이
난다. **결번을 받아들이고 가용성을 지키는 선택이고**, 그 선택이 일어난 것은 로그에 남는다.

```
COUPON_SEQ_STALL_BUDGET_EXCEEDED   어느 단계에서 넘겼나
COUPON_SEQ_REBUILD_ABANDONED       그만뒀다
```

**5초의 근거는 약하다.** 재건 실측 299ms 의 열몇 배라는 것뿐이다. 회차에서 발급 정지를 재서
다시 정해야 한다.

## 7. 남는 위험

**T 안에 문을 못 본 대가 있으면 그 대의 회원은 여전히 순서를 잃는다.** 트래픽도 배치도 없어
`-4` 를 못 보고 자기 재연결 감지도 늦은 대다.

**그 수는 그 대의 큐 깊이만큼이고, 트래픽이 없다는 것은 큐도 얕다는 뜻이다.** 두 조건이 같은
방향이라 위험이 스스로 작아진다. 다만 0 은 아니다.

**이것은 보장이 아니라 "T 안에 들어온 대까지의 보장" 이다.** 0 을 원하면 명부를 세야 하고,
그 기계가 이 세션에서 다섯 번 깨졌다. 그 교환을 알고 고른다.

## 8. 재야 할 것

지난 회차가 판정 지표에 한 번 속았으므로 재는 것을 먼저 적는다
(`rounds-2026-10-14.md` 3장).

| 재는 것 | 왜 |
|---|---|
| **순번 역전 건수** | 이 설계의 목적이다. 받은 번호보다 큰 번호로 끝난 회원을 DB 로 센다 |
| **`resolveDuplicate` 호출 수** | 어긋난 번호 발급 수다. 0 에 가까워지는 것이 성능 쪽 이득이다 |
| 발급 정지 시간 | 문이 닫혀 있던 시간. 이 설계가 치르는 값이다 |
| 문 전파 시간 | A 가 닫은 뒤 마지막 대가 닫기까지. T 를 정하는 근거다 |
| 결번 | Y-2 의 404 가 줄어야 한다 |
| `http_req_duration` p99 | `settled` 단독은 모집단이 깎여 속는다 |

**순번 역전 건수가 0 이 아니면 이 설계는 목적을 달성하지 못한 것이다.** 그리고 **그 수를 지금까지
한 번도 안 쟀다.** 순서가 실제로 얼마나 깨지고 있었는지 아직 모른다.
