# 선착순 쿠폰: `reclaim-after` 를 얼마로 둘까

**세 값을 재고 60초를 유지하기로 했다.** 값은 안 바뀌었고 **근거가 바뀌었다.**

```
전    요청 예산(800ms)보다 길어야 한다
후    장애가 끝나고 회로가 닫히는 구간보다 길어야 한다
```

**둘의 차이가 수십 배다.** 약한 쪽만 적혀 있어서 10초로 내렸다가 발급이 깨졌고, 그 회차가
이 문서의 근거다.

---

## 1. `reclaim-after` 가 무엇인가

**`pending` 키의 TTL 이 아니다. 판정 기준선이다.**

```lua
local cut = now - tonumber(ARGV[3])                              -- ARGV[3] = reclaim-after
local stale = redis.call('ZRANGEBYSCORE', KEYS[4], 0, cut, 'LIMIT', 0, 1)
```

`pending` 은 정렬집합이고 **점수가 번호를 내준 시각**이다. 이 값보다 오래된 항목을 "번호만
받고 사라진 요청" 으로 보고 그 번호를 다른 회원에게 준다.

**소진 시점에만 돈다.** 재고가 남아 있으면 `INCR` 로 새 번호를 주고, 다 나간 뒤에야
`pending` 을 뒤진다. 평상시에는 이 경로의 비용이 없다.

---

## 2. 왜 회복 구간이 하한인가

**회수에는 가드가 있다.** 확정 표시가 붙은 번호는 발급이 끝난 것이라 건너뛴다.

```lua
if seq and not string.find(seq, ':') then   -- ':' 가 확정 표시다
  redis.call('HDEL', KEYS[1], stale[1])
  return give(seq)                          -- 남에게 준다
end
```

**그 표시를 붙이는 `markCommitted` 도 Redis 호출이다.** Redis 가 죽으면 가드가 무력해진다.

```
1. 큐에 있던 티켓은 DB 에 잘 써진다              DB 는 멀쩡하다
2. markCommitted 가 실패한다                    Redis 가 안 닿는다
3. 확정 표시가 안 붙고 pending 에도 남는다
4. 그 항목의 점수는 번호를 받은 옛 시각 그대로다
5. Redis 가 돌아오면 그 항목이 오래된 것으로 보인다
6. 가드가 확정 표시를 못 찾아 회수 대상으로 판정한다
7. 이미 DB 에 있는 번호를 남에게 준다  ->  두 유니크 제약에 걸린다
```

### 페일오버 시간보다 긴 회복 구간

**캐시 페일오버 실측이 20~21초인데, 순번 확보가 막힌 구간은 45초를 넘었다.**

**가로축은 장애를 주입한 순간(캐시 페일오버를 부른 시각) 기준이다.**

```
주입 대비   발급      seq-unavail   already-issued   seq-taken   db-failed
   +0초     1,427         -              -             -           -
  +15초     5,064      6,312             -             -           -
  +30초        -       10,422            -             -           -
  +45초        -       13,202            -             -           -
  +60초    11,206      1,960           213            24           2
```

**두 국면으로 갈린다.**

```
+15 ~ +45초   순번 확보가 통째로 막힌다.  번호가 안 나가니 충돌도 없다
+60초         회로가 닫히며 밀린 것이 쏟아진다.  실패 셋이 전부 여기 몰린다
```

**차이가 회로다.** 캐시가 21초에 돌아와도 회로는 `waitDurationInOpenState` 3초를 기다렸다가
반열림으로 30건을 시험하고서야 닫힌다. **그리고 닫히는 순간 밀린 요청과 재시도가 한꺼번에
들어와 같은 회원의 요청이 겹친다.**

**`reclaim-after` 가 이 구간 안에 들어오면 깨진다.**

---

## 3. 세 값의 계측

**조건은 같다.** 캐시 Multi-AZ 페일오버를 발급 50% 지점에 걸고 종합 구성(`queue-capacity`
2,000)에 `reclaim-after` 만 바꿨다.

| `reclaim-after` | DB 발급 | `gap` | `already-issued` | `seq-taken` | SLO p99 | 판정 |
|---|---:|---:|---:|---:|---:|---|
| **60초** | 9,989 | 11 | **0** | **0** | **1.041초** | **유지** |
| 30초 | 9,997 | 3 | 129 | 14 | 1.889초 | 쓰지 않는다 |
| 10초 | 9,405 | 591 | 476 | - | - | 깨진다 |

### `gap` 으로 고르지 않은 이유

**`gap` 만 보면 30초가 나아 보인다** (3 대 11). 그런데 **그 차이는 시험 길이의 산물이다.**

```
회차 길이      90초 (ramp 60 + hold 30)
번호가 탄 때    장애 주입 +60초 = k6+77초
회수 가능       +60초 뒤 = k6+137초
회차 종료       k6+90초
```

**회수가 돌 창이 애초에 없었다.** 게다가 `issue.js` 는 결판난 VU 가 잠들어 다시 안 쏘므로,
**램프가 끝난 뒤에는 회수를 깨울 요청 자체가 없다.**

**못 회수한 번호는 운영에서 회수된다.** 이벤트가 몇 분 이상 돌고 요청이 계속 들어오기
때문이다. **90초짜리 시험에서만 남는 값이라 채택 근거로 못 쓴다.**

### 실재하는 차이, p99 와 충돌

```
60초   already-issued   0건   seq-taken  0건   p99 1.041초
30초   already-issued 129건   seq-taken 14건   p99 1.889초   81% 나쁘다
```

**30초는 회수가 회복 구간 끝자락에 걸려 살아 있는 번호를 뺏었다.** 그 충돌이 재시도를 불러
지연을 키웠다. **혼잡은 오히려 적은데(27,372 대 52,667) p99 가 나쁘다.** 거절을 덜 하고
붙들고 있었다는 뜻이다.

### 10초는 왜 깨지나

**회복 구간 한복판에서 돈다.** `already-issued` 476건에 `congested-queue-full` 4,309건이
났다. **회수를 돌게 만들려다 회수가 스스로 번호를 태우게 만들었다.**

---

## 4. `gap` 은 무엇으로 이루어지나

**30초 회차의 `gap` 3 을 뜯어 보면 이렇다.**

```
1건   congested-db-failed        지표로 확인됨.  반납 경로를 안 탄다
2건   Redis 응답 유실로 추정      지표로 확인 불가
```

**반납되는 것은 `gap` 을 안 만든다.**

```
129건  already-issued    returnAndRepairs 가 free 에 돌려놓는다.  다시 나간다
 14건  seq-taken         남이 쓰는 번호라 애초에 gap 이 아니다
```

**설계가 의도대로 돌았다.** 143건이 반납 경로를 타고 되돌아왔고, 못 되돌린 것은 **반납할
대상을 앱이 모르는 2건과 DB 가 거부한 1건**뿐이다.

### 앱이 모르는 경우가 왜 생기나

```
1. 앱이 순번 확보 스크립트를 호출한다
2. Redis 가 카운터를 올리고 pending 에 등록한다   <- 번호가 소비됐다
3. 페일오버로 연결이 끊기거나 100ms 타임아웃에 걸린다
4. 앱은 실패로 보고 congested-seq-unavailable 로 센다
5. 티켓을 안 만들었으니 반납할 대상도 모른다
```

**원리상 앱이 알 수 없다.** 네트워크 너머 호출이라 "안 됐다" 와 "됐는데 못 들었다" 를 구분할
방법이 없다. **그래서 회수가 뒤처리를 맡는 구조다.**

---

## 5. 더 내리려면 먼저 잴 것

```
회로가 닫히고 밀린 것이 다 빠지기까지 걸린 시간
```

**이 값이 진짜 하한이다.** 지금은 그 지표가 없어서 시간축을 눈으로 읽어 45~60초로 잡고 있다.

**재려면 회로 상태 전이 시각과 큐 길이가 0 으로 돌아온 시각을 함께 내야 한다.**

---

## 6. 회수를 제대로 시험하려면

**지금 시험으로는 회수가 도는 것을 못 본다.** 결판난 VU 가 잠들어 요청이 끊기기 때문이다.

```
k6+0 ~ 30초    발급이 나가고 소진된다
k6+30 ~ 60초   남은 VU 가 뜨면서 410 을 받고 잠든다
k6+60초 이후   램프가 끝나 새 VU 가 없다.  이미 뜬 VU 2만은 전부 잠들어 있다
               요청이 0 이다
```

**`HOLD` 를 늘려도 안 된다.** 잠든 VU 는 깨어나도 `settled` 를 보고 바로 다시 잔다.

**소진 응답을 받은 VU 가 가끔 다시 쏘게 만드는 것**이 요구 조건을 안 깨는 방법이다. 실제
사람도 이벤트가 도는 동안 몇 번 더 새로고침한다. 다만 **"몇 초마다 몇 번" 이 회수 측정
결과를 좌우하므로 그 값을 먼저 정해야 한다.**
