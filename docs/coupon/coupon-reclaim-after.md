# 선착순 쿠폰: `reclaim-after` 를 얼마로 둘까

**회수 기준 시간을 세 값으로 재고 30초로 정했다.** 근거가 바뀐 것이 값이 바뀐 것보다 크다.

```
전    요청 예산(800ms)보다 길어야 한다
후    Redis 다운타임보다 길어야 한다
```

**둘의 차이가 20배다.** 약한 쪽만 적혀 있어서 10초로 내렸다가 망가뜨렸고, 그 회차가 이
문서의 근거다.

---

## 1. `reclaim-after` 가 무엇인가

**`pending` 키의 TTL 이 아니다. 판정 기준선이다.**

```lua
local cut = now - tonumber(ARGV[3])                              -- ARGV[3] = reclaim-after
local stale = redis.call('ZRANGEBYSCORE', KEYS[4], 0, cut, 'LIMIT', 0, 1)
```

`pending` 은 정렬집합이고 **점수가 번호를 내준 시각**이다. 이 값보다 오래된 항목을 "번호만
받고 사라진 요청" 으로 보고 그 번호를 다른 사람에게 준다.

**소진 시점에만 돈다.** 재고가 남아 있으면 `INCR` 로 새 번호를 주고, 다 나간 뒤에야
`pending` 을 뒤진다. 그래서 평상시에는 이 경로의 비용이 없다.

---

## 2. 왜 다운타임이 하한인가

**회수에는 가드가 있다.** 확정 표시가 붙은 번호는 실제로 발급이 끝난 것이라 건너뛴다.

```lua
if seq and not string.find(seq, ':') then   -- ':' 가 확정 표시다
  redis.call('HDEL', KEYS[1], stale[1])
  return give(seq)                          -- 남에게 준다
end
```

**그 표시를 붙이는 `markCommitted` 도 Redis 호출이다.** 그래서 Redis 가 죽으면 가드가
무력해진다.

```
1. 큐에 있던 티켓은 DB 에 잘 써진다              DB 는 멀쩡하다
2. markCommitted 가 실패한다                    Redis 가 안 닿는다
3. 확정 표시가 안 붙고 pending 에도 남는다
4. 그 항목의 점수는 번호를 받은 옛 시각 그대로다
5. Redis 가 돌아오면 그 항목이 오래된 것으로 보인다
6. 가드가 확정 표시를 못 찾아 회수 대상으로 판정한다
7. 이미 DB 에 있는 번호를 남에게 준다  ->  두 유니크 제약에 걸린다
```

**즉 다운타임 동안 커밋된 티켓들이 통째로 "버려진 것" 으로 보인다.** 다운타임이 길수록
그 수가 는다.

---

## 3. 세 값을 쟀다

**조건은 같다.** 캐시 Multi-AZ 페일오버를 발급 50% 지점에 걸고, 종합 구성(`queue-capacity`
2,000)에 `reclaim-after` 만 바꿨다.

| `reclaim-after` | 발급 | `gap` | `already-issued` | `congested-seq-taken` | 판정 |
|---|---:|---:|---:|---:|---|
| 60초 | 9,989 | 11 | **0** | 0 | 안전 |
| **30초** | **9,997** | **3** | 129 | 14 | **채택** |
| 10초 | 9,405 | 591 | **476** | - | 깨진다 |

**`already-issued` 와 `congested-seq-taken` 이 판정 지표다.** 둘은 회수가 살아 있는 번호를
뺏었을 때만 난다.

### 10초는 왜 깨지나

**페일오버가 20~21초인데 기준선이 10초다.** 다운타임 동안 커밋된 티켓이 전부 회수 대상이
된다. `already-issued` 476건이 그 결과이고, `congested-queue-full` 도 4,309건 났다.
**회수를 도게 만들려다 회수가 스스로 번호를 태우게 만들었다.**

### 30초가 60초보다 나은 이유

```
60초   gap 11   회수가 돌 창이 없었다.  버려진 번호가 안 돌아왔다
30초   gap  3   회수가 돌았고 대부분 메웠다
```

**60초는 안전하지만 늦다.** 회차가 90초라 60초 기준선을 넘긴 항목이 생길 시간이 거의 없었다.
30초는 그 창을 만들면서도 다운타임(21초)보다 길다.

**대가가 없지는 않다.** 30초에서 `already-issued` 129건과 `congested-seq-taken` 14건이
났다. **60초의 0건보다 나쁘다.** 다만 그 대가로 `gap` 이 11에서 3으로 줄었다.

---

## 4. 30초는 여유가 얇다

```
ElastiCache Multi-AZ 페일오버   20~21초   test-failover 실측 3회
회로 반열림 대기                 3초       waitDurationInOpenState
밀린 markCommitted 처리          미측정
                                ────────
                                24초 이상
```

**`test-failover` 는 통제된 경로다.** 노드가 실제로 죽거나 AZ 장애면 더 걸린다. AWS 는
계획되지 않은 페일오버를 30초 이상으로 본다. **그때는 10초 회차와 같은 일이 난다.**

**그래서 30초는 "계획된 페일오버를 견디는 값" 이지 "어떤 장애든 견디는 값" 이 아니다.**

---

## 5. 더 내리거나 올리려면 먼저 잴 것

```
장애 중 pending 항목이 확정 표시를 받기까지 걸린 시간
```

**이 값이 진짜 하한이다.** 지금은 그 지표가 없어서 페일오버 시간으로 대신 잡고 있다.

**재려면 `markCommitted` 성공까지의 지연을 티켓 단위로 내야 한다.** 지금은 실패 건수만
세고(`coupon.seq.cleanup.failures`) 지연은 안 센다.

---

## 6. 함께 확인한 것

### 발급 50% 지점은 첫 발급 +15초다

**장애 주입 시점의 근거다.** 여섯 회차가 전부 같았다.

```
첫 발급       0초
25%         5~10초
50%          15초      6회차 동일
100%        25~30초
```

**k6 기동이 2초라 `k6+17초` 가 50% 지점이다.** 추정으로 고른 값이었는데 실측과 맞았다.

### 회수는 재시도가 없으면 안 돈다

**소진 뒤에 들어온 요청이 있어야 회수가 돈다.** `issue.js` 가 502 를 최종으로 처리하던
때에는 장애로 실패한 사람이 그대로 사라져 **그 경로가 영영 안 돌았다.**

**502/504 재시도를 넣고 나서야 회수가 처음 시험됐다.**
