```
앱         fm-backend main ca37c3c9 (#184 릴리스)
```

## 2. 계측이 평상시에 조용하다

회차 1과 3은 아무것도 안 넣고 돌렸다. 세 대 전부 `COUPON_SEQ_COUNTER_BEHIND` 가 0건이고 숫자를 못 읽은 경우도 0건이다.

```
회차 1   BEHIND 0 / UNREADABLE 0 / SEQ_TAKEN 0 / REBUILD 0   (세 대 전부)
지표     coupon_seq_counter_behind_count = 0
k6       1,168,639 요청, 실패 0.00%, p99 262.28ms
```

**지표가 계열로는 있고 표본이 0이다.** "안 재는 것" 과 "재서 0인 것" 이 갈린다. 계량기를 기동 때 다 만들어 두는 규칙이 여기서 값을 한다.

**이것이 자동 재건을 붙이기 전에 필요했던 확인이다.** 재건은 그 이벤트의 플러시를 3초 넘게 멈추므로 오탐이 곧 장애다.

## 3. 뒤처짐을 실제로 잡는다

회차 4에서 `counter` 를 200 뒤로 보냈다. 세 대가 정확히 1건씩 남겼다.

```
i-07cb  counter=9973 seen=10000 gap=27
i-07a8  counter=9973 seen=9996  gap=23
i-0ba2  counter=9950 seen=9998  gap=48
```

**gap 이 200 이 아닌 것은 줄어서가 아니라 늦게 봐서다.** `DECRBY 200` 직후 부하의 `INCR` 이 카운터를 곧바로 밀어 올려, 플러시가 다음 배치에서 볼 때는 9,800 에서 9,973 까지 회복돼 있었다. **그래도 자기가 본 최댓값보다는 낮아 잡혔다.** 여태 본 최댓값을 들고 있는 설계가 여기서 값을 한다.

피해 신호는 주입량과 정확히 같다.

```
COUPON_ISSUE_SEQ_TAKEN     67 + 67 + 66 = 200
COUPON_SEQ_TAKEN_REPAIRED  3 + 3 + 3
```

**재건은 한 번도 안 걸렸다.** `counter` 가 있으니 `-2` 가 안 난다. 막은 것은 앱이 아니라 `uk_mc_coupon_seq` 이고, 그런데도 재고 10,000장이 정확히 다 나갔다.

## 4. DB 가 막혀도 기여한다

회차 2에서 세 대의 DB 를 막고 한 대만 풀어 재건을 이끌게 했다.

```
i-07cb (주도자)   CONTRIBUTED 1    size 0     lagMillis 5
i-07a8 (DB 막힘)  CONTRIBUTED 3    size 231   lagMillis 864
i-0ba2 (DB 막힘)  CONTRIBUTED 330             lagMillis 3185
```

**`size=231` 이 증거다.** DB 에 못 닿는 인스턴스가 자기 큐 231건을 올렸다. 고치기 전이라면 `findById` 에서 터져 0건이었다([앞 회차](rebuild-measurement-2026-09-21b.md) 3장).

## 5. 3초가 여유 있는 값이 아니다

기여 지연 분포를 처음 얻었다.

```
표본     334건
합계     541.952초
평균     1.62초
최대     3.202초
```

**`rebuild-contribute-wait` 가 3초인데 최댓값이 그것을 넘었다.** 창이 닫힌 뒤에 도착한 기여가 있었다는 뜻이고, 그 회차의 재건은 그 큐를 못 받고 카운터를 세웠다.

이 회차는 DB 를 세 대 모두 막은 극단이라 값을 그대로 운영으로 옮길 수는 없다.

**그리고 이 수치만으로는 3초를 어떻게 할지 못 정한다.** 기여 지연은 총합이라 그 안에 셋이 섞여 있다. 불리기까지 기다린 시간, 돌던 배치가 끝나기를 기다린 시간, 실제로 훑고 쓴 시간이다. **셋의 처방이 정반대다.** 마지막 것이 크면 3초는 맞는 값이고, 첫째가 크면 고칠 자리는 대기가 아니라 늦게 불리는 이유다.

**`flusher.pause` 가 시한을 다 쓴 것은 아니다.** 그 대기가 실패하면 기여를 건너뛰고 `COUPON_SEQ_CONTRIBUTED` 를 아예 안 남기는데, 로그가 남았으므로 멈추기는 성공했다. 나머지 둘 중 어느 쪽인지는 이 회차의 계측으로 못 가른다. **총합 하나만 재고 있었기 때문이다.**

## 6. 재개설이 계측을 속인다

**회차 2의 뒤처짐 730건은 전부 오탐이다.** 가장 이른 것이 주입보다 26초 앞선다.

```
11:07:57  counter=63  seen=10000  gap=9937      주입은 11:08:23
```

`seen=10000` 은 앞 회차가 남긴 값이다. 이벤트를 발급 이력째 다시 준비했는데, 그 사이에 부하가 없어 **플러시가 카운터 부재를 관측하지 못해 기준이 안 버려졌다.**

운영에서는 안 나는 모양이다. 한 이벤트를 발급 이력을 지우고 다시 준비하는 일이 없기 때문이다. **다만 회차를 이어 돌릴 때는 인스턴스를 재시작해 기준을 비워야 한다.** 회차 4는 그렇게 하고 돌렸다.

고치려면 준비 시점이 기준을 무효로 만들어야 한다. 관리자 API 가 카운터를 다시 세울 때 그 사실을 앱이 알 수 있어야 하는데, 지금은 알 길이 없다.

## 7. 다음에 할 것

1. **자동 재건을 붙인다.** 평상시 0건을 확인했으므로 이제 근거가 있다. 다만 `gap` 이 얼마일 때 띄울지를 정해야 한다. 회차 4에서 실제 어긋남이 23에서 48 사이로 관측됐다
2. **`rebuild-contribute-wait` 를 다시 본다.** 3초가 최댓값을 못 덮었다. 정상 부하에서의 분포를 따로 재서 극단과 갈라야 한다
3. 준비 시점이 계측 기준을 무효로 만들게 한다(6장)
4. 주기 정합성 검증에도 같은 식을 넣는다. 플러시가 안 도는 구간의 안전망이다
