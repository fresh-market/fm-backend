# 조기 종료를 붙이고 돌려 본 회차 (2026-09-22)

팀은 주도자가 고정으로 3초를 자던 것을 **다 모이면 끝내도록** 바꾸고 AWS 에서 세 회차를 돌렸다.

```
AWS 실측   20,000 VU / ramp 60초 / 재고 10,000장 / 전용 인스턴스 3대
앱         fm-backend main c40cc532 (#187 릴리스)
```

## 2. 3.202초의 정체는 기다림이 아니었다

앞 회차에서 기여 지연 최대가 3.202초였는데 **팀은 그 안을 못 갈랐다.** 팀이 구간을 셋으로 나누고 다시 재니 답이 한 번에 나왔다.

```
pause    전부 0ms         플러시 멈추기는 즉시 끝난다
write    0~21ms          큐를 훑어 Redis 에 쓰는 것은 순식간이다
wait     203~3,158ms     전부 여기다
```

**`flusher.pause` 가 시한을 다 쓴다던 첫 설명은 완전히 틀렸다.** `pause` 는 0ms 다. 기여는 **불리기만 하면 1밀리초 안에 끝난다.** 오래 걸린 것은 주도자가 그 인스턴스를 부르기까지였다.

**다만 세 대가 고르게 늦은 것도 아니다.**

```
주도자 i-03b0   기여 1건     lag 15ms
비주도 i-05c0   기여 307건   lag 최소 213ms   중앙 1,727ms
비주도 i-01ae   기여 44건    lag 최소 2,871ms 중앙 3,009ms
```

한 대는 213밀리초 만에 올렸고 한 대만 2,871밀리초가 걸렸다. **"다른 쿠폰의 대기에 줄 서 있었다" 던 가설이라면 셋이 비슷해야 하므로, 그 설명도 맞지 않는다.** 늦은 쪽은 `COUPON_SEQ_REBUILD_FAILED` 를 10건 내며 주도자가 되려다 실패를 반복했다.

## 3. 조기 종료는 돌았지만 아낀 것이 적었다

팀의 회차 2가 이렇게 끝났다.

```
COUPON_SEQ_CONTRIBUTIONS_COMPLETE couponId=900001 instances=3 waitedMillis=2848
```

**명부가 세 대를 세었고 주도자가 다 차자 끝냈다.** 그것이 팀의 설계대로다.

**그런데 주도자가 3,000 대비 152밀리초만 아꼈다.** 가장 느린 한 대가 2,871밀리초였기 때문이다. **병목이 대기가 아니라 그 한 대의 감지였다.**

조기 종료는 "다 모였는데도 기다리는" 낭비를 없애는 장치다. 인스턴스가 실제로 늦게 모이면 주도자가 아낄 것이 없다.

## 4. DB 장애가 길면 명부가 통째로 빈다

회차 3이 이것을 드러냈다. **이 회차에서 가장 값진 결과다.**

```
COUPON_SEQ_CONTRIBUTIONS_TIMEOUT couponId=900001 instances=0 done=3 waitedMillis=3000
```

**셋이 다 올렸는데(`done=3`) 명부가 0 을 주어 주도자가 못 끝냈다.**

원인은 두 값이 부딪힌 것이다.

```
STALE_AFTER   10초    이보다 오래 갱신이 없으면 죽은 것으로 본다
주입           10초    DB 를 이만큼 막았다
```

명부 갱신이 `checkAfterFlush` 에 있었고 그것은 `flush(batch)` **뒤**다. DB 가 막혀 배치가 안 끝나니 갱신도 멈췄고, 10초가 지나 **세 대 모두 명부에서 빠졌다.**

**설계의 전제가 깨진 자리다.** 팀은 앞서 이렇게 적었다.

> 플러시 루프는 큐에 티켓이 있을 때만 한 바퀴를 마치므로, 갱신이 신선하다는 것이 곧
> "이 인스턴스가 지금 큐를 쥐고 있다" 와 같아진다.

**DB 장애에서는 인스턴스가 큐를 쥐고 있는데도 갱신이 멈춘다.** 그리고 하필 그때가 큐가 두꺼워 기여가 가장 중요한 순간이다.

### 안전 규칙이 막아 주었다

팀이 `instances` 가 0 일 때 "다 모였다" 로 읽지 않고 주도자가 천장까지 기다리게 해 둔 것이 정확히 이 상황을 막았다. **주도자가 덜 기다렸으면 재건이 그 인스턴스가 쥔 번호를 남에게 다시 내줬을 것이다.**

**모르면 안 줄인다는 규칙이 실제로 값을 한 첫 사례다.**

### 팀이 고친 방법

팀은 갱신을 **쓰기보다 먼저** 하게 옮겼다. 플러시가 배치를 집은 직후에 `holdingQueue()` 를 부른다. 큐를 쥐었다는 사실은 DB 쓰기 성공과 무관하기 때문이다.
