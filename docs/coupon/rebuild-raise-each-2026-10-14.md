# 카운터는 각자 올리고 기다림은 안전 경로에서 빼는 설계

재건을 아홉 번 고치는 동안 결함이 매번 자리를 옮겼다. 2026-10-12 에 합의를 통째로 걷는 재설계를
했다가 `free` 를 함께 버려 되돌렸고, 2026-10-13 에 `-4` 만 따로 들였더니 재건 횟수가 안 줄었다.

**이 문서는 그 둘에서 살아남은 것만 골라 붙인다.** 코드는 아직 안 고쳤다.

---

## 1. 지금 구조

재연결을 본 인스턴스가 각자 재건을 띄우고, 그 뒤에 락으로 갈린다.

```
락을 잡은 한 대    플러시를 멈추고, 기여를 모으고, 네 키를 다 세우고, 문을 연다
못 잡은 나머지     플러시를 멈추고, 자기 큐를 rebuild:queued 에 올리고, done 에 이름을 남긴다
```

**카운터를 쓰는 것은 주도자 하나뿐이다.** 나머지는 자기 큐만 올린다.

**발급은 락이 있는 동안 멈춘다.** 순번 확보 Lua 첫 줄이 락을 보고 `-2` 를 낸다. 그것은
의도된 설계다. 재건이 네 키를 다시 세우는 사이에 번호가 나가면 그 번호가 어느 쪽에도 안 잡혀,
재건이 아무도 안 쥔 것으로 보고 `free` 에 넣어 남에게 내준다.

### 1.1 그 비용

| 회차 | 장애 | 재건 횟수 | 플러시 정지 |
|---|---|---:|---:|
| N-2 | 캐시 페일오버 | 2 | 0.960초 |
| P-1 | 복합 | 2 | **1.287초** |
| O-1 | 순번 키 유실 | 1 | 0.327초 |
| V-3 | 캐시 페일오버 | 2 | 0.942초 |

**정지가 그 이벤트의 발급을 통째로 멈춘다.** P-1 의 복합 발급량 9,542 가 그 1.287초의 값이고,
같은 장애에서 F-3 은 9,868 을 냈다.

## 2. 회차가 가른 것

### 2.1 카운터를 각자 올려도 수렴함

2026-10-12 U-1 에서 **세 대가 16밀리초 안에 각자 복구를 돌았고 카운터가 최댓값으로 수렴했다.**

```
i-032497d   dbMax=7945  mark=7944  bound=7945  ->  counter=7945
i-06135fb   dbMax=7945  mark=7947  bound=7947  ->  counter=7948
i-0f5f3f1   dbMax=7945  mark=7945  bound=7945  ->  counter=7949
```

**`counter=` 는 쓴 뒤의 값이다.** 셋째 대는 7,945 를 쓰려 했는데 7,949 를 돌려받았다. 남이
이미 더 높게 세워 둔 것이고, **낮은 값이 높은 값을 덮지 못하는 성질이 실측으로 작동했다.**

**U-1 과 U-2 는 결번 0 에 재고 10,000 이다.** 키 부재 경로에서 이 방식이 깨지지 않았다.

### 2.2 `free` 를 걷으면 승격에서 결번이 남

| 회차 | 판 | 결번 |
|---|---|---:|
| U-3 | `free` 를 걷은 판 | 42 |
| U-5 | 같은 판, 복합 | 20 |
| V-1 | 같은 판 | 3 |
| V-2 | 같은 판 | 1 |
| V-3 | `free` 를 되살린 판 | **0** |

**V-3 의 첫 재건이 `freed=310` 을 되살렸다.** 그래서 결번 0 이다.

**크기는 변동이 크다** (42 / 20 / 3 / 1). 한 점을 원인의 크기로 삼으면 안 된다.

### 2.3 `-4` 가 재건 횟수를 못 줄임

2026-10-13 V-3 에서 **두 번 돌았고 지표로도 확인됐다** (각 대 1회, 합 0.942초).

```
11:26:22.038  i-074e81a0  REBUILT maxSeq=6775  queued=3  freed=310   724ms
11:26:50.577  i-0201921f  REBUILD_STARTED                            29초 뒤
11:26:50.756  i-0201921f  REBUILT maxSeq=9723  queued=0  freed=0     177ms
```

**두 현상이 다르다.**

```
-4 가 막는 것    재건 중 -2 를 받은 요청이 재건을 또 띄우는 자기호출 고리     Q-1 의 네 번
V-3 의 두 번     인스턴스별 재연결 감시가 29초 간격으로 각자 울린 것
```

**막는 장치 셋이 후자를 다 통과한다.** `inProgress` 는 JVM 안의 맵이고, 락은 동시 실행만 막고,
`minInterval` 은 인스턴스마다 따로 센다.

## 3. 바꾸는 축

**카운터와 `free` 를 가른다.**

```
counter = max(DB 의 MAX(issue_seq),  각 인스턴스가 받아 본 최댓값)
free    = 1..최댓값  빼기  (DB 행 ∪ 모든 큐)
```

**왼쪽은 각 항이 지역 정보다.** 올리기만 하는 값이라 각자 자기 항만 올려도 결과가 전체
최댓값으로 수렴한다. **기다릴 대상이 없다.**

**오른쪽만 전역 시야를 요구한다.** 내 큐만 빼고 세우면 남이 쥔 번호를 되살려 같은 번호가 두 번
나간다. 2026-10-10 J-4 의 결번 180 이 그 모양이었다.

**그래서 기다림을 없애지 않고 안전 경로에서 뺀다.** 문을 여는 것은 카운터이고, `free` 는 문을
여는 데 필요하지 않다. 카운터가 먼저 서면 발급이 돌아가고 `free` 는 그 뒤에 채워도 된다.

## 4. 절차

### 4.1 재연결을 본 각 인스턴스

```
1. 자기가 받아 본 최대 순번을 꺼낸다
2. DB 에서 MAX(issue_seq) 를 읽는다
3. bound = max(2, 1)
4. coupon-open-gate.lua 로 counter 를 bound 까지 올린다. 올리기만 한다
5. 자기 큐의 티켓을 seq 와 pending 에 되살린다. 둘 다 없을 때만 쓴다
6. 자기 큐를 rebuild:queued 에 올리고 done 에 이름을 남긴다
7. 끝낸다. 플러시를 멈추지 않는다
```

**4 가 끝나면 문이 열려 있다.** 셋이 동시에 돌아도 되고 순서가 무관하다.

### 4.2 락을 잡은 한 대가 더 하는 일

```
8.  락을 잡는다. 못 잡으면 4.1 만 하고 돌아간다
9.  상한 안에서 기여가 다 모이기를 기다린다        rebuild-contribute-wait
10. 큐를 먼저 읽고 DB 를 나중에 읽는다
11. free 를 1..최댓값에서 그 둘을 빼 세운다
12. 네 키에 카운터의 수명을 물려준다
13. 락을 푼다
```

**락은 발급만 막는다.** 플러시와 확정 표시는 9 ~ 12 동안에도 돈다.

### 4.3 락을 언제 푸나

**지금 설계에서 락이 막는 것은 "재건이 free 를 세우는 사이에 번호가 나가는 것" 이다.**
11 이 끝나면 그 이유가 사라진다. 그래서 13 이 11 바로 뒤다.

**모든 인스턴스가 끝날 때까지 쥐지 않는다.** 그 조건은 5장에서 반려한다.

## 5. 멈춤을 뺄 수 있는 근거

**멈춤이 있던 까닭은 기여자가 `seq` 를 덮어쓰기 때문이다.** 훑는 사이에 티켓이 커밋되면 확정
표시 `"N:1"` 을 미확정 `"N"` 으로 덮고, 그러면 회수가 끝난 번호를 뺏는다.

**조건 둘을 지키면 그 덮어쓰기가 구조적으로 안 생긴다.**

| 조건 | 무엇을 막나 |
|---|---|
| `seq` 는 `HSETNX`, `pending` 은 `ZADD NX` | 확정 표시를 미확정으로 덮는 것 |
| 큐를 먼저 읽고 DB 를 나중에 읽는다 | 그사이 넘어간 티켓이 어디에도 안 잡히는 것 |

**둘째가 성립하는 근거는 방향이다.** 티켓은 큐에서 DB 로만 가고 반대로는 안 간다. 큐를 먼저
읽으면 그사이 넘어간 티켓이 양쪽에 다 잡히고, DB 를 먼저 읽으면 어디에도 안 잡혀 결번이 된다.

**`pending` 에 뒤늦게 들어간 항목도 해롭지 않다.** 회수 스크립트가 확정 표시가 붙은 번호는
`pending` 에서만 빼고 되살리지 않는다.

**이 방식은 2026-10-12 재설계에서 구현해 통합 시험으로 고정했다.** 그 코드가 되돌린 커밋
`12e07970` 에 있다.

## 6. 반려한 대안 둘

### 6.1 모든 인스턴스가 끝날 때까지 락을 쥐기

**정지가 지금보다 길어진다.** 지금은 주도자가 문을 연 직후에 락을 푸는데, 모든 대를 기다리면
그만큼 발급이 더 멈춘다. **V-3 에서 두 대의 감지가 29초 벌어졌으므로 최악에는 상한을 꽉 쓴다.**

**그리고 "모두" 를 세는 것이 이 세션에서 다섯 번 실패한 자리다.**

```
N-2  3대인데 명부가 2         주도자가 남을 못 셌다
Q-1  재건 4회                자기호출 고리
S-3  명부가 0, 8밀리초         못 셌다
J-4  결번 180                못 셌다
T-1  instances=0             셀 자격 없는 대가 주도자가 됐다
```

**세는 일을 안전 경로에 두지 않는 것이 이 설계의 요점이다.** 세기가 틀려도 문은 이미 열려 있고,
틀림의 결과는 `free` 가 덜 채워지는 것뿐이다.

### 6.2 연결 확인 주기를 줄이기

**재연결 감시는 주기 폴링이 아니다.** Lettuce 의 끊김과 활성화 이벤트를 받는다.

**`minInterval` 10초는 확인 주기가 아니라 같은 단절에 여러 번 안 띄우게 묶는 값이다.** 줄이면
재건이 더 자주 돈다.

**V-3 에서 두 대의 감지가 29초 벌어진 것은 각 대의 연결이 실제로 끊기고 되살아난 시점 차이다.**
설정으로 못 줄인다.

## 7. 함께 들여야 할 것

### 7.1 `CouponSeqMarks`

**각 인스턴스가 쿠폰마다 받아 본 최대 순번이다.** 4.1 의 1 이 이것을 읽는다. 53줄이고 되돌린
커밋 `12e07970` 에 있다.

**번호 1 을 보면 기억을 버리는 규칙이 핵심이다.** 준비 단계가 카운터를 0 으로 세우므로 1 은 갓
열린 이벤트의 첫 번호다. 안 버리면 같은 쿠폰을 다시 열 때 지난 최댓값까지 건너뛰어
**그만큼의 재고를 통째로 버린다.** 만 장짜리에서 기억이 5,887 이면 4,113장만 나간다.

### 7.2 `KEEPTTL`

**지금 `coupon-open-gate.lua` 의 `SET` 셋에 `KEEPTTL` 이 없다.** 카운터가 네 키의 수명을 들고
있어서, 그 쓰기가 만료를 지우면 넷이 이벤트보다 오래 산다.

**전손 복구 경로에서는 안 드러난다.** 그 뒤에 `applyTtl` 이 다시 걸기 때문이다. **4.1 의 4 는
그 복원을 안 지나므로 거기서 샌다.** 통합 시험
`반납한_번호를_담는_키가_카운터의_수명을_물려받는다` 가 그것을 잡은 적이 있다.

## 8. 나빠지는 것

### 8.1 `free` 가 비어 있는 동안 발급이 돌음

**4.1 의 4 가 문을 먼저 열면 `free` 가 아직 안 채워진 상태로 발급이 재개된다.** 그 사이에 나가는
번호는 `INCR` 로만 나오므로 **주인 잃은 번호가 11 까지 재고로 안 돌아온다.**

**창의 크기는 9 의 기다림과 11 의 쓰기를 더한 값이다.** V-3 의 실측으로 보면 기여가 다 모이는
데 211밀리초, 읽고 쓰는 데 16밀리초였다. **재고 끝자락에 겹치면 소진으로 답할 수 있고 그 크기는
안 쟀다.**

### 8.2 재건이 인스턴스 수만큼 도는 것

**카운터를 올리는 일을 각 대가 하므로 그 횟수는 안 줄어든다.** 다만 **멱등이고 단조라 무해하고,
각 호출이 DB 한 번과 Redis 한 번이다.**

**횟수 자체를 줄이려면 `minInterval` 을 인스턴스 사이에 공유해야 한다.** 그것은 또 공유 상태를
안전 경로에 들이는 일이라 이 설계에서 다루지 않는다.

### 8.3 `free` 가 늦거나 덜 채워지는 것

**기여가 상한 안에 다 안 모이면 그만큼 `free` 가 덜 채워진다.** 지금도 같지만, **지금은 그 동안
발급이 멈춰 있어 피해가 드러나지 않고 새 설계에서는 발급이 돌므로 그 창에 번호가 나간다.**

## 9. 받아들이기 전에 재야 할 것

### 9.1 선행 조건

**컨테이너 메모리 한도를 먼저 정해야 한다.** 복합 장애 회차가 세 번 연속 커널 OOM 에 덮였다.

```
S-2  캐시 페일오버    dmesg "out of memory" 1건     p99 1.330초
V-4  복합            재건 3회 전부 QueryTimeout     결번 144
W-1  복합            oom-kill 3건 x 2대            발급 4,603
```

**W-1 의 실측이 그 값을 정할 근거다.** t3.small 1,905MB 에서 자바가 1.4GB 를 썼다.

```
i-0c4771c4   java anon-rss 1,399,604kB
i-0a039d03   java anon-rss 1,414,844kB
```

**한도가 없으면 커널이 호스트에서 가장 큰 프로세스를 죽인다.** 한도를 두면 컨테이너만 죽고
JVM 이 그 안에서 힙을 조절한다. 근거는 `fm-infra` 의 미결정 값 2.1.1 이다.

**그것을 안 고치면 복합 장애 회차가 재건이 아니라 OOM 을 재게 된다.**

### 9.2 기준

| 재는 것 | 기준 | 지금 값 |
|---|---|---|
| 결번 | **0** | V-3 0, P-1 0 |
| 초과 발급 | 0 | 전 회차 0 |
| **플러시 정지** | **0 에 가깝다** | N-2 0.960초, P-1 1.287초, V-3 0.942초 |
| 발급 본체 p99 | SLO 1초 안 | V-3 1.03초 초과 |
| 복합 발급량 | 9,868 (F-3) 에 근접 | P-1 9,542, V-4 8,616 |
| `COUNTER_BEHIND` | 장애에서 점프 횟수 | 0 |
| 소진 오답 | 크기를 잰다 | 안 쟀다 |

**결번 0 이 깨지면 이 설계를 버린다.** 그것이 `free` 를 지키는 유일한 이유다.

**플러시 정지가 안 줄면 이 설계의 값이 없다.** 카운터를 각자 올리는 것의 목적이 그 하나다.

### 9.3 회차

```
cache-failover         두세 번. 한 번은 변동에 묻힌다
app+cache-failover     메모리 한도를 넣은 뒤에만 뜻이 있다
seq-loss, cache-wipe   키 부재 경로가 안 깨졌는지
```

**캐시를 쓰는 회차 사이에는 15분을 띄운다.** 페일오버에 쿨다운이 있다.
