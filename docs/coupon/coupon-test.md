백엔드 **`402fb1f4`** / 전용 인스턴스 `t3.small` 3대 / VU 20,000, ramp-up 60초, 재고 10,000

시나리오는 `loadtest/issue.js`, 장애 주입은 `fm-infra` 의 `scripts/loadtest-fault.sh` 다.

## 2. 정상 회차

```
발급 10,000 / 재고 10,000     gap 0     members 10,000
p99 0.590초   p95 0.344초
504 / 연결 오류 / 502          0 / 0 / 0
```

**요구 조건인 p99 1초를 통과한다.** 서버 오류가 한 건도 없다.

이 회차는 워밍업이 정상 동작한 뒤의 값이다. 세 인스턴스 모두 기동 때
`COUPON_WARMUP_DONE sent=3000 ok=3000` 을 남겼다.

## 3. 앱 1대 장애

3대 중 1대를 `systemctl stop` 으로 세우고, ALB 가 대상에서 뺀 뒤 시험했다.

```
발급 10,000 / 재고 10,000     gap 0     members 10,000
p99 0.332초   p95 0.178초
504 / 연결 오류 / 502          0 / 0 / 0
```

**2대만으로도 재고를 다 소진했고 p99 가 오히려 좋았다.** 대수가 줄어 인스턴스당 부하가
늘었는데도 나빠지지 않았다. 3대가 여유였다는 뜻이다.

## 4. 캐시 장애

`iptables` 로 전용 인스턴스에서 캐시(6379)로 가는 패킷을 버렸다. **끊는 시점을 둘로 나눠 쟀다.**

### 4-1. 이벤트 시작 전에 끊었을 때

```
발급 0
congested-seq-unavailable  55,249
p99 39.7초
```

순번을 Redis 에서 받으므로 **새 요청은 하나도 못 받는다.** 대체 경로를 두지 않기로 한 설계
그대로다. 재고는 그대로 남고 초과 발급도 없다.

### 4-2. 회차 도중(25초 시점)에 끊었을 때

```
발급 9,772        gap 0     members 9,772
issued                     10,146
congested-seq-unavailable  29,867     끊긴 뒤 새로 온 요청
COUPON_SEQ_MARK_FAILED          1     확정 표시만 실패
```

**이미 순번을 받아 큐에 들어간 요청은 전부 발급됐다.** 플러시 스레드는 DB 에 쓰고, Redis 는
확정 표시에만 쓴다. 그 표시가 실패해도 `markCommitted` 가 삼키고 `ticket.complete(Issued)`
가 그대로 돌기 때문이다.

`gap = 0` 이 그 증거다. **번호를 받고 못 써진 요청이 하나도 없다.**

확정 표시가 1건 실패했는데, 코드 주석이 그 대가를 적고 있다. 표시를 못 남겨도 발급은 이미
끝났고, 그 회원이 다시 오면 `uk_mc_coupon_member` 가 막는다.

**그래서 캐시 장애의 성격은 "이미 받은 사람은 지키고 새 사람은 못 받는다" 다.**
전면 중단이 아니다.

## 5. DB 장애

같은 방식으로 DB(3306)를 끊었다. **여기서 회로가 일했다.**

```
발급 0
congested-budget          9,566
congested-write-circuit   8,560     <- 쓰기 회로가 열려 순번 발급을 막았다
congested-seq-unavailable 7,892
congested-db-failed           9
```

`congested-write-circuit` 8,560건이 요점이다. DB 가 죽으면 순번을 받아 봐야 커밋할 수 없다.
쓰기 회로가 열려 **순번 확보 전에 끊었으므로** 못 쓸 번호가 8,560개 덜 나갔다.

그 회로가 없었다면 그만큼이 `pending` 에 남아 회수 대상이 됐을 것이다.

## 6. 앱 1대 + 캐시 장애

```
발급 0
congested-seq-unavailable  26,436
p99 61.0초
```

캐시 단독(55,249)보다 거절 건수가 적다. **남은 2대가 처리할 수 있는 요청 수 자체가 줄어**
같은 시간에 더 적게 거절한 것이다. 결과는 캐시 단독과 같다.

## 7. 시험 도중에 고친 것

**시험의 수확은 통과 자체보다 이쪽이 크다.** 세 번은 장애가 주입되지 않은 회차를
통과로 읽을 뻔했다.

| 문제 | 어떻게 드러났나 | 조치 |
|---|---|---|
| 워밍업이 통째로 실패 | 3대 모두 `COUPON_WARMUP_FAILED elapsedMs=704`. 요청을 한 건도 못 보냄 | 첫 Redis 커넥션 재시도 (`39d5e2e9`) |
| 보안 그룹으로는 장애가 안 남 | 캐시 인그레스를 뗐는데 10,000건이 다 나갔다 | `iptables` 로 전환 |
| `iptables OUTPUT` 이 안 먹음 | 다시 10,000건이 다 나갔다 | `FORWARD` 체인도 함께 |
| 앞선 시험의 차단이 안 풀림 | 워밍업 실패와 `event:open` 500 의 진짜 원인이었다 | 복구 로직 수정 |

### 워밍업이 왜 죽었나

`markExhausted()` 가 이 JVM 의 **첫 Redis 명령**이었다. 그때 DNS 조회와 TCP 핸드셰이크와
Lettuce 초기화가 함께 일어나는데, 그 전부가 명령 타임아웃 100ms 안에 끝나야 한다.
차가운 JVM 에서는 못 끝낸다.

타임아웃을 올려 풀지 않았다. 100ms 는 SLO 에서 역산한 값이고(왕복 2회 + 확정 대기 800ms
= 1초), 이 문제는 정상 상태가 아니라 **최초 1회**다. 재시도로 고쳤고 로그가 그것을 보여준다.

```
COUPON_WARMUP_REDIS_CONNECTED attempts=2
COUPON_WARMUP_DONE sent=3000 ok=3000 elapsedMs=14608
```

**이 재시도는 워밍업만의 이야기가 아니다.** 워밍업이 없으면 그 첫 실패를 실제 사용자의
첫 요청이 문다.

### 보안 그룹으로는 왜 장애가 안 났나

**AWS 보안 그룹은 상태 추적이라 규칙을 떼어도 이미 맺어진 연결은 그대로 흐른다.**
Lettuce 는 커넥션 하나를 세워 두고 모든 명령을 다중화하므로 앱은 아무 일도 없었다는 듯
계속 돌았다. `congested-seq-unavailable` 이 0 인 것으로 알아챘다.

### `iptables OUTPUT` 은 왜 안 먹었나

**앱이 도커 브리지 네트워크 안에서 돈다.** 컨테이너가 내보내는 패킷은 호스트의 `OUTPUT`
체인을 안 지나고 `FORWARD` 를 지난다. 둘 다 넣어야 막힌다.

확인 방법은 이것이다. 규칙만 보지 말고 **컨테이너 안에서 직접 찔러 본다.**

```
docker exec freshmarket timeout 3 bash -c '</dev/tcp/<캐시>/6379'
```

## 8. 아직 확인하지 않은 것

* **장애에서 회복.** 도중에 끊는 것은 쟀지만(4-2), 도중에 **다시 붙였을 때** 얼마나 빨리
  정상으로 돌아오는지는 재지 않았다
* **DB 장애를 도중에 걸었을 때.** 캐시는 4-2 로 갈랐지만 DB 는 시작 전 차단만 쟀다.
  쓰기 회로가 열리는 시점과 큐에 남은 티켓의 운명이 달라질 수 있다
* **부분 장애.** 캐시 3노드 중 1노드나 읽기 복제본만 죽는 경우
* **차가운 상태의 p99.** 워밍업 없이는 4.69초까지 간다. 워밍업이 그 조건을 없앤다
* **상한.** 도착률 333건/초는 요구 조건이지 한계가 아니다
