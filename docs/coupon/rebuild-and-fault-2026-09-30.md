# 재건과 장애를 부하 생성기가 죽지 않는 조건에서 다시 잰 회차 (2026-09-30)

**팀이 부하 스크립트를 고친 뒤 처음으로 장애 회차를 끝까지 돌렸다.** 앞선 재건 회차는 k6 가
87% 에서 OOM 으로 죽어 HOLD 30초가 통째로 날아갔고, 그래서 결번을 그대로 못 읽었다
([rebuild-measurement-2026-09-21b.md](rebuild-measurement-2026-09-21b.md) 4장).

```
AWS 실측     20,000 VU / ramp 60초 / HOLD 30초 / 재고 10,000장 / 전용 인스턴스 3대
스프링 서버  fm-backend main f9ea2041cf0a
생성기       m7i-flex.large 1대
```

**여섯 회차 전부 k6 가 완주했다. OOM 이 한 번도 없다.**

---

## 1. 결론

**첫째, 재건은 큐를 못 쓴다.** 재건이 시작되면 각 인스턴스는 자기가 쥔 번호를 Redis 에 올려야
한다. 안 올리면 재건 담당이 그 번호를 주인 없는 것으로 보고 남에게 다시 내준다. 팀이 2026-09-21 에
고친 것은 그 올리는 동작이 시작되게 한 것이고, **올릴 번호가 남아 있게** 한 것이 아니다.
597번 올렸는데 매번 0개를 올렸다.

**둘째, 원인은 플러셔의 실패 경로다.** 배치를 큐에서 뺀 뒤 실패하면 되돌리지 않는다. 재건이
지켜야 할 티켓이 재건보다 먼저 큐를 떠난다.

**셋째, 장애 3종의 판정이 09-14 보다 좋아졌다.** 특히 캐시 페일오버 회차가 SLO 를 지킨다.

**넷째, 여섯 회차 전부 초과 발급 0 이고 1인 1매가 지켜졌다.** 발급행과 회원수가 매번 같다.

## 2. 재건 회차

**DB 를 막아 큐를 쌓고 `counter` 를 지워 재건을 일으킨다.** 재건 담당 한 대만 DB 를 풀어 준다.

| 회차 | 차단 | `counter` 삭제 | 발급행 | 최대순번 | 결번 | 회원수 | 큐 최대 |
|---|---|---|---:|---:|---:|---:|---:|
| f4-1 | k6+17초 | k6+44초 | 9,240 | 10,000 | 760 | 9,240 | 2,121 |
| f4-2 | k6+16초 | k6+43초 | 9,303 | 10,000 | 697 | 9,303 | 409 |
| f4-3 | k6+10초 | k6+37초 | 8,957 | 10,000 | 1,043 | 8,957 | 7,519 |

**결번 697에서 1,043 이다.** 앞 회차의 836 과 1,050 은 회차가 잘려 나온 값이라 견줄 대상이 아니다.

**최대순번이 세 회차 다 10,000 이다.** 번호는 끝까지 나갔고 그중 몇 장이 DB 에 못 들어갔느냐만 갈렸다.

## 3. 빈 채로 올라간 597번

**2026-09-21 회차에서는 한 대도 번호를 못 올렸다.** `rebuildIfLost` 가 DB 읽기를 먼저 해서
막힌 인스턴스가 거기서 터졌다. 팀이 그것을 고쳤다.

**고침은 돈다.**

| 회차 | 올린 횟수 | 그중 번호가 담긴 것 |
|---|---:|---:|
| f4-1 | 263 | **0** |
| f4-2 | 258 | **0** |
| f4-3 | 76 | **0** |

**597번 전부 빈 채로 올라갔다.** 팀이 세 인스턴스의 로그를 전수로 세어 확인했다.

### 올리기 직전에 비는 큐

f4-1 의 큐 깊이다. 막힌 인스턴스 하나를 따라간다.

```
16:29:50   1,508      DB 가 막혀 쌓인다
16:30:00   1,508
16:30:04   counter 삭제
16:30:05   0          DB 는 여전히 막혀 있는데 비었다
16:30:07   올렸다. 담긴 번호 0개
```

**플러셔가 실패한 배치를 큐로 안 되돌린다.**

```java
queue.drainTo(batch, batchSize - 1);
...
} catch (RuntimeException e) {
    log.error("event=COUPON_FLUSH_BATCH_FAILED size={}", batch.size(), e);
    failAll(batch, IssueResult.ABORTED);
}
```

`failAll` 은 티켓을 `Congested(ABORTED)` 로 끝낼 뿐이고 순번을 `free` 로 안 돌린다.
**DB 가 빨리 실패하면 플러셔가 큐를 전속력으로 비운다.**

### 왜 이것이 설계와 어긋나나

`CouponSeqContributor` 는 큐를 이렇게 적어 두었다.

> 큐는 Redis 가 죽어도 살아 있는 유일한 미확정 기록이다.

**그 전제가 DB 장애에서 깨진다.** 올릴 번호를 찾을 때 보는 곳이 큐인데(`queue.snapshot()`),
위험한 티켓은 이미 큐 밖의 배치에 있다가 버려진다. 결번 697에서 1,043 이 그 숫자다.

**팀은 이 회차에서 고치지 않았다.** 무엇을 고쳐야 하는지가 이 회차의 결과다.

## 4. 장애 3종

**2026-09-14 와 같은 주입을 걸었다.** 주입 시점은 k6 가 실제로 VU 를 내보내기 시작한 때부터 센다.

| 회차 | 건 장애 | 주입 | 발급행 | 최대순번 | 결번 | 회원수 | p99 |
|---|---|---|---:|---:|---:|---:|---:|
| F-1 | 스프링 서버 컨테이너 급사 | k6+16초 | 10,000 | 10,000 | 0 | 10,000 | 0.442초 이하 |
| F-2 | 캐시 Multi-AZ 페일오버 | k6+16초 | 10,000 | 10,000 | 0 | 10,000 | **0.814초** |
| F-3 | 스프링 서버 급사 + 캐시 페일오버 | k6+12초 | 9,868 | 9,868 | 0 | 9,868 | 0.228초 |

**셋 다 결번 0 이다.** 초과 발급도 0 이고 예상 못 한 응답도 0 이다.

**F-1 의 p99 는 요약이 잘려 값을 못 읽었다.** 최댓값이 0.442초이므로 p99 는 그 아래다.

### 09-14 와 달라진 것

| 회차 | 2026-09-14 | 2026-09-30 |
|---|---|---|
| 스프링 서버 급사 | 10,000 / 결번 0 / 0.522초 | 10,000 / 결번 0 / 0.442초 이하 |
| 캐시 페일오버 | 9,989 / 결번 11 / **1.041초** | 10,000 / 결번 0 / **0.814초** |
| 스프링 서버 급사 + 캐시 페일오버 | 9,031 / 결번 4 / 0.321초 | 9,868 / 결번 0 / 0.228초 |

**캐시 페일오버 회차가 SLO 를 지킨다.** 앞 기록은 이 회차를 근거로 "장애 중에는 SLO 를 못
지킨다" 고 적었는데, 이번 회차는 그 반대다.

**조합 장애의 판매량이 9,031 에서 9,868 로 올랐다.** 결번도 4 에서 0 이 됐다.

### 이 차이를 만든 것을 못 가르는 이유

**팀은 원인을 이 회차로 못 가른다.** 사이에 세 가지가 함께 바뀌었다.

```
1  스프링 서버 코드      09-15 이후 쿠폰 경로에 커밋 스무 건이 넘게 들어갔다
2  생성기 부담  앞 회차는 8GB 중 7.4GB 를 썼고 이번엔 남은 메모리가 최소 1.6GB 다
3  주입 시점    앞 회차의 실제 오프셋이 기록에 없다
```

**둘째가 특히 크다.** k6 가 메모리에 쪼들리면 자기 지연이 측정에 섞인다. **스프링 서버가 빨라진 것과
재는 쪽이 정직해진 것을 이 회차로는 못 가른다.**

### 이번에도 안 걸린 재건

**F-1 과 F-2 에서 재건 로그가 없다.** 페일오버는 복제본이 데이터를 갖고 승격되므로 카운터가
살아남는다. 재건의 방아쇠는 카운터 부재인데 그 조건이 안 생긴다. 09-14 와 같은 결과다.

## 5. 절차에서 고친 것

### 막는 것과 지우는 것 사이의 부하

**`lead-drop` 을 `loadtest-fault.sh` 에 넣었다.** 큐를 쌓으려면 차단이 부하보다 앞서야 해서
`backlog_then_drop` 을 한 호출로 못 쓴다. 뒷부분만 떼어 따로 부른다.

### 부하보다 먼저 막을 때 비는 큐

**시나리오 문서의 조언이 틀렸다.** "DB 를 먼저 막고 k6 를 띄운다" 는 순서로 돌린 회차가
발급 2,886 에 재건 `issued=0 queued=0 maxSeq=0` 을 냈다.

**DB 가 막힌 인스턴스를 ALB 가 대상에서 뺀다.** 그 두 대는 요청을 한 건도 안 받아 올릴 큐가
없었다. 발급 2,886 이 재건 담당 한 대 몫이다.

**그래서 부하를 먼저 띄우고 발급이 도는 중에 막는다.** 이 회차는 그 순서로 돌았다.

## 6. 이 회차가 답하지 못한 것

**첫째, 플러셔가 실패한 배치를 어디에 둬야 하는지.** 큐로 되돌리면 순서가 섞이고 두 번 쓸 수
있다. 별도의 미확정 보관소가 필요한지, 아니면 올릴 번호를 찾을 때 큐 대신 그 배치를 봐야
하는지를 안 정했다.

**둘째, 장애 회차가 좋아진 원인.** 4장에 적은 세 가지가 함께 바뀌어 안 갈린다.

**셋째, f4-3 의 k6 발급 수와 DB 행 수가 다른 것.** k6 는 7,113 을 셌고 DB 에는 8,957행이 있다.
차이 1,844건은 응답을 혼잡으로 받았는데 행은 들어간 것으로 보이며, 팀이 확인하지 않았다.

**넷째, F-1 의 p99.** 요약을 `tail -40` 으로 잘라 임계 줄을 잃었다. 다음 회차는 전문을 남긴다.
