# 같은 일을 서버마다 되풀이하지 않는 설계

**이 문서는 제안이다. 코드는 아직 안 고쳤고 회차도 안 돌렸다.** 그래서 9장에 선행 조건을,
10장에 아직 못 정한 분기를 적었다.

```
지금 도는 것   docs/coupon/rebuild-v4/design.md
근거 회차      docs/coupon/rebuild-v4/rounds.md 3장 (V2-1, V2-2)
```

---

## 1. 서버 셋이 같은 일을 되풀이하는 자리

A 단계는 서버마다 돈다. 그 안의 세 걸음은 성질이 다르다.

| 걸음 | 서버마다 다른가 |
|---|---|
| DB 전수 조회 | 같다. 같은 쿠폰의 같은 표를 읽는다 |
| `seq` 해시 쓰기 | 같다. 읽은 것을 그대로 옮긴다 |
| 자기 큐 되살리기 | **다르다.** 그 서버만 안다 |
| 카운터 올리기 | **다르다.** 자기 기억이 필요하다 |
| B (`free` 되돌리기) | 같다. 입력이 DB 행과 카운터뿐이다 |

**같은 것이 셋인데 셋 다 서버 수만큼 돈다.**

### V2-1 실측

```
서버 1   issued 7,030   raise 283ms   free 23ms
서버 2   issued 7,178   raise 411ms   free 18ms
서버 3   issued 7,203   raise 185ms   free 21ms
```

```
DB 행 읽기          21,411행     그 중 약 14,200행이 앞 서버가 이미 읽은 것
seq 해시 필드 쓰기   21,411개     그 중 약 14,200개가 같은 값을 다시 쓴 것
HGETALL seq 전수    3번
Redis 왕복          약 63번
```

### 재건 락이 이것을 못 막는 까닭

```
05.391   서버 1 이 B 를 끝내고 락을 지운다
05.650   서버 2 가 빈 락을 새로 잡고 B 를 한다
05.955   서버 3 이 또 잡고 B 를 한다
```

**락이 "했다" 가 아니라 "하는 중" 표시라서다.** 끝나면 지우므로 뒤 서버에게는 빈 자리로
보인다. 세 서버의 A 가 300ms 간격으로 끝나 **락이 한 번도 안 부딪혔다.**

이 성질은 `rebuild-v1` 에서 왔다. 거기서는 주도자가 나머지를 기다려 **락 하나가 곧 "이 장애의
재건 한 번"** 이었는데, `rebuild-v2` 가 기다림만 걷어내면서 **한 번도 안 부딪히는 락**이 남았다.

## 2. 얼마나 아픈가

**정직하게 적는다. 자원은 많이 줄고 사용자가 겪는 시간은 조금 준다.**

| | 지금 | 바꾼 뒤 |
|---|---:|---:|
| DB 행 읽기 | 21,411행 | 약 7,200행 |
| `seq` 해시 필드 쓰기 | 21,411개 | 7,208개 |
| Redis 왕복 | 약 63번 | 약 18번 |
| B 단계 | 3번 | 1번 |

**순번 발급이 멈춘 시간은 11% 밖에 안 준다.**

```
지금
05.076   서버 1 이 차단하고 A 시작
05.745   서버 3 이 차단하고 A 시작      670ms 늦게 깨어났다
05.955   서버 3 이 끝나고 다시 차단
06.955   시한 1초가 지나 풀린다          1.879초

최선 (뒤 서버의 일이 0이 된다고 쳐도)
05.745   서버 3 이 차단한다. 바로 끝난다
06.745   시한 1초가 지나 풀린다          1.674초
```

```
차단 시한 1초      53%     일과 무관하게 붙는다
전파 간격 670ms    36%     서버 3 이 그만큼 늦게 깨어났다
실제 일 209ms      11%     이 설계가 건드리는 것
```

**Redis 는 한 스레드다.** 왕복 63번이 18번이 되는 것은 **그동안 다른 요청이 서지 않는다**는
뜻이라 시간으로 안 잡혀도 값이 있다. 다만 **이 설계를 "정지 시간을 줄인다" 로 팔면 안 된다.**

## 3. 바꾸는 것

**표시 키 하나를 들인다. 올라가기만 한다.**

```
coupon:{id}:seqhash-mark     "여기까지 seq 해시에 넣었다"
담는 값                       그 스냅숏에서 읽은 max(member_coupon_id)
```

**`openGate` 와 같은 모양이다.** 올리기만 하는 값 하나로 순서를 안 따져도 되게 만든다. 합의도
기다림도 안 든다.

---

## 4. 절차

### 4.1 표시가 없는 서버

```sql
SELECT member_coupon_id, member_id, issue_seq
  FROM member_coupon WHERE coupon_id = ?
```

```
seq 해시에 전부 쓴다
자기 큐를 되살린다
카운터를 올린다
B 를 한다
표시 = 읽은 행의 max(member_coupon_id)
```

### 4.2 표시가 있는 서버

```sql
SELECT member_coupon_id, member_id, issue_seq
  FROM member_coupon WHERE coupon_id = ? AND member_coupon_id > ?
```

```
seq 해시에 새 행만 쓴다
자기 큐를 되살린다
카운터를 올린다
B 를 건너뛴다
표시 = 읽은 행의 max(member_coupon_id)
```

**B 를 건너뛰는 것은 선택이 아니라 결과다.** 구멍을 세려면 전체 목록이 있어야 하는데 delta
만으로는 못 센다.

---

## 5. 왜 번호가 아니라 PK 로 끊나

**번호로 끊으면 빈틈이 생긴다.**

```
번호는 Redis 가 즉시 내준다
행은 플러시가 나중에 쓴다

-> 번호 5,000 을 쥔 느린 티켓이 번호 7,200 짜리 행들보다 늦게 들어올 수 있다
```

서버 1 의 스냅숏에 `max(issue_seq) = 7,038` 이어도 **번호 5,000 짜리 행이 아직 안 들어와 있을
수 있다.** 서버 2 가 `issue_seq > 7038` 만 읽으면 **그 행을 영영 못 보고**, 그 회원이 결번이
된다.

**`member_coupon_id` 는 들어온 순서대로 늘기만 한다.** 번호가 몇이든 나중에 들어왔으면 PK 가
크다. **그래서 delta 가 빠지는 행 없이 완전하다.**

**지우는 경로가 없는 것이 전제다.** `member_coupon` 에 삭제가 없는 것을 확인했다. 생기면 이
전제가 깨진다.

---

## 6. 표시를 언제 올리나

**다 쓴 뒤에 올린다.**

| 올리는 때 | 그 서버가 중간에 죽으면 |
|---|---|
| 쓰기 전 | 아무도 안 쓴 범위를 "썼다" 고 믿는다. 다음 서버가 그 위만 읽는다. **결번** |
| 쓴 뒤 | 표시가 안 올라간다. 다음 서버가 전수로 다시 한다. **겹칠 뿐 안 빠진다** |

**겹치는 쪽은 비용이고 빠뜨리는 쪽은 결번이다.**

**표시에 `counter` 의 수명을 물려준다.** 안 걸면 다음 이벤트까지 남아서 그때 재건을 건너뛴다.
나머지 네 키와 같은 방식이다.

**승격으로 Redis 가 뒤로 가도 안전하다.** 표시와 `seq` 해시가 같이 뒤로 가므로 **표시가 해시
내용보다 앞서지 않는다.** 더 읽을 뿐 덜 읽지 않는다.

---

## 7. 함께 걷히는 것

**재건 락을 뗀다.**

```
락이 하려던 일   B 를 한 번만 돌게 한다
실제로 한 일     없다.  V2-1 에서 세 서버가 차례로 잡아 세 번 다 돌았다
표시가 하는 일   뒤 서버가 delta 만 읽으므로 B 를 못 한다.  구조적으로 한 번이다
```

락이 없어지면 **주도자가 B 중간에 죽어서 그 회차의 B 가 통째로 빠지는 경우**도 같이 없어진다
(`rebuild-v4/design.md` 9.2).

---

## 8. 안 건드리는 것

| 걸음 | 왜 그대로 두나 |
|---|---|
| 순번 발급 차단 | 건너뛰면 시한이 안 늘어 복구 중에 창이 열린다 |
| 자기 큐 되살리기 | 그 서버의 메모리 큐는 그 서버만 안다 |
| 카운터 올리기 | 왕복 하나다. 쪼개도 왕복 수가 같다 |
| 나이 조건 `freeMargin` | 아직 A 를 안 한 서버의 티켓을 덮는 장치다 |

**각 서버의 기억으로 DB 조회를 대신할 수는 없다.** `mark` 는 숫자 하나라 **누가 그 번호를
가졌는지가 없다.** 커밋된 매핑은 DB 말고 있는 곳이 없다.

## 9. 받아들이기 전에 할 것

### 9.1 선행 조건

**계측이 먼저다.**

```
coupon.seq.rebuild.db        findIssuedSeqs
coupon.seq.rebuild.seqhash   writeSeqHash
coupon.seq.rebuild.gate      openGate 와 TTL
```

**지금 `raise` 가 한 덩어리로만 잡혀 411ms 의 내역을 모른다.** 그 411ms 가 DB 조회와 `seq`
쓰기면 2장의 11% 를 다 얻고, **페일오버 중 Redis 지연이면 거의 못 얻는다.**

**V2-2 가 2,400행 더 읽고도 124~136ms 였다는 것이 후자 쪽 단서다.**

**그리고 계측은 이 설계보다 먼저 들어가야 한다.** 같이 넣으면 **견줄 전(前) 숫자가 영영 안
생긴다.**

### 9.2 전손 회차

**그 쿠폰의 키 넷을 `UNLINK` 하고 재건을 돌린다.** 한 번도 안 해본 조건이다.

## 10. 아직 못 정한 분기

**B 단계의 운명이 전손 회차에 달렸다.**

```
지금까지   COUPON_SEQ_FREE_WRITTEN 124건, added=0 (전부)
```

**`seq` 해시가 살아남는 장애에서는 B 가 영원히 0일 수 있다.** 되살리려는 번호의 매핑이 아직
해시에 있어서 "누가 쥔 것" 으로 가려지기 때문이다.

| 전손 회차 결과 | 이 설계가 바뀌는 곳 |
|---|---|
| B 가 번호를 건진다 | 4장 그대로. B 를 한 번만 돈다 |
| B 가 또 0이다 | B 를 뗀다. 4.1 에서도 안 한다 |

## 11. 나빠지는 것

### 11.1 뒤 서버가 늦게 찾을 결번을 못 찾음

나이 조건이 `counter - 번호 >= 500` 이라, **카운터가 오르면 후보가 몇 개 늘 수 있다.**

```
서버 1 이 볼 때   counter 7,204   ->  6,704 이하가 후보
서버 3 이 볼 때   counter 7,234   ->  6,734 이하가 후보
                                      그 사이 30개가 새로 자격을 얻는다
```

**V2-1 에서는 셋 다 `candidates=5` 로 같았다.** 그 구간에 결번이 없었다. 있었다면 뒤 서버가 몇
장 더 건졌을 것이다.

**잃는 양이 나이 조건이 그은 선 바로 옆이다.** 그리고 같은 이벤트에서 재건이 또 돌면 그때
잡힌다.

### 11.2 키가 하나 늘어남

`seq` `free` `counter` `pending` `raising` 에 `seqhash-mark` 가 더해져 여섯이 된다. **수명을
`counter` 에서 물려받는 키도 하나 는다.**

### 11.3 첫 서버에 일이 몰림

전수 조회와 `seq` 해시 전부 쓰기와 B 를 **한 서버가 다 한다.** 지금은 셋이 나눠 지던(겹치던)
부하다.

**그 서버의 A 가 길어지면 차단이 그만큼 더 서 있는다.** 다만 **지금도 가장 느린 서버가 창을
결정한다** (차단은 마지막으로 끝낸 서버 기준이다).
