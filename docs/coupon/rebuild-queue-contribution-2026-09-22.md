# 큐가 실제로 재건에 쓰인 회차 (2026-09-22)

**일곱 회차 만에 처음으로 기여가 비지 않았다.** 그전까지는 `size` 가 늘 0 이어서, 재건이 큐를 쓰는 경로를 한 번도 실물로 못 봤다.

```
AWS 실측   20,000 VU / ramp 60초 / 재고 10,000장 / 전용 인스턴스 3대
앱         fm-backend main affe07de
```

## 1. 왜 여태 비어 있었나

**주입이 늦어서다.** 회로 타이밍 때문이라던 앞선 진단은 틀렸다.

```
COUPON_SEQ_REBUILT couponId=900001 issued=10000 queued=0 maxSeq=10000 freed=0
```

재건 시점에 **재고 10,000장이 전부 DB 행이 돼 있었다.** 소진된 뒤에는 새 티켓이 안 생기므로 큐가 빌 수밖에 없다. k6 시작 12초, 15초, 25초 뒤에 주입한 회차가 전부 그랬다.

`--backlog` 를 줄여 회로를 피하려던 것도 번지수가 틀렸다. **그 회차에서 회로는 한 번도 안 열렸는데도 `size` 가 0 이었다.**

**SSM 왕복이 `--backlog` 를 무의미하게 만든다는 것도 함께 드러났다.** 대당 4~5초씩 걸려 `--backlog 1` 이 실제로는 20초였다.

## 2. 순서를 뒤집으니 나왔다

**차단을 먼저 걸고 k6 를 시작한 뒤, 발급이 도는 중에 counter 를 지웠다.**

```
16:18:58 ~ 16:19:18   DB 차단 (세 대)
16:19:31              k6 시작
16:20:21              주도자만 풀고 counter 삭제
```

DB 가 막혀 있으니 번호는 나가는데 행이 안 된다. **큐가 쌓인 채로 재건이 걸린다.**

```
COUPON_SEQ_REBUILT couponId=900001 issued=2602 queued=1645 maxSeq=10000 freed=5753
```

**`queued=1645` 가 이 기능의 존재 이유다.** 재건이 DB 의 2,602건에 큐의 1,645건을 더해 `maxSeq=10000` 을 세웠다. 큐를 안 올렸으면 `maxSeq` 가 2,602 에 그쳐 **2,603번부터가 전부 "아무도 안 쥔 번호" 로 분류돼 남에게 다시 나갔을 것이다.**

## 3. 조기 종료가 2밀리초에 끝났다

```
COUPON_SEQ_CONTRIBUTIONS_COMPLETE couponId=900001 instances=2 waitedMillis=2
```

**3,000밀리초 중 2밀리초만 썼다.** 기다림이 통째로 사라졌다. 조기 종료의 값어치가 처음으로 수치로 드러났다.

## 4. 구간 분해가 뒤집혔다

```
size=1645 lagMillis=602 pauseMillis=585 writeMillis=14 waitMillis=3
```

**이번에는 `pause` 가 585밀리초로 대부분이다.** 앞 회차들에서는 전부 `wait` 이었는데 정반대다.

당연한 결과다. 큐에 1,645건이 있으니 **돌던 배치가 끝나기를 실제로 기다려야 한다.** 앞 회차들은 큐가 비어 멈출 것이 없었다.

**총합만 재고 있었으면 "602밀리초 걸렸다" 로 끝나고 이유를 몰랐을 것이다.** 같은 숫자가 회차마다 전혀 다른 곳에서 나온다.

## 5. DB 가 막힌 인스턴스는 여전히 기여를 못 한다

막힌 두 대는 `size` 가 0 이고 `REBUILD_FAILED` 만 남겼다. 명부 점수도 차단 시점 이후로 안 올랐다.

**원인은 알림 위치가 아니라 루프가 갇히는 것이다.**

```java
} catch (DataAccessException e) {
    flushOneByOne(batch);   // 한 건씩 다시 넣는다
    return;
}
```

DB 가 안 닿으면 벌크 쓰기가 통째로 실패하고, 그러면 **어느 행이 범인인지 가리려고 한 건씩 다시 넣는다.** 배치 500건에 건당 커넥션 타임아웃 300밀리초면 **그 배치 하나에 최대 150초를 붙잡힌다.**

그동안 루프가 다음 바퀴를 못 돌고 `holdingQueue()` 도 안 불린다. **알림을 `flush` 앞으로 옮긴 것만으로는 안 풀린다. 한 바퀴에 한 번 알리는데 그 한 바퀴가 150초다.**

`flushOneByOne` 은 중복을 가려내려고 있는 것이지 DB 가 통째로 안 닿는 상황을 위한 것이 아니다. **통신 실패와 제약 위반을 가려야 한다.**

## 6. 정합성

| 회차 | 주입 | 발급행 | 최대순번 | 결번 | 회원수 |
|---|---|---:|---:|---:|---:|
| A | `--backlog 1` | 10,000 | 10,000 | 0 | 10,000 |
| B | 차단 먼저 + 발급 중 삭제 | 7,847 | 10,000 | 2,153 | 7,847 |

**둘 다 초과 발급 0 이고 1인 1매가 지켜졌다.**
