# 재건을 실제로 일으켜 본 회차 (2026-09-21)

`rebuild-contribute-wait` 3초를 실측으로 좁히려고 AWS 에서 재건을 일곱 번 일으켰다.
**결론부터 적으면 3초는 아직 못 좁혔고, 대신 좁히기 전에 풀어야 할 것 셋을 찾았다.**

## 1. 끝까지 돈 재건 두 회차

**두 회차에서 재건이 끝까지 돌았다.**

```
5회차  COUPON_SEQ_REBUILT couponId=900001 issued=6393 queued=0 maxSeq=6393 freed=0
7회차  COUPON_SEQ_REBUILT couponId=900001 issued=5125 queued=0 maxSeq=5829 freed=704
```

**7회차가 이 시험의 값어치다.** DB 를 끊은 동안 플러시가 실패해 **번호는 나갔는데 행이 없는 것이 704개** 생겼고, 재건이 그것을 전부 `free` 로 되살렸다. `5125 + 704 = 5829` 로 최댓값과 맞는다.

**정합성은 어느 회차에서도 안 깨졌다.** 마지막 상태가 `issued_rows 5501 / members 5501` 이라 1인 1매가 지켜졌고 초과 발급은 0이다.

## 2. 한 번도 아무것도 못 모은 큐 수집

**일곱 회차 전부 `queued=0` 이고, `lagMillis` 표본은 0건이다.**

```
sum(coupon_seq_rebuild_contribute_lag_seconds_count) = 0
```

지표가 안 붙은 것이 아니다. 세 인스턴스 모두 `# HELP` 와 `# TYPE` 이 나오고 Prometheus 도 `coupon` 잡으로 긁는다. **올릴 것이 없어서 안 찍혔다.**

**큐가 너무 얕다.** 평상시 부하에서 잰 최대 깊이가 **92개**다.

```
max_over_time(coupon_issue_queue_size[45m]) = 92
```

배치 창이 20ms 이고 한 번에 500건을 끊으므로 **플러시가 유입을 가볍게 따라잡는다.** 그리고 카운터가 사라지는 순간 스크립트가 `-2` 를 주기 시작해 **새 티켓이 아예 안 들어온다.** 그래서 재건이 시작될 때쯤이면 큐가 이미 비어 있다.

```
카운터 삭제  ->  요청이 전부 -2  ->  새 티켓 0
                 남은 92개가 20ms 안에 빠진다
                 그 뒤에 트리거 -> 비동기 -> 락 -> contribute()  ->  큐가 비어 있다
```

**큐를 깊게 만들어도 결과가 같았다.** 7회차에서 DB 를 끊어 깊이를 **502** 까지 올린 뒤 카운터를 지웠는데도 `queued=0` 이었다. DB 가 돌아오는 순간 502개가 두 배치에 빠져서다.

## 3. 그래서 찾은 것 셋

### 3.1 재건을 안 일으키는 캐시 페일오버

`loadtest-fault.sh cache-failover` 를 부하 중에 걸었는데 **재건 로그가 한 줄도 안 나왔다.** 복제본이 승격돼도 데이터가 복제돼 있어 **네 키가 그대로 살아남는다.**

**재건은 승격이 아니라 진짜 키 손실에서만 돈다.** 장애 주입으로 재건을 재현하려면 키를 직접 지워야 한다. 이 회차에서는 손으로 보냈다.

```
(쿠폰 인스턴스에서)
H=$(aws ssm get-parameter --name /freshmarket/cache-endpoint --region ap-northeast-2 \
      --query Parameter.Value --output text)
printf 'DEL coupon:900001:counter\r\n' | nc $H 6379
```

**배치 인스턴스에서는 안 된다.** 보안 그룹이 배치에서 캐시로 가는 6379 를 막아 둬서 명령이 캐시에 닿지도 않는다. 처음에 그걸 모르고 배치에서 보내 한 회차를 헛돌았다.

**이 절차는 `fm-infra` 의 시나리오가 됐다.** 손으로 보내던 것을 `loadtest-fault.sh` 가 받았다.

```bash
./scripts/loadtest-fault.sh lost-tail --lost 200   # 복제가 밀린 채 승격
./scripts/loadtest-fault.sh seq-loss --backlog 5   # 큐를 쌓은 뒤 counter 를 지운다
./scripts/loadtest-fault.sh cache-wipe             # 순번 네 키를 전부 지운다
```

**여기서 이 회차가 놓친 것이 드러났다.** 이 회차가 만든 것은 키가 통째로 사라지는 전손인데, **Multi-AZ 복제에서 가장 안 일어나는 모양이다.** 실제 페일오버에서 확률이 높은 것은 복제가 밀린 채 승격돼 `counter` 가 뒤로 가는 것이고, 그때는 `-2` 가 안 나오므로 **재건이 아예 안 걸린다**([재건 문서](redis-promotion-rebuild.md) 7장). 막는 것은 앱이 아니라 스키마의 `uk_mc_coupon_seq` 다. `lost-tail` 이 그 모양을 만든다.

### 3.2 DB 가 죽어 있으면 시작조차 못 하는 재건

DB 를 끊은 채로 카운터를 지웠더니 세 인스턴스가 전부 `COUPON_SEQ_REBUILD_FAILED` 만 반복했다.

`rebuildIfLost` 의 첫 줄이 `couponRepository.findById` 다. **관리자가 아직 안 연 이벤트와 진짜 손실을 가르려고 DB 를 보는데**, DB 가 없으면 그 판정 자체를 못 한다. 그래서 `contribute()` 까지 가지도 못한다.

**이건 설계상 맞는 동작이다.** DB 가 없으면 재건해 봐야 쓸 곳이 없다. 다만 **DB 와 Redis 가 함께 죽으면 재건이 DB 복구를 기다린다**는 점이 문서에 없다.

### 3.3 "안 늦었다" 와 "올릴 게 없었다" 를 못 가르는 지표

`contribute()` 가 `mine.isEmpty()` 면 **`lagMillis` 를 재기 전에 돌아간다.**

```java
Map<String, String> mine = mineFor(couponId);
if (mine.isEmpty()) {
    return;          // 여기서 끝나 지표가 안 찍힌다
}
```

그래서 `count = 0` 이 **"기여가 늦지 않았다" 인지 "올릴 것이 없었다" 인지 구분이 안 된다.** 이번 회차가 전부 후자였는데, 지표만 보면 알 수 없다.

**빈 기여도 재면 그 구분이 생긴다.** 그러면 "재건이 시작되고 몇 ms 뒤에 이 인스턴스가 큐를 확인했나" 가 쌓이고, 그것이 곧 3초를 좁히는 근거다.

## 4. 3초를 어떻게 할까

**아직 줄이지 못한다.** 근거가 될 표본이 0건이다.

다만 이번 회차가 **방향은 가리킨다.** 큐 최대 깊이가 92이고 배치가 20ms 라면, 살아 있는 인스턴스의 기여는 **수십 ms 안에 끝난다.** 3초는 그보다 두 자릿수 크다.

**줄이기 전에 3.3 을 먼저 고쳐야 한다.** 빈 기여까지 재서 분포를 얻고, 그 위에서 값을 정하는 것이 순서다.

**그리고 줄일 때는 `counter` 를 기준으로 봐야 한다.** 기여가 빠지면 `free` 는 그 번호 하나가 충돌하는데, **`counter` 는 최댓값이 뒤로 가 그만큼의 구간 전체가 재발급 대상이 된다.**

| 7 | DB 차단 -> 키 삭제 -> DB 복구 | **돎** | 0 | `issued=5125 freed=704` |

## 6. 다음에 할 것

1. **빈 기여도 재도록 고친다**(3.3). 이것 없이는 3초를 못 좁힌다. **끝냈다**
2. `cache-failover` 로는 재건이 안 난다는 것을 `redis-promotion-rebuild.md` 에 적는다(3.1). **끝냈다**
3. DB 가 죽어 있으면 재건이 시작조차 못 한다는 것을 `coupon-failure.md` 에 적는다(3.2). **끝냈다**
4. **`lost-tail` 회차를 돌린다.** 이 회차가 한 번도 안 만들어 본 모양이고 실제로는 이쪽이 더 흔하다. `counter` 가 뒤로 갔을 때 스키마가 정말로 막는지, 그때 응답이 무엇인지를 본다
5. `seq-loss --backlog` 로 회차를 다시 돌려 `lagMillis` 분포를 얻는다
