# 재건이 어떻게 도나

**Redis 가 순번 키를 잃었을 때 앱이 스스로 다시 세우는 것을 재건이라 부른다.** 이 문서는 그것이
무엇이고 어떤 순서로 도는지를 설명한다.

**`coupon.md` 10장과 나눠 읽으면 된다.** 그쪽은 **왜 그렇게 정했나**를 다루고 대안과 실측을
함께 적는다. 여기는 **무엇이 어떻게 도나**만 적는다. 키가 무엇을 담는지는
[coupon-redis-keys.md](coupon-redis-keys.md) 에 있다.

코드와 설정값은 실제 파일에 있고 여기서는 **이름만 괄호로 가리킨다.**

---

## 0. 먼저 알아야 할 것 셋

처음 보는 사람을 위한 배경이다. **이미 아는 내용이면 1장으로 건너뛰면 된다.**

### 순번을 Redis 가 나눠 준다

한정 수량 쿠폰을 락 없이 지키려고 **발급마다 `1, 2, 3...` 번호를 붙인다** (`issue_seq`).
그 번호를 나눠 주는 자리가 Redis 이고, 이벤트 하나가 키 넷을 쓴다.

```
counter   마지막으로 발행한 순번
seq       회원 -> 그 회원의 순번
pending   번호는 받았는데 발급됐는지 모르는 회원
free      쓰이지 않은 것이 확인된 순번
```

### 카운터가 이벤트의 문이다

**순번 확보 스크립트의 첫 줄이 `counter` 가 있는지 묻는다.** 없으면 번호를 안 주고 거절한다.

**그래서 이 키가 사라지면 발급이 통째로 멈춘다.** 그리고 그 거절이 곧 "Redis 가 잃었다" 는
신호가 된다.

### 왜 사라지나

```
페일오버      복제 지연이 남은 채 복제본이 승격된다
동시 재시작   지속성이 없어(appendonly no) 메모리 내용이 그대로 사라진다
메모리 압박   만료가 걸린 키를 버리는 정책이라 이 키도 대상이 된다
```

**셋 다 앱은 멀쩡한 채로 Redis 만 잃는다.** 그래서 앱이 스스로 알아채고 다시 세워야 한다.

## 1. 재건은 DB 만으로 할 수 없다

**얼핏 DB 만 읽으면 될 것 같다.** 발급된 행을 다 읽으면 누가 몇 번을 받았는지 나오기 때문이다.

**그런데 앱 큐에 아직 행이 안 된 번호가 떠 있다.**

```
요청 스레드   Redis 에서 번호를 받는다 -> 큐에 넣고 잔다
플러시 스레드  큐에서 모아 DB 에 쓴다
```

**그 사이에 있는 티켓은 DB 에도 Redis 에도 없다.** DB 만 보고 세우면 그 번호들을 **아무도 안 쥔
것으로 보고 다시 내줘서**, 같은 번호가 두 사람에게 간다.

**그래서 각 인스턴스가 자기 큐를 올려야 한다.** 재건이 그것을 기다린다.

## 2. 어떻게 도나

**요청이 하나라도 들어오면 앱이 스스로 시작한다. 사람이 누를 것이 없다.**

```
1  누군가의 요청이 거절당한다        카운터가 없다는 뜻이다
2  DB 를 봐서 정말 열려 있어야 할 이벤트인지 가른다
3  락을 잡는다                     먼저 잡은 한 대만 주도한다
4  각 인스턴스가 자기 큐를 올린다     주도하는 쪽도 올린다.  잠시 기다린다
5  큐를 읽고 DB 를 읽는다           큐가 먼저다
6  seq 를 쓴다                     행이 있으면 확정 표시까지, 큐에 있으면 번호만
7  pending 을 쓴다                 큐에 있던 것만
8  free 를 쓴다                    행에도 큐에도 없는 번호
9  counter 를 쓴다                 이 순간 문이 열린다
10 큐 키를 지우고 락을 푼다
```

### 2번이 없으면 안 된다

**카운터가 없다는 것은 두 가지를 뜻한다.**

```
잃었다          재건해야 한다
아직 안 열었다   관리자가 준비를 안 한 것이다.  건드리면 안 된다
```

**Redis 만 봐서는 못 가른다.** DB 의 쿠폰 행을 봐야 한다. 이 확인이 없으면 **기동할 때마다
재건이 헛돈다.**

### 5번의 순서가 중요하다

**티켓은 큐에서 DB 로만 가고 반대로는 안 간다.**

```
큐를 먼저 읽는다   그사이 넘어간 티켓이 양쪽에 다 잡힌다.  중복은 6번이 정리한다
DB 를 먼저 읽는다  그사이 넘어간 티켓이 어디에도 안 잡힌다.  구멍이 된다
```

**한쪽으로만 틀릴 수 있으면 안전한 쪽으로 틀리게 한다.**

### 9번이 곧 문을 여는 것이다

**카운터를 마지막에 쓴다.** 그 전까지는 모든 요청이 거절되므로, **요청을 막는 장치를 새로 만들
필요가 없다.** 이벤트의 문이 이미 그 역할을 한다.

**그래서 재건의 안전장치는 원자성이 아니라 순서다.** 넷을 한꺼번에 쓸 필요가 없고, 그것이
재건을 Lua 스크립트로 묶지 않는 이유이기도 하다.

## 3. 키를 각각 어떻게 세우나

**읽는 것은 둘뿐이다.** 발급된 행과 각 인스턴스의 큐다. 네 키가 전부 그 둘에서 나온다.

```
발급된 행   member_coupon 에서 (회원, 순번) 을 전부 읽는다
큐          각 인스턴스가 rebuild:queued 에 올린 (회원, 순번)
```

### `counter` - 둘의 최댓값을 본다

```
counter = max(발급된 행의 MAX(issue_seq),  큐에 있는 순번의 최댓값)
```

**세지 않는다.** 행 개수로 정하면 안 된다.

```
1번부터 10번까지 나갔는데 3번이 안 쓰여 free 로 갔다가 다시 나갔다
  행 개수    10
  최대 순번  10
  둘이 같다

3번이 free 에 담긴 채 이벤트가 계속됐다
  행 개수     9
  최대 순번  10
  개수로 정하면 카운터가 9 가 된다
  free 에 담긴 3번이 먼저 나가고, 그다음 요청이 10번을 받는다
  그 번호는 이미 남이 쓰고 있어 반드시 실패한다
```

**`free` 재사용과 회수가 있는 한 행 개수와 최대 순번은 다를 수 있다.** 그래서 최댓값을 본다.

**`+1` 도 아니다.** 순번 확보는 `INCR` 을 먼저 돌리고 그 결과를 번호로 주므로, **이 키는 다음에
나갈 번호가 아니라 마지막으로 발행한 번호**를 담는다. `+1` 을 하면 한 번호를 통째로 건너뛴다.

**큐도 함께 보는 이유가 있다.** 큐에 있는 티켓은 아직 행이 아니라 DB 최댓값에 안 잡힌다. 그것만
보면 카운터가 뒤처져서 그 번호들이 다시 나간다.

**둘 다 없으면 0 이다.** 이벤트를 여는 준비 단계가 세우는 값과 같아진다.

### `seq` - 큐를 먼저 넣고 행을 나중에 넣는다

```
큐에 있는 회원   "6"      아직 발급 여부를 모른다
행이 있는 회원   "6:1"    발급이 끝났다
```

**같은 회원이 양쪽에 다 잡힐 수 있다.** 큐를 읽은 뒤 DB 를 읽는 사이에 그 티켓이 커밋되면
그렇다. **그때 DB 쪽이 이겨야 한다.**

**확정 표시를 미확정으로 덮으면** 회수가 그 번호를 버려진 것으로 보고 남에게 넘겨, **이미 발급이
끝난 번호가 두 번 나간다.** 그래서 넣는 순서가 큐 다음에 행이다.

### `pending` - 큐에 있던 것만

**"번호는 받았는데 아직 행이 안 됐다" 가 곧 큐의 정의다.** 그래서 큐에 있던 회원을 그대로 옮긴다.
행이 있는 회원은 이미 결판이 났으므로 안 넣는다.

**점수로 쓸 원래 시각은 복원할 수 없다.** 그 시각은 사라진 Redis 에만 있었다. 그래서 재건하는
시점의 시각을 넣고, **그만큼 그 티켓들의 회수가 뒤로 밀린다.**

### `free` - 어디에도 없는 번호

```
1 부터 counter 까지 훑는다
  행에도 없고
  큐에도 없는 번호
-> 전부 구멍이다
```

**행 개수까지가 아니라 최대 순번까지 훑는 것이 요점이다.** 그 둘이 다른 것이 곧 구멍이라,
행 개수까지만 보면 구멍을 하나도 못 찾는다.

**여기 담긴 번호는 다음 요청부터 다시 나간다.** 낮은 번호부터 나가므로 최대 순번과 실제 발급
수의 간격이 다시 좁혀진다.

## 4. 재건이 쓰는 키 둘

**위 넷과 성격이 다르다.** 재건이 도는 동안만 살고 자기 만료로 사라진다.

```
rebuild          재건 락이자 "재건 중" 표시
rebuild:queued   각 인스턴스가 자기 큐를 올려 두는 자리
```

**락 키가 곧 표시라는 것이 요점이다.** 락을 못 잡은 인스턴스는 이 키가 있는 것을 보고 자기 큐를
올린다.

**플러시가 배치마다 한 번씩 그 키를 확인한다** (`CouponSeqRebuildTrigger.checkAfterFlush`).
**이 확인이 없으면 요청을 못 받는 인스턴스가 자기 큐를 영영 안 올린다.** 로드밸런서가 그쪽으로
요청을 안 보내고 있으면 알아챌 길이 없기 때문이다.

**큐를 올리는 동안 그 인스턴스의 플러시가 멈춘다.** 훑는 사이에 같은 티켓이 DB 로 내려가면
재건이 확정된 것을 미확정으로 덮는다.

## 5. 얼마나 걸리나

**이 시간이 곧 장애 시간이다.** 카운터가 서기 전까지 모든 요청이 거절되므로, 재건이 오래 걸리면
Redis 가 돌아온 뒤에도 그만큼 발급이 멈춰 있다.

```
기여 대기    남들이 자기 큐를 올리기를 기다리는 고정 시간   (rebuild-contribute-wait)
읽고 쓰기    DB 를 읽고 네 키를 세우는 시간
```

**대부분이 고정 대기다.** 읽고 쓰는 쪽은 그보다 한 자릿수 작다. 실측값은 `coupon.md` 10장에
있고, `CouponSeqRebuildLatencyIntegrationTest` 가 그 값을 낸다.

**감지 시간은 여기에 안 들어 있다.** 요청이 들어와야 알아채는 구조라, **트래픽이 뜸한 구간에
페일오버가 나면 그만큼 늦어진다.** 요청이 도는 중에는 첫 거절이 곧 신호라 사실상 즉시다.

## 6. 무엇을 보면 되나

**지표 하나가 이 상황을 가리킨다.**

```
coupon_issue_results_total{result="congested-not-prepared"}
```

**평상시 이 값은 0 에 가깝다.** 관리자가 아직 안 연 이벤트를 찌를 때만 나온다. **이벤트가 도는
중에 오르면 Redis 가 카운터를 잃은 것이다.**

`sold-out` 이 오르는 것은 다른 이야기다. 그쪽은 정상적인 소진이다.

**로그가 진행을 알려 준다.**

| 이벤트 | 뜻 |
|---|---|
| `COUPON_SEQ_REBUILD_STARTED` | 락을 잡았고 남들이 큐를 올리기를 기다리는 중이다 |
| `COUPON_SEQ_REBUILT` | 끝났다. 발급 수와 최대 순번과 되살린 구멍 수가 함께 찍힌다 |
| `COUPON_SEQ_REBUILD_SKIPPED` | 기다리는 동안 카운터가 생겼다. 남이 먼저 했다 |
| `COUPON_SEQ_REBUILD_FAILED` | 실패했다. 다음 요청이 다시 띄운다 |

**`FAILED` 가 반복되면 대개 DB 쪽이다.** 재건이 `member_coupon` 을 통째로 읽으므로, DB 가
돌아오면 다음 요청이 알아서 다시 띄운다.

## 7. 재건이 안 불리는 경우가 있다

**못 고치는 것이 아니라 안 불린다.** 이 둘을 갈라야 한다.

```
복구 능력   있다.  DB 와 큐만 보고 다시 계산하므로 Redis 가 얼마나 어긋났든 상관없다
감지 능력   없다.  카운터가 살아 있으면 아무도 이상하다고 말해 주지 않는다
```

**재건은 복구가 아니라 재계산이다.** 3장이 보였듯 네 키를 전부 발급된 행과 큐에서 만든다.
Redis 의 옛 값을 하나도 안 읽으므로, **불리기만 하면 어떤 어긋남이든 그대로 낫는다.**

### 신호가 하나뿐이다

재건을 띄우는 길이 둘인데 **둘 다 카운터가 없을 때만 열린다.**

```
요청이 거절당했다        스크립트가 카운터를 못 찾았다는 뜻이다
플러시가 락 키를 봤다     이미 누가 시작했을 때만 있는 키다.  위의 파생이다
```

그리고 재건 본체도 카운터가 있으면 곧바로 돌아간다.

```java
if (counterExists(couponId)) {
    return;      // 값이 아무리 뒤처져 있어도 "멀쩡하다" 로 본다
}
```

**그래서 카운터가 살아남은 모든 어긋남이 감지 밖이다.**

### 카운터가 살아남는 경우

**복제 지연이 남은 채 승격됐을 때다.** 승격된 복제본이 어느 시점만큼 뒤처져 있고 그 창 안의
쓰기가 사라지는데, **카운터는 이벤트를 열 때 써서 오래됐으므로 살아남는다.** 값만 뒤처진다.

**만료가 걸린 키를 버리는 축출에서도 난다.** 넷 다 만료가 있어 어느 것이든 대상인데,
카운터 아닌 것이 버려지면 문이 안 닫힌다. 다만 이벤트가 도는 중에는 넷 다 매 요청마다
만져져서 그럴 확률이 낮다.

### 무엇이 어긋나느냐에 따라 증상이 다르다

| 어긋난 키 | 무슨 일이 나나 |
|---|---|
| `counter` 가 뒤처짐 | 이미 행이 있는 번호가 다시 나간다. 순번 충돌이 반복된다 |
| `seq` 가 뒤처짐 | 이미 받은 사람이 새 번호를 받는다. 1인 1매 제약에 막혀 번호가 죽는다 |
| `pending` 이 뒤처짐 | 묶인 번호를 못 찾는다. **비어 보이면 소진을 최종으로 판정해 재시도를 막는다** |
| `free` 가 뒤처짐 | 다시 내줄 번호가 증발한다. 그만큼 덜 팔린다 |

**세 번째가 특히 나쁘다.** 스크립트는 `pending` 이 비면 "다시 나올 번호가 없다" 로 보는데,
**사라진 것과 원래 없는 것을 구분하지 못한다.** 회수할 것이 실제로 있는데 재시도를 막는 응답을
준다.

**어느 것도 초과 발급이나 1인 2매를 만들지는 않는다.** DB 제약이 지킨다. **잃는 것은 번호와
그 사람들의 응답이다.**

### 잡으려면 불변식을 재면 된다

```
counter >= MAX(issue_seq)
```

**깨질 수 없는 식이다.** 번호는 Redis 가 내준 뒤에야 DB 행이 되기 때문이다. **깨졌다면 Redis 가
뒤처진 것이고 차이가 곧 뒤처진 양이다.**

**지금 이것을 재는 곳이 없다.** 정합성 검증(`coupon.md` 11장)도 이 식을 안 본다.

**요청 경로에서는 못 잰다.** DB 를 읽어야 하는데 그 자리는 이벤트가 열리는 순간 수만 개가
지나는 곳이다. **주기로 도는 정합성 검증이 맞는 자리이고, 발급 경로에 드는 비용이 0 이다.**

**재고 나서 재건을 띄우는 것도 안전하다.** 재건이 세우는 카운터가 `max(DB 최댓값, 큐 최대)` 라
**뒤처진 값보다 반드시 크거나 같다.** 되돌아가는 일이 없다.

**다만 함부로 띄우면 안 된다.** 재건은 그 이벤트의 플러시를 잠깐 멈추고 큐를 훑는다.
**불변식이 실제로 깨졌을 때만 띄워야 하고, 그래서 감지가 먼저다.**

---

## 8. 이벤트가 이미 마감됐다면

**아무것도 안 해도 된다.** 종료 배치가 마감에서 얼마 뒤에 이벤트를 끄고, 발급 수를 실제 행 수로
맞춘 뒤 네 키를 지운다. 배치가 안 돌아도 **네 키에 걸린 만료가 그물로 받는다.**

**다만 그때 남은 구멍은 회수되지 않는다.** 회수는 소진 상태에서 요청이 올 때만 돌기 때문이다.
그만큼 덜 팔린 것으로 남는다.

## 9. 이 문서가 다루지 않는 것

```
왜 그렇게 설계했나            coupon.md 10장
키가 무엇을 담나              coupon-redis-keys.md
스크립트가 무엇을 묶나         coupon-redis-scripts.md
Redis 가 죽었을 때의 응답      coupon.md 9장
정합성 검증                   coupon.md 11장
```

**장애 한복판에서 손으로 확인하고 조치하는 절차는 이 문서에 없다.** 재건은 사람이 누를 것이
없는 자동 복구다. **7장의 경우도 손으로 고칠 일이 아니라 감지를 붙일 일이라**, 절차가 아니라
남은 과제로 적었다.
